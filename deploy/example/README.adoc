= Self-Hosting Example (Docker)
:toc:
:toc-placement: preamble
:icons: font

A complete, working example for deploying Lapis Cloud with Docker: `lapis-server` (built from the
repo-root `Dockerfile`, with the `lapis-client` production bundle baked in) plus PostgreSQL, both
managed by `docker-compose.yml` in this directory. Copy this whole directory as the starting point
for your own deployment -- fill in `.env` (see `.env.example`), everything else works as-is.

This is a generic, redacted template: every value that would identify a specific real deployment
(hostname, IP, organization name) is a placeholder (`PROD_HOST` etc., see the NOTE block below) or
an env var. It also replaces an earlier bare-JVM-under-systemd + native-PostgreSQL setup (see
"Migrating from a prior bare-JVM + native-PostgreSQL deployment" below) for anyone cutting over an
existing non-Docker install.

[NOTE]
====
This repo is public, so it never carries any real deployment's actual hostname/IP/org identity --
this whole directory is a generic template. Wherever these docs and templates say `PROD_HOST`,
substitute your own real hostname (e.g. what `turn.PROD_HOST` says is really `turn.<your-domain>`);
`${LAPIS_PUBLIC_IP}` is the literal env var from `.env` (see `.env.example`) that carries the real
public IPv4 at runtime. `PROD_HOST` is a prose placeholder only -- it is NOT an
`envsubst`/environment-variable placeholder like `${LAPIS_PUBLIC_IP}`, so a template or doc that
still says it literally (e.g. `wss://video.PROD_HOST`) has not yet been substituted with your real
value for prose purposes. coturn's `realm` (`turnserver.conf.template`) is a genuine `envsubst`
variable, `${LAPIS_TURN_REALM}`, sourced from the gitignored `.env` like every other secret in that
file (see "Video conferencing" below) -- never a prose placeholder hand-edited into the tracked
template, which would risk committing the real value the next time you `git add -A`.

**Real deployment data lives in a separate, private repo.** This project's own maintainer runs
three real instances from this template and keeps their filled-in `.env`/rendered
configs/certs/branding in a private companion repo, never in this one -- see
`lapisproject-dev/Lapis-Cloud-Ops` (private; ask the maintainer for access if you need it) for that
pattern in full, including the server-layout/sync workflow. This is optional: nothing about
deploying from this template requires a second repo, it's simply how the project's own real
instances happen to be organized. A `deploy/production*/` directory populated this way on a live
host is `.gitignore`d in this repo (see `.gitignore`) precisely so it can coexist with a checkout
of this repo without risk of being committed here by accident.

**Scope, explicitly**: this redaction only touches the current tip of the default branch. It does
NOT rewrite git history -- every commit prior to the redaction still has the real values in its
tree, and `git log -p` / `git show <old-commit>:<path>` on this public repo still returns them, as
does anyone's existing local clone made before the redaction landed. Scrubbing that would require
a history rewrite (`git filter-repo` or similar) followed by a force-push and every clone being
discarded and redone -- a decision for the repo owner to make deliberately, not something folded
silently into a routine redaction commit. Until/unless that happens, treat the real historical
values as already public and rotate/replace anything among them that is an actual secret (this
list only ever covered hostnames/IPs/mail relay, never credentials) rather than relying on this
redaction for confidentiality.
====

The host's reverse proxy (Caddy, or a compatible alternative) is unchanged by this move: it still
terminates TLS and reverse-proxies to `127.0.0.1:8080`, which this compose file publishes exactly
the way the old systemd unit did. **Caddy** is the reference/recommended choice (see "Reverse
proxy" below) -- automatic HTTPS with zero manual certbot/vhost bookkeeping, and its
`reverse_proxy` directive detects and proxies WebSocket upgrades on its own, unlike Apache's
`mod_proxy_wstunnel` + `RewriteCond %{HTTP:Upgrade}` dance. Any other reverse proxy capable of
WebSocket-aware HTTP proxying (Apache with `mod_proxy_wstunnel`, nginx) works too -- the app itself
has no Caddy-specific dependency.

== Reverse proxy (Caddy)

The PROD_HOST production instance runs Caddy (migrated from Apache 2026-08-15,
zero functional regression, ~90s of actual downtime during the cutover itself). Install from
Caddy's own apt repository (see https://caddyserver.com/docs/install#debian-ubuntu-raspbian), then
point `/etc/caddy/Caddyfile` at both this app and the video-conferencing signaling subdomain (see
"Video conferencing" below for that second block):

[source,caddyfile]
----
PROD_HOST {
    reverse_proxy 127.0.0.1:8080
    log {
        output file /var/log/caddy/prod-host-access.log
    }
}
----

That's the entire vhost -- no separate HTTP-vs-HTTPS block, no manual `RewriteCond` for the ACME
challenge, no `SSLCertificateFile`/`SSLCertificateKeyFile` paths to track: `systemctl reload caddy`
after any edit (graceful, zero-downtime) picks up new/changed site blocks, obtains and renews
Let's Encrypt certificates for them automatically, and redirects plain HTTP to HTTPS on its own.

**`X-Forwarded-For` still behaves correctly with `AuthTestMode`'s `useLastProxy()` posture** (see
`Application.kt`'s `install(XForwardedHeaders) { useLastProxy() }` and its own KDoc for the
spoofing-prevention reasoning this depends on): Caddy's `reverse_proxy` appends the real client IP
to any existing `X-Forwarded-For` value rather than trusting/replacing it, the same append-only
semantics `mod_proxy_http` already had -- live-verified post-migration by sending a request with a
forged `X-Forwarded-For` header and confirming the app-visible client IP in Caddy's own access log
was still the real one, not the forged one.

**One easy-to-hit trap**: if you ever run `caddy validate`/`caddy adapt` manually as `root` (e.g.
while debugging a Caddyfile edit) with a `log { output file ... }` block already present, it
pre-creates that log file owned by `root` with restrictive `0600` permissions -- the `caddy.service`
systemd unit then fails to start (`permission denied`) because it drops privileges to the `caddy`
user before opening that file for real. Fix: `rm` the stale root-owned log file (under
`/var/log/caddy/`) and let the service recreate it fresh on its next start/reload.

== Prerequisites

* Docker Engine + `docker compose` v2 on the host.
* A `.env` file in this directory (copy `.env.example`, fill in real secrets -- see that file's own
  comments). Never committed; the repo's `.gitignore` already excludes `.env*`.
* **If the host has a hand-written nftables ruleset with a restrictive `forward` chain policy**
  (as PROD_HOST/VPS 4000 does, for example), see "Firewall (nftables) on a hardened host" below --
  Docker will not work correctly without it, and the failure mode is confusing (DNS resolution
  inside containers times out with no obvious firewall-related error).

== Firewall (nftables) on a hardened host

Found live during the VPS 4000 cutover: a hand-written `/etc/nftables.conf` with
`chain forward { type filter hook forward priority 0; policy drop; }` and no rules in it (a
reasonable default-deny posture for a host that, until Docker, forwarded nothing) silently breaks
all Docker container networking -- `docker build` fails with `UnknownHostException` resolving
`services.gradle.org`, and a plain `docker run alpine ping 1.1.1.1` gets 100% packet loss with no
error.

**Root cause**: Docker's own `dockerd`-managed `ip filter FORWARD` chain (iptables-nft) and this
host's own `inet filter forward` chain are BOTH base chains hooked at the same point (`hook
forward`). nftables evaluates every base chain at a given hook; Docker's chain correctly accepts
its own container traffic, but the host's own chain -- empty, `policy drop` -- still drops that
same traffic afterward, since an ACCEPT verdict in one base chain does not skip evaluation of
sibling chains at the same hook.

**Fix**: add explicit accept rules for Docker's interfaces to the host's own `forward` chain --
`ct state established,related accept` plus `iifname`/`oifname` accepts for `docker0` and any
compose-created bridge (`br-*`). Docker's own per-container isolation rules remain the real
security boundary for what that traffic is allowed to do; this only stops the outer chain from
re-blocking what Docker already permitted.

**A second, easy-to-miss trap**: if you reload the ruleset with `nft -f /etc/nftables.conf` and
that file starts with `flush ruleset` (the standard idiom, present in this host's own config), it
deletes Docker's own dynamically-created `ip nat`/`ip filter` tables along with everything else --
`dockerd` does not recreate them automatically. Container traffic keeps failing (now silently
un-NAT'd: outbound packets leave the host's public interface with the container's private source
IP, which upstream networks drop as unroutable/spoofed) until `systemctl restart docker`, which
makes `dockerd` re-establish its own tables. If a `docker build`/`docker run` still can't reach the
internet immediately after an nftables reload, restart Docker before assuming the ruleset itself is
still wrong.

[source,bash]
----
cd deploy/example
cp .env.example .env   # fill in LAPIS_DB_PASSWORD / LAPIS_PUBLIC_BASE_URL
docker compose up -d --build
docker compose logs -f lapis-server
----

== Migrating from a prior bare-JVM + native-PostgreSQL deployment

This is the exact procedure used to cut the VPS 4000 test instance over from the systemd/native-
PostgreSQL setup to this containerized one, kept here as the reproducible runbook for any future host
doing the same migration (a new pilot's own VPS, for example).

**Order matters: stop the old service BEFORE dumping, not after restoring.** An earlier draft of
this runbook dumped the live database first and only stopped the old systemd service after the
restore -- any write landing in the old database during that window (bring-up + restore both take
real time) would silently never make it into the new deployment, and would be permanently lost once
the old install is later removed. The correct order accepts a short downtime window instead of a
silent-data-loss window:

. **Stop (don't yet disable) the old systemd service**, so nothing writes to the native database or
  the document-storage directory while the dump is taken:
+
[source,bash]
----
sudo systemctl stop lapis-cloud.service
----

. **Dump the existing database** from the now-quiesced native PostgreSQL instance:
+
[source,bash]
----
pg_dump -U lapiscloud -h 127.0.0.1 -d lapiscloud -F c -f /tmp/lapiscloud.dump
----

. **Copy the old document-storage directory** (if any documents were ever uploaded -- check first;
  on a fresh pilot this may be empty) into a location the new named volume can be seeded from.
  Since V1.4.11, uploaded travel-expense receipts also live under this same
  `LAPIS_DOCUMENT_STORAGE_ROOT` volume (under a `travel-expenses/` storage-key prefix, no separate
  volume or environment variable) -- this one copy step already carries them along:
+
[source,bash]
----
sudo tar -C /var/lib/lapis-cloud/document-storage -cf /tmp/lapis-document-storage.tar .
----

. **Bring up only the `postgres` service** from this compose file (not `lapis-server` yet):
+
[source,bash]
----
docker compose up -d postgres
----

. **Restore the dump into the container.** `--single-transaction` makes the restore atomic -- any
  error rolls back the whole restore loudly instead of leaving a silently-partial database, which
  plain `pg_restore`'s default per-object-error-tolerant behavior would not catch:
+
[source,bash]
----
docker cp /tmp/lapiscloud.dump lapis-cloud-postgres:/tmp/lapiscloud.dump
docker compose exec postgres pg_restore -U lapiscloud -d lapiscloud --no-owner --role=lapiscloud \
    --single-transaction /tmp/lapiscloud.dump
echo "exit code: $?"   # must be 0 -- do not proceed past a non-zero exit
----
+
Spot-check row counts on a few key tables against the source before proceeding, e.g.
`docker compose exec postgres psql -U lapiscloud -d lapiscloud -c "SELECT count(*) FROM member;"`
compared against the same query run on the old native database before it was stopped.

. **Seed the document-storage volume** from the tarball made above (skip if it was empty):
+
[source,bash]
----
docker run --rm -v lapis-cloud_lapis-document-storage:/target -v /tmp:/backup \
    alpine tar -C /target -xf /backup/lapis-document-storage.tar
----

. **Start the containerized server** and verify:
+
[source,bash]
----
docker compose up -d --build lapis-server
docker compose logs -f lapis-server   # Flyway should report "Successfully validated N migrations"
                                       # against the RESTORED schema, not a fresh baseline
----
+
Then verify end to end in a browser against the real public URL (login with an existing account,
confirm previously-created data -- and any documents -- are visible) before treating the native
PostgreSQL instance as disposable.

. Only once the above is confirmed working: disable the old systemd unit, and the native
  PostgreSQL packages/data directory and any now-fully-replaced prior service installation can be
  removed from the host. This is a separate, deliberately later step -- do not remove the source of
  truth before the migration target has been verified against real traffic.

== Updating an existing deployment

This is the routine used to deploy a new `master` commit to an already-running instance -- unlike
"Migrating from a prior bare-JVM + native-PostgreSQL deployment" above (a one-time cutover), this
runs on **every release**. It applies unchanged to any additional co-located instance (see "Running
more than one instance on the same host" below): substitute that instance's own directory and
Postgres database name in the commands below.

**Order matters: back up before syncing, sync before rebuilding.** A backup taken after the new
code is already live would capture the schema the new code expects, not the one that was actually
running when something went wrong -- it defends against nothing. The order below keeps a restorable
snapshot of the pre-deploy state at every step until the new version is verified working.

CAUTION: **Before the next deploy of the "Redact real infra topology from public repo" wave** on
any instance: that wave edited 16 already-applied Flyway migration files in place
(comment-only changes, real hostnames replaced with placeholders), which changes their checksums.
`DatabaseConfig.kt`'s `migrate()` runs with the default `validateOnMigrate = true` and will refuse
to run at all on any of these three already-migrated instances until `flywayRepair` has run against
each of them -- see the CHANGELOG "Operator notes" entry for this wave for the full mechanism and
the exact command. Run it once per instance before rebuilding that instance below.

. **Back up the database.** Read the Postgres credentials from the running container's own
  environment rather than sourcing `.env` in the shell -- unquoted special characters in a
  `LAPIS_DB_PASSWORD` value can otherwise break a plain `source ./.env`:
+
[source,bash]
----
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
    | gzip > ~/backups/lapiscloud-pre-deploy-$(date +%Y%m%d-%H%M%S).dump.gz
gzip -t ~/backups/lapiscloud-pre-deploy-*.dump.gz   # verify the archive isn't truncated
----

. **Sync the new code**, from a local clone with the target commit checked out, using an explicit
  file list rather than a blanket directory copy. `git ls-files` only lists files this repo
  actually tracks, so this is inherently safe against touching a real instance's own
  `deploy/production*/` directory (real `.env`, rendered configs, certs) -- those live in a
  separate private repo (see "Real deployment data lives in a separate, private repo" below), never
  part of this repo's tracked file list. `$REMOTE_ROOT` is wherever this repo is checked out on
  the host (its name is a per-host choice, not a repo convention -- e.g. `/opt/lapis-cloud-docker`):
+
[source,bash]
----
git ls-files > /tmp/lapis-cloud-files.txt
rsync -a --dry-run -i --files-from=/tmp/lapis-cloud-files.txt . user@host:"$REMOTE_ROOT/"
----
+
Inspect the dry run before the real sync: past releases have found only the expected source-file
changes and harmless permission-denied lines on directories the deploying user doesn't own -- if
something else appears, stop and find out why before syncing for real. **Do not pass `--delete`**
unless a prior `git diff <old-sha> <new-sha> --diff-filter=D --name-only` confirmed the release
actually removes files -- an unscoped `--delete` has deleted a live `.env` before, back when `.env`
still lived inside this repo's own directory tree (2026-08-15 incident, see the infra notes); it
cannot recur now that real deployment data isn't part of this checkout at all, but the general
caution about `--delete` deleting something you didn't mean to remains good practice. Real sync:
+
[source,bash]
----
rsync -a --files-from=/tmp/lapis-cloud-files.txt . user@host:"$REMOTE_ROOT/"
----
+
A `failed to set times` / `Permission denied` pair on `coturn-certs/.gitkeep` is a known, harmless
ownership quirk of that directory (root-owned certs) and not a sign the sync failed elsewhere.

. **Confirm `.env` is unchanged** (the sync above must never touch it -- this is a second,
  independent check, not a substitute for the exclude list itself):
+
[source,bash]
----
md5sum "$REMOTE_ROOT/deploy/example/.env"   # compare against the value from before the sync
----

. **Rebuild and restart only `lapis-server`**, from inside this directory on the host -- `postgres`
  and the other long-running services (LiveKit, coturn, redis, egress) are untouched by a routine
  app release:
+
[source,bash]
----
cd "$REMOTE_ROOT/deploy/example"
docker compose up -d --build lapis-server
----

. **Verify.** Flyway must report the same migration count as before (a routine release rarely adds
  one; if it does, the count goes up by exactly the expected amount, not an unrelated number), and
  the app must actually come up:
+
[source,bash]
----
docker compose logs --tail 300 lapis-server | grep -Ei 'error|exception|responding|validated'
curl -s -o /dev/null -w '%{http_code}\n' https://<the instance's public URL>/
----
+
`Successfully validated N migrations` and `Responding at http://0.0.0.0:8080` in the log, plus a
`200` (or `401` on an instance behind HTTP basic auth, e.g. staging) from `curl`, confirm the new
version is live. A stack trace, a non-2xx/401 status, or a Flyway migration-count mismatch means
stop and investigate -- do not treat "the container started" alone as success.

. **If something goes wrong after this point**, the pre-deploy dump from step 1 is the way back:
stop `lapis-server`, restore the dump into `postgres` (see "Migrating from a prior bare-JVM +
native-PostgreSQL deployment" above for the `pg_restore --single-transaction` invocation and its
row-count spot-check), `git checkout` the prior commit locally and re-sync, then bring
`lapis-server` back up. This has not been needed in practice as of this writing -- every release so
far has verified clean at step 5 -- but the dump exists precisely so this path is available without
improvising it under pressure.

== Video conferencing

Covers Videokonferenzen Wave 1 (live audio/video/screen-share/chat), Wave 2 "Aufzeichnung", and
Wave 3 "Externes Streaming" -- `redis`/`egress` join `livekit`/`coturn` in this stack so recording
and external RTMP streaming (`ConferenceStreamDestinationsScreen`) both work, not just live calls.

Unlike everything else in this stack, LiveKit and coturn need **real public exposure** -- WebRTC
media does not go through the reverse proxy, browsers connect to them directly. `redis` and
`egress` stay compose-internal only (no published ports) -- nothing outside the stack ever talks to
either directly, same posture `deploy/local/docker-compose.yml` already establishes:

* **Signaling** (LiveKit's HTTP/Twirp/WebSocket port, 7880) stays loopback-only and goes through
  the reverse proxy instead, TLS-terminated on its own subdomain (`video.<domain>` by convention --
  needs its own DNS record and cert, separate from the main app's vhost, because LiveKit's own path
  conventions and the app's Ktor routes would collide if reverse-proxied off the same origin).
* **Media** (LiveKit's ICE TCP/UDP ports 7881/7882, and coturn's TURN port 3478 + relay range
  51000-51019) must be reachable directly from the public internet -- published `0.0.0.0`, not
  `127.0.0.1`, and the host firewall must allow inbound traffic to them (this host's own nftables
  ruleset defaults to `policy drop` on everything not explicitly listed -- see that host's
  `/etc/nftables.conf` for the exact accept rules this required).

Setup:

. Get the host's real public IPv4 and put it in `.env` as `LAPIS_PUBLIC_IP`. Generate
  `LAPIS_LIVEKIT_API_SECRET`/`LAPIS_TURN_SECRET` with `openssl rand -base64 32` each (never reuse
  one secret for both, never reuse `deploy/local`'s dev secrets). Set `LAPIS_TURN_REALM` to this
  deployment's real domain (coturn's `realm`, substituted into `turnserver.conf.template` --
  never hand-edit that template file directly, it is tracked and this repo is public). Point
  `LAPIS_LIVEKIT_URL` at the public `wss://` origin the signaling subdomain will be reachable at.
  No SEPARATE secret is needed for `egress` -- it authenticates against LiveKit's own Twirp API
  using the SAME `LAPIS_LIVEKIT_API_KEY`/`LAPIS_LIVEKIT_API_SECRET` pair.
. **Wave 3 "Externes Streaming" specifically** (Wave 1/2 work without this): generate a THIRD,
  separate secret with `openssl rand -base64 32` and put it in `.env` as
  `LAPIS_SECRET_ENCRYPTION_KEY` -- this is the AES-256-GCM key `SecretBox` uses to encrypt stream
  destination RTMP keys at rest, unrelated to the LiveKit/TURN secrets above. `docker-compose.yml`
  already hardcodes `LAPIS_STREAMING_ENABLED: "true"`, so this key is the only Wave-3-specific value
  this step needs from `.env`. Missing/invalid, `ConferenceStreamingService` fails every streaming
  RPC (list/create/start/pause/resume/stop) with a generic conflict error -- easy to miss because
  Wave 1/2 (calls, recording) keep working fine and the failure only surfaces once someone actually
  opens the Stream-Ziele admin screen.
. `./render-secrets.sh` -- renders `livekit.yaml`/`turnserver.conf`/`egress.yaml` from their
  `.template` files using `.env` (requires `envsubst`, package `gettext-base` on Debian). Re-run
  this any time `.env` changes; the rendered files are gitignored.
. Set up the signaling subdomain's DNS record (A/AAAA, same IP as the main app), then add its own
  block to the Caddyfile (see "Reverse proxy" above) -- no `Upgrade: websocket` handling to spell
  out, `reverse_proxy` detects and proxies WebSocket upgrades on its own:
+
[source,caddyfile]
----
video.PROD_HOST {
    reverse_proxy 127.0.0.1:7880
    log {
        output file /var/log/caddy/video-prod-host-access.log
    }
}
----
+
`systemctl reload caddy` picks it up and obtains its own Let's Encrypt certificate, independent of
the main app's vhost.
. Open the firewall for the public media ports listed above, then
  `docker compose up -d livekit coturn redis egress`.
. Verify Wave 1 with a real two-participant call in a browser (see `deploy/local/README.adoc` "Live
  verification results" for the same manual recipe against the dev stack). Verify Wave 2 by
  starting a recording, ending the call, and confirming a composed recording lands in the org's
  document storage once `RecordingPoller` picks it up (poll interval `LAPIS_RECORDING_POLL_INTERVAL_SECONDS`,
  default 10s). Verify Wave 3 with a real external RTMP target, ideally in `GRID`/`SPEAKER` layout
  (not just the Chrome-free `SINGLE_PARTICIPANT` path) -- `GRID`/`SPEAKER` render through Chrome
  inside the `egress` container, which needs the `shm_size: 1gb` setting already on that service in
  `docker-compose.yml` (Docker's 64MB default is not enough for Chrome's renderer; undersized, egress
  aborts with "Start signal not received", found live on this exact deployment 2026-08-15 -- see
  `egress.yaml.template`'s own comment for the full diagnosis, including why this is NOT a
  `template.livekit.io`-reachability issue despite older assumptions in this repo's history). If
  `GRID`/`SPEAKER` still fail after that, `docker exec <egress-container> sh -c 'df -h /dev/shm'`
  first before assuming a template/network problem again.

`ffmpeg` (needed to compose Wave 2's raw per-track recordings into one gallery video) is baked into
the `lapis-server` image itself (see repo-root `Dockerfile`) -- nothing extra to install on the
host. A startup WARN from `ConferenceRecordingConfig` ("ffmpeg probe failed") after a rebuild means
the image wasn't actually rebuilt (stale container still running the pre-Wave-2 image) -- re-run
`docker compose up -d --build lapis-server`.

**Shared `lapis-egress-output` volume needs a self-healing ACL fix, not just a default ACL.**
`egress` (raw-track writer, uid 1001, primary gid 0/root) and `lapis-server` (`ffmpeg` composer,
uid 999/`lapiscloud`, own gid 999 -- NOT a member of `root`) run as different, unrelated users but
both need write access into the same per-recording subdirectory under the shared volume. `egress`
creates each subdirectory itself at recording-start time with mode `0755` (no group-write bit) --
a one-time `chgrp 0 && chmod 2775` on the volume ROOT (as this deployment first did, 2026-08-15)
only fixes directories that already exist at the time it's run; every NEW recording creates a fresh
subdirectory that reverts to the same unwritable-by-`lapiscloud` state, so composition fails again
on the very next recording with `ffmpeg exited with code 243` / `Permission denied` opening
`composed-N.mp4` (found live on this deployment 2026-08-18, three days after the volume-root fix).

A POSIX **default ACL** on the volume root (granting `lapiscloud` `rwx` so every new subdirectory
inherits it) was applied next as the presumed durable fix -- but this recurred a second time,
2026-08-23, five days later, for a structural reason rather than an application mistake: Linux
computes a newly-created object's *effective* ACL mask as the inherited default ACL's mask **ANDed
with the creating process's own requested mode's group bits** (`man 5 acl`, "Interaction between
mode and ACLs"). `egress` requests mode `0755` (group bits `r-x`) for every subdirectory it
creates, so the inherited default `mask::rwx` gets silently capped down to `mask::r-x` on every
single new recording, discarding the write grant even though the named ACL entry itself still says
`rwx` (`getfacl` shows this as `user:lapiscloud:rwx #effective:r-x`). A default ACL therefore
**cannot** be durable here no matter how it's set up -- it is re-derived and re-capped at every
`mkdir`, for as long as `egress` keeps requesting mode `0755`.

The actually-durable fix (installed 2026-08-25) is a systemd timer on the HOST that re-applies the
ACL to the whole volume every 30 seconds, self-healing any newly-capped subdirectory well within
`RecordingPoller`'s own poll interval:
+
[source,bash]
----
sudo apt-get install -y acl   # once per host, if not already present

sudo tee /etc/systemd/system/lapis-egress-acl-fix.service > /dev/null << 'EOF'
[Unit]
Description=Re-apply lapiscloud ACL grant on the shared LiveKit egress-output volume (self-heal for POSIX ACL mask-capping on newly created directories -- see Lapis-Cloud repo deploy/example/README.adoc, "Video conferencing" section, "Shared lapis-egress-output volume" paragraph)

[Service]
Type=oneshot
ExecStart=/usr/bin/setfacl -R -m u:lapiscloud:rwx -m mask::rwx /var/lib/docker/volumes/lapis-cloud_lapis-egress-output/_data/
ExecStart=/usr/bin/setfacl -R -d -m u:lapiscloud:rwx -m mask::rwx /var/lib/docker/volumes/lapis-cloud_lapis-egress-output/_data/

=== TURNS over TLS (port 443) -- restrictive networks / browser privacy settings

**Why**: an operator reported 2026-09-10 that "in some browsers audio and video do not
start at all" -- despite the camera/microphone permission prompt having already been granted. Two
causes reproduce this: a browser's own restrictive WebRTC privacy policy (Brave's Shields /
fingerprinting protection blocks the direct ICE path and can also block plain TURN on
3478/3479 UDP+TCP), or a corporate/hotel network whose outbound firewall only permits port 443.
`turns:` (TURN over TLS) on port 443 looks like ordinary HTTPS on the wire and survives both.

The client already helps on its own, without TURNS: `LiveKitRoomSession.connect` retries
automatically, exactly once, with `RTCConfiguration.iceTransportPolicy = "relay"` whenever the
first connection attempt fails in a way a relay could plausibly fix -- see that method's own KDoc.
This alone resolves the symptom for any participant who can reach the existing plain `turn:`
endpoint (3478/PROD_HOST, 3479/SECOND_HOST) but was blocked only on the *direct* ICE path. It does NOT help a
participant whose network blocks port 3478/3479 outright -- that is exactly the gap TURNS on 443
closes.

[NOTE]
====
**Live on both instances since 2026-09-12.** `LAPIS_TURNS_URLS` is set in both `.env` files
(`turns:turn.PROD_HOST:443?transport=tcp` / `turns:turn.SECOND_HOST:443?transport=tcp`).
If `LAPIS_TURNS_URLS` is ever unset again, this deployment falls back to exactly the pre-rollout
behavior: `ConferenceConfig` simply carries no `turns:` entry in any minted TURN credential -- see
that class's own KDoc, same "O4" optional-env posture as every other feature-flag-shaped variable
in this codebase.
====

**Rollout mechanism, as actually built (2026-09-12)**: Caddy already owned port 443 on this host
(the reverse-proxied app vhosts, see "Reverse proxy" above), so coturn could not bind 443 directly.
The originally planned `caddy-l4` layer4 plugin (would have needed a full Caddy rebuild via
`xcaddy`, replacing the stock apt-managed binary) was replaced with **`sniproxy`**
(`apt install sniproxy`, a small dedicated SNI-based TCP router that never terminates TLS itself)
sitting in front of the real public `:443`:

* Caddy no longer binds `:443` at all -- every site address in `/etc/caddy/Caddyfile` now carries
  an explicit `:8443` (e.g. `PROD_HOST:8443 { ... }`). **Caddy's `bind` directive
  cannot set a custom port** (host only, confirmed against Caddy's own docs the hard way -- an
  earlier attempt using `bind 127.0.0.1:8443` silently ignored the port and left Caddy on the
  default `:443`, which then collided with sniproxy's own bind attempt). Because an explicit
  non-default port on a site address suppresses Caddy's *automatic* HTTP->HTTPS redirect, six
  matching `http://<name> { redir https://{host}{uri} permanent }` blocks provide that redirect
  explicitly instead -- the `{host}` template variable carries no port, so the `Location` header a
  browser receives still says `https://PROD_HOST/...`, exactly the port-less URL
  that is publicly reachable via sniproxy. Port 80 itself (ACME HTTP-01 challenges and these
  redirects) is untouched throughout.
* `sniproxy` (`/etc/sniproxy.conf`, a systemd service, `enabled` so it survives reboots) owns the
  real public `:443`. Its config is a `listener 0.0.0.0:443 { protocol tls; table https_hosts;
  fallback 127.0.0.1:8443 }` plus a `table https_hosts` with one regex-anchored entry per `turn.*`
  name, each pointing at that instance's coturn TLS port (`127.0.0.1:5350` PROD_HOST / `127.0.0.1:5351`
  SECOND_HOST). Every other SNI (the four app vhosts) falls through to the `fallback`, i.e. Caddy on
  `127.0.0.1:8443`. Plain TCP passthrough only -- sniproxy reads the ClientHello's SNI and forwards
  the raw bytes verbatim, so Caddy and coturn each keep terminating their own TLS exactly as
  before; sniproxy itself never sees plaintext.
* Two DNS A records were added (`turn.PROD_HOST` / `turn.SECOND_HOST`,
  both -> this host's IP) -- the two names must differ even though the IP is identical, because SNI
  is the only signal sniproxy has to tell the two instances' TURNS traffic apart on the shared 443
  port.
* Each `turn.*` name gets its own real Let's Encrypt certificate, obtained (and auto-renewed) by
  **Caddy itself**, via two minimal, cert-only Caddyfile vhosts (`turn.PROD_HOST:8443
  { respond "Not a website -- TURNS relay endpoint only." 404 }` and the second instance's counterpart) -- these
  are never actually reached through sniproxy in normal operation (sniproxy diverts their SNI
  straight to coturn), their only purpose is to make Caddy's ACME client manage the certificate.
  `/usr/local/sbin/sync-turn-certs.sh` (installed on the host, NOT part of this repo) copies the
  resulting cert/key pair out of Caddy's own certificate store
  (`/var/lib/caddy/.local/share/caddy/certificates/.../<name>/`) into each instance's
  `./coturn-certs/` directory (mounted read-only into the `coturn` container at
  `/etc/coturn/certs/`, `0640`/group-`nogroup`-readable key so the container's `uid=65534(nobody)
  gid=65533(nogroup)` process can read it without the key being world-readable), and restarts that
  instance's `coturn` container ONLY when the certificate content actually changed (sha256/`cmp`
  compare -- avoids dropping in-progress TURN relay sessions on every check). A
  `sync-turn-certs.timer` systemd timer (`enabled`, daily, `RandomizedDelaySec=1h`) runs it
  automatically; Caddy renews roughly 30 days before expiry, so a daily check comfortably keeps up.
* coturn's own TLS config directive names are **`cert`/`pkey`**, NOT `cert-file`/`pkey-file` -- an
  easy first guess to get wrong (this wave did, initially): the wrong names produce a `WARNING Bad
  configuration format: cert-file` log line and coturn silently refuses to start the TLS listener
  at all, while every other listener (plain `turn:`) keeps working normally, so the failure is easy
  to miss without checking `docker logs <coturn container>` after any config change here.

Note TURNS is TCP-only; none of this touches QUIC/HTTP-3 on `443/UDP`, which stays exclusively the
app vhosts' own concern (unaffected either way, since sniproxy's listener above is TCP-only too).

**Operational workaround for any remaining case** (a network that blocks port 443 itself entirely,
or a board member on an old client build before the relay-fallback shipped): in Brave, click the
lion-head Shields icon in the address bar and lower the protection level for this one site, or go
to `brave://settings/shields` and relax the fingerprinting protection setting there, then reload
the page.

== Public read path (SEO)

Welle V1.1.3 "Öffentlicher SEO-Lesepfad" added the first unauthenticated HTML read path this app
serves: `GET /s` (public timeline), `GET /s/{id}` (a single public post plus its thread),
`GET /sitemap.xml` (+ shards once the URL count exceeds 45,000), `GET /robots.txt`. Nothing here
needs a dedicated Caddyfile block -- it is served from the same `127.0.0.1:8080` upstream as
everything else, through the same `reverse_proxy` directive already shown above.

**`LAPIS_PUBLIC_BASE_URL` must point at the real public HTTPS origin before this path is exposed to
the internet.** Every `canonical`/`og:url` link this path emits, and every `<loc>` entry in
`/sitemap.xml`, is built from this env var -- if it is left at its `http://localhost:8080` default
(see `FederationConfig.publicBaseUrl` KDoc), a search engine that crawls `/sitemap.xml` will index
`localhost` URLs. This env var already had to be set correctly for Federation to work at all (see
"Quick start" above); this wave makes it SEO-relevant too, not just Federation-relevant.

**Caddy is free to cache these responses** -- every `200` response under `/s`/`/s/{id}` carries
`Cache-Control: public, max-age=300, stale-while-revalidate=3600`; `/s/assets/style.css` carries
`max-age=86400, immutable`; `/sitemap.xml`/`/robots.txt` carry `max-age=3600`/`max-age=86400`. No
extra Caddyfile directive is required for this -- `reverse_proxy` alone does not cache responses on
its own, so nothing changes unless a caching layer (a CDN in front of Caddy, or Caddy's own
`cache-handler` plugin if that is ever added) is introduced later; if one is, be aware that after a
legal removal or a DSGVO tombstone the affected page can remain cached and publicly reachable for up
to five minutes (`max-age=300`) after the underlying row changes -- accepted and deliberately short,
see the implementation plan's own § 5.2 for the reasoning; whoever needs faster propagation purges
the cache layer manually.

**Submit the sitemap to search engines once this path is live**: Google Search Console and Bing
Webmaster Tools both accept `https://<LAPIS_PUBLIC_BASE_URL>/sitemap.xml` directly as a sitemap
submission -- `robots.txt` also advertises it via its `Sitemap:` line, so a well-behaved crawler
discovers it on its own, but an explicit submission speeds up first indexing.

== Client version hint (V1.4.20)

Welle V1.4.20 "Client-Hinweis: Neue Version verfügbar" adds one public, unauthenticated route and
changes the caching of the app shell -- relevant for anyone putting a caching reverse proxy or CDN in
front of Caddy:

* `GET /api/client-version` returns the server's build id as plain text with `Cache-Control:
  no-store`, rate-limited to 120 requests/minute per IP. Open tabs poll it (~every 5 minutes) to
  detect a newer deploy. **Do not cache it** -- a cached answer would hide a deploy from every open
  tab.
* `GET /app` and `GET /index.html` now carry `Cache-Control: no-cache` (revalidate on every load), so
  a reload after a deploy picks up the new bundle instead of a heuristically cached shell. A caching
  layer must honour this and must not override it with its own TTL.

* A new client bundle only takes effect for the hint after a **restart of the server process**
  (the build id is computed once). Bind-mounting a client directory and swapping the bundle without a
  restart would leave open tabs uninformed. The hint also assumes **one instance**; behind a load
  balancer with differing bundles it would show a permanent false hint.

See `docs/architecture/client-version-check.adoc` for the full design.

== Price-Oracle: Gold anchor (optional)

`LAPIS_ORACLE_GOLDAPI_KEY`, `LAPIS_ORACLE_METALPRICEAPI_KEY`, `LAPIS_ORACLE_ALPHAVANTAGE_KEY` are
**all optional**. Only needed if this deployment's `price_oracle_config.anchor_asset` is switched
to `GOLD_XAU` (an ADMIN action via `updateOracleConfig`, default remains `BITCOIN_BTC`). A
gold-anchored deployment requires **at least two of the three** keys -- `updateOracleConfig` rejects
the anchor switch otherwise, naming the missing env vars.

**Configuring all three keys is the recommended security baseline, not just an outage-avoidance
nicety.** With exactly 2 sources configured, the quorum floor is met and gold works normally, but the
outlier-rejection check is mathematically unable to discriminate a single bad source from a good one
at n=2 (the median of two values is always their average, so both deviate from it identically -- see
`network.lapis.cloud.shared.domain.AnchorPolicy.quorumFloor` KDoc for the exact math). Concretely: a
single compromised or malfunctioning source among exactly 2 can still skew the reported gold price by
roughly 3% (at the seeded default `outlierThresholdBps`) while the quote continues to report `LIVE`.
This holds for **any** 2-of-3 pairing, including the "safe-looking" `goldapi + metalpriceapi` pair
below -- 2 sources buys the same one-source-may-fail *availability* redundancy the always-on Bitcoin
source set already has (a single provider outage does not halt donation conversion), but **not**
manipulation/outlier resilience. Configure all three keys if operationally feasible; treat a 2-key
deployment as availability-only, not tamper-resistant.

If `LAPIS_ORACLE_ALPHAVANTAGE_KEY` is configured, that source also reaches `www.ecb.europa.eu` for
its USD-to-donation-currency conversion leg (the free ECB daily reference-rate feed, keyless) --
relevant to any egress firewall rules. The FIAT anchor's own source (`EcbFiatPriceSource`) reaches
the same host and needs no key at all.

Get free API keys: https://www.goldapi.io (Sandbox tier, no card), https://metalpriceapi.com (free
tier), https://www.alphavantage.co/support/#api-key (free signup, no card). See
`network.lapis.cloud.server.economy.oracle.GoldPriceSources` KDoc for the exact free-tier request
budget this deployment's 12h refresh interval stays within.

**Worst-case fan-out rate under repeated config saves** (Security-Audit-Runde 2 / S9): the 12h
refresh interval is the normal-operation cadence (`<=2` real fan-outs/day/key), not a hard ceiling
on its own -- a rapid sequence of genuinely different `updateOracleConfig` changes (an ADMIN tuning
thresholds in direct response to a bad quote, or a hijacked-session save-loop) can each force a fresh
real fan-out. `PriceOracleOrchestrator` enforces an additional, config-invalidation-proof hard floor
derived from the anchor's own refresh interval (currently `refreshIntervalSeconds / 3` = 4h for
GOLD_XAU/FIAT), capping this worst case at **at most 6 real fan-outs/day/key** -- a 3x multiple of
the normal-operation budget, not an unbounded rate. See
`network.lapis.cloud.server.economy.oracle.PriceOracleOrchestrator.lastFanoutAt` KDoc for the full
derivation.

== E-Mail-Versand (SMTP, optional)

`LAPIS_SMTP_HOST`, `LAPIS_SMTP_PORT`, `LAPIS_SMTP_USERNAME`, `LAPIS_SMTP_PASSWORD`,
`LAPIS_SMTP_FROM_ADDRESS`, `LAPIS_SMTP_FROM_NAME`, `LAPIS_SMTP_REPLY_TO` (optional) -- **all
optional, but ALL-OR-NOTHING for the five required ones**
(`HOST`/`USERNAME`/`PASSWORD`/`FROM_ADDRESS`/`FROM_NAME`). Without any `LAPIS_SMTP_*` variable set,
this deployment sends no real mail at all -- password-reset and FRIEND-email-verification messages
are only logged (`NoOpMailTransport`), exactly as before this feature existed. With a **partial**
configuration (some but not all five required variables set), the server refuses to start
(`IllegalStateException`, fail-fast) -- see `network.lapis.cloud.server.mail.SmtpStartupCheck` KDoc
"Fail-fast or only loud" for why a half configuration is treated as an operator error rather than a
legitimate intermediate state.

**`LAPIS_SMTP_FROM_NAME` is the only sender identity a recipient ever sees** (V1.2.3 Design-Review):
`network.lapis.cloud.server.mail.MailTemplates` no longer hardcodes a product name, so an unset
`LAPIS_SMTP_FROM_NAME` is now a fail-fast startup error rather than a mail that quietly says "Lapis
Cloud" to people who have never heard that name (this codebase is designed to run multiple,
separately white-labeled instances -- see `network.lapis.cloud.server.mail.MailBranding` KDoc).

**Deploy ordering for existing deployments with SMTP already configured (breaking change)**: set
`LAPIS_SMTP_FROM_NAME` in the deployment's `.env` file *before* deploying this version -- e.g.
`LAPIS_SMTP_FROM_NAME=Partei der Vernunft`. Deploying with SMTP configured but no
`LAPIS_SMTP_FROM_NAME` set crash-loops the container (`SmtpStartupCheck` throws
`IllegalStateException` on every start). While editing `.env`, also remove any leftover
`LAPIS_SMTP_STARTTLS` line -- that variable no longer exists and is silently ignored, but keeping
`.env` clean avoids confusion later. Setting `LAPIS_SMTP_REPLY_TO` at the same time is optional.
After deploying, verify the container was actually recreated (image digest/`Created` timestamp, not
just a green health check) and check the startup log for a line naming the new `fromName=`. A first
live test -- one password-reset request to an address you control -- confirms sender name, dash
character (`–`, not `--`) in the subject, a footer, and no leftover "Lapis Cloud" in the body.

**Port 465 = implicit SSL/TLS, NOT STARTTLS.** `LAPIS_SMTP_PORT=587` or `25` switches to STARTTLS,
which is then *required* (`mail.smtp.starttls.required=true`) -- there is no plaintext fallback,
ever. Transport security follows the port alone; there is deliberately no override variable
(V1.2.3 Design-Review removed `LAPIS_SMTP_STARTTLS` before this feature's first release -- one
fewer knob is one fewer way to accidentally weaken transport security).

**`LAPIS_SMTP_REPLY_TO`** (optional): when set, every outgoing mail carries a `Reply-To` header on
this address and the mail footer invites a reply. When unset, the footer instead points recipients
at `LAPIS_PUBLIC_BASE_URL` -- no mail ever leaves without some way back to the operator.

**Egress firewall**: the server needs outbound access to the configured SMTP host/port (e.g.
`mail.example.invalid:465` for a typical hosted-mailbox provider).

**The From address must match the authenticated mailbox** (`LAPIS_SMTP_FROM_ADDRESS` ==
`LAPIS_SMTP_USERNAME`'s mailbox), or the relay rejects the message with a 5xx error.

**SPF/DKIM/DMARC** for the sending domain must authorize the relay's outbound mail servers, or
messages land in recipients' spam folders even though the SMTP transaction itself succeeds. This is
a DNS/deployment concern, not something this codebase can verify.

**`LAPIS_PUBLIC_BASE_URL` must be correct** before enabling SMTP -- every link
`network.lapis.cloud.server.mail.MailTemplates` builds is `$LAPIS_PUBLIC_BASE_URL/app#/...` (Welle
V1.4.6: `/app`, since the member SPA moved off `/` -- see `docs/architecture/public-landing.adoc`). A
deployment with SMTP configured but a stale/default `LAPIS_PUBLIC_BASE_URL` sends real mail
containing unusable `http://localhost:8080` links -- `SmtpStartupCheck` logs a `WARN` for exactly
this case, but only a WARN, not a startup failure (an operator can legitimately be mid-migration).

`LAPIS_FRIEND_REQUIRE_EMAIL_VERIFICATION` (see `network.lapis.cloud.server.rpc.FriendRegistrationConfig`
KDoc) stays on its default `false` regardless of whether SMTP is configured -- activating hard
enforcement is a separate, later operational decision, not automatically flipped by this wave.

== AI assistance (optional, default off)

`LAPIS_AI_*` -- **not passed through by the compose files, on purpose.** Statute Q&A ("Fragen zur
Satzung") sends a member's question **and the retrieved document excerpts to an external AI
provider**. Enabling it is a data-protection decision of the operator, not a technical default.
Architecture: xref:../../docs/architecture/ai-assistant.adoc[ai-assistant.adoc]; variable reference:
`README.adoc` in the repository root, section "AI assistance".

To enable it, add the variables to the service's `environment:` block yourself (copy-paste template;
the `${...:-}` form keeps the value in `.env`, out of the compose file):

[source,yaml]
----
    environment:
      # ... existing entries ...
      LAPIS_AI_ENABLED: "${LAPIS_AI_ENABLED:-}"
      LAPIS_AI_PROVIDER: "${LAPIS_AI_PROVIDER:-}"            # anthropic | openai_compatible
      LAPIS_AI_MODEL: "${LAPIS_AI_MODEL:-}"
      LAPIS_AI_API_KEY: "${LAPIS_AI_API_KEY:-}"
      LAPIS_AI_BASE_URL: "${LAPIS_AI_BASE_URL:-}"            # required for openai_compatible
----

The feature is on only when `LAPIS_AI_ENABLED` is exactly `true` **and** provider, model, API key and
(where required) base URL are all present. A partial or invalid configuration means "off": the server
still starts, and the startup log names the offending variables (never their values). With the
feature off, no provider client is created and the RPC service is not registered.

**Provider choice is yours.** The abstraction supports the Anthropic Messages API and any
OpenAI-compatible endpoint (OpenAI, Mistral, OpenRouter, a self-hosted gateway, Ollama). For a
EU-hosted profile use an EU provider such as Mistral through `openai_compatible`; for a fully local
setup point `LAPIS_AI_BASE_URL` at Ollama's loopback address and set
`LAPIS_AI_ALLOW_PLAINTEXT_BASE_URL=true` (loopback only; a private LAN address is rejected). Any
other HTTPS host works when configured explicitly; it draws an INFO hint in the startup log.

**Operator duties before enabling it (GDPR):**

* **Processing agreement (Art. 28 GDPR)** with the provider -- the question and the retrieved
  excerpts of released documents leave your server. Record it in the processing-agreement register
  of the DSGVO-compliance screen.
* Check that the provider **does not train on API data** and where it processes it (EU hosting).
* **Member opt-in is the precondition**: every member decides for themselves on the screen; there is
  no server-wide consent. The former `LAPIS_AI_MEMBER_OPT_IN_DEFAULT` switch was removed (it produced
  "consent" without a consent record); setting it has no effect and is only reported in the startup log.
* Mention the processing in your privacy policy. `/datenschutz` renders a paragraph on it
  automatically, but only when the feature is on -- review that text and your own additions.
* Only documents at access level `PUBLIC_MEMBERS` can be released to the knowledge base by BOARD/ADMIN
  (the switch is in the document list). Do not release documents containing third-party personal data.
* The redaction of the question is simple pattern matching (e-mail, IBAN, telephone, long numbers);
  names and free text are **not** detected -- the consent text tells members not to write personal
  data into a question.
* The usage log (`ai_call_audit`) keeps only hashes and counters, never clear text.

**Before the first productive use**, verify the PostgreSQL full-text path once against the real
instance: CI has no PostgreSQL container, so it only checks the SQL shape. Run
`PostgresFullTextRetrieverLiveTest` with `LAPIS_TEST_POSTGRES_URL` pointing at a migrated, disposable
database (never the production database). The GIN index is created automatically at startup when the
feature is on and `LAPIS_DB_URL` is PostgreSQL; a failure there is only logged, retrieval stays
correct without it.

=== Environment variables

`LAPIS_KEYCLOAK_*` -- **not passed through by the compose files, on purpose** (same deliberate
opt-in as `LAPIS_AI_*` above). `lapis-server`'s `environment:` list in the shipped
`docker-compose.yml` names every variable it forwards explicitly and has no `env_file:`, so a
`LAPIS_KEYCLOAK_*` line in `.env` alone never reaches the container: `KeycloakConfig.load()` sees
nothing and the instance silently stays in password mode. This is intentional -- the login mode is
security-critical (it decides who can get in and how), and an ambient `.env` line must not be able to
flip it by accident.

To enable Keycloak, add the variables to the service's `environment:` block of **your own** compose
file yourself (copy-paste template; the `${...}` form keeps the values in `.env`, out of the compose
file). Note that the three boolean switches which default to `true` use `:-true` rather than a plain
`:-` -- see the WARNING below the snippet for why:

[source,yaml]
----
    environment:
      # ... existing entries ...
      LAPIS_KEYCLOAK_ENABLED: "${LAPIS_KEYCLOAK_ENABLED:-}"
      LAPIS_KEYCLOAK_ISSUER_URL: "${LAPIS_KEYCLOAK_ISSUER_URL:-}"
      LAPIS_KEYCLOAK_CLIENT_ID: "${LAPIS_KEYCLOAK_CLIENT_ID:-}"
      LAPIS_KEYCLOAK_CLIENT_SECRET: "${LAPIS_KEYCLOAK_CLIENT_SECRET:-}"
      LAPIS_KEYCLOAK_SCOPES: "${LAPIS_KEYCLOAK_SCOPES:-}"
      LAPIS_KEYCLOAK_REQUIRE_VERIFIED_EMAIL: "${LAPIS_KEYCLOAK_REQUIRE_VERIFIED_EMAIL:-true}"
      LAPIS_KEYCLOAK_EMERGENCY_ADMIN_LOGIN_ENABLED: "${LAPIS_KEYCLOAK_EMERGENCY_ADMIN_LOGIN_ENABLED:-true}"
      LAPIS_KEYCLOAK_ALLOW_PRIVATE_ISSUER_HOST: "${LAPIS_KEYCLOAK_ALLOW_PRIVATE_ISSUER_HOST:-}"
      LAPIS_KEYCLOAK_ALLOW_PLAINTEXT_ISSUER_URL: "${LAPIS_KEYCLOAK_ALLOW_PLAINTEXT_ISSUER_URL:-}"
      LAPIS_KEYCLOAK_RP_INITIATED_LOGOUT: "${LAPIS_KEYCLOAK_RP_INITIATED_LOGOUT:-true}"
      LAPIS_KEYCLOAK_DISCOVERY_CACHE_SECONDS: "${LAPIS_KEYCLOAK_DISCOVERY_CACHE_SECONDS:-}"
      LAPIS_KEYCLOAK_JWKS_CACHE_SECONDS: "${LAPIS_KEYCLOAK_JWKS_CACHE_SECONDS:-}"
----

WARNING: With a plain `${VAR:-}`, a variable you leave unset (or blank) in `.env` reaches the container
as an **empty string**, not as "unset". For the three boolean switches that default to `true`
(`REQUIRE_VERIFIED_EMAIL`, `EMERGENCY_ADMIN_LOGIN_ENABLED`, `RP_INITIATED_LOGOUT`) an empty value would
mean `false`, because `KeycloakConfig` only applies its own default when the variable is genuinely
unset -- in particular, an empty `LAPIS_KEYCLOAK_REQUIRE_VERIFIED_EMAIL` would silently switch off
verified-email enforcement. The snippet above therefore supplies the intended `true` default itself
(`:-true`) for exactly these three. Docker Compose applies `:-true` when the variable is **unset or
blank**, so both an absent and an empty `.env` entry stay safe; only an explicit non-`true` value
(for example `false`) turns a switch off. Keep the `:-true` if you edit the block; do not "simplify" it
back to `:-`. (Verified against `docker compose config`: unset and `VAR=` both resolve to `true`,
`VAR=false` resolves to `false`.)

All `LAPIS_KEYCLOAK_*` variables (`network.lapis.cloud.server.keycloak.KeycloakConfig`):

[cols="2,1,3"]
|===
| Variable | Default | Purpose

| `LAPIS_KEYCLOAK_ENABLED`
| `false`
| Activates the feature when the value, trimmed and compared case-insensitively, is `true` (so
  `True` also activates it). With anything else (unset, `false`, any other value), every
  `/auth/keycloak/*` route responds `404` and nothing else below is even read.

| `LAPIS_KEYCLOAK_ISSUER_URL`
| *(required when enabled)*
| The Keycloak realm's issuer URL, e.g. `\https://sso.example.org/realms/myorg`. **Must equal the
  `issuer` value in Keycloak's own discovery document (`<issuer>/.well-known/openid-configuration`)
  byte for byte** -- a document whose `issuer` differs is rejected and never cached, so every login
  fails as "login service not reachable". That value follows Keycloak's own hostname setting, so
  check the discovery document rather than guessing. The URL must be reachable by **both** the
  members' browsers and the Lapis server (see `LAPIS_KEYCLOAK_ALLOW_PRIVATE_ISSUER_HOST`). HTTPS
  always allowed; plain HTTP only for a loopback host and only with
  `LAPIS_KEYCLOAK_ALLOW_PLAINTEXT_ISSUER_URL=true`. No query string, fragment, or userinfo
  allowed; max 200 characters; a trailing slash is normalized away.

| `LAPIS_KEYCLOAK_CLIENT_ID`
| *(required when enabled)*
| The confidential client's client ID, as registered in Keycloak (see "Keycloak client
  configuration" below).

| `LAPIS_KEYCLOAK_CLIENT_SECRET`
| *(required when enabled)*
| The confidential client's secret. Never logged, not even redacted-length; `KeycloakConfig
  .toString()` always prints `<redacted>` or `unset`, never a hint of the real value.

| `LAPIS_KEYCLOAK_SCOPES`
| `openid email profile`
| Space-separated OIDC scopes sent on `/start`. `openid` is force-added if your own value omits
  it.

| `LAPIS_KEYCLOAK_REQUIRE_VERIFIED_EMAIL`
| `true`
| When `true`, an unverified Keycloak email can never auto-link to a local member (which also
  means the member's Keycloak user needs **Email verified = On**, see "Keycloak client
  configuration"). When `false`, ordinary members can still auto-link on an unverified email, but
  `BOARD`/`TREASURER`/`ADMIN` members are **always** protected regardless of this setting (see
  "Account-linking decision table" in the architecture doc). Only an *unset* variable gives the
  default `true`; any set value other than `true` (`1`, `yes`, or an empty `VAR=`) means `false`
  *as far as the application itself is concerned* -- the compose snippet above supplies `:-true`
  for this variable, so an absent or blank `.env` entry still reaches the application as `true`.

| `LAPIS_KEYCLOAK_EMERGENCY_ADMIN_LOGIN_ENABLED`
| `true`
| Keeps the classic email/password login reachable (collapsed disclosure on the login screen) as
  a fallback if Keycloak becomes unreachable. **Enforced server-side:** in Keycloak mode
  `POST /api/auth/login` accepts only `ADMIN` accounts; every other role is rejected with the usual
  generic failure. With this set to `false`, the local login is rejected for **all** accounts,
  admins included. Same parsing as above (the compose snippet's `:-true` keeps an absent or blank
  `.env` entry at `true`). See "Verify the emergency-admin path" below before ever setting this to
  `false`.

| `LAPIS_KEYCLOAK_ALLOW_PRIVATE_ISSUER_HOST`
| `false`
| Only relevant when `LAPIS_KEYCLOAK_ISSUER_URL` uses a **literal private IP address**
  (an IPv4 address in an RFC 1918, link-local or CGNAT range, or an IPv6 ULA address, written directly
  in the URL instead of a hostname): such a URL is rejected
  unless this is `true`. A hostname (e.g. `keycloak` or `sso.example.org`) is never classified as
  private, so the flag does nothing for hostnames. It does **not** make a Keycloak reachable only
  inside a Docker Compose network usable: the browser is redirected to Keycloak's
  `authorization_endpoint`, which is forced onto the issuer's own scheme/host/port, so the members'
  browsers must be able to reach the issuer URL as well. Plain HTTP to a non-loopback host is
  rejected regardless of this flag.

| `LAPIS_KEYCLOAK_ALLOW_PLAINTEXT_ISSUER_URL`
| `false`
| Set `true` only to allow plain `http://` against a loopback Keycloak (local/dev use). Has no
  effect on a non-loopback host -- plaintext against a remote host is never allowed regardless of
  this flag.

| `LAPIS_KEYCLOAK_RP_INITIATED_LOGOUT`
| `true`
| Publishes an RP-initiated end-session URL via `POST /auth/keycloak/logout-redirect` when
  Keycloak's discovery document advertises one (`404` when this is `false`). **Not yet wired into
  the app's own logout button**, so logging out of Lapis Cloud does not end the Keycloak SSO session
  -- see "Known limitations" in the architecture doc. Same boolean parsing and the same `:-true`
  compose default as `REQUIRE_VERIFIED_EMAIL`.

| `LAPIS_KEYCLOAK_DISCOVERY_CACHE_SECONDS`
| `3600`
| TTL for the cached `.well-known/openid-configuration` document. Range `60..86400`; an
  out-of-range or unparseable value silently falls back to the default (the variable is only
  reported by name when the configuration is *also* unusable and startup fails fast, so a typo here
  is not visible in the log).

| `LAPIS_KEYCLOAK_JWKS_CACHE_SECONDS`
| `300`
| TTL for the cached JWKS (signing-key) document. Same range and fallback behavior as the
  discovery-cache variable above.
|===

**All-or-nothing for the three required variables** (`ISSUER_URL`/`CLIENT_ID`/`CLIENT_SECRET`):
with `LAPIS_KEYCLOAK_ENABLED=true` but any of the three missing or invalid, the server refuses to
start (`IllegalStateException`, fail-fast) and the startup log names exactly which variables were
rejected -- never their values. This mirrors the SMTP configuration's own fail-fast posture above:
a half-configured, security-relevant feature is treated as an operator error, never a silent
partial state.

=== Keycloak client configuration

Set up a dedicated client in the Keycloak admin console for this Lapis Cloud deployment, matching
`LAPIS_KEYCLOAK_CLIENT_ID`/`LAPIS_KEYCLOAK_CLIENT_SECRET` above:

* **Client authentication: On** (confidential client, not public) -- a client secret is required;
  this feature never uses a public client / implicit flow.
* **Standard flow (Authorization Code): On.**
* **Direct access grants (Resource Owner Password): Off** -- this feature never sends member
  credentials directly to Keycloak's token endpoint, only the browser-redirect Authorization Code
  flow.
* **PKCE Code Challenge Method: `S256`, required.** Lapis Cloud always sends
  `code_challenge_method=S256`; if the client requires PKCE, set it to `S256`, not `plain`.
* **Valid redirect URIs**: exactly `<LAPIS_PUBLIC_BASE_URL>/auth/keycloak/callback` (e.g.
  `\https://cloud.example.org/auth/keycloak/callback`). `LAPIS_PUBLIC_BASE_URL` must already be
  correct for this deployment before enabling Keycloak, same precondition the SMTP section above
  already documents for its own link-building.
* **Valid post-logout redirect URIs** (if using RP-initiated logout): `<LAPIS_PUBLIC_BASE_URL>/`.
* **Scopes**: at minimum `openid`, `email`, `profile` (matching `LAPIS_KEYCLOAK_SCOPES`'s
  default) -- `email` and `email_verified` claims on the ID token are required for account
  linking to work at all.
* **Email verified = On for every member's Keycloak user.** With the default
  `LAPIS_KEYCLOAK_REQUIRE_VERIFIED_EMAIL=true`, automatic linking only works for users whose email is
  verified. Users created or imported by an admin default to *Off*, and a missing `email_verified`
  claim counts as `false` -- so every first login of such a user is rejected as `EMAIL_NOT_VERIFIED`.
  Set it in Keycloak (user detail, or an import/required-action flow) before the cutover.
* **ID tokens must be signed with RS256** (the realm's default). Lapis Cloud only reads RSA keys from
  the JWKS document; if the realm's default signature algorithm is changed to something else (e.g.
  ES256), no key is found and every login fails as `UNKNOWN_KID`.

=== Verify the emergency-admin path before switching

Before enabling `LAPIS_KEYCLOAK_ENABLED`, confirm at least one real `ADMIN` account has a
known-good internal password (test a login against `/api/auth/login` directly, or via the
collapsed "Interner Notfall-Zugang für Administratoren" disclosure once the login screen is
already in Keycloak mode). **After the cutover, password reset is unavailable for everyone, admins
included** (see "What changes for members once Keycloak is on" below), so this pre-cutover check is
the only reliable chance to fix an admin password (the admin UI offers no password reset in Keycloak
mode) short of rolling back. Same "verify a risky operator action actually works before relying on
it" discipline the "Updating an existing deployment" section above already applies to its own
post-deploy check: the architecture guarantees the internal-login *code path* survives a Keycloak
outage (see "Emergency-admin-login safety property" in the architecture doc), but only an
operator can verify a specific ADMIN account's password is actually usable on the day it might be
needed.

=== What changes for members once Keycloak is on

These are server-side effects of Keycloak mode, independent of the login screen:

* **Local password login is `ADMIN`-only.** `POST /api/auth/login` rejects every non-`ADMIN`
  account, and rejects `ADMIN` accounts too when `LAPIS_KEYCLOAK_EMERGENCY_ADMIN_LOGIN_ENABLED` is
  `false`.
* **Password reset is gone for everyone.** `POST /api/auth/password-reset/request` and `/confirm`
  return `404` for all callers, admins included.
* **Non-admins cannot change a local password** (`changePassword` is rejected for any role other than
  `ADMIN`); they manage their password in Keycloak.
* **Self-registration stops entirely.** `registerApplication` and `registerFriend` both fail with a
  conflict error, because a self-registered account could never log in. New members must be created by
  an administrator and then linked (automatically by email, or via the manual-linking panel).

=== Migration runbook: switching a live instance from internal login to Keycloak

Concrete, step-ordered procedure for cutting an already-running instance over. Unlike "Updating
an existing deployment" above (routine release), this runs **once**, at the moment of the
Keycloak cutover.

. **Pre-flight email reconciliation.** Export every member's email from Lapis Cloud (Mitglieder-
  Export or a direct read-only query against `member.email`) and compare it against the Keycloak
  realm's user list. Fix typos/mismatches on **either** side before switching --
  `KeycloakAccountLinker`'s auto-link matches case-insensitively but does not fuzzy-match, so a
  mismatched email is a hard `NO_MATCHING_MEMBER` rejection at first login, not a silent wrong
  match. Also check that every Keycloak user has **Email verified = On** (admin-created or imported
  users default to Off) -- with the default `REQUIRE_VERIFIED_EMAIL=true` an unverified email is
  rejected as `EMAIL_NOT_VERIFIED` at first login. Reconciling this list up front minimizes how many
  members hit the manual-linking panel on day one.

. **Provision the Keycloak client** -- the checklist in "Keycloak client configuration" above.

. **Announce to members**, ahead of the cutover. Sample text (German, adapt freely): "Ab dem
  [Datum] melden Sie sich nicht mehr mit Ihrem bisherigen Lapis-Cloud-Passwort an, sondern über
  [Keycloak/SSO-Systemname] -- klicken Sie auf der Anmeldeseite auf „Mit [Name] anmelden“." Also
  tell them what stops working: "Passwort vergessen" and password changes inside Lapis Cloud are
  gone (use Keycloak), and self-registration is switched off. Keep it short; this is not a full
  comms plan.

. **Verify the emergency-admin path works** -- see the dedicated section above. Do this *before*
  step 5, while the instance is still reachable in internal-login mode to test against. Confirm
  the password of at least one `ADMIN` account really works: **after the cutover there is no
  password reset for anyone, admins included** (the admin UI offers none), so this is the only
  reliable chance to fix an admin password short of rolling back.

. **Deploy.** Add the `LAPIS_KEYCLOAK_*` values to the instance's `.env` **and** the
  `environment:` block from "Environment variables" above to your compose file -- the shipped
  compose files do not forward these variables, so `.env` alone has no effect. Then follow the
  routine from "Updating an existing deployment" above (back up, sync, confirm `.env` unchanged),
  with one addition for an **existing, already-running** instance (true for every production Lapis
  Cloud instance as of Wave 3): run `flywayRepair` **before** rebuilding. Wave 1 (`V1.7.1`) and Wave
  2 (`V1.7.2`) each edited `V1__baseline.sql`'s `oidc_guest_login_event` CHECK constraint in place
  (new `KEYCLOAK_*` event-type literals). One run covers both edits -- it re-baselines the stored
  checksum against the migration files of the checkout it runs from, so **run it from the commit you
  are about to deploy**. It is required by **any deploy that includes V1.7.1/V1.7.2, even for
  instances that never enable Keycloak**; otherwise `migrate()` refuses to run on the checksum
  mismatch and `lapis-server` does not start. `FlywayRepair` reads the database connection from the
  environment (`LAPIS_DB_URL`, `LAPIS_DB_USER`, `LAPIS_DB_PASSWORD`, all three required, as a plain
  PostgreSQL JDBC URL reachable from where you run it) and fails with an error naming the missing
  variable otherwise:
+
[source,bash]
----
LAPIS_DB_URL='jdbc:postgresql://<db-host>:5432/<db-name>' \
LAPIS_DB_USER='<db-user>' \
LAPIS_DB_PASSWORD='<db-password>' \
./gradlew :lapis-server:flywayRepair

cd "$REMOTE_ROOT/deploy/example"
docker compose up -d --build lapis-server
----
+
Verify as in "Updating an existing deployment", step 5 (migration count, `Responding at ...`, HTTP
status). On the first deploy that includes the Keycloak work, the reported migration count is
**4 higher** than before (`V45`-`V48`); that is expected, not a mismatch. Keep the pre-deploy backup
from step 1 of that section until this is confirmed.

. **Smoke test, in this order:**
+
--
.. One real member's SSO login end-to-end (an account already reconciled in step 1).
.. One deliberately-unmatched-email login (an account whose Keycloak email does not match any
   local member) -- confirm a clean rejection page, and confirm no new `member` row was created
   (`KeycloakAccountLinker` never creates members, but this is the moment to prove it against the
   real deployment, not just trust the architecture doc).
.. An `ADMIN` emergency login via the internal-login disclosure, with Keycloak temporarily
   blocked (e.g. a firewall rule or stopping the Keycloak container) -- confirms the safety net
   from step 4 actually holds under a real outage, not just in theory.
.. If `LAPIS_KEYCLOAK_RP_INITIATED_LOGOUT=true` and the discovery document advertises an
   `end_session_endpoint`: confirm `POST /auth/keycloak/logout-redirect` returns a URL (this
   endpoint is not yet wired into the app's own logout button, see the architecture doc -- this
   step only confirms the URL itself resolves, not an end-to-end logout).
--

. **Use the manual-linking admin panel** ("Keycloak-Verknüpfung", ADMIN role, member
  administration screen) to fix up any members the automatic email match missed or flagged
  ambiguous -- expected for any email mismatch step 1 didn't catch in time.

. **Rollback path**: unset `LAPIS_KEYCLOAK_ENABLED` (or set it to `false`) in `.env`, then run
  `docker compose up -d lapis-server` -- **not** `docker compose restart`, which does not re-read
  `.env`. The same applies to every later `.env` or compose change. Internal login returns instantly -- password hashes are never deleted or
  touched by enabling Keycloak mode, so no data restore is needed for this specific rollback (a
  full restore from the pre-deploy backup, per "Updating an existing deployment" above, is only
  needed if something else in the same deploy also went wrong).

== Impressum & Datenschutz (V1.4.7)

`GET /impressum` and `GET /datenschutz` render templates for the statutory Impressum
(§ 5 TMG) and Datenschutzerklärung (Art. 13 DSGVO) every German operator is legally
required to provide. Full field reference, validation rules, and content rationale:
see xref:../../docs/architecture/legal-pages.adoc[legal-pages.adoc].

**Seven `LAPIS_LEGAL_*` variables are mandatory**: `LAPIS_LEGAL_OPERATOR_NAME`,
`LAPIS_LEGAL_STREET`, `LAPIS_LEGAL_POSTAL_CODE`, `LAPIS_LEGAL_CITY`,
`LAPIS_LEGAL_COUNTRY`, `LAPIS_LEGAL_CONTACT_EMAIL`, `LAPIS_LEGAL_REPRESENTATIVE`. Seven
more are optional (`LAPIS_LEGAL_PHONE`, `LAPIS_LEGAL_REGISTER_COURT`,
`LAPIS_LEGAL_REGISTER_NUMBER`, `LAPIS_LEGAL_VAT_ID`, `LAPIS_LEGAL_DPO_CONTACT`,
`LAPIS_LEGAL_MSTV_RESPONSIBLE`, `LAPIS_LEGAL_SUPERVISORY_AUTHORITY`).

**Never fail-fast, exactly like `LAPIS_BRAND_*` above**: a missing mandatory variable
does NOT stop the server from starting and does NOT produce an HTTP 500 -- the affected
page renders an operator-addressed notice in place of the missing data instead (see
`network.lapis.cloud.server.legal.LegalConfig` KDoc). The server still logs a `WARN` at
startup naming which variables are missing, never their values.

**This is a template, not legal advice.** Review the rendered `/impressum` and
`/datenschutz` pages against your own jurisdiction's requirements (and, for a political
party, § 25 PartG where relevant) before going live -- both pages carry an explicit
disclaimer to this effect, but the disclaimer alone does not discharge that obligation.

== Price-Oracle Snapshot Poller (optional)

`LAPIS_ORACLE_SNAPSHOT_ENABLED` (default `false`) starts the background poller
(`network.lapis.cloud.server.economy.oracle.PriceOracleSnapshotPoller`) that persists an hourly
snapshot per anchor asset into `price_oracle_snapshot`, feeding `getPriceHistory` for
TREASURER/BOARD/ADMIN. **Same bug class as `LAPIS_SEPA_POLLER_ENABLED` above (F-2, 2026-08-26)**:
this variable was not passed through `docker-compose.yml` until now -- the poller could not be
enabled on any production deployment. Without it, `price_oracle_snapshot` stays permanently empty
and `getPriceHistory` silently returns `[]` to every caller, with no error and no log.
`LAPIS_ORACLE_SNAPSHOT_INTERVAL_SECONDS` (default 3600, floor 300) tunes the poll interval.

**Set `LAPIS_ORACLE_SNAPSHOT_ENABLED=true` on at most one instance**, exactly like
`LAPIS_SEPA_POLLER_ENABLED` below (Security-Audit finding "Kontingent-Erschoepfung durch
Multi-Instanz-Betrieb", 2026-09-17) -- `recordIfAbsent`'s idempotency only covers the DATABASE
write side (two instances racing to write the same snapshot row is harmless), not the NETWORK
side. The two throttles that protect the gold/fiat sources' free-tier request budgets
(`PriceOracleOrchestrator`'s `lastAttempts`/`lastFanoutAt` maps, see `GoldPriceSources.kt`'s
"Free-tier request budget" KDoc) live entirely in that JVM's process memory and do not coordinate
across instances at all -- enabling this poller on every instance multiplies the real fan-out rate
against GoldAPI.io/MetalpriceAPI by the instance count, which can exceed their 100-requests/month
free tier and get the organization's API key rate-limited or banned, halting the entire
donation-to-LTR conversion path once `GOLD_XAU` falls below quorum.

== SEPA-Lastschriftlauf-Poller (optional)

`LAPIS_SEPA_POLLER_ENABLED` (default `false`) starts the background poller
(`network.lapis.cloud.server.payment.sepa.SepaBatchPoller`) that auto-expires stale mandates,
lapses a withdrawn/rejected member's mandate, and marks SEPA-Lastschrift items settleable after the
8-week return window. **Fix (2026-08-26, F-2)**: this variable existed since V1.2.2 but was never
passed through `docker-compose.yml` -- the poller could not be enabled on any production
deployment until now. Set `LAPIS_SEPA_POLLER_ENABLED=true` on **at most one** instance;
`LAPIS_SEPA_POLL_INTERVAL_SECONDS` (default 3600, floor 60) tunes the poll interval.

== Automatisiertes Mahnwesen (optional)

`LAPIS_DUNNING_POLLER_ENABLED` (default `false`) starts the background poller
(`network.lapis.cloud.server.payment.dunning.DunningPoller`) that fälligstellt overdue
contributions and, once `organization_settings.dunning_enabled` is switched on via
`IDunningService.enableDunning` (ADMIN, disclaimer-acknowledgment-gated) AND at least one active
`dunning_level` exists, escalates them through the configured dunning ladder -- generating and
archiving a PDF per notice. Set `LAPIS_DUNNING_POLLER_ENABLED=true` on **at most one** instance,
same discipline as the SEPA poller above.

* `LAPIS_DUNNING_POLL_INTERVAL_SECONDS` (default 3600, floor 60).
* `LAPIS_DUNNING_MAX_NOTICES_PER_TICK` (default 200, `1..5000`) -- cost-/DoS-cap per poll pass.
* `LAPIS_DUNNING_POSTAL_DISPATCH_ENABLED` (default `false`) -- a THIRD, independent gate on top of
  `organizationSettings.postalMailEnabled` (see "E-Mail-Versand" above's sibling postal-dispatch
  precedent). Automated postal dispatch of a dunning letter costs real money per letter and
  transfers a member's postal address to Letterxpress -- keep this off until an AVV is in place and
  the wording has been reviewed via the `preview.pdf` route.

No default dunning levels are seeded -- an empty `dunning_level` table is itself one of five
independent safeguards before a real letter can ever be issued (poller flag, DB flag, disclaimer
acknowledgment, an active level, and -- for postal dispatch -- the third flag above). See
`network.lapis.cloud.server.payment.dunning.DunningConfig`/`DunningPoller` KDoc.

== Running more than one instance on the same host

You can co-locate several fully independent instances (their own Postgres, their own
`lapis-server`/LiveKit/coturn/redis/egress containers, their own named volumes) on one physical
host -- for example a production instance plus a staging/test instance, or separate instances for
separate organizations. Copy this whole directory, set it up exactly like this one (`cp
.env.example .env`, fill in real values, `./render-secrets.sh`, `docker compose up -d --build`),
then add its own Caddy vhost blocks (see "Reverse proxy" above) for its own subdomain(s).

**Every host-visible port has to move** to avoid colliding with the first instance's own -- copy
this directory's `docker-compose.yml` and shift each `HOST:CONTAINER` port mapping to a free host
port (`lapis-server`, Postgres, LiveKit signaling, LiveKit ICE, coturn + its relay range, redis).
**Not just a host-side remap for every port**, though -- found live in production ("could not
establish pc connection" on the second instance, every ICE candidate pointed at the first
instance's own ports): LiveKit and coturn each bake their own configured port number literally into
the WebRTC/TURN protocol payload they hand back to the browser (an ICE candidate, or an allocated
TURN relay address), unlike the plain HTTP signaling port (Caddy-proxied, the raw port number never
reaches the browser). For LiveKit's `rtc.tcp_port`/`udp_port` and coturn's relay `min-port`/
`max-port` range specifically, the container-INTERNAL config and the docker-compose HOST-side
publish must be IDENTICAL numbers -- `livekit.yaml.template`'s/`turnserver.conf.template`'s own
comments have the specifics. Every other service's internal port is unaffected and stays a simple
host-side remap, same isolated-network-namespace reasoning as before.

**`egress` can use `network_mode: host` for every co-located instance** -- found live in production
that LiveKit egress's embedded template-server port (7980 by default) is a real, documented
`egress.yaml` field (`template_port`, verified against the pinned v1.13.0 source), not a hardcoded,
non-configurable value. Give each additional instance's `egress.yaml.template` its own distinct
`template_port` (the first instance stays at the 7980 default) -- no collision between
host-networked instances. Wave 3 external streaming in `GRID`/`SPEAKER` layout works identically
across instances once each has its own `template_port`, not just Wave 1 (live calls) and Wave 2
recording.

**The `branding/` self-heal ACL timer (see "Video conferencing" above, "Shared
lapis-egress-output volume") needs its own copy per instance** -- `lapis-egress-output` is a
per-Compose-project named volume (its full name includes the Compose project name, which differs
per instance), so the same POSIX ACL mask-capping bug recurs independently on each additional
instance's own volume the first time its own `egress` creates a recording directory. Either add a
second `systemctl enable --now` timer pointed at the second volume's mountpoint, or generalize the
existing unit to loop over all of them -- this file does not prescribe which, only flags that
skipping it silently leaves the additional instance's recordings permanently `FAILED`.

A dedicated STAGING/TEST instance can seed itself with entirely fictitious data (`Testverein
Musterstadt e.V.`-style, `@*.invalid` emails) instead of running against real membership data --
see `StagingSeedConfig`/`StagingSeedData` in the source. Its `docker-compose.yml` is the only one
that should forward `LAPIS_STAGING_MODE`/`LAPIS_STAGING_SEED_PASSWORD` into the container; every
other (real) instance's `docker-compose.yml` should deliberately NOT forward those two variables,
so they can never reach a real deployment's process even if accidentally set in that instance's own
`.env` file.

== Staging seed mechanism

Implemented in `StagingSeedConfig`/`StagingSeedData`
(`lapis-server/src/main/kotlin/network/lapis/cloud/server/db/`), wired into `Application.kt`'s
`main()` **only** -- never into `module()` (which every test's `testApplication { application {
module() } }` re-invokes thousands of times; putting the seed check there would make it a real,
non-free DB read on every single test in this codebase, not just a structural mistake).

`DevSeedData` (the existing H2-only demo-data seeder) is completely unchanged by this mechanism --
not one line of it was touched. `StagingSeedData` is a new, separate object; the only thing it
reads from `DevSeedData` is `demoLedgerAccounts` (a plain data list, reused rather than duplicated)
and `DEMO_PASSWORD` (only to refuse ever reusing it, see lock 1 below).

Four independent locks, all of which must fail before a staging instance's `member` table could
ever be populated against a real deployment:

1. **`StagingSeedConfig.decide`** -- `LAPIS_STAGING_MODE` must be the exact, case-sensitive string
   `"true"` (mirrors `AuthTestMode.evaluate`'s own exact-literal comparison). If it is anything
   else (unset, empty, `"True"`, `"1"`, ...), seeding is silently skipped -- this instance then
   behaves like any other empty Lapis Cloud deployment. If the mode IS `"true"` but
   `LAPIS_STAGING_SEED_PASSWORD` is missing, blank, fails `PasswordPolicy` (12-128 characters), or
   equals the source-published `DevSeedData.DEMO_PASSWORD`, the process refuses to start at all
   (`error(...)`, fail-fast, message visible in `docker compose logs lapis-server`) -- there is no
   silent fallback to "skip seeding and start anyway".
2. **The `member`-table-not-empty guard** inside `StagingSeedData.seedWith` -- checked FIRST,
   before any insert (including the `organization_settings` update). The single strongest
   real-world protection: a real deployment's `member` table is never empty once live, so even a
   badly misconfigured `.env` there would still be a no-op here.
3. **A real deployment's `docker-compose.yml` should never forward
   `LAPIS_STAGING_MODE`/`LAPIS_STAGING_SEED_PASSWORD` into its container at all** -- see "Running
   more than one instance on the same host" above. Those env vars should then never reach this
   code path in the first place, regardless of what is in that deployment's `.env` file.
4. **Everything inserted uses the `@staging.invalid` email domain, a fixed UUID namespace
   (`0000000a-...`) disjoint from both `DevSeedData`'s (`00000000-...`) and the migration
   sentinels, and an obviously-placeholder org name** -- nothing seeded here can be mistaken for
   real membership data even if all three locks above were somehow defeated at once.

**Re-seeding**: delete the Postgres volume (`docker compose down -v`, or `docker volume rm
<compose-project>_lapis-staging-postgres-data`) and restart -- the next boot's empty `member` table
triggers a fresh seed. There is no in-place "reset" RPC; this is the same volume-delete workflow
local dev already uses to re-seed `DevSeedData`.

**Password rotation**: `LAPIS_STAGING_SEED_PASSWORD` is the login password for every seeded
login-capable account (ADMIN/BOARD/TREASURER/MEMBER accounts, see `StagingSeedData.seedMembers`).
There is no separate rotation mechanism beyond deleting the Postgres volume and re-seeding with a
new `.env` value -- acceptable for a throwaway test instance, called out here so it is not assumed
to be rotatable in place.
