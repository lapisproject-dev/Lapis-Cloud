= Local LiveKit/coturn/Egress/Redis Stack (Videokonferenzen, Wave 1 + Wave 2 "Aufzeichnung")
:toc:
:toc-placement: preamble
:icons: font

WARNING: **DEV-ONLY.** Every credential in this directory (`livekit.yaml`'s `keys.devkey` secret,
`turnserver.conf`'s `static-auth-secret`) is committed in plaintext and is meant to be. This mirrors
the project's already-established `DevSeedData.DEMO_PASSWORD` posture: a published-in-source dev
credential, opt-in only, never used against a real deployment. There is no TLS/`wss://` termination
and no production hardening here at all -- see "Not covered here" below. **Audit-round-1 fix**: every
`docker-compose.yml` port now binds `127.0.0.1:` only (was `0.0.0.0`), and `turnserver.conf` uses
coturn's short-lived `use-auth-secret` REST-credential scheme instead of a forever-valid static
username/password -- see both files' own headers and `TurnCredentialMinter.kt` KDoc.

This directory holds the first infrastructure (Docker) setup in this repository: a local LiveKit SFU
plus a coturn TURN server, backing the `IConferenceService`/`ConferenceScreen` Videokonferenzen
feature (V1.0 Wave 1) end to end -- server-side LiveKit admin/token minting, the RPC layer, and the
browser-side `livekit-client` integration have all been live-verified against exactly this stack (see
"Live verification results" below).

== Prerequisites

* Docker with `docker compose` v2 (this stack was built and verified against Docker 29.x/Compose
  5.x on Colima -- see "The Colima `node_ip` trap" below if you are also on Colima on macOS; a
  Docker Desktop or native Linux Docker install needs none of that workaround).
* JDK 21+ and the repository's own `./gradlew` wrapper (no separate Node/Yarn install needed --
  Gradle's Kotlin/JS plugin bootstraps its own).
* A Chromium- or Firefox-based browser with a webcam/microphone for the two-profile manual
  recipe below (or two separate machines/devices).
* **Wave 2 "Aufzeichnung" only**: `ffmpeg` on the HOST machine's `PATH` (or pointed at via
  `LAPIS_FFMPEG_PATH`) -- NOT inside any container. `RecordingPoller`'s composition step
  (`RecordingComposer`, see that class's own KDoc) shells out to the host binary the same way the
  Ktor server itself runs outside Docker in this dev recipe (see "Running the app against this
  stack" below). `brew install ffmpeg` on macOS, `apt install ffmpeg` on Debian/Ubuntu. Without it,
  `ConferenceRecordingConfig.probeFfmpegAvailable` reports `false` at server startup (logged once as
  a WARN) and `ConferenceRecordingAvailabilityDto.ffmpegAvailable` stays `false` -- recording still
  starts and raw tracks still land in `egress-out/`, but every recording gets stuck in `PROCESSING`
  until `ffmpeg` is installed and the server restarted (see "Wave 2 Aufzeichnung" below for the full
  env surface). This is independent of the `egress`/`redis` containers, which need no `ffmpeg` of
  their own -- Track Egress writes raw, uncomposed files; composition is this repository's own code,
  not LiveKit's.

== Quick start

[source,bash]
----
docker compose -f deploy/local/docker-compose.yml up -d
docker compose -f deploy/local/docker-compose.yml logs -f      # tail both services
docker compose -f deploy/local/docker-compose.yml down         # tear down
----

Once up, LiveKit's signaling/Twirp API is reachable at `\http://localhost:7880`, matching this
wave's default `LAPIS_LIVEKIT_URL=ws://localhost:7880` / `LAPIS_LIVEKIT_API_URL=http://localhost:7880`
(see `ConferenceConfig` in `lapis-server`).

== Running the app against this stack

The stack alone is just LiveKit + coturn -- to actually use Videokonferenzen end to end you also need
the Lapis Cloud server (and, for the full UI, a built client bundle) pointed at it:

[source,bash]
----
# 1. Client bundle (same-origin static serving, see Application.kt "clientDistRoot"):
./gradlew :lapis-client:jsBrowserDistribution

# 2. Server, with LiveKit env vars matching livekit.yaml's dev keys.node_ip below, plus demo-data
#    seeding so you have real member logins to test with (see DevSeedData -- opt-in, H2-only, never
#    a real deployment, same posture this whole file documents for the LiveKit credentials):
cd lapis-server
LAPIS_SEED_DEMO_DATA=true \
LAPIS_COOKIE_SECURE=false \
LAPIS_LIVEKIT_URL=ws://localhost:7880 \
LAPIS_LIVEKIT_API_URL=http://localhost:7880 \
LAPIS_LIVEKIT_API_KEY=devkey \
LAPIS_LIVEKIT_API_SECRET='lapis-dev-livekit-secret-32bytes-min!!' \
LAPIS_TURN_URLS='turn:127.0.0.1:3478?transport=udp,turn:127.0.0.1:3478?transport=tcp' \
LAPIS_TURN_SHARED_SECRET='lapis-dev-turn-shared-secret-32bytes-min!!' \
LAPIS_RECORDING_ENABLED=true \
LAPIS_EGRESS_OUTPUT_HOST_DIR="$(cd .. && pwd)/deploy/local/egress-out" \
../gradlew run
----

`LAPIS_RECORDING_ENABLED=true` opts into Wave 2 "Aufzeichnung" on top of the Wave 1 trio above --
requires the `redis`/`egress` services from this SAME `docker-compose.yml` to already be up (see
"Wave 2 Aufzeichnung" below) and `ffmpeg` on the server's own host `PATH` (see "Prerequisites"
above).

**`LAPIS_EGRESS_OUTPUT_HOST_DIR` is NOT optional with this exact recipe -- a real bug found live
during this wave's completion step (2026-08-09), corrected here rather than worked around.**
`ConferenceRecordingConfig`'s own default for this var is the relative string
`deploy/local/egress-out`, which is only correct if the JVM's working directory is the repo root.
But the recipe above does `cd lapis-server` first, and Gradle's `application` plugin's `run` task
defaults its child process's working directory to the *subproject* dir -- so with the bare default
(no `LAPIS_EGRESS_OUTPUT_HOST_DIR` override), the server actually looks for raw track files under
`lapis-server/deploy/local/egress-out` (nonexistent), while `egress` keeps writing the real bytes to
the repo-root `deploy/local/egress-out` regardless (its own bind mount in `docker-compose.yml` is
fixed and knows nothing about the server's working directory). Symptom: `RecordingPoller` logs
`could not resolve raw file '...' -- skipping this track` followed by `no resolvable video track ...
FAILED`, for every recording, unconditionally -- confirmed live: composition failed 100% of the time
against the bare documented recipe before this fix, and succeeded (`READY`, real playable MP4, see
"Live verification results" below) immediately after adding the explicit absolute-path override
above. Every other `LAPIS_RECORDING_*`/`LAPIS_EGRESS_OUTPUT_CONTAINER_DIR` var has a working local
default and does not need to be set for this recipe.

`LAPIS_TURN_URLS`/`LAPIS_TURN_SHARED_SECRET` must match `turnserver.conf`'s own `static-auth-secret`
-- see `TurnCredentialMinter.kt` KDoc for how the server turns this shared secret into a fresh,
short-lived TURN credential on every `joinRoom` call instead of handing the shared secret itself to a
browser. Both are optional and independent of the `LAPIS_LIVEKIT_*` trio above (see
`ConferenceConfig.load` KDoc "TURN is independently optional") -- omitting them just means no TURN
relay fallback (direct/host ICE candidates only), same as running without coturn at all.

`LAPIS_COOKIE_SECURE=false` is only needed because this recipe serves plain `\http://localhost:8080`
(no TLS) -- see `registerAuthRoutes` KDoc "Cookie transport". Never set it against a real deployment.

Then open `\http://localhost:8080`, log in as one of `DevSeedData.demoMembers` (e.g.
`max.mitglied@example.org` / `boris.board@example.org`, password `correct-horse-battery-staple` --
same published-in-source dev credential this file already flags above), and go to "Videokonferenz"
in the nav.

=== The `\http://localhost:8080` secure-context requirement

Browsers only grant `getUserMedia`/`getDisplayMedia` (camera/microphone/screen-share) on a
https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts[secure context] --
`https://` or, as a browser-vendor carve-out, `\http://localhost`/`\http://127.0.0.1` specifically.
This recipe's `\http://localhost:8080` qualifies for that carve-out and needs no TLS setup for local
manual testing. It does **not** extend to a LAN IP (`\http://192.168.x.x:8080`) -- testing from a
second physical device on the same network needs either a `https://` reverse proxy in front of the
server or that device's browser flags relaxed for the specific origin, neither of which this wave
sets up (see "Not covered here").

== Two-profile browser recipe (manual two-participant verification)

LiveKit sessions are per-participant-token, not per-browser-tab -- the practical way to run two
independent participants locally is two independent cookie jars against the SAME server, so each
gets its own login session and its own LiveKit join token:

. Open the app in **two separate browser profiles** (e.g. Chrome's own multi-profile switcher, or
  one normal window + one Incognito/private window -- anything with an independent cookie jar).
  Logging in as a second member in a second *tab* of the same profile works for driving the UI, but
  overwrites the first tab's session cookie (Lapis Cloud sessions are cookie-based, one active
  session per cookie jar) -- fine for exercising RPC calls sequentially, not for two people typing
  in the same browser window at once.
. Profile A: log in as `max.mitglied@example.org`, go to "Videokonferenz", click "Besprechung
  erstellen" (with a title), then "Beitreten". You are now the room's MODERATOR.
. Profile B: log in as `boris.board@example.org` (or any other seeded member), go to
  "Videokonferenz" -- the room Profile A created appears under "Aktive Besprechungen" with a live
  participant count. Click "Beitreten".
. Both profiles now show a live, two-tile video grid, updating in real time as the other side
  joins/leaves (`RoomEvent.ParticipantConnected`/`Disconnected`) -- no manual refresh needed.
. Grant camera/microphone permission when your browser prompts (see "Secure-context requirement"
  above) to test real audio/video; click "Bildschirm teilen" on either side to test screen share;
  open "Chat" on either side and send a message -- it should appear on the other side within a
  second or two, prefixed with the sender's real display name.
. As the moderator (Profile A), "Für alle beenden" ends the room for everyone (two-step confirm
  dialog first); "Entfernen" next to a participant in "Teilnehmende" kicks just that one (also
  confirm-gated). A BOARD/ADMIN account can do both even without being the room creator -- see
  `IConferenceService` KDoc's role table.

== The Colima `node_ip` trap (read this before debugging a black call)

`livekit.yaml` sets `rtc.node_ip: 127.0.0.1`. **This is the single most load-bearing line in that
file.** Without it, LiveKit advertises the *container's* VM-internal address as its own ICE
candidate. The browser runs on the macOS host, outside the Colima VM, and can only reach LiveKit
through Docker's *published* ports -- so ICE negotiation silently never completes, and the symptom is
a black video tile with no error message anywhere. Setting `node_ip: 127.0.0.1` makes LiveKit
advertise the loopback address, which resolves correctly through the published `7882/udp` (and
`7881/tcp` as a TCP fallback if UDP forwarding misbehaves).

If you ever see a connection that never progresses past "Connecting..." against this stack, check
this setting first before anything else. **This fix is live-verified, not theoretical**: the
2026-08-09 two-browser session below observed real signaling connects
(`connected to Livekit Server ... version: 1.13.5`), real SDP offer/ICE-credential/DTLS-fingerprint
exchanges in the LiveKit container logs for both participants, and -- the strongest possible proof,
stronger than a static `chrome://webrtc-internals` candidate-pair screenshot -- real bidirectional
chat delivered over LiveKit's SCTP data channel between two independent browser sessions, which is
only possible once a genuine DTLS/ICE-secured `PeerConnection` is fully established end to end
through Colima's port forwarding.

== Troubleshooting

[cols="1,2"]
|===
|Symptom |Likely cause / fix

|Black video tile, connection stuck on "Connecting..."
|The Colima `node_ip` trap above -- verify `docker compose -f deploy/local/docker-compose.yml logs
livekit \| grep nodeIP` shows `"nodeIP": "127.0.0.1"`.

|Loud screech / feedback loop when two participants are in the same room
|**The audio-feedback trap**: this is not a bug, it is two microphones picking up two speakers in
the same physical room. If you are testing the two-profile recipe above on **one machine** (two
browser windows side by side), mute one side's speakers/output device, or -- better -- use
headphones on at least one side. This is standard WebRTC/video-call behavior, not specific to this
stack; it is called out here only because it is the first thing a first-time tester of this stack
usually assumes is broken.

|`KeyLengthException` at server startup or on first LiveKit call
|You are pointing at a `livekit-server --dev` instance instead of this `docker-compose.yml` --
see "Why not `livekit-server --dev`" below.

|Camera/microphone permission silently denied, no visible error, control button still flips to
"an" ("on")
|**Fixed (2026-08-09, same-day as the gap was found)**: independently reproduced during this wave's
own live-browser verification pass -- clicking the camera toggle while `getUserMedia` was blocked
flipped the button straight to "Kamera an" with no error. Root cause matched the implementation's
own diagnosis exactly: `ConferenceScreen.kt`'s mic/camera/screen-share toggle handlers flipped their
local `micEnabled`/`cameraEnabled`/`screenShareEnabled` flag and the button label *before* awaiting
`guarded { session.setXxx(...) }`'s result, never checking whether it actually succeeded. Fixed by
only applying the optimistic flag/label flip when `guarded {}` returns non-null (i.e. the call truly
succeeded); a failed toggle now reverts to the truthful prior label instead of lying about state.
The initial post-connect auto-publish (`setMicrophone(true)`/`setCamera(true)`) had the same class of
gap -- both default to `micEnabled = true`/`cameraEnabled = true` at declaration, so a failed initial
publish never corrected them -- fixed the same way. This closes the concrete UI-truthfulness bug; the
broader D2 finding (a first-class, non-technical permission-preflight *interstitial*, asked before
LiveKit's own device prompt fires) remains legitimately open for a later polish step, see
`ConferenceScreen.kt` file KDoc "Still open from the Wave 1 design review".

|`docker compose up` fails to bind `3478/udp` or `7882/udp`
|Another process (often a VPN client or another LiveKit/coturn instance) is already using that port
-- `lsof -i :3478` / `lsof -i :7882` to find it.

|A recording never leaves `RECORDING`/`STOPPING` (no track egresses ever start, or
`StartTrackEgress` calls throw `LiveKitAdminException`), and `docker compose -f
deploy/local/docker-compose.yml logs egress` shows a repeating `"no response from servers"` /
`"context deadline exceeded"` around a `redis` dial
|**The classic Wave 2 Redis-connectivity symptom.** `egress` (and `livekit-server` itself, once
`redis:` is set in `livekit.yaml`) cannot reach the `redis` container -- check, in order: (1)
`docker compose -f deploy/local/docker-compose.yml ps` shows `redis` as `Up` (not restarting/
exited); (2) `egress.yaml`'s `redis.address` and `livekit.yaml`'s `redis.address` both read
EXACTLY `redis:6379` (the compose SERVICE name, never `localhost`/`127.0.0.1` -- those only resolve
inside a container to that container itself); (3) `redis` was started as part of the SAME `docker
compose up` as `livekit`/`egress` (all four services share one `lapis-conference-dev_default`
network by being in the same compose file/`up` invocation -- starting `redis` via a separate,
unrelated `docker run` would put it on a different network, unreachable by name). Confirm a clean
connection with `docker compose -f deploy/local/docker-compose.yml logs egress \| grep redis`,
which on a healthy stack shows a single `connecting to redis {"addr": "redis:6379"}` INFO line and
nothing further about it (see "Live verification results, Wave 2 infra step" below for what a
healthy startup log looks like end to end).

|A `READY` recording never appears after a call ends -- the recording stays `PROCESSING` forever
|`ffmpeg` is missing/not on `PATH` on the machine running the Ktor server -- see "Prerequisites"
above. Check the server's own startup log for `ffmpeg -version did not complete` /
`ffmpeg probe failed` (`ConferenceRecordingConfig.probeFfmpegAvailable`'s WARN), and confirm via
`GET`ting `IConferenceRecordingService.getRecordingAvailability` (or just looking at whether the
moderator's "Aufzeichnung starten" button is visible at all -- design review D14 hides it entirely
when unavailable) that `ffmpegAvailable == true` before assuming this is a poller bug.

|Every recording goes `FAILED` with `Die Aufzeichnung konnte nicht zusammengesetzt werden.`, and the
server log shows `RecordingPoller: could not resolve raw file '...' -- skipping this track` even
though `docker exec lapis-conference-dev-egress ls /out/<recordingId>/` shows the file is really
there
|**The `LAPIS_EGRESS_OUTPUT_HOST_DIR` working-directory mismatch -- see "Running the app against
this stack" above, which now sets this var explicitly for exactly this reason.** If you started the
server your own way (not via the documented recipe) and are still hitting this: confirm your
process's actual working directory (`lsof -p <pid> | grep cwd` on macOS/Linux) and either `cd` to
the repo root before `../gradlew run`, or set `LAPIS_EGRESS_OUTPUT_HOST_DIR` to an absolute path
yourself. Live-verified 2026-08-09: this is not a hypothetical, every single recording attempted
against the bare documented recipe (before the fix above) failed this exact way, 100% reproducible.

|A recording that previously worked starts failing the SAME way right after you manually cleared
out `deploy/local/egress-out/` while the stack was already running (e.g. to save disk space between
test runs)
|**Observed once, 2026-08-09, on Colima -- not fully root-caused, but reproducibly worked around by
restarting the `egress` container.** `rm -rf deploy/local/egress-out/*` while `egress` is still
running produced a track egress that logged a completely normal `egress_active` -> `egress_ending`
-> `egress_complete` lifecycle (HTTP-level success, no error anywhere in the container's own log)
but left **zero bytes** anywhere under `/out` inside the container afterwards -- `docker exec
lapis-conference-dev-egress ls -la /out` came back empty even immediately after `egress_complete`.
A plain `docker compose -f deploy/local/docker-compose.yml restart egress` immediately before the
next recording attempt made the very next run succeed cleanly (confirmed: real `READY` recording,
real playable MP4, see "Live verification results" below). Best current hypothesis: a Colima
virtiofs/9p bind-mount consistency quirk when the host removes directory entries out from under an
already-running container's open mount, not (yet) confirmed against native Linux Docker. If you
routinely clear `egress-out/` between test sessions, restart the `egress` container afterwards
rather than assuming the next recording will "just work".

|In the in-call moderator view, "Aufzeichnung beenden" used to change to a permanently disabled
"Aufzeichnung wird beendet ..." that never resolved to "Aufzeichnung starten", even though the
recording had already reached a terminal state (`READY`/`FAILED`) -- confirmed via the Lobby's own
"Aufzeichnungen" list, which showed the correct final status
|**FIXED in review-round-1 of this wave's own code review (2026-08-09).** Root cause, found during
this wave's own live verification the same day: `ConferenceScreen.kt`'s in-call recording-detail
line and moderator button label were refreshed by exactly one mechanism --
`refreshRecordingState()`, called only from inside the `onRecordingStatusChanged` LiveKit-push
handler (see that file's own "D1/D2" KDoc). LiveKit flips `room.isRecording` back to `false` as
soon as the LAST track egress ends -- which is always *before* `RecordingPoller`'s own
`STOPPING -> PROCESSING -> READY`/`FAILED` transition, sometimes by a wide margin for a long
composition. There was no separate signal (poll or push) for that second, often-longer phase while
a moderator stayed in the call view, so the button could be left showing a stale in-flight label.
Observed **inconsistently**, not on every run: one `FAILED`-path recording left the button stuck
even after a full page reload and rejoin of the same room; a later `READY`-path recording
self-corrected to "Aufzeichnung starten" on an equivalent reload+rejoin -- the exact trigger
condition for the stuck case was not isolated at the time.

**Fix**: `enterCall` now runs a periodic `pollInFlightRecordingStatus` loop (15s interval, close to
`RecordingPoller`'s own 10s default tick) for as long as the tracked recording sits in
`STOPPING`/`PROCESSING`. Each tick falls back to `listRecordings(roomId)` -- not just
`getActiveRecording(roomId)`, which server-side (`ACTIVE_RECORDING_STATUSES`) never returns anything
past `STOPPING` -- to find the SAME recording id's true, possibly-terminal status. On reaching
`READY`/`FAILED` the control unsticks (reverts to an actionable "Aufzeichnung starten") and a toast
now surfaces the outcome to the moderator. Deliberately not run through `guarded {}` (would re-toast
a transient network hiccup on every tick); see `ConferenceScreen.kt`'s own KDoc on
`pollInFlightRecordingStatus` for the full reasoning, and `ConferenceScreenTest.kt` for the new
`conferenceRecordingNeedsPoll`/`conferenceFindRecordingById` unit coverage.

**One narrow residual gap, disclosed rather than silently left**: `listRecordings`' access-level
filter (`ConferenceRecordingAccess.mayAccess`) can still hide a recording from a moderator who is
neither its starter nor privileged enough for its `accessLevel` (e.g. a plain room-creator moderator
stopping another BOARD/ADMIN member's `ADMIN_ONLY` recording) -- for that narrow case the button
stays exactly as stuck as before this fix, never worse. Not root-caused/closed here.

== Why not `livekit-server --dev`

`--dev` hardcodes the API key/secret pair `devkey`/`secret`. `secret` is 6 bytes = 48 bits. This
project's JWT library, `nimbus-jose-jwt` (already a dependency, see `OidcJwt.kt`), refuses to
construct an HS256 `MACSigner` for a key shorter than 256 bits and throws `KeyLengthException` --
so `--dev` cannot be used here at all. `livekit.yaml` instead pins an explicit `keys:` block with a
38-byte dev secret (`lapis-dev-livekit-secret-32bytes-min!!`), and the server-side `ConferenceConfig`
fails fast with an explanatory message (not a raw `KeyLengthException`) if a configured
`LAPIS_LIVEKIT_API_SECRET` is ever shorter than 32 bytes -- see that class's KDoc.

== coturn's role is mostly symbolic here

On a single developer machine, the host/`127.0.0.1` ICE candidate almost always wins -- the TURN
relay path is only exercised when the direct path fails (e.g. a peer genuinely behind a restrictive
NAT, which a local Docker setup can't easily simulate). `livekit-client` does not expose an
`iceTransportPolicy: 'relay'` option, so the relay path cannot be forced from the app side either.

coturn is included anyway because it's the component the production/multi-network deployment will
need (per the Videokonferenzen concept note's NAT-traversal requirement) -- wiring the config surface
now means it already exists, reviewed, before it becomes load-bearing. Verification of the relay path
in this wave is therefore **observational only**:

[source,bash]
----
docker compose -f deploy/local/docker-compose.yml logs -f coturn
# watch for allocation requests while a call is active
----

== Verifying the stack without a browser

A hand-minted admin JWT (HS256, signed with the `devkey` secret above) can exercise the Twirp
Room-Service API directly:

[source,bash]
----
curl -sS -X POST http://localhost:7880/twirp/livekit.RoomService/ListRooms \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{}'
# {"rooms":[]}
----

See `LiveKitAdminClientTest.kt` in `lapis-server` for the real, verified request/response wire shapes
(snake_case JSON -- e.g. `empty_timeout`, `max_participants` -- not the camelCase the LiveKit docs'
*general* protobuf-JSON convention would suggest; confirmed empirically against this exact stack).

For a real, automated round trip against a running container (rather than a hand-typed `curl`), see
`LiveKitLiveIntegrationTest.kt` (`lapis-server/src/test/kotlin/network/lapis/cloud/server/conference/`)
-- an opt-in, env-gated Kotest spec (deliberately **not** part of `./gradlew clean check`, see that
file's own KDoc for why Testcontainers was not introduced for this):

[source,bash]
----
docker compose -f deploy/local/docker-compose.yml up -d
LAPIS_LIVEKIT_IT=true ./gradlew :lapis-server:test --tests "*.LiveKitLiveIntegrationTest"
----

Unset (or anything other than `true`), every test in that spec is a no-op (reported skipped, never
failed) -- safe to leave committed and safe on machines/CI without Docker.

== Wave 2 "Aufzeichnung" -- Egress + Redis

`redis`/`egress` join the stack for Track-Egress-based meeting recording (see
`ConferenceRecordingConfig`/`LiveKitEgressClient`/`IConferenceRecordingService` KDoc for the
server-side half). Re-uses the same `livekit.yaml` API key/secret -- `egress.yaml` MUST carry the
SAME `api_key`/`api_secret` (both files' own headers cross-reference this).

**The `livekit.yaml` change is real, not cosmetic**: adding a `redis:` block switches
`livekit-server` from its Wave 1 single-node in-process router to the Redis-backed router --
LiveKit's own self-hosting docs state Egress needs this to communicate with the server at all. The
FIRST thing verified in this wave, before writing any recording code, was that this switch does NOT
regress plain Wave 1 conferencing: `LAPIS_LIVEKIT_IT=true ./gradlew :lapis-server:test --tests
"*.LiveKitLiveIntegrationTest"` still passes against the Redis-enabled stack, and the LiveKit
container's own Twirp access log still shows real `CreateRoom`/`ListParticipants`/`DeleteRoom`
calls succeeding, with `nodeIP: 127.0.0.1` unchanged in the startup log line.

**Two deliberately separate output-directory env vars -- the single most likely bug in this wave if
collapsed into one.** `LiveKit Track Egress`'s `DirectFileOutput.filepath` is a path INSIDE the
`egress` container (`LAPIS_EGRESS_OUTPUT_CONTAINER_DIR`, default `/out`); the Ktor server reads
those SAME bytes back from the HOST filesystem (`LAPIS_EGRESS_OUTPUT_HOST_DIR`, default
`deploy/local/egress-out`, gitignored) because in local dev it runs outside Docker entirely.
Conflating the two produces a `FileNotFoundException` on the composer side (a later step) that
looks exactly like "egress silently produced nothing". On Colima/macOS the bind-mounted files
surface as the host user (verified live below); on native Linux Docker they may land root-owned --
if the Ktor process cannot read `deploy/local/egress-out/`, add a `user:` override to the `egress`
service in `docker-compose.yml` matching your host UID/GID.

Full recording-related env surface (`ConferenceRecordingConfig`): `LAPIS_RECORDING_ENABLED` (master
opt-in, default `false`, see "Running the app against this stack" above for the full recipe with it
turned on), `LAPIS_EGRESS_OUTPUT_CONTAINER_DIR`/`LAPIS_EGRESS_OUTPUT_HOST_DIR` (see above),
`LAPIS_FFMPEG_PATH` (default `ffmpeg`, resolved via `PATH` if not absolute -- see "Prerequisites"
above for the HOST-machine `ffmpeg` install this needs), `LAPIS_RECORDING_POLL_INTERVAL_SECONDS`/
`_EGRESS_TIMEOUT_MINUTES`/`_MAX_DURATION_MINUTES`/`_COMPOSE_TIMEOUT_MINUTES`/`_MAX_TRACKS`/
`_KEEP_RAW` (all consumed by `RecordingPoller`, the single application-scoped coroutine that drives
`RECORDING -> STOPPING -> PROCESSING -> READY`/`FAILED` -- see that class's own KDoc for the full
state machine). `ConferenceRecordingConfig.load()` remains string-parsing only (no I/O), so
`./gradlew clean check` never needs `ffmpeg`/Docker even though every one of these vars is now fully
wired end to end (poller, `ffmpeg`-based gallery composition, Dokumentenablage archiving, and the
`ConferenceScreen.kt`/`ConferenceRecordingsPanel.kt` client UI all landed as of this wave's
storage/poller and client-UI steps).

**Recordings inflate `OrganizationExportService` backups -- not a hypothetical, a real and
potentially large size increase.** A composed recording is archived as an ordinary `document` under
`documentStorageRoot` (see "Storage and access" reasoning in the wave plan -- reused deliberately for
soft-delete/versioning/DSGVO-export reuse), and `OrganizationExportService` walks
`documentStorageRoot` in full for every backup. A single Vorstandssitzung recording easily runs into
the hundreds of MB; a `deploy/local/README.adoc`-scale dev instance won't notice, but an operator
running regular backups against a real deployment WILL see backup size and duration grow
substantially the moment recording is turned on for real meetings. Excluding recordings from backups
(or a separate, opt-in "include recordings" backup mode) is an explicit, undecided question for a
later wave -- this wave does not silently make that call either way; it is flagged here and in
`CHANGELOG.md`'s own Wave 2 entry precisely so it is not discovered by surprise the first time a
backup takes ten times as long as before.

== Not covered here

* No TLS/`wss://` termination -- everything is plain `ws://`/`http://` on loopback.
* No production deployment story: this Redis is single-node/compose-internal (added purely so
  Egress can talk to `livekit-server`, not for multi-node LiveKit clustering), no autoscaling, no
  certificate setup, no embedded-TURN-vs-standalone-coturn comparison (all remain open questions
  for the production deployment wave).
* No RTMP live-streaming egress -- Wave 3's job, see the Videokonferenzen concept note. Track Egress
  (recording) itself IS covered as of Wave 2, see below. The Redis + Egress infrastructure this wave
  adds is exactly the prerequisite Wave 3 needs, so that later wave becomes substantially cheaper.
* No S3-compatible (or any other) object storage for recordings -- the Dokumentenablage/local-disk
  default (`documentStorageRoot`) is the only backend this wave implements, per the concept note's
  own 2026-08-01 decision. LiveKit Egress supports S3/GCP/Azure sinks natively; a later wave would
  change `DirectFileOutput` plus the archive step, not the whole storage model.
* No recording retention policy / automatic deletion, no per-participant recording opt-out, no
  auto-transcript/live-subtitles, no chapter markers, no WebM/VP9 alternate output format, no
  four-tier Moderator/Präsentator/Teilnehmer/Zuhörer role model, no E2EE interaction (E2EE does not
  exist yet either). See `IConferenceRecordingService`'s own class KDoc "Out of scope this wave" for
  the complete, deliberately-cut list this file does not repeat in full.
* **One known, NOT-YET-CLOSED gap from the wave's own design review, carried forward
