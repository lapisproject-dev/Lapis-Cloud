= Lapis Cloud -- Staging/Test Instance

A dedicated, THIRD, co-located instance on the same host as `../production/` (PdV) and
`../production-elb/` (ELB) -- but running against a real Postgres, not H2, and seeded with
entirely fictitious data instead of any real membership data. Purpose: give an interactive or
agentic tester something realistic to click through -- a member directory, committees, meetings,
motions, contributions, an event with registrations -- without any real member ever being at risk.

WARNING: This instance seeds FREE, FICTITIOUS test data. Organisation `Testverein Musterstadt
e.V.`, member emails on the `@staging.invalid` domain (RFC 2606 -- never resolvable, never
deliverable). **Never import real membership data here.** If this instance is ever repurposed for
something real, delete its Postgres volume first (see "Quick start" below) and never set
`LAPIS_STAGING_MODE`/`LAPIS_STAGING_SEED_PASSWORD` again.

**One structural difference from PdV/ELB, deliberately**: `docker-compose.yml` in THIS directory
forwards `LAPIS_STAGING_MODE` and `LAPIS_STAGING_SEED_PASSWORD` into the `lapis-server` container.
`../production/docker-compose.yml` and `../production-elb/docker-compose.yml` do **not** have
these two lines at all -- not "set to false", genuinely absent -- so even a stray
`LAPIS_STAGING_MODE=true` entry accidentally left in PdV's or ELB's own `.env` file could never
reach either of those two real deployments' processes. This is the third of the four independent
locks described below.

== Staging seed mechanism

Implemented in `StagingSeedConfig`/`StagingSeedData`
(`lapis-server/src/main/kotlin/network/lapis/cloud/server/db/`), wired into `Application.kt`'s
`main()` **only** -- never into `module()` (which every test's `testApplication { application {
module() } }` re-invokes thousands of times; putting the seed check there would make it a real,
non-free DB read on every single test in this codebase, not just a structural mistake).

`DevSeedData` (the existing H2-only demo-data seeder) is completely unchanged by this mechanism --
not one line of it was touched. `StagingSeedData` is a new, separate object; the only thing it
reads from `DevSeedData` is `demoLedgerAccounts` (a plain data list, reused rather than duplicated)
and `DEMO_PASSWORD` (only to refuse ever reusing it, see lock 1 below).

Four independent locks, all of which must fail before this instance's `member` table could ever be
populated against a real deployment:

1. **`StagingSeedConfig.decide`** -- `LAPIS_STAGING_MODE` must be the exact, case-sensitive string
   `"true"` (mirrors `AuthTestMode.evaluate`'s own exact-literal comparison). If it is anything
   else (unset, empty, `"True"`, `"1"`, ...), seeding is silently skipped -- this instance then
   behaves like any other empty Lapis Cloud deployment. If the mode IS `"true"` but
   `LAPIS_STAGING_SEED_PASSWORD` is missing, blank, fails `PasswordPolicy` (12-128 characters), or
   equals the source-published `DevSeedData.DEMO_PASSWORD`, the process refuses to start at all
   (`error(...)`, fail-fast, message visible in `docker compose logs lapis-server`) -- there is no
   silent fallback to "skip seeding and start anyway".
2. **The `member`-table-not-empty guard** inside `StagingSeedData.seedWith` -- checked FIRST,
   before any insert (including the `organization_settings` update). The single strongest
   real-world protection: neither PdV's nor ELB's `member` table is ever empty once live, so even a
   badly misconfigured `.env` on either of those two would still be a no-op here.
3. **`../production/docker-compose.yml` and `../production-elb/docker-compose.yml` do not forward
   `LAPIS_STAGING_MODE`/`LAPIS_STAGING_SEED_PASSWORD` into their containers at all** -- see
   "Abgrenzung" above. Those two real deployments' env vars never reach this code path in the first
   place, regardless of what is in their `.env` files.
4. **Everything inserted uses the `@staging.invalid` email domain, a fixed UUID namespace
   (`0000000a-...`) disjoint from both `DevSeedData`'s (`00000000-...`) and the migration sentinels
   (`...-f1`/`...-f2`/`...-f3`), and an obviously-placeholder org name** -- nothing seeded here can
   be mistaken for real PdV/ELB data even if all three locks above were somehow defeated at once.

**Re-seeding**: delete the `lapis-staging-postgres-data` volume (`docker compose down -v`, or
`docker volume rm lapis-cloud-staging_lapis-staging-postgres-data`) and restart -- the next boot's
empty `member` table triggers a fresh seed. There is no in-place "reset" RPC; this is the same
volume-delete workflow local dev already uses to re-seed `DevSeedData`.

**Password rotation**: `LAPIS_STAGING_SEED_PASSWORD` is the login password for every seeded
login-capable account (ADMIN/BOARD/TREASURER/MEMBER accounts, see `StagingSeedData.seedMembers`).
There is no separate rotation mechanism beyond deleting the Postgres volume and re-seeding with a
new `.env` value -- acceptable for a throwaway test instance, called out here so it is not assumed
to be rotatable in place.

== Quick start

[source,bash]
----
cp .env.example .env
# fill in real values -- especially LAPIS_STAGING_SEED_PASSWORD (openssl rand -base64 24)
./render-secrets.sh
docker compose up -d --build
docker compose logs -f lapis-server
# expect: "LAPIS_STAGING_MODE aktiv -- diese Instanz seedet FREI ERFUNDENE Testdaten ..."
----

Login with any seeded account's email (e.g. `anna.musterfrau@staging.invalid` for the seeded ADMIN)
and `LAPIS_STAGING_SEED_PASSWORD`.

== Updating an existing deployment

Same routine as xref:../production/README.adoc[../production/README.adoc], section "Updating an

The seeded test data (see "Staging seed mechanism" below) is disposable, but back up before syncing

== Reverse proxy + Basic-Auth

This host binds Caddy on `:8443`, not `:443` -- `sniproxy` owns the real public `:443` (see
`../production/README.adoc` "TURNS over TLS (port 443)" for the full mechanism). Every new site
address therefore needs the explicit `:8443` suffix, and Caddy's automatic HTTP->HTTPS redirect
(suppressed by a non-default port) needs an explicit `http://` block instead:

[source,caddyfile]
----
staging.parteidervernunft.de:8443 {
    basic_auth {
        staging $2a$14$<bcrypt-hash-hier-einsetzen>
    }
    reverse_proxy 127.0.0.1:8082
    log {
        output file /var/log/caddy/staging-parteidervernunft-de-access.log
    }
}
http://staging.parteidervernunft.de { redir https://{host}{uri} permanent }

video-staging.parteidervernunft.de:8443 {
    # WebSocket upgrade exception -- see "Video conferencing" below for why.
    @nichtupgrade not header Connection *Upgrade*
    basic_auth @nichtupgrade {
        staging $2a$14$<bcrypt-hash-hier-einsetzen>
    }
    reverse_proxy 127.0.0.1:7886
    log {
        output file /var/log/caddy/video-staging-parteidervernunft-de-access.log
    }
}
http://video-staging.parteidervernunft.de { redir https://{host}{uri} permanent }
----

Generate the bcrypt hash (never store the plaintext password in the Caddyfile or this repo):

[source,bash]
----
caddy hash-password --plaintext 'DAS-PASSWORT'   # -> $2a$14$...
----

`basicauth` was renamed `basic_auth` in Caddy 2.7 -- both directive names work on a current Caddy,
but `basic_auth` is the current one. After any Caddyfile edit: `systemctl reload caddy`
(graceful, zero-downtime). Watch out for the root-owned-log-file trap described in
`../production/README.adoc` ("Reverse proxy (Caddy)") if you ever run `caddy validate`/`caddy
adapt` manually as `root` with the `log { output file ... }` block already present.

Add two DNS A records (`staging` and `video-staging`, both -> this host's IP) before the Caddyfile
edit above will obtain a Let's Encrypt certificate for either name.

**Open question (WebSocket vs. Basic-Auth)**: a browser's `wss://` handshake cannot carry an
`Authorization` header from JavaScript, and cached Basic-Auth credentials are not reliably
re-sent on a WebSocket upgrade of the same origin. The `@nichtupgrade` exception above protects the
plain HTTP/Twirp surface while leaving the WebSocket upgrade path unauthenticated at the Caddy
layer -- acceptable because that path is independently secured by a server-minted, short-lived
LiveKit JWT (see `ConferenceConfig`). Verify this with a real two-participant call before treating
video conferencing as working on this instance; if it does not work, the alternative is dropping
Basic-Auth on `video-staging` entirely, or accepting broken video conferencing on a Basic-Auth-
protected `video-staging`.

**Open question (how an agent authenticates against Basic-Auth)**: a headless/automated browser
session hitting a native Basic-Auth prompt, or a `https://user:pass@host` URL (which modern Chrome
only honors for top-level navigation, not subresources), may not work smoothly for an agentic
tester. If that proves true in practice, an alternative is a Caddy IP allowlist or a long, secret
URL path prefix instead of Basic-Auth -- not implemented here, flagged for whoever operates this
instance to decide once a concrete agent access pattern is known. Credential handoff to whichever
human or agent needs it is out of scope for this repo either way -- `.env`/the bcrypt hash never
leave this host via this codebase.

== Egress-ACL self-heal timer

The POSIX-ACL mask-capping self-heal timer described in `../production/README.adoc` ("Video
conferencing", "Shared lapis-egress-output volume") needs its own copy for this instance's own
`lapis-cloud-staging_lapis-staging-egress-output` volume -- the same per-Compose-project-named-
volume reasoning already documented there for `../production-elb/`. Either add a third
`systemctl enable --now` timer pointed at this volume's mountpoint, or generalize the existing unit
to loop over all three -- skipping this silently leaves staging's own recordings permanently
`FAILED`.

== TURNS over TLS (optional)

Not required for the core staging use case (see "Offene Frage O-3" in the implementation plan this
README documents) -- only set this up if the staging instance should also exercise the TURNS-over-
TLS path. `turnserver.conf.template`'s TLS block (`tls-listening-port`/`cert`/`pkey`) is therefore
commented out by default: `coturn-certs/` in this directory ships empty (only a `.gitkeep`), so an
uncommented block would point coturn at certificate files that do not exist on a fresh install. To
enable it: a third DNS A record (`turn-staging.parteidervernunft.de` -> this host's IP), a third
`sniproxy` table entry pointing at `127.0.0.1:5352`, a third target for
`/usr/local/sbin/sync-turn-certs.sh` (or an equivalent that populates `coturn-certs/` here) -- see
`../production/README.adoc` "TURNS over TLS (port 443)" for the full mechanism this mirrors --
and only then uncomment the three lines in `turnserver.conf.template`.

== AI assistance

The optional AI assistance ("Fragen zur Satzung") is **off here** and this compose file does not
forward any `LAPIS_AI_*` variable (guarded by `AiEnvNotForwardedInComposeTest`). A tester who wants
to exercise it adds the variables on purpose -- see
xref:../production/README.adoc[../production/README.adoc], section "AI assistance", including the
data-protection duties (never point a staging instance at a real provider account with real data).

== What is deliberately off

`docker-compose.yml` in this directory hardcodes (not `.env`-driven, so a stray `.env` entry cannot
silently turn one on) the following to off: SMTP (no outgoing mail at all), the SEPA-Lastschrift
poller, the automated Mahnwesen (dunning) poller and its postal dispatch, and outbound webhooks. A
testing instance must never send anything to the outside world -- real emails, real SEPA batch
files, real dunning letters, or real webhook deliveries to a third party. If a future test
scenario genuinely needs one of these paths exercised, treat that as a deliberate, reviewed
decision to loosen this file, not an oversight to silently work around.
