= Public event page: Lapis header and `?embed=1` (V1.9.128)
:toc:

The public event page `GET /veranstaltung/{slug}` and every page of its registration flow (thanks, waiting list, cancelled, storno, payment,
ticket, error pages) exist in two presentations.

[cols="1,3,3"]
|===
| | Standard | `?embed=1`

| Header
| Full Lapis header (brand, icon navigation, language switcher, login link), skip link, shared footer.
| None. A slim page for an `<iframe>`; footer links (start page, Impressum, Datenschutz) are site-relative with `target="_top"`.

| Layout
| Wide column (56 rem), facts list, registration card.
| Same components, narrow column (36 rem).

| Language
| `?lang=xx` switches the chrome and is passed through the whole flow, including the links from `/veranstaltungen?lang=xx` to the detail page (V1.9.140). The page content is German in every language.
| German only.

| Indexing
| Canonical and hreflang on the detail page.
| `noindex`, canonical onto the standard URL.

| Framing
| Never (`frame-ancestors 'none'`, `X-Frame-Options: DENY`).
| Only by the embed origins, see below.
|===

Only the exact value `embed=1` (a single parameter) activates the embed mode; anything else is the standard page. The raw value is never
reflected.

== Message field and occupancy (V1.9.204)

* The registration form has the optional field `nachricht` ("Nachricht an die Veranstalter (optional)", `maxlength` 500, the hint sentence "Ihre Nachricht
  sehen die Veranstalter. Gültig ist Ihre Anmeldung durch die Bestätigung, nicht durch eine Antwort auf Ihre Frage."). It is NOT the honeypot `kommentar`.
  A text over 500 characters answers 400 before the strict registration budget is spent and without echoing the text. The page has no JavaScript, so no
  live counter.
* The body cap of the form is **16 384 bytes** (was 4 096): 500 three-byte characters are up to 4 500 bytes URL-encoded, the name up to 2 700 more.
* **The occupancy line stays binary** ("Plätze frei" / "Ausgebucht -- Warteliste möglich", no number). This is a decision of V1.9.204: a number on a page
  anybody can open lets a stranger watch an organisation fill up. Members see the counter inside the app. Do not "repair" this.
* Details: link:event-registrations.adoc[Event registrations].

== Order of the detail page (V1.9.140)

Facts, cover image (4:3, at most 36 rem wide, left-aligned), description, status callout (ended / closed / full), then the registration card and, in the standard presentation, the share bar
(see <<public-sharing.adoc#,share buttons>>; that is also the only reason the detail page can carry `script-src 'self'`). The registration card used to sit above the
description, so the visitor had to get past the form to read about the event; now the text comes first.

The card carries `id="anmeldung"`. The "Plätze" row ends with a same-page link "Zur Anmeldung" (`href="#anmeldung"`, no `target`, in both modes)
only while registration is possible *and* the description is not blank. Occupancy stays binary: the row never shows a count.

== Robots (V1.9.140)

The token and follow-up pages -- registration POST, thanks, waiting list, cancelled, storno, payment (including the hand-off page and the `303`),
ticket page, `ticket.svg`, `ticket.pdf` -- send `X-Robots-Tag: noindex, nofollow` on every response, set as the first statement of the handler so that
404, 429, 400, 500 and redirects carry it too. Their HTML bodies, and every error page of the family, also carry
`<meta name="robots" content="noindex, nofollow">`; in the embed mode this replaces (never duplicates) the plain `noindex`. The detail page (`200`)
never sends the header and, in the standard mode, has no robots meta. `Referrer-Policy: no-referrer` was already set on all HTML responses.

== Passing the mode on

Every family-internal link and redirect is built by `EventPageContext.href(...)`, which appends `embed=1` (or `lang=xx` in the standard mode).
The POST routes read the mode from the query string of the form action, not from a hidden field. Links in e-mails (storno, payment, ticket)
are built without the parameter on purpose: a mail is not an iframe.

== Framing rules

[cols="2,2,2"]
|===
| Response | `frame-ancestors` | `X-Frame-Options`

| Standard mode (any configuration)
| `'none'`
| `DENY`

| `?embed=1`, embed feature off (`LAPIS_EMBED_ENABLED` not `true`)
| `'none'`
| `DENY`

| `?embed=1`, embed feature on
| `'self'` plus the origins of `LAPIS_EMBED_ALLOWED_ORIGINS`
| not sent
|===

Each origin is checked once more against `scheme://host[:port]` before it reaches the header. `img-src` is `'self' data:` in the standard mode (the
navigation icons are CSS masks with `data:` URLs) and `'self'` in the embed mode.

== Paid events inside an iframe

A payment provider cannot be framed. In the embed mode a payment-required result is therefore a `200` page "Zahlung abschließen" with a link to the
checkout that opens in the top-level window (`target="_top"`), instead of a `303` inside the frame. The return URLs of the provider carry no
`embed` parameter, because after the checkout the visitor is top-level anyway.

== Language switcher and tokens

The switcher of the token pages (storno, payment, ticket) always points at the detail page, so a bearer token or ticket code never appears in a
chrome link.

== Using it on a website

[source,html]
----
<iframe src="https://cloud.example.org/veranstaltung/sommerfest?embed=1"
        title="Anmeldung Sommerfest" width="100%" height="900" loading="lazy"></iframe>
----

Do not add a `sandbox` attribute, or it must include `allow-forms allow-top-navigation-by-user-activation allow-popups`. The height is fixed: there is
no script, so there is no automatic height.

[kuml, public-event-page-flow, svg]
----
stateDiagram(name = "Public event page flow") {
    val start = initialState()
    val detail = state(name = "Detail page")
    val thanks = state(name = "Thanks")
    val waitlist = state(name = "Waiting list")
    val cancelled = state(name = "Cancelled")
    val handoff = state(name = "Payment hand-off (embed)")
    val provider = state(name = "Payment provider")

    transition(source = start, target = detail)
    transition(source = detail, target = thanks) { trigger = "free event, seat free" }
    transition(source = detail, target = waitlist) { trigger = "event full" }
    transition(source = detail, target = cancelled) { trigger = "honeypot / closed" }
    transition(source = detail, target = provider) { trigger = "paid, standard: 303" }
    transition(source = detail, target = handoff) { trigger = "paid, embed=1" }
    transition(source = handoff, target = provider) { trigger = "link, target _top" }
}
----

The diagram omits the parameter for readability: in the embed mode every transition between pages of this family carries `embed=1`.

== Recurring events (V1.9.243)

A series is one entry on `/veranstaltungen`: its earliest still-upcoming public, published date, with a small "repeat" mark, a one-line
sentence ("Jeden ersten Montag im Monat") and a link "Alle Termine (n)" to the anchor `#weitere-termine` of that date's page. The last
remaining date of a series shows "Letzter Termin dieser Serie" and no link. Single events render exactly as before. The `/veranstaltungen`
cap of 50 counts entries, not dates.

The detail page of a series date shows, in the STANDARD mode only, the block "Weitere Termine dieser Serie" after the registration card:
the sentence, "Noch n Termine, bis ...", and the other public upcoming dates (the first five open, the rest inside a closed `details`
element, at most 50 in total, then "... und n weitere Termine"). The block also shows on the page of a date that has already taken place.
Each row can carry two tags: *geändert* (the date was edited on its own -- every "only this date" edit sets `series_detached` -- or moved
away from its original slot) and *Warteliste* (that date is full). The embed variant (`?embed=1`) has no block, because its site-relative
links would leave the frame.

`n` counts the dates that exist as `event` rows and are public, published and not yet over; the rule is never expanded, so a series that is
only partly materialised shows a smaller `n`. A moved date that was edited before it was detached still belongs to its series (`series_id`
is kept), so it counts.

== Member-aware registration (V1.9.259)

The detail page knows who is looking at it, and the guest form no longer tells whether an address belongs to an account.

=== Signed-in visitors

The page reads the **session cookie only** (never `Authorization: Bearer`, never the test-only `X-Member-Id`), and never in the embed mode (there the
cookie is not even read). A visitor counts as signed in when the session is valid, the status is `ACTIVE`, `FRIEND` or `GUEST`
(`MemberStatusSets.EVENT_SELF_REGISTRANT`) and the row is not anonymised; every other case renders the signed-out page byte for byte.

The registration card of a signed-in visitor shows "Angemeldet als <name>", a button "Zur Veranstaltung anmelden" (a body-less
`POST /veranstaltung/{slug}/anmeldung/konto`) and, below a divider, the guest form headed "Weitere Gäste anmelden" with the sentence that the form is
**not for the visitor's own registration but for further guests**. With a current registration (`CONFIRMED`, `WAITLISTED`, or a `PENDING_PAYMENT`
whose hold has not lapsed) the button is disabled (`disabled`, `aria-disabled`, `aria-describedby`), a note says why and a link leads to the member
area (to pay, or to manage). A signed-out STANDARD visitor sees a hint above the guest form: members should sign in first.

Headers of the signed-in page: `Cache-Control: private, no-store`, `Vary: Cookie`, `Referrer-Policy: same-origin` (with `no-referrer` Chromium sends
`Origin: null` on a form POST, which the strict check below would refuse). Signed-out STANDARD responses keep `no-store` and add `Vary: Cookie`;
the embed responses are unchanged. None of them sets a cookie.

=== The button POST

`POST /veranstaltung/{slug}/anmeldung/konto` runs in this order: attempt limiter, embed refused (404), `isStrictSameOriginFormPost` (403 with a fixed
page and no effect otherwise), content length, public event (404), session lookup (no session: `303` to the detail page), strict registration
limiter, then the same registration code as the member RPC (`MemberEventSelfRegistration`). Success, a waitlist place and "already registered" all
answer `303` to `/veranstaltung/{slug}#anmeldung` (post/redirect/get). A paid event answers `200` with the hand-off page (provider link with
`target="_top"`), **not** a `303` to the provider: Chrome checks a form's redirect target against `form-action`.

`isStrictSameOriginFormPost` is stricter than `isSameOriginRequest`: `Sec-Fetch-Site` (if present) must be `same-origin`; an `Origin` must match
(the literal `null` fails); without `Origin` the `Referer` must match; with neither header the request is refused.

=== The guest form and the address of an account

Binding order of `POST /veranstaltung/{slug}/anmeldung` (a reordering is a review blocker):

. noindex marker, attempt limiter, content length and type, honeypot, validation, event lookup and `PUBLIC` check, strict registration limiter (as before);
. `probeAvailability`: the reasons that do not depend on the address (closed: `404`; waitlist full or payment not available: `303` to `/abgebrochen`);
. **one** account query (`GuestAddressAccountMatcher`) for the normalised address;
. an address of an account: nothing is stored, nobody is told, the lock-and-sweep of a placement is run, and the owner gets a notice mail (once per
  event and address per 24 hours, 100 per hour overall); otherwise a guest registration with `deferCheckout = true`;
. every accepted case ends in the same `303` to `/danke` (no registration id in the URL).

A duplicate guest address gets a short "already registered" mail under the same limits, with no new token. The mails carry no text of the visitor
(`logRecipient = false`, purposes `event-registration-member-notice` and `event-registration-duplicate-notice`).

A **paid** event no longer sends a guest to the payment provider from the POST: the seat is reserved (hold: 30 minutes) and the confirmation mail
carries "Jetzt bezahlen" (`/veranstaltung/{slug}/zahlung?token=...`, the same token as the cancel link). That keeps a network round trip out of the
request, which a member address would never have had. `GET /zahlung` therefore sends no `form-action` directive (its POST answers with a `303` to the
provider). The provider's success return is `/veranstaltung/{slug}/bezahlt`; `/danke?r=` of older sessions still works (the id is ignored).

== Known limitations

* `/aktuelles/{slug}` got the same two modes in V1.9.130 (link:public-article-page.adoc[Public article page]); the header core is now shared (`applyPageModeHeaders`) without any change in the event headers.
* `ticket.svg` and `ticket.pdf` send no `Referrer-Policy` (only CSP, `nosniff`, `no-store`, `noindex`); harmless, as neither document loads or links anything.
* The "Zur Anmeldung" link has not been tried on a phone.
* No automatic iframe height.
* `/veranstaltungen` has no calendar or date filter, so a series cannot be expanded there; the exception for it is gone and the link to the detail page is the way in.
* The repeat mark's tooltip works on hover only (not on touch); the same sentence is printed in the row below it.
* The CSP `form-action 'self'` against the `303` to the payment provider has not been verified in a live browser (pre-existing). Since V1.9.259 the
  payment-confirmation page (`GET /zahlung`) sends no `form-action` for that reason, and the signed-in button answers with a hand-off page instead of a
  `303`; neither has been tried in a real browser.
* The JSON embed endpoint `POST /api/embed/v1/event/{slug}/registration` is unchanged: it still stores an address of an account as a guest and still answers
  `PAYMENT_REQUIRED` with a URL (see the KDoc of `embedEventResponseFor`).
* The notice-mail limiter lives in the process: a restart resets it, and a flood of distinct keys evicts the oldest first. The global cap bounds the damage.
* A capacity side channel remains: with exactly one free seat, a guest address fills it and the page then shows "Ausgebucht", an account address does not.
  Rate limits bound it; it is not closed.
* The two branches of the guest form do comparable database work (one account query, the event lock and sweep, a mail enqueue) but their running time
  is not identical; it has not been measured.
* The session cookie is `SameSite=Strict`: arriving through a link from another site shows the signed-out variant until the next navigation.
