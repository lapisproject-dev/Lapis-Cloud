= Travel expense reimbursement (V1.4.11, PdV form V1.9.122, SEPA file V1.9.123)
:toc:

NOTE: V1.9.122 reworks the editor and the calculation to follow the PdV travel expense form (template 2024, notes of
23.07.2025). The V1.4.11 text below still describes the state machine, the four-eyes rule, the receipt handling and
the booking, all unchanged; the sections "PdV form (V1.9.122)" and "Settings and contact person" describe what is new, and the
limitations list at the end names what the new model deliberately does not do.

Any authenticated member can file a self-service travel expense report for a board/functionary
trip — "board and functionaries" describes the real usage, not a technical restriction. A report
carries one **day line per travel day** (the day allowance, see below) plus further lines: **mileage**
(kilometers × an operator-configured rate), and four receipted kinds -- **public transport**, **accommodation**,
**hospitality** and **other** (a fixed amount plus at least one uploaded receipt). (Before V1.9.122 there were three kinds: mileage, a flat
**per diem** and generic **receipted**; reports created then stay readable and submittable.) A line's kind is fixed once created — no dropdown,
separate "add line" actions instead. A draft can be edited freely; `submitReport`
(`DRAFT -> REQUESTED`) validates every line, requires a rate to be configured for every kind
actually used, and **freezes** each mileage/per-diem line's rate into `rate_snapshot` — a later rate
change never retroactively changes an already-submitted report. BOARD/ADMIN decide in a queue at
`/travel-expense-approvals` (**not** TREASURER, same narrower gate `/contribution-relief` already
established) with a mandatory decision note on both approval and rejection, and a **four-eyes rule
that closes a gap the contribution-relief queue leaves open**: neither the report's subject nor
whoever submitted it "on behalf of" them may decide it (`decideReport`'s own `ForbiddenException`
covers both `subjectMemberId` and `requestedBy`). Approval books an EXPENSE-side debit per line
against an operator-configured `travelExpenseAccountId` and one CREDIT for the total against the
payment bank account (`TravelExpensePostingBridge`) — the first "money out" bridge in this
codebase — in the same transaction as the decision; a failed booking (unconfigured/inactive/
wrong-type account, or a transient cash-register shortfall) leaves the report `APPROVED` with a
recorded `executionError`, retryable via a dedicated RPC method exactly like the contribution-
relief precedent. Receipt files travel over dedicated HTTP routes (never Kilua RPC), with the
declared `Content-Type` discarded entirely in favor of a server-side magic-byte sniff
(`application/pdf`/`image/jpeg`/`image/png` only, deliberately no `image/svg+xml`), a 10 MiB
streaming cap, and an IDOR gate on download (subject/requester/BOARD/ADMIN only). See
`docs/architecture/travel-expenses.adoc` for the full state machine, booking shape, and security
model.

== PdV form (V1.9.122)

=== The day grid

`createDraft`/`updateDraft` keep **exactly one `DAY_ALLOWANCE` line per travel day** (at most 31 days). The member fills one row per
day (V1.9.181; a `fieldset` per day, one line from 50 rem of grid width, stacked below): an optional destination, departure and/or arrival time (which fields appear depends on the day's *position* in the trip, see below), and the three meals that were
provided -- each with a short label and the percentage and amount it takes off shown under the box. The return time is optional on a single-day trip (a note says that without departure and return no daily allowance is calculated) and on the last day. While Von/Bis in the header form differ from the saved range, a notice above the rows says the travel days are updated after saving; the rows themselves are created by the server and are not rebuilt live. "Tage speichern" calls `saveDays`; the server recomputes **every** amount with the shared
calculator -- the client shows the same numbers live, as a clearly marked preview ("Vorschau -- nicht gespeichert"), but never supplies one.

[cols="1,3"]
|===
| Position | Time rule

| single day
| departure and arrival, arrival not before departure; duration = arrival − departure

| first day
| departure only; the day runs until 24:00, duration = 24:00 − departure

| middle day
| no times; always 24 h

| last day
| arrival only; the day starts at 00:00, duration = arrival
|===

The position rule lives in `MultiDayRule` -- **the one place** that decides how an arrival/departure day counts (the statute, section 9 paragraph 4a EStG,
pays a flat amount for those days on a trip with an overnight stay; the form and the design team ask for a count by hours; this is documented
as an open question to the treasurer in the CHANGELOG). Night trips across midnight are **not** added up, and a daylight-saving shift is
ignored (wall clock without a time zone).

=== Tiers, meals, rounding

* Three ascending thresholds in hours (default **8 / 14 / 24**) and three amounts (default **6,00 / 12,00 / 28,00 EUR**). The thresholds are **inclusive**
  ("ab", as printed on the form): exactly 8 h already earns the first tier. `PerDiemTierRule` is the one place.
* A provided breakfast / lunch / dinner reduces the day by a percentage (default **20 / 40 / 40 %**) of the **third tier's** amount. Each deduction is
  rounded **HALF_UP to whole cents** (the single rounding rule of the whole calculation); the sum of the deductions is **capped at the day's
  allowance** (a day never goes negative).
* An overnight stay **with breakfast** supplies the breakfast of the following mornings: the server deducts it whatever the client sends, and the grid shows
  the box checked and locked with the reason.
* Mileage: whole kilometers 1..5000 times the mileage rate, plus the **passenger surcharge** (default 0,02 EUR per km and passenger, 0..8 passengers).
  The mileage rate has **no default** (`NULL` = not offered), exactly as in V1.4.11.
* Everything is calculated in whole cents with overflow checks; nothing uses floating point.

=== Advance, payout, donation waiver

The member may enter an **advance** already received and **must choose** how to settle, **without a preselection**: *Auszahlen* (pay out) or
*Spendenquittung (Aufwandsverzicht)* (waive the reimbursement and ask for a donation receipt). The donation receipt itself is issued **outside
Lapis**. The payout amount is `total − advance` and never negative; an advance **above the total** is not supported (submit refuses it and points
to the contact person).

=== Submission

`submitReport` additionally requires: a payout choice; complete day times (a day that cannot be calculated is refused, never frozen as 0);
a receipt on every public-transport, accommodation, hospitality and other line (a **map proof for mileage is optional**); a total above 0.
It **freezes the whole rate set** as JSON in `rates_snapshot` (so a later settings change never touches a submitted report) and the member's
membership number in `membership_number_snapshot` (may be empty). The informational submission deadline is 31 December of the travel year: a hint
is shown after it, **it never blocks**.

=== Booking

With an advance and/or a donation waiver the credit side splits (see `docs/architecture/travel-expenses.adoc`): *bank* for the payout,
*advance account* for the advance, *donation-waiver income account* for a waived amount -- never the bank, because no money flows.

=== Date format follows the locale (V1.9.132)

The date fields of the travel expense screens (travel from / to, first night, SEPA execution date) are typed and shown in the order and with the separator of the person's locale, not as ISO text.

* The label carries no pattern. The field shows the pattern as placeholder and as a hint ("Format: TT.MM.JJJJ", `DD/MM/YYYY` in English, ...) which `aria-describedby` reads.
* Since V1.9.137 the order, the separator and the clock come from the fixed table of nine locales in `TemporalLocale.kt` (see xref:locale-dates.adoc[Dates and times in the UI locale]); there is no `Intl` probe and no browser call any more. German is always day-month-year with dots; English is `en-US` (month/day/year, 12 h) only when the browser language is exactly `en-US`, otherwise `en-GB`. The digits are always written by the application.
* Input is read strictly in the locale order, never guessed: `03/04/2026` is 3 April in day-month-year and 4 March in month-day-year. A four-digit-first ISO date (`2026-03-04`) is accepted in every locale. A year with fewer than four digits is refused ("Bitte das Jahr vierstellig eingeben"), years outside 1900-2999 are refused, and impossible dates (31 April, 29 February 2025) are named as such.
* **Deliberate deviation from rule R24** ("the hint names the format, never the message"): the error message of these fields names the pattern, because the same date is `22.11.2033` or `11/22/2033` depending on the locale.
* Leaving the field rewrites a valid entry to the canonical form (`5.3.2026` becomes `05.03.2026`); an invalid entry stays exactly as typed. What is sent to the server is always an ISO date.
* The travel expense screens also *display* their dates in this order (period line, deadline, legend of the day grid, accommodation line). In English that means `DD/MM/YYYY` or `MM/DD/YYYY` there, while the rest of the application still shows ISO dates. Moving `DateTime.kt` onto the same mechanism is a follow-up.

=== Meal deductions shown per meal (V1.9.132)

Each meal checkbox of the day grid says what it takes off: "Frühstück gestellt (20 % = −5,60 €)". The amount is the shared `MealDeductionRule` asked for exactly one meal against the 24-hour tier, so rounding (half up per deduction) is the calculator's own; the client adds no rule. The locked breakfast of an overnight stay shows its amount as well.

Two notes appear under a day when a checked meal changes less than its label promises: "Kein Tagegeld an diesem Tag, daher kein Abzug." (the day earns no allowance) and "Abzug auf den Tagessatz von ... begrenzt." (the meals together exceed the day's allowance). They are linked to the checkboxes with `aria-describedby`.

=== Live breakdown (V1.9.132)

"So setzt sich der Betrag zusammen" is a table below the editor (after the totals bar in reading order): gross daily allowance, meal deductions, each mileage line as `km x rate` (plus passengers), the other cost lines by kind, the sum, the advance and the payout (or the donation waiver). One collapsed `<details>` per travel day shows that day's own calculation (duration, allowance, each meal with its percentage, the cap, the day amount). Open days stay open and keep their focus while the figures change.

* Every figure comes from the shared `TravelExpenseCalculator` or from a stored line; the rows always add up to the calculator's subtotal.
* A draft uses the current rates. A submitted or decided report (own list, approval screen) uses **only** its frozen `ratesSnapshot`; without one the page says so and shows no numbers.
* A mileage line is split into own and passenger kilometres only when the two parts add up to the stored amount to the cent; otherwise only the stored amount is shown.
* It is not a live region. The sentence a screen reader hears stays the totals bar's job (one region, debounced).

== Settings and contact person

The ADMIN-only page **`/travel-expense-settings`** (sidebar: System → Reisekosten-Einstellungen) holds: the three tiers (hours and amounts), the three meal
percentages, the mileage rate and passenger surcharge, the legacy flat per-day rate (only for reports created before V1.9.122), the two optional account
mappings (advance, donation waiver) and the **contact person** (name, e-mail, phone, free hint text) that every member sees at the top of the travel
expense page. "Standardwerte der PdV-Vorlage übernehmen" only **fills the form**; nothing is saved until "Speichern". **This is where the contact
person is entered** -- the block stays empty ("Kontaktdaten werden noch ergänzt.") until an administrator does so; nothing is pre-filled.

Ranges (validated by the server before the database): tier hours 1 ≤ h1 < h2 < h3 ≤ 24; tier amounts 0 ≤ a1 ≤ a2 ≤ a3 ≤ 100,00 EUR; meal percentages
0..100; passenger surcharge 0..0,20 EUR/km; mileage rate 0,01..1,00 EUR/km (whole cents); contact fields trimmed, blank becomes `NULL`, e-mail validated
(no CR/LF), phone `^[+0-9 ()/\-]{3,40}$`, hint plain text only.

CAUTION: The default values are the **PdV template** -- provisional and PdV-specific, *not* the statutory 14 / 28 EUR. They are database column defaults and
therefore take effect on **every** instance until an administrator reviews them; the settings page says so in a fixed notice.

=== The calculation core in one picture

The pure functions live in `lapis-shared` (`commonMain`, so the server and the browser run the very same code); the server persists what they return.

----
classDiagram(name = "Travel expense calculation core") {
    val rateSet = classOf(name = "TravelExpenseRateSet") {
        attribute(name = "tierHours", type = "List<Int>") // 8, 14, 24 -- inclusive
        attribute(name = "tierCents", type = "List<Long>") // 600, 1200, 2800
        attribute(name = "breakfastPercent", type = "Int") // 20, of tier 3
        attribute(name = "mileageCentsPerKm", type = "Long") // null = not offered
        attribute(name = "passengerCentsPerKm", type = "Long") // 2
    }
    val multiDay = classOf(name = "MultiDayRule") {
        operation(name = "positionOf") { returns("DayPosition") }
        operation(name = "absenceMinutes") { returns("Int") }
    }
    val tier = classOf(name = "PerDiemTierRule") { operation(name = "tierFor") { returns("Long") } }
    val meals = classOf(name = "MealDeductionRule") { operation(name = "deductionCents") { returns("Long") } }
    val calculator = classOf(name = "TravelExpenseCalculator") {
        operation(name = "day") { returns("CalcResult<DayResult>") }
        operation(name = "mileage") { returns("CalcResult<Long>") }
        operation(name = "totals") { returns("Totals") }
    }
    val snapshot = classOf(name = "ratesSnapshot (JSON, frozen at submit)") { attribute(name = "version", type = "Int") }

    association(source = calculator, target = tier) { target { multiplicity("1") } }
    association(source = calculator, target = meals) { target { multiplicity("1") } }
    association(source = calculator, target = rateSet, id = "uses") { target { multiplicity("1") } }
    association(source = rateSet, target = snapshot, id = "frozen") { target { multiplicity("0..1") } }
}

== SEPA credit transfer file (V1.9.123)

A booked report (`EXECUTED`, payout choice `PAYOUT`) can be put into a **SEPA credit transfer file** (ISO 20022 `pain.001.001.09`) that the treasury uploads in the
online banking of the organization. This is the missing step between the booking ("Zur Auszahlung gebucht") and the money: Lapis Cloud **creates the file and marks
the reports as exported -- it does not send anything to a bank and does not know whether a transfer was executed.**

=== How it works

. *Refund account.* In the draft, below "Vorschuss und Auszahlung", the member enters the IBAN for refunds and the account holder (pre-filled with the member's own
  earlier account, and with the member's name). The IBAN is validated (country, length, check digits, SEPA area) and stored **encrypted** (`SecretBox`, AES-256-GCM, bound to the
  report); screens and the Art.-15 export only ever show the masked end (`IBAN •••• 2051`). After submission only the *member* can change the account (never the requester,
  never the board); the change is flagged on the report ("Konto nach Einreichung geändert") and audited without the IBAN. Reports created before this release have no account:
  the member sets it on the existing report or the treasury transfers by hand.
. *Selection.* On the approvals page, section "Zur Auszahlung bereit" (BOARD/ADMIN), booked reports are cards with a checkbox. A report that cannot be selected keeps a
  disabled checkbox and shows the reason as text: not booked, waived as a donation, nothing to pay out, no refund IBAN, own report, amount differs from the booking,
  encryption key missing, already exported. The bottom bar shows "N ausgewählt · Summe X".
. *Dialog.* "SEPA-Datei erzeugen" opens a dialog that names the sum, the number of transfers, the debit account (a choice only if there is more than one bank account) and the
  execution date (default: the next TARGET2 business day). "Datei erzeugen und als exportiert markieren" creates the file, **marks the reports as exported in the same
  transaction** and downloads it. The file is never stored and **cannot be downloaded a second time**; the list "Bisherige SEPA-Dateien" holds metadata only.
. *Upload.* The treasury uploads the file in the online banking as "Sammelüberweisung / SEPA-Datei (pain.001)". Test it with the check tool of your own bank first.

=== Rules the server enforces

* *Four eyes, identical to approving and retrying a booking:* the subject and the requester of a report can never export it (an own report in the selection refuses the **whole** export, nothing
  is filtered silently); the person who approved it may -- they are not the beneficiary.
* *Double-payment protection:* a report that is marked as exported cannot be exported again. The only way is "Erneut exportieren …" with a reason of 10 to 500 characters (which must not
  contain an account number); the dialog names the first export. A re-export creates a new file with an `-R<n>` suffix on the EndToEndId, increases a counter (at most 99) and is audited.
  Two parallel exports of one report: exactly one wins (row lock), the other sees "already exported".
* *Amount invariant:* the transferred amount is `total − advance` in exact cents, read from the database -- never from the browser -- and compared with the CREDIT posting on the
  payment bank account of the booked journal entry. If they differ the report is blocked ("Betrag weicht von der Buchung ab"), so file and booking cannot drift apart.
* *Limits:* 1 to 500 transfers per file (no automatic splitting), 0,01 EUR to 999.999.999,99 EUR per transfer. Names are transliterated to the SEPA character set
  (ä -> ae, ß -> ss, é -> e, unsupported characters become `.`) and truncated to 70 characters, the remittance text (`Reisekosten RK-1A2B3C4D vom 20.09.2026`, 140 characters) never contains the purpose of the trip.
* *Execution date:* today up to 60 days ahead, and a TARGET2 business day (not Saturday/Sunday, 1 January, Good Friday, Easter Monday, 1 May, 25 and 26 December). A wrong date is refused with a reason, never moved silently.
* *Rate limit and CSRF:* 10 requests per member and minute (shared by both routes), same-origin check, `Content-Type: application/json`, body at most 64 KiB. The response carries `Cache-Control: no-store`.
* *Privacy:* no IBAN, holder or name ever appears in an audit entry, a log line, an error message, a batch table or the file name.

=== Why `pain.001.001.09`

`pain.001.001.09` is the generation the German DK implementation guidelines use since November 2023 and the same ISO 20022 generation as the `pain.008.001.08` direct debit file this system
already writes (element `BICFI`). `pain.001.001.03` is not supported (different element names). The element `DbtrAgt` is mandatory in this version: without a BIC on the debit account it is
written as `NOTPROVIDED`; the creditor agent is never written (members give no BIC).

=== Operator setup

. Create the bank account under *Einstellungen › Bankkonten* and mark it as default (the file debits this account; an account that was ever used for a file cannot be deleted any more).
. Maintain the organization name (or the SEPA creditor name) in the organization settings -- it is the name of the debtor in the file.
. Set `LAPIS_SECRET_ENCRYPTION_KEY` (the same key that protects mandate and FinTS data). Without it refund IBANs cannot be stored and no file can be created; there is no plaintext fallback.
. The booking account (`paymentBankAccountId`, a *ledger* account) and the bank account that is debited (`bank_account`, an IBAN) are **two different things and are not reconciled by the system** --
  keep them pointing at the same real bank account.

== What doesn't work yet (V1.9.123, SEPA file)

* *Never tested with a real bank upload.* The file is validated structurally (golden file, element order of `pain.001.001.09`) and optionally against the official XSD when `LAPIS_TEST_PAIN001_XSD` points at a local copy -- the XSD itself is not checked in (licence not reviewed).
* Your bank may require another version or its own profile; only `pain.001.001.09` is written.
* There is **no reconciliation**: the system does not learn whether the bank executed a transfer, and "exported" means "a file was created", not "paid".
* No automatic splitting above 500 transfers: select fewer reports and export twice.
* The country list is the one of the IBAN validator (EEA, Switzerland, United Kingdom, Monaco, San Marino, Andorra); Vatican City, Gibraltar and the 2025 SEPA newcomers are missing.
* The ledger account of the booking and the debited bank account are not linked or compared.
* Reports submitted before this release have no refund IBAN until the member adds it.

== What doesn't work yet (V1.9.122)

* The default tier values are provisional; the PdV form's footnote mentions 24 EUR in one place and 28 EUR in another -- 28 EUR is used.
* Thresholds are inclusive ("ab"), not the statutory "more than".
* An arrival/departure day is counted by hours (see `MultiDayRule`), not as the statutory flat 14 EUR.
* Night trips across midnight are not added up.
* An advance larger than the claim is not supported.
* No donation receipt (Zuwendungsbestätigung) generation, no VAT columns. (The SEPA payment file arrived with V1.9.123, see above.)
* The contact person is empty until an administrator enters it.
* The help link on the travel expense page points to `+<platform>/de/help/travel-expenses+` in German and `+<platform>/help/travel-expenses+` in every other UI language.
* Old MILEAGE lines with fractional kilometers cannot be submitted any more (`mileage_fractional_km_reenter`) -- enter the line again.
* A legacy mileage rate stored with sub-cent digits is rounded HALF_UP to whole cents when the rate set is built.

== What doesn't work yet (V1.4.11, partly superseded)

Mileage and per-diem rates are **operator-configured values with no automatic adjustment to
changes in the law** — `NULL` means "not configured", and the affected line kind is disabled in
the form until an ADMIN sets it; there is no rate history, only the currently configured value is
editable, and a submitted report is immune to a later change because its rate is frozen. No
Verpflegungsmehraufwand reduction per the full German travel-expense rules (arrival/departure-day
special cases, cuts for meals provided by the organization) — a flat per-diem × days calculation
is a nachweis aid for the board, not an automated compliance decision, the same framing the
Mittelverwendungsrechnung caveat already uses elsewhere in this document. **No payout** — the end
state reads "Zur Auszahlung gebucht" ("Posted for payout") and means exactly that: a journal
entry. (Payment run: superseded by V1.9.123 -- a SEPA credit transfer file, see above; the file is not a payment confirmation.) No
line-by-line partial approval; rejection with a mandatory reason plus "copy as draft" is the
intended correction path (receipts are not copied — new line ids — and must be re-uploaded). The
Übungsleiter-/Ehrenamtspauschale gap this section used to name here is closed by V1.4.12 as its
own, separate feature and bridge — see "Volunteer/instructor allowance" below; no shared
abstraction was forced between the two domains. The
Gemeinnützigkeit sphere every posting uses is hardcoded to `IDEELLER_BEREICH`, not configurable
(a board trip is practically always ideeller Bereich under Rams' "one account, one field" logic
applied to the sphere; revisit if a Zweckbetrieb-funded trip ever needs this). Receipt files are
**not** removed by a DSGVO erasure once a report has left `DRAFT` — they *are* the accounting
voucher (§147 AO); unlike the contribution-relief wave's Art. 9 free text, there is no automatic
redaction sweep here, because there is no Art. 9 free text to redact and §147 AO already demands
10 years' retention regardless. Inline receipt preview was deliberately not built (attachment-only
download, `nosniff`, no `image/svg+xml` in the allowlist).
