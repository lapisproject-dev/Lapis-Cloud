= Dashboard, signals and navigation registry (V1.9.224)
:toc:

The dashboard answers one question: *do I need to do anything today?* It shows only what the menu cannot tell, and nothing the menu already offers.
Since V1.9.224 there are no destination tiles any more (V1.9.220 had the sidebar as tiles). One new RPC service (`IDashboardService`), no
migration (the index check below found nothing to add), no new setting, no new dependency.

== What the person sees

* **Three chips**: member status, role and the end of the session.
* **A sentence with a link** to "Meine Daten" (password, membership card, leaving).
* **"Gerade angemeldet"** (ADMIN only): the block of the online counts, directly below the chips (see link:online-counts.adoc[Signed-in users]).
* **"Für Sie"**: one card per thing that concerns the person right now. Title = the menu label of the module, one line of reason (cut with
  an ellipsis, the full text in `title`), a count badge only for more than one object. An urgent card (priority 300) has an amber left edge.
  The whole card is the link. Nothing for a module the person's menu does not show.
** While loading: one line "Wird geladen ...", no skeleton. Nothing to show or a failed request: "Im Moment gibt es nichts Neues für Sie." (no toast,
   no retry loop; an earlier list stays when a later refresh fails). An answer after the person left the page is dropped.
** The list is fetched when the page opens and again when the tab becomes visible and the last fetch is more than a minute old.
* The grid follows the width of its section (a container query, not the window): one column below 36rem, two from 36rem, three from 56rem.

== The signals

Every row is read from the caller's own data unless the "rows" cell says otherwise. Gate = module switch, then status or role, always before the query.
A priority of 300 is "urgent", 200 "action", 100 "information". `LIMIT` is 50 per query.

*Honest differences from what one might expect*

* Elections, consensus processes and votes have no scheduled end in the data model (only the actual moments `voting_closed_at` and similar), so their
  cards are always "action", never "urgent", and carry no date. Only polls have a real deadline.
* There is no "settlement open" state for auctions (settlement is atomic); that is why `auction.won` / `auction.sold` exist, for seven days.
* "Dunning step due" is computed per row in Kotlin and is not a cheap query; the treasurer's signal is the count of overdue contributions instead.
* A tender is nudged only if `tenderBidderEligible` allows the bid (it is the rule `submitBid` and the screens use). The conflict-of-interest rule
  does not prevent a bid and is not part of it.

== How a signal reaches the screen

* `DashboardSignalSource` per module (`dashboard/sources/`), listed once in `DashboardSources`. The collector runs all sources in ONE transaction, each
  in its own savepoint: a failing source costs only its own signals, and on PostgreSQL the transaction stays usable. The log line names the module key and the exception class,
  nothing else.
* The collector validates every signal (`params` only digits or ISO dates, an id only for a count of one, known keys, count 1..99) and sorts: priority
  descending, earliest deadline (none last), module, reason. The client sorts identically.
* A deadline is an ISO local date-time in the *organization wall clock*, seconds precision, whatever clock the column has (class A values are converted).
* The server never sends a route. The signal carries a module key and (for exactly one own object) its id; the client builds the route from a fixed
  table (`DashboardSignalRoutes`), uses the detail screen only where there is one and the id looks like a UUID, and draws the card only if the person's
  menu shows the module.
* All texts are chosen on the client (`DashboardSignalTexts`), singular and plural as whole messages.

== Cache and limit

* Signals are cached for 20 seconds, the sidebar counters for 30 seconds, per (member, role, status): a role or status change gets a new key at once.
  A cache hit costs no database access and no budget.
* An uncached call is limited to 12 per minute per member and method. Over the limit, the last answer (up to ten minutes old) is served; without one the
  call is a `ConflictException` and the client shows nothing.
* The status is read fresh from the database on every uncached call; an anonymous caller is rejected by both methods before anything else.

== Sidebar counters "(aktiv/gesamt)"

* "Videokonferenz" and "Begegnungsräume" show `(active/total)`. *Total* is the number of rooms that are OPEN right now, not the number that ever existed (an ended
  room disappears from the list the same way). *Active* are those with at least one participation whose `left_at` is empty. For the conference the rooms are exactly the
  ones `ConferenceService.listActiveRooms` lists (event rooms and encounter sessions excluded, one shared predicate). For encounter spaces, archived ones are not counted,
  and a guest or friend counts only the spaces that admit non-members.
* The figures come from the database only (`NavCountsQuery` has no media-server client, a tripwire pins that). A room whose last participant left a moment ago may
  read "active" for up to about 90 seconds (cache 30 s plus the 60 s poll). A guest sees the conference as 0/0 (the conference needs an active membership).
* The poller is one object for the whole page (`NavCountsPoller`): the sidebar is rebuilt often (language change, phone off-canvas) and every rebuild
  replaces its bindings instead of adding timers. It asks while the tab is visible, at once when a tab that was hidden for more than a minute becomes visible, and it
  stops at sign-out. A failure keeps the last figures; there is never a toast.
* The suffix is a child element of the link (`aria-hidden`), never part of the label: the menu search does not index it, and the counters of the
  approval entries that overwrite the label do not erase it. With a total of 0 nothing is shown. The accessible name is "Videokonferenz, 2 von 5 aktiv".

== One list for the sidebar and the menu search

`NavRegistry` holds every destination once: route, label, icon, group (or flat), the visibility predicate and, for two entries, the live suffix. The sidebar
(`buildSidebar`) builds from it; the dashboard uses it to decide whether a card's module is in the person's menu and for the card's icon and title.
The only live parts that stay in `Sidebar.kt` are the open-request counters (a later wave may move them to a shared mechanism with the new suffix) and the
visibility of the member finder.

`SidebarGoldenTest` pins the sidebar (route, label, icon, order, group headers) for member, member with chapter and finder, treasurer, board, admin, friend
and guest. `DashboardHasNoMenuDuplicatesDomTest` pins that the dashboard repeats no destination of that sidebar.

== Deliberately not signalled

* Messages (badge in the navbar), carpool (sidebar badge), travel-expense, volunteer-allowance, contribution-relief and article approvals (the sidebar already
  shows a counter: a second one would be a duplicate).
* Open registration in my groups (not a cheap query), settlement of an auction (no such state), deadlines of elections, consensus and votes (no such column).

== How to add a signal

. Add the reason key to `DashboardReasonKeys` (and the module key to `DashboardModuleKeys` if new) in `lapis-shared`.
. Write a `DashboardSignalSource` in `dashboard/sources/`: gate first through `SignalGates` (never `== ACTIVE` inline), then an indexed query on the caller's own rows with
  `ORDER BY` (a unique tiebreaker) and `LIMIT`; reuse the existing rule (`computeAuctionOutcome`, the `*OwnParticipation` helpers, `isCommitteeEligible`), never rebuild it.
  Return `emptyList()` for "not eligible", never an exception. List the source in `DashboardSources`.
. Client: a text (singular and plural, as whole messages) in `DashboardSignalTexts`, the two catalog entries per language (`messages.pot` and the seven `messages-*.po`), the route
  in `DashboardSignalRoutes`.
. Tests: a positive and a negative case in `DashboardSignalScenarios` (H2 and PostgreSQL), one case that the serialized signal contains no foreign title or name, and the
  statements are picked up by `DashboardQueryPlanPostgresTest` (extend its fixture so the new source reaches all its queries). A migration (V121) is justified only by a failure of that test.

== Honest limits

* Tested with unit tests, DOM tests in headless Chrome and PostgreSQL tests, plus one look in a local browser. Nothing was looked at on a real phone, with a real screen reader or on a real instance.
* The texts of the new messages in the six non-German catalogs were written by the model, not by a native speaker.
* The figures of the counters are a snapshot of the database, not of the media server.
