= Recording and live streaming in event rooms (V1.9.156)
:toc:

The online room of an event (`LAPIS_CONFERENCE`, see link:event-online-participation.adoc[Online participation in events]) can be recorded and streamed live --
*if the operator allows it, if the board releases the event and if everybody who is in the room has acknowledged the consent*. The instance switch is **off by default**;
since V1.9.280 a newly created Lapis-conference event is released by default once the operator switched the feature on.
The design and the threat model are in link:../architecture/conference-recording.adoc[docs/architecture/conference-recording.adoc], section "Event rooms (V1.9.156)".

IMPORTANT: Whether and under which conditions persons may be recorded and streamed depends on the **country** of the instance (data protection, personality and
copyright law; at political or religious events also the special categories of Art. 9 GDPR). Lapis Cloud does not decide that and is not legal advice. It makes the
feature opt-in on three levels, puts the responsibility with the operator in writing, and keeps a nameless proof that every participant acknowledged the consent
text. The texts shown to the persons concerned are drafts the operator replaces with legally reviewed ones -- and the feature **cannot be switched on before the
operator has published its own consent text**.

== Switching on

. *Instance (ADMIN):* page Organisation, section "Aufzeichnung & Übertragung", part "Veranstaltungen": "Aufzeichnung und Übertragung in Veranstaltungsräumen erlauben". The switch opens the
  operator notice (four paragraphs, version in the foot); "Einschalten" stays locked until the legal-check box is ticked. The switch is locked with a hint and a link
  while the consent text (`EVENT_REC`, tab "Aufzeichnung (Veranstaltung)" under "Vertragstexte") is still the built-in placeholder. The audit entry records the notice
  version and the hash of the German reference text. Switching **on** is refused while a released event is active (people who entered while it was off acknowledged
  nothing); switching **off** is refused while any event room records or streams (nothing is stopped remotely -- the moderator ends it first).
. *Event (BOARD/ADMIN):* the event form has the box "Aufzeichnung und Übertragung erlauben" (only for a Lapis conference and only while the instance switch is on). Since V1.9.280
  the box of a NEW event is ticked by default (until the person touches it) and travels with the event (`EventInput.captureAllowed`); an existing event shows its stored value and
  changes it with its own call (`setEventCaptureAllowed`). Both are audited as `EVENT_CAPTURE` (creation: `CREATE`, `source` = `default` or `explicit`; change: `UPDATE`, flag `afterStart`)
  with the event id and flags only. See "Default for new events" below.
. *Room:* the moderator starts and stops the recording and the stream in the room exactly as in an ordinary room. The recording of an event room is stored `BOARD_ONLY`
  (or `ADMIN_ONLY`); `PUBLIC_MEMBERS` is refused.

== Releasing after the start (V1.9.280)

The release of ONE event is no longer frozen while the room is active:

* *Switching ON works at any time*, also while the window is open and people are inside. The people inside have acknowledged nothing yet, so they are asked **in the room**
  (see "Consent inside the room"). Nothing is recorded or streamed before all of them agreed.
* *Switching OFF* is refused only while a recording is running (`RECORDING`, `STOPPING`) or a stream is not over (including `PAUSED`):
  `EventCaptureStillCapturingException`, change lock `CAPTURE_RUNNING`. The check runs under the row locks of the event and the room, so it cannot interleave with a start.
* The **instance** switch keeps the old freeze (`EventCaptureLock.isActive` / `anyReleasedEventActive` are unchanged): people who entered while it was off acknowledged nothing.
  Because more events are released by default now, switching the instance feature back ON is refused more often while such an event is active.

The entry path re-reads the release under the row lock of the event (lock order: event, then room). A release that is granted while a person is being let in is noticed
there and that person is refused. A kind of the event other than the Lapis conference drops the release.

=== Default for new events

`EventCaptureDefaults.resolve(explicit, onlineKind)` is the one place that decides: a new event is released iff the online kind is a Lapis conference **and** the instance
switch is on with the current notice; an explicit `false` always wins; an explicit `true` while the switch is off is silently `false`. The default lives in code, never in
the database (`event.capture_allowed` keeps `DEFAULT FALSE`), so no path that does not go through it can release an event by accident. Existing events are never touched.

[cols="2,2,3",options="header"]
|===
|Path |Value |Why
|`createEvent` (UI, API, MCP) |`resolve(input.captureAllowed, kind)` |The form's box travels in the same transaction as the event.
|`createEventSeries` |`resolve(template.captureAllowed, kind)` per occurrence |An explicit `false` applies to every occurrence; one audit entry per released occurrence.
|Series edit (`applyEdit`), `updateEvent` |unchanged |An edit never grants or withdraws a release.
|Event importer |`false` |Past events; a release is meaningless.
|Sitzung announcement (`MeetingEventLinkOperations`) |`resolve(null, kind)` |No explicit choice exists on this path. The start gate and `SecretBallotStreamLock` stay in force.
|Staging seeds |`false` |Deterministic seeds.
|===

== Consent inside the room (V1.9.280)

[cols="1,3",options="header"]
|===
|Piece |Behaviour
|Ask |`EventCaptureLiveBroadcaster` (consent pass: every 2 s while a recording or stream runs, otherwise every 5 s, and right after a release change or an acknowledgment) compares the people in the room with the proofs of the CURRENT text. Everybody who is connected and lacks a proof gets the packet `lapis-event-capture-ask` (`{"v":1}`), point to point. The client shows a blocking dialog: "Zustimmen und bleiben" or "Ablehnen und Raum verlassen". Declining is leaving (no server call, nothing stored); Escape does nothing.
|Acknowledge (member / guest with an account) |`IEventService.acknowledgeEventCaptureInRoom` -- needs an open participation, refuses a stale text, throttled (the join budget), idempotent.
|Acknowledge (guest without an account) |`POST /api/events/{slug}/online-guest/capture-consent`, body `{token, consentVersion, consentSha256}` (the token is in the body, never in a URL). The LiveKit token is verified (HS256, issuer, expiry, an `evg-` subject, the room of this event). A guest token lives only about 15 minutes, so an EXPIRED token is still accepted when everything else is valid and that identity is connected in LiveKit right now (otherwise a guest who has been inside for a while could never answer the ask). `204` recorded, `409` text changed, `429` throttled, everything else one uniform `403`.
|Count for the moderators |Packet `lapis-event-capture-count` (`{"v":1,"n":N,"m":M}`), point to point to the moderators who are connected: "Zustimmung zur Aufzeichnung: N von M". Numbers only -- nobody sees who agreed or who is missing, and "pending" and "declined" are not told apart. A polite live region is fed at most once per 1500 ms.
|Gate at the start |`EventCaptureConsentGate`, called only from `EventConferenceGuard.requireEventCaptureAllowed`: the start is refused (`EventRoomCaptureConsentMissingException`, no name, no number) while any identity in the room lacks a proof of the current text (version AND hash). Counted are LiveKit identities, guests with a minted token who have not connected yet (a minted identity that was seen connected and then left, or reloaded under a new identity, is not counted any more), and open participations; the egress is left out; every other identity counts as missing; the placeholder text acknowledges nobody. If LiveKit cannot be asked the start is refused (fail closed, `ServiceBusyException`) -- after the authorization and availability checks. The start buttons are `aria-disabled` with the reason while the count is below the total.
|While something captures |Whoever is in the room without a proof is removed (connection cut, participation closed) within the 2-second pass. This covers a return with an old, still valid LiveKit token, the return from a breakout (which is also refused up front while something captures) and a connection made between collecting the presence and committing the start.
|===

Lock order: the join and switching OFF lock the event row and then the room row; the start locks the ROOM row only and reads the event row and the proofs without locking
them (a start that locked the event after the room would deadlock with them).

== What a participant sees and acknowledges

[kuml, event-capture-consent, svg]
----
sequenceDiagram(name = "Entry into a released event room (V1.9.156)") {
    val person = participant(name = "Person")
    val client = participant(name = "Client")
    val server = participant(name = "Server")
    val db = participant(name = "Database")

    message(from = person, to = client, text = "opens the event")
    message(from = client, to = server, text = "getEventCaptureState / online-state")
    message(from = server, to = client, text = "consent text (version, hash), only if required")
    message(from = person, to = client, text = "ticks the consent")
    message(from = client, to = server, text = "join with version and hash")
    message(from = server, to = db, text = "re-check the release under the event lock")
    message(from = server, to = db, text = "write the proof, in the same transaction")
    message(from = server, to = client, text = "token, initial banner state")
}
----

* *Members* (and guests with an account): the screen "Aufzeichnung und Übertragung in diesem Raum" with the headline, three key points and the full text behind a
  disclosure, one box, "Teilnehmen" locked until every box is ticked. A guest account also sees the **capture variant** of the guest notice with its own box on the
  same screen (the old notice says "Es wird nichts aufgezeichnet.", which would be false). Reconnecting after a lost connection does not ask again as long as the text is
  the same; a new version always asks.
* *People without an account* (`#/event-join/<slug>`): the same consent block above the guest notice, both boxes required; the request carries both versions and
  hashes. `409` means "the text or the release changed": the page reads the state again.
* The server decides and checks; the client never decides. A client that sends no consent for a released event is refused; the old `joinEventOnline` refuses it too.
* *Everybody inside* sees a line (dot and words, `role="status"`, no close button, no animation) while the room is recorded and / or streamed. It follows the state
  sent by the server as a LiveKit data packet (`lapis-event-capture`, only packets without a sending participant are accepted) and the state in the join answer.

== The proof (`event_capture_acknowledgment`)

[cols="1,3",options="header"]
|===
|Column |Meaning
|`event_id` |The event (FK, no cascade; deleting an event deletes its proofs first).
|`member_id` / `guest_key` |Exactly one of them (CHECK). `guest_key` = HMAC-SHA256 hex of the LiveKit identity (`evg-...`) of a person without an account, keyed with a domain-separated sub-key of the LiveKit API secret. It names nobody and, without the server secret, cannot be linked to a registration or a ticket hash (the identity of a ticket holder derives from `event_registration.ticket_code_sha256`, so an unkeyed hash would have made the table an online attendance list by name). The server can match it with the track files of a recording (whose participant identity it is), which is what the proof is for. Rotating the LiveKit API secret makes old keys unmatchable with later recordings.
|`consent_version`, `consent_sha256` |What was acknowledged (the live `EVENT_REC` text, or its version and hash at the moment of entry).
|`acknowledged_on` |A DATE of the organization zone -- no clock time, no room, no name.
|===

Unique per event, subject and version, so an entry is idempotent and a new text is a new proof. The table is part of the organization backup. In the GDPR export a member sees
their own proofs (event title, version, day); an erasure *retains* the proof (Art. 5(2), 7(1) GDPR: it is the organization's record that the consent was acknowledged
before the image could be recorded) -- it carries no name and no time of day.

== What a moderator sees when capture is blocked (V1.9.158)

The room DTO carries `eventCapture` (`ConferenceEventCaptureState`). Only a moderator of the event room (its creator, or BOARD/ADMIN) receives the concrete reason; every other caller sees `EVENT_ROOM`.

[cols="2,3,3"]
|===
|State |Meaning |What the moderator sees

|`EVENT_ROOM_CAPTURE_AVAILABLE` |switch on with the current notice and text, event released, Lapis conference |record and stream buttons work; the start dialog offers "Vorstand" and "Administration" only
|`EVENT_ROOM_CAPTURE_BLOCKED_BY_ADMIN` |instance switch off, operator notice outdated or the consent text still the placeholder |buttons are `aria-disabled`, the line under the bar names the administration
|`EVENT_ROOM_CAPTURE_BLOCKED_BY_ORGANIZER` |the event is not released, or it is no Lapis conference |buttons are `aria-disabled`, the line names the organizers
|===

The administration's reason has precedence, because the organizer could not help. A start that the server still refuses (the switch changed while the room was open) throws `EventRoomCaptureBlockedByAdminException` or `EventRoomCaptureBlockedByOrganizerException`; the client corrects its state and shows the same text. These typed exceptions are thrown after the moderator check, so a stranger only ever receives `ForbiddenException`.

== Known limitations

* Nothing was verified in a real browser, in a real call, against a real LiveKit or a real egress. A rehearsal on staging (a guest without an account, a participant egress, an RTMP stream, the banner) is the next step before a real event.
* The proof does not show what a third party does with the stream (screenshots, their own recordings); the software cannot prevent that.
* A person without an account now leaves a nameless proof in a released event (until V1.9.155 such a person left no row at all).
* The banner can be up to 5 seconds late for transitions that only a poller makes; it never switches off because of a failed send.
* The instance feature cannot be moved while an event room records or streams, and the start reads the settings without the lock the switching side takes.
* *A new consent text cannot be published while a recording or stream of an event room runs (V1.9.280).* Every proof would be stale at once and the consent pass would cut everybody out before the first person could answer; the publication is refused with `EventCaptureBusyException` until the capture is over.
* *Window of up to 2 seconds (V1.9.280).* LiveKit tokens cannot be revoked. A person who was in the room before the release was switched on, left it, and returns with the old
  token while something captures is on the recording until the next consent pass (at most 2 seconds) removes them. This is accepted and stated openly; the alternative would be to
  forbid switching ON after the start, which defeats the purpose.
* `LiveKitParticipantInfo.kind` (`EGRESS`) was not verified against a real LiveKit. If LiveKit does not report it, the egress counts as an unknown identity and the gate refuses
  (fail closed) -- it could block the start of a second capture.
* The in-room texts are unreviewed drafts; whether such a question is sufficient depends on the law of the country. Their translations are model translations.
* No per-person opt-out of the picture inside the room (a person who does not want to be recorded leaves, or keeps camera and microphone off).
* The built-in consent text is a draft; the translations are model translations.
* *A guest's screen share (V1.9.282).* A screen share that a moderator allowed to one guest without an account is recorded and streamed like the share of a member
  (it shows that person's desktop). The moderator sees a standing hint while a recording or stream runs. The consent text is unchanged and covers the pictures of
  participants; whether it also covers a shared screen needs a legal review, which is outstanding.
