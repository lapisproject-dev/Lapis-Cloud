= Online participation in events (V1.9.113)
:toc:

An event can now be attended online *through Lapis itself*. The event form replaces the former single "Online-Link" field with
one choice of four kinds (`EventOnlineKind`):

[cols="1,3",options="header"]
|===
|Kind |Meaning
|`NONE` |On-site only.
|`EXTERNAL_LINK` |A link of your own (the behaviour before V1.9.113): optional https URL, optionally shown publicly.
|`LAPIS_CONFERENCE` |Lapis creates a video conference when the first person joins (see below).
|`LAPIS_ENCOUNTER` |Participants enter a permanent encounter space (`Begegnungsraum`) chosen on the event.
|===

A place and a Lapis conference can be combined: that is a hybrid event, there is no switch for it.

== The window

Access opens *30 minutes before* the start and closes *60 minutes after* the end (`EventOnlineWindow`, the only place
that computes it). Both bounds are inclusive and are wall clocks of the organization zone (time class B); the stored
`event_conference.window_*` columns are UTC (class A). A conference event may last at most 12 hours. Rescheduling an event moves the
window; a conference that is already running vetoes a change that would remove its basis.

== Who may enter

`decideEventOnlineAccess` decides in this order: authorization first, then the window. An unauthorized caller always receives the same
`FORBIDDEN` answer, so the call cannot be used to probe whether an event exists or what its window is.

* *Members* join through `IEventService.joinEventOnline`. A registration (not waitlisted, not cancelled) or moderator role is required
  for events with registration; public events without a registration deadline are open to anybody with the link.
* *Guests without an account* use the public page `#/event-join/<slug>`. They confirm the guest notice
  (`EventGuestNotice`, version and SHA-256 are checked server-side), enter a display name (normalized, suffix " (Gast)") and receive a
  short-lived token with identity prefix `evg-`. Protection is a per-IP and per-event rate limit, an own-origin check, a 4 KiB body cap
  and a uniform HTTP 200 answer. A moderator sees the guests of the event and can remove one. For an event that is *not* released for recording no row is
  written about such a guest; for a released one (V1.9.156) a proof *without a name* is (see link:event-capture.adoc[Recording and live streaming in event rooms]).
  Account-less guests are capped per room (the non-member ceiling) and a quarter of the room's seats stays reserved for members and
  moderators. For events with a registration deadline the identity is derived from the ticket, so one confirmed ticket holds at most one
  live connection (a second use replaces the first). Guests are subject to the room-wide audio rules (lock, mute all, reconciler) like
  every other non-moderator.

*Donors (V1.9.298).* A donor takes part in a *public* event only (the visibility rule of a non-member) and is never a moderator. Inside the room a donor is treated like a member: no guest notice, the member token lifetime, not counted against the guest cap.

== Devices in the guest call view (V1.9.272)

The lean call view of an account-less guest (`EventGuestCallView`) has a "Geräte" section with microphone, camera and, where the browser
can switch the output (`setSinkId`) and lists at least two real outputs, a speaker field. It opens by default on screens from 768 px, closed
below; the "Geräte" button carries `aria-expanded` and `aria-controls`.

* *Permission rule:* the page never opens the browser's permission dialog on its own. Until the browser lists the devices the fields show
  "Erst nach Freigabe verfügbar" and the usual button "Zugriff auf Mikrofon und Kamera erlauben" is the only way to ask (one click, every
  acquired track is stopped at once). A blocked browser gets an explanation, not a dialog. Microphone and camera stay off.
* *Privacy rule:* nothing is remembered between visits (no browser storage), no device id or label is sent anywhere or written to a log, and
  a label appears only as the text of an option. `ClientEventGuestDevicePrivacyTripwireTest` pins this as a source scan over
  `EventGuestCallView.kt`, `EventGuestDevicePanel.kt` and `ConferenceDeviceSelectWiring.kt`.
* *Truthful state line:* the bold line at the top names the real state ("Sie sind in der Videokonferenz. Ihr Mikrofon ist aus. Ihre Kamera
  ist aus."); the grey line below it carries only notes and errors (a device that vanished, a switch that failed).
* The select wiring is shared with the member call screen (`wireConferenceDeviceSelect`); the member screen additionally remembers the
  chosen id, the guest view never does.

== Conference creation (claim protocol)

The room is created exactly once, on the first successful join, by `EventConferenceProvisioner.ensureRoom`:

[kuml, event-online-join, svg]
----
sequenceDiagram(name = "First join of an event conference (V1.9.113)") {
    val person = participant(name = "Person")
    val service = participant(name = "EventService")
    val store = participant(name = "EventConferenceStore")
    val livekit = participant(name = "LiveKit")

    message(from = person, to = service, text = "joinEventOnline")
    message(from = service, to = store, text = "insertPending, claim_token")
    message(from = service, to = livekit, text = "createRoom, outside any transaction")
    message(from = service, to = store, text = "activate, fenced by claim_token")
    message(from = service, to = person, text = "join token")
}
----

LiveKit is never called inside a database transaction. A concurrent joiner receives `PREPARING` and retries; a stale claim can be taken
over, and `activate`/`markFailed` are fenced by the `claim_token`, so a slow first caller cannot overwrite the successor. The poller
(`EventConferencePoller`, every 60 s) ends conferences whose window has closed and orphaned rooms.

== Isolation from ordinary rooms

An event room is entered *only* through `joinEventOnline`. `EventConferenceGuard` refuses the ordinary conference RPCs (join, rename,
guest access, meeting binding, recording, streaming) for an event room, and the room lists never show it. Since V1.9.156 the recording and the stream do not refuse
an event room outright any more but ask one decision function, `EventConferenceGuard.requireEventCaptureAllowed` (instance switch, release of the event, Lapis
conference), at exactly two places; every other function keeps the plain refusal. Tripwire tests
(`EventConferenceGuardTripwireTest`) force a decision for every new room-id method.

== Screen share of a guest without an account (V1.9.282)

A person who joined without an account may share their screen **only while a moderator allows exactly this person** (the single most sensitive
thing a guest can add to a room that may be recorded or live-streamed).

* *The token never carries it.* The guest join mints its token with `ParticipantSourcePolicy.EVENT_GUEST`: `canPublishSources` is always set, never empty,
  and lists only `microphone` and `camera` (`camera` alone while the room is locked). Before V1.9.282 a guest token with the microphone allowed carried no
  source list at all, which LiveKit reads as "every source" -- a guest with their own LiveKit client could already share the screen. The reconciler
  (below) also covers guest sessions that were still running with such a token at the deploy.
* *Grant and withdrawal are moderator RPCs* (`IConferenceModerationService.setGuestScreenShare`, `guestScreenShareState`, appended at the end of the
  interface). There is no guest route and no guest action token for it; a guest has no member session, so a forged call is refused like any other
  unauthorised call. Order: member session, role (the room creator or BOARD/ADMIN, `ConferenceModeratorAuthority`), the room is an event room, rate limit,
  the target must be an `evg-` identity, per-guest rate limit, then LiveKit. Every refusal is the same `ForbiddenException`.
* *At most one guest per room.* A second request answers `TAKEN`. The grant lives in `EventGuestScreenShareGrants` (in memory, no table, no migration) **and**
  in the LiveKit permission of that one participant (`guestConferencePermission`, which names `SCREEN_SHARE` and `SCREEN_SHARE_AUDIO`).
* *Bound to the participant session.* The registry stores the LiveKit participant sid. LiveKit gives a new sid at every join and refreshes the token of a
  connected client with its current permission, so a guest who reconnects (also with the same deterministic ticket identity, or with a token kept from the
  time of the grant) loses the grant; an ICE resume keeps the sid and with it the grant. A server restart empties the registry and the reconciler then takes
  every guest share back: *the moderator has to allow it again after a restart.*
* *Withdrawal stops a running share.* Registry first, then the permission without the screen share sources, then a mute of every screen share track, a
  bounded re-read (3 times, 300 ms apart) and, if a track is still switched on, `RemoveParticipant` (outcome `REVOKED_REMOVED`). A mute is **not** a hard
  boundary (LiveKit has no server-side unpublish; a modified client can switch the track on again) -- see `EventGuestScreenShareReconciler`.
* *Audit.* One entry per grant and per withdrawal (`GUEST_SCREEN_SHARE_GRANT`, `GUEST_SCREEN_SHARE_REVOKE`, `GUEST_SCREEN_SHARE_REVOKE_REMOVED`), carrying
  the HMAC guest key of `EventCaptureAcknowledgments.guestKeyOf` -- no name, no raw identity, no time list.
* *In the guest view* the button "Bildschirm teilen" is built once (after "Kamera", before "Hand") and shown only while the own LiveKit permission names the
  screen share (an empty source list counts as *not* allowed) **and** the browser has `getDisplayMedia`. Phones therefore see no button and read one calm
  sentence. "Teilen beenden" is always possible. Withdrawing the permission stops a running share on the guest's side at once. The sentences go through a
  polite `role="status"` region at least one second apart.
* *The moderator* sees a "Gäste" section in the Moderation sheet (event rooms only): one row per guest with the state in words ("Darf den Bildschirm nicht
  teilen" / "Darf den Bildschirm teilen" / "Teilt gerade den Bildschirm") and the button "Bildschirm teilen erlauben" or "Freigabe entziehen"; while a
  recording or a stream runs a standing hint says that a shared screen is part of it.
* *What other participants can see.* LiveKit reports the permission of a participant in its `ParticipantInfo` to the other participants of the room, so other
  guests may be able to tell who may share. This is accepted and not prevented.
* *Recording and stream.* A guest's screen share is recorded and streamed exactly like a member's (`RecordingPoller` starts a track egress for every unmuted
  `SCREEN_SHARE` track of an acceptable identity; `isScreenShare` picks the presentation layout). The consent text is **not** changed by this wave: it
  covers the pictures of participants; a legal review of whether it also covers a shared screen is outstanding.

== Configuration

`LAPIS_EVENT_CONFERENCE_MAX_PARTICIPANTS` (default 100, clamped to 2..1000). Seats are `min(event capacity or 25, ceiling)`.
`IConferenceService.getAvailability` reports the ceiling as `eventMaxParticipants`.

== Known limits

See the V1.9.113 entry of `CHANGELOG.md`: no load test was run, the ceiling of 100 is an assumption, the flow was not verified in a real
browser against a real LiveKit, guests are not part of the participant history, guests cannot enter encounter spaces. An event room is never recorded or streamed
*unless* the operator, the board and every participant agreed (V1.9.156, link:event-capture.adoc[Recording and live streaming in event rooms]); the guest notice
"Es wird nichts aufgezeichnet." is only used for events that are not released -- a released event shows the capture variant of the notice instead.

*Consent inside the room (V1.9.280).* A release can be switched on after people entered. Everybody who is then in the room without a proof of the current consent text is asked
in a blocking dialog ("Zustimmen und bleiben" / "Ablehnen und Raum verlassen"); declining is leaving. A member answers with `acknowledgeEventCaptureInRoom`, a person without an
account with `POST /api/events/{slug}/online-guest/capture-consent` (the LiveKit token proves who they are; the token travels in the body). The moderators see only "N von M", never
a name. See link:event-capture.adoc[Recording and live streaming in event rooms].

* A removed account-less guest keeps a valid token for up to `guestTokenTtlMinutes` and LiveKit has no identity blocklist, so the person
  can reconnect with the same token until it expires. Re-minting a token is bounded by the rate limits only.
* A flood of join requests can still use up the per-event hourly budget of the route (rate limiting is per IP/prefix and per event).
* While the conference runs, narrowing who may take part (visibility away from PUBLIC, a new or changed registration deadline) is refused;
  the kind cannot change either.
