= Partner servers (V1.9.244 wave P1, V1.9.245 wave P2)
:toc:

Lapis Cloud servers can be connected as **partners**. In wave P1 a server fetches the *public events* of the servers an administrator has entered. The partners have to set nothing up: every Lapis Cloud
server already publishes the feed. Wave P1 collected the data of the *direct* partners; **wave P2 (V1.9.245)** follows the partner lists of those partners
(partners of partners, up to three additional levels) and **shows the cached events on the public pages** with their origin.

NOTE: The `[kuml]` blocks of the architecture page are rendered and validated by the `:docs-render:renderDocs` Gradle task.

== What an administrator does

On the page *Organisation* the section **Partnerserver** has one button, "Partnerserver verwalten" (`/organization/partner-servers`, ADMIN only):

. Enter the address of the partner (`partner.example.org`; `https://`, a trailing slash or a path are tolerated and dropped) and, optionally, a display name.
. "Prüfen und speichern" makes **one** request to the partner. The partner is stored only if it answered with a valid feed; the page then says how many events were found.
. The list shows per partner: name, host, a status with a symbol *and* words (fetched, waiting until HH:MM, paused, blocked), the last fetch, the number of cached events and the last error as a plain sentence.
  "Aktiv" pauses and resumes the fetching; "Entfernen" deletes the partner and its cached events.
. **Sperrliste**: a host (`spam.example.org`) or all sub-domains of a host (`*.example.org`) that is never fetched and never shown. A new block deletes the cached events of every matching partner at once. A block always wins over a partner.
. "Eigene Partnerliste im Feed ausblenden": other servers then do not see who this server is connected with.

Every change is written to the audit log (`PARTNER_SERVER`, `PARTNER_BLOCKLIST`): the kind of change and the host or pattern the administrator typed, never a name from a foreign feed.

== What leaves this server (our feed)

`GET /api/public/partner-feed/v1` -- no sign-in, rate limited (30 requests per minute and client, `429` + `Retry-After`), the body memoised for 60 seconds, `ETag`/`If-None-Match` (`304`).
It repeats exactly what `/veranstaltungen` and `/veranstaltung.ics` already show anybody:

* public, published events that have not ended and start within 365 days (a series is **one** entry: the next date plus the repeat sentence), at most 500 events and 512 KiB;
* per event: id, title, start and end with the UTC offset, the organisation's time zone, an online yes/no, the location text, the short summary, the public page URL;
* the own server id and name, and -- unless hidden -- the list of active, not blocked partners (host and name).

**Never**: an online URL, the long description, capacity, fee, registrations, members, creators, drafts, cancelled or members-only events.

== What we fetch

Once an hour per partner (the minute is spread per partner so that servers do not all fetch at the same second), plus once when the partner is added. At most 50 partners per run, four at the same time.
A failed fetch is retried after 1, 2, 4, 8, 16 and then 24 hours; the cached events stay until they expire (6 hours after the last successful fetch or `304`).

Limits: 5 s to connect, 10 s for the whole request including the body, 512 KiB, no redirects, `application/json` only, at most 200 events per partner, at most 100 entries of the partner's own partner list.

== Wave P2: partners of partners, origin and filter

*Behaviour change first.* The recursion is **on by default** (depth 2), and `/veranstaltungen` now lists the cached events of partners next to the own ones by default. `/veranstaltung.ics` is unchanged without a parameter.

* **Switch and depth.** *Organisation > Partnerserver > Partner von Partnern*: "Auch Partner der Partner einbeziehen" (default on) and "Zusätzliche Stufen" (1 to 3, default 2). Level 1 is a direct partner, level 2 a partner of a
  direct partner, and so on. Switching off hides every event of level 2 and deeper at once and the next poller tick deletes them; lowering the depth does the same for the levels that are now too deep.
* **When it runs.** Once an hour (plus a fixed per-server offset of up to five minutes), after the direct partners, by the same poller, through the same fetcher (https on port 443 only, address guard and IP pinning, no redirects, 512 KiB, 10 s).
  A run takes at most five minutes; what is left follows in the next run.
* **What it follows.** The stored partner list of every active, not blocked direct partner, breadth first. A host is contacted at most once per run; this server itself and every direct partner (also a paused one) count as already visited.
  A partner that hides its list is not followed further; its own events are still shown.
* **Bounds.** At most 20 hosts are taken from one server's list, 15 per direct partner and 40 per run; at most 100 events per reached server and 2000 in total; at most 60 stored servers per direct partner and 200 in total.
  Servers not fetched for a while come first, so the caps rotate over the runs.
* **Where the origin is shown.** Every foreign event on `/veranstaltungen` carries a line "Partnerserver: Name" (direct partner) or "Partnerserver: Name (host) · über Name" (reached through a partner). The link opens the origin's own page,
  with `rel="noopener noreferrer external"`, no referrer, no new tab, and the words "(externe Seite)" for assistive technology; the arrow is decoration only.
* **Filter.** `/veranstaltungen?quelle=eigene` lists only this server's events (`noindex`); `?quelle=alle` and no parameter list both. The two links "Alle" and "Nur eigene" appear only when there is something to filter. An unknown or
  repeated value redirects to the plain URL. A recurring partner event is one entry with the sentence "Reihe: ...".
* **Calendar feed.** `/veranstaltung.ics?quelle=alle` additionally contains the partner events (own first, at most 500 entries, at most 50 partner entries and 10 per origin, `CATEGORIES:Partnerserver`, the origin line in `DESCRIPTION`).
  Without the parameter -- or with any other value -- the feed is exactly the own events, as before. A partner series is one entry for its next date, **without** a repeat rule.
* **Block list.** A pattern hides the host itself *and* everything that was reached through it. A block takes effect on the public page at once (read-time filter plus a counter that empties the 30-second server-side memo) and the
  cached events and servers are deleted in the same transaction. Browsers and proxies may keep the page for the `max-age` of five minutes.
* **Not shown elsewhere.** The member area (`EventsScreen`) lists this server's own events only. The partner events are never passed on in our own partner feed or in the embed feed.
* **Admin page.** Switch, depth, the state of the last run in words and numbers, the list of reached servers (name and host as plain text, level, chain "über a -> b", events, state) with a "Sperren" button, and per direct partner
  the line "Über diesen Partner: n Server, m Veranstaltungen".

== Honest limits

* **A partner cannot make this server fetch from just any host -- but it can make it ask a few.** Within the bounds above a partner can list hosts that are not Lapis servers; each is asked once per hour for the feed path (see the
  reflector note in the architecture page). The switch turns this off.
* **A server id is bound to one host.** The first id a host announces is kept; a later different id is the error "meldet eine andere Kennung", and a second host claiming an already bound id is refused.
  This is what stops a malicious partner from overwriting the cached events of another one.
* **Staging and backup.** The own server id lives in `organization_settings` and is part of the backup. A staging instance restored from a production backup has the *same* id as production: the two then
  refuse each other as "this server itself". Accepted in P1; a later "create a new id" action is possible.
* The partner events cache (`partner_event`) and the reached servers (`partner_discovered_server`) are **not** part of the backup (refilled caches of foreign data); the partner list, the block list and the recursion settings are.
* **Partner series in the calendar feed** are one entry without a repeat rule: the feed carries a sentence, not a rule.
* **No subscribe link.** The overview page has no link to the calendar feed (it had none before); `?quelle=alle` is for people who build the subscription address themselves.
* **HTTP cache.** `Cache-Control: public, max-age=300` is unchanged, so a browser or proxy may show a blocked event for up to five minutes.
* Event texts are in the partner's language. The repeat sentence comes as the partner wrote it.
* **Not verified:** a fetch against a real second or third server over the internet -- all tests run on a simulated network of several servers. PostgreSQL behaviour is covered by the `postgresTest` lane.

== Outlook

Merging an event that two partners announce is not needed so far: an event (announced server id plus event id) is stored once, whichever path reaches it first. Further extensions need their own review.

See link:../architecture/partner-server-feed.adoc[the architecture page] for the contract, the limits and the security chain.
