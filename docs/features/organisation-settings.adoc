= Organisation page (V1.9.221)
:toc:

The settings that apply to the whole organization used to sit as separate cards at the bottom of the member administration. Since V1.9.221 they live on one
page, *Organisation* (`/organization`, sidebar group System, ADMIN only), in five collapsible sections (a sixth, *Partnerserver*, was added in V1.9.244: one button to `/organization/partner-servers`, see link:partner-servers.adoc[partner servers]; a seventh, *Aktionen*, in V1.9.246: one button to `/activism/settings`, see link:activism.adoc[actions]). Client only: no migration (schema stays V118), no new
RPC, no DTO change. Every switch and form calls the RPC it called before; the server still enforces ADMIN on each of them.

== Rules

* Each section is a native `<details>` element, closed at first. The `<summary>` shows an icon (decoration, `aria-hidden`), the title and one line with the
  current values. Keyboard and screen readers work without script.
* The content of a section is built when it is opened for the first time, never twice. A section nobody opens makes no request of its own.
* The summary lines come from one read of the organization settings and one read of the time zone. A saved change refreshes them; the section stays open.
  If a read fails, its part of the summary stays empty and the sections remain usable.
* Deep link: `#/organization?section=<key>` opens and scrolls to that section. Aliases: `zeitzone` and `mitgliederzahl` open `allgemein`, `overlays` opens
  `videokonferenz`, `stream` opens `aufzeichnung`. An unknown key is ignored. The key is only looked up in a fixed map; it is never rendered.
* There is no old address to redirect from (the cards never had a route). The member administration shows an ADMIN a pointer with a link instead.
* UI rule: settings that save at once are folded with `<details>`; `collapsibleCreateForm` stays for forms that create a record (R36B).

== Online membership application (V1.9.315)

Section *General* carries the switch *Online-Mitgliedsantrag anbieten ("Mitglied werden")* (ADMIN only, audited on change, default *on* on every instance;
schema `V163`, column `organization_settings.membership_application_enabled`). It is written only through
`IOrganizationSettingsService.updateMembershipApplicationEnabled`; the generic settings update never touches it. Switching it off:

* **hides** every "Mitglied werden" link: the login page, the friend registration page, the hero button of the public start page (it becomes "Anmelden") and the
  `join` block of the embed widget on other websites. The registration page itself shows one fixed sentence and a link to the login, never a reason.
* **refuses on the server** every self-service path that creates a membership application: `registerApplication`, `getMembershipAgreement` and
  `applyForMembership` (a friend turning into an applicant) answer one constant `MembershipApplicationClosedException`, independent of the input, as their
  first statement: no database write, no rate-limiter entry, no way to tell an existing e-mail from a new one. A tripwire test keeps it that way.
* leaves untouched: registration as a friend or guest, the list of regional chapters, applications already received and the administrator and board paths
  (`approveApplication`, `rejectApplication`, `createMemberDirect`).
* On an instance in *Keycloak mode* the links are hidden as well, with the switch on or off (the server refuses local self-registration there anyway).

The public start page is cached for up to a few minutes (page cache of 30 s, `Cache-Control: public, max-age=300`): after a change the old button can stay
visible for a while. The server refuses meanwhile. The single-page app shell reads the switch on every page load. A backup made before `V163` cannot be restored,
as after any schema change.
