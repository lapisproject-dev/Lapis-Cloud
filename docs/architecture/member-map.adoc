= Member Map ("Vorstands-Karte")
:description: BOARD/ADMIN-only aggregate view of member geographic distribution at postal-code granularity, on a self-hosted PMTiles/MapLibre basemap.
:toc:
:toc-placement: preamble
:icons: font

== Context

Welle V1.9.5 (second attempt after an aborted first pass, see the CHANGELOG entry for the
Q1-Q7 decisions this wave records). The board wants to see roughly where the organization's
members live -- not to identify individuals, but to answer questions like "do we have members
outside our home region", "would a regional event reach many members", "is our footprint
concentrated in one city". This document describes the resulting data flow and the privacy
boundary that shapes every decision in it.

== Data flow

[source,kuml,name="member-map-data-flow"]
----
sequenceDiagram(name = "Member map -- request paths") {
    val browser = lifeline(name = "Browser")
    val server = lifeline(name = "Lapis Cloud Server")
    val db = lifeline(name = "PostgreSQL")
    val csv = lifeline(name = "Classpath CSV (GeoNames centroids)")
    val pmtiles = lifeline(name = "PMTiles file (operator-provisioned)")

    message(from = browser, to = server, label = "RPC getMemberMap()")
    message(from = server, to = db, label = "SELECT postal_code, country WHERE status IN MEMBER_MAP_ELIGIBLE AND anonymized_at IS NULL")
    message(from = db, to = server, label = "rows: (postal_code, country) only -- no id, name, street, city, date")
    message(from = server, to = server, label = "group + count in memory (privacy boundary IS the query shape)")
    message(from = server, to = csv, label = "lookup(postalCode) per distinct code, in-memory index, parsed once per JVM")
    message(from = csv, to = server, label = "place name + centroid, or nothing (unresolvable bucket)")
    message(from = server, to = browser, label = "BoardMemberMapResponse: entries[] + 5 aggregate counts, no identifying field")

    message(from = browser, to = server, label = "GET /api/board/member-map/basemap.pmtiles (Range, hundreds of requests)")
    message(from = server, to = server, label = "auth (BOARD/ADMIN) BEFORE any file probe -- see registerMemberMapRoutes KDoc")
    message(from = server, to = pmtiles, label = "read 127-byte header (PmtilesBasemap.probe, every request) + requested byte range")
    message(from = pmtiles, to = server, label = "header valid -> bytes; anything else -> nothing revealed")
    message(from = server, to = browser, label = "206 Partial Content (never gzip-wrapped) or 404 (never 500)")

    message(from = browser, to = server, label = "RPC searchPlaces(query) -- V1.9.9 Ortssuche")
    message(from = server, to = csv, label = "PlaceSearchIndex.bundled -- built once at startup from the SAME csv, never re-read per request")
    message(from = csv, to = server, label = "ranked List<PlaceGroup>: place name + centroid + postal codes, institution-like rows already excluded")
    message(from = server, to = browser, label = "List<MemberMapPlaceDto>, capped at 8 -- no member data, GeoNames facts only")
}
----

Two entirely separate request paths never cross: the RPC path never touches the PMTiles file, and
the basemap route never touches the database. Vector tile geometry (country/state boundaries,
water, roads) comes from the PMTiles file; postal-code place names and coordinates come from the
bundled CSV; member counts come from PostgreSQL. Nothing about an individual member ever leaves the
first query's result set -- see <<privacy-boundary,Privacy boundary>> below.

[[privacy-boundary]]
== Privacy boundary

The privacy guarantee is enforced by the *shape of the database query*, not by filtering a richer
result afterward:

* `network.lapis.cloud.server.rpc.BoardMemberMapService.getMemberMap` selects **only**
  `member.postal_code` and `member.country` for members in
  `network.lapis.cloud.shared.domain.MemberStatusSets.MEMBER_MAP_ELIGIBLE` (currently just
  `ACTIVE`) with `anonymized_at IS NULL`. No `id`, `display_name`, `email`, `street`, `city`,
  `date_of_birth` or `joined_at` column is ever part of the `SELECT`.
* `member.city` is **never** read by this feature at all -- the only place name shown anywhere
  (table, map popup) comes from the bundled GeoNames postal-code centroid index, never from a
  member's own address field.
* The response (`network.lapis.cloud.shared.domain.BoardMemberMapResponse`) carries only
  postal-code-bucketed counts and five running totals. `BoardMemberMapRpcWireTest` asserts this
  against the *raw* RPC response body, not just the typed DTO, specifically so a future field added
  to the DTO without updating that test's expectations would be caught.
* Role gate: `BOARD`/`ADMIN` only, enforced server-side (`BoardMemberMapService`,
  `registerMemberMapRoutes`) -- this is the actual, currently-enforced boundary, and by itself
  sufficient (a non-BOARD/ADMIN caller gets `ForbiddenException` from the RPC and 401/403 from the
  basemap route regardless of any client). A client-side route guard
  (`requireRole(routing, BOARD, ADMIN)` on `Routes.MEMBER_MAP`) additionally lands as defense in depth
  in V1.9.6. There is deliberately **no** self-service variant -- a member's own location is never
  singled out.
* No export, no print button, no "share" link, no postal code ever appears in a URL -- server-side
  properties, true independent of the client, and the V1.9.6 screen adds no such affordance either.
  The screen carries a persistent notice ("Nur für Vorstand und Administration. Genauigkeit:
  PLZ-Mittelpunkt, keine Adressen. Bitte nicht weitergeben.").

== Classification rules (the three-way split, plus foreign)

`network.lapis.cloud.server.membermap.aggregateMemberMap` partitions every eligible member's
(postal code, country) group into exactly one of four buckets, in this order:

. `!MemberMapRules.isGermanCountry(country)` -> `foreign`. Checked *first*, before postal-code
  shape -- see <<q3>> below: a foreign postal code that happens to look like a valid German one
  (France's `75001`) must never land in either German bucket.
. `!MemberMapRules.isGermanPostalCode(postalCode)` -> `noPostalCode` (missing or malformed).
. The (trimmed) postal code resolves against the bundled centroid index -> `mappedTotal`, with a
  place name and coordinates.
. Otherwise (a valid-shaped German postal code the bundled index has no entry for) ->
  `unresolvableGermanPostalCode` -- an entry with no coordinates, counted separately from
  `noPostalCode` so the board can tell "we don't know this person's postal code" apart from
  "we know it, but our reference data doesn't cover it" (this THIRD category is the concrete
  difference between this wave and the first, aborted attempt at this feature, whose scope had
  collapsed both into one bucket).

Invariant, checked at the end of `aggregateMemberMap` and exercised over 200 random group lists in
`MemberMapAggregationTest`: `total == mappedTotal + unresolvableGermanPostalCode + noPostalCode +
foreign`.

== Degradation matrix

The server side of this matrix is real: `tilesAvailable`/`geodataAvailable` on
`BoardMemberMapResponse` report exactly these two independent conditions, computed fresh on every
call. The "Result" column describes how the V1.9.6 client (`MemberMapScreen.kt`,
`memberMapDegradation`) reacts to each combination. Two independent optional data sources, each
degrading gracefully and independently on the server
(never a hard failure, never blocking server startup -- same posture as
`BrandConfig`/`SmtpConfig`):

[cols="1,1,2"]
|===
| PMTiles basemap | Postal-code centroid CSV | Result

| configured, valid
| bundled, parses
| Full map + full table (place names, coordinates).

| not configured / invalid / missing
| bundled, parses
| Table only (`tilesAvailable=false`), all resolvable entries still have place names and
  coordinates -- the numbers are never worse for a missing basemap.

| configured, valid
| fails to parse (packaging error)
| Map basemap renders, but every valid German postal code counts as
  `unresolvableGermanPostalCode` (`geodataAvailable=false`) -- no place names, no points on the
  map, counts are still exactly right.

| not configured
| fails to parse
| Table only, every valid German postal code unresolvable. The feature never disappears entirely --
  the aggregate counts (the most important numbers) are always correct regardless of either
  source's availability.

| n/a
| n/a (WebGL missing/disabled in the browser)
| A dedicated "the map cannot be displayed in this browser" notice, distinct from the two cases
  above -- the table remains fully available (Q6).
|===

== Q1-Q8 decisions

Q1, Q2, Q4-Q8 below are `lapis-client` decisions -- Q1, Q2, Q4-Q7 implemented in V1.9.6, Q8 in
V1.9.8. Q3 is a server+shared decision, implemented and tested since V1.9.5
(`MemberMapRules.isGermanCountry`).

[[q3]]
* **Q1 -- route and menu placement**: `Routes.MEMBER_MAP = "/member-map"`, menu entry
  "Mitgliederkarte" directly next to "Geburtstage & Jubiläen" in the existing
  Verwaltung/Administration sidebar group -- there is no dedicated "Vorstand" menu section in this
  codebase to place it under instead.
* **Q2 -- attribution text**: a hardcoded, XSS-safe constant
  (`© OpenStreetMap contributors`, linking to `https://www.openstreetmap.org/copyright`) rather
  than trusting the PMTiles file's own embedded metadata HTML (which is missing the word
  "contributors" in the bundled build, and would be an operator-controlled-HTML-into-DOM path if
  used directly). The map's vector source is configured *without* a TileJSON `url`, specifically so
  MapLibre never reads that embedded metadata attribution at all.
* **Q3 -- what counts as "Germany"**: `member.country` is free text with no normalization. Blank/
  unset counts as Germany -- the decisive rule (`MemberMapRules.isGermanCountry`): without it,
  almost every domestic member (whose `country` field was simply never filled in) would
  incorrectly land in the `foreign` bucket. Recognized spellings, case/whitespace-insensitive:
  `de`, `deu`, `d`, `deutschland`, `germany`, `brd`, `bundesrepublik deutschland`.
* **Q4 -- MapLibre version**: `maplibre-gl` pinned to `5.24.0` (last UMD-bundle release before
  `6.x` went ESM-only, which Kotlin/JS's `@JsModule`/webpack interop cannot currently consume
  without extra build-side work). `pmtiles` (the JS `pmtiles://` protocol handler) at `4.5.0`.
* **Q5 -- bundle size**: accepted cost, no code-splitting this wave -- the client ships as one
  `main.bundle.js`, and MapLibre + pmtiles add roughly 230 KB gzipped for every visitor, not just
  BOARD/ADMIN ones who actually use the map.
* **Q6 -- no WebGL**: a distinct notice ("Die Karte kann in diesem Browser nicht angezeigt werden.
  Alle Zahlen stehen in der Tabelle.") separate from the two data-source-degradation cases above --
  the table never depends on WebGL.
* **Q7 -- search**: a screen-local search field (postal-code prefix, or place name from the start,
  case-insensitive) -- this codebase has no generic, reusable table-search component; every screen
  with a search field implements its own, and this one follows that existing pattern rather than
  inventing a shared component as a side effect of this wave.

[[q8]]
* **Q8 -- orientation (V1.9.8)**: live board feedback said the circles could not be matched to a
  region -- nothing on the map named a country, state or place. The bundled basemap's `places`
  vector layer DOES carry the names (`name`/`name:de`), but rendering it as a MapLibre `symbol` text
  layer needs a `glyphs` URL this style has none of, and standing up a glyph-serving pipeline for a
  static handful of labels is disproportionate. Instead: 24 Bundesland-/Nachbarland-labels
  (`MemberMapLabels.kt`) as plain DOM `Marker`s, shown/hidden by a `data-zoom-band` attribute so the
  low-zoom overview is not crowded by all 16 states' full names at once. Alongside this, a hover
  tooltip on points/clusters closes the same "which row is this?" gap without adding a second
  synchronized view of the data to maintain (the always-visible table stays the exhaustive ledger,
  see this document's own top-level KDoc reference in `MemberMapScreen.kt`). Same wave: a bug fix
  where a cluster click never zoomed in, because `maplibre-gl` 5.24.0's
  `getClusterExpansionZoom` is `Promise`-returning, not the Node-style callback the code had been
  written against.
  +
  _(revised V1.9.9, see <<q11,Q11>>: `MemberMapRules.MAX_ZOOM` moved from the vector source's own
  `maxzoom` to a separate constant -- the historical reasoning above stays as written.)_

[[q9]]
* **Q9 -- borders barely visible (V1.9.9)**: direct user feedback -- state and country borders were
  present in the style (`member-map-state-borders`/`member-map-country-borders`) but painted with
  `--lapis-border`/`--lapis-border-strong`, two tokens calibrated for hairline UI dividers on WHITE,
  not for a filled map background; against `--lapis-surface-sunken` the contrast was close to 1:1.
  Fix: three dedicated, higher-contrast tokens (`--lapis-map-border-country`/`-state`/`-road`, all
  three `theme.css` blocks), zoom-interpolated line widths (thin at the overview zoom, thicker once
  zoomed in) instead of one flat width, a dashed style for state borders (visually distinct from the
  solid country border at a glance), and a soft "halo" line under the country border for extra
  separation from the state borders and the highway layer. The highway layer, which used to be the
  LAST layer added (painted over everything, including the borders), now paints first among the line
  layers so borders always sit on top.

[[q10]]
* **Q10 -- Landeshauptstädte (V1.9.9)**: direct user feedback named Magdeburg (Sachsen-Anhalt) and
  Dresden (Sachsen) specifically as missing -- `MEMBER_MAP_LABELS` only ever named the STATE, never
  its capital. `MEMBER_MAP_CAPITALS` (`MemberMapLabels.kt`) adds one marker per Bundesland (16,
  including the three city-states, whose capital is the state itself) as a dot + name, same DOM
  `Marker` technique as Q8, always visible (not zoom-band-gated -- unlike a neighbour country, "which
  city is this state's capital" is useful context at every zoom level).

[[q11]]
* **Q11 -- small localities without a glyph pipeline (V1.9.9)**: the user also asked for smaller
  towns to appear on zooming in. The bundled `places` vector layer carries them, but a real MapLibre
  `symbol` text layer needs a `glyphs` URL -- a new server route serving vendored, third-party
  Noto-Sans `.pbf` glyph files. That route was deliberately **not** built this wave (see below); this
  wave instead reads the SAME `places` source-layer WITHOUT ever adding a style layer for it:
  `MemberMapMapController.updatePlaceLabels` calls `map.querySourceFeatures("member-map-basemap",
  {sourceLayer: "places"})` -- a query against already-fetched vector-tile bytes, independent of
  whether a style layer renders that source-layer at all -- and turns a capped, deduplicated set of
  nearby small-locality names into DOM markers, the same technique as Q8/Q10. Active from
  `PLACE_LABELS_MIN_ZOOM` (9) onward, refreshed on `"moveend"`, capped at 40 simultaneously rendered
  markers. Alongside this, `MemberMapRules.MAX_ZOOM` (the VIEWPORT zoom limit) moved from 10 to 12 so
  a board member can zoom in far enough to tell members' circles apart in a dense small town; the
  vector SOURCE's own `maxzoom` stays at 10 (`BASEMAP_TILE_MAX_ZOOM`, a new, separate constant) since
  the bundled/deployed `.pmtiles` file is extracted at `--maxzoom=10` -- MapLibre overzooms z10 tiles
  past that rather than requesting nonexistent z11/z12 tiles.
+
**Known limitation, not solved this wave**: small-locality DENSITY depends entirely on how the
operator's own `.pmtiles` file was extracted. At `--maxzoom=10` the `places` layer's smaller
`locality`-kind features may be sparse or absent in some regions -- this wave did not re-extract the
bundled/example basemap at a higher `--maxzoom` to keep file size and the operator-facing extraction
instructions unchanged. A future wave could either accept this as documented behaviour, or revisit a
real `glyphs` route (Q8's "disproportionate" judgement reconsidered) if village-level coverage turns
out to matter enough to the board to justify vendoring third-party font assets into the server JAR.

[[q12]]
* **Q12 -- Ortssuche (V1.9.9)**: alongside the existing table filter (renamed "Tabelle filtern (PLZ
  oder Ort)" to disambiguate it from the new field), a second, independent search field sits as an
  overlay in the top-left of the map panel itself. It searches `PlaceSearchIndex`
  (`lapis-server/.../membermap/PlaceSearchIndex.kt`) -- a grouped, ranked index built once at startup
  from the SAME bundled GeoNames postal-code centroid CSV `PostalCodeCentroidIndex` already loads,
  never a new dataset. Postal codes sharing an identical place name are grouped (single-linkage,
  15 km) so "Berlin" returns one result with ~180 postal codes attached rather than 180 near-identical
  rows, while two real, unrelated towns that happen to share a name (e.g. "Bernau") correctly stay
  separate. Institution-like `place_name` rows (`Commerzbank AG`, `Finanzamt Dresden - Nord`, ...) are
  filtered out before grouping -- useful for the original per-postal-code lookup, but noise as
  Ortssuche autocomplete suggestions. Selecting a result flies the map to it
  (`MemberMapRules.PLACE_FLY_TO_ZOOM`) and shows a pin popup with member counts within 5/10/25 km
  (`memberCountsWithinRadii`, Haversine distance over the ALREADY-LOADED `dto.entries` -- no second
  server round-trip, and no new member data crosses the wire: the counts are computed entirely
  client-side from data the board member's own screen already holds). The RPC method itself
  (`searchPlaces`) returns only GeoNames-derived place facts (name, coordinates, postal codes) --
  never a member id, count, or anything else -- and is validated server-side (length 2-50 after
  trimming, no control characters) independent of whatever the client widget already enforces, since
  the RPC route is directly reachable by anyone who can forge a BOARD/ADMIN session. The raw query
  text is deliberately never logged (unlike `getMemberMap`'s aggregate-only log line), since a search
  term is closer to free-text board-member input than five aggregate numbers.
+
**Breaking change to a previously pinned assumption**: `IBoardMemberMapService` was single-method
before this wave, and `BoardMemberMapRpcWireTest` pinned `/rpc/routeBoardMemberMapServiceManager0`
specifically BECAUSE it was the interface's only method. `searchPlaces` is a second, deliberate
method -- `getMemberMap` keeps route index 0 (Kilua-RPC-KSP assigns indices by declaration order),
`searchPlaces` is index 1, and both are pinned now instead of just one.

== No database migration

`member.postal_code`, `member.country`, `member.status` and `member.anonymized_at` have existed
since V1 -- this wave adds no column, no table, and the kUML entity-relationship model is
unchanged. Still true as of V1.9.9: `PlaceSearchIndex` (Q12) is an in-memory index built from the
already-bundled CSV, not a new table.
