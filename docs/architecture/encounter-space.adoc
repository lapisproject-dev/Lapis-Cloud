= Encounter space ("Begegnungsraum"), server and data protection (V1.9.61, wave B1)
:toc:

== Purpose

An *encounter space* is a standing room with a *pulpit* (one or a few people who speak) and a *congregation* (everybody else, who listens).
The first theme is a church service. It is built on the LiveKit conference stack but is a different thing from the ordinary conference
("Besprechung"): the congregation is *listen-only*, the authority comes from an *office* (not from having created the room), and --
because attending a church service can reveal religious belief, a special category of personal data under Art. 9 GDPR -- the system is
built so that **no lasting trace of who attended remains**.

Wave B1 is the server and the data protection; wave B2 (V1.9.62, <<client>>) is the client. B1 adds no client screen: `IEncounterSpaceService` is the RPC
surface, `V73__encounter_space.sql` the schema, `network.lapis.cloud.server.encounter.*` plus `rpc/EncounterSpaceService.kt` the implementation.

NOTE: This document's `[kuml]` blocks are rendered and validated by the `:docs-render:renderDocs` Gradle task.

== Model

A *space* is permanent configuration. A *session* is one running occurrence: an ordinary `conference_room` row that carries
`encounter_space_id`. The session is "open" while its room row has `ended_at IS NULL`. There is deliberately **no `opened_at` /
`current_room_id` column** on `encounter_space` -- it would need a circular foreign key, and the opening time and the opener already are
`conference_room.created_at` / `created_by_member_id`. "At most one open session per space" is enforced by the row lock on the space (see
<<lock-order>>), not by a constraint.

* `encounter_space` -- title, description, `theme_key` (`CHURCH`), `mode` (`SERVICE`), `guest_policy` (`MEMBERS_ONLY` /
  `MEMBERS_AND_GUESTS`), `max_participants` (`NULL` = the instance maximum; the service clamps it to `ConferenceConfig.maxParticipants`),
  `closed_notice` (free text such as "Gottesdienst beginnt um 10:15 Uhr" shown while closed -- no time field on purpose), `archived_at`.
* `encounter_space_role` -- the *office* configuration: who is `PULPIT` or `STEWARD` ("Ordner") of a space. Composite primary key
  `(space_id, member_id)`: one office per member per space. Never the congregation.
* `encounter_consent_acknowledgment` -- the accountability proof of a *non-member's* explicit consent (<<consent>>). Composite key
  `(member_id, consent_version)`, **no room or space reference and no timestamp -- only a date**, so it cannot be read as an attendance record.
* `conference_room.encounter_space_id` -- `NULL` for every ordinary room.

=== States

[source,kuml,name="encounter-space-session-states"]
----
stateDiagram(name = "Encounter space and its sessions") {
    val start = initialState()
    val closed = state(name = "CLOSED (space active)")
    val open = state(name = "OPEN (one session running)")
    val archived = state(name = "ARCHIVED")

    transition(source = start, target = closed) { trigger = "createSpace (BOARD/ADMIN)" }
    transition(source = closed, target = open) { trigger = "openSpace (office holder, BOARD/ADMIN)" }
    transition(source = open, target = closed) { trigger = "closeSpace / poller: EMPTY or MAX_DURATION" }

----

A session is closed for one of three reasons, all audited with the same snapshot shape `{"state":"CLOSED","reason":...}`: `MANUAL`
(`closeSpace`), `EMPTY` (the LiveKit room is gone) or `MAX_DURATION` (older than 12 hours). Closing deletes the LiveKit room and **deletes
every presence row** (<<privacy>>).

== Offices and access

The office is *re-derived from the database on every call*; nothing is cached and the participation row is never an authorization source.
An office only counts while the holder is `ACTIVE`: a withdrawn or rejected member loses it the moment the status changes, with no cleanup job.

[cols="2,1,1,1,1,1,1", options="header"]
|===
| Operation | BOARD/ADMIN | PULPIT | STEWARD | other ACTIVE | GUEST/FRIEND | other status
| list / get / entry info | yes | yes | yes | yes | only `MEMBERS_AND_GUESTS` | no
| create / update / archive / list+set roles | yes | no | no | no | no | no
| open / close a session | yes | yes | yes | no | no | no
| enter | yes (listen only) | yes (may speak) | yes (may speak) | yes (listen only) | yes, after consent (listen only) | no
| leave | yes | yes | yes | yes | yes | yes
| list who is present | only if present | only if present | only if present | only if present | only if present | no
| remove / silence | anybody | congregation only | congregation only | no | no | no
|===

* An archived space is visible to BOARD/ADMIN only (a `NotFoundException` for everybody else); a guest policy miss is a `ForbiddenException`.
* **BOARD/ADMIN without an office listen only** (`canPublish = false`) but may moderate. Speaking requires an office.
* A PULPIT or STEWARD holder may remove or silence only members of the congregation, never another office holder and never BOARD/ADMIN; only
  BOARD/ADMIN may. Nobody moderates themselves.
* `setSpaceRoles` is replace-all, at most 20 assignments, no duplicate member, every member `ACTIVE` at the time of the assignment.

=== The token: two shapes, one service

`LiveKitAccessToken.mintParticipantToken` takes `canPublish` and `canPublishData` as *required* parameters (no default), so the compiler forces
every call site to decide. An ordinary conference passes `true, true` (byte-for-byte the grant map of before). The *congregation* token has
`canPublish = false`, `canSubscribe = true`; a person a steward silenced additionally has `canPublishData = false`. The token is never
`hidden`, never `recorder`, never carries an admin grant. Token lifetime: non-members `guestTokenTtlMinutes` (15), members `tokenTtlMinutes`.

=== The ordinary conference RPC surface is fenced off

The congregation's listen-only token is enforced *by the server when it mints the token*. `ConferenceService.joinRoom` and
`ConferenceBreakoutService.rejoinMainRoomToken` mint tokens with `canPublish = true` for any `ACTIVE` member. If they accepted the id of an
encounter session, any congregation member could ask for a publishing token for the same LiveKit room and speak from the pulpit. That
would make "listen only" worthless, so `EncounterRoomGuard.requireNotEncounterRoom` is the *first* statement of every room-id method of the
six conference services (and of `requireRoomEntryAuthorization`, which the shared entry gate uses).

[cols="2,3", options="header"]
|===
| Service | In an encounter session
| `ConferenceService` | `getRoom`, `joinRoom`, `leaveRoom`, `endRoom`, `listParticipants`, `removeParticipant`, `renameRoom`, `getGuestJoinInfo`, `setRoomGuestAccess`, `setRoomMeeting`, `getRoomVotingState`: all refused. `listActiveRooms` and the lazy reconciliation skip encounter rooms (they would close a session by `left_at` instead of deleting the rows).
| `ConferenceBreakoutService` | every room-id method refused, including `rejoinMainRoomToken` and (defence in depth) `requestBreakoutJoinToken`. `returnToMainRoom` only closes the caller's own assignment row.
| `ConferenceRecordingService` | `startRecording`, `getActiveRecording` refused: a recording would be a lasting record of who was in a church service. **Unchanged since V1.9.143**: the optional pulpit recording is a separate, deliberately narrow path (see "Pulpit recording (V1.9.143)").
| `ConferenceNotesService`, `ConferenceWhiteboardService` | every method refused (attributed, persistent content).
| `ConferenceStreamingService` | allowed, but `startStream` only with layout `SINGLE_PARTICIPANT` on an `ACTIVE` `PULPIT` holder: the congregation never reaches an external platform. `getActiveStream` stays visible to everybody present ("everybody in the room may know a stream runs").
|===

`ConferenceModeratorAuthority` replaces the six private copies of `requireModeratorOrPrivileged`: ordinary room = creator or BOARD/ADMIN
(unchanged), encounter session = `ACTIVE` office holder or BOARD/ADMIN. **The one who pressed "open" has no special right**: an office can be
withdrawn while a session runs and must take effect at once. `EncounterRoomGuardTripwireTest` fails the build if a room-id method stops
referring to the guard.

[#privacy]
== Data protection by construction (Art. 9 GDPR)

* **Presence is transient.** `enterSpace` inserts one `conference_participation` row (at most one per session and person, a reconnect reuses
  it). `leaveSpace` *deletes* it (no `left_at` is ever kept), `closeSpace` deletes all rows of the session, and `EncounterSpacePoller`
  deletes what a crashed client left behind. `conference_guest_consent_acknowledgment` is *never written* for an encounter session; if such a
  row existed it is deleted with the session.
* **`listPresent`** answers only a person who is present themselves, sorted by name (the order must not reveal who arrived when), without
  times and without home servers. BOARD/ADMIN who are not in the room see nothing: no surveillance from outside. `EncounterSpaceDto.presentCount`
  is only a number.
* **The audit log** receives configuration changes (`create`, `update`, `archive`, `setSpaceRoles`, actor = BOARD/ADMIN) and open/close
  (actor = the office holder, or `null` for the poller's automatic close). **Never** entering, leaving, presence, removing or silencing:
  the log is hash-chained and cannot be erased, so an entry "member X was in the church service" would be a permanent trace.
  `setSpaceRoles` records the office holders' member ids (an office is an act of the organization and the assignment of rights must be
  traceable); the alternative -- only counts -- is an open question.
* **Moderation state** (who was removed, who was silenced) lives only in memory (`EncounterModerationState`, bounded to 64 sessions and 200
  entries per list; a full list *refuses* instead of evicting a block) and is dropped when the session ends. A database block list would be a
  lasting record about a person. Consequence: it is lost on a server restart.
* **The entry notice (V1.9.76)** tells the office holders _that_ someone without an office arrived, never _who_: no name, address, id or role of the entrant is in the
  mail, in the memory state, in the logs or in the audit log, and nothing is written to the database (see "Entry notice for office holders").
* **The temporary floor (V1.9.138)** is memory only, like the moderation state: who may speak, since when and for how long lives in
  `EncounterFloorState` (monotonic clock, bounded to 64 sessions), is dropped when the session ends and is lost on a restart (then nobody
  has the floor). No table, no migration, no audit entry, no log line with a person; the congregation never sees a name (see "Temporary
  floor grant").
* **Logs** in the encounter code never name a member id, an identity, a display name or a room id above DEBUG. Stream keys are untouched
  (`SecretBox`). `EncounterPrivacyTripwireTest` and `EncounterPrivacyWatchTest` pin all of this.
* **Export and erasure** (`EncounterSpacePersonalData`): the export lists the subject's own spaces, offices and consent proofs. Erasure
  *deletes* the office rows and *retains, with the reason*, the spaces the member created (organization configuration) and the consent proof
  (Art. 5(2)/7(1) accountability).

[#consent]
=== The consent of a non-member

A GUEST or FRIEND must explicitly consent (Art. 9(2)(a)) before entering a space with `MEMBERS_AND_GUESTS`. `getEntryInfo` returns
`consentRequired`, `consentChanged` and the text; `enterSpace` takes the version and hash *unmodified* (`ResolvedEncounterConsent.matches`, constant time; a malformed
hash is a plain mismatch). The proof is one row `(member, version)` with the hash and a *date*, written inside a savepoint (`isUniqueViolation()` is the only exception
swallowed -- on PostgreSQL a failed statement would otherwise poison the transaction). Consent given once covers every space for that version.
For an `ACTIVE` member a submitted consent is ignored and nothing is stored. **The text is a draft** and needs legal review.

==== Consent text (V1.9.148): administered per instance

Since V1.9.148 the text is no code constant. `encounterConsentFor(profile, pulpitRecordingAllowed)` maps the profile to a kind (`ENC_CHURCH` for a church service,
`ENC_ASSEM` for an assembly) and asks `AgreementTextResolver` for the live text: the published version with the highest sequence number, else the built-in placeholder
(`BuiltinEncounterConsentTexts.kt`). A database version is re-hashed on every read; a stored hash that no longer matches is a `ServiceBusyException` and nobody enters.
A body that breaks the paragraph rule is never served half-way (also `ServiceBusyException`).

[cols="1,3", options="header"]
|===
| Rule | Detail
| Layout | `EncounterConsentLayout` (shared): paragraph 1 headline (at most 160 characters), paragraphs 2 to 4 key points (at most 600), the rest detail; the whole body is hashed and is the disclosure text. Paragraphs are separated by blank lines (spaces and several line feeds allowed).
| Recording | For a room whose option "the pulpit may be recorded" is on, the code appends one fixed paragraph (never admin-editable) as an extra visible key point and at the end of the text, adds the suffix `+rec` to the label and hashes the result. The placeholder's own sentence "Es wird nichts aufgezeichnet." is removed there.
| Label | `[0-9A-Za-z][0-9A-Za-z._-]{0,49}`, but at most **46** characters for the ENC kinds: the system adds `+rec` and the column is `VARCHAR(50)`. `+` is not allowed in an admin label, so the suffix namespace belongs to the code.
| Namespace | `encounter_consent_acknowledgment` has the key `(member_id, consent_version)` and **no kind column** (and must not get one). A label therefore identifies one text across *both* ENC kinds and every label code ever wrote (`EncounterConsentLabels.reserved`). Checked on save and on publish; both drafts are locked in a fixed order while one is published; `recordConsent` refuses a unique violation whose stored hash differs (`ServiceBusyException`, logged without label, hash or person).
| Re-consent | A new label means every non-member acknowledges again. `consentChanged` is `true` when the caller holds an acknowledgment of an older notice *of the same line* (the profile's earlier code objects, its placeholder, any published version, each with or without `+rec`); an acknowledgment of the other profile's notice does not count.
| Earlier objects | The four earlier objects stay byte for byte as proof, are `@Deprecated` and are never served; `EncounterConsentLabels` and the pin tests are their only readers.
| Count | `olderAcknowledgmentCount` is always 0 for the ENC kinds (it would be the number of non-members who entered services or assemblies).
|===

What the placeholder says about what everybody present sees and hears of a guest is pinned by `EncounterConsentTextPinTest`:

[cols="2,3", options="header"]
|===
| What others see or hear | Shown to
| Display name; seat with initials; table and seat at the table; guest status (`isGuest` goes to every client); reactions at the seat | Everybody present
| Chat messages, with the name (not stored) | Everybody present at that moment
| Name in the floor banner, and the voice, while the person has the word and has switched the microphone on themselves | Everybody present
| Voice at a table, only after the person switched the microphone on themselves | The people at that table
| Picture | Never sent
|===

== Session lifecycle and the poller

`openSpace` is idempotent (an open session is returned unchanged): transaction 1 authorizes, the LiveKit room is created *outside* any
transaction (`empty_timeout` 1800 s for a room nobody has joined yet, plus `departure_timeout` 1800 s for a room whose last participant left, so a break or a dropped pulpit connection does not tear the session down), transaction 2 re-verifies under the locks and inserts the room
row. A call that loses the race deletes its freshly created LiveKit room again. `closeSpace` deletes the LiveKit room first (a failure is only
logged -- data protection beats availability, the poller retries), then ends the session and deletes the rows under the locks.

`EncounterSpacePoller` runs at start and every 60 s: (a) deletes presence rows of ended sessions -- always, even if LiveKit is down;
(b) per open session deletes presence rows of people no longer connected (older than 120 s *and* absent in two consecutive sweeps, because
`livekit-client` reconnects with its still-valid token without calling `enterSpace` again, so one sweep inside a short network gap must not
cost a person their row), disconnects blocked people who reconnected with a still-valid token; (c) closes a session that is older than 12
hours (`MAX_DURATION`, done *before* any LiveKit call, so an outage cannot keep it open past its limit) or whose LiveKit room is gone
(`EMPTY`); (d) retries the LiveKit deletion of sessions that ended in the last 24 hours. If LiveKit is unreachable, (b), the room-gone part
of (c) and (d) are skipped with a warning that carries no ids. A client that is told its connection was re-established need not call
`enterSpace` again; if it does, that is harmless.

[#lock-order]
== Lock order and transactions

Every writer takes the locks in this order, without exception: (1) `encounter_space FOR UPDATE`, (2) `conference_room FOR UPDATE`, (3) the
caller's status is *read* without a lock, (4) inserts and deletes, (5) `AuditLogRecorder.record` *last*. Never `FOR UPDATE` on `member`
(see `docs/architecture/row-locks.adoc`). LiveKit and HTTP calls are never inside `transaction {}`. The ceilings are enforced inside the
locked transaction:

* The congregation stops `2` places short of the maximum (`ENCOUNTER_OFFICER_RESERVED_SLOTS`), so a full congregation can never lock the pulpit
  out; office holders and BOARD/ADMIN use the reserve; the hard maximum (LiveKit `max_participants`, at most 25) holds for everybody. A
  reconnecting person already present is never turned away.
* At most `maxNonMemberParticipants` (20) non-members.

== Assumptions about LiveKit

* A token with `canPublish = false` is believed to be *enforced by LiveKit* (the grant is part of the signed token). This is **not verified
  against a live instance** in this wave; `docs/architecture/encounter-space-staging-test.adoc` is the test script for it. `hidden` is not used.
* `removeParticipant` disconnects but does not invalidate the token: a removed person who still holds a valid token can reconnect to LiveKit
  directly. The server blocks re-entry (`enterSpace`) and the poller disconnects blocked identities again within its period (60 s). A *silenced*
  person's old token still carries the data channel; the poller compares the live `permission.can_publish_data` of every silenced identity and
  disconnects it again within its period (60 s), so the bypass window is bounded by the sweep, not by the token lifetime.
* A withdrawn office: `setSpaceRoles` disconnects (best effort, after the commit) every ex-holder who is present in the running session, and
  a re-entry via `enterSpace` gets a listen-only token. Even after a successful disconnect, the old token (`canPublish = true`) allows a
  direct reconnect to LiveKit; the poller therefore disconnects, every sweep (60 s), any live participant that holds publish rights
  (`permission.can_publish` or published tracks) without being a current ACTIVE office holder. Only re-entry via `enterSpace` is listen-only.
  The moderation checks of the server are unaffected.
* `auto_create` (LiveKit default `true`) would revive a deleted room when somebody connects with an old token; the server checks that the
  session is open when a token is requested, and the poller closes the session record.

=== The three phases of a room

[source,kuml,name="encounter-client-phases"]
----
stateDiagram(name = "Encounter room view (client)") {
    val start = initialState()
    val closed = state(name = "Closed")
    val entry = state(name = "Entry")
    val inside = state(name = "Inside")

    transition(source = start, target = closed) { trigger = "getEntryInfo: doors closed" }
    transition(source = start, target = entry) { trigger = "getEntryInfo: doors open" }
    transition(source = closed, target = entry) { trigger = "doors opened (poll every 30 s, or openSpace)" }
    transition(source = entry, target = inside) { trigger = "click Eintreten: enterSpace + connect" }
    transition(source = inside, target = closed) { trigger = "doors closed / session ended" }
    transition(source = inside, target = entry) { trigger = "Verlassen, connection lost, re-entry refused" }
}
----

* *Closed*: the notice of the room (untrusted text) or a plain sentence; a moderator gets "Türen öffnen".
* *Entry*: `EncounterEntryPanel`, deliberately *not* a modal. Three plain sentences, the Art. 9 remark ("Dieser Hinweis ist keine Rechtsberatung."), for a
  non-member the server's consent text (headline and key points as untrusted text, the full text behind a disclosure, a required tick box). The version and the
  hash go to `enterSpace` unmodified. There is no link to any streaming platform: whether the pulpit is transmitted is the operator's decision.
* *Inside*: `EncounterRoom`. A disconnect with the reason `DUPLICATE_IDENTITY` (the same account entered on another device) is decided first: the room view is replaced by the
  "connected on another device" card with "Hier fortsetzen" / "Zur Übersicht"; no `getSpace`, no re-entry, no `leaveSpace` (that would delete the presence row and the poller would then
  disconnect the other device). Any other disconnect: the state is read: closed means "Der Gottesdienst ist beendet."; open means one automatic re-entry
  (at most 3 per 5 minutes), then the entry panel again; a refusal on re-entry means "Sie wurden aus diesem Raum entfernt.".

The room view's teardown is the destroy hook of the screen root, registered *before* the root is added (see `addWithLifecycle`): leaving the route stops every timer and
listener, disconnects the session and calls `leaveSpace`. A closing page does the same best effort on `pagehide` (a plain RPC can be cancelled by the browser then; the
server's presence poller removes a stale row).

Unlike a video conference since V1.9.70 (`conference-dock.adoc`), the encounter room is *not* kept in the conference dock: leaving its route still ends it as described
above. It does not start while a conference holds the dock (`ConferenceDock.canJoin()`; the entry shows "Sie sind bereits in einer Besprechung. Verlassen Sie diese
zuerst."). Becoming a second kind of dock session is a follow-up, not started.

=== Listen-only, three layers

. The server mints the token with `canPublish = false` for everybody without an office (B1).
. *The type*: `EncounterMediaSession.kt` hands a congregation member an `EncounterListenerSession`, an interface *without any media method*. Only an entry with
  `canPublish = true` yields an `EncounterSpeakerSession` (with `setCamera`/`setMicrophone`). The code that could switch a camera on does not compile for a listener.
. *The runtime flag*: `LiveKitRoomSession(publishEnabled = entry.canPublish)`. With `false`, `setCamera`/`setMicrophone`/`setScreenShare` return at once without touching the SDK, and
  device listing, switching and enumeration are empty or refused (some browsers answer an enumeration with a permission heuristic). The conference keeps the default `true`.

A pulpit person's camera is switched on in the same click chain that entered (so Safari's gesture rule is met); the microphone stays off.
Since V1.9.90 there is no standing status band any more: the state lives on the microphone button alone (red outline `btn-outline-danger`, slashed symbol, `aria-pressed`; on: filled primary, plain symbol).
Because the frequent error is speaking into a muted microphone, the room announces "Ihr Mikrofon ist aus." once, 750 ms after entering, in the polite `role="status"` region of the room (a fixed sentence, no personal data); toggling later announces nothing.
A steward starts with both off.

==== Control bar layout (V1.9.90, replaced by the three zones in V1.9.184)

Since V1.9.184 the bar is the same *three-zone bar* as the conference's (`RoomControlBar`, a grid `auto | 1fr | auto`; see "The room bar (V1.9.184)" below). The group order (DOM and tab order) is:
*settings* (the gear, alone in the start zone) | in the centre: *devices* (microphone and camera; for a seated congregation person the table microphone and "Pulpit louder"), reactions, liturgy, panels (chat, map),
view, recording, moderation (transmission), "Mehr" | in the end zone: exit ("Türen schließen", "Verlassen").
The devices group has the accessible name "Geräte" and carries the divider itself. What does not fit leaves the middle first and the devices last (see `encounterOverflowOrder`).
The pure invariants `settingsIsFirst` and `moreImmediatelyBeforeEnd` pin the order in tests (`devicesAreFirst` of V1.9.90 is gone: the gear stands in front of the devices now).

=== Scene, pews, reactions

* *Two layers* (design team, Duarte): the scene (`lapis-encounter-scene-layer` with its drawings and `lapis-encounter-scene-rows`) consists of decorative CSS masks. Until V1.9.151 they were the floor plans under `/assets/encounter-themes/<theme>/` (V1.9.67, see <<stage-1>>); since V1.9.152 the drawings come from the fixed room templates under `/assets/encounter-objects-v1/` (see <<stage-2c>>; set inline by the layout, colour and visibility from `theme.css`; own drawings, vector only, `aria-hidden`). The old `encounter-themes/*` files stay in the repository and are still staged, because a cached old client still loads them; the current client no longer references them;
  the stage on top holds opaque surfaces (pulpit, stewards' strip, seats, name labels), so text never sits on the motif. Contrast pairs are documented in `theme.css`
  (`--lapis-encounter-*`, light and dark). "Szene aus" removes the layer; forced-colours and `prefers-contrast: more` hide it automatically.
* *Pews* (B2 as built, *replaced by stage 2a, see <<stage-2a>>*): 2 blocks of 3 seats per row, an aisle between. In B2 the plan was assigned *per device* (filled alternately left/right from the
  front, name order for the people already present, nothing synchronised) and a seat was a non-interactive `listitem`. Since V1.9.79 the seat plan is the server's picture, a seat is a button, and nobody is seated
  automatically. Unchanged: only people `listPresent` names are shown -- a LiveKit participant that is not listed (an egress bot, a stranger) never gets a seat or a symbol.
* *Reactions* (data-channel topic `lapis-encounter-reaction`, payload `{"r":"<NAME>"}` only, at most 32 bytes (the longest, `HAND_LOWERED`, is 20)): `HAND` is a *state* (renewed every 30 s by its owner, lapses after 90 s,
  `HAND_LOWERED` ends it), `AMEN` an *event* (likewise `APPLAUSE`, `HEART`, `FLOWER`, `LAUGH`, `ASTONISHED`, `QUESTION`, `CRY`; a symbol at the seat for 3 s, announced as the fixed sentence "Amen aus der Gemeinde" at most every 10 s, never a number). Limits: sender
  amen 5 s / hand 2 s, receiver 2 per second and sender, the sender table bounded to 64. **Trust boundary**: the receiver reads only the key `r`; the sender is the SDK-verified identity of the packet,
  never a payload field; oversize and malformed payloads are dropped unread; since V1.9.79 every person of the congregation in `listPresent` can react (see <<stage-2a>>: sitting is no precondition any more).
* *Raised hands* are listed (in the order they went up) only for office holders and BOARD/ADMIN; the congregation sees seats, not a queue.
* *Chat* reuses the conference's topic `lapis-chat`: in-memory only, at most 200 lines of 500 characters, plain text (no markup, no links, the KVision i18n marker neutralised), and *no time*
  (the wire field is sent as `0`). A silenced person (`canPublishData = false`) can read but not write.

=== Moderation and transmission

* The menu "Stummschalten"/"Entfernen" (`encounterCanActOn`): never for oneself, never for the congregation viewer; an office holder acts against the congregation only (the server refuses another office
  holder and BOARD/ADMIN -- the client cannot see a congregation member's global role, so an office holder may see the menu for a BOARD member and the server then refuses; the client says so in one fixed sentence).
  "Entfernen" asks first. The guest marker "Gast" is shown only to people who moderate.
* The transmission tab (`EncounterStreamPanel`, moderators only) starts and stops the transmission of the *pulpit*: the layout is fixed to `SINGLE_PARTICIPANT` ("Nur Kanzel", no choice), the picture is the pulpit person's
  (a choice only with more than one), the latency is the conference's default (`STANDARD`). It creates and activates no destination, in particular no YouTube destination; administrators get a link to the
  destination screen. Pause and resume are not part of B2.
* The badge "Live (nur Kanzel)" is shown to *everybody present* while a stream runs: the server's transparency read (`getActiveStream`) is allowed for all present people. It is polled every 30 s while the
  page is visible; a conflict answer (streaming not enabled) stops the polling.

=== Polling and the rate budget

The server's `list` budget (60 per minute and member) is shared by `listSpaces`, `getSpace`, `getEntryInfo` and `listPresent`. The client therefore refreshes `listPresent` at most every 5 s on a roster event
(merged: `EncounterRefreshPlanner`), every 20 s by timer, and only while the page is visible; a closed room is asked every 30 s; re-entry after a disconnect is limited to 3 per 5 minutes (the `enter` budget is 30 per minute).

=== Accessibility

Controls are real buttons with names; the hand button carries `aria-pressed` (fixed label); the pulpit is a `group` named "Kanzel: <name>" and receives the focus after entering (`tabindex=-1`); two polite live
regions (amen bundling for everybody, "<name> hebt die Hand" for office holders only); no single-letter shortcuts (stage 2a: the seat plan is one tab stop with arrow-key navigation, see <<stage-2a>>); the side panel is closed by default, Escape closes it, below 768 px it is a full-screen sheet
(`role="dialog"`, `aria-modal`, focus trap, focus returns to the opener); amen fades in and out in 200 ms, switched off under `prefers-reduced-motion`; the control bar shows symbols only, the reactions included (names and tooltips stay); see "The control bar" below.

=== Browser storage

The encounter client has exactly two storage keys of its own (both in `EncounterSceneToggle.kt`; the device picker additionally writes the device ids of the video conference's keys, see "Device selection"): `lapis.encounter.sceneOff` (value `1`) and, since V1.9.96, `lapis.encounter.bellSoundOn` (value `1`, see "Bell"). Neither has a room, a person or a time. Reading or writing them is wrapped in `try`/`catch`; a blocked
storage means "scene on" and "bell sound off". `ClientEncounterPrivacyTripwireTest` pins this together with the other privacy rules (no `innerHTML`, no console, no exception text, devices only in the two allowed files, no telemetry). V1.9.196: the entry notice of a guest may be a Markdown text; the encounter files still never spell `rich = true` -- the full text goes through `renderAgreementBody` of `AgreementTextRendering.kt`, the one function that inserts server-rendered HTML (`ClientAgreementHtmlTripwireTest`), while headline and key points stay untrusted element text with the Markdown characters removed by the server.

=== Known limitations of B2

* B1's staging script was not run when B2 was built: that LiveKit really enforces `canPublish = false`, and the exact client-side symptom, are *assumptions* (the client prevents the attempt, the token refuses it).

* The LIVE badge is visible to everybody present (a transparency right of the server), not only to office holders.

[[stage-1]]
== Stage 1 (V1.9.67): room profiles, configurable reactions, stage mode, floor-plan scenes

A room now has a *profile* (`encounter_space.profile`, V76) and a *reaction set* (`encounter_space.reaction_set`). Both describe the *room*, never a person: no new
table, no new column with personal data, no log of reactions, so the Art. 9 position of the room is unchanged.

=== Profiles and vocabulary

[cols="2,3,3"]
|===
| | `CHURCH_SERVICE` (default, every existing room) | `ASSEMBLY`

| Who speaks | Kanzel (pulpit) | Podium
| Who moderates | Ordner im Gottesdienst | Moderation
| Who listens | Gemeinde | Teilnehmende
| Default reactions | hand, amen | hand, applause
| Scene | chancel, pews | podium, chairs
| Consent text | agreement text kind `ENC_CHURCH` (placeholder `2026-10-17.v2`) | agreement text kind `ENC_ASSEM` (placeholder `2026-10-17.assembly.v2`)
|===

All profile words live in one client file (`EncounterVocabulary.kt`, `EncounterTerms`); `ClientEncounterVocabularyTripwireTest` fails the build if another file of
`client/encounter/` writes one of them as a literal or branches on the profile. `theme_key` stays frozen at `CHURCH` so a cached old client still decodes `EncounterTheme`;
the profile is the truth. Existing rooms get `CHURCH_SERVICE` and `HAND,AMEN` from the migration: the behaviour of a running church room does not change.

=== Reaction set

`HAND`, `AMEN`, `APPLAUSE`, `HEART` and, since V1.9.164, `FLOWER`, `LAUGH`, `ASTONISHED`, `QUESTION`, `CRY` (nine options; append only, the canonical order is the declaration order). The new options are opt-in and never part of a profile default (`CRY` exists only here, never in the video conference); `QUESTION` is an event like `AMEN` and is not coupled to `HAND`. There is deliberately no thumbs-up: in an assembly it reads as a vote. `HAND` is always on (a person must always be able to ask for the floor);
`HAND_LOWERED` is the wire counterpart of `HAND` and is never selectable. The server stores the canonical list (`EncounterReactionOption.normalize`: deduplicated, fixed order, `HAND` first)
as a CSV and rejects a list of more entries than there are options (DoS guard, `EncounterReactionOption.entries.size`, nine). The order of the buttons is fixed. The set is enforced *on the client only*: the server never reads a reaction (data channel,
no server path), so the client builds a button per allowed option and drops a received reaction the room does not allow (`admitReaction`; silent, no log, no counter). A manipulated client can
still send anything; the 32-byte limit and the per-sender receive limit stay in force (and, in stage 2a, "only people in the congregation list react"). The three event reactions share one 5 s send budget; the hand has its own 2 s budget and
is never blocked by an event. The longest canonical CSV (all nine) is 61 characters and the column `encounter_space.reaction_set` is `varchar(64)`; a test fails as soon as a tenth option exceeds that, and the fix is a new migration (never a change to the released `V76`). Old subsets load unchanged (unknown tokens are dropped by `parseReactionSet`); clients older than V1.9.164 drop the new wire names silently. A seat has one event slot (a newer event replaces the older), announced as one fixed sentence at most every 10 s, never as a count.

=== Changing the profile

`createSpace`: `profile = null` means `CHURCH_SERVICE`, `reactions = null` means the defaults of the profile. `updateSpace`: `null` means *unchanged* -- an old cached admin client sends neither field
and must not silently turn an assembly into a church service. A real change of profile or reactions while a session is open is a `ConflictException` (same pattern as the guest policy): the
vocabulary and the reaction set cannot change under people who are present. Unchanged values while open are accepted; title, description, notice and maximum stay editable. Only BOARD/ADMIN, as before.
The audit snapshot (`configSnapshot`) gets `profile` and `reactions` (room values only; the only member id in an audit entry is still the actor's).

=== Consent per profile

The consent a guest gives is bound to a text (`encounterConsentFor(profile)`). A guest who consented for a church service must consent again for an assembly: the purpose is another (Art. 9: a political
opinion or worldview instead of a religious belief). `getEntryInfo`, `enterSpace` (version and hash must match the room's own text, constant-time compare), the stored proof and `hasCurrentConsent` all use the room's text.
The church text and its hash are unchanged, so existing consents stay valid. *The assembly text is a draft and MUST be reviewed by a lawyer.*

=== Stage mode

* The room fills at least the height under the header (`--lapis-header-h`, a token) minus the bar; `100vh` first, `100dvh` second (older Safari has no `dvh`). The pulpit/podium keeps 16:9 and takes at most
  56 % of that height (62 % until V1.9.152; the front strip of the scene stands above it since V1.9.153); the old 720 px cap is gone (`ClientEncounterVocabularyTripwireTest` pins that). The benches sit below. Since V1.9.68 (R59, one scroll surface) the height is a minimum, not
  a fixed size: the room grows with its benches and the page scrolls; there is no inner scrolling area for the benches any more. In full screen the room itself is the scroll container
  (ledger entry E0 of `ScrollSurfaceTripwireTest`, see `ui-ux-guideline.adoc` R59).
* The dock (V1.9.165): the bar, the "Mehr" sheet and the device panel are children of ONE wrapper, `.lapis-encounter-dock`, which is `position: sticky; bottom: 0` on layer 6 (see the stacking table in `theme.css`). The bar is therefore on
  screen in every mode: window (the page scrolls), full screen and fallback full screen (the room is the scroll root). Sticky is *not* a scroll surface: the ledger of `ScrollSurfaceTripwireTest` is unchanged, there is still exactly one scroll
  surface per mode. The two sheets are anchored to the dock with `bottom: calc(100% + 4px)` (a sticky box is the containing block of its absolute children), no longer to the room. No `backdrop-filter`, `filter` or `transform` on the dock or an
  ancestor (a stacking and containing-block trap), and no `overflow` other than `visible` or `clip` on an ancestor up to the scroll root (sticky would silently stop working; `EncounterControlBarStickyDomTest` walks the chain). The shadow is static, no
  JavaScript. While the conference bar is shown (`html.lapis-has-dock`) the dock rests on top of it (`bottom: var(--lapis-dock-h)`), except in full screen, where the room (layer 1060) covers it. `scroll-padding-bottom` keeps a focused seat out from
  under the dock. The room's `vPanel` puts 10 px under every child: the dock, the two empty audio sinks that follow it and (V1.9.167) the map layer have no margin, otherwise the dock could not reach the bottom edge.
* The map layer (V1.9.167): the grid map is no longer a block of the stage. `EncounterMapOverlay` is a `position: fixed` child of the room (a sibling of the dock) on layer 5 that ends above the dock (`bottom` is built from `--lapis-encounter-bar-h`; with the conference bar shown it also leaves room for `--lapis-dock-h`), so the bar stays operable. The "Mehr" sheet (layer 6) therefore lies above the layer. See <<stage-3-map-layer>>.
* The side panel: from 1200 px a 340 px column (closable), from 768 to 1199 px an *overlay* over the right edge (closed by default, Escape closes it, focus returns to the opener), below 768 px the full-screen sheet.
  The toggle carries `aria-expanded` and `aria-controls`; the state lives in memory only.
* Full screen (`EncounterFullscreen`): the Fullscreen API on the room element; without it (or when `requestFullscreen()` is rejected) the room gets `is-pseudo-fullscreen` (`position: fixed; inset: 0`) and Escape leaves it.
  Listeners are removed when the person leaves. Nothing is stored.
* The bar (`EncounterControlBar`, V1.9.74: icon bar) is described in the next section.

=== The control bar (V1.9.74)

The bar under the stage shows *symbols only*; since V1.9.84 this holds for the reactions (hand and the room's event reactions) too. Every symbol button has an accessible
name, a tooltip (`title`) and a stable label; the state of a toggle is carried by `aria-pressed` (hand, scene, full screen, microphone, camera) or `aria-expanded` (chat, transmission,
"Mehr") together with a ring and, for microphone and camera, the slash symbol -- never by colour alone and never by a changing label ("Szene ausblenden" is pressed while the scene is
hidden; "Vollbild" changes its symbol, not its name).

Groups, in DOM order (`EncounterControlGroup`, V1.9.184): *settings (gear) | devices (office holders) | reactions | liturgy | panels (chat, map) | view (scene, full screen) | recording | moderation (transmission) | "Mehr" | exit*. A divider
(CSS) separates two non-empty groups. The *exit group* sits at the far end of the bar, 12 px between its controls and no hit area in the gap: "Türen schließen" (people who moderate; outline,
danger colour) and "Verlassen" (everybody; filled, always the *last* control). "Verlassen" has no confirmation; it locks itself (`disabled`, `aria-busy`) at the first click, so a double click
leaves once. The leave button of the page header is gone (the room owns the only "Verlassen"). The moderation group never borders the reactions.

"Türen schließen" is guarded by the confirmation dialog, not by distance: the focus starts on "Abbrechen", the dialog fires once (`ConfirmOnce`), a full-screen room is left first, and the
control in the bar and its twin in the sheet call the *same* function (`askCloseDoors`), so there is exactly one path to `closeSpace`. The server still decides who may close.

==== Reaction buttons (V1.9.84)

* Symbol only in every width; the name stands in `title`, `aria-label` and `data-label`. The group is a `role="group"` named "Reaktionen". There is no media-query rule any more that brings a word back.
* The hand is the only reaction with a state: `aria-pressed` plus the filled style and the double ring, with a *stable* name (ARIA: either the name changes or `aria-pressed` is used, never both).
* The hand never overflows into the sheet and has no twin: a request to speak must never need a second tap. The event reactions overflow into the sheet like before, and their twins keep the word (the sheet is a menu).
* Trade-off (Kare / Atkinson): `fa-hand` may be read as "stop". It is kept because the seat shows the same glyph (button equals seat feedback). A different symbol is only allowed together with the seat rendering.
* Touch devices have no tooltip; there the name of a reaction is available to screen readers only.
* An optional first-visit hint was not built: without persistence it would reappear on every page load, and `localStorage` is ruled out by the promise of no lasting trace of participation.

*Overflow.* The bar never wraps and never scrolls sideways (R59). What does not fit moves into the "Mehr" sheet, measured by the shared `ControlBarOverflow` (also behind the conference bar).
The order is: full screen, scene, transmission, the event reactions (the last of the canonical order first), the bell, the blessing, the recording, the map, the chat, and (V1.9.184) last of all
"Türen schließen", the gear, the camera and the microphone. Never moved: the hand, "Mehr" and "Verlassen". "Mehr" is there exactly while something sits in the sheet. At 360 px a person at the pulpit keeps
hand, microphone, camera and "Verlassen" (view, chat and the gear moved into the sheet); at 320 px the camera follows and only the microphone is left of the devices. The gear, the camera and the microphone have
labelled twins in the sheet (built before the twin of "Türen schließen", which ends the sheet); a twin clicks its primary. A group whose controls all moved is hidden, so it takes no gap.

*The sheet* (`.lapis-encounter-more-sheet`) is a sibling of the bar inside the dock, anchored above it, *not modal* (`role="dialog"`, no focus trap, name "Weitere Bedienelemente"). It holds labelled twins in the bar's
order; the twins of scene and full screen mirror `aria-pressed`; the twin of "Türen schließen" stands last, set apart by a rule. "Verlassen" is never in the sheet. On opening, the focus goes
to the first twin; Escape or a click outside closes it, and Escape returns the focus to "Mehr". A twin closes the sheet and then runs the action. The two document listeners (Escape, click)
exist only while the sheet is open and are removed on close and in `dispose()`. The sheet scrolls itself (ledger class E1 of the scroll rule, R59).

== Entry notice for office holders (V1.9.76)

A room can tell its office holders (PULPIT and STEWARD) by e-mail that a person *without an office* has entered. It is configured per room
(`encounter_space.notify_mode`, migration V78, BOARD/ADMIN only like the rest of the configuration) and is off by default.

[cols="1,3"]
|===
| Mode | Behaviour

| `NONE`
| No message (default; every existing room).

| `FIRST_GUEST`
| One message per opening of the room: for the first newcomer of the session. A closed and reopened room is a new session and announces its first newcomer again.

| `EVERY_GUEST`
| Newcomers are counted into fixed five-minute slots of the organisation's wall clock ("between 10:00 and 10:05"). When a slot has ended, one summary mail follows, and a space sends at most one mail per five minutes
  (late slots are merged into one).
|===

*Who counts as "a person without an office".* A _newly admitted_ person whose `presenceRole` is `CONGREGATION` and who is not BOARD/ADMIN. A reconnect reuses its presence row and never counts. PULPIT and STEWARD never trigger a notice
(and never use up the first-newcomer claim). BOARD/ADMIN without an office do not either: the product owner decided that they are not "guests" of the room.

*Who is informed.* The ACTIVE PULPIT/STEWARD office holders who are *not in the room at that moment* -- read from `conference_participation`, which is already the transient live presence (written on entry, deleted on leave, on close and by the poller). No
new presence storage was needed. Addresses are lower-cased and deduplicated, anonymised members (`*.invalid`) are dropped, at most 20 recipients. Each recipient gets an individual mail (nobody sees the others' addresses). If nobody remains, nothing is sent.
Honest blur: an office holder who closes the tab without `leaveSpace` still counts as present until the poller removes the row (about two to four minutes) and gets no mail in that time.

*What the mail says.* Room name, the time (the minute for a single entry, the window for a summary), the number of newcomers and the number of people present, German first, English below, no link, no logo, plus the sentence that the message names nobody on purpose.
It never carries a name, an address, an id or the role of the entrant: `EncounterEntryNotice` has no field for a person, `EncounterEntryNoticeAnonymityTest` pins that. The HTML part is an unformatted mirror of the plain text (the transport always sends multipart/alternative).

*Where the state lives.* `EncounterEntryNoticeState` holds, only in memory, the claim of the first newcomer per session and the slot counters per session, bounded (64 sessions, 4 pending slots per session; a full state refuses instead of evicting).
It is dropped when the session is closed (`closeSpace`, the poller), when the notify mode of the room changes, and by a server restart. A window of a session that has ended is discarded without a mail. Nothing is written to the database.

*When it runs.* `EncounterSpaceService.enterSpace` calls `EncounterEntryNotifier.onGuestEntered` only after the entry transaction has committed (Exposed may re-run a block, a claim inside it could be spent twice or survive a rollback). The notifier never throws: a mail problem
can never block or undo an entry. The recipient query runs in its own short read transaction; the mail is only _enqueued_ (outside any transaction). With SMTP not configured the notifier does no work at all (no state, no database read).
`EVERY_GUEST` windows are sent by a ticker of the notifier (every 30 seconds, independent of LiveKit and of the poller) and opportunistically by the next entry.

*What is audited.* The _setting_ (`notifyMode` is part of the configuration snapshot of `create`/`update`, actor = BOARD/ADMIN). The mail itself is not audited, and neither is an entry: an audit line "somebody entered at 10:03" would be the permanent trace this room is built to avoid.
The notify mode may be changed while the room is open (it only affects future entries); a real change resets the state of the room.

*Logs.* The notice code logs only exception classes and the fact that the state is full -- no id, title, address or number. `MailDispatcher.enqueue(logRecipient = false)` makes the dispatcher write `to=(withheld)` instead of the masked address.
The remaining line "Mail delivered: purpose=encounter-entry-notice to=(withheld)" says that a notice mail left, without room and without person.

=== Known limitations of the entry notice

* Only with SMTP configured; without it the setting is stored but nothing is sent.
* The claim and the throttle live in the memory of one server instance: a restart forgets them (a first newcomer may be announced twice), and several instances do not share them (a mail may come twice).
* The time of a single entry (`FIRST_GUEST`) remains a weak correlate with the one person who arrived then; `EVERY_GUEST` blurs it to a window.
* If the first newcomer arrives while every office holder is present (nobody to tell), the claim is still spent: later newcomers of that session are not announced, even if the office holders have left in the meantime.
* An office holder with a stuck presence row gets no mail until the poller has removed it.
* The website help page `gathering-room` (EN, DE) is not updated in this wave; do that at the rollout.

[#stage-2a]
== Stage 2a (V1.9.79): seat choice and person symbols

The B2 pews were a local drawing: every device placed everybody itself and nobody could choose where to sit. Stage 2a turns the pews into a *shared, chosen* seat plan. Everybody in the
congregation can choose a free seat; everybody sees who sits where as initials. There is still no automatic seating, no history and no database column.

=== Model

* *Server-authoritative, chosen seats only.* `IEncounterSpaceService.selectSeat(spaceId, seat)` sets the caller's *own* seat, `null` releases it. There is no member-id parameter: nobody can put another person on a seat. Only a CONGREGATION person
  who is present in the open session may choose (`ForbiddenException` for an office holder, a person who is not present, a closed room).
* *State* (`EncounterSeatState`): `session -> (seat -> member)` and `member -> seat`, *in memory only*, never persisted, never logged, never audited -- like `EncounterModerationState`. At most 64 sessions (a 65th gets
  `Full`), one seat per person, `0 until 240` seats (40 rows of six; the shared `encounterSeatCapacity` offers whole rows, at least 24, one spare row). Choose-and-claim is one `synchronized` block: whoever enters first wins a contested seat.
  A seat whose occupant is not present any more (stale) counts as free.
* *No schema change.* Stage 2a added no migration (`EncounterPrivacyTripwireTest` pins that no migration and no generated encounter table knows a seat); the one later migration, V79 of stage 2b, adds room settings only.
* *Release points:* `leaveSpace`, removal (`removeFromSpace`; silencing keeps the seat), `closeSpace`, the poller (a deleted stale presence row releases the seat; a session it closes is cleared) and every `enterSpace`
  (an entry always starts without a seat -- a reload does not resurrect a seat). A person who becomes an office holder loses the seat at the next read.
* *`listPresent` carries the seat* (`EncounterPresentDto.seat`, last and with a default: an old client ignores the key, a new client reads `null` from an old server). `selectSeat` answers with the same list.

=== Exceptions, throttle, budget

Kilua transmits only the exception *type*, so the outcomes are distinguishable by type: `ConflictException` = seat taken, `ServiceBusyException` = throttled (1 change per second and member, `requireSeatRate`) or seat table full,
`BadRequestException` = seat out of range. The shared `requireWithinRate` (a `ConflictException`) is deliberately not used for `selectSeat`. The throttle is checked first, before any database access.
`selectSeat` shares the `list` budget with nothing; the reload it triggers on the *other* clients goes through the existing `EncounterRefreshPlanner` (at most one `listPresent` per 5 s and client), so the 60-per-minute `list` budget is not
loaded more than before.

=== The seat nudge

After a successful change the client sends a content-free data-channel packet on `lapis-encounter-seat` (`{"s":1}`, 7 bytes). Receivers *decode nothing*: they check the length (more than 8 bytes is dropped unread), accept only an
SDK-verified identity that is in their `listPresent`, wait a random 0 to 1000 ms and ask the refresh planner for a reload. The server stays the authority; a missing nudge only means the others see the change at the next 20 s refresh.
A seat change is *never announced*.

=== The room

* The seat plan is a `group` "Sitzplan" of real `<button type="button">` seats, minimum 44 x 44 px (also on a phone: 6 x 44 + 4 x 4 + 16 = 296 px). A seat's accessible name is row, position, state and the *initials spelled letter by letter* ("Reihe 1, Platz 3,
  besetzt, M S", plus ", Hand erhoben" and ", Reaktion: Amen" while they show); there is no name and no `title`. The viewer's own seat has a double ring *and* the visible word "Sie".
* *Keyboard:* roving tabindex (exactly one tab stop: the own seat, else the first free one), Left/Right along the row over the aisle without wrapping, Up/Down to the same position in the neighbouring row, Home/End to the row ends. Enter and Space
  are the native button activation; a taken seat (also the own one) is `aria-disabled` and does nothing. There is no focus trap. The cells are updated in place, so the focus survives every refresh.
* *No optimistic picture:* the chosen seat shows as "pending" (`aria-busy`) until the server answered; the answer replaces the list. A lost race is the fixed sentence "Dieser Platz ist inzwischen besetzt ..." and a reload, a throttle the fixed sentence "Bitte warten Sie ...".
  The client also allows one change per second.
* *People without a seat* stand in the row "Noch ohne Platz" under the pews: initials, a hand badge and a reaction glyph, not operable, no name. *Reactions of such a person are admitted* (B2 dropped everything from a person without a seat, which would have swallowed
  every hand and amen now that nobody is seated automatically) and shown at the seat or at the symbol in that row.
* *List alternative (BR-E2):* "Platz über eine Liste wählen", a `<details>` in the "Anwesende" tab with one labelled button group per row of free seats (no names, no taken seats, at least 44 px), the own-seat status and "Platz freigeben". Not offered to office holders.
* "Platz freigeben" is a secondary button (`ActionIcon.RELEASE_SEAT`), visible only while the viewer sits.
* *Announcements:* the viewer's own result (seated, released, taken, busy) in a polite `status` region; a newcomer in the list is announced anonymously ("Eine Person ist hinzugekommen.", at most every 10 s, no name and no number).
* *"spricht":* LiveKit's active-speaker signal is evaluated for the tiles of office holders only (3 px outline *and* the word "spricht"; volatile, nothing is stored).
* Forced colours keep a `Highlight` outline, the initials, the word "Sie" and the glyphs; the one seat transition (120 ms) is in the single `prefers-reduced-motion` block.

=== Data protection

The *position is visible to everybody who is present*, and the initials can be matched to a name through the "Anwesende" list. That is new compared with B2, where the plan was a per-device drawing that said nothing. The state is in memory, per server instance, not
exported, and dropped when the person leaves, when the session closes and on a restart. *The consent text (`EncounterConsentDisclaimer`, lines "Andere Anwesende sehen höchstens Ihren Namen") does not cover the shared seating position and was deliberately not changed: needs legal review.*

=== Known limitations of stage 2a

* No load test (the precondition of stage 2 in the vault, about 20 people, is not met); tool and run sheet: xref:encounter-load-test.adoc[] (V1.9.149, not run yet).
* Seats live in the memory of one server instance; several instances would not share them (a deployment with more than one instance per Lapis instance is not supported for this feature).
* A silenced person's nudge is dropped by LiveKit; others see the change within 20 s.
* After a page reload the person is without a seat (by design).
* Translations of the new texts are agent-made, not checked by native speakers.
* The seat plan has no "sit anonymously" option (initials are always shown); noted for the legal review.

[#stage-2b]
== Stage 2b (V1.9.80): tables with their own audio group

In a room with the *assembly profile* the BOARD/ADMIN can switch on *tables* (`encounter_space.tables_enabled`, `table_count` 1 to 12, `table_seats` 2 to 8; migration V79, additive; a CHECK constraint ties `tables_enabled` to the profile `ASSEMBLY`).
A person of the congregation sits down at a table and then hears and speaks *only with the others at that table*; the plenary (pulpit or podium) is turned down to 30 % on that device. Office holders never join a table, so nobody who moderates listens in.
Everything about who sits where is in memory only (`EncounterTableState`), like the seat plan of stage 2a.

=== Configuration and profile rules

* The three columns describe the *room*, never a person. `EncounterSpaceInput.tables` (`null` = unchanged on update, off on create) and `EncounterSpaceDto.tables` (effective: `enabled` only ever `true` for the assembly profile) are the last fields with a default (wire compatible both ways).
* `validateInput`: count 1..12 and seats 2..8 (`BadRequestException`, also for a disabled configuration), `enabled` with another profile than ASSEMBLY is a `BadRequestException` -- also when only the profile changes on update while tables are on (the client switches the tables off in the same call; the SQL CHECK never fires first).
* A real change of the table configuration while the room is open is a `ConflictException` (same pattern as the profile and the reactions). The audit snapshot carries the three fields and no person.

=== The security model: one LiveKit room per table, rotated on every departure

*Why not just remove a participant?* LiveKit refreshes the token of a connected client by itself with the same grants, so a short token TTL is no revocation: a client that was only removed could walk back into the table with a refreshed token and listen in.
Therefore the server never relies on removal or on the TTL:

* Each table has an opaque LiveKit room `lc-et-<uuid>` (no space id, no table number). The room is created when the first person sits down, with `max_participants` = the seats of a table, and has *no* `conference_room` row: no participation row, no recording, no protocol, nothing that the ordinary conference RPC surface can address.
* *Every* departure rotates the table: somebody leaves the table, sits at another one, chooses a bench seat, leaves the room, is removed, loses the presence row (the poller), becomes an office holder, or the table is quieted or released. The server allocates a *new* room name, creates it, then *deletes the old room* -- which disconnects everybody in it at once. Names are never reused.
  The remaining people fetch a fresh token for the new name (`tableToken`); a stale token only points at the deleted name and, at worst, re-creates an empty room (LiveKit's default `auto_create`) that nobody listens in and that the reconciler deletes again. *There is no window in which a departed person still hears the table.*
* The table token (`LiveKitAccessToken.mintTableParticipantToken`): room-pinned, `canSubscribe`, `canPublish` only while the table is not quieted, `canPublishSources = ["microphone"]` (no camera, no screen), `canPublishData = false` (no chat and no reactions at a table), never `hidden`/`recorder`/admin. TTL 30 s -- this is only the time to connect, *not* a protection.
  The identity is the member id (as in the plenary), the display name in the token is the *initials*. TURN credentials of a table connection carry the *plenary* lifetime (coturn checks the credential on every allocation refresh; 30 s would cut the audio of everybody behind a relay).
* *"Tisch beruhigen"* needs no `UpdateParticipant`/`MutePublishedTrack` call: the table is rotated and the new tokens carry `canPublish = false` for five minutes (`ENCOUNTER_TABLE_QUIET_MINUTES`) or until a moderator lifts it (which rotates again). `UpdateParticipant` replaces the *whole* `ParticipantPermission` (a partial object would silently set `can_subscribe=false`), so it was deliberately not built.
* `EncounterTableReconciler` (every 5 s) is defence in depth: it deletes every `lc-et-*` room that is not the current room of a table (phantoms, rooms orphaned by a restart or a failed rotation), and rotates a table in which somebody is connected who is not assigned there, holds a track that is not the microphone, or may publish / publishes in a quieted table. It also lifts quiets whose time is up. If LiveKit is unreachable only a warning *without ids* is logged.

=== Service rules

* RPCs: `joinTable(spaceId, table, seat)`, `leaveTable`, `tableToken` (answer `EncounterTableTokenAnswer`, its `token` is `null` when the caller sits nowhere -- Kilua's generator cannot express a nullable return type), `listTables` (seat numbers only, no persons), `quietTable` and `sendToPlenum` (moderation).
* `joinTable`: only a CONGREGATION person present in the open session, tables enabled, not removed from the session (`ForbiddenException` otherwise); `BadRequestException` out of range; `ConflictException` seat taken; `ServiceBusyException` throttled (1 change per 2 s, `requireSeatRate`, checked first) or the table state is full. One place per person: a table seat frees the bench seat and the other way round.
  `tableToken` has its own throttle (20 per minute: a rotation makes everybody at the table ask at once). A token is only returned if the assignment is unchanged after minting (otherwise `ConflictException`, the client asks again).
* `quietTable` / `sendToPlenum`: office holder or BOARD/ADMIN; `sendToPlenum` uses the protection rules of `removeFromSpace` (`moderationSessionInTx`): a steward may not act against a pulpit person, another steward or BOARD/ADMIN; no self-moderation. Neither writes an audit entry or a log line.
* *No LiveKit call inside a transaction or a `synchronized` block*: mutations return `Rotation`s that the caller carries out after its commit (`EncounterTableRooms.apply`: create the new room, delete the old one, best effort -- data protection beats availability, the reconciler is the backstop).
* The state is dropped when the session closes (`closeSpace`, the poller) and its rooms are deleted.

=== The room (client)

* A section "Tische" between the pulpit and the pews: one card per table (`role="group"`, "Tisch 3 · 2 von 6 Plätzen frei"), per seat a real `<button type="button">` of at least 44 x 44 px, standing on a ring around the table top (V1.9.159: first seat at 12 o'clock, clockwise, DOM order unchanged). The accessible name is table, seat, state and the spelled initials ("Tisch 3, Platz 2, besetzt, M S"); there is no name and no `title`. Own seat: double ring and the word "Sie"; a quieted table says so in words and with a symbol; a speaking seat carries the word "spricht" (only at the *own* table -- LiveKit reports the speakers of the room one is connected to).
  Roving tab stop per table, Left/Right/Home/End. A card is at least 172 px wide (V1.9.159, so that eight seats on the ring do not touch): two cards stand side by side from a viewport width of about 400 px, a 320 px phone shows one table per row, never a sideways scroll. No transition.
* Sitting down is not optimistic: the seat is pending until the server answered. The microphone is *off* after sitting down (`EncounterTableSession.microphone` is the only media call; the type has no camera, screen or data method, and a video track is dropped unread). After a rotation the client reconnects with a new token and the microphone comes back only if it was on and the table is not quieted.
  Controls (icon-only bar controls, shown while one sits at a table): the table microphone (`aria-pressed`, state also as text in the card) and the pulpit turned up again ("Kanzel lauter" / "Podium lauter", profile word). The device APIs live in `EncounterMediaSession.kt` only; the allow-list of `ClientEncounterPrivacyTripwireTest` is unchanged.
* List alternative "Tisch über eine Liste wählen" in the "Anwesende" tab (tables with a free seat, no names). Moderators get "Tisch beruhigen" / "Beruhigung aufheben" on every card and "Ins Plenum setzen" in a person's row.
* Announcements (polite region, only the viewer's *own* events): sat down, back in the plenary, the table was quieted or released, seat taken, please wait, connection lost. No sentence names another person.

=== Data protection

Who sits at which table is visible to everybody present (initials; matchable to a name through the "Anwesende" list), and people at a table talk audibly with each other. Nothing is stored: no column, no log line, no audit entry, not part of the Art. 15 export (`EncounterSpacePersonalDataTest`).
The consent texts were *not* changed. *Needs legal review:* (1) the table membership is visible to all present people; (2) conversations at a table are heard by everybody at that table; (3) pulpit and stewards can quiet a table and send people back to the plenary without listening in; (4) there is no option to sit at a table without initials.

=== Known limitations of stage 2b

* No load test (the precondition of stage 2 in the vault, about 20 people, is not met); several table connections raise the TURN load (a second connection per person at a table); tool and run sheet: xref:encounter-load-test.adoc[] (V1.9.149, not run yet).
* The table state lives in the memory of one server instance and is lost on a restart (the people at tables are then back in the plenary and their client reconnects or gives up).
* Every departure briefly interrupts the others at the table (the room is replaced); the client reconnects within about half a second.
* "Kanzel lauter": the plenary is turned down through `HTMLMediaElement.volume`, which is read-only on iOS Safari -- there the plenary keeps its full volume.
* `canPublishSources` is a LiveKit grant; whether v1.13.5 enforces it against a client that tries to publish a camera was *not verified live* in this wave. The reconciler therefore rotates a table in which a non-microphone track appears (checked every 5 s); until then such a track could be heard/seen for up to five seconds.
* `room.auto_create: false` in the LiveKit production configuration would be extra hardening but is not needed (the rotation makes stale tokens harmless); not changed here.
* Translations of the new texts are agent-made, not checked by native speakers.

== Device selection (V1.9.91)

A person in the room can choose the devices they use, locally and without a server round trip. Client only: no migration (the schema stays at V81), no DTO, no RPC.

=== Who can choose what

[cols="2,1,1,1",options="header"]
|===
| Role | Microphone | Camera | Speaker
| Office holder (pulpit, steward) | yes | yes | yes
| Congregation, at a table | the table microphone | no | yes
| Congregation, no table | no | no | yes
|===

The control is one icon-only bar button (`ActionIcon.SETTINGS`, gear), since V1.9.184 *alone in the start zone* of the bar (group `SETTINGS`); in a narrow bar it moves into the "Mehr" sheet (labelled twin "Einstellungen") after "Türen schließen". Its accessible name says what can be chosen ("Einstellungen", "Mikrofon und Lautsprecher wählen", "Lautsprecher wählen"; before V1.9.184 the first was "Geräte wählen"). It exists only while at least one field is a real, enabled choice, so a person who can choose nothing sees no dead control. (V1.9.96: in a church-service room it also exists for the bell sound switch, see "Bell"; it is then named "Glockenton einstellen" when there is nothing else to choose.) It opens a panel (`role="group"`, no dialog, no focus trap): a popover above the bar from 768 px, a sheet from below under 768 px (the guideline's one breakpoint). Escape closes and returns the focus to the button, a click outside or Tab out of the panel closes it, and the "Mehr" sheet and the panel are never open together. Every field has a visible label and a line "Aktiv: ..." (linked with `aria-describedby`).

=== Where the speaker lives

A congregation member's LiveKit session has `publishEnabled = false`, so `LiveKitRoomSession.listDevices`/`switchDevice` answer nothing for them. The sound of the room comes out of the `<audio>` elements of the two media hosts (pulpit and table). The speaker is therefore set on those elements (`HTMLMediaElement.setSinkId`), the same way for everybody, in one class: `EncounterAudioOutput`. `EncounterMediaHost.add` hands every new audio element to it, so the table audio keeps the chosen device across a rotation. Switching is all-or-nothing: if one element refuses, every element goes back to the previous device, and if that fails too, to the system default; two elements never end on different devices. The speaker field exists only with the `setSinkId` API and at least two usable outputs (the Chrome alias `default` and blank ids do not count); the first entry is "Standard des Systems" (`setSinkId("")`). Without the API (Safari) an office holder or a table person sees a plain sentence instead. `webAudioMix` must stay off (it is, and a tripwire pins it): with it the sound would not come from the elements and the choice would do nothing.

=== What is remembered, and why under the conference's key

Only the device id of a choice the person made on purpose, and only after it worked, is written to the browser, under the same key the video conference already uses (`lapis-cloud-device-<kind>`, `conferenceDeviceStorageKey`). The key has no room id, no person and no time. A key of its own with "encounter" in its name would additionally record that this browser visited an encounter room, which the "nothing is stored about the room" promise excludes. The side effect is intended: the choice also holds in the next video conference. Listing, opening the panel, a plug event, a failed switch and the quiet restore never write. "Standard des Systems" removes the speaker key. The single reader, writer and remover are `encounterStoredDevice`/`encounterRememberDevice` in `EncounterDevicePicker.kt`; the tripwire pins one `setItem`, one `removeItem` and that every storage line names the shared key function.

On the next visit the remembered device is applied *quietly* when the device is switched on (office holder: after the microphone or camera went on; table: after the table microphone went on, also after a rotation; speaker: after connecting). A remembered device that is not there is not applied and not deleted; the open panel says "Ihr gemerktes Gerät ist gerade nicht angeschlossen. Es wird das Standardgerät verwendet." Between switching on and the quiet switch the default microphone briefly records, as for any device choice.

=== Plug and unplug

The picker listens to `devicechange` (through `EncounterDeviceEnvironment`, removed again on dispose). A field that has the focus is not rebuilt under the person's hands; it catches up on blur, and the focus never moves. If the active device vanished, the picker switches to the first device of the list (not remembered) and the polite region says once "Das Mikrofon ist nicht mehr verfügbar. Es wird das Standardgerät verwendet." -- it names the *kind* of device, never the device (a label is often a person's name).

=== Data protection

A device id or name never leaves the browser: no RPC, no data-channel packet, no log line, no audit entry, no telemetry, no live-region sentence, no error message. The picker asks for no permission (no `getUserMedia`, no `selectAudioOutput`). The room and table files hand objects on and never name a device identifier (`ClientEncounterPrivacyTripwireTest`: identifiers only in `EncounterMediaSession.kt`, `EncounterAudioOutput.kt`, `EncounterDevicePicker.kt`; `setSinkId`/`enumerateDevices`/`devicechange` only in `EncounterAudioOutput.kt`; the table's microphone devices are a narrow interface of their own with exactly three members, the V1.9.80 three-member table session is untouched).

=== Known limitations of device selection

* Safari (macOS, iOS) has no `setSinkId`: no speaker field, only the sentence for office holders and table people; the congregation without a table sees no control there at all.
* Chrome and Firefox usually list no output devices (or only blank ids) for a congregation member who never allowed the microphone, because the room asks for no permission. Such a person sees no control until a list is available; that is deliberate.
* The output choice on Android depends on the browser.
* There is no test tone.
* The choice is shared with the video conference (same key).
* The breakpoint is 768 px (the guideline's only one), not 600 px.
* The help page `gathering-room` is updated at rollout.

== Blessing (V1.9.95)

The pulpit of a church-service room can speak the blessing: one button, one quiet cross for everybody in the room for seven seconds. It is deliberately *not* a reaction (a reaction comes from a person and is shown at a seat; the blessing comes from the room and belongs to the liturgy).

=== Who may bless (decided by the server)

`IEncounterSpaceService.blessSpace(spaceId)` succeeds only when *all* of this holds, re-read from the database at every call (no cache, no bypass for BOARD/ADMIN):

. the space has the `CHURCH_SERVICE` profile (an assembly has no blessing),
. the caller holds the office `PULPIT` and is an `ACTIVE` member (`EncounterRoles.roleOf`; a steward, the congregation, and BOARD/ADMIN without an office are refused),
. the space is open,
. the caller is present (a presence row of the open session exists).

Every refusal is the *same* bare `ForbiddenException`, so the answer does not tell which condition failed. The client hides the button for everybody else as well, but that is a courtesy, not the lock: the lock is the server.

=== How it travels

The server sends one LiveKit `RoomService/SendData` (RELIABLE, topic `lapis-encounter-blessing`, fixed payload `{"b":1}`, no destination identities, 16 random nonce bytes) after the transaction has ended (an external call never runs inside `transaction {}`). A packet sent this way has *no sender*, so receivers see it without a participant. The client accepts the topic only in that case (`encounterBlessingPacketAccepted`: no participant, 1..16 bytes) and never decodes the payload; the branch stands *before* the participant check that drops participant-less packets. A congregation member with a data channel who publishes the same topic arrives *with* a participant and is dropped.

=== Data protection

* Nothing is stored: no table, no audit entry (the audit log is hash-chained and cannot be erased, so an entry would permanently record that somebody took part in the liturgy and was present, with no protective gain -- misuse is prevented by the permission check and the throttle), no counter, no log line above one fixed `DEBUG` text ("blessing send failed", no room, no person).
* The throttle `EncounterBlessingState` lives in memory per server instance: session room id -> instant of the last blessing, nothing else (no member, no count). At most one blessing per session room and 10 s; a second one is swallowed silently (the call returns normally). Entries expire lazily, the map is capped at 10 000 entries (oldest first) and an entry is dropped when the session closes. A per-member flood guard (the moderation limiter, answering with a `ConflictException` like the other encounter throttles) comes first.
* `ClientEncounterPrivacyTripwireTest` / `EncounterPrivacyTripwireTest` pin all of it: no write and no `AuditLogRecorder` in the blessing path, exactly one logger call, no `memberId`/`identity`/logger in the throttle, no decode and no storage in the client.
* The announcement is one fixed sentence ("Der Segen wird gesprochen"); it names nobody.

=== The display

A latin cross (outline, drawn with `createElementNS`, never parsed from text) and the word "Segen" in the pulpit area, `aria-hidden`, `pointer-events: none`, visible to *everybody* in the room (also with "Szene ausblenden" and in the full screen, because it lives in the pulpit area, not in the scene layer). A second packet while it is on restarts the 7 s window and opens no second display. A persistent polite live region (created with the room, so it is announced) receives the fixed sentence when the display opens and is cleared one second later, so a later blessing is announced again; an extension is not announced.

No accent colour, no scaling. Since V1.9.97 the first blessing of a window also sounds a recorded low bell in a room with a bell, under the rules of "Bell and blessing sound" below (switch on, page visible; an extension never sounds); since V1.9.98, in a room with a bell, a second line "Ton aus" (the same text and the same line style as the bell sign, `.lapis-encounter-blessing-mute`) appears while this browser's sound is off. It is read once when the sign opens, is `aria-hidden`, adds no announcement, is not rebuilt on an extension and does not appear in a room without a bell. The only motion is an opacity transition of 200 ms that `prefers-reduced-motion` switches off (the display is then hidden at once). Contrast, worst case (text on the panel, panel = encounter surface at 80 % over pure black in the light theme, over pure white in the dark theme): light `#14181E` on about `#C3BFB8` = 9.7:1; dark `#E8E6E0` on about `#4F545C` = 6.1:1 -- both above 4.5:1. `ClientEncounterBlessingCssTripwireTest` pins the CSS facts, because Karma cannot emulate the media query reliably.

=== The control

`ActionIcon.BLESSING` (`fa-cross`), icon-only, 44 x 44 px, in its own `LITURGY` group between the reactions and the panels; the group does not exist in the DOM for anybody but the pulpit of a church room. It has a labelled twin in the "Mehr" sheet and leaves the bar late (after "Türen schließen", before the chat). One press = one call (a press while the call is out is ignored); a refusal or an error is neither shown nor logged.

=== Known limitations of the blessing

* The client recognises "from the server" by *no participant*. The SDK also reports no participant for a sender it does not know yet (during the join race or after a full reconnect that cleared its event buffer). A member who may publish data could, in that narrow window, show the cross to single receivers for 7 s. The damage is brief and nameless; checking the raw packet identity would depend on an internal SDK API and is not done.
* The throttle is in memory and per server instance: a restart resets it.
* A failed delivery is not reported to the pulpit.
* A person who loses the office during the session keeps the button until the next reload; the server refuses the call.
* The help page `gathering-room` is updated at rollout.

== Bell and blessing sound (V1.9.96 / V1.9.97)

The pulpit of a church-service room can ring a bell: one button, one quiet sign for everybody in the room for five seconds and, if the person chose so, a recorded bell sound (since V1.9.97 also for the blessing). Like the blessing it comes from the room and belongs to the liturgy, not to a person; it is *not* a reaction.

=== Who may ring (decided by the server)

`IEncounterSpaceService.ringBell(spaceId)` has *exactly* the rights of `blessSpace`: both call the same private helper `liturgyTargetInTx` (so the permission is structurally identical, not copied): `CHURCH_SERVICE` profile, an `ACTIVE` `PULPIT` office holder, an open space, the caller present. Every refusal is the same bare `ForbiddenException`. The permission check runs *before* the throttle, so an unauthorised caller cannot probe the throttle state.

=== How it travels

One LiveKit `SendData` after the transaction (topic `lapis-encounter-bell`, fixed payload `{"v":1}`, no sender). The client accepts the topic only without a participant and with 1..16 bytes (`encounterBellPacketAccepted`) and never decodes the payload; the branch stands *before* the participant check, like the blessing's. A participant who publishes the topic arrives with a participant and is dropped. An old client ignores the unknown topic (the packet has no participant, so it is dropped before any topic switch); a new client against an old server fails the call, which is swallowed silently. No client version gate is needed.

The throttle `EncounterBellState` is a separate in-memory class (room id -> instant, nothing else; at most one bell per session room and 10 s, swallowed silently; capped at 10 000 entries; cleared when the session closes). The blessing and the bell never throttle each other. The pulpit's button also locks itself for 10 s (`aria-disabled`, still focusable, no number).

=== The sign

A chip with the bell symbol and the word "Glocke" in the pulpit area, in the same holder as the blessing's cross (`.lapis-encounter-signs`: the bell on the left, the blessing on the right, wrapping under each other on a narrow screen), `aria-hidden`, `pointer-events: none`, visible to everybody in the room for 5 s; a second packet restarts the window and neither opens a second sign nor rings again. While this browser's sound is off, a second line says "Ton aus" (since V1.9.98 the blessing sign shows the same text under the same rules, in a room with a bell). Its own persistent polite region (separate from the blessing's, so one never clears the other's sentence) receives the fixed sentence "Die Glocke läutet" and is cleared one second later. Nothing in the sign can be operated (WCAG 2.2.1). The sign is set *before* the sound is tried; a failing sound never keeps it away. Same surface and motion rules as the blessing (opacity transition of at most 200 ms, off under reduced motion; `ClientEncounterBellCssTripwireTest`).

=== The sound

Two recordings, played through WebAudio (V1.9.97; V1.9.96 synthesised the sound, which is gone for good). Both are CC0 (Creative Commons 0 1.0, confirmed on 2026-10-10); provenance, processing and hashes are in `lapis-client/src/jsMain/webAssets/encounter-sounds-v1/PROVENANCE.adoc`. Pixabay recordings were deliberately not used (the licence forbids passing a file on unchanged).

|===
| File | Source | Used for | Level

| `call-bell.mp3`
| "Church bells Pont Barer, la Drôme", MJPtack, Freesound 753412
| the call: a peal of several strikes, 8 s
| gain 0.25

| `blessing-bell.mp3`
| "bec low bell solo.wav", HMTSCCSound (Bethesda Church, Saratoga Springs NY), Freesound 554655
| the blessing: one low strike, 8 s
| gain 0.18

Both are MP3, mono, 44.1 kHz, 8.0 s, 48 kbit/s (48690 and 48713 bytes; SHA-256 `b41a4b3e...4405` and `7eebd9ed...d267`, pinned in `EncounterSoundAssetsTest` and, on the staging and on the webpack copy, in `VerifyVideoEffectAssets` of `lapis-client/build.gradle.kts`). The sample peaks are -2.2 and -2.7 dBFS (ffmpeg `volumedetect`), so the decoded peak is at most 1.0 and the output peak at most 0.25 x 0.78 (call) and 0.18 x 0.73 (blessing): never above the 0.25 the synthesis had. The switch's confirmation sample is the blessing strike at gain 0.25, cut after 3.0 s with a 0.5 s fade-out.

*Delivery.* `/assets/encounter-sounds-v1/` is served by its own route in `ClientAssetRoutes.kt` (registered before the generic `/assets` prefix): `Content-Type: audio/mpeg`, `Cache-Control: public, max-age=31536000, immutable`, no listing, no logging. The directory is versioned: if the bytes ever change, it becomes `encounter-sounds-v2` in the three places that name it (client constant `ENCOUNTER_SOUNDS_DIR`, `ENCOUNTER_SOUNDS_ASSET_DIR`, Gradle `into(...)`; `EncounterSoundAssetsTest` keeps them together).

*Loading.* Only after the person's own decision, never earlier: in the switch's `change` handler (`probe()`) or, after a reload with the switch remembered as on, in the first pointer or key press (`prime()`); both need a user activation (without one no context and no request exist). Both files load in parallel, once; a ring never starts a load, a room without a bell and a person with the sound off never load anything. A failed load is silent and not retried automatically; switching the sound on again makes exactly one new attempt. The request (`EncounterSoundFetch.kt`, the only file with `fetch` and `decodeAudioData`) is same-origin with `credentials: "omit"`, `referrerPolicy: "no-referrer"`, `mode: "same-origin"`, `redirect: "error"`; the answer must be `ok`, of an `audio/...` content type (the catch-all route could answer an unknown path with a page and status 200) and at most 256 KiB. The URLs are the two constants, without query, fragment, room or person.

*Why WebAudio and not an `<audio>` element.* The chosen speaker acts on exactly one audio context (`EncounterAudioOutput.applyToContext`); a second sink path through an element would clash with the all-or-nothing selection of the picker. An element with a `src` could be pre-loaded by the browser before the person switched the sound on. A gain node caps the level deterministically and allows exact stopping and fading.

*One voice.* At most one voice sounds per room. A second call of the kind that is sounding is ignored; a call of the other kind fades the running voice out over 0.25 s and starts after it. A recording that is still loading when it is asked for is remembered as the one waiting request (a newer one replaces it) and played only if it is ready within 1500 ms and the page is still visible; later it would no longer match the sign. Nothing ever starts in a hidden tab, `silence()` (hidden tab, switch turned off) fades the voice out and forgets the waiting request, and `dispose()` stops at once, closes the context and drops the buffers.

The call sounds with the sign (first packet of a window only), the blessing with its display (likewise, only in a room with a bell, i.e. the church profile); an extension of a window never sounds. It never sounds without the person's own switch.

*Autoplay.* A browser only lets a sound start after a user activation. The switch's `change` handler creates / resumes the context and starts the loading synchronously, then plays the probe sample (no `await`, no `launch` before it: Safari). After a reload with the sound remembered as on, the first pointer or key press anywhere primes the audio context silently (one `once` listener pair, removed on dispose); a bell that rang before that is not played afterwards. Without a prior activation no `AudioContext` is created at all (it would only earn a console warning). Every `resume()`/`close()` promise has a `catch`, so a refusal is never an unhandled rejection.

*Speaker.* If the browser's `AudioContext` has `setSinkId`, the context follows the speaker chosen in the device panel (through a lambda; the room never sees a device id, `EncounterAudioOutput` stays the only place with the sink logic). Without it (Safari) the sound plays on the system default.

=== The switch

The gear (device picker) holds a "Glockenton" switch (`role="switch"` on a native checkbox, its own label, and a description with two lines under one id: "Erklingt beim Ruf und beim Segen." (what it does) and "Gilt nur für diesen Browser." (the hint)). Turning it on starts the loading and the sample, turning it off silences a sounding voice. It exists only in church-service rooms and for *every* role. Default off. Because the switch lives in the gear, the gear is now always in the bar of a church-service room (also for the congregation, whose gear used to be hidden without a choice of devices); it then says "Glockenton einstellen". That costs one permanent place in the bar, also at 360 px.

=== What is remembered

Exactly the second storage key `lapis.encounter.bellSoundOn` (value `1`), written only by the person's own change of the switch (`storeEncounterBellSoundOn`, called through the switch model's `write`), removed when switched off; opening and redrawing the panel only read. *Honest limit:* the key exists only after somebody chose the sound in a church-service room, so its existence is a local hint that this browser has been in one (see `dsgvo.adoc`). Rejected alternatives: remember nothing (a sound switch that forgets itself is unusable) and a neutral key name (does not change that the key arises only from such a room).

=== Data protection

Nothing is stored on the server, nothing counted, no audit entry (it would permanently record that somebody took part in the liturgy), one fixed `DEBUG` text ("bell send failed"). `EncounterPrivacyTripwireTest` and `ClientEncounterPrivacyTripwireTest` pin all of it (no write in the bell path, one log line, memory-only state, no decode of the packet, the two storage keys and where they are written, no console/counter in the sign and the sound, and -- V1.9.97 -- the one network request of the whole encounter client is the sound loader `EncounterSoundFetch.kt` with its fixed options).

=== Known limitations of the bell

* Never tried against a real LiveKit server with `SendData`.
* The autoplay rule can keep the first sound after a reload from playing until the next gesture in the room.
* Without `AudioContext.setSinkId` (Safari, partly Firefox) the sound uses the system default, not the chosen speaker.
* No call outside the room (a push notification is a follow-up wave) and no automatic bell with the blessing (follow-up wave).
* The existence of the storage key is a local hint of a church-service visit.
* The symbol `fa-bell` has two other meanings elsewhere (see `action-icons.adoc`).
* The throttle is in memory and per server instance; a failed delivery is not reported; a person who loses the office keeps the button until the next reload (the server refuses).
* The website and the help page `gathering-room` are not changed in this wave and are updated at rollout.
* V1.9.98: the "Ton aus" line is read when the sign opens and not updated live; the line shows the switch, not the result (sound on in a background tab shows no line). The help page `gathering-room` for the blessing is checked at rollout; the website is not changed in this wave.
* V1.9.97: the sound can ring on for up to 8 s, longer than the 5 s sign (intended: a bell fades away).
* V1.9.97: the blessing sounds only in a room with a bell (church profile) and only under the bell's switch; an assembly's blessing stays silent.
* V1.9.97: on a slow network the sample of the first switch-on is dropped if the files take longer than 1500 ms (the same lateness rule as for the call and the blessing); the switch is on nevertheless and the next call sounds once the files are there.
* V1.9.97: the server's and the proxy's access logs see IP, time, user agent and the path of the recording; the path name is itself a hint of a use in a church-service room (see `dsgvo.adoc`). The HTTP cache entry (immutable, one year) is a further local trace of the same kind as the storage key.

[#floor]
== Temporary floor grant (V1.9.138)

An office holder (PULPIT or STEWARD) can give one person of the congregation the floor for two minutes, extend it, and take it back.
The person's microphone then reaches everybody in the room. Nothing about this is stored.

=== Who may grant

Only an ACTIVE PULPIT/STEWARD of *this* space who is present in the open session (`floorAuthorityInTx`). BOARD/ADMIN without an office
may not, nor may an office holder of another space; the space must not be archived. Every refusal -- wrong role, not present, closed,
archived -- is the same bare `ForbiddenException` (no side channel: a bystander learns nothing, not even whether somebody speaks).
`endFloor` additionally lets the person who has the floor hand it back; `floorState` answers everybody who is present.

=== Who may receive

Every person with the CONGREGATION role who is present, not silenced, not seated at a table, and connected at LiveKit without a track
-- BOARD/ADMIN without an office and guests with a valid consent included. Not allowed (`ConflictException`): oneself, an office holder, a
silenced person, a person at a table, somebody absent or not connected, somebody who already publishes. Decision of 2026-10-15 (guests
included); if a guest must be excluded later it is one more `status in NON_MEMBER` check in `floorTargetInTx`.

=== The permission

The grant is *not* a token: a token lives until its TTL and cannot be taken back; the congregation's tokens keep `canPublish = false`.
The server raises that ONE live connection with `UpdateParticipant` to `{subscribe, publish, publish-data, sources = [MICROPHONE]}`
(`encounterFloorPermission`, the only source of this permission; never `conferencePermission`, which would give camera and screen share).
`UpdateParticipant` replaces the whole permission, so `canSubscribe` is always set. The sources stay `["MICROPHONE"]` *also when the floor
is taken away*: an empty list means "all sources" in LiveKit, so should `can_publish` ever be evaluated wrongly the camera stays locked
(defence in depth; the design text said "empty sources").

The state is set *before* the permission is raised, so the poller never sees a raised permission without a grant. A LiveKit failure while
raising rolls the grant back and is a conflict.

=== Expiry and the revoke ladder

`EncounterFloorEnforcer` ticks every second. A floor lasts 120 s; extensions of 60 or 120 s are allowed up to a total of 600 s since the
grant. When it ends (expiry, `endFloor`, the holder leaves, is removed or silenced, sits down at a table, gets an office, the session
closes) the ladder runs: (1) the grant is no longer valid at once and "off" goes to everybody; (2) three attempts of `can_publish = false`
plus muting every unmuted microphone track; (3) `removeParticipant`; (4) if even that fails the grant stays as "revoking" and the
enforcer tries again every 5 s. *There is no path on which a grant leaves the state without a successful demotion or disconnect* (a
restart and the end of the session excepted -- then the poller disconnects every publisher that is not an office holder).

Every 15 s the enforcer verifies a valid floor against LiveKit: the holder is still connected (two checks in a row without them end the
floor), nothing but one microphone track is published (a camera or a second track ends the floor and disconnects the person), and the
permission is still raised (a LiveKit reconnect with the old token resets it to "listen only"; the grant is applied again while it is valid).

=== Poller tolerance and the 90 s grace

`EncounterSpacePoller` still disconnects every non-officer who publishes -- with one exception: the holder of a *valid* floor who publishes
one microphone track and whose sources are limited to the microphone. After the end it tolerates, for 90 s, a leftover *muted* microphone
track without publish right (LiveKit may keep the track until the client unpublishes it; the client does unpublish). Everything else --
a camera, a second track, an unmuted track after the end, a right that outlived the grant, any leftover after the grace -- is
disconnected as before. A floor that expires between the poller's two reads costs the person the connection; that is intended (safety
before comfort) and rare.

=== Restart

The state is empty after a restart, and the poller runs once at start: the first run disconnects every publisher that is not an office
holder. A floor in progress is lost, never kept.

=== The packet

Topic `lapis-encounter-floor`, sent only by the enforcer: `{"s":"ON","t":118}` to everybody, `{"s":"YOU","t":118}` to the holder alone,
`{"s":"OFF"}` to everybody. No identity, no name. The client accepts it only without a sending participant, with 1..64 bytes and the strict
shared parser (`encounterFloorPacket`); a forged packet is dropped and would grant nothing anyway (without `UpdateParticipant` LiveKit
refuses the publish). `SendData` has a size limit per topic: `lapis-encounter-floor` has its own entry (64 bytes) in
`sendDataPayloadLimit`; without it the topic would fall back to 16 bytes and throw an `IllegalArgumentException` that fakes do not show.

=== Data protection

The congregation sees "somebody from the congregation is speaking" and the time left -- no name and no seat, although the names of the
people present are visible to them elsewhere (decision of 2026-10-15: the stricter variant). Only office holders and the holder see the
name. No audit entry, no database row, no log line with a person or room above DEBUG; the floor files carry tripwires for exactly that
(`EncounterPrivacyTripwireTest`).

=== Threat model

[cols="2,3", options="header"]
|===
| Case | Behaviour
| A hostile client asks for a token with `canPublish` | Impossible: `enterSpace` still issues `canPublish = false` to the congregation. The raise happens server side on the running connection and can be taken back at any time -- a token cannot.
| A forged `lapis-encounter-floor` packet | Dropped unread by the client; even if accepted it grants nothing.
| A manipulated clock in the client | No effect: the server clock is monotonic, the revoke comes from the server.
| The client does not unpublish / unmutes after the end | `can_publish = false` plus `MutePublishedTrack`; an unmuted track after the end is a violation and the poller disconnects the person.
| A camera or second track during the floor | The sources are limited to the microphone; additionally the 15 s check and the poller disconnect the person.
| A double grant | A mutex per session plus `Busy`: a conflict, never a silent replacement.
| LiveKit is down at the end | Three attempts, then a disconnect, then "revoking" with a retry every 5 s; the poller disconnects independently. The right is never unlimited.
| A server restart | The state is empty; the first poller run disconnects every community publisher.
| The holder's LiveKit reconnect | The right falls back to the token (`false`); the enforcer applies it again within 15 s while the floor is valid.
| The grantor loses the office | The floor runs on until expiry or revoke (at most 10 minutes); documented, see the open questions.
|===

=== Hand order

The list of hands is numbered in the order the hands arrived *at the viewing office holder's client*. A renewed hand keeps its place; a
hand that was raised before the office holder arrived appears in the order of its next renewal (every 30 s). A server-side order would mean
state about persons on the server and contradicts the memory-only decision.

=== Known limitations of the floor

* Not verified against a real LiveKit (v1.13.5): in particular whether LiveKit removes a published track itself when `can_publish` is
  withdrawn, or only stops forwarding it. The design is robust both ways (mute, client unpublish, 90 s grace, then disconnect); the proof is
  step 5 of the staging script.
* Only tested in Chromium (Karma, headless).
* The state is lost on a restart (then nobody has the floor).
* Microphone only: no device choice and no noise suppression for the floor microphone.
* One person at a time.
* The order of hands holds from the arrival of the office holder's client on.
* The translations are model translations.

[#pulpit-recording]
== Pulpit recording (V1.9.143)

An encounter room can optionally record **the pulpit**: the camera and the microphone of the person who holds the PULPIT office, into the document store. It is the
one deliberate exception to "nothing is recorded"; it is built so that it stays narrow. Operator view: `docs/features/pulpit-recording.adoc`.

=== Why it is configuration, not a decision of the product

Whether a recording of a person is lawful depends on the country of the instance. Lapis Cloud therefore does not rule on it: the feature is **off**, an ADMIN switches it
on after acknowledging an operator notice (`PulpitRecordingNotice`, version `1`, hash pinned by `PulpitRecordingNoticePinTest`; a changed text needs a new version, which
blocks only *new* starts until it is acknowledged), and BOARD/ADMIN allow it per room. The notice is not legal advice either.

=== Gates (every one answers with the same bare `ForbiddenException`)

. instance switch on **and** the current notice version acknowledged (for a *start*; a *stop* needs neither, so a recording can always be ended);
. the room option on and the room not archived;
. an open session that is an encounter session (`EncounterRoomGuard.isEncounterRoom`), so an ordinary conference room is never reachable;
. the caller is an ACTIVE PULPIT/STEWARD **of this space** (`EncounterRoles.roleOf`) and present in the session;
. the setting is read again in the final transaction after the egress started (prepare, act, re-verify); if a condition vanished meanwhile the egress is stopped and its file
  discarded.

`PulpitRecordingService` is registered **last** in `Application.kt` (Kilua numbers routes by declaration order; `ConferenceTimerServiceEventGuardTripwireTest` pins the tail:
timer, agreement texts, pulpit recording).

=== Who is recorded

Only `PulpitRecordingSources.select`: ACTIVE PULPIT holders with a presence row in the session and a connected LiveKit participant whose identity equals the member UUID.
A steward never; a person with a temporary floor holds no office, so never. Per room at most `PULPIT_RECORDING_MAX_CONCURRENT_PER_ROOM = 2` (stable order by member id,
those already recorded keep their slot), server-wide `MAX_ACTIVE_PULPIT_EGRESSES = 8`. The congregation is not in the file: a *participant* egress records only the
published tracks of one identity. The existing `LiveKitEgressClient.startParticipantFileEgress` is reused; **no new egress method** exists
(`ConferenceTimerRecordingTripwireTest` still pins the four kinds). The output path is `<container dir>/pulpit/<space uuid>/<random uuid>.mp4` -- no identity in it.

=== The pulpit's own agreement

With "require confirmation" (default) the start asks the PULPIT identities point to point (`ask` flag of the recording packet) and throws
`PulpitRecordingAwaitingConfirmationException`; the person agrees in a dialog (the `REC_PULPIT` text, label and hash sent back and compared in constant time) and the
engine then starts their file. **Nothing is persisted**: who agreed in this session lives in `PulpitRecordingState` (memory, `PulpitRecordingPersistenceTripwire` in
`PulpitRecordingTripwireTest`), because a table "person X stood at the pulpit on day Y" would be a lasting trace in an Art. 9 context. The audit entry of a start carries
`pulpitConfirmed`, `confirmationRequired`, the hashes of both texts and the notice version -- no participant count, no identity but the acting person (the audit frame's actor).

=== Echo rule (floor)

A person of the congregation who holds the temporary floor is played through the pulpit's loudspeaker and could end up in the pulpit's microphone. Therefore: a start is
refused while a floor is granted (`PulpitRecordingFloorActiveException`), and a floor granted during a recording stops the recording *before* the right is raised
(`FLOOR_GRANTED`); it has to be started again, which gives a new file.

=== The clock (`PulpitRecordingCoordinator.tick`, every 15 s)

Per running session: instance off, room option off, floor granted, maximum duration (`LAPIS_RECORDING_MAX_DURATION_MINUTES`), the room gone -- each stops the recording
(audit without an actor, `reason`); a source that is no PULPIT any more is stopped (`SOURCE_NOT_PULPIT`, also directly after `setSpaceRoles`); a file that ended on its own is
queued for archiving and the session stays *armed*; a pulpit person who arrives later (and has agreed) is recorded; every newcomer learns the state point to point
(roster key = identity + LiveKit sid). **The banner is never switched off on doubt**: an unreachable LiveKit leaves the state as it is. After a restart the first run stops
every file egress in an encounter room that the process does not own (a stream egress has no file result and is left alone), sends "off" to the open rooms and logs a
warning with a count if files lie unclaimed on the volume (nothing is deleted).

=== Storage, marker and hard delete

`PulpitRecordingDocuments.archive` copies the file with the existing streaming `archiveGeneratedFile` (new parameters `folderAccessLevel` -- the folder "Aufzeichnungen
Begegnungsraum" is created `BOARD_ONLY`, because the function used to create missing folders `PUBLIC_MEMBERS` -- and `onDocumentCreated`, which writes the marker row
`pulpit_recording_document(document_id, space_id, recorded_at)` in the same transaction). The marker has no member column (`PulpitRecordingSchemaDriftTest`). Deleting is
**hard**: bytes of every version (path checked to stay inside the store), version rows, the AI-knowledge rows of the document, the marker and the document; the ordinary
`DocumentService.deleteDocument` redirects a pulpit recording to the same function. Backups keep older copies until rotation. The table is part of the organization backup
(`OrganizationBackupRoundTripTest`).

=== Privacy rules of the code

No log line of the pulpit files names a member, identity, room, space, title or path (`PulpitRecordingTripwireTest`, `EncounterPrivacyTripwireTest`); LiveKit is never called
inside a `transaction {}`; the recording topic `lapis-encounter-recording` is sent only by the engine and accepted by the client only without a participant and before the
participant check; its payload limit (32 bytes) is registered in `sendDataPayloadLimit` (without an entry the topic would fall back to 16 bytes and every send would fail).

=== Consent texts for non-members

(Superseded in V1.9.148: the recording variants are now derived by the code from the administered text, see "Consent text (V1.9.148)" above; the objects `EncounterRecordingConsentDisclaimer` (`2026-10-16.rec.v1`) and `EncounterAssemblyRecordingConsentDisclaimer`
(`2026-10-16.assembly-rec.v1`) remain only as proof.) A room with the option on shows a notice with the same attendance statements, but "the pulpit can be recorded; your own picture and sound never are". The choice follows the **room option**, not
the instance switch (rather too much information than too little), which is why the option can only be switched on while the room is closed. The two old texts are unchanged
byte for byte (their acknowledgments are proof). All consent texts are drafts and need a legal review for the country of the instance. Members are not asked; the entry panel
tells them and shows the operator's `REC_ROOM` text.

=== Threat model

[cols="2,3", options="header"]
|===
| Threat | Answer
| A listener starts a recording | The gate: only an ACTIVE PULPIT/STEWARD of this space who is present; the same bare Forbidden for everybody else.
| A client names whom to record | There is no such parameter; the source is derived from the database and the LiveKit roster.
| The congregation ends up in the file | A participant egress records one identity; the echo rule keeps a floor speaker out.
| A forged "recording off" packet | The client accepts the packet only without a participant (server only) and a strict shape.
| The banner lies after an outage | It is never switched off on doubt; a stop that LiveKit does not confirm keeps the recording "on".
| A recording outlives the switch | The instance switch stops all, the room option stops the room, the clock re-checks every 15 s.
| A restart loses the state | The first run stops unowned file egresses and sends "off"; leftover files stay and are counted, never deleted.
| Deleting is only "soft" | Hard delete of bytes and rows; older backups keep a copy until rotation (documented).
|===

=== Known limitations of the pulpit recording

* Not verified against a real LiveKit v1.13.5 / egress: the participant file egress request, that the recording participant is ignored by the encounter poller, and that an
  active file egress reports its target path at start (the restart sweep relies on a non-empty `file_results` without `stream_results`).
* The camera can show people who are physically next to the pulpit person; the software cannot prevent it.
* The state is in memory and not shared between several server instances.
* The egress volume needs the right for the `pulpit/` subdirectory (the ELB ACL trap of the conference recording applies).
* The unlimited retention, the `BOARD_ONLY` level (TREASURER can read it as for every such document), the draft consent texts and the model translations are decisions or
  tasks of the owner.

=== Data and rules

* *Migration V109* (`V109__encounter_room_layout.sql`, additive; V1 to V108 untouched): the column `encounter_space.room_layout` (`VARCHAR(16)`) is added nullable, **back-filled** (church service becomes `NAVE`, every other room `HALL`), only then set `NOT NULL`, and only then do the two CHECK constraints apply (`chk_encounter_space_room_layout`: the four names; `chk_encounter_space_room_layout_profile`: `NAVE` only with `CHURCH_SERVICE`, `FOYER` and `SMALL_GROUP` only with `ASSEMBLY`, `HALL` with both). The order matters: a CHECK or `NOT NULL` before the back-fill fails on existing rows.
  The column keeps a database default of `HALL`. `HALL` is valid for both profiles, so a row written by a server image from before V109 (a rollback, staging) still satisfies the CHECK instead of failing every `createSpace`; the current server always writes the column explicitly. Verified on H2 and on PostgreSQL 17 (`EncounterRoomLayoutMigrationScenarios`).

The audit snapshot carries the enum name and no person. `encounterConsentFor` does not take the template: the entry notice and its hash are identical for all four templates (`EncounterRoomLayoutServiceTest`).

== Stage 3 wave 1 (V1.9.166): grid map

A room of the *assembly* profile can have a *grid map*: a small floor plan of 12 x 8 tiles on which the **members** who are present stand and walk. This is wave 1 of stage 3 (map and positions only; no proximity audio yet). The map is configuration of the room (`encounter_space.map_enabled`, migration V111, default off); a position is **never stored anywhere but in the memory of the server and of the tab**.

=== Data and rules

* *Migration V111* (`V111__encounter_map_option.sql`, additive; V1 to V110 untouched): `encounter_space.map_enabled BOOLEAN NOT NULL DEFAULT FALSE` with the CHECK `chk_encounter_space_map_profile` (`map_enabled = FALSE OR profile = 'ASSEMBLY'`), and `encounter_consent_acknowledgment.consent_version` widened from `VARCHAR(50)` to `VARCHAR(58)` (the entry-notice label gets the code-owned suffix `+map`, so `<label>+rec+map` is up to 46 + 8 = 54 characters; `ENC_LABEL_MAX` stays 46 so that every published label stays valid). No time field, no table, no column for a position, a facing or a path (`EncounterPrivacyTripwireTest` scans the migrations and the generated schema).
* *Shared* (`lapis-shared`, `EncounterMap.kt`): the dimensions, the three templates `HALL`, `FOYER`, `SMALL_GROUP` (walls and objects only; the nave has none), the breadth-first searches `encounterMapNearestFree` and `encounterMapPath`, the DTOs, and the strict parser `encounterMapPacket`. Enums are append only.
* *Server* (`EncounterMapState`): ONE monitor, no `suspend`, no logger, no transaction, no audit (`EncounterPrivacyTripwireTest`). At most 25 walkers, 64 sessions and 500 registered viewers. A person who leaves is gone at once; there is no history and no per-person counter. The state has an `epoch` (random per process): a restart is visible to every client, and all positions are empty.
* *Authority*: the API has no coordinate and no member id parameter (`mapEnter(spaceId)`, `mapStep(spaceId, direction)`, `mapTeleport(spaceId, anchor)`, `mapLeave(spaceId)`, `mapSnapshot(spaceId)`), so "next to" is guaranteed by the API itself and there is nothing to forge. `mapEnter` and `mapSnapshot` pass `mapGateInTx` (database). `mapStep` and `mapTeleport` touch **only memory** (25 people x 8 steps a second would otherwise be a DoS surface); their authority is the entry `mapEnter` created after the full check, removed at once by the hooks below and re-checked every 5 s by the reconciler.
* *Gate*: every refusal is the same bare `ForbiddenException`. Order: (1) status ACTIVE -- a guest or friend is refused **before the space is looked up**, so for them every id gives the same answer and there is no existence oracle; (2) the space is visible; (3) assembly profile with the map on; (4) the session is open; (5) the caller is present; (6) for walking: no office; (7) for walking: not removed or silenced. An office holder may call `mapSnapshot` (read only).
* *Pace*: token bucket per walker, capacity 3, one token per 120 ms (monotonic clock); without a token the step is `THROTTLED`, silently and without a change. A wall, the edge, an object or another person is `BLOCKED` (the facing still changes). Teleport at most once per 1 s (a jump onto the own tile sets no cooldown). On the client every anchor click is answered: inside the cooldown no request is sent but one spoken notice is given per cooldown phase; a running step is waited out instead of swallowing the click; the anchor buttons show `aria-disabled` and `is-cooling` and NEVER the native `disabled` (it would drop the focus). Outer flood brake 600 requests a minute; `mapEnter` and `mapSnapshot` one per 2 s. Throttles are `ServiceBusyException` (own type: `ConflictException` means "seat taken" in this service).
* *One place per person*: `mapEnter` releases a bench seat and leaves a table (a throttled departure from a shared table changes **nothing**, the new entry is taken back). `selectSeat`, `joinTable`, `enterSpace` (a reload), `leaveSpace`, moderation (removing also drops the registration for the packets), `setSpaceRoles` (a new office), `closeSpace`, the poller and switching the option off all drop the position.
* *Delivery* (`EncounterMapBroadcaster`): every 200 ms the state is drained into deltas (`changed` and `removed` only) and sent with `LiveKitAdminClient.sendDataTo` (never `sendData`) on the topic `lapis-encounter-map` to the **registered viewers only** (chunks of at most 50). A viewer is registered only by `mapEnter`/`mapSnapshot` after the gate, i.e. an ACTIVE member who is present -- a guest can never be a recipient. A delta over 4096 bytes or over 64 entries becomes a `reset`. A packet is `{"v":1,"t":"d","e":epoch,"s":seq,"c":[[id,x,y,"N","AB"]],"r":[id]}`; it carries **no name** (the client resolves names through `listPresent`, which already shows them to everybody present). `sendDataPayloadLimit` has the entry for the topic (without it the 16-byte fallback applies and every real send fails).
* *Reconcile* (every 5 s, from the database): a session that is closed, a map that is switched off, a person who is no longer present, no longer ACTIVE (a status change during the session) or who got an office leaves the map. The window for a status change is therefore **at most 5 seconds**, not "at once".
* *Room option* (`createSpace`/`updateSpace`, BOARD/ADMIN): off by default; a flag **sent** for a profile without a map is `BadRequestException`; a stored `true` that no longer fits (an old cached admin client switches the profile without a flag) is reset like the room template. Switching it ON needs a closed room (`ConflictException` otherwise: the entry notice people acknowledged depends on it), switching it OFF is always allowed and drops every position at once (viewers get a `reset`). The audit snapshot carries the switch `mapEnabled` and nothing else.

=== Entry notice

For a room with a map the code appends a second code-owned paragraph (`EncounterConsentLayout.mapParagraph`) as the last key point and the end of the full text, adds the label suffix `+map` (`+rec+map` with the recording option) and hashes the result. Without both options the notice is byte-identical to before (the old pins stay green). Non-members acknowledge it as before (`consentChanged` is true for a guest who acknowledged an older version); members see the paragraph as `EncounterEntryInfoDto.mapRoomNotice` and above the button "Auf die Karte" -- they have no proof row, the free click is their act. **The wording is a DRAFT without legal review** (`ASSEMBLY_MAP_PARAGRAPH_DRAFT`, pinned word for word and by hash in `EncounterMapConsentTextTest`).

=== The client

* `EncounterMapController` (DOM free) and `EncounterMapView` (DOM, built once, then only filled). The board is a `role="group"` named "Karte" with ONE tab stop, described by the status line. Arrow keys and W/A/S/D step (a key with Ctrl, Alt or Meta is left to the browser), "L" speaks the own place and the names nearby, Escape focuses "Karte verlassen" while the viewer is on the map (a further Escape, or Escape off the map, is the layer's: it closes), a click walks along the shortest path (at most 20 single steps, 150 ms apart, any refusal ends the walk). Below the guideline breakpoint (768 px) a pad of four buttons of 44 px appears. Initials on the figures are `aria-hidden`; no name is in a `title`, an `aria-label` or a `data-*` (the only one is `data-cell`); names appear only in the list "In Ihrer Nähe", through the sanitising helper.
* Figures move by the custom properties `--x`/`--y` and a `transform` **on the figure itself** (never on an ancestor: the sticky dock must not get a new containing block); the 100 ms transition exists only under `prefers-reduced-motion: no-preference` and is listed in the single reduced-motion block (rule R54).
* A guest never gets a controller: the room builds the map only when the presence list shows the viewer is no guest, and the server refuses them anyway.
* The room form has the checkbox "Karte (Positionen der Mitglieder)": assembly only, off by default; while the room is open it can be switched off but not on.

=== Threat model

* A member can pass on what they see (a screenshot, or the reaction channel to a guest). That cannot be prevented; the notice says who sees positions.
* A forged packet from a peer is dropped (the client accepts the topic only without a sending participant, strictly parsed).
* Positions are in the memory of the server process: a **heap dump** contains them, and an operator who raises the LiveKit log level may log the **contents** of data packets (the topic is the same for every room). Both are operations checks (Lapis-Cloud-Ops), not something this code can promise away; "not in logs" is true for Lapis itself.
* The map is **per server instance**, like the seat plan: several instances behind a balancer do not work.

* *Layer.* `EncounterMapOverlay` is `role="dialog"` with `aria-modal="true"`, named by its heading "Karte"; it is *hidden* (the `hidden` attribute plus a CSS guard) until it is asked for. The dock button "Karte öffnen" (`aria-haspopup="dialog"`, `aria-controls`, `aria-expanded`) opens it; when the bar is narrow the button moves into the "Mehr" sheet just before the chat and its twin does the same. The focus lands on the board, or on "Auf die Karte" when the viewer is not on the map.
* *Keyboard.* Tab and Shift+Tab wrap inside the panel (a focus trap); the background is deliberately *not* inert, so the dock stays operable. Escape closes the layer wherever the focus is, unless the "Mehr" sheet is open (it closes first). On the map the first Escape inside the board moves to "Karte verlassen" and the layer stays; the next one closes it. The focus returns to the dock button, or to "Mehr" when the button sits in the sheet. Opening the chat, the side panel, the device picker or "Mehr" closes the layer (the panels never stand open together).
* *Closing is never an action on the map.* Escape, the close button and the scrim only hide the layer; nobody leaves the map by closing it. The dot on the dock button (and the name "Karte öffnen, Sie sind auf der Karte") says that the viewer still stands there.

* *Scrolling.* The layer's panel scrolls itself (ledger class E1 of `ScrollSurfaceTripwireTest`); the page behind does not.
* *Known limitations.* Not looked at in a real browser or on a phone, as in wave 1: the geometry is checked in ChromeHeadless only, and the narrow-screen rules of the hall (media queries) are pinned by a stylesheet scan because a test cannot resize the window. The layer ends above the dock by a CSS formula; where the page scrolled so far that the dock rests above the window's bottom edge (page padding under the room), the last pixels of the dock can lie under the layer.
