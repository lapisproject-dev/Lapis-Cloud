= Staging and demo seed coverage (V1.9.296)
:toc:

== Purpose

This page lists every navigation entry of the sidebar (`NavRegistry.entries`) and says what a seeded staging or demo instance shows in it,
and why. Most entries are filled by the staging seed (`StagingSeedData` for the first start, `StagingSeedTopUp` for instances that were seeded
before). Entries that stay empty are listed on purpose: an empty screen on a demo instance is either a gap that this page names, or the
consequence of a rule (no file, no secret, no external effect, no consent of a person).

The *Demo* column says "same seed (not verified on the instance)" for everything that depends only on the seed: the README states that the demo
runs the same seed and is re-seeded every night, but this cannot be checked from the repository. Entries that depend on an operator setting say
so.

A drift guard (`StagingSeedCoverageDocTest`) fails the build when a route of `NavRegistry` is missing from the table.

== Reading the table

[cols="1,3", options="header"]
|===
| Status | Meaning
| filled | The seed writes the data the screen shows.
| partly | Some of the data exists (see the note), or the screen is derived from other seeded data.
| empty | No seed part writes the backing table.
| operator-dependent | The screen needs an operator setting, a file or an external service that a seed must not create.
|===

== Entries that stay empty, and why

* *Documents* (files): a document version needs a stored file; the seed creates the folder structure only.
* *Dunning cases*: a notice needs a generated PDF.
* *Material of activism actions*: material links a document, which needs a file. Activism reports are not seeded either (they are written by members).
* *Encounter spaces, conference rooms, stream targets*: they need the video infrastructure, and stream targets carry secrets.
* *Messages, mailing lists, CRM contacts*: written by people during use; nothing to show on day zero.
* *Donors (external), donations, payment transactions*: only one member with the status DONOR exists; money flows need a payment gateway.
* *Travel expenses and volunteer allowances*: reports and payments carry receipts and declarations.
* *Volunteer shifts, catering, event rooms*: planned per event in the UI.
* *Bank accounts and statement imports*: bank data is never seeded; an import needs an uploaded file.
* *Postal mail*: switched off in the seeded organization settings.
* *API keys*: secrets are never seeded.
* *Moderation reports*: the removed and hidden posts exist, the queue of reports does not.
* *Board terms and transparency register, cost centers*: not seeded (cost centers could be added later; not done in V1.9.296).
* *Member finder*: opt-in by each member; a seed must not consent for a person.
* *AI drafts and the statute Q&A*: need the AI switches and a provider; the drafts come from an AI client.
* *Party report*: visible only for an organization marked as political party.
* *Systemic consensus*: not seeded (polls are).

== Operator settings the seed cannot supply

* `LAPIS_MAP_PMTILES_PATH`: the tile background of the member map (a file on the instance, kept in the operator repository). Without it the map degrades to the list.
* The compliance acknowledgement of the auctions, the payment gateway, mail delivery, the AI assistant, the MCP interface and the stream targets.

== Time drift

A seed uses the day it ran as "today". A running action, an upcoming action or an upcoming birthday on an instance that is not re-seeded expires
by itself; the demo is said to be re-seeded every night, a staging instance is not. The top-up never refreshes or overwrites a value (a postal code
or a birth date that is already set stays as it is).
