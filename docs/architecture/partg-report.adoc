* `partg_report_position`: the 42 statutory positions, seeded by `V121__partg_report.sql` with fixed ids; only `org_hint` changes. 35 `LEAF`, 7 `SUM`. `PartgPositions` (lapis-shared)
  is the same catalogue in code; `PartgPositionsSeedTest` pins database and code against each other.
* `partg_report_sheet`: one header per (fiscal year, `unit_key`); carries the revision (optimistic locking) and is the audit entity. `unit_key` is `FEDERAL`, `STATE:<chapter uuid>` or
  `SUB:<chapter uuid>`; `chk_partg_sheet_unit_consistency` keeps it equal to level and chapter, with the UUID text in lower case on H2 and PostgreSQL (`PartgReportMigrationScenarios`, both lanes).
* `partg_report_value`: cents (`0 .. 99999999999999`), one per sheet and `LEAF` position. A missing row is "not entered". That a value may only point to a `LEAF` position is not
  expressible without a trigger; the service enforces it and `PartyReportSaveScenarios` pins it.
* The column is `value_source`, not `source`: `source` collides with `ColumnSet.source` of Exposed.
* The foreign keys onto the natural key `code` need a UNIQUE *constraint* (H2 does not accept a unique index as a target).
* Deviations from the first design, all technical: an `id` column on positions (the audit log needs a UUID entity id), `sheet_id` in the values instead of year and unit per row, and the
  catalogue has 42 rows (35 + 7), not 43.
* The migration is `V121`. V120 is released and not edited. While the wave is unreleased V121 may be corrected in place on the feature branch; after the release every change is a new migration.

== Access and write path

* `requirePartyReportAccess(call)` is the first statement of every RPC method and every route handler (`PartyReportAccessTripwireTest`): role BOARD/ADMIN, then `isPoliticalParty`.
* `PartgReportStore` is the only reader and writer of the three tables (`PartgReportStoreTripwireTest`; the exception is `PartgReportPersonalData`, which lists who changed what).
* One write path, `PartgSheetWriter`, for the RPC `saveSheet` and the import apply route: one transaction; **lock order** regional chapter row, then the sheet of the older year, then the
  sheet of the younger year (`deleteChapter` locks the chapter row first as well, so neither can deadlock the other); the revisions are compared under the lock; the values are applied; the
  audit entries are written last (one per effective value, plus one collective entry for an import with the SHA-256 and the shortened file name); no external effect in the transaction.
* Creating a sheet that a parallel caller creates too: the insert runs under a savepoint, a unique violation is the only SQL error that is caught (PostgreSQL aborts the whole
  transaction after any other), then the winner's row is locked and its revision decides.
* `deleteChapter` refuses with the typed `RegionalChapterHasPartyReportValuesException` as soon as any sheet (even an empty header) of the chapter exists, before any delete runs.
* Writes are limited to 60 per member and minute. Nothing is logged except counts; no amount, no hint, no file name.
* Backup: all three tables are in the generic backup. The restore treats `partg_report_position` as a *seeded set* (fresh unless an `org_hint` exists) and overwrites the 42 rows by id.
* DSGVO: `PartgReportPersonalData` exports "changed by you" without amounts; erasure retains everything (sections 24 and 19a PartG, ten years).

== R4a: the link to the bookings (V1.9.289)

* **Migration `V144__partg_report_r4.sql`** (V143 is already on `master`): `journal_entry.regional_chapter_id` (nullable FK, no cascade, index on chapter and date), `regional_chapter_treasurer`, `partg_account_mapping`, `partg_report_unit_mode`, value source `LEDGER`, three audit types (the list of V139, verbatim). Additive, repeatable, no backfill. The active-grant CHECK has `active_key IS NOT NULL` on purpose: a CHECK that evaluates to *unknown* passes, so `active_key = ...` alone would admit an active grant without a key (`PartgReportR4MigrationScenarios`).
* **Booking scope** (`security/BookingScope.kt`): `Federal` (the role is in the federal roles of the method, checked first) or `Chapters(ids)` (a MEMBER and organization member with at least one active grant, read fresh inside the caller's transaction, no cache), else `ForbiddenException`. **The default is refusal**: `bookingScope(` is called only in `AccountingService` and only in the methods of an allowlist (`BookingScopeAllowlistScanTest`). Writing with `Chapters` needs a chapter id in the grants and refuses donor fields; reading adds `regional_chapter_id IN ids`; a single entry or draft outside the scope is `NotFoundException` (nothing can be enumerated); a unit filter outside the scope, including "FEDERAL", is `ForbiddenException`. `memberVisibility` and its allowlist are untouched.
* **All access paths to `journal_entry` and `posting`** (grep, as of this wave): `AccountingService` (scoped as above), `CashRegisterGuard` (per account and chapter), `JournalEntryBalance`, `DonationIncomeAmount`, `FinancialStatementCalculator`, the six `*PostingBridge`s (insert on the federal level; `JournalEntryInsertSitesTest` pins every insert site), `TravelExpenseSepaExport`, `ContributionService`, `MemberFinancialHistoryService`, `accounting/export/JournalExportSource`, `routes/MailmergeRoutes`, `routes/PublicTransparencyReader`, `dsgvo/AccountingPersonalData`, `partg/PartgLedgerReader` (new), `RegionalChapterService` (a delete guard). Indirect: `DatevRoutes` via `previewDatevExport`, `BankStatementImportService` via the contribution bridge, the generic backup. Neither `mcp/` nor the public API reads the booking tables. Everything except the scoped methods is federal and consolidates over all units.
* **Audit payload:** `JournalEntrySnapshot.regionalChapterId` has a default and the audit JSON encoder keeps `encodeDefaults = false`, so the payload (and the hash chain input) of a federal entry is byte-identical to before (`ChapterTreasurerScopeScenarios`).
* **`PartgLedgerLinkStore`** is the only reader and writer of the mapping and mode tables (`PartgLedgerLinkStoreTripwireTest`; exception `PartgReportPersonalData`). **`PartgLedgerReader`** is the only code of the party report that reads the booking tables and the ledger accounts; the package `partg/report` touches no table. Sums are one `GROUP BY` query per call, converted with `longValueExact()` and capped at 99,999,999,999,999 cents (a larger sum is a clean error, never a silent cap).
* **Scoped gate** `requirePartyReportScopedAccess(call)`: role (BOARD/ADMIN) -> `Federal`; else the fresh grant -> `ChapterTreasurer(chapterIds)`; else forbidden; then the party switch. It is used by exactly eight methods (`PartyReportAccessTripwireTest`): `listUnits`, `overview`, `getSheet`, `saveSheet`, `reportFindings`, `getAccountMappings`, `proposeFromLedger`, `applyLedgerProposal`. All others keep `requirePartyReportAccess`. For a chapter treasurer a foreign unit is `NotFound` on reading and `Forbidden` on writing; `overview` and `listUnits` are filtered; `reportFindings` drops the hints of the whole organisation.
* **Proposal path:** `PartgLedgerProposals.proposalFor` (stores) -> `PartgLedgerProposal.compute` (pure). `applyLedgerProposal` runs `PartgSheetWriter.writeLedgerProposal`: lock order unchanged (chapter row, prior sheet, sheet), revisions compared, mode checked, the proposal **recomputed under the lock**, every pick compared exactly, `applyChanges(source = LEDGER)` bumps the revision in the same commit, audit last (one entry per value plus a collective snapshot with count and codes).
* **Mode change** (`setUnitMode`): lock of the chapter row (or the settings row for the federal unit), the count of posted entries read under it, upsert under a savepoint, audit.
* **Deleting a chapter** is refused with a clean exception when a booking, a mode row or an active treasurer grant refers to it; revoked grants go with the chapter (their history stays in the audit log).
* **Session:** `SessionInfoDto.chapterTreasurerScopes` (empty for BOARD/TREASURER/ADMIN); the client uses it only to show or hide doors, the server enforces everything.

== R5: consolidation over the units (V1.9.290)

*Tables and monopoly*:: `partg_consolidation_sheet` (header per year: lock and revision), `partg_intra_transfer`, `partg_donor_combination`, `partg_donor_combination_row` (migration V145; no cascade, no `organization_id` -- the installation is single-tenant like every `partg_*` table). `PartgConsolidationStore` is the only reader and writer (exception: `PartgReportPersonalData`); users: `PartgConsolidationWriter`, `PartgReportSnapshotReader`, `PartyReportService`, `RegionalChapterService` (delete guard), `PartgAnnexWriter` (**only** `detachDonor`) and the pure consumers of its value classes (`PartgConsolidationStoreTripwireTest`).
*One write path*:: `PartgConsolidationWriter`: (1) lock the header of the year, (2) compare `expectedRevision` under the lock, (3) validate, (4) write, (5) bump the revision **in the same commit**, (6) audit last. **Lock order:** consolidation header, then the chapter rows of a pair (sorted by unit key) or the annex headers of a combination (sorted by unit key). The annex writer never takes the consolidation header; it locks chapter and annex header and, when a donor row is deleted, calls `detachDonor` under its own lock (there is no cascade). So there is no cycle: the combination writer inserts rows only after it holds all annex locks. The caps (1000 pairs, 500 groups) are checked under the header lock.
*Fence*:: `PartgReportSnapshotReader` also reads the consolidation tables and compares `CONS:<year>` revisions; `readWithin` is the same fence inside a writer's transaction (the writer returns exactly the state it wrote).
*Computation*:: `partg/report/PartgConsolidation` (pure, no table, no clock): included and excluded units, leaf cells (value or n. b.), elimination per pair (minimum, both units included, both amounts stated), sums only through `PartgPositions.sums` and `PartgReportComputation.inputsOf`, **never capped** (an elimination above the sum is n. b.). `PartgDonorConsolidation`: groups, display row, candidates (NFKD normalisation exists only on the JVM, so it is computed on the server; sorting is done in Kotlin because the collation of H2 and PostgreSQL differs). `PartgConsolidationView` turns one snapshot into the screen model. The rules of both sides are `PartgConsolidationRules` (shared).
*Access*:: the five RPC methods start with `requirePartyReportAccess(call)` (BOARD, ADMIN, then the party switch), **not** the scoped gate (`PartyReportAccessTripwireTest` still pins exactly eight scoped methods). `reportFindings` is scoped, so the hints P17 to P21 are computed **only** for `PartyReportActor.Federal`; the chapter-treasurer branch passes `consolidation = null`.
*Export*:: `PartgReportDocument.consolidated` was renamed `unitSum`; the new `consolidation` section is only set for the scope ALL. The PDF section is appended last; the XLSX sheet names are a function of the scope (`sheetNames(withConsolidation)`), content types, workbook and relations are generated from it.
*Migration*:: V145 may be corrected in place on the feature branch until the release; after it every correction is a new migration.

== R6: kept versions, assurance, internal final mark, deadline (V1.9.291)

*Storage decision*:: a version stores the **computed document** (`PartgReportDocument`, the one thing the PDF and the XLSX render) as canonical JSON, not a recipe for a recomputation. A recomputation would depend on positions, mappings, consolidation rules, unit names, hint rules and the bookings (`takeOverPending`); every later change would silently change an old version. The document also holds only what is exported (statement B: name, address line, country, kind, amount -- no ids, no `created_by`, no free-text note). Honest limit: the **numbers** are unchangeable, the **rendering** by a later renderer is not.
*Format*:: `PartgVersionFormat`: one `Json` instance (`encodeDefaults = true`, `explicitNulls = true`, no pretty printing), the hash is SHA-256 over the UTF-8 bytes of exactly the stored text (a new `MessageDigest` per call), the budget is 4 MiB (also a CHECK). `format_version` starts at 1. **Rule:** fields are added to the document only with a default; renaming, removing or changing the meaning needs a new `CURRENT` and a decoder for the old format that stays. `PartgVersionFormatGoldenTest` pins the bytes of a fixed document (`src/test/resources/partg/version-format-1.json`) and fails on purpose with "bump PartgVersionFormat.CURRENT"; `PARTG_GOLDEN_WRITE=1` rewrites the file after the bump. A version of another format shows `UNKNOWN_FORMAT` in the status line, never "deviates". `UnitPage` carries a stable `unitKey` so that the comparison survives a rename.
*Tables and monopoly*:: V146: `partg_report_version_counter`, `partg_report_version`, `partg_report_declaration`, `partg_report_deadline` (V145 is on `master` and untouched; V146 may be corrected on the branch until the release). `PartgVersionStore` is the only reader and writer (exception `PartgReportPersonalData`; `PartgVersionStoreTripwireTest`). It has **no function that changes content, checksum, number, year, scope or the keeping stamp**: the only UPDATE of a version is `markFinal` (`WHERE finalized_at IS NULL`), and a version is removed only by `deleteVersions`. The counter row is never deleted, so numbers are never reused.
*Write path*:: `PartgVersionWriter` (one transaction per call, audit last, no external effect). Keeping: the document is built **outside** the write transaction through the revision fence of `PartgReportSnapshotReader`; inside, the counter row is locked (created under a savepoint, only the unique violation is swallowed), the cap of 200 and "same hash as the newest" are checked under the lock, then the number is `last_number + 1`. Declaring and finalising lock the counter row, then the version row, and re-hash the stored text before they write. **Lock order:** counter rows sorted by (year, scope key), then the version row. The writer takes no sheet, annex, notes or consolidation lock, so there is no cycle with the writers of R1 to R5. The deletion routine locks all counter rows in that order and recomputes the candidates under the locks.

*Access*:: eight new RPC methods at the end of `IPartyReportService`; each starts with `requirePartyReportAccess(call)` (BOARD, ADMIN, then the party switch), **not** the scoped gate (`PartyReportAccessTripwireTest` pins 38 methods and exactly eight scoped ones). The two deletion methods add `requireRole(ADMIN)`. The work sits in `PartgVersionOperations`; the shared limiters come from `Application.module` (keeping 10 per member and minute under `partg:version:<id>`, reading and comparing 60, the other writes the existing write limiter, and the shared export semaphore).
*Downloads*:: `GET /api/partg-report/version/pdf|xlsx?id=`: gate first, rate limit, strict UUID, permit, one read transaction, **integrity check** (the stored text is hashed again; a mismatch is `409 INTEGRITY` with only the version id in the log), decode, render on `Dispatchers.Default`, audit before sending, fixed file name. `PartgReportDocuments.build` is the single assembly of the document, shared with the working-state export (a pure refactor; the audit bytes of an export without a version are unchanged because the new snapshot fields default to `null`).
*Footer*:: `PartgReportPdfRenderer.render(document, footer)` writes the line at y = 12 on every page (below the legend and the page number at y = 22); `PartgReportXlsxWriter.write(document, footer)` writes it in row 2 of every sheet as an `inlineStr` and in `<headerFooter><oddFooter>` with `&` doubled (it is a control character in an Excel footer).
*Dashboard*:: `PartyReportSignals` (last in `DashboardSources.all`): BOARD/ADMIN of a party only; `params` carry only digits and ISO dates (the collector drops anything else), so the status travels as `statusCode` 0..3. The dashboard is cached with a TTL: the card can be a little stale (documented limit).
*Deletion*:: `PartgVersionRetention.eligible` needs `today.year > fiscalYear + N` **and** `today.year > frozenAtYear + N` (N from 10 to 30); the declarations are removed first (no cascade).
*Client*:: tab `FREIGABE` appended to `PartyReportTab` and `PARTG_TAB_DISPLAY_ORDER` (the remembered tab is read by name; the chapter treasurer's list is unchanged), `PartyReportStatusLine` (on every tab, refreshed on year, tab and `PartyReportContext.onSaved`), `PartyReportVersionsTab`, `PartyReportVersionDialogs`, `PartyReportVersionCompare`, `PartyReportVersionLogic`.

== The XLSX reader (no spreadsheet library)

No Apache POI: a general spreadsheet library is a large attack surface for a file that is only ever read as a fixed template. The reader is small and strict.

[cols="2,3",options="header"]
|===
|Limit |Value
|Upload |2 MB, counted while streaming
|ZIP entries / entry / total / ratio |64 / 8 MB / 20 MB / 100
|Names |printable ASCII, `/` separated; no `..`, no leading `/`, no backslash, no duplicate, no encrypted entry, no symlink
|Macros |any `xl/vbaProject.bin` or a `macroEnabled`/`vbaProject` content type is refused
|XML |StAX, DTD off, no external entities, a DTD or entity event rejects the file; at most 200,000 elements per file
|Cells |only columns A to E, rows up to 500 (content below is an error), text up to 200 characters, at most 5,000 shared strings
|First sheet |found through `workbook.xml` and its relationships; the target must be `xl/worksheets/sheet<1-3 digits>.xml`
|Numbers |`BigDecimal`, rounded to two places when the deviation is below 1e-6 (Excel stores IEEE doubles), else `TOO_MANY_DECIMALS`
|Dates |detected through the number format of the cell style and refused
|Errors |at most 50, then one marker
|===

The ZIP container reader (`OoxmlZipReader`) is **derived from the article import's `ArticleImportZipReader`**. The plan preferred extracting one shared reader; the article reader is fused with
its slug classification and its localized reasons, so the parser core was copied and adapted instead. **The security logic therefore exists twice**; a fix to the central-directory
parsing, the local-header cross check, the overlap check or the bounded inflater has to be applied to both files.

The template writer produces a deterministic file (fixed ZIP time). Organisation and unit names are written as `inlineStr`, never as `<f>`; invalid XML characters are removed.

== The preview store

`PartgImportPreviewStore` keeps the parsed changes between "Prüfen" and "Übernehmen" in memory only: one entry per member, 64 in total (the oldest falls out), 15 minutes on the monotonic clock,
a token of 32 random bytes of which only the SHA-256 is kept and compared in constant time, single use whatever the outcome (a foreign member's guess burns the token). A restart drops
all previews. Apply checks the revisions twice: against the preview and again under the lock.

== Report model (R2)

`PartgReportComputation` (shared, commonMain) is the computing core for client and server. A cell is `Value`, `Partial(cents, missing)` or `NotEntered`, and `NotEntered` is never 0. `PartgPositions.sums`
stays the ONE formula of the seven sums; `inputsOf(sum)` only states which LEAF positions a sum depends on (derived from the catalogue), and `PartgInputsOfParityTest` proves that both agree (raise each leaf
by one, the sum changes exactly when the leaf is in `inputsOf`). `aggregate` adds the entered leaves of several units; a leaf is complete only when every unit entered it. Shares are tenths of a percent by
integer long division, rounded half up (away from zero on a tie), with no Double and no BigDecimal in commonMain. `MAX_UNITS = 201` (federal level plus 100 chapters with two units each) keeps every
sum below 201 x 35 x 99,999,999,999,999 cents inside the Long range, and the percentage division multiplies only the remainder by ten.

`PartgReportStore.enteredSnapshot` reads sheet LEFT JOIN value with ONE statement for all requested years, so the picture is consistent under READ COMMITTED (a loop of `values(sheetId)` would be N+1 and
not consistent). The overview, the checklist (`PartgCompletenessCalculator`) and the export all use it.

== PDF renderer (R2)

`PartgReportPdfRenderer` is its own table builder on PDFBox (A4 landscape, Helvetica, WinAnsi): `LetterPdfBuilder` is portrait. The text clean-up of the Standard-14 fonts lives in `PdfFontText`
(shared with `LetterPdfBuilder`): unencodable characters become `?`, control characters become spaces. Two passes: the content first; then on every page the watermark with `PREPEND` (behind the content,
saved and restored graphics state, `ExtGState` alpha 0.12, `resetContext` so nothing leaks into the content), and the header, legend and "Seite x von y" with `APPEND`. Amount cells are never truncated: each
cell is fitted to its column (8, 7, 6 pt, then smaller); the income matrix uses compact cells (`*` for partial) and splits into two column blocks when the largest amount would not fit 12 columns. A page
break falls only between rows and repeats the header. Limits: pages (`PdfLimitExceeded`), bytes after `save`, and a deadline checked per row. Determinism: no creation date, fixed producer, and an explicit
trailer `/ID` from the SHA-256 of the document (PDFBox otherwise writes a time-dependent ID).

== XLSX export (R2)

`PartgReportXlsxWriter` writes by hand (only `PartgXlsxWriter.escape` is reused; `PartgXlsxWriter` itself is untouched). Every string is `inlineStr`; there is no `<f>` anywhere, no shared strings and no
macro part. The style indices are constants: 2 euro (`numFmtId` 164, with a negative section), 3 percent (165, `0.0%`), 4 quote prefix. A string starting with `= + - @` gets the quote-prefix style;
tab, CR and LF become spaces; invalid XML characters are dropped. Fixed ZIP time and part order, so equal documents give equal bytes.

== Export routes (R2)

`PartgReportExportRoutes.kt` (`GET /api/partg-report/export/pdf|xlsx?year=&scope=`). Order: access gate (the first statement of each handler, pinned by `PartyReportAccessTripwireTest`), rate limit
(10 per member and minute), strict input check (`year`, `scope` = `ALL` or a unit key of at most 48 characters), concurrency permit (`Semaphore(2)`, released in `finally`), ONE read transaction (organisation
name, units, `enteredValues`), assemble and render outside the transaction on `Dispatchers.Default`, audit in its own transaction BEFORE anything is sent (if the audit fails, no file is delivered), response with
a fixed file name, `Cache-Control: no-store` and `nosniff`. The refusal body is the existing `PartgImportRejectionDto`. Only format, year, scope key and counters are logged.

== Migration V136

Only the CHECK of `audit_log_entry.entity_type` is widened by `PARTG_REPORT_EXPORT` (the list is V133's, copied verbatim, plus one). `AuditAction` has no export action, so the entry is a `CREATE` of that
entity type; the format is in the snapshot. `PartgReportSheet` is not reused because it means "one entry per value" and the whole party has no sheet id.

== Client

Route `Routes.PARTY_REPORT`, guarded by `NavVisibility.showsPartyReport(session)` (`SessionInfoDto.politicalParty`, appended at the end with a default). `PartgSheetDraft` holds the
typed-in state without the DOM (blank means not entered, 0 is a value); the live sums use the shared `PartgPositions.sums`, so client and server cannot compute differently. Labels
come from `partgLabel`, one literal `tr(...)` per code. The fourth tab (`PartyReportExport.kt`) loads `reportCompleteness` and the unit list, filters the checklist with the pure `completenessLines`, and starts a download with a temporary anchor (the codebase convention; an error response would be saved as a JSON file, which is why the checklist loads over RPC first). The browser's own question appears when the tab is closed with unsaved values; a change of year, unit or tab asks first.

* `V139__partg_report_r3.sql` (V121 and V136 are released and untouched). `partg_report_annex` is one header per (year, unit) with the revision and the four deduction fields and the member count (NULL = not entered). `partg_report_large_donor` holds statement B;
  `chk_partg_donor_amount` keeps the data minimisation in the database (`amount_cents > 1000000`). The notes are `partg_report_notes_sheet` (per year), five `partg_report_note` rows and up to 50 `partg_report_holding` rows. The audit CHECK list is V136's, copied
  verbatim, plus `PARTG_REPORT_ANNEX` and `PARTG_REPORT_NOTES`. The row limits (500, 50) are not expressible without a trigger: the service checks them under the lock of the header row.
* **Store monopol:** `PartgAnnexStore` is the only reader/writer of the five tables (`PartgAnnexStoreTripwireTest`; the exception is `PartgReportPersonalData`). The one write path is `PartgAnnexWriter`: one transaction, lock order regional chapter row, then the header row,
  revision compared under the lock, child rows written, revision bumped, audit last; the audit snapshot holds counters, ids and codes only. `PartgReportPrivacyTripwireTest` pins that no log line or exception message in the package carries a name, street, city, postal code or text.
* **Sorting** of the donor list is done in Kotlin (amount descending, name, id), not by SQL `ORDER BY name`: the collation differs between H2 and PostgreSQL and the export bytes would differ.
* **Revision fence** (`PartgReportSnapshotReader`): the data lives in several tables with child lists, so one statement cannot read it (R2 could, with the sheet-value join). Reads under READ COMMITTED could see a half-applied write. Every writer bumps the revision of its
  header in the **same commit** as the child rows, and a revision only ever grows, so equal revisions before and after the reads prove that nothing was committed in between (no ABA). A difference repeats the whole read, at most three times, then `PartyReportRevisionConflictException`
  (export: `REVISION_CONFLICT`, 409). `betweenReadsHook` is the test seam (`PartgReportSnapshotReaderTest`).
* **Plausibility** (`PartgPlausibility`) is pure: no database, no clock. The member count suggestion (`PartgMemberCountSuggestion`) is a `COUNT` over `member` (`ORGANIZATION_MEMBER`, not anonymised; state units add the chapter).
* **Document and renderers:** `PartgReportDocument` gets `annex`, `notes` and `findings` (default empty, so R2 tests are unchanged). The PDF adds the pages A, B, member count and notes after the assets; the XLSX adds four sheets before `Hinweise` and lists the hints there
  (codes, unit, row numbers, position number; no name). Strings are `inlineStr` with the quote prefix; the PDF text clean-up replaces characters outside WinAnsi.
* **Findings rate limit:** `reportFindings` has its own limiter (30 per member and minute, key `partg:findings:<id>`), not the export's.
* **Client:** `PartyReportTab` got `AUSWEISE` and `ERLAEUTERUNGEN` appended (the remembered tab is read by name); the display order is `PARTG_TAB_DISPLAY_ORDER`. Below 640 px a select with the label "Bereich" replaces the buttons (CSS shows exactly one of the two).
  The input rules are `PartgAnnexRules` in lapis-shared, called by client and server (`PartgAnnexRulesTest`).

== Statements C and F (R3b, V1.9.283)

* `V142__partg_report_r3b.sql` (V139 is on master and untouched): `partg_report_sponsor`, `partg_report_sponsoring_entry` (no `annex_id`: the sponsor carries the assignment), `partg_report_youth_org`. No amount CHECK for the limits (computed), no `ON DELETE CASCADE`.
* **Store monopol:** `PartgStatementStore` is the only reader/writer of the three tables (`PartgAnnexStoreTripwireTest`; exception `PartgReportPersonalData`). It is used only by `PartgAnnexStore` (snapshot), `PartgAnnexWriter`, `PartyReportService`, `PartgReportAssembler` and `PartgPlausibility`.
* **Write path:** `PartgAnnexWriter.saveSponsor/deleteSponsor/saveYouthOrg/deleteYouthOrg`: lock order regional chapter row, then the annex header; revision compared under the lock; caps (500 sponsors, 2000 entries per annex, 20 youth organisations) checked under the same lock; entries replaced by id (ids kept, unknown ids are `NotFound`); revision bumped in the same transaction; audit last (`PARTG_REPORT_ANNEX`, counters and ids only).
* **Rules:** `PartgStatementRules` (lapis-shared) computes the qualification (strictly above 75,000 cents single, strictly above 600,000 cents yearly, `Long` only, bounded by the caps).

* **Client:** `PartyReportAnnexNav` (jump bar, disclosure blocks, `AnnexEditorGuard` = one open form for the whole tab), `PartyReportSponsoringBlock`, `PartyReportYouthBlock`.

== R5b: the proposal for statement B from the bookings (V1.9.293)

*Migration*:: `V147__partg_report_r5b.sql` (V146 is on `master` and untouched): two nullable columns on `partg_report_large_donor` (`source_donor_key` VARCHAR(80), `source_applied_at` TIMESTAMP), two CHECKs (`chk_partg_donor_source_key`: `M:`/`X:` plus a 36 character UUID; `chk_partg_donor_source_applied`: a take-over time needs a key), one **normal** unique index `(annex_id, source_donor_key)` (several NULL keys stay allowed on H2 and PostgreSQL, so the house rule against partial indexes holds) and the audit CHECK with `PARTG_LARGE_DONOR_PROPOSAL`. No new table, no backfill.
*Readers and writers*:: `PartgLedgerReader.federalDonationTotals` is still the only reader of the booking tables (cap 200,000 entries, `TOO_MANY_BOOKINGS`); `PartgDonorMasterData` is the only reader of `external_donor` in the package `partg` and reads the member master data for the proposal; `PartgDonorProposals` is pure (no table). The only writer is `PartgAnnexWriter.applyDonorProposal` through three functions of `PartgAnnexStore` (`insertDonorFromLedger`, `replaceDonorAmountFromLedger`, `linkDonor`); the existing `updateDonor` never writes the two new columns, so a hand change keeps the key and the take-over time and turns the origin into "changed afterwards" (`updated_at` > `source_applied_at`). `PartgDonorProposalTripwireTest` pins the monopolies and that no key, name or amount reaches a log line or an exception text.
*Checksum*:: SHA-256 (a new `MessageDigest` per call) over a canonical, length-prefixed text: year, annex revision, the two counters, every entered row of the federal annex (sorted by id) and every row of the proposal (sorted by key). It travels to the client and back and is never stored or audited.
*Lock order*:: federal annex row (`lockOrCreateAnnex`; the federal level has no chapter row to lock), then the mode is read again (a state change of the mode is not blocked by this lock, like in R4a), then the proposal is recomputed, the picks are validated, the rows are written, the revision is bumped once, the audit entry is written last. Two parallel take-overs with the same checksum: one wins, the other is stale; `PartgAnnexWriter.afterLockHook` is the test seam.
*Gate*:: `largeDonorProposal` and `applyLargeDonorProposal` (methods 40 and 41) start with `requirePartyReportAccess(call)` -- the federal gate. A chapter treasurer reaches neither (`PartyReportAccessTripwireTest`: 41 methods, nine scoped).
*Kept versions*:: `PartgReportDocument` and `PartgReportSnapshotReader` are unchanged: the origin is not part of the stored document, so no hash of a kept version and no byte of a PDF or XLSX changes.

== Statement D (R3c, V1.9.287)

* `V143__partg_report_r3c.sql` (V142 shipped with 0.46.0 and is untouched; while V143 is unreleased it may be corrected in place on the branch, afterwards only by a new migration): one table `partg_report_enterprise` on the annex (`annex_id`), no link to `partg_report_holding`, no `ON DELETE CASCADE` (annex rows are never deleted; a chapter with an annex cannot be deleted). CHECKs for the text lengths, the share (0..10000) and the amounts (0..99999999999999 or NULL).
* **Store monopol:** `PartgStatementStore` also owns `partg_report_enterprise` (`PartgAnnexStoreTripwireTest`, exception `PartgReportPersonalData`). Sorting in Kotlin (created at, id), never in SQL.
* **Write path:** `PartgAnnexWriter.saveEnterprise/deleteEnterprise`, an exact copy of the youth organisation path: chapter lock, annex lock, revision compare, the cap of 50 under the lock, `NotFound` for an id of another annex, revision bump in the same commit (so the snapshot reader's revision fence covers D without a change), audit last with ids and counters only.
* **One rule:** `PartgEnterpriseRules` (lapis-shared) holds validation, the computed result, the complete sum and the adjustment status (`check`); the screen, the server hints P11 to P13 and the DTO use the same function. Integer arithmetic only (50 * 99,999,999,999,999 fits a `Long`); a difference counts only when strictly greater than 100 cents.
* **Adjustment against R1:** `PartyReportService.annexDto` reads `E05` and `A02F` of the sheet (read only) and returns `enterpriseChecks` with a status per position, never an amount. The PDF and the XLSX read no R1 value in D.
* **Document:** `AnnexSection` gets `enterprises` and `enterpriseTotals` (one per unit that has a row, no whole-party sum). The XLSX has 13 sheets (`Ausweis D` after `Ausweis C`, so the sheet index of the following sheets moved by one); the completeness sheet only counts the enterprises.
* **Client:** `PartyReportEnterpriseBlock` in the `Ausweise` tab (block D, same one-form guard as C and F).
