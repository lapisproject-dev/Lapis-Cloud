= The conference dock: a running conference survives navigation (V1.9.70, floating window V1.9.71)
:toc:

== Purpose and promise

A person in a video conference clicks "Mitglieder", "Anträge" or any other page. Until V1.9.69 that ended the call: the route outlet was
cleared, the screen's destroy hook disconnected the LiveKit session, and the camera and microphone stopped.

Since V1.9.70 the call **keeps running** when the route changes:

* microphone, camera, remote audio, chat, roster, running votes and a secret-ballot receipt all stay alive;
* while the call view is not on screen, a **mini bar** at the bottom of the page (V1.9.70) or, from 768 px and since V1.9.71 by default,
  a **floating window** (see <<presentation>>) stands for it (status, recording / live stream badges, microphone, camera, "Verlassen",
  and a way back);
* there is exactly **one** conference per browser tab.

V1.9.70 was step 1 of two. Step 2 (V1.9.71) adds the free-floating conference window described in
<<presentation>> and the sections after it. Neither step adds Document Picture-in-Picture or the encounter room as a second dock
session.

== Decision: the view stays, it is only hidden

The call screen (`enterCall` in `ConferenceScreen.kt`) is one closure of roughly 3,700 lines in which the session and the view are woven
together: LiveKit callbacks, raw-DOM video tiles, chat, votes, whiteboard, notes, background effects, moderation. Splitting that into a
model and a view would be the largest regression risk of the whole client.

So the KVision subtree of the call view (`ConferenceDock.callPanel`) lives in a **permanent dock host** next to the route outlet:

.Shell structure (`App.kt`)
----
.lapis-content (role=main, id=lapis-content)
 |- route outlet   (cleared on every route change by Routing.show)
 `- dock host      (never cleared; carries the call view; hidden by the class d-none, NEVER by hide())
conference dock bar (position: fixed; sibling after the landmark, before the version banner)
document.body > div#lapis-conference-audio (hidden; created once; outside the KVision root)
----

"Docking" means showing the host and moving the focus; "undocking" means hiding it with CSS. Nothing is torn down, so:

* nothing a person has typed or received in the call is lost (chat log, roster, vote panel and receipt just keep running);
* the background-effect processor is never released by an undock (it only ends with the call);
* a media element is never removed from the document while the call runs.

[IMPORTANT]
====
The host and the bar are hidden with the Bootstrap class `d-none`, never with KVision's `hide()`. KVision does not render a hidden
widget at all: it would drop the call view out of the document (its raw-DOM tiles, its videos) and, for a widget that *starts* hidden,
never run its insert hook. The bar's first paint additionally runs one tick after its insert hook: changing the bar's own classes
inside its insert hook re-patches the vnode that is still being inserted and fires the hook again (endless recursion, found by the
Karma test of the bar).
====

Remote audio is the one exception to "the tile holds its media": the HTML specification pauses a media element that leaves the
document. Remote `<audio>` elements therefore live in `#lapis-conference-audio`, a permanent container in `document.body`.

[#presentation]
== Presentation: bar, floating window, full view (V1.9.71)

`DockState` (see <<state-machine>> below) says *whether* a conference runs. A second, **derived** axis says *how it is shown*: `DockPresentation` is computed by
the pure function `dockPresentationOf(state, wish, wide)` and never stored.

[source,kuml,name="conference-dock-presentation"]
----
stateDiagram(name = "Conference dock presentation") {
    val bar = state(name = "BAR (mini bar)")
    val float = state(name = "FLOAT (window)")
    val full = state(name = "FULL (call view in the route)")

    transition(source = bar, target = float) {
        trigger = "Als Fenster zeigen (wide viewport, Live or Resolving)"
    }
    transition(source = float, target = bar) {
        trigger = "Einklappen, viewport below 768 px, Joining, Stopped"
    }
    transition(source = bar, target = full) { trigger = "route opened (ViewAttached)" }
    transition(source = float, target = full) { trigger = "route opened (ViewAttached)" }
    transition(source = full, target = float) { trigger = "route left, wish is FLOAT, wide" }
    transition(source = full, target = bar) { trigger = "route left, wish is BAR or narrow" }
}
----

* The view in the route always wins (`FULL`). Floating needs a **live** call (`Live` or `Resolving`, not `Joining`, not an end state), the
  stored wish and a viewport of at least 768 px (`matchMedia`); everything else is the mini bar. A phone never gets the window.
* The wish (window or bar) and the window's anchor (corner, two distances, width) are stored in one short string,
  `lapis.conferenceFloat.v1` (`v1|float|0|16|16|352`). A whitelist parser rejects everything else and deletes the key; storage that is
  missing or throws is ignored. The value holds no room, person or identifier, so it is deliberately **not** cleared on sign-out or an
  account switch (it is a per-device display preference). **From 768 px the window is the default**; after that the person's last choice
  counts. This changes the V1.9.70 behaviour (the bar) on wide screens.
* The window is anchored to the nearest corner (`FloatGeometry`: corner, `dx`, `dy`, width) instead of absolute pixels, so a shrinking
  viewport never leaves it off screen: the rectangle is recomputed and clamped on every paint (margin 16 px plus the safe-area insets,
  width 256..640 px and never so wide that the height no longer fits).
* The window is built by `conferenceFloatWindow()` and mounted by `App.kt` as a sibling of the bar (never inside the dock host, which is
  `d-none` while the view is away). It is shown and hidden by the class `d-none`, never by `hide()`. The controller
  (`ConferenceFloatController`) observes the dock, the viewport and the storage and is the only place that decides the presentation.
* The window offers: header with status and consent badges, corner / size / collapse / back-to-view buttons, a 16:9 big picture, a strip of
  up to three more pictures (from 320 px width; the own picture takes one place and only exists with the camera on), a "+N" counter for
  the rest, and the same microphone / camera / stop-sharing / leave controls as the bar (`conferenceDockBarControls`, same handlers, same
  receipt gate through `conferenceDockLeaveRequested()`). Small (256 px) has no strip; the own picture is a 64 x 36 inset.
* Which picture is big: a foreign screen share; else the person who is speaking (a new speaker takes over only after 2 s of uninterrupted
  leading, so an interjection does not flip the picture); else the first remote person; alone, the own picture. Names are shown from the
  finished tile text the call view hands over (`FloatMediaSource.label`, always via `textContent`); the bar stays free of names.

[#video-ledger]
== Video ledger: borrow, never re-attach

One track is one `<video>`. The window never creates a video element and never attaches a track a second time: it **lends** the element
the call view already owns (`ConferenceVideoLedger.borrow`) and hands it back (`returnHome`). Only `setTileVideo` and
`showScreenShareStage` create elements, through `track.attach()`. A video moves with a single `appendChild` of a connected node, never
`remove()` followed by a later insert (a media element outside the document for longer than one task is paused by the browser, see
V1.4.19).

Rules that keep this true:

* `setTileVideo`, `removeTile` and the screen-share stage call `videoLedger.reclaimSlot(slot)` **before** they `clearElement(slot)`, so a
  picture that is on loan is back where the call view expects it (otherwise switching the own camera off would leave the old picture in
  the window).
* `ConferenceDock.terminate` calls `videoLedger.returnAll()` **before** `current?.terminate(...)`; `clearRun()` and the test reset do the
  same; when the dock turns idle the controller additionally stops and drops every `<video>` still in its stage (last guard: no live
  stream stays behind after leave, sign-out, account switch, language change, a root restart or a narrow viewport).
* FLOAT to FULL: the observer runs synchronously inside `dispatch(ViewAttached)`: `returnAll()`, window hidden, quality high; then
  `session.attach()` resumes the videos. FLOAT to BAR: `returnAll()`, window hidden, the bar paints and (after "Einklappen") the focus
  goes to "Als Fenster zeigen". To FLOAT: window shown, then the pictures are lent, then `resumeStalledVideosIn(stage)`.
* The call view's watchdog only looks under its own panel and never finds a video on loan, so `resumeStalledVideos` is the top-level
  `resumeStalledVideosIn(scope)` and the controller runs it on its stage after every move and every two seconds.
* `track.detach()` removes elements wherever they hang, so a track that goes away is cleaned up regardless of a loan; `prune()` then
  forgets the stale loan.
* Switching the presentation never calls `beginJoin`, `register`, `connect` or `attach()`: one connection, one session.

== Keyboard model and WCAG 2.5.7 / 2.4.11

* **Alt+Shift+K** (global, only while the bar or the window is visible) moves the focus to the window, or to the bar's first control when
  it is folded; it does nothing without a running call. The window is a `role="region"` with `tabindex="0"` and an
  `aria-description` naming the keys.
* With the window itself focused: arrow keys move it by 16 px, Shift+arrow keys resize it by 32 px (right/up wider, left/down narrower),
  Home returns to the default corner. These are the single-pointer / keyboard alternatives to dragging the header and the resize grip
  (2.5.7). The corner and size buttons do the same by click. The preference is stored on key-up, on release and on a button, never on
  every `pointermove`.
* Escape anywhere in the window gives the focus back to the element that had it on the page (else `#lapis-content`); the mode stays.
* **The window never dodges the focus.** If a focused page element is more than half covered (`coversFocus`), the window gets a
  2 px focus-token ring (`is-covering-focus`) and the person hears the key hint once per page load. A window that jumps away under the
  keyboard would be worse than one that can be moved on purpose.
* Dragging is by the header only (not from its buttons), with pointer capture, a 4 px threshold, edge snapping (24 px) and a reset on
  `pointercancel`. Touch targets are 32 px (44 px under `pointer: coarse`).

== Stacking order

[cols="2,1"]
|===
|Layer |z-index

|App chrome (sidebar, banners), call control bar |<= 6
|Conference dock bar |5
|**Conference floating window** (`--lapis-z-conference-float`) |**1034**
|"New version" pill |1035
|Offcanvas backdrop / offcanvas |1040 / 1045
|Modal, `.lapis-encounter-side.is-sheet` |1055
|Popovers, tooltips |1060
|Toast, skip link |2000
|===

The window lies above the page and below every dialog (a dialog must cover it) and below the update pill. It is non-modal: no backdrop,
the page stays operable. It is `position: fixed` with no `transform`, `filter` or `overflow` (rounded corners come from `border-radius`
on the pictures, so it adds neither a clip to the ledger of `ScrollSurfaceTripwireTest` nor a scroll surface).

== The announcer

The two live regions (polite, alert) used to sit inside the bar. The bar is `display: none` while the window floats, and a region in
`display: none` is not read out, so they moved into `conferenceDockAnnouncer()`: a never-hidden sibling of the bar and the window, fed
once per dock transition in **both** presentations. A change of recording or live stream is therefore announced while the window floats
too (consent). The first-detach note reads "Konferenz als schwebendes Fenster" when the window stands for the call; a later switch between
window and bar announces "Konferenz als schwebendes Fenster" or "Konferenz eingeklappt" (polite).

== Load: `setVideoQuality`, never `setSubscribed`

While floating, only the big picture needs medium quality; the strip and the folded pictures need low, the full view high, and the bar low
(nothing is visible). `requestRemoteVideoQuality` calls `RemoteTrackPublication.setVideoQuality` (livekit-client 2.21.0: LOW 0, MEDIUM 1,
HIGH 2) for a **subscribed** publication; it only sends `UpdateTrackSettings` and neither re-subscribes nor fires a new
`TrackSubscribed`, so the `<video>` stays the same and it is compatible with `adaptiveStream = false`. `setSubscribed` is deliberately not
used. The whole adaptation is switched off by `FLOAT_ADAPTS_REMOTE_QUALITY = false`; then only visible pictures are rendered and the
quality is whatever the SDK negotiated. Pictures that the window does not show **stay subscribed** (only their quality is lowered).

[#state-machine]
== State machine

[source,kuml,name="conference-dock-states"]
----
stateDiagram(name = "Conference dock") {
    val start = initialState()
    val idle = state(name = "Idle")
    val joining = state(name = "Joining")
    val live = state(name = "Live (attached | undocked)")
    val resolving = state(name = "Resolving")
    val stopped = state(name = "Stopped (reason)")

    transition(source = start, target = idle)
    transition(source = idle, target = joining) {
        trigger = "beginJoin"
        guard = "[state is Idle]"
    }
    transition(source = joining, target = live) { trigger = "Connected" }
    transition(source = live, target = resolving) { trigger = "RoomEvent.Disconnected" }
    transition(source = resolving, target = joining) { trigger = "ReEntered (breakout, recall)" }
    transition(source = live, target = stopped) { trigger = "duplicate identity / rejoin exhausted / ended undocked" }
    transition(source = joining, target = stopped) { trigger = "connect failed undocked" }
    transition(source = stopped, target = joining) { trigger = "ReEntered (deliberate resume)" }
    transition(source = stopped, target = idle) { trigger = "Dismissed" }
    transition(source = live, target = idle) { trigger = "Terminated (leave, sign-out, account switch, language, root restart)" }
}
----

`conferenceDockReduce` is a pure function (no DOM): an unknown (state, event) pair returns the old state unchanged, `Terminated` leads to
`Idle` from every state, and "attached" (is the call view shown in the route?) is an orthogonal flag inside every non-idle state. A
stopped dock never joins by itself; only an explicit click ("Hier fortsetzen", "Erneut beitreten") re-enters.

Side effects live in one place, `ConferenceDock.dispatch`:

* `ConferenceCallPresence` is true exactly in `Joining`, `Live` and `Resolving` (it feeds the "new version available" hint and the
  language switcher);
* the unload guard (`ConferenceUnloadGuard`, exactly one instance in the client) is installed in those states and removed otherwise;
* the dock host is visible only while the state is not `Idle` *and* attached;
* `document.body` and `html` get `lapis-has-dock` exactly while the bar is shown (it reserves the bar's space and sets
  `scroll-padding-bottom`, so a focused control never ends up behind the bar, WCAG 2.4.11);
* when the dock becomes `Idle`, everything is cleared: the active session, the registered `DockableSession`, the room id, the device
  wish, the vote runtime, the audio container and the call panel (no chat, roster or receipt DOM may survive).

== Lifecycle

[cols="2,3,3"]
|===
|Event |What happens |Why

|Route change away from the conference screen
|The screen's destroy hook calls `ConferenceDock.detachView(token)` only. The call keeps running.
|The view is hidden, not torn down. The destroy hook of an *older* screen instance can run after a newer one attached (a click on the
current route in the sidebar), so detaching is keyed by a per-screen token.

|Route change back ("Zur Konferenz" in the bar or the window)
|`attachView(token, fromBar)`: the host is shown, stalled videos are resumed, the bar re-measures, and only a click from the bar moves
the focus into the view (after the route's own focus handling).
|Navigation only: it never joins.

|Sign-out
|`ConferenceDock.terminate(LOGOUT)` runs before `AuthHttp.logout()`.
|Camera and microphone must be off before the session goes.

|Session change
|`AppState.setSession` calls `onAuthSessionChanged(old, new)` before `onSessionChange()`: `null` ends the call (`LOGOUT`), another
identity (member id, guest flag, home server) ends it (`ACCOUNT_SWITCH`), a refresh of the same identity (new `expiresAt`) does not.
|Includes session expiry by a failing RPC.

|Language change
|`requestLanguageChange` ends the call hard first, then applies the switch.
|`I18n.language` restarts the KVision root and rebuilds every widget, including the dock host. The call cannot survive that.

|Root restart
|`App.start` calls `bindHost`; a running call is terminated with `ROOT_RESTART`.
|A new root means a new host.

|Reload or closing the tab
|Unchanged: `beforeunload` / `pagehide` disconnect (`beforeunload` only without a secret-ballot receipt on screen).
|Reloading ends the call (a known limit, see below).
|===

`terminate` is idempotent and bounded (5 seconds for the call's own teardown), bumps a *generation* counter first, and finishes with a
last guard `disconnect()` of the active session, whatever the session's own `terminate` did. Every `await` in `enterCall` after
which a device could be switched on (connect, microphone, camera) checks the generation, so a join or re-entry that was in flight when
a sign-out or a language change happened can never leave a camera running without a view.

== One conference per tab

`beginJoin(roomId)` returns `false` unless the dock is `Idle`: the second click of a double click, a second room card, the deep link
`#/conference/:roomId` during a call (the screen then shows its view plus a hint, no auto-join) and the guest lobby all go through it.
The encounter room asks `ConferenceDock.canJoin()` before it enters (it is not a second dock session yet).

All automatic re-joins share **one** `AutoRejoinGuard` (three per 60 seconds) that lives in the dock, not in the screen.

== Microphone and camera across re-entries

`enterCall` takes `initialDevices`. A deliberate join switches both on. Every **automatic** re-entry (breakout assignment, recall to the
main room, "Zurück zum Hauptraum", the manual resume) passes the last wish of the person (`ConferenceDock.lastDeviceIntent`, taken from
the last `Live` snapshot only, never from what stopping tracks report during a hand-over). Before V1.9.70 every re-entry switched
both devices on again; with the view undocked that would have been an invisible re-activation of a camera the person had switched off.

== The mini bar

`conferenceDockBar()` is built once and mounted as a direct child of the shell. It shows only what a person must know and may do from
anywhere, from a `DockSnapshot` (no personal data, no room title, no room id):

* the return surface (a button; the status text gives way, the badges never do) and, from 768 px, the words "Zur Konferenz";
* from 768 px and only while the call is live, "Als Fenster zeigen" (V1.9.71), which brings the floating window back after "Einklappen";
* consent badges with glyph and word: "● Aufzeichnung", "◆ Live-Stream", "◆ Live-Stream pausiert" (secret-ballot pause); "Abstimmung
  läuft"; "Bildschirmfreigabe";
* microphone and camera with `aria-pressed`, "Bildschirmfreigabe beenden" only while sharing, "Verlassen";
* below 480 px with something to show above the controls: two rows (badges row over the controls).

The controls are the same functions the call view's buttons call (`DockableSession`: `toggleMic`, `toggleCamera`, `stopScreenShare`,
`leave`). "Verlassen" with a secret-ballot receipt on screen does not leave: it takes the person to the view (leaving would lose the
receipt, exactly as the unload guard does). There is no moderation in the bar, no Escape handling, no shortcut, no animation and no
transition.

=== End states

[cols="2,3,3"]
|===
|Reason |Bar text |Actions

|`ENDED` (kicked, ended for everyone, token refused)
|"Die Besprechung wurde beendet oder die Verbindung getrennt."
|"Zur Übersicht", "Schließen"

|`CONNECT_FAILED`
|"Die Verbindung zur Besprechung konnte nicht hergestellt werden."
|"Zur Übersicht", "Schließen"

|`DUPLICATE_IDENTITY`
|"Dieses Konto ist auf einem anderen Gerät verbunden."
|"Zur Konferenz" (the card with "Hier fortsetzen"), "Schließen"

|`REJOIN_EXHAUSTED`
|"Die Verbindung wurde mehrmals getrennt."
|"Zur Konferenz" (the card with "Erneut beitreten"), "Schließen"
|===

"Removed" and "ended" are not distinguishable on the client (a kick in the main room ends in a failing `rejoinMainRoomToken`), so both
are `ENDED` with the existing text. Undocked, there is no toast (the bar is the message); an end state nobody looked at is dismissed
when the conference route opens.

=== Announcements

Two visually hidden live regions, only while the view is not on screen, never moving the focus. In V1.9.70 they sat inside the bar;
since V1.9.71 they live in `conferenceDockAnnouncer()` and speak in both presentations (see "The announcer" above):

* polite, once per call, when the view goes away for the first time (with a hint when microphone or camera are on);
* an alert on every change of recording or live stream (also paused / resumed) and on an involuntary end that the person must act on;
* switching microphone or camera is never announced (the person did it).

The tab title keeps its "● " marker while a recording or stream runs, on whatever page is shown (`PageTitle.apply` asks
`ConferenceDock.decorateTitle`); an undocked call never writes a title of its own, and a room title never reaches the tab title.

== Privacy

* The bar, the announcements and the tab title carry no name, no room title and no room id; the room id is kept in the dock only to
  compare with a deep link and is never rendered or logged.
* **The floating window shows faces and therefore names** at its tiles, exactly the text the full view already shows (`tileLabel`, set by
  `textContent`); the bar stays name-free. The own picture appears only while the camera is on (`cameraOn` and a real video), never as a
  stale frame, and the state of microphone and camera is visible and operable in every size, also in the smallest one.
* A foreign screen share is always labelled ("Bildschirm von ...") and cannot be dismissed from the window; the own share is never shown as
  a picture, only as the badge "▣ Sie teilen Ihren Bildschirm" and the stop button.
* **Sharing the whole screen** captures the floating window with the other participants' videos and sends it into the conference, and
  with it into a running recording or live stream. Only the badge and this note address it today (the page cannot tell which surface the
  person shares); an audit point for a later wave.
* The stored preference holds only numbers and the mode (see above); it is not cleared on sign-out because it is not personal data.
* The window itself never logs a name, a label or a track id.
* Everything is cleared when the dock becomes idle (sign-out, account switch, leave): no chat, roster or receipt DOM survives.
* The dock and the bar contain no `rpcService` read (ledger of `ClientDataStateTripwireTest`).

== `DockableSession` and the encounter room

`DockableSession` (`attach`, `detach`, `leave`, `terminate`, `toggleMic`, `toggleCamera`, `stopScreenShare`) is the only bridge from
the dock into a running call; `DockSessionKind.ENCOUNTER` is declared for the follow-up wave in which the encounter room becomes a
second kind of dock session. Until then the encounter room only asks `canJoin()`.

`detach()` leaves browser fullscreen and closes the dialogs of the call. It deliberately does **not** call `cleanupFullscreen()`, which
also stops the ballot poll and the control bar's observers.

== Guards (tripwires)

`ClientConferenceDockTripwireTest` (server test module, source scan) keeps the wiring true: the conference screen's destroy hook only
detaches; exactly one unload guard, one rejoin guard and one `var state` exist, all in the dock; `disposeBackgroundEffects` has five
known callers; remote audio goes to the permanent container; sign-out, identity change and language change end the dock first; the
dock and bar make no RPC read and show no personal data; the bar is `position: fixed` without transform, transition or animation.
`ClientConferenceRejoinTripwireTest`, `ClientToolbarIconTripwireTest` (R58 ledger: `conferenceDockBarControls` with four
controls) and `ClientPageHeaderTripwireTest` were adapted. Karma: `ConferenceDockReduceTest`, `ConferenceDockLifecycleTest`,
`ConferenceDockBarTest` (view model and announcements), `ConferenceDockBarDomTest`, `ConferenceScreenRootLifecycleDomTest`,
`LanguageChangeDomTest`.

V1.9.71 extends the tripwire with the floating window: its files make no RPC read, never join or attach a track, build no markup from
text and show no personal data; `localStorage` is touched only by `ConferenceFloatStore`; `reclaimSlot` precedes `clearElement` in the
call view and `returnAll` precedes the session's teardown in `terminate`; the window's CSS is fixed, not transformed or clipped and below
1035; `ClientUiGuidelineTripwireTest` (R54) names seven transitions. `ClientDataStateTripwireTest` is deliberately unchanged (the wave has
no RPC; its ledger of 153/46 cannot move). Karma: `ConferenceFloatGeometryTest`, `ConferenceFloatStoreTest`,
`ConferenceFloatSelectionTest`, `ConferenceDockPresentationTest`, `ConferenceVideoLedgerDomTest`, `ConferenceFloatWindowDomTest`,
`RemoteVideoQualityTest`.

== Known limits

* **Not tested on a real device.** A real call with real participants over a route change, the real effect of `setVideoQuality` on the
  bandwidth, Safari and iOS cannot run in Karma (no LiveKit server). Covered automatically: the geometry, the codec and the selection
  (pure jsTests), the loan ledger and the window in a mounted root with the real stylesheet (`ConferenceVideoLedgerDomTest`,
  `ConferenceFloatWindowDomTest`), the wiring as a source scan (`ClientConferenceDockTripwireTest`). Karma's iframe is narrower than
  768 px, so these tests fake the media query and neutralise the CSS guard; the guard itself is pinned as text.
* No picture-in-picture, no chat and no encounter room in the window; on a phone only the mini bar exists.
* Pictures the window does not show stay subscribed (only their quality is lowered).
* `prefers-reduced-motion` switches the window's 160 ms move transition off (R54, tested as CSS text; Karma cannot emulate the media
  feature here).
* Still only one device per account at a time (V1.9.69: a second device evicts the first, which shows the "connected on another device"
  card instead of re-joining); multi-device support needs a server change and is not started. Not tested with two real devices.
* The encounter room is not part of the dock: leaving its page still ends it, and it does not start while a conference holds the dock.
* That sound and video really keep running across a route change with a real LiveKit call is not testable in Karma. It needs a manual
  test on desktop Chrome, Firefox, Safari and a phone before it is announced.
* Mobile browsers can pause background tabs; the bar cannot prevent that.
* A reload or closing the tab still ends the call.
* `adaptiveStream` is off, so hidden remote videos keep loading (bandwidth); dynacast and the subscription logic are unchanged.
* The narrow two-row bar is covered by a view-model test and a CSS review, not by a 360 px browser test (Karma runs at a fixed width).
* The new texts in the seven catalogs come from an agent and are not checked by native speakers.
