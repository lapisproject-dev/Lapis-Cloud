= Direct messages: inbox, conversation history and unread counter (V1.9.34)
:description: How the member inbox, the expandable conversation history and the sidebar's unread counter work, what personal data they handle and what they do not do yet.
:toc:
:icons: font

== Scope

Direct messages are one-to-one messages between active members (`IDirectMessageService`). The client shows them on the screen "Nachrichten"
(`MessagesScreen.kt`, route `/messages`). V1.9.12 added the list and the reply form (carpool contact messages arrive here); V1.9.34 adds
the conversation history and the unread counter. The server changed in one place only: `listConversation` is capped (see below). No migration.

NOTE: **V1.9.231 split the former "Kommunikation" screen** into "Nachrichten" (this document) and "Mailinglisten" (`MailingListsScreen.kt`, route
`/mailing-lists`, see `features/dynamic-mailing-lists.adoc`). The separate "Postfach" section is gone: it listed the same messages as the
conversation list once more, by message instead of by partner. There is now ONE list, one row per conversation partner (`DirectMessagePartnerList.kt`),
each row marked with the chat icon and the word "Gespräch". Only *opening* a conversation marks it read (`conversationView`, once per open
conversation); loading the screen no longer marks everything read, so a message stays unread (and counted in the navbar and sidebar pills) until its
conversation is opened. The old address `/communication` redirects to `/messages` (fixed target, address replaced in place without a history entry).
Mailing-list letters are not part of the list yet: a member cannot read the sent messages of their lists (`IMailingService.listMailingMessages` is
board-only); a read-only call for the member's own received letters is the planned next step. After a reply is sent the field is emptied and the
focus returns to the new, empty field.

== Inbox (superseded by V1.9.231)

NOTE: **Superseded.** The separate "Postfach" section and the batch marking described here are gone (see the NOTE at the top): loading the screen no longer marks anything read; only opening a conversation does. The text below is the V1.9.34 state, kept for history.

`listInbox()` returns the messages addressed to the caller. After the list is rendered, all unread ones are marked read in one batch
(`markReadThenRefreshCounter`): one coroutine marks them one after another and only then refreshes the sidebar counter exactly once. This
order matters -- refreshing before the marks landed would leave "(3)" in the sidebar, and one refresh per message would be N calls.

== Conversation history (V1.9.34; the entry point changed in V1.9.231)

NOTE: Since V1.9.231 there is no inbox row to expand: a conversation is opened from the conversation list (`conversationView`), and the "Verlauf anzeigen" disclosure below an inbox message no longer exists. The cap, the ordering and the error state below still apply to the conversation view; unread messages are marked read when the conversation is opened, not by a batch after the list loads.

Below every inbox message the link-button "Verlauf anzeigen" opens the whole conversation with that member (`conversationDisclosure`):

* Loaded only on expand (a closed disclosure costs no call); collapsing removes the content, expanding again loads again. No state is kept.
* Oldest first (the server delivers newest first; the client reverses for display). The viewer's own messages say "Sie", the other member's
  name is shown for theirs. No chat bubbles, no left/right alignment.
* `listConversation` returns only conversations the caller takes part in, and since V1.9.34 at most the newest 200 messages
  (`MAX_CONVERSATION_MESSAGES`); at 200 the client says "Es werden die neuesten 200 Nachrichten angezeigt."
* Received, still unread messages shown here are marked read through the same batch helper as in the inbox.
* A failed load is the standard error state (fixed sentence, "Erneut versuchen"), never the exception text.

== Unread counter (sidebar part replaced in V1.9.36, see below)

NOTE: Since V1.9.36 the number lives in the navbar, not in the sidebar link (section "V1.9.36"). The description below is the V1.9.34
state; `communicationSidebarLabel` and `attach`/`detach` no longer exist.

The sidebar link "Kommunikation" showed "(n)" for 1 to 99 unread messages and "(99+)" from 100 (`communicationSidebarLabel`). `UnreadMessages`
is the only writer:

* It loads when the sidebar is built (`attach`), on **every route change** (`UnreadMessages.onRouteShown`, called from `show()` in
  `Routing.kt`) and after a batch of messages was marked read or a reply was sent. There is **no timer, no polling and no websocket** -- a
  message that arrives while the page is open shows up at the next screen change, not while the user stays on the same screen.
* Calls are coalesced: at most one in flight plus one follow-up.
* Failures are silent (no toast): the counter runs on every sidebar build, and an inactive member's `unreadCount` is rejected by the server.
* `detach` (on logout) stops a late answer from writing into a dead link.

== V1.9.36: conversation list, paging, navbar counter

=== Conversation partners

`listConversationPartners(limit)` returns everyone the caller has exchanged messages with: partner id and name, the time of the last message
in either direction and the number of unread messages from that partner -- **never a message text**. It is an aggregation over
`direct_message` (three grouped queries on the indexed sender/recipient columns, merged in Kotlin); there is no migration. Messages to
oneself (possible before V1.9.12) are not a conversation and are filtered out. Order: `lastActivityAt DESC`, then `partnerId ASC`; `limit` is
clamped to 1..100 (`MAX_CONVERSATION_PARTNERS`). The screen shows the heading "Gespräche" with the list; opening a row shows the conversation and
a reply form (`DirectMessageReplyForm.kt`, extracted from the inbox row); only one conversation is open at a time.

The partner list loads **first**; the inbox is built only after its first load. Reason: the inbox marks everything read as soon as it loads,
so the "n neu" hint would otherwise already be empty. The hint is therefore a snapshot of the state since the last visit.

=== Keyset paging

`listConversationPage(otherMemberId, beforeSentAt, beforeId, limit)` returns one page, newest first, ordered by `(sent_at DESC, id DESC)`; the
cursor is the last (oldest) message of the previous page, passed as two flat nullable primitives (both null for the first page, both set
otherwise; one alone is a `BadRequestException`). `limit` is clamped to 1..100 (`MAX_CONVERSATION_PAGE`); the server fetches `limit + 1`
rows to know `hasMore`. `sent_at` is truncated to microseconds on write, so the cursor round trip is lossless; identical `sent_at` values
are separated by `id`. A message inserted between two pages causes neither a duplicate nor a gap. The client loads 50 per page, prepends older
pages block by block, drops duplicates by id and stops offering older messages at 1000 loaded (`DIRECT_MESSAGE_CLIENT_CAP`). `listConversation` and its
200-message cap stay for existing callers.

A conversation that does not exist, or that belongs to others, is an empty page, not an error: no existence oracle. A malformed id is a
uniform `BadRequestException` that does not echo the input.

=== `markConversationRead`

One `UPDATE` marks every unread message **from** the partner **to** the caller as read and returns the count (unknown or foreign id: 0).
Why it exists next to `markRead`: with paging the conversation view only holds the newest page, so older unread messages could not be
marked through the ids of that page; and one atomic statement replaces N single calls. The inbox list keeps using `markRead`.

=== Navbar counter

The unread count is shown as a pill on an envelope in the navbar (`NavbarUnreadIndicator.kt`), visible on every width and with a collapsed
sidebar, only for members who see the MESSAGES link. It links to `#/messages` (V1.9.231; before: `#/communication?section=messages`; no id, no personal data;
`?section=messages` is still honoured and focuses the list heading). `UnreadMessages` is one state with a registry of displays keyed by name (the navbar is rebuilt on every
`refreshNavbar`; the new display replaces the old under the same key). Triggers: registration, every route change (unthrottled), a mark-read
or reply, and **tab return** (`visibilitychange`/`focus`, installed once) throttled by a timestamp comparison to one refresh per 30 seconds
(`TAB_RETURN_REFRESH_THROTTLE_MS`). Still no timer, no polling, no websocket. V1.9.231 brings the number back on the sidebar entry "Nachrichten" as a second display of the same count (`bindSidebarUnread`, key
`sidebar-messages`; a child span, never part of the label, so the menu search is unaffected; accessible name as the envelope's). The pill is not
an `aria-live` region and not animated; its accessible name is "Nachrichten, n ungelesen".

== Attachments (V1.9.233)

A reply can carry up to **5 files, 10 MiB each, 20 MiB in total** (binary, like the mailing attachments). The rule set is the SAME code as for mailing messages
(`AttachmentRules`, `AttachmentSniffer`, `AttachmentZip`, `sanitizeAttachmentName`, `classifyAttachmentUpload` -- extracted in this wave, not copied;
`AttachmentRulesSingleSourceTripwireTest` pins it): PDF, PNG/JPEG/GIF/WebP, docx/xlsx/pptx, odt/ods/odp, txt/csv, checked by extension AND by content, the MIME type
being the server's. The message text stays mandatory; there is no message without text.

=== Pending, then sent

An upload is first *pending*: a `direct_message_attachment` row with `message_id` NULL, owned by the uploader and addressed to ONE recipient
(`POST /api/direct-messages/attachments`, multipart: the form field `recipientId` first, then the file). It becomes part of a message only through
`IDirectMessageService.sendDirectMessageWithAttachments(recipientId, body, attachmentIds)` (new, last method of the interface; there is one method for
"new message" and "reply" because they are the same operation on the server). The send is atomic: message insert and assignment of the files run in one
transaction under the sender's member-row lock; ANY problem with an id (unknown, foreign, already sent, addressed to someone else, expired, duplicate, more than 5)
fails the WHOLE send with one uniform `DirectMessageAttachmentsUnavailableException` (a dedicated type: Kilua RPC transmits only the exception type, and a plain `ConflictException` also covers a bad body, a send to oneself and an unreceivable recipient) -- no message is created and the caller learns nothing about which id was wrong.

[source,kuml,name="dm-attachment-flow"]
----
sequenceDiagram(name = "Direct message -- attachment, pending to sent") {
    val sender = lifeline(name = "Sender (browser)")
    val routes = lifeline(name = "DirectMessageAttachmentRoutes")
    val db = lifeline(name = "PostgreSQL (direct_message_attachment)")
    val service = lifeline(name = "DirectMessageService")
    val recipient = lifeline(name = "Recipient (browser)")
    val poller = lifeline(name = "DirectMessageAttachmentPendingPoller")

    message(from = sender, to = routes, label = "POST attachment: recipientId field, then the file (same origin, active member)")
    message(from = routes, to = db, label = "gate BEFORE the file stream: recipient receivable? pending limits free?")
    message(from = routes, to = db, label = "lock sender member row; re-check limits and name; INSERT row (message_id NULL)")
    message(from = sender, to = service, label = "sendDirectMessageWithAttachments(recipient, text, ids)")
    message(from = service, to = db, label = "lock member row; INSERT message; UPDATE pending rows of THIS sender and recipient SET message_id (all or nothing)")
    message(from = recipient, to = routes, label = "GET download: only sender or recipient of the message; uniform 404 otherwise")
    message(from = poller, to = db, label = "hourly: DELETE pending rows older than 24 h, then their files")
}
----

A rebuilt composer (page reload, navigation) finds its pending files again through `GET /api/direct-messages/attachments/pending?recipientId=` (own uploads for ONE
partner, upload order, `Cache-Control: no-store`; `401` / `403` / `400 NO_FILE` for a missing or malformed partner). Without it, invisible pending files would still count
against the limits and the duplicate-name check for up to about 25 hours. The client freezes the list while a send runs and removes only the sent ids afterwards.

=== Who may do what

[cols="2,3,3,3",options="header"]
|===
| Action | Uploader (sender) | Recipient | Anyone else (incl. BOARD/ADMIN)
| Upload | active member, recipient receivable by the rule of `sendDirectMessage` | -- | no
| Delete | only while pending, own upload | no | no
| Download | pending: yes; sent: yes | sent: yes, pending: no | no -- the same 404 as for an unknown id
|===

There is no role in any predicate (`DirectMessageAttachmentRoutes` and the store never read a role; tripwire). Unknown id, foreign id, malformed id, inactive caller
and a missing file all answer the same `404 {"code":"NOT_FOUND"}` with the same body and `Cache-Control: no-store`; `401` (not signed in) and `429` (rate limit) do not
depend on the id either. A recipient who is unknown, inactive, anonymized or the caller itself yields one `RECIPIENT_UNAVAILABLE` -- no existence oracle. Downloads are
always `Content-Disposition: attachment` (also PDF and images), `nosniff`, `private, no-store`, `Cross-Origin-Resource-Policy: same-origin` and
`Content-Security-Policy: default-src 'none'; sandbox`; the file name is never part of a URL and never logged.

=== Limits and lifetime of pending files

Per sender and recipient: at most 5 pending files and 20 MiB. Per sender over all recipients: at most 20 pending files and 80 MiB (`PENDING_LIMIT`). Both are checked
twice: fail-fast before the file is streamed (so a refused request never writes 10 MiB to disk) and authoritatively inside the insert transaction under the
sender's member-row lock. A pending file that is not sent within 24 hours is removed by an hourly poller, so it lives at most about 25 hours (the 24 h poller of
the mailing retention would have allowed up to 48 h). A sent attachment has no retention period.

=== Deletion

There is no `ON DELETE CASCADE` (repo convention; a cascade could not delete the files either). Rows and files are deleted in code. Today NO code path deletes a direct message;
"deleted with the message" therefore only happens through the DSGVO erasure (`CommunicationPersonalData`): the sender's pending uploads are deleted in every mode,
and under `HARD_DELETE_WHERE_UNCONSTRAINED` every file the person uploaded (rows and files) is deleted together with the redaction of the sent texts. In the default mode
sent attachments stay with the recipient, as the texts do; received attachments always stay. The export (Art. 15) lists name, type, size, instant and direction
(SENT/RECEIVED/PENDING) -- never the file or its storage key. The organization backup carries the rows and the files (`BLOB_TABLES`).

=== Not covered

Carpool contact (`CarpoolService.contactAuthor`), the member finder and the event-registration notifier keep calling `insertDirectMessage` and carry no files
(`CarpoolMessageDmBoundaryTripwireTest`). There is no virus scan; PDF JavaScript and image polyglots are not detected -- the client says so ("Lapis prüft Anhänge nicht auf Viren.").

== Composing a new message (V1.9.237 "Neue Nachricht")

The Nachrichten page gets a header action "Neue Nachricht" (`MessagesScreen.kt`, `DirectMessageComposeView.kt`). The page has no right-hand pane, so the compose view *replaces
the list area* (in memory; `?view=new` opens it directly and is kept with `replaceState`, no id ever goes into the address). Back is "Zur Liste".

=== Person

A name search (`searchMessageRecipients`): at least 3 and at most 60 characters after trimming (anything else answers an empty list, never an error and never an echo), a 300 ms debounce
on the client and no call below 3 characters. Only `display_name` is searched, case-insensitive, with `%`/`_` escaped (`containsLikePattern`; without it `%%%` would list the whole membership).
At most 10 hits, ordered by name then id. Excluded: the caller, non-members, anonymized members, members who switched "Auffindbarkeit" off (`member.dm_discoverable`, default true), and everybody
blocked in either direction (direct-message block or finder block). A hidden member looks exactly like a name that does not exist. `hasConversation` marks people the caller already
exchanged messages with. After choosing, a chip and the same form as a reply appear, including attachments; changing the recipient discards the drafts (pending uploads are bound to
the recipient).

=== Group

`listMessageGroups` returns the committees the caller may write to: active, not the general assembly, and either the caller is a member *today* or the caller is BOARD/ADMIN. Membership is never
rebuilt: `eligibleMemberIds` / `isCommitteeEligible` cover manual committees (seat rows with `since`/`until`) *and* rule committees (no seat rows). A rule that no longer parses hides
the committee; it neither breaks the list nor leaks as an error. `sendGroupMessage` writes **one individual message per current member** (ACTIVE, not anonymized, the sender
excluded), text only, in one transaction with one shared `sentAt`. More than 50 recipients (`DirectMessageRules.MAX_RECIPIENTS_PER_SEND`) is refused with nothing written.
A recipient who blocked the sender is skipped silently and the sender sees the same confirmation (`memberCount` of the list does not subtract blocks, the result carries no count).

Lock order of the send: the sender's member row (`forMemberUpdate`, serializes two parallel group sends), recipients in ascending id order, the audit entry LAST (`AuditLogRecorder` locks the chain-state row).
The group rule and the recipients are read again under the lock.

=== One answer for every refusal (no oracle)

An unknown, malformed, non-member, anonymized or blocked recipient is ONE `DirectMessageRecipientUnavailableException` with a fixed text and no id. Before V1.9.237 an unknown id
answered `NotFoundException("Member <id> not found")` and an unreceivable one a `ConflictException`, which let a caller probe membership. The rule lives in
`directMessageRecipientRefusal` and runs for all five entry points: `sendDirectMessage`, `sendDirectMessageWithAttachments` (and the upload route), `CarpoolService.contactAuthor`,
`MemberFinderService.contactConnection` and the event-registration notifier. The member lookup and both block lookups always run, so the amount of work is the same for every reason.
Writing to oneself stays a `ConflictException`. **Behaviour change:** callers that used to see NotFound/Conflict for the recipient now get the typed exception (mapped centrally in
`AppState.typedRefusalText`). The event-registration notifier swallows every exception (it logs only the class name), so a block also suppresses the registration message to the event
creator -- the e-mail notice still goes out.

=== Blocking

"Blockieren" in the header of an open conversation (plain text button, inline confirmation "Abbrechen" / "Blockieren"). `blockMessageSender` is idempotent, an unknown or malformed id is a silent no-op
(always `Unit`), and nothing tells the blocked person. The blocked person can no longer write to the blocker and the blocker cannot write to them (a block hides the pair from each other).
Lifting: "Blockierte Personen" at the end of the page (`listMessageBlocks` / `unblockMessageSender`, own blocks only; a foreign or unknown id is a uniform `NotFoundException`). A name is shown only
where a conversation exists, otherwise a neutral "Mitglied": a block that came from a finder request must not reveal an identity.

*Why a table of its own and not `member_finder_block`.* The finder table is emptied when the finder switch goes off, can only be managed while the switch is on, carries no names and belongs to the Art. 9
finder data (excluded from the backup, nothing audited). A direct-message block must survive all of that. `direct_message_block` (V128) is written only by `DirectMessageBlockStore`
(`DirectMessageComposeTripwireTest`). The DM rule *additionally* respects finder blocks in either direction (read only), but they disappear when the finder switch goes off.

=== Limits

`DirectMessageRateLimiter` (in process, bounded map, **resets on restart and is per JVM**): 30 sends per 10 minutes and 150 recipients per hour per member (a group of 50 counts as 50), 60 searches per
minute, 30 blocks per hour. A check records the attempt when it allows it, so a send that the recipient rule refuses afterwards still counts; a refused attempt is not recorded. It is never called
inside a `transaction {}` (Exposed retries the block on an SQLException and would count twice). Carpool and finder keep their own limiters; the event notifier is a system path and exempt.

=== Audit, backup, DSGVO

* Audit: only `DIRECT_MESSAGE_GROUP_SEND` (`entityId` = the committee id, snapshot `{"deliveredCount":n}`, no text, name or recipient). Blocks and the visibility switch are *not* audited -- the audit chain
  cannot be erased, so a block between two people would survive an erasure request (same rule as the finder).
* Backup: `direct_message_block` stays *in* the organization backup (it is not in `EXCLUDED_TABLES`). Direct messages are backed up too; a restore without the blocks would silently lift the protection.
* DSGVO (`CommunicationPersonalData`): the export lists the blocks the member *set* (and the visibility), never blocks against the member; erasure deletes the blocks on both sides.
* The direct-message path sends no e-mail, so the mail relay is not involved.

=== Not in this wave

Several recipients at once, a group label, group attachments, writing to the whole organisation, reporting a message, telling same-named members apart in the search (the list shows the name
and "bereits im Gespräch" only), persistent limits.

== Personal data

Message text and the names of both sides are personal data. In the new files they reach the screen only through `untrustedDiv`/`textCell`/
`untrustedOptions` (a forged i18n marker is neutralised), and never a toast, the route, the document title, the console or browser storage.
`ClientDirectMessagePiiTripwireTest` checks this on the source, plus "no timer in the counter or the conversation view".

== Known limitations

* There is no way into the history for a partner who never wrote to you (only inbox messages carry the link).
* The counter does not update by itself while the user stays on one screen; it refreshes on the next route change or tab return (see V1.9.36).
* (V1.9.36) The inbox stays next to the conversation list and still marks everything read when it loads; the "n neu" hint of the list is a snapshot.
* (V1.9.36) At most 100 conversations in the list, at most 1000 messages per conversation in the client. No message preview in the list.
* (V1.9.36) A reply to a partner who is no longer an active member is refused by the server; the form shows one general sentence.
* (V1.9.36) No real-time push: the pill refreshes on navigation and on tab return.
* (V1.9.233) Attachments exist for direct messages SENT FROM the conversation view's reply form only; carpool contact, member finder and event-registration messages carry none (see "Attachments" below). A message always needs text. There is no virus scan and no retention period for sent files.
* Not tested against real data or a staging server (see `direct-messages-quorum-declarations-staging-test.adoc`, not executed).

See also the contact routing of the carpool board in `carpool.adoc`.
