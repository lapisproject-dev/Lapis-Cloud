= Collapsed create forms (V1.9.40)
:toc:

== Purpose

On a list screen the form that adds a record used to sit under the list as a second, always visible section ("Neues Gremium anlegen"). That put
a long form between the person and the content they came for, and it repeated on every screen with a slightly different title. Rule R36B
(`ui-ux-guideline.adoc`) replaces it: the screen offers one button in the title row and opens the form on demand. This wave adds the building
block and converts four governance screens as a pilot. It is a client-only change: no migration, no server change, no new RPC.

== Behaviour

[cols="1,4", options="header"]
|===
| Moment | What happens
| After the load | The form is not built. The button ("Neues Gremium", "Neue Bestellung", "Neue Sitzung", "Neuer Antrag") sits in `.lapis-page-action` of the title row with `aria-expanded="false"` and `aria-controls` pointing at the form host, which exists (empty) while the form is closed.
| Open | The button stays in its place but is `visibility:hidden` with `aria-hidden="true"` and `tabindex="-1"` (nothing jumps, no hidden tab stop). The form is built at once, without animation. The focus moves to the first field. The host scrolls into view (`block: nearest`); the scroll is smooth only without `prefers-reduced-motion`. The focus is only moved on a user action, never when the page is built.
| Open again | `open()` without a prefill on an open form does nothing. The host is emptied before every build, so a double click can never build two forms. `open(prefill)` on an open form that was changed asks first.
| Cancel, `Escape` | Compares the field values with the values taken at open. Equal: closes at once. Different: the dialog "Eingaben verwerfen?" with "Verwerfen" and "Weiter bearbeiten"; the focus is on "Weiter bearbeiten", and `Escape` inside the dialog means "keep editing". The `Escape` listener sits on the form host (it dies with the page, nothing global), ignores an `Escape` that a combobox already used, and is silent while a dialog is open.
| Saved | The screen's save path calls `close(true)`: no question, the focus returns to the button, `aria-expanded="false"`, the list is reloaded by the screen as before.
| Save fails (validation, 409, no right) | The form stays open with its banner: the component is only told about success.
|===

"Changed" is a comparison, not a flag: typing a word and deleting it again is "unchanged". A field that is filled programmatically after the
form was built (the member picker of the board appointment preselects the first member when its options arrive) calls `FormSnapshot.rebaseline()`,
so the preselection is not mistaken for an edit.

== The building block

`CollapsibleCreateForm.kt`:

* `collapsibleCreateForm(actionSlot, formHost, buttonLabel, formId, build)` returns a `CollapsibleCreateFormController` (`open(prefill)`, `close(force)`, `isOpen`).
  `build` builds the form into the host and returns a `FormSnapshot`; it receives a `close(saved)` function for the Cancel button and for the save.
* `PageHeader.actionSlot` (in `PageHeader.kt`): the `.lapis-page-action` slot, created on first access. `pageHeader(primaryAction = ...)` fills the same slot as before.
* `LapisForm.snapshot()`: the values of every field of a form, in order.
* `collapseCancelButton(close)`: the "Abbrechen" button of the form row.
* `confirmDialog(cancelLabel = ...)` (in `ConfirmDialog.kt`): a new optional parameter for the label of the dismissing button; every existing caller is unchanged.

The existing `render...Form` functions keep their call shape; they gained an optional `collapse` parameter and now return the
`FormSnapshot`. `collapse` stands BEFORE the last lambda parameter (`onCreated`, `onSaved`, `onGranted`, `onRecorded`), not at the very end: the
tests call the functions with a trailing lambda (`renderCostCenterCreationForm(root) { }`), and a function parameter at the end would capture that
lambda and break the call. Callers that ignore the result (the body tests, which call them directly) are unaffected.

== Where the data comes from

The pilot screens that need candidates for their pickers (meetings: members; motions: amendable motions) load them with the page, as before.
The form is built from data already in hand when the button is pressed, and the button lives outside the list refresh, so reloading the list
never discards a form that someone is filling in. Loading the candidates when the form opens instead was considered and not done: it would add
RPC reads outside a data region (`ClientDataStateTripwireTest` budget) and a loading state inside the form for no benefit to the pilot.

== The tripwire

`ClientUiGuidelineTripwireTest`, block R36B (see `ui-ux-guideline.adoc` for the rule table entry):

* the four converted screens must use `collapsibleCreateForm` and hold no visible create form;
* every other visible create form is listed per file in `R36B_NOT_YET_COLLAPSED` with the group that pays it (a fingerprint per finding, so a new
  one turns the test red, and a converted one must be deleted from the ledger);
* the look-alikes that are not create forms are in `R36B_EXEMPT`, each with its reason;
* a downward ratchet (`R36B_REMAINING_MAX`).

The scan is a heuristic (a section title `h2(tr("Neu ..."))`, or a call of a `render...Creation/CreateForm/SubmissionForm/AppointmentForm`
function outside a `collapsibleCreateForm` call). It does not see a create form built under another name or hand-rolled in a screen: the ledger
is an honest approximation of the debt, not a complete census.

Two screens have two buttons. R36 says "at most one primary action"; here both buttons are equal-rank outline buttons, one per list on the page
(journal and account list; batch list and return list). That is a deliberate exception (see `ui-ux-guideline.adoc`, R36). `.lapis-page-action` is a
wrapping flex row (`gap: .5rem`), so the two buttons wrap at 375 px instead of overflowing. In the journal the two slot containers are created
before the data arrives, so the order is fixed no matter which answer comes first.

Two additions to the building block, both additive (the pilot calls are unchanged):

* `collapsibleCreateForm(..., icon = ActionIcon.ADD, build)`: the icon of the title-row button. Only "Kontoauszug hochladen" needs another one (`UPLOAD`).
* `FormSnapshot.applyProgrammatic { ... }`: a programmatic change of a field after the form was built (a server-loaded preselection). It becomes
  the new "unchanged" state ONLY if the form was unchanged before; what the person typed is never swallowed. (`rebaseline()` takes the current
  values unconditionally: fine when the form cannot have been touched yet, wrong when the answer of a slow request arrives after typing.) Used in
  the SEPA return form (batch and item preselection) and the batch form (tier list).

Findings that shaped the conversion:

* *The journal form is dynamic.* Posting lines are fields registered with the form (`LapisForm.fields` is a live list; removing a line unregisters
  its fields), and `snapshot()` reads the values at every comparison. A newly added, empty line therefore already counts as a change (Escape asks):
  the safe direction. "Neue Buchung" is converted, not exempted; `FinanceCollapsibleFormsDomTest` proves it.
* `open(prefill)` is now wired: "Als neuen Entwurf duplizieren" opens the form pre-filled. Before, the duplicate silently overwrote what was typed
  into the always-visible form; now an open, changed form asks first.
* Open items: the hand-built toggle ("Posten anlegen") threw typed input away on "Abbrechen" and on a second click. It is replaced by the shared
  component, which asks.
* The bank statement upload frame lives INSIDE the build lambda; otherwise an empty bordered box would stay on the page while collapsed. After a
  successful import the screen closes the form through the controller. The snapshot of the upload form also contains the chosen file names,
  because the raw upload control may not report its selection through the generic field value.

== V1.9.47: group "Veranstaltungen" converted

Client only: no migration, no server change, no new RPC. Four screens, one button each in the title row: "Neue Veranstaltung" (`EventsScreen`),
"Neuer Raum" (`EventRoomsScreen`), "Neue Schicht" (`EventVolunteerShiftsScreen`), "Neue Bestellposition" (`CateringScreen`). The create button inside
a form is `ActionIcon.ADD` (as on the finance forms and as the R57 table says for "anlegen"), next to "Abbrechen"; the labels are unchanged. These
forms are loose KVision widgets, not `LapisForm`: they still guard against a double click with `createButton.disabled`, and each builds its
`FormSnapshot` by hand. The screens have no client-side rights check (the route is BOARD/ADMIN only and the server enforces the rights), so there is
no "button hidden for a role" case and none was added.

Specifics of these screens:

* *Picker lock (catering, shifts).* The form belongs to the event chosen in the picker above the list. While the form is open the picker is
  disabled (`onOpenChange` of the component); it is released by every way of closing (save, cancel, discard). The form names its event on a line of
  its own: a `tr("Für Veranstaltung:")` label and the title as a separate widget through `untrustedSpan` -- never one concatenated string. The event
  id is captured when the form is opened and the save uses that id, not the picker value. Without an event (or after a failed event load) the button
  does not exist; a retry after an error builds it once.
* *`onOpenChange`.* `collapsibleCreateForm` and the controller take an optional `onOpenChange: (Boolean) -> Unit`, called with `true` after every
  (re)build of the form and with `false` after it closed. Existing callers are unaffected.
* *Series editor fingerprint.* The weekday chips of the recurrence editor are buttons, so a snapshot of field values alone would miss them and Escape
  would discard a toggled chip silently. `RecurrenceEditor.stateFingerprint()` joins the checkbox, preset, frequency, interval, sorted selected
  weekdays, monthly variant, end type, count and until into one string; the event form snapshot appends it. It is compared only, never rendered or logged.
* *Rooms arrive late (events).* The room select of the open form is refilled in place when `listRooms` answers while the form is open (the chosen
  value is kept and re-set, because replacing the options can reset it); the form is not rebuilt, so typed input and the changed-state survive. The
  second `listRooms` call that used to rebuild the always-visible form is gone (one call instead of two).
* *Kept as they were:* the navigation row of the events page (Räume, Helfer-Schichten, Catering, Check-in), "Offene Erstattungen", the status filter,
  and every edit form. A save that fails after the person discarded the form shows only the toast; the text is gone (a deliberate user decision).

The R57 strict set now also holds the four event screens: a plain button for "anlegen|hinzufügen|speichern|..." is a finding there.
R36B debt ledger: 30 -> 21 findings.

*Beyond the ledger.* The mailing-list form, the travel-expense and volunteer-allowance buttons (a self-built "the button hides itself" pattern) and the two
dunning forms (a permanently visible "Mahnstufe anlegen" under the list) were not in `R36B_NOT_YET_COLLAPSED`; the scanner did not see them. They are converted
in this wave ("everywhere means everywhere"). The scanner now sees such cases (below).

*Pattern "controller once, slot shown or hidden"* (new): for a button that depends on an asynchronous load (the document form needs an open folder with
loaded documents; the draft forms need a load without an open draft) the button hangs in a sub-slot (`slot = header.actionSlot.div()`), the
`collapsibleCreateForm` is created exactly ONCE at page build, and the slot is shown or hidden after the load. A generation counter drops the answer of a
superseded load. Consequences: never a second button, no race between a late callback and the slot, and a failed load leaves the slot hidden. The form host is
never touched by a reload, so typed text survives it. Hidden slots render no children (KVision), so the button is built when the slot is first shown.

*Documents.* The form is built per opening, for the folder that is open at that moment. A folder switch goes through `requestClose`: a changed form asks first,
"Weiter bearbeiten" stays in the folder. The visibility default of a new folder is the default of the role at every opening (the form is rebuilt, which replaces the
old `setValue` reset). The version upload stays visible, see "Not converted".

*DSGVO.* The four builders (`renderAgreementForm`, `renderTomForm`, `renderDpiaForm`, `renderBreachForm`, in `DsgvoComplianceForms.kt`) serve creating and
editing; creating passes a Cancel and `collapse`, editing stays inline in the row (no Cancel, the row toggle is the way out). Their fingerprint is built by hand
over EVERY input (loose widgets); `RestGroupFormsDsgvoDomTest.everyFieldIsInTheFingerprint` changes each input one by one and checks that Escape asks, and that restoring
the value closes at once. Switching the view (the toggle row stays as it is) asks first when the form of the current view was changed.

*Auction.* The LTR balance strip and the fee line (design decision D3) are the first elements of the opened form, not of the closed page. Validation and
the confirm dialog (Tier 1) are unchanged. The server conflict for a switched-off auction keeps the form open.

*Stream destinations.* After saving and after discarding, the form host is empty: no password field, no key value anywhere. A platform preset that fills the
URL counts as a change.

*Travel expenses and volunteer allowance.* The old button hid itself and never came back. The new button is part of the page header; if a draft shows up
after a reload while the form is open, an unchanged form closes and a changed one asks first.

*Convention.* A call of a shared create/edit builder that CREATES names the argument: `renderXxxForm(..., existing = null, ...)`; the scanner finds such a call
outside a `collapsibleCreateForm`. Edit calls pass the row (`existing = row`), declarations spell `existing: T? = null` (a colon).

Component and scanner:

* Scanner additions of `ClientUiGuidelineTripwireTest`: (1) a section title written as a bold `div(tr("Neu ...")) { fw-bold }`, (2) any `render...Create...Form`

appears only when something is NOT saved: the last save failed, or the form differs from the last successful save (`ArticleAutoSaveController.lastSavedInput`, or
the loaded draft / the empty form when nothing was saved yet). "Verwerfen" calls `cancelPending()` once (cancels the debounce timer, never saves) and leaves;
"Weiter bearbeiten" changes nothing. A silent "discard without saving" was deliberately NOT introduced: it would be the opposite of the autosave promise. The
