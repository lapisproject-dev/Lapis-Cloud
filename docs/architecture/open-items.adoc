= Kreditoren-/Debitorenbuchhaltung — Open Items (V1.4.15)

NOTE: This document's `[kuml]` block is not rendered or validated by any Gradle task -- it is
prose documentation only, kept in sync by hand with
`lapis-server/src/main/kuml/48-open-item.kuml.kts` (the actual, load-bearing model). Same
convention `travel-expenses.adoc`/`domain-model.adoc` already establish.

Any `TREASURER`/`ADMIN` may create and settle an open item (a single payable or receivable line);
`BOARD` may read but not write. This document explains the four decisions the design team made
that depart from a naive reading of the original brief, and the reasoning behind each.

== Data shape

Five new tables -- `open_item` (one row per payable/receivable line), `open_item_netting` (one row
per pairing of exactly one payable and one receivable settled against each other),
`open_item_settlement` (one row per `PAYMENT` or `NETTING` applied to an `open_item`),
`receivable_dunning_level` and `receivable_dunning_notice` (a second, independent dunning domain,
see below) -- plus three new columns on `organization_settings` (`receivables_account_id`,
`payables_account_id`, `receivable_dunning_enabled`). See
`lapis-server/src/main/kuml/48-open-item.kuml.kts` for the full kUML model and
`V35__open_items.sql` for the migration.

== The two-booking rule

The original brief described a single booking, made "when the item is marked paid". The design
team overruled this (Jobs/Atkinson-Ruling) and requires **two** bookings:

[cols="1,2,2"]
|===
| Event | Debit | Credit

| Payable created
| `contraAccountId` (must be `EXPENSE`)
| `payablesAccountId` (must be `LIABILITY`)

| Payable settled
| `payablesAccountId`
| bank account

| Receivable created
| `receivablesAccountId` (must be `ASSET`)
| `contraAccountId` (must be `INCOME`)

| Receivable settled
| bank account
| `receivablesAccountId`

| Netting
| `payablesAccountId`
| `receivablesAccountId`

| Any reversal
| exact opposite of the original entry, as its own new `journal_entry`
|
|===

The reason is structural, not stylistic: netting two open items against each other only makes
sense once BOTH sides already exist as real accounting facts. A payable and a receivable that were
never booked have nothing for a netting entry to reference. Booking at creation also means
`contraAccountId` is a mandatory field on the creation form -- a deliberate, visible consequence of
this ruling, not an oversight.

A missing account mapping (`payablesAccountId`/`receivablesAccountId` not yet configured in
Organization Settings) degrades the booking attempt rather than failing the whole creation: the
open item is still recorded, with `creationPostingError` set to a named reason
(`payables_account_not_configured`, `receivables_account_not_configured`,
`ledger_account_inactive`, `contra_account_wrong_type`, `receivables_account_not_asset_type`,
`payables_account_not_liability_type`, `cash_voucher_required`,
`cash_register_balance_insufficient`). `retryOpenItemPosting`/`retrySettlementPosting` re-attempt
the booking once the configuration is fixed.

== Which account may be the "bank account" of a settlement (V1.4.22)

The money side of a settlement is either the account the treasurer picks in the settle dialog or,
when none is picked, `organization_settings.payment_bank_account_id`. Until V1.4.22 the dialog
offered every `ASSET` account and the server accepted whatever arrived -- so the receivables
collective account itself was selectable, and choosing it booked receivables against receivables:
balanced, posted, and meaningless (found live on staging).

`PaymentCapableAccounts` (in `lapis-shared`, so client and server share one rule) now answers
"may money be booked against this account?" with four rejection reasons: the account is inactive,
is not an `ASSET` account, is the configured receivables/payables collective account, or lies
outside SKR42 Kontenklasse 1 ("liquide Mittel" -- the only signal this chart has for "bank or
cash"). A cash register is deliberately payment-capable (paying a creditor in cash is ordinary, and
the GoBD cash guards still apply to the posting), unlike the organization-wide default mapping,
which rejects one.

The two consumers use the same rule at different strictness, on purpose:

* the settle dialog offers only accounts with no rejection at all, so a fixed-asset account is
  never presented again;
* `settleOpenItem`/`retrySettlementPosting` reject with `BadRequestException` only for the first
  three reasons (`PaymentCapableAccounts.SERVER_ENFORCED`). The account class is a chart
  convention, not an invariant this codebase owns -- refusing it server-side would break every
  organization whose bank account carries a different Kontenklasse. An explicitly chosen
  non-class-1 asset account is logged (WARN) and accepted. The configured default bank account is
  exempt from the class check entirely, and only from that one.

Four causes a treasurer can actually act on are distinct `@RpcServiceException` types instead of
`ConflictException`/`BadRequestException` messages -- `PaymentBankAccountNotConfiguredException`,
`OpenItemNotBookedException`, `OpenItemAmountExceedsOpenAmountException`,
`PaymentAccountNotPaymentCapableException`. Kilua RPC transmits only the exception type, never its
message, so a shared `ConflictException` left the client with one generic "the action conflicts with
the current state -- please refresh the view" toast for all of them, including the case where nothing
but an ADMIN configuring an account helps. `OpenItemRpcWireTest` pins that the type really does
survive the wire (a real JSON-RPC request against the full `module()`); if the KSP-generated
`registerRpcServiceExceptions()` ever stopped knowing a subclass, the client would silently fall back
to the generic toast again.

Two dead ends were closed alongside, both of which made the mapping rot unnoticed:
`deactivateLedgerAccount` refuses to deactivate an account still mapped as the payment bank,
receivables or payables account, and `updateOrganizationSettings` refuses a self-referential mapping
(bank == receivables/payables, or those two equal). The settle dialog additionally treats the default
option as valid only while that account is present in the active chart of accounts AND payment-capable,
and it offers no accounts at all while chart or mapping are unknown -- without the mapping, the
receivables account cannot be told apart from a bank account (both class 1).

=== Behaviour change: an unusable payment account is refused, not degraded

Before V1.4.22 a settlement against an inactive/missing account was RECORDED: the
`open_item_settlement` row was written, the open amount dropped, and `posting_error` was set to
`ledger_account_inactive` -- a bookkeeping fact with no journal entry behind it that somebody had to
notice and reverse. It is now refused before anything is written. This deliberately narrows
`OpenItemPostingBridge`'s "degrades instead of failing" posture for this one case (see that object's
KDoc); every other degradation, above all the `*_account_not_configured` cases of item CREATION, is
unchanged -- refusing there would mean losing the open item itself.

== Netting without four-eyes

A single `TREASURER`/`ADMIN` may execute a netting -- there is no second approver, unlike SEPA
batch submission or a large manual journal entry elsewhere in this codebase. The Jobs-Ruling
justification: four-eyes exists to protect money that *leaves the house* (a bank transfer, a SEPA
debit run); a netting moves nothing out, it only reclassifies which internal drawer an already-
booked payable and an already-booked receivable sit in.

Two safeguards replace the missing second approver:

1. **Mandatory preview** (`previewNetting`) -- writes nothing, returns the literal debit/credit
   account numbers and names, the amount, and both items' resulting open amount and status. The
   client is expected to show this verbatim before offering an execute button.
2. **GoBD-compliant reversal** (`reverseNetting`) -- never deletes or edits the original booking,
   always posts an exact opposite entry as its own new `journal_entry`. A netting can be reversed
   exactly once; `open_item_netting.reversed_at` guards a second attempt.

Double-netting the same open item under the same netting is additionally impossible at the schema
level: `uq_ois_netting_item`, a plain unique index on `open_item_settlement (netting_id,
open_item_id)`.

== Aging is always server-computed

`OpenItemDto.daysOverdue`/`.asOf` are computed server-side against `DbClock`, never re-derived by
the client -- a client-side clock/timezone drift must never disagree with which
`ReceivableDunningLevel` the server is about to escalate to. The UI shows exactly one overdue
badge (Ive-Ruling) with the exact day count in plain text next to it, never a four-color traffic
light.

In the aggregate summary (`getOpenItemSummary`), the payables total and the receivables total are
**never netted against each other** (Jobs-Ruling) -- "what we owe" and "what we are owed" answer
two different questions, and collapsing them into one number would hide which one dominates.

== A second, independent dunning domain

`ReceivableDunningService`/`ReceivableDunningPoller`/`ReceivableDunningEngine` deliberately share
no code, no table, and no configuration with the pre-existing member-contribution dunning domain
(`DunningService`/`DunningPoller`, V1.2.7, `dunning_notice`). A receivable open item is a single,
non-recurring invoice -- unlike a membership contribution, there is no "dunning cycle" concept:
`receivable_dunning_notice.cycle_number` is always `1`, and `uq_rdn_slot` on `(open_item_id,
cycle_number, level_number)` still fully guards against re-issuing the same level twice.

Three independent safeguards replace the disclaimer-acknowledgment flow the member-contribution
domain has:

* `LAPIS_RECEIVABLE_DUNNING_POLLER_ENABLED` (env, one instance only),
* `organization_settings.receivable_dunning_enabled` (DB flag, ADMIN-writable, defaults `false`),
* zero active `receivable_dunning_level` rows on a fresh organization.

A dunning fee (if configured on the level) books as its own journal entry (Debit
`receivablesAccountId`, Credit the item's own `contraAccountId`) but deliberately does **not**
increase the original item's `amount`/`openAmount` -- the fee is a separate, recorded accounting
fact (`receivable_dunning_notice.fee_amount`/`.fee_journal_entry_id`), not a retroactive change to
the frozen original invoice.

=== The enable switch governs the automatic run, not the manual single case

`organization_settings.receivable_dunning_enabled` gates `ReceivableDunningPoller` only.
`ReceivableDunningService.issueReceivableDunningNotice` (the manual, single-item override) does
**not** check it, and it books a configured fee like any other issuance. That is deliberate: a
treasurer must be able to dun one overdue invoice without switching the whole automatic run on for
the organization. But it must not be invisible -- so while the switch is off, the open-item detail
view shows a warning band on every dunnable receivable ("Forderungs-Mahnwesen ist deaktiviert; ein
manuell ausgestellter Hinweis wird trotzdem ausgestellt und eine hinterlegte Gebühr gebucht."), and
the issue-confirmation names the fee amount whenever the next level carries one.

=== What the three `OpenItemDto` dunning fields mean

`highestDunningLevelNumber`/`nextDunningLevelNumber`/`nextDunningLevelDueOn` are filled by
`ReceivableDunningEngine.loadDunningProgress`, batch-loaded per page (two queries, never one per
row -- `listOpenItems` returns up to 200 rows):

* `highestDunningLevelNumber` counts **`ISSUED` notices only**. A `SKIPPED` slot is the explicit
  record that this level was deliberately not dunned, a `CANCELLED` one was withdrawn -- showing
  either as "Mahnstufe N" would claim a notice that does not exist. It is reported for every
  receivable regardless of status, because it is a historical fact.
* `nextDunningLevelNumber`/`nextDunningLevelDueOn` describe a future action and are therefore `null`
  unless the item is still settleable -- exactly the gate `issueNextLevel` applies. Their
  "already recorded" basis is **every** notice slot (any status), because `uq_rdn_slot` blocks
  re-using an occupied `(open_item_id, cycle_number, level_number)` slot regardless of its status.
  So the announced level is always the level `issueReceivableDunningNotice` would really issue.
* `nextDunningLevelDueOn` is the item's `dueDate` plus the next level's `graceDays` -- the date the
  automatic run would reach that level, not a deadline for the manual one.

== Deferred / out of scope

* **Automatic bank-statement reconciliation.** `BankStatementMatcher` is unchanged -- its
  `MatchOutcome` carries a single `contributionId` field, all three matching strategies query
  `ContributionTable` directly. Extending it to also match against `open_item` is a structural
  change to a live core system, left for a future wave.
* **Rebuilding the member-contribution dunning domain into a polymorphic one.** `DunningService`/
  `DunningPoller`/`Dunning.kt`/`V9__dunning.sql` are bit-for-bit unchanged.
* **Default interest (§288 BGB).** Explicitly struck from scope by the design review.
* **Counter badges on dashboard tiles.** Explicitly struck from scope.
* **Dedicated counterparty master data.** `counterpartyName` stays free text, optionally linked to
  an existing `crm_contact` (V1.4.2); no new master-data entity was introduced.
* **PDF/postal dispatch for receivable dunning notices.** No `MahnungPdfGenerator` equivalent, no
  `postal_delivery_log` integration -- and therefore no compliance-disclaimer-acknowledgment flow
  either (see above): no letter leaves the building in this wave.
* **VAT/input-tax split on a payable.** Every posting this wave's bridge writes stays
  `VatRate.UNCLASSIFIED`, the same posture all six pre-existing posting bridges already have.

== Client screens (V1.4.21)

The KVision client followed in V1.4.21. Four design rulings shape it:

. **One screen, three segments.** `/open-items` (`OpenItemsScreen.kt`) shows payables and
  receivables in one list with a segmented control (all / creditors / debtors) instead of three
  screens -- same objects, same grammar. The create form has a visible, mandatory "direction"
  field that is only *pre-filled* from the segment (never in the "all" segment, so the choice is
  deliberate).
. **Three tiles plus a collapsed section.** The summary row shows at most three tiles
  (`openItemMetricTiles`), never one netted payables-minus-receivables figure. The aging buckets sit
  in a collapsed section. `openAmount` and `daysOverdue` are always the server-computed values.
. **Account mapping stays in the chart-of-accounts screen.** The receivables/payables accounts are
  two more selects (type-filtered ASSET/LIABILITY) in `LedgerScreen`'s "payment account mapping"
  section; the new screen only points there when they are missing. Along the way the wholesale-replace
  helpers of `LedgerScreen`, `PoliticianScreen` and `NonprofitComplianceReportsScreen` were fixed --
  they silently reset `receivablesAccountId`, `payablesAccountId` and `receivableDunningEnabled`
  on every unrelated settings save.
. **One netting dialog with a preview-gated button.** Candidate, amount, the mandatory server preview
  and the (inline) confirmation live in one modal. "Net" is enabled only while the *displayed*
  preview belongs to exactly the current (payable, receivable, amount) triple
  (`canExecuteNetting`); the preview is debounced.

The debtor-dunning configuration (enable/disable, level CRUD) is the ADMIN-only screen
`/receivable-dunning-settings` in the "System" sidebar group. Unlike the member-contribution
dunning screen it has no disclaimer flow (`enableReceivableDunning()` takes no argument).

Role gates mirror the server exactly: read = TREASURER/BOARD/ADMIN, everything that writes,
including `previewNetting` and `getCounterpartyDefaults`, = TREASURER/ADMIN (BOARD sees neither the
form nor any write action). A creation with a wrong-typed contra account still creates the item -- the
server only rejects it in the posting bridge (`contra_account_wrong_type`), so the UI shows "created,
but not booked" with a plain-text reason instead of a failure.

Known gaps after V1.4.21:

* No server-side status filter or search: `listOpenItems` has neither, so status, search and
  "overdue only" act on the rows loaded so far. The screen says so with "N of M loaded items", and
  adds that the summary tiles count every item while the list counts only the loaded ones.
* No PDF and no postal dispatch for receivable dunning notices.
* No assignment from bank statements (`BankStatementMatcher` is unchanged).
* No dashboard integration (counter badges stay out of scope, see above).
* No audit trail for the dunning-level configuration (`ReceivableDunningLevelSnapshot` is still
  written nowhere); levels are deactivated, never deleted.
* **Organization settings are still a wholesale replace with no optimistic concurrency.**
  `updateOrganizationSettings` replaces the single `organization_settings` row completely and carries
  no version/ETag, so a stale read can still lose a concurrent change: an ADMIN who opened the
  chart-of-accounts screen, then enabled debtor dunning in a second tab, and then saves the account
  mapping in the first tab writes that tab's stale `receivableDunningEnabled = false` back. The three
  client helpers now all go through one `OrganizationSettingsDto.toInput()` (so a field can no longer
  be *forgotten*), but that does not make a stale value fresh. Building real optimistic concurrency
  (a row version the client must echo, a 409 on mismatch) is a change to a service every screen uses
  and is deliberately out of scope here.
* **Amounts are shown in the app-wide format** (`formatMoney`, e.g. "1234.5 €" -- a house rule from
  earlier waves, unchanged here) while input accepts the German "1234,56". Input is additionally
  capped at 1.000.000.000,00 € on both sides, because `open_item.amount` is `numeric(12,2)`.
* **Every action reloads the list from page one.** After a settle/cancel/netting/dunning action the
  screen calls `loadPage(reset = true)`, so an operator who had clicked "Mehr laden" several times
  loses that chain and has to click through again. Keeping the loaded pages would mean re-fetching
  each page (the keyset cursor is per page), which this wave did not build.
