= Postgres test lane (V1.9.37)
:toc:

== Purpose

Until V1.9.36 the whole test suite ran on H2 (`MODE=PostgreSQL`). Production runs PostgreSQL. Everything that depends on the database
engine itself -- `SELECT ... FOR UPDATE` row locks, the isolation level, deadlocks, the behaviour of a transaction after a failed
statement, the real Flyway chain -- was therefore argued from reading the code, never measured. The "Known limitations" of V1.9.23 and
V1.9.30 said exactly that ("concurrency tests run on H2 only").

The Postgres test lane closes that gap: a second Gradle task, `:lapis-server:postgresTest`, runs a defined set of specs against a real,
disposable PostgreSQL, locally and in CI. It is part of `check`. The normal `test` task is unchanged and still needs nothing but a JDK.

== How it works

[cols="1,3", options="header"]
|===
| Piece | Behaviour
| `test` task | System property `kotest.tags=!Postgres`: every spec tagged `@Tags("Postgres")` is excluded (and, because of the annotation, never instantiated).
| `postgresTest` task | `kotest.tags=Postgres` plus a class filter `*Postgres*` (some legacy H2 specs touch the database in their constructor, so Kotest must not even instantiate them in this JVM). Never up to date, never read from or written to the build cache (`outputs.upToDateWhen { false }`, `outputs.cacheIf { false }`) because the external database is not a task input. `onlyIf` the variable `LAPIS_TEST_POSTGRES_URL` is present -- otherwise the task is SKIPPED. Timeout 20 minutes.
| Spec markers | `@Tags("Postgres")` and `@EnabledIf(PostgresConfigured::class)` on every lane spec (`PostgresLaneNamingTest` keeps tag and the `Postgres` class-name convention in step).
| Isolation | One FRESH database per spec: `lapis_pgtest_<16 hex>`, cloned with `CREATE DATABASE ... TEMPLATE` from a template that is migrated ONCE per JVM. Extensions, `search_path` and leftovers cannot leak between specs, and `information_schema` shows only the spec's own schema. `PostgresMigrationTest` deliberately uses an EMPTY database instead of the template (it must run the migrations itself).
| Wiring | The lane uses the same factory functions as production (`DatabaseConfig.buildDataSource`, `DatabaseConfig.flywayFor`) and its own Exposed `Database`; it sets `TransactionManager.defaultDatabase` for the duration of a spec and restores it afterwards. It never touches the `DatabaseConfig` singleton.
| Same assertions on both databases | A scenario spec is an abstract class taking a `TestDatabase`; `FooTest` passes `TestDatabase.H2`, `FooPostgresTest` (tagged) passes `TestDatabase.Postgres()`. The H2 class names are unchanged. Where H2 is only tolerant because of its 1-second lock timeout, the H2 assertion stays and the Postgres run adds a stricter one.
| Guards in every lane spec | Before every test: the Exposed dialect must be PostgreSQL and `current_database()` must be the spec's own database (catches a silent fall-back to H2 through `module()`). For concurrency specs, after every test: the server's `pg_stat_database.deadlocks` counter must not have moved.
|===

== Running it locally

Use a FRESH, disposable container bound to the loopback interface. Never point the lane at a shared or real database.

[source,bash]
----
PGPW="$(openssl rand -hex 16)"
docker run --rm -d --name lapis-pgtest -e POSTGRES_PASSWORD="$PGPW" -p 127.0.0.1:55432:5432 postgres:17
LAPIS_TEST_POSTGRES_URL=jdbc:postgresql://localhost:55432/postgres \
LAPIS_TEST_POSTGRES_USER=postgres LAPIS_TEST_POSTGRES_PASSWORD="$PGPW" \
  ./gradlew clean :lapis-server:postgresTest
docker stop lapis-pgtest
----

One spec only: add `-Plane.tests='*PollConcurrencyPostgresTest'` (an extra `--tests` would only ADD to the built-in class filter).

Without `LAPIS_TEST_POSTGRES_URL` the task is skipped and `./gradlew clean check` is green on a machine without Docker.

== Continuous integration

Since V1.9.58 the lane has its own job, `postgres`, in `.github/workflows/ci.yml` (see `ci-pipeline.adoc`). The job starts a `postgres:17`
service container (`lapis_test`, a disposable password that is not a secret) and sets the three `LAPIS_TEST_POSTGRES_*` variables on the
`./gradlew clean :lapis-server:postgresTest` step ONLY (not job-wide, never echoed). The host is `localhost` through the port mapping.
The job runs in parallel with the H2 job (`check`, which excludes `postgresTest` by name) and the browser job.

A SKIPPED task (missing variable) writes no JUnit XML and still leaves the build green. The step `Assert Postgres lane ran (not SKIPPED)`
therefore fails the job unless at least 30 XML files exist and `ElectionIntegrityPostgresTest` is among them
(`scripts/ci-assert-lane-ran.sh`).

`LAPIS_DB_URL` must NOT be set -- neither in CI nor locally. `DevSeedData`'s production guard keys off that variable, and the lane
refuses to start when it is present.

== Safety guards

The lane creates and drops databases, so it is deliberately paranoid.

* *URL whitelist* (`PostgresTestSupport.validateUrl`): prefix `jdbc:postgresql://`; host one of `localhost`, `127.0.0.1`, `[::1]`,
  `postgres`; no multi-host URL, no credentials in the URL; database name `^[a-z_][a-z0-9_]{0,62}$`; the only query parameter allowed
  is `sslmode` (with a known value) -- `socketFactory`, `sslfactory`, `options`, `loggerFile` and everything else is refused. A set but
  invalid URL is a HARD error, never a silent skip. Error messages name at most the host, never the raw value.
* *Throwaway instance check* (`checkThrowawayInstance`): the lane aborts unless `pg_database` contains only `postgres`, `template0`,
  `template1`, the URL's own database and `lapis_pgtest_*`, AND the URL's own database has no user tables. There is no escape hatch.
* *DROP guard*: `DROP DATABASE ... WITH (FORCE)` only for a name matching `^lapis_pgtest_(tpl_)?[0-9a-f]{16}$` that THIS JVM created
  itself (a `createdNames` set); the check runs before any connection is opened. A JVM shutdown hook drops whatever a crashed spec left
  behind. Names are never concatenated into SQL before these checks pass.
* *No secrets in the build*: user and password are read from the environment inside the test JVM only -- not in `build.gradle.kts`,
  not as a task input, not in the configuration cache, not in any exception text.

== Findings of the first run

Measured on PostgreSQL 17 (2026-10-02). Everything not listed here behaved exactly like H2.

. *Migrations*: all 66 apply cleanly; no migration change was needed (`V67` is NOT introduced).
. *Isolation and locks*: Exposed on Hikari + pgjdbc runs at `read committed`; every lock helper blocks and re-evaluates as the design assumes;
  zero new deadlocks across all concurrency specs, including the all-paths-at-once race on one motion.
. *Schema*: no difference between H2 and PostgreSQL. One spelling is normalized on purpose and documented in the introspection: H2 has no
  unbounded `text`, it reports `VARCHAR(1000000000)`, which is compared as `text`. A real `VARCHAR(n)` still has to match exactly.
. *`25P02` after a caught unique violation -- three production defects, fixed with a savepoint*
  (`db/Savepoints.kt`, the idiom `PaymentReferenceAllocator` and `WebhookEventPublisher` had already established inline):
  .. `EventTicketIssuer.mintWithRetry` retried a ticket-code collision on the poisoned transaction. Measured: three codes were minted
     instead of two, i.e. the retry failed and Exposed re-ran the WHOLE transaction. Invisible on H2.
  .. `FederationRelationshipStore.upsertByRemoteActorUri`: the loser of a concurrent first Follow re-read inside the poisoned transaction;
     measured: the transaction body ran twice (Exposed's hidden re-run). The outcome was right only because of that re-run.
  .. `EventRegistrationSubmission.submit`: after a unique violation at INSERT time the transaction continued with the waitlist sweep and the
     commit. Measured: the waitlist promotion made under the same lock acquisition was not committed (the registrant stayed `WAITLISTED`)
     because the poisoned transaction was thrown away and re-run. Note: with an ordinary INSERT-based race this backstop is practically
     unreachable, because the foreign-key lock on the event row queues the second registrant behind the event lock and its duplicate pre-check
     then catches the case; the deterministic test reaches it by re-activating a cancelled row with an UPDATE.
  Exposed re-runs a whole `transaction {}` after any `SQLException`, which MASKS this bug class; the tests therefore count how often the
  body ran or a side effect fired, not only the result.
. *Reviewed and left unchanged*: `DunningIssuance` (returns right after the catch; the `FOR UPDATE` on the contribution makes the collision
  unreachable), `McpMemberBlockStore`/`AiMemberOptInStore` (own transaction), and every other `catch (ExposedSQLException)` in the code base
  (they rethrow or translate to a domain exception inside the same transaction).
. *Not a defect, but worth knowing*: `recordResolution` is a free-form resolution; it is refused only while an election is running and may
  succeed any number of times afterwards. It does not decide a motion, so it is excluded from the "decided exactly once" count.

== Known limitations

* Since V1.9.55 production sets Postgres-side `lock_timeout`/`statement_timeout`/`idle_in_transaction_session_timeout`
  (see `database-timeouts-and-retries.adoc`) and the lane runs with the same defaults (`DbSessionTimeouts.DEFAULTS`); a long-held lock in
  a lane spec must stay below the lock timeout -- adjust the test, never raise the default. Exposed's automatic re-run of a whole
  transaction after an `SQLException` (default 3 attempts) still exists: the timeouts bound the wait (up to three times the lock timeout),
  and external effects inside `transaction { }` are now fenced by a source-scan tripwire instead of convention.
* Only PostgreSQL 17 is exercised. `DROP DATABASE ... WITH (FORCE)` needs PostgreSQL 13 or newer; the version is logged.
* The Postgres lane adds minutes to CI. Since V1.9.58 it runs in its own parallel job, so it no longer lengthens the H2 job (about 4 to 6 minutes of its own, plus compiling the server).
