= Mitfahrzentrale (Carpooling)
:description: Offer/request carpool postings among members, contact routed through the existing direct-message system, and the retention policy that expires a posting after its departure date.
:toc:
:toc-placement: preamble
:icons: font

NOTE: **Implementation status.** V1.9.12 built the whole feature in one wave: the `carpool_posting`
table, `ICarpoolService`, the retention poller, the DSGVO contributor, and the `lapis-client`
screen. V1.9.125 added passengers (`carpool_participation`, ten more RPC methods, a changed access rule) --
see <<access-rule-change>> and <<participations>>. V1.9.139 added a short message history per confirmed ride (<<ride-messages>>).

== Context

Every `MemberStatus.ACTIVE` member may offer a ride (`OFFER`, 1-8 free seats) or ask for one
(`REQUEST`) between two free-text places on a given date. Until V1.9.125 this was deliberately a lightweight
bulletin board: no seat reservation, no confirmation workflow, no notion of who ultimately rides with whom.
Since V1.9.125 a person can ride along on an offer and the driver confirms (<<participations>>); a `REQUEST`
posting stays a plain bulletin-board entry (nobody rides along on a search).

The sidebar entry "Mitfahrzentrale" sits in the existing `MEMBERSHIP` group and carries no
dedicated `NavVisibility` predicate of its own -- it falls under that group's existing
`showsMembershipSection` gate, the same way "Kommunikation" does, per this codebase's convention
that a route without a DIFFERING visibility rule does not get a bespoke predicate.

NOTE: V1.9.186 renamed the centre in the user interface to "Mitfahrzentrale" (client only). Identifiers, the route and the RPC names keep
"carpool"; the server-written texts (e-mails, legal text, data export below) still say "Mitfahrerzentrale" until a follow-up wave.

== Data model

[source,kuml,name="carpool-model"]
----
classDiagram(name = "Carpooling -- Model") {
    val posting = classOf(name = "CarpoolPosting") {
        attribute(name = "id", type = "UUID")
        attribute(name = "authorMemberId", type = "UUID")
        attribute(name = "type", type = "CarpoolPostingType")
        attribute(name = "fromPlace", type = "String")
        attribute(name = "toPlace", type = "String")
        attribute(name = "departureDate", type = "LocalDate")
        attribute(name = "departureTime", type = "LocalTime", isReadOnly = true)
        attribute(name = "seatsOffered", type = "Int", isReadOnly = true)
        attribute(name = "notes", type = "String", isReadOnly = true)
        attribute(name = "createdAt", type = "LocalDateTime")
        attribute(name = "updatedAt", type = "LocalDateTime")
    }

    val type = enumOf(name = "CarpoolPostingType") {
        literal(name = "OFFER")
        literal(name = "REQUEST")
    }

    val member = classOf(name = "Member") {
        attribute(name = "id", type = "UUID")
    }

    association(source = member, target = posting) {
        source { multiplicity(spec = "1"); role = "author" }
        target { multiplicity(spec = "0..*"); role = "postings" }
    }

    dependency(client = posting, supplier = type, name = "has")
}
----

`carpool_posting` (`V58__carpool.sql`, purely additive) carries no field for a precise meeting
point -- `from_place`/`to_place` are free-text place-or-postal-code strings, never a street/house
number, a deliberate scope cut recorded in the migration's own header comment. Two `CHECK`
constraints enforce shape independently of the application layer: `type IN ('OFFER', 'REQUEST')`,
and `seats_offered` is set (1..8) if and only if `type = 'OFFER'` -- a `REQUEST` row's
`seats_offered` must be `NULL`. `CarpoolPostingDto` deliberately carries no `authorMemberId` field
(see <<contact-routing>>).

== RPC surface (`ICarpoolService`)

Until V1.9.125 every method was `ORGANIZATION_MEMBER`-exclusive; since then six of sixteen are open to
the passenger statuses (<<access-rule-change>>). The guard is checked first inside every transaction, same
discipline as every other member-gated service in this codebase. The six original methods keep their
indices 0..5 on the wire (Kilua RPC numbers routes by declaration order); the ten new ones are appended:

[cols="1,3", options="header"]
|===
| Method | Behaviour

| `listPostings(type: CarpoolPostingType? = null)`
| The public feed -- only `departure_date >= today`, capped at `MAX_FEED_SIZE = 200`, ordered by
  date/time/creation. An optional `type` filter narrows to `OFFER`-only or `REQUEST`-only.

| `listMyPostings()`
| The caller's own postings, including already-departed ones not yet purged by the retention
  poller (`isPast = true`) -- lets an author still see, and re-create from, a posting that just
  fell out of the public feed.

| `createPosting(input)` / `updatePosting(id, input)`
| `CarpoolValidation.validate` re-checks every field server-side regardless of client-side
  pre-validation, then `CarpoolValidation.requireUnderQuota` enforces
  `MAX_FUTURE_POSTINGS_PER_MEMBER = 10`. `updatePosting` additionally passes its own `id` as
  `excludingPostingId` so editing a row never counts it against its own quota twice, and actively
  writes `seatsOffered = null` when a row's `type` flips `OFFER -> REQUEST` -- a plain
  field-for-field update would otherwise violate `chk_carpool_posting_seats` (see the inline
  comment at that call site).

| `deletePosting(id)`
| Author-only (`ForbiddenException` otherwise).

| `contactAuthor(postingId, message)`
| See <<contact-routing>>.

| `requestParticipation`, `confirmParticipation`, `declineParticipation`, `withdrawParticipation`, `listMyParticipations`
| V1.9.125, passenger allowlist (ACTIVE, GUEST, FRIEND) -- see <<participations>>. `listPostings` joined this list.

| `findInvitee`, `inviteParticipant`, `listParticipants`, `setMeetingNote`, `getPassengerHint`
| V1.9.125, ACTIVE only. The driver's side: exact-name search, invitation, passenger list, meeting note, and the number for the travel expense suggestion.
|===

Every write path re-derives ownership from the freshly read row rather than trusting a
client-supplied author id -- there is no such field to trust in the first place, since
`CarpoolPostingInput`/`CarpoolPostingDto` never carry one.

[[contact-routing]]
== Contact routing: an existing direct message, not a new messaging system

The Design Team's explicit ruling (Larry Tesler's line, recorded in `CarpoolService`'s own KDoc):
a client must never be able to address `contactAuthor` with a member id it read off a DTO. This
shaped two decisions at once -- `CarpoolPostingDto` carries no `authorMemberId` field at all, and
`contactAuthor` resolves the recipient itself from `postingId` alone, inside the same transaction
that validates the posting is not expired and not the caller's own.

Rather than build a bespoke carpool-messaging system, `contactAuthor` sends a normal
`DirectMessageDto` through the pre-existing direct-message mechanism -- the reply lands in the
recipient's ordinary "Kommunikation" mailbox alongside every other direct message they have. This
reuse surfaced two real gaps in that pre-existing mechanism, both closed as part of this wave
rather than deferred:

* **No client UI had ever existed for direct messages.** `DirectMessageService.sendDirectMessage`
  was reachable only via RPC/raw HTTP before this wave; the "Kommunikation" screen showed nothing
  more than a raw unread-count badge. `contactAuthor` needed a real reply surface, so the
  Kommunikation screen was extended from a bare counter into an actual message list with an inline
  reply form -- carpooling is the first feature in this codebase to give direct messages a client
  UI at all.
* **`sendDirectMessage` under-validated its input.** Before this wave, the RPC method's own insert
  path accepted an empty message body and a message addressed to oneself without complaint --
  never exercised in practice because no client caller existed yet. Building `contactAuthor`
  exposed this: `DirectMessageService.sendDirectMessage`'s insert logic was extracted into a shared
  `network.lapis.cloud.server.rpc.insertDirectMessage` helper (`DirectMessaging.kt`), used by both
  `sendDirectMessage` and `contactAuthor`, which now rejects an empty/over-length body
  (`DIRECT_MESSAGE_MAX_BODY_LENGTH = 10 000`), a message to oneself, and a recipient who is not an
  active, non-anonymized `ORGANIZATION_MEMBER` (`ConflictException` in each case) -- the same gap
  class `DirectMessageService`'s own "V0.11.0 security fix" KDoc had already closed for the
  *sender* side, now closed for the recipient/content side too. This is a deliberate, reviewed
  behaviour change for `sendDirectMessage` itself, not just new code for carpooling.

`contactAuthor` layers one further, carpool-specific check on top of `insertDirectMessage`: the
posting must still be in the future (`departure_date >= today`) at contact time, re-checked
server-side even though the public feed already filters expired postings client-visibly -- a
client could otherwise hold a stale posting id from an earlier `listPostings()` response.

[[access-rule-change]]
== Access rule change (V1.9.125)

V1.9.12 made the whole carpool centre members-only. V1.9.125 **opens exactly six methods** to a wider set,
`MemberStatusSets.CARPOOL_PASSENGER` = `ACTIVE`, `GUEST`, `FRIEND`, through its own guard
`requireCarpoolPassengerMembership` (it mirrors the conference guard: an anonymised account is refused for every status, and an unverified
`FRIEND` is refused while `LAPIS_FRIEND_REQUIRE_EMAIL_VERIFICATION` is on):

[cols="3,1,1,1,1", options="header"]
|===
| Method | ACTIVE | GUEST | FRIEND | other (APPLICATION, WITHDRAWN, ...)

| `listPostings` (offers only, no free text, for a guest or friend) | yes | yes | yes | no
| `requestParticipation`, `confirmParticipation`, `declineParticipation`, `withdrawParticipation`, `listMyParticipations` | yes | yes | yes | no
| `listMyPostings`, `createPosting`, `updatePosting`, `deletePosting`, `contactAuthor` | yes | no | no | no
| `findInvitee`, `inviteParticipant`, `listParticipants`, `setMeetingNote`, `getPassengerHint` | yes | no | no | no
|===

Why the opening is acceptable: a guest or friend can only act on **offers**, only on their **own** participation row, and sees no free text of
other people and no member name before the ride is confirmed (the feed and `listMyParticipations` send the neutral label "Mitglied"
instead; a driver's own invitation or a CONFIRMED seat reveals the name); it cannot enumerate members (there is no search for it) and cannot start anything on a posting that is not an offer. The risk
that remains is a self-registered `FRIEND` asking for rides (a driver confirms nobody they do not want). Two tripwires keep the change narrow:
`CarpoolAccessTripwireTest` pins the method list and the guard of each method, and forbids every other use of the guard and of the two sets;
`FriendDeniedEverywhereElseTest` and `FriendCapabilityBoundaryTest` name the carpool exception explicitly.

----

`carpool_participation` (`V100__carpool_participation.sql`, additive) holds ONE row per `(posting, person)` (unique index); `posting_id` is
`ON DELETE CASCADE`, `person_id` has no cascade (people are anonymised, the GDPR erasure deletes the rows explicitly). `decided_at` is set
exactly when `status <> OPEN` (a CHECK) and is the basis of the seven-day display rule and the 24-hour lock. The same migration adds
`carpool_posting.meeting_note` and widens the `audit_log_entry.entity_type` CHECK by `CARPOOL_PARTICIPATION`.

[source,kuml,name="carpool-participation-states"]
----
stateDiagram(name = "Carpool participation") {
    val start = initialState()
    val open = state(name = "OPEN")
    val confirmed = state(name = "CONFIRMED")
    val declined = state(name = "DECLINED")
    val withdrawn = state(name = "WITHDRAWN")

    transition(source = start, target = open) { trigger = "request / invite" }
    transition(source = open, target = confirmed) {
        trigger = "confirm by the other side"
        guard = "[free seat, both sides eligible]"
    }
    transition(source = open, target = declined) { trigger = "decline by the other side" }
    transition(source = open, target = withdrawn) { trigger = "withdraw (either side)" }
    transition(source = confirmed, target = withdrawn) { trigger = "withdraw (either side)" }
    transition(source = declined, target = open) { trigger = "request / invite again [after 24 hours]" }
    transition(source = withdrawn, target = open) { trigger = "request / invite again" }
}
----

*Who decides.* The initiator is `DRIVER` (invitation) or `PASSENGER` (request); only the *other* side may confirm or decline, the initiator
gets a conflict, a third party the constant not-found answer. Either of the two may withdraw.

*Lock order (everywhere): the posting row first (`SELECT ... FOR UPDATE` on the bare posting row, never on a join), then the participation row.* The
posting lock serialises every write on one ride: two confirmations cannot both take the last seat, `updatePosting` cannot undercut the
confirmed seats, two requests of one person cannot both insert (so there is no unique-violation race and no savepoint). The audit write is the
last lock-taking statement (the audit chain has one global lock). `CarpoolSeatConcurrencyScenarios` proves this with parallel requests on H2 and
on PostgreSQL.

*No enumeration.* An unknown id, a malformed id, somebody else's participation, a `REQUEST` posting and an expired ride all answer the **same**
text (`CarpoolParticipations.NOT_FOUND_MESSAGE`, never the id). `findInvitee` compares the whole normalised display name for equality (no prefix, no
wildcard), needs three characters per part, returns at most three hits, reads only `id` and `display_name`, and answers an empty list for
"nobody", "too short" and "rate limited" alike. A hit carries an opaque 128-bit token bound to the searching driver (15 minutes, in memory), never
a member id.

*Identity and verification.* The driver sees the account kind (member, guest, friend) of every search hit and participant, because a
self-registered friend chooses the display name freely and could imitate a member. While `LAPIS_FRIEND_REQUIRE_EMAIL_VERIFICATION` is on, an
unverified friend is neither found by the search nor invitable (same rule as the guard).

*Known residual risk.* Friend accounts can be self-registered (up to 500), so about 20 sybil friends can fill the 20 open-request slots of
every ride (one friend covers up to 10 rides) and block genuine requests until the driver declines them. Accepted; a smaller quota for friends
is the lever if it is ever abused.

*Limits.* At most 10 open requests per person, 20 open per ride; 24 hours before the same direction may be tried again after a decline (the
lock only covers the counter-party: whoever declines their own invitation may still ask); per-hour rate limits per member and action (20 requests,
20 invitations, 10 searches, 60 decisions) -- taken *before* the transaction.

*Notifications.* Collected inside the transaction, sent after the commit (Exposed repeats a block on `SQLException`). One generic mail purpose
`carpool-notice` (BULK lane, never starves a password reset) naming nobody and carrying no meeting point; only to `ACTIVE` members and to
`FRIEND`s with a verified address -- never to a `GUEST` (its address is synthetic) or an anonymised account.

*Audit.* Every request, invitation, confirmation, decline and withdrawal writes an `AuditEntityType.CARPOOL_PARTICIPATION` entry (participation
id, posting id, initiator, status -- no name, place or meeting note). The audit log is append-only, so these entries outlive the ride.

*Retention and GDPR.* `CarpoolRetention` deletes the participations together with a due posting (explicitly, independent of the cascade).
`CarpoolPersonalData` covers all four tables (V1.9.139 added the two message tables, see <<ride-messages>>): the export lists the person's own rides and the meeting note of their own offers, and only the *number*
of passengers per own offer -- never the name of a third person; the erasure removes the person's own rides first (their seats are released), then
their offers with everybody else's participations on them.

[[ride-messages]]
== Ride messages (V1.9.139)

A confirmed ride has a short message history that only the driver and that one person can use. It is **a narrow, deliberate exception** to the rule
that guests and friends cannot write messages: it is not the direct-message system (nothing in `CarpoolMessages` touches `DirectMessageService`,
`insertDirectMessage` or the `direct_message*` tables), and the direct messages stay members-only. `CarpoolMessageDmBoundaryTripwireTest` pins that
every method of `DirectMessageService` keeps `requireActiveMembership`.

*RPC surface.* Three methods at the END of `ICarpoolService` (routes 16, 17, 18; Kilua RPC numbers routes by declaration order):
`sendCarpoolMessage(participationId, body)` (answers the first page), `carpoolMessages(participationId, beforeId)` (a page, newest first, 50 per
page, `beforeId` is a cursor within the same history) and `endCarpoolThread(participationId)` (idempotent). They use the passenger guard like the other
six allowlist methods, and then the ONE gate `CarpoolMessages.requireAccess`.

*Access.* The caller is the driver (author of the offer, a member) or the person of a participation that is `CONFIRMED`. **Everything else is the same
not-found answer** (`CarpoolParticipations.NOT_FOUND_MESSAGE`): a malformed or unknown id, a participation that is `OPEN`, `DECLINED` or `WITHDRAWN`,
a third person (also one who rides on the same offer), a deleted ride. The access ends for BOTH sides as soon as the other side is anonymised, is no
longer eligible (a driver who is no longer an active member, a person whose status left the passenger set, an unverified friend while the verification
duty is on). So a block or a withdrawal from the organisation closes the history for both people, without a hook in the member administration.

*Order of the checks of a send* (so that nothing can be learned without access): (1) access, (2) the history has ended, (3) the text is empty,
(4) the text is longer than 1000 characters, (5) the history holds 200 messages, (6) the rate budget (ten per minute and member; counted only after
1-5 passed, outside any transaction), (7) the write under the lock on the ride, which repeats 1-5 (the limit of 200 wins a race). The text is
trimmed at its ends only; line breaks are unified, control characters (except a line break and a tab) and the bidirectional override characters are
removed, nothing is escaped (the client only creates text nodes).

*Ending.* Either side can end the history for good; after that nobody can write, reading stays possible until the messages are deleted.

*Deletion.* The messages and the thread row are deleted explicitly (the generated Exposed tables cannot express `ON DELETE CASCADE`) in the same
transaction when a participation leaves `CONFIRMED` (the person steps back, the driver removes them), when a revived participation is opened again
(safety net), when the offer is deleted, by the GDPR erasure of either side, and by `CarpoolRetention` together with the posting: that is departure
day + 8 days, at 00:00 organisation time (a change of the date by the driver moves it with the ride). If a person leaves or is blocked WITHOUT a
GDPR erasure, access ends at once (see above) and the rows follow with the retention at the latest.

*Backup exclusion.* `carpool_message` and `carpool_message_thread` are in `OrganizationSchemaCatalog.EXCLUDED_TABLES`: the data lives for days, its
deletion is promised to both people, and a restore must not bring it back or let the ADMIN-only whole-organisation backup become a way to read the
histories. A restore targets an empty database, so both tables simply stay empty. (Direct messages are permanent and therefore not comparable.)
They are not in `BLOB_TABLES` either.

*Mail.* At most one mail per history and hour (`carpool_message_thread.last_mail_at`), to the other side, only when the instance can send mail
(otherwise the throttle is not consumed). The text names no date, no place, no person and none of the message ("You have a new message about one of
your rides. Open the carpool centre to read it."); recipient rules are those of `CarpoolNotifier` (an active member, or a friend with a verified
address; never a guest).

*No audit, no logging.* `CarpoolMessages` has no logger and writes no audit entry; no exception names a text. `CarpoolMessageNoContentLeakTest`
sends a sentinel through every path and searches the log, the audit log and the mail notices for it.

*GDPR.* `CarpoolPersonalData` covers both tables. The export lists only the texts the person sent themselves (`carpoolMessagesSent`: participation id,
time, text -- the side is the person's role in that ride), never a text or a name of the other side. The erasure removes every history the person
takes part in.

*Data.* `sender_side` and `ended_by_side` are `DRIVER` or `PASSENGER`, not a member id: both parties follow from the participation, so no second
personal reference is stored. Timestamps are `TIMESTAMP` like the rest of the schema (class A, UTC).

== Retention and expiry

A posting's lifecycle has two independent cutoffs, deliberately not the same date:

[cols="1,3", options="header"]
|===
| Cutoff | Effect

| `departure_date < today`
| The posting drops out of `listPostings()` (the public feed) the day after departure, but
  **stays** in `listMyPostings()` for its own author, marked `isPast = true`.

| `departure_date < today - CarpoolRetention.RETENTION_DAYS_AFTER_DEPARTURE` (7 days)
| `CarpoolRetentionPoller` hard-deletes the row.

|===

The 7-day gap between "leaves the public feed" and "is actually deleted" exists so an author whose
own trip just departed can still see and duplicate it (e.g. to re-post the same weekly commute)
without re-typing every field, without ever showing that stale posting to anyone else.

`CarpoolRetentionPoller` and `CarpoolRetention.deleteDueRows` are a deliberate 1:1 copy of
`network.lapis.cloud.server.social.PostDraftRetention`'s pattern: always running (no feature flag,
no external secret required), `start()`/`stop()` idempotent, one `tick()` per interval (default 24
hours) wrapped in `runCatching` so a single failed run never crashes the poller loop, and a
`MAX_DELETED_PER_RUN = 5 000` cap on each run as a DoS/runaway-query guard, same as the post-draft
poller's own cap.

== DSGVO contributor

`CarpoolPersonalData` (`sectionKey = "carpool"`, `displayName = "Mitfahrerzentrale"`) exports every
posting a member has authored (`carpoolPostings`, full field set including timestamps) under Art.
15, and **hard-deletes** every one of them on erasure regardless of the requested `ErasureMode`.
This is a deliberate departure from `CommunicationPersonalData`'s handling of `direct_message`:
a direct message has a counterparty who may have an independent interest in retaining their copy
of the conversation, so that table is anonymized rather than deleted outright. A `carpool_posting`
has no such counterparty copy -- once a member is erased, nothing about their carpool postings is
kept anywhere, deliberately simpler than the direct-message case rather than mirroring it.

== Non-goals (this wave)

* (V1.9.125 added a participation workflow for offers; a `REQUEST` posting remains a bulletin-board entry.)
* No structured place data (no postal code/geocoding, no map, no distance calculation) -- `from
  Place`/`toPlace` are plain free text, unrelated to the separate Member Map feature's postal-code
  handling.
* No notification when a new posting matching a member's interest appears -- a member must check
  the feed themselves. (Participation news is mailed, see above.)
* No distance or kilometre calculation, no automatic end of a participation when a person's status changes (new confirmations are refused).
* No moderation/reporting path specific to carpool postings beyond what already exists for direct
  messages in general. The ride messages (V1.9.139) cannot be reported at all: there is no report path except for social posts.

Since V1.9.34 the "Kommunikation" mailbox also offers the conversation history below each message and an unread counter in the sidebar; see `direct-messages.adoc`.
