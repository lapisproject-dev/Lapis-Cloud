== Resolving conflicts in the comparison

Three methods were added at the END of `ILupaBbSyncService` (Kilua numbers the routes by declaration order): `applyProtectedRow`, `searchLinkTargets`, `skipRow`; the new DTO fields have defaults and stand at
the end. Every method starts with the ADMIN gate (pinned by `LupaBbSyncAccessTripwireTest`, ten methods).

* **Tamper:** the row is found in the server-side preview store by the person number; the held-back values (`PlanRow.protectedDiffs`) come from the store, never from the client. A number that is not in the preview is a
  `BadRequestException`, a foreign or expired token `LupaBbPreviewExpiredException` (a foreign guess does not burn the token). The blocker of a row (`protectedBlocker`) is only a hint for the client: the applier
  decides again under the row lock.
* **`LupaBbApplier.applyProtected`** reuses `updateMember` (mode `PROTECTED_BY_ADMIN`), so there is still exactly one call of `applyStatusChangeLocked`. Lock order: member row, then the account union
  (`PeerGuard.lockFactsAfterMemberLock`, taken once). Before the first write: own record, the transition rules, donor with a management role and the peer decision (`WRITE_PROTECTED_DATA` for the data,
  `SUSPEND` or `NON_BLOCKING_STATUS` for the status). A refusal is a `PeerDeniedSignal`, converted by `peerGuarded` after the rollback. The role is never written; `ADMIN_ROLE_MANUAL` of the bulk run is unchanged.
* **Receipt:** the `PeerNotifier` is held by `rpc/LupaBbSyncService`, not by the package `lupabb/` (the package must not touch the mail pipeline; tripwire). Sessions of a member whose status blocks the login
  are revoked after the commit.
* **Search:** the query is trimmed, 3 to 100 characters, no control characters; `LIKE` with escaped wildcards on name and e-mail, at most ten rows, only name, e-mail, status and the link flag are read (no address column).
* **Link:** `LupaBbLinker.link(row, memberId, ...)` accepts any member that is not anonymised and not linked yet (`LupaBbMemberAlreadyLinkedException`, also for a unique violation under the savepoint).
* **Skip:** the row is replaced in the store (`SKIPPED`, `SKIPPED_BY_ADMIN`) and one audit entry `LUPABB_SYNC_CONFIG` / `PREVIEW_ROW_SKIPPED` is written, without a person number. No migration: the audit entity types have
  a CHECK constraint, so no new type was introduced.
* **Sync-only transitions:** `LupaBbStatusRules.SYNC_ONLY_TRANSITIONS` = `FRIEND` -> `DONOR`, `WITHDRAWN`, `DECEASED`, each only with a matching person number.

== Title is its own field (V1.9.303)

* `LupaBbRecordParser` computes the display name as given name + family name + affix (legal person: the company), never the title; `record.title` is kept. No migration, no new environment variable.
* The one tolerance is the named function `isLegacyTitledDisplayName` (`LupaBbPlanner.kt`, `internal`, tested without a database): the Lapis display name equal to "<LupaBB title> <computed name>"
  after blank normalisation counts as unchanged. Case sensitive, against the LupaBB title only (never `member.title`, otherwise the old name would stay and the letter would read "Prof. Dr. Dr. X"), never for an
  empty title.
* `MemberIndex.byName` has a third key (the name with the LupaBB title in front), because "Dipl.-Des." leaves the token `des` behind when title tokens are stripped.
* New DTO fields, always at the end and with defaults (clients that build the DTOs positionally keep compiling): `LupaBbPreviewRowDto.conflictMemberId`, `conflictMemberName`, `conflictPersonNumber`,
  `conflictLikelyDuplicate`; `LupaBbLinkTargetDto.linkedPersonNumber`. They are set only for `EMAIL_BELONGS_TO_OTHER` with a linked holder (not for an anonymised one) and only for a member linked elsewhere,
  appear only in the ADMIN RPC answers (`getPreviewPage`, `link`, `skip`, `applyProtected`, `searchLinkTargets`), are not part of the fingerprint (`LapisMember.fingerprint()`), and never reach a log or an audit
  entry (`LupaBbLogPrivacyTripwireTest`, `LupaBbNoSecretLeakTest`).
* The "probably the same person twice" hint is decided on the server (`isLikelyDuplicate`: sorted name tokens without title tokens and particles are equal and not empty); the client only shows it.

== Hardening of the client

* Fixed host ([`LupaBbEndpoint.PRODUCTION`]); the only other accepted shape is a loopback address for the tests. The host is read from the *parsed* URL (a prefix check would let `http://localhost:80@evil/` through).
* `followRedirects = false`, `expectSuccess = false`, GET only, `Accept-Encoding: identity`, no ContentEncoding plugin, **no Ktor `Logging` plugin**; `logback.xml` floors `io.ktor.client` at INFO.
* Timeouts 10/30/30 s per request, 5 minutes for the whole fetch (`withTimeout`), 5 MiB per body (read against the cap), 200 pages, 20,000 records.
* **Every Ktor/IO exception becomes a `LupaBbFetchException(code)` without a cause.** Such an exception carries the request URL, and with the query transport the API key; the RPC layer logs the message
  and the cause chain of every exception. The typed RPC exceptions are fixed texts, too.
* The wire payload is read by hand from the JSON tree (PHP backends send numbers quoted or not); an unexpected type is `UNEXPECTED_RESPONSE` without the text of a decoder error.
* An empty answer while members are linked is `UNEXPECTED_RESPONSE`: never "everybody left LupaBB".

== Token, guard, fencing

* The preview token is 32 random bytes; only its SHA-256 is kept, compared in constant time. It belongs to one administrator, lives 15 minutes on the monotonic clock, at most two previews exist.
* The run guard is a compare-and-set on `lupabb_sync_config` (`running_since`, `run_claim`, `last_fetch_started_at`): it works across server processes. Release is fenced (only the holder of the current
  claim can release it); a claim older than 10 minutes is free. The guard is never held inside a database transaction together with HTTP.
* The apply step takes the claim, then the token, so a busy guard does not burn the preview.

== Writing

* One transaction per record. The member row is locked `FOR UPDATE` first; the Lapis side is re-read and hashed (`LapisMember.fingerprint`, covering fields, status, chapter, link, hint and the *account role*).
  A different hash than in the preview is `CHANGED_SINCE_PREVIEW`, so a role granted after the preview stops a status change.
* The status goes through `MemberRoleStatusMutations.applyStatusChangeLocked` (last-admin protection, regional-chapter rule, committee seats, mandates, photo/bio publication, member finder, history, audit) with the
  history source `LUPABB_SYNC`; the peer notification and every mail are *not* part of that function and are not called. The sessions of a member whose new status blocks the login are revoked after the commit.
* A new member is inserted under a savepoint; a unique violation (e-mail or person number taken meanwhile) becomes a fixed code, the transaction stays usable (PostgreSQL aborts it otherwise).
* Audit entries carry field keys and counters only (`MemberChangeSnapshot.lupabbFields`, `LupaBbSyncRunSnapshot`), never a value, a name or a person number.

== Tables

See `77-lupabb-sync.kuml.kts` and `V122__lupabb_sync.sql`: `member.lupabb_person_number` (unique), `member.lupabb_missing_since`, `member_lupabb_profile`, `lupabb_sync_config` (one row),
`lupabb_sync_run`, `lupabb_sync_suppression`. `lupabb_sync_config` is excluded from the organisation backup; the other three are backed up.

== Why a person number link and not `external_reference`

`external_reference` (CSV import) is free text of another source; the person number needs a unique index and a numeric check. The two stay separate.

== Voting right (V1.9.298)

`LupaBbStatusMapping.Mapped` carries the voting right a label implies (`Neumitglied` = no, `Mitglied` = yes, every other label `null` = untouched). The planner turns it into a field `VOTING_RIGHT` only when the
record carries a value, the member is neither anonymised nor deceased and the source is not `MANUAL`; a `MANUAL` value gives the reason `VOTING_RIGHT_MANUAL` instead (parameter "ours>theirs", `true`/`false`
only). `VOTING_RIGHT` is deliberately *not* in the safe subset of a protected member, so it lands in `ADMIN_ROLE_MANUAL`. The Lapis side of the fingerprint contains the value and the source, so a change by hand
between preview and apply is `CHANGED_SINCE_PREVIEW`. The applier writes through `MemberVotingRights` only and audits `votingRight = GRANTED_BY_SYNC | REVOKED_BY_SYNC` (a key, no value).
