[[scope-this-wave]]
== Scope of this wave

* `network.lapis.cloud.server.mail.newsletter.MailingHtmlSanitizer` (jsoup, allowlist-based) and
  `MailingPlainText` (derives the plain-text body from the sanitized HTML, never the other way
  round) give board-authored messages real HTML content
  (`IMailingService.createDraftMessageHtml`), alongside the pre-existing plain-text path
  (`createDraftMessage`, unchanged).
* `MailingMailRenderer` is the ONE render path both the async send and the two preview RPCs
  (`previewMailingMessage`/`previewMailingHtml`) go through -- a preview can never drift from what
  actually gets sent.
* `MailingDeliveryWorker` replaces the previous synchronous, always-simulated send with a real
  asynchronous one: `LAPIS_MAILING_DELIVERY` (`log` default, or `smtp`) decides whether
  `network.lapis.cloud.server.mail.MailTransport.send` is actually called. `sendMailingMessage` is
  now a bounded `DRAFT -> QUEUED` transition (a repeat call throws
  `network.lapis.cloud.shared.rpc.ConflictException` instead of re-queuing -- the bug this wave's
  plan calls "finding #1": the previous implementation never called any transport at all and could
  write a second full round of delivery-log rows on a repeat click).
* Recipients are filtered once, at queuing time, to active, non-anonymized, non-deceased members --
  everyone who fails that filter gets no delivery-log row at all. A syntactically invalid mailbox
  address is NOT part of this queuing-time filter: such a recipient still gets a delivery-log row
  (`PENDING`, then `SKIPPED_NO_ADDRESS` once the worker gets to it), because the address itself is
  only re-validated later, per recipient, by `MailingDeliveryWorker`.
* **Exception since V1.9.111:** a message to an *automatic* (rule-based) list gets **no** rows at queuing time. `MailingDeliveryWorker.resolveRecipientsIfNeeded`
  resolves the recipients when the worker takes the message (see link:../features/dynamic-mailing-lists.adoc[Dynamic and mandatory mailing lists]).
* Follow-up wave V1.9.15 (<<tracking>>, <<editor>>) builds everything the V1.9.7 schema was prepared for;
  it needs no new migration.

    message(from = worker, to = db, label = "load message + re-sanitize stored body_html (defense in depth) + PENDING rows")
    message(from = worker, to = transport, label = "send(to, subject, plainText, html) -- SMTP mode only, LOG mode skips this call")
    message(from = transport, to = worker, label = "Sent / Failed / Skipped")
    message(from = worker, to = db, label = "UPDATE mailing_delivery_log SET deliveryStatus=SENT|FAILED|SKIPPED_NO_ADDRESS per recipient")

}
----

== Automatic lists in the worker (V1.9.111)

For a message to a `DYNAMIC` list the worker starts with one extra step, *before* the per-recipient loop:

. **One transaction**: lock the `mailing_message` row (never a `member` row), return if `recipients_resolved_at` is already set (idempotent), parse the
  stored rule, resolve the recipients through `resolveDynamicRecipients` with the organisation's "today", insert one `PENDING` row per recipient, stamp
  `recipients_resolved_at`, write one `MAILING_MESSAGE`/`POST` audit entry (list id, rule, recipient **count**, mandatory flag -- no member id, name or
  address). The audit chain lock is the last lock of the transaction. No external effect is inside, so Exposed may retry the block.
. More than `MailingHtmlPolicy.MAX_RECIPIENTS` recipients, or an unparsable stored rule, close the message `FAILED`; nothing is queued.
. **Per recipient, just before rendering** (`prepareRecipient`): still `ACTIVE`, not anonymised, not deceased, and not opted out unless the list is mandatory --
  otherwise the row becomes `SKIPPED_UNSUBSCRIBED` (an existing literal, so no CHECK change). Automatic lists are never tracked: no token, no pixel, no rewritten link.
. `MailingMailRenderer` adds the notice of a mandatory list (subject prefix, banner, footer without an unsubscribe link) or the "Abmelden" hint of a normal automatic one.

*Recovery exception.* A `QUEUED` message of an automatic list whose `recipients_resolved_at` is empty has no rows, so "nothing pending and nothing sent" does **not**
mean "done": `finishMessageIfDone` and `recoverInterrupted` skip it (`awaitsResolution`) and the worker resolves and sends it after the restart.

== Crash recovery (D2, rewritten in V1.9.81)

Since V1.9.81 a send is **resumable and at most once** -- see link:mail-delivery-budget-and-outbox.adoc[mail-delivery-budget-and-outbox.adoc] for the full
account. In short: a recipient row is *claimed* (`mailing_delivery_log.claimed_at`) before it is sent, after its hourly budget slot was reserved.
`MailingDeliveryWorker.recoverInterrupted()` runs once at startup, before the server accepts any request:

* a `PENDING` row *with* a claim becomes the new status `INTERRUPTED` (the outcome is unknown, the mail may already have reached the relay) and is **never** sent
  again -- mailing real members twice is still treated as strictly worse than a manual re-check by the board;
* a `PENDING` row *without* a claim stays `PENDING` and is sent after the restart, exactly once; a `QUEUED` message stays `QUEUED` and the worker is woken;
* a `QUEUED` message whose rows are all final is closed: `SENT` if at least one recipient row is `SENT`, otherwise `FAILED` (`INTERRUPTED` does not count as reached).

Before V1.9.81 every leftover `PENDING` row became `FAILED` on a restart, including the recipients that had not been touched yet.

The send queue is no longer an in-memory channel of 16 message ids (which could be "saturated"): it is the `mailing_message` table, ordered by the new column `queued_at`,
and `MailingDeliveryWorker.enqueue` only wakes the worker. `enqueue` now throws `ConflictException` only when the worker has been shut down; `sendMailingMessage` then rolls
its queuing back as before.

*Retry.* A clear SMTP 4xx reply or a connection failure before anything was sent releases the claim and schedules the next attempt after 5, 15 and 60 minutes
(at most three retries; `attempt_count`, `next_attempt_at`) and pauses the whole bulk lane for 10 minutes. 5xx, authentication failures and a timeout *after* the data
transfer began are final (`FAILED`). The hourly budget (`LAPIS_MAIL_MAX_PER_HOUR`, lane BULK) holds the worker back *before* the claim.

*Display.* `mailingSendEstimate` (before sending: count, hourly budget, duration) and `mailingSendProgress` (while `QUEUED`: counts, pause with reason, ETA) -- both
BOARD/ADMIN only and limited to 60 calls per minute and member. `DeliveryStatus` gained `INTERRUPTED` (`V80` widens the `delivery_status` CHECK constraint; the unnamed
inline CHECK of `V1__baseline.sql` is dropped by its generated H2 name inside `V80`, so `V1` stays untouched and **no `flywayRepair` is needed**).

== Content model

* `mailing_message.body_text` (`VARCHAR(20000)`) -- always populated: either authored directly
  (`createDraftMessage`) or derived from sanitized HTML (`createDraftMessageHtml`).
* `mailing_message.body_html` (`TEXT`, nullable) -- sanitized HTML, `NULL` for plain-text drafts.
  `MailingMailRenderer` treats `body_html == null` as the "legacy" path: the plain-text body is
  HTML-escaped and wrapped in `<p>` tags per blank-line-separated paragraph, never raw-embedded.
* Allowlist (`network.lapis.cloud.shared.domain.MailingHtmlPolicy`, shared between server and the
  eventual client-side sanitizer): `p`, `br`, `strong`, `em`, `h2`, `h3`, `ul`, `ol`, `li`,
  `blockquote`, `a` (href only, `http`/`https`/`mailto`). No `style`, no images, no forms, no
  scripts, no iframes.

[[attachments]]
== Attachments (V1.9.232)

Mailing-list messages (manual and automatic lists alike) can carry attachments. Every recipient receives them as real MIME attachments of the mail.

*In scope:* attachments on mailing messages; upload, delete and download through dedicated HTTP routes (file bytes do not travel over Kilua RPC); the list in
`listMailingMessages` (`MailingMessageDto.attachments`, a new LAST field with a default); real attachments in every recipient mail.

*Not in scope:* direct messages (in-app only, no mail), system mails through `mail_outbox` (the outbox schema is unchanged, attachments exist only on the bulk path),
a member view or download links in the mail, choosing files that are already stored in the compose form (a follow-up). `IMailingService` has **no new method** and the
`registerService` order of `Application.kt` is unchanged.

.Limits (binary MiB, enforced on the server, mirrored in the client)
[cols="1,3"]
|===
|Files per message |5
|Size per file |10 MiB (10,485,760 bytes)
|Total per message |20 MiB (20,971,520 bytes)
|Display name |at most 120 characters, unique per message ignoring case (NFC + `lowercase(Locale.ROOT)`)
|===

.Type matrix (the extension must be on the list AND the content must match; the client `Content-Type` is never read)
[cols="1,2,3"]
|===
|Extensions |Server-chosen MIME type |Content check

|`pdf` |`application/pdf` |`%PDF-` at offset 0. An encrypted PDF is accepted; macros or JavaScript inside a PDF are not detected.
|`png`, `jpg`, `jpeg`, `gif`, `webp` |`image/png`, `image/jpeg`, `image/gif`, `image/webp` |Magic bytes; WebP needs `RIFF????WEBP` with a RIFF length that fits the file. Image polyglots are not detected.
|`docx`, `xlsx`, `pptx` |the OOXML types |A bounded ZIP parse (own central-directory reader, no `ZipFile`): the main part (`word/document.xml`, `xl/workbook.xml`, `ppt/presentation.xml`) must exist, `[Content_Types].xml` is inflated with a cap. `vbaProject.bin`, `activeX/`, `embeddings/`, `macrosheets/`, a binary main part or a `macroEnabled` content type are refused (`MACRO_OR_EMBEDDED`) -- strict: a docx with an embedded Excel chart is refused too. Encrypted entries are refused.
|`odt`, `ods`, `odp` |the OpenDocument types |The first local entry is `mimetype`, STORED, with exactly the type of the extension; `content.xml` and `META-INF/manifest.xml` exist; `Basic/` and `Scripts/` are macros; `encryption-data` in the manifest is refused (encryption is detected only through the manifest).
|`txt`, `csv` |`text/plain`, `text/csv` |No NUL and no C0 control character except TAB/LF/CR/FF; no known binary magic number; no HTML/SVG/XML markup in the first 512 bytes. Valid UTF-8 (BOM allowed) is stored with charset `UTF-8`, otherwise `windows-1252` unless one of its undefined bytes occurs.
|===

Everything else (exe, zip, html, svg, js, a name without extension) is `TYPE_NOT_ALLOWED`. Error bodies are `{"code": "..."}` with a fixed code, never free text.

*Routes* (`MailingAttachmentRoutes`): `POST /api/mailing/messages/{messageId}/attachments`, `DELETE /api/mailing/attachments/{attachmentId}`,
`GET /api/mailing/attachments/{attachmentId}/download`. BOARD/ADMIN only, checked before existence and status (no state oracle); upload and delete require a same-origin
request; uploads have their own per-member rate limiter (30 per minute). Upload and delete work in `DRAFT` only. The pre-check is a fail-fast; the authoritative check
(existence, `DRAFT`, count, total, duplicate name) runs inside the insert transaction under `forUpdate()` on the *message row* -- the row that `sendMailingMessage`'s
conditional `DRAFT -> QUEUED` update locks too -- so neither parallel uploads nor a concurrent send can slip past; an upload is either part of what the send sees or
refused with `NOT_DRAFT`. Download: the stored server type (plus charset), `Content-Disposition: attachment` (RFC 5987), `nosniff`, `private, no-store`,
`Cross-Origin-Resource-Policy: same-origin`. The storage key is `mailing/{messageId}/{attachmentId}.bin`, always generated on the server. Logs never contain a file name or key.

.Sending a mail with attachments
[source,kuml,name="mailing-attachment-send"]
----
sequenceDiagram(name = "Mailing send -- attachments") {
    val board = lifeline(name = "Board member")
    val routes = lifeline(name = "MailingAttachmentRoutes")
    val db = lifeline(name = "PostgreSQL (mailing_message_attachment)")
    val worker = lifeline(name = "MailingDeliveryWorker")
    val transport = lifeline(name = "JakartaMailTransport")

    message(from = board, to = routes, label = "POST attachment (DRAFT only, same origin, BOARD/ADMIN)")
    message(from = routes, to = db, label = "SELECT message FOR UPDATE; re-check DRAFT, count, total, name; INSERT row")
    message(from = board, to = routes, label = "sendMailingMessage -> conditional DRAFT to QUEUED (same row lock)")
    message(from = worker, to = db, label = "load attachments; check file exists, size and SHA-256 BEFORE the first recipient")
    message(from = worker, to = transport, label = "sendWithAttachments(to, subject, plain, html, attachments) per recipient")
    message(from = transport, to = worker, label = "multipart/mixed > [multipart/alternative, attachment ...], base64 streamed from disk")
}
----

*One rule set for two features (V1.9.233).* The limits, the type whitelist, the content sniffer (`AttachmentSniffer`, `AttachmentZip`), the name cleaning and the upload classification are shared with the attachments of direct messages (`AttachmentRules`, `classifyAttachmentUpload`; see `direct-messages.adoc`). Only the storage, the routes and the authorization differ. The refusal codes keep their wire names; `NOT_DRAFT` is mailing-only.

*Mail structure.* With attachments the message is `multipart/mixed` containing first the unchanged `multipart/alternative` (plain before html) and then one body part per
attachment, in upload order: server MIME type, `Content-Disposition: attachment`, the name as an RFC 2231 parameter, and `Content-Transfer-Encoding: base64` set
explicitly (otherwise Jakarta Mail would scan the whole file to choose an encoding). The bytes are streamed from disk (`FileAttachmentDataSource`), never held in the
heap. Without attachments the message is byte-for-byte the previous one. `MailTransport.sendWithAttachments` fails closed by default (`ATTACHMENTS_UNSUPPORTED`): a
transport that does not know attachments never drops one silently.

*Integrity.* At every start of a message (including a resume after a restart) the worker checks that every attachment still exists with the recorded size and SHA-256 and
was not removed by retention. If not, nothing is sent: the open rows and the message become `FAILED` (log token `ATTACHMENT_INTEGRITY`, message id only). LOG mode checks
too, but does not send.

*Relay size and volume.* Base64 makes 20 MiB about 28 MB on the wire (factor about 1.37). The operator must raise the relay limit (Postfix `message_size_limit`, default
10,240,000 bytes) to at least 30,000,000. A mail with attachments also costs transfer time and relay quota: 1,000 recipients with 20 MiB each are about 28 GB of outgoing
traffic. The hourly mail budget counts mails, not bytes. The per-send timeout is extended by the transfer time of the encoded bytes at an assumed 256 KiB/s (at most 10
minutes), otherwise a large mail would hit the 60 second timeout, which counts as a delivery of unknown outcome and is never retried.

*Retention.* The files are deleted 180 days after sending (`MailingHtmlPolicy.RETENTION_DAYS`, the period of the tracking retention) by the same daily job
(`MailingTrackingRetentionPoller`) for messages in `SENT`/`FAILED`; the metadata row (name, size, hash) stays and gets `file_deleted_at`, so the board view shows "Datei
gelöscht". Drafts that are never sent keep their files (there is no draft deletion today). `MailingAttachmentStore.deleteAllForMessageInTx` is the hook for any future
deletion of a message; a tripwire test requires every `MailingMessageTable.deleteWhere` to call it.

*Data protection.* The table is covered by the communication contributor: the uploader sees their own uploads (name, type, size, instant) in the export; the rows are
retained on erasure like `mailing_message.sent_by` (the attachment is part of the communication other members received). The table is a blob table of the organization backup;
rows whose file was removed travel as plain metadata.

*Known gaps (not detected / not verified):* no virus scanner (the UI says so); macros or JavaScript in PDFs, image polyglots and ODF encryption outside the manifest are not detected; not
verified against a real SMTP relay or real mailboxes (Outlook, Gmail, Thunderbird); members cannot download attachments (they only receive them in their mail).

[[tracking]]
== Click and open tracking (V1.9.15)

*Opt-in, default off.* A member enables "count opens" and "count clicks" independently per list
(`IMailingService.setTrackingConsent`, active subscription required). An administrator can never set
consent (`adminSubscribeMember` does not), re-subscribing starts without consent, and **withdrawing or
unsubscribing erases what was already counted for that member and list** (Art. 7(3)/17(1)(b) DSGVO).
Consent changes are audited under `AuditEntityType.MEMBER` (list id and two booleans, no PII), so no
schema change was needed.

*Token.* `MailingTrackingToken` issues `1.<nonce>.<linkIndex>.<mac>` (click) and `1.<nonce>.o.<mac>`
(open); the nonce is 16 `SecureRandom` bytes that live only in memory and in the mail, the database
stores `SHA-256(nonce)`. The MAC is HMAC-SHA256 (truncated to 16 bytes) under
`LAPIS_MAILING_TRACKING_KEY`, compared in constant time; the `c`/`o` prefix stops a click token from
working as an open token. The key is mandatory for `LAPIS_MAILING_DELIVERY=smtp` (fail-fast) and
**must stay stable: rotating it makes every already-sent tracking link answer 404.**

*Snapshot per delivery.* `MailingDeliveryWorker` renders once per recipient. It reads the recipient's
consent at send time and stores `open_tracked`/`click_tracked` plus the token hash on the delivery
row; only then is the mail rendered (links rewritten to `/m/c/<token>`, a 1x1 pixel `/m/o/<token>.gif`
before the footer). Plain-text messages, the plain-text body, the footer and `mailto:` links are never
touched, and previews never contain tracking artifacts.

[source,kuml,name="mailing-tracking-flow"]
----
sequenceDiagram(name = "Mailing tracking -- send and click") {
    val worker = lifeline(name = "MailingDeliveryWorker")
    val db = lifeline(name = "PostgreSQL")
    val mail = lifeline(name = "Recipient mail client")
    val route = lifeline(name = "GET /m/c/{token}")
    val target = lifeline(name = "Link target")

    message(from = worker, to = db, label = "read consent; store token hash and open/click snapshot on the delivery row")
    message(from = worker, to = mail, label = "mail with signed click URLs and open pixel")
    message(from = mail, to = route, label = "click: GET /m/c/token")
    message(from = route, to = db, label = "verify MAC, look up hash, resolve target from mailing_message_link")
    message(from = route, to = db, label = "count only if: not HEAD, snapshot on, consent still set, subscription active, member not anonymized")
    message(from = route, to = mail, label = "302 to the stored target (404 without Location on any failure)")
    message(from = mail, to = target, label = "follows the redirect")
}
----

*Routes.* `GET /m/c/{token}` redirects to the target stored for `(message, index)` -- never to anything
in the request, so it is not an open redirect; the target is re-validated (http/https, no control
characters, bounded, ASCII-encoded) and every failure is one identical neutral 404 without a
`Location`. `GET /m/o/{token}.gif` always answers the same 43-byte GIF (even over the rate limit, so it
is no oracle). Both are rate limited per IP (click 120/min, pixel 600/min because image proxies bundle
many recipients behind few IPs), send `Referrer-Policy: no-referrer`/`Cache-Control: no-store`/
`X-Robots-Tag: noindex`, and never log a token or target. `AutoHeadResponse` rewrites a HEAD request
to GET before routing, so the handlers read `request.local.method` to keep link scanners' HEAD
probes from counting. Counters saturate at `MailingHtmlPolicy.MAX_EVENT_COUNT` (1000) in the `WHERE`
clause.

*Statistics.* `mailingMessageStats` (Board/Admin) returns counts only -- delivered, open/click cohort,
opened at least once, per-link unique recipients and total clicks -- never an id, name or personal
timestamp. A cohort below `MIN_CONSENTS_FOR_STATS` (5) is suppressed (`null`, open and click
separately). The UI shows no percentages and labels opens an estimate (image blockers, automatic image
loading).

*Retention and DSGVO.* `MailingTrackingRetentionPoller` (every 24 h, batched) erases click rows and
resets the open data for messages older than 180 days; the token hash stays so old links keep
redirecting. `CommunicationPersonalData` exports consent timestamps, the member's deliveries and
per-link clicks (Art. 15) and deletes the click rows before the delivery log (the FK has no cascade).

[[editor]]
== Editor (V1.9.15)

The compose screen uses a `contenteditable` editor (`MailingHtmlEditor`, editing commands isolated in
`RichTextCommands`): a toolbar with nine buttons (`role="toolbar"`, roving tabindex, `aria-pressed`),
an inline link form (https/http/mailto only), Ctrl/Cmd+B/I/K, paste as plain text only, drops refused,
and a preview that shows the server's own render. No DOMPurify: the client normalizer
(`MailingHtmlNormalizer`, same allowlist and renames from `MailingHtmlPolicy`) only tidies browser
differences; `MailingHtmlSanitizer` on the server stays the authority. The server accepts at most 200
links in total (not 200 distinct ones).
