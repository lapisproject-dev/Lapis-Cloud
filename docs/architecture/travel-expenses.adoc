= Travel Expense Reimbursement (V1.4.11, PdV form V1.9.122, SEPA file V1.9.123)

NOTE: This document's `[kuml]` block is rendered and validated by the `:docs-render:renderDocs`
Gradle task (see `docs-render/`), kept in sync by hand with
`lapis-server/src/main/kuml/45-travel-expense.kuml.kts` (the actual, load-bearing model).

Any authenticated member can file a self-service travel expense report for a board/functionary
trip -- "board and functionaries" describes the real usage this wave was built for, not a
technical restriction: nothing in `TravelExpenseService` checks a caller's committee role. This
is a deliberate departure from the V1.4.10 "Beitragsvergünstigungen" wave, which has no dedicated
architecture document of its own (see link:../features/contribution-relief.adoc[that domain's own feature document]) -- the design team asked
for one here, and `bank-statement-import.adoc`/`datev-export.adoc` are the established
counter-precedent for a domain complex enough to warrant it.

NOTE: V1.9.122 ("Reisekostenabrechnung nach PdV-Formular") adds the day grid, four receipted line kinds, an advance, the payout/waiver choice, a
frozen rate set and a configurable contact person. The V1.4.11 sections below remain valid; the sections "PdV form: calculation core",
"PdV form: data and synchronisation" and "PdV form: settings, booking, DSGVO" at the end describe the delta. See
link:../features/travel-expenses.adoc[the feature document] for the rules in plain words and the list of deliberate limits.

== Data shape

Three new tables -- `travel_expense_report` (one row per reimbursement request),
`travel_expense_line` (one row per mileage/per-diem/receipted-expense line), and
`travel_expense_receipt` (one row per uploaded proof file) -- plus three new columns on the
existing `organization_settings` table (`travel_expense_account_id`,
`travel_mileage_rate_per_km`, `travel_per_diem_rate`). See
`lapis-server/src/main/kuml/45-travel-expense.kuml.kts` for the full kUML model and
`V29__travel_expense.sql` for the migration. V1.9.198 adds a fourth table, `travel_expense_attachment`
(`V113__travel_expense_attachment.sql`): report-level files such as an invitation or an itinerary, see
"Report attachments (V1.9.198)" below. V1.9.199 adds the organisation-wide `travel_expense_document`
(`V114__travel_expense_documents.sql`), see "Organisation documents and the Markdown contact hint (V1.9.199)".

== State machine

[cols="1,1,1,2"]
|===
| From | To | Method | Condition

| —
| DRAFT
| `createDraft`
| Subject active, < 10 open drafts

| DRAFT
| DRAFT
| `updateDraft`/`addLine`/`removeLine`/receipt upload/deletion
| Subject or requester

| DRAFT
| REQUESTED
| `submitReport`
| Full validation + rate freeze

| DRAFT
| WITHDRAWN
| `withdrawReport`
| Subject or requester

| REQUESTED
| WITHDRAWN
| `withdrawReport`
| Subject or requester

| REQUESTED
| REJECTED
| `decideReport(false)`
| BOARD/ADMIN, neither subject nor requester, note mandatory

| REQUESTED
| EXECUTED
| `decideReport(true)`
| + booking succeeded

| REQUESTED
| APPROVED
| `decideReport(true)`
| + booking failed -> `executionError`

| APPROVED
| EXECUTED
| `retryPosting`
| Booking succeeded

| APPROVED
| APPROVED
| `retryPosting`
| Failed again, `executionError` updated

| APPROVED
| REJECTED
| `decideReport(false)`
| Only way out of a permanently unbookable report ("no dead end")
|===

`submitted_at` is nullable (a draft is private) but is the keyset-pagination column
`listReports` orders by -- the query therefore hard-filters `submitted_at IS NOT NULL`
unconditionally, and `status = DRAFT` as a filter argument throws rather than silently returning
an empty page.

== Four-eyes, over both paths

`ContributionReliefService.decideReliefRequest` blocks only `subjectMemberId == decider`. This
wave closes the second half of that gate: `TravelExpenseService.decideReport` rejects the decider
if they are **either** the report's subject **or** its requester (`requestedBy`) -- whoever
submitted a report "on behalf of" someone else may not approve/reject it themselves either. A
different BOARD/ADMIN member always can.

== Rate configuration and freezing

`organization_settings.travel_mileage_rate_per_km`/`travel_per_diem_rate` are deliberately
**absent** from `OrganizationSettingsDto`/`OrganizationSettingsInput` -- their read path is
`ITravelExpenseService.getTravelExpenseRates()` (every authenticated member; the self-service
form needs them, but `getOrganizationSettings()` is TREASURER/BOARD/ADMIN-gated) and their write
path is `updateTravelExpenseRates()` (ADMIN). Neither carries a default: `NULL` means "not
configured," and the affected line kind is disabled in the self-service form until an ADMIN sets
it. `addLine` writes a **provisional** `rate_snapshot` from the current rate (so the running total
displays correctly while the report is still a draft); `submitReport` re-reads the rate and
**freezes** it authoritatively into every mileage/per-diem line. No code path ever reads
`OrganizationSettings` again for an already-submitted report -- a later rate change is never
retroactive.

== Booking (`TravelExpensePostingBridge`)

The first bridge in this codebase that books money **out**. Runs inside the caller's
(`decideReport`/`retryPosting`) already-open transaction, same "transaction-free by contract"
idiom `DonationPostingBridge`/`ContributionPostingBridge`/`EventFeePostingBridge` establish for
their own (income-side) bookings.

[cols="1,1"]
|===
| Side | Account

| Debit (one posting per line)
| `organization_settings.travel_expense_account_id` (must be `EXPENSE`-typed)

| Credit (one posting, the total)
| `organization_settings.payment_bank_account_id`
|===

Sphere is hardcoded to `IDEELLER_BEREICH` (Q2 in the implementation plan) -- a board/functionary
trip is practically always ideeller Bereich; revisit only if a Zweckbetrieb-funded trip ever needs
its own sphere. `posting` has no memo/description column, so the line-by-line breakdown survives
structurally as N debit postings (one per line) rather than as free text; `journal_entry
.description` carries the report id and a per-kind line count for human traceability back to
`travel_expense_line`.

**Degrades instead of failing** (returns `Failed(code)`, WARN log, no journal entry, no audit
entry, the APPROVED decision is preserved) for: `travel_expense_account_not_configured`,
`payment_bank_account_not_configured`, `ledger_account_inactive`,
`travel_expense_account_not_expense_type`, `cash_register_balance_insufficient`,
`cash_voucher_required`. The last two are a deliberate departure from the three income-side
bridges' own posture ("`CashRegisterGuard`'s guards are NOT degrading cases") -- this is the first
bridge that can ever book a CREDIT against a potential cash-register account, and a board's
APPROVE decision is a governance act that must survive a transient till shortfall; `retryPosting`
books as soon as the till has cover again. A `JournalEntryBalance.validateBalanced` failure is
**not** a degrading case (a code defect, not a state) and throws, rolling back the whole
transaction.

Idempotency: `posted_journal_entry_id` plus the plain (non-partial) unique index
`uq_ter_posted_journal_entry` guarantee at most one booking per report, on top of the application-
level status check (`retryPosting` requires `APPROVED` with a set `executionError` and no posted
entry).

== Receipt upload/download security

File bytes travel over dedicated HTTP routes (`TravelExpenseReceiptRoutes`), never Kilua RPC --
same reasoning `DocumentRoutes` KDoc gives. Security posture, mirroring that route's own
checklist:

* **Path traversal**: `storage_key` is always server-generated
  (`travel-expenses/{reportId}/{receiptId}.bin`), never derived from the client-supplied file name.
* **DoS cap**: 10 MiB, enforced while streaming, before the file is buffered.
* **MIME allowlist derived from magic bytes, not the declared `Content-Type`**: the client's
  declared type is discarded entirely. `application/pdf`/`image/jpeg`/`image/png` only --
  deliberately **no** `image/svg+xml` (a stored-XSS vector every other MIME allowlist in this
  codebase already excludes for the same reason).
* **Filename sanitization**: `original_filename` is stripped of path separators and control
  characters before it reaches the database -- pure display metadata, never used to build a
  filesystem path (a second safeguard on top of the server-generated `storage_key`).
* **IDOR on download**: enforced in the route itself, not only in the UI -- subject, requester,
  or BOARD/ADMIN only. Deliberately **not** TREASURER, the same narrower tier as the decision
  itself.
* **Header injection / MIME confusion on download**: the `Content-Disposition` filename is
  carried via RFC 5987 `filename*=UTF-8''...` percent-encoding (plus an ASCII `filename=`
  fallback), and every download response carries `X-Content-Type-Options: nosniff`. `DocumentRoutes`
  does neither today -- a pre-existing gap in that route, out of scope for this wave, flagged as a
  follow-up rather than fixed here.

== Report attachments (V1.9.198)

`travel_expense_attachment` holds files that belong to the whole report, not to one cost line. The table mirrors
`travel_expense_receipt` (server-generated `storage_key`, sniffed `mime_type`, `sha256`, `uploaded_by`), with a foreign key to
the report instead of the line. `V113` is purely additive; `V29` is not touched (its Flyway checksum must not change). Constraints:
the MIME allowlist (`chk_tea_mime`), the size range up to 10 MiB (`chk_tea_size`) and unique `storage_key`. The cap of 10
attachments per report is not a constraint; it is checked under the row lock (below). Attachments do not count against the 50
receipts of a report, and the reverse.

Routes (`TravelExpenseAttachmentRoutes`, registered next to the receipt routes with the *same* rate limiter instance, so receipts and
attachments share one budget of 30 requests per minute and member):

* `POST /api/travel-expenses/reports/{reportId}/attachments` -- 201 `{"attachmentId": ...}`
* `DELETE /api/travel-expenses/attachments/{attachmentId}` -- 204, DRAFT only
* `GET /api/travel-expenses/attachments/{attachmentId}/download`

Shared upload code. The streaming, size cap, magic-byte sniffing, hashing, file-name sanitising, the download headers and the
download rule live once in `TravelExpenseFileSupport.kt` and are used by the receipt routes and the attachment routes alike. The
receipt routes keep their HTTP codes, texts and check order (their tests are unchanged).

* **Authoritative check under a lock.** A cheap pre-check fails fast. The insert transaction re-checks everything from scratch
  with `forUpdate()` on the *report* row, the row `submitReport`, `withdrawReport` and `decideReport` lock too: existence, who is
  asking, status (DRAFT only) and the count (below 10). Parallel uploads therefore cannot exceed the cap, and an upload cannot land
  on a report that has just been submitted. Every refusal and every exception deletes the file that was already written.
* **Permission before status.** Unlike the receipt route, the attachment route checks "subject or requester" *before* the status, so a
  foreign member gets 403 and cannot learn the state of someone else's report (the receipt route answers 409 first; left as it is).
* **Immutable once submitted.** Delete and upload are DRAFT only; there is no replace route. On withdrawal or rejection the files are
  removed from disk (`deleteUploadedFilesForReport`), the rows stay as the audit trail, and the download then answers 404.
* **Download rule, one function** (`canDownloadTravelExpenseFile`): subject and requester always; BOARD and ADMIN only after the
  report left DRAFT; never TREASURER (the same rule as for receipts). Headers: `Content-Disposition: attachment` (RFC 5987),
  `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, the sniffed content type.
* **No byte quota per member.** There is none for receipts either; the limits are the counts, 10 MiB per file and the shared rate
  limit. Worst case per draft: 50 x 10 MiB receipts plus 10 x 10 MiB attachments (600 MiB), with up to 10 open drafts per member.
* **No virus scan hook** exists in the repository, so none is described or called.
* **Retention.** Keeping files is the operator's responsibility; no retention period is set here and the legal review is pending.
  The existing erasure text for receipts (above) is unchanged.

DTO: `TravelExpenseReportDto.attachments` (additive, default empty); the service loads them for a list of reports in one batch
query (four queries in total, no query per report).

== Organisation documents and the Markdown contact hint (V1.9.199)

`travel_expense_document` (`V114__travel_expense_documents.sql`, additive; `V113` is not edited, its Flyway checksum must not change) holds files that belong to the
organisation, not to a report: `title` (1..120), server-generated `storage_key`, `original_filename`, the sniffed `mime_type`
(PDF, XLSX, XLS -- `chk_ted_mime`; the column is `VARCHAR(100)` because the XLSX type is 65 characters long), `size_bytes` (1..10 MiB), `sha256`, a *nullable* `uploaded_by`
(`ON DELETE SET NULL`) and `uploaded_at`. The same migration widens `organization_settings.travel_contact_hint` to `VARCHAR(2000)`, adds
`travel_contact_hint_format` (`PLAIN` default | `MARKDOWN`) and widens the `audit_log_entry.entity_type` CHECK by `TRAVEL_EXPENSE_DOCUMENT` (23 characters).

*Deviation from the design text:* the design council specified a `content BYTEA` column. The files live on disk under `travel-expenses/documents/{id}.bin` like
every other upload of this domain (V29, V113), because the organisation export and restore hang on the `storage_key` column of the blob tables
(`travel_expense_document` joined `OrganizationExportService.BLOB_TABLES`). Timestamps are `TIMESTAMP` (not `TIMESTAMPTZ`), consistent with V113 and `DbClock`.

Routes (`TravelExpenseDocumentRoutes`, registered with the *same* rate limiter instance as receipts and attachments):

* `POST /api/travel-expenses/documents` (multipart: optional `title`, the file; either order) -- 201 `{"documentId": ...}`; BOARD/ADMIN
* `PATCH /api/travel-expenses/documents/{id}` (`{"title": ...}`, JSON content type required) -- 204; BOARD/ADMIN
* `DELETE /api/travel-expenses/documents/{id}` -- 204; BOARD/ADMIN
* `GET /api/travel-expenses/documents/{id}/download` -- any signed-in member; unknown id or missing file -> 404

Order for the upload: authentication (401) -> role (403) -> rate limit (429) -> quota fail-fast (409 `limit`) -> streaming (413, 415, 400) -> insert + audit under
a lock. Every refusal and every exception deletes the file already written. The quota of 10 is re-counted inside the insert transaction under `forUpdate()` on the
singleton `organization_settings` row, so parallel uploads cannot exceed it (a Postgres scenario covers the race). One instance has exactly one organisation, so
"another organisation's document" does not exist as a case; a random or unknown id is simply 404.

Upload code is shared, not copied: `streamSingleTravelExpenseFile` gained a `classify` callback (default: the magic-byte allowlist of receipts and attachments,
unchanged behaviour), an optional collection of text form fields and a file-name fallback. The new `TravelExpenseDocumentSniffer` runs *after* streaming on the complete file:

* *PDF*: `%PDF-` at offset 0; a `/Encrypt` token found by a streaming scan with an overlapping window -> `encrypted`.
* *XLSX*: an own, bounded ZIP central-directory parser (not `ZipFile`/`ZipInputStream`, which trust header values). Refused: ZIP64, more than 2000 entries, names over 512 bytes,
  the encryption bit, a missing `[Content_Types].xml` or `xl/workbook.xml`, a duplicated required entry. Macro parts (`vbaProject.bin`, `xl/macrosheets/`, `xl/activeX/`,
  `xl/embeddings/`, `xl/workbook.bin`) or a `macroEnabled`/`vbaProject` content type -> `macro_content`. Only `[Content_Types].xml` is ever inflated, capped at 256 KiB of *real*
  output and a 100:1 ratio.
* *XLS (OLE2)*: header and directory walk through the FAT (visited set, 128 directory sectors at most, sector size 512 or 4096). `EncryptionInfo`/`EncryptedPackage` -> `encrypted`,
  `_VBA_PROJECT_CUR`/`VBA` -> `macro_content`, no `Workbook`/`Book` stream (a `.doc`) -> `unsupported_type`. More than 109 FAT sectors are refused (no DIFAT chain).

The 415 body is one of three fixed tokens (`unsupported_type`, `macro_content`, `encrypted`), never built from input. The stored name gets the extension of the sniffed type.

Audit: `TRAVEL_EXPENSE_DOCUMENT` with `CREATE` / `UPDATE` / `VOID` (`after = null`; the vocabulary has no delete) and `TravelExpenseDocumentSnapshot` (title, MIME type, size) -- no content, no file name.
Backup: a blob table. DSGVO: the uploader link is set to `NULL` on erasure (`rowsRetained`: an organisation document is not a personal datum); the Art.-15 export lists the member's uploads as metadata only.

The rates answer carries `documents` (sorted by title) and `canManageDocuments` (BOARD/ADMIN). `uploaderName` is filled only for those two roles; `null` there means a former member.
`updateTravelExpenseSettings` and the preview stay ADMIN-only: opening the page route to BOARD must not reach the writer (a test pins it).

*Markdown hint.* `TravelExpenseContactDto` gained `hintFormat` (in and out) and `hintHtml` (out only; the server ignores it on input). `TravelContactHintMarkdown` renders through the same sanitizing pipeline as the
agreement texts (raw HTML escaped, only `http`, `https` and `mailto` links keep an `href`, images become alt text, headings shifted to h2-h4), capped at 2000 characters. The audit snapshot of the settings carries only the flag `contactHintMarkdown`.
`previewTravelContactHint` is ADMIN-only with its own 30-per-minute budget.

On the client the HTML reaches the page only through `renderAgreementBody` (the one rich site, pinned by `ClientAgreementHtmlTripwireTest`); a plain hint keeps `white-space: pre-line`, a Markdown hint uses
the modifier class `lapis-te-contact-hint--md` (`white-space: normal`), otherwise the `<br />` of the renderer and the CSS line breaks would double up.

Honest limits are in the changelog entry of V1.9.199.

== DSGVO erasure

A `DRAFT` report (or a `WITHDRAWN` report that was never submitted) has no organizational
retention interest and is deleted outright, including its lines, receipt rows, **and receipt
files**. From `REQUESTED` on, the report is a Buchungsbeleg candidate: `purpose` and every line's
`description` are redacted to a fixed placeholder, but status, every amount/date value, the
decision note, and the booking reference are retained (Art. 5(2) DSGVO Rechenschaftspflicht +
§147 Abs. 1 Nr. 4 AO, 10 years). Receipt **files** for a submitted report are never removed by
erasure -- they *are* the accounting voucher. Unlike the V1.4.10 wave's Art. 9 free-text reason,
there is no automatic redaction sweep here: there is no special-category free text to redact, and
§147 AO's retention period applies regardless of any later erasure request.

V1.9.198: report attachments follow the receipts. For a deletable report (DRAFT, WITHDRAWN, REJECTED) the attachment files and rows
are removed *before* the report (foreign key order) and reported as the erasure outcome `travel_expense_attachment`; for a
retained report both stay. The data export lists attachment metadata (name, type, size, upload time), never the bytes. The
organization backup treats `travel_expense_attachment` as a blob table: the files travel in the bundle under `blobs/` like receipts.

== PdV form: calculation core (V1.9.122)

`TravelExpenseCalculator` (`lapis-shared/src/commonMain/.../TravelExpenseCalculator.kt`) is a set of **pure functions in whole cents (`Long`) and
whole minutes (`Int`)** -- there is no `Decimal` in the core, because the browser has no exact decimal type. **The client never calculates with
code of its own**: the day grid, the totals bar and the server all call these functions; the server's result is the only one that is persisted.

* `MultiDayRule` -- the **one** place that decides how the first / last / middle / single day counts (`positionOf`, `absenceMinutes`, `travelDays`).
* `PerDiemTierRule` -- the **one** place for the tiers; inclusive ("ab"): `tierFor(minutes)` returns the highest tier whose threshold is reached.
* `MealDeductionRule` -- percentage of the *third* tier per meal, **HALF_UP on whole cents per deduction**, the sum **capped at the day's allowance**.
* `CalcResult` -- user errors are values (`CalcResult.Err(field, code)`), never exceptions. Multiplications go through `mulExact` (overflow -> error).
* Bounds: kilometers 1..5000 (whole), passengers 0..8, receipted amount 1..1 000 000 cents, 31 travel days.

Rounding is documented once and applies everywhere: half-up per deduction on cents; there is no second rounding step anywhere.

== PdV form: data and synchronisation (V1.9.122)

Migration `V97__travel_expense_pdv_form.sql` (additive; V29..V96 untouched). `travel_expense_line` gains `destination`, `day_date`, `time_from`/`time_to`
(`LocalTime`, class-B wall clock, never converted), the three meal flags, `passenger_count`, `breakfast_included`, `computed_minutes`, `base_amount`,
`deduction_amount`; `kind` widens to 16 characters and `chk_tel_kind` / `chk_tel_kind_shape` / `chk_tel_amount_positive` are recreated (a day line may be 0; every
other line stays strictly positive). `travel_expense_report` gains `advance_amount`, `payout_choice`, `membership_number_snapshot`, `rates_snapshot`.
`organization_settings` gains the tier/percentage/passenger columns (PdV-template defaults), the four contact columns and two optional account FKs.

* **One day line per (report, day) is an application rule**, not a unique index (accommodation lines reuse `day_date`; a conditional unique index is not portable
  between H2 and PostgreSQL). It is upheld by `SELECT ... FOR UPDATE` on the report row that `createDraft`/`updateDraft`/`saveDays` take before `TravelExpenseDaySync` touches
  the day lines; `TravelExpenseConcurrencyScenarios` proves it with parallel requests on H2 and on real PostgreSQL (including "no deadlock").
* `TravelExpenseDaySync.sync` is idempotent (Exposed may retry a transaction): it creates missing day lines, deletes **empty** ones outside the new period, refuses a
  filled one (`day_lines_outside_range`, 409) and normalises the times of the rest to what their position allows.
* `TravelExpenseDaySync.recomputeReport` is **the only path that writes amounts** -- live rates while a report is a draft, the frozen set at submit.

== PdV form: settings, booking, DSGVO (V1.9.122)

* **Settings**: `ITravelExpenseService.updateTravelExpenseSettings` (ADMIN) validates every range before the database, writes one ORGANIZATION_SETTINGS audit entry on an
  actual change -- the payload carries numbers and booleans **only**; the contact's name/e-mail/phone never enter the audit log (`TravelExpenseRatesSnapshot.contact*Set`).
  `getTravelExpenseRates` (every member) returns the rate set and the contact block; account ids are returned to ADMIN only.
* **Booking** (`TravelExpensePostingBridge`): debit per non-zero line; credit *bank* for `total − advance` (payout), *advance account* for the advance, *donation-waiver income account*
  for the waived amount (no money flows -- booking it against the bank would be wrong under GoBD). The bank account (and the cash-register guards) apply only when the bank is actually
  credited. New degrading codes: `travel_advance_account_not_configured`, `donation_waiver_account_not_configured`, `donation_waiver_account_not_income_type`; every posting line
  stays strictly positive, zero day lines never reach the bridge.
* **DSGVO**: the Art.-15 export carries every new field; erasing a retained (REQUESTED/APPROVED/EXECUTED) report sets `destination` and `membership_number_snapshot` to `NULL` and keeps
  times, dates, meal flags, amounts, the advance and the payout choice (Buchungsbeleg, section 147 AO). The contact block in `organization_settings` is personal data of a contact
  person **without a foreign key to `member`**: it is erased manually by the administration (clear the fields on `/travel-expense-settings`).
* **Security**: `saveDays`/`updateLine` follow the draft rules (subject or requester, no BOARD/ADMIN bypass, DRAFT only); a client-supplied cent value for a mileage line is refused (mass
  assignment); the contact hint is rendered as text, never as markup; `mailto:` is percent-encoded, `tel:` carries only `+` and digits.

* *No XML and no member IBAN in a batch table.* The file is produced inside the export transaction as pure computation and returned in the same HTTP response (`POST`, `Cache-Control: no-store`). It is deliberately
  not an RPC returning base64 and not a `GET`: a second download would have to regenerate the file and bypass the double-payment guard.
* *Transaction boundary (`TravelExpenseSepaExport.generate`).* Role check, key check, id validation and the execution date happen before the transaction; inside ONE `transaction {}`: debtor account and organization name,
  `SELECT ... FOR UPDATE` on the reports **sorted by id** (no deadlocks), blockers per report, decrypting the IBANs in memory, writing the XML (pure), inserting batch, items and marks, one audit entry per report and one for the batch. There is no
  outside effect inside the block (Exposed may repeat it on an `SQLException`); the response is written only after the commit. One clock read before the transaction keeps a repeated block identical.
* *AAD.* `"travel_expense_report.refund_iban:" + reportId` binds the ciphertext to its row; a ciphertext copied onto another report cannot be opened (`refund_iban_unreadable`). A fresh `SecretBox` state per call; no key means `409 encryption_key_missing`.
* *Amount invariant.* `total_amount − advance_amount` (exact cents, from the database) must equal the sum of CREDIT postings on `paymentBankAccountId` of the booked entry; otherwise `AMOUNT_MISMATCH_WITH_BOOKING`. There is no void status for a posted entry in this system, so a reversed booking cannot be detected here -- a reversal changes the credit sum and blocks the report the same way.
* *Identifiers (`Max35Text`).* `MsgId = "LCRT-" + 30 hex of the batch id`, `PmtInfId = "LCRTP" + 30 hex` (35 characters each), `EndToEndId = "TE" + 28 hex of the report id` plus `-R<n>` for the n-th re-export (at most 34). The
  unique index `uq_tesbi_end_to_end_id` is the database-side guarantee.
* *`audit_log_entry.entity_type`* gains `TRAVEL_EXPENSE_SEPA_BATCH` (25 characters, fits `VARCHAR(29)`); V98 widens the CHECK constraint exactly like V92. The batch entry carries ids, counts, cents, the date and the report ids -- never an IBAN or a name.
* *DSGVO.* Erasing the subject sets `refund_iban_ciphertext`, `refund_iban_last4` and `refund_account_holder` to `NULL` in every status (the organization's bank statement proves the payment; a copy of the member's IBAN is not needed); `sepa_exported_*`
  and the batch rows stay (accountability, section 147 AO) and contain no personal data. The Art.-15 export shows the masked end, the holder and the export mark -- never the ciphertext (same pattern as `PaymentsPersonalData`).
* *Tests.* `SepaPain001WriterTest` (golden file, structure, limits, escaping), `Target2CalendarTest`, `TravelExpenseSepaExportScenarios` (H2 and PostgreSQL: rights, blockers, four eyes, double export, atomicity, re-export, dates, parallel exports), `TravelExpenseRefundAccountTest`, `TravelExpenseSepaRoutesTest`, `TravelExpenseSepaMigrationTest`, the schema drift and DSGVO tests and `TravelExpenseSepaPanelDomTest`.

== Day rows: labels and the amount cell (V1.9.194)

The time fields of a day row are "Beginn der Reise" and "Ende der Reise" (single day: both; first day: the start and the fixed "bis 24:00"; last day: the end and the fixed
"ab 00:00"; middle day: "ganztägig (24 Std.)"). One hint on the end field says what it means ("Rückkehr oder Ankunft; bei einer einfachen Fahrt die Ankunft am Ziel"). Both
fields are marked as required (marker and `aria-required`), but **saving is not blocked** by an empty time: it still means "no allowance that day" and the calculator is
unchanged. The "Ende before Beginn" check on a single day keeps its message.

The day amount is shown in two lines in the right-hand cell, never cut: "Tagesbetrag: ..." and, only when the day has a result, "(Abzüge: ...)" below it. The numbers come from the
shared calculator as before.
