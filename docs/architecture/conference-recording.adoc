= Conference recording: composition, layout, sync, repair, recompute, per-person egress and the speaker view (V1.9.107, V1.9.109, V1.9.110, V1.9.115)
:toc:

NOTE: This document's `[kuml]` block is rendered and validated by the `:docs-render:renderDocs` Gradle task.

== Purpose

A conference recording is captured as raw files (one per person with LiveKit Participant Egress, the default since V1.9.116, or one per track with Track Egress), then composed into one MP4 by `ffmpeg` (`FfmpegSegmentedComposer`, driven by `RecordingPoller`).
V1.9.107 fixes a composition that never ended on a real recording and adds a moderator action to repair a recording whose composition failed.
Operating context: the ELB recording `bacce4ae-a65c-4f3d-9266-33fcfd309e25` (68 minutes) stayed `FAILED` although all raw files were on disk; `ffmpeg` 8 aborted with `-shortest` when
the audio ran far ahead of the video, and the video chain ran for about 8000 s instead of 4100 s.

V1.9.109 replaces the one-big-filter-graph composition by a *segmented* one (a new layout that follows who is actually in the picture, A/V sync that holds over a long meeting) and adds "Neu berechnen":
a moderator can compose a READY recording anew from its raw tracks. Both are described below; the section marked _(V1.9.107)_ describes the retry, which the new composer keeps.

V1.9.110 adds a second way to capture the raw files, *Participant Egress* (the default since V1.9.116) (one file per person with audio and video on one clock), because Track Egress cannot keep a person's audio and video in sync; see <<Participant egress mode (V1.9.110, default since V1.9.116)>>.

== State machine

[kuml, conference-recording-states, svg]
----
stateDiagram(name = "Conference recording") {
    val start = initialState()
    val recording = state(name = "RECORDING")
    val stopping = state(name = "STOPPING")
    val processing = state(name = "PROCESSING")
    val ready = state(name = "READY")
    val failed = state(name = "FAILED (failure_code)")

    transition(source = start, target = recording)
    transition(source = recording, target = stopping) { trigger = "stopRecording, room ended, maximum duration" }
    transition(source = stopping, target = processing) { trigger = "all tracks terminal, or egress timeout with a video track" }
    transition(source = stopping, target = failed) { trigger = "NO_TRACKS, EGRESS_TIMEOUT" }
    transition(source = processing, target = ready) { trigger = "composition archived" }
    transition(source = processing, target = failed) { trigger = "NO_TRACK_STORED, COMPOSE_FAILED (attempts exhausted)" }
    transition(source = failed, target = processing) {
        trigger = "retryRecordingComposition / recomputeRecording (moderator): attempts = MAX - 1"
        guard = "[failure_code = COMPOSE_FAILED, raw files present]"
    }
    transition(source = ready, target = ready) {
        trigger = "recomputeRecording (moderator): recompute_started_at set, new document version, marker cleared"
        guard = "[raw files present, no recompute running]"
    }
}
----

`conference_recording.failure_code` (V87) says why a row is `FAILED`: `COMPOSE_FAILED`, `EGRESS_TIMEOUT`, `NO_TRACKS`, `NO_TRACK_STORED`. It is only set while the status is `FAILED` (CHECK) and is written together
with the fixed German `failure_reason` text by `RecordingPoller.markFailed`. The client renders its own text per code and never the server's `failure_reason`.

A READY recording that is being recomputed is still READY: `recompute_started_at` (V89) is a sub-state of READY, see <<Recompute>>.

== Edit decision list

`RecordingEditDecisionList.build(tracks, totalSeconds, fps, canvasW, canvasH)` is pure arithmetic: it cuts the output into *segments of constant layout*.

[kuml, conference-recording-composition, svg]
----
activityDiagram(name = "Segmented composition") {
    val start = initialNode()
    val probe = action(name = "ffprobe packet ranges per track (video gap >= 1.0 s, audio gap >= 0.5 s)")
    edge(from = start, to = probe)
    val edl = action(name = "edit decision list: cut points, visible tracks, shared best-fit grid, stable slots")
    edge(from = probe, to = edl)
    val remux = action(name = "remux every raw file once (-c copy -copyts, Matroska with an index)")
    edge(from = edl, to = remux)
    val video = action(name = "per segment: video segment (seek, fps, scale, overlay, x264, no B-frames)")
    edge(from = remux, to = video)
    val audio = action(name = "per segment: audio segment (sample-exact PCM, amix, limiter)")
    edge(from = video, to = audio)
    val more = decision(name = "more segments?")
    edge(from = audio, to = more)
    edge(from = more, to = video, guard = "yes")
    val mux = action(name = "concat without re-encoding, audio to AAC once, MP4 +faststart")
    edge(from = more, to = mux, guard = "no")
    val verify = action(name = "ffprobe: video and audio stream, duration within 1 s")
    edge(from = mux, to = verify)
    val switch = action(name = "first composition: archive document; recompute: new version, switch current version in ONE transaction (fenced)")
    edge(from = verify, to = switch)
    edge(from = switch, to = finalNode())
}
----

*Cut points* are every start and end of a track's data range, rounded to an *absolute* frame (`round(t * fps)`, never a sum of rounded lengths, so the segments always add up to the total), plus 0 and the last frame, plus a forced cut every
`MAX_SEGMENT_SECONDS = 120`. The forced cuts are what gives the promise "a mistake never grows beyond the end of its own segment" a meaning for a 70 minute meeting in which nobody joins or leaves. Segments shorter than
`MIN_CUT_FRAMES = 2` are merged into their predecessor (the first one into its successor); if a flapping camera still produces more than `MAX_SEGMENTS = 1500` segments the minimum length doubles until it does not, with a warning in the log.

*Visibility.* A track is in a segment when one of its ranges covers the middle of the segment. There is no grace period: whoever switches the camera off and on within a second leaves and re-enters the layout (a data gap of less than the threshold
does not count at all). A muted LiveKit track does not end, it stops sending, so the layout is derived from the *data* (`RecordingMediaProber.probePacketRanges`: `ffprobe -show_entries packet=pts_time,duration_time`, parsed as a stream, at most 5 million lines and 120 s),
not from the file's start and end.

== Grid and slots (shared with the live view)

The grid is the live call's own function. `computeConferenceTileGrid` (V1.9.92) moved from `lapis-client` to `lapis-shared` (`network.lapis.cloud.shared.conference`), and the recording calls it with `gap = 0`, no hysteresis and no minimum tile width;
the live view passes its 8 px gap, 160 px floor and previous column count explicitly. Every column count is tried, the largest 16:9 tile wins, a tie goes to fewer empty cells and then to *more* columns (V1.9.109; with a gap of 0 and a 16:9 area, 2x1 / 1x2, 3x2 / 2x3
and 4x3 / 3x4 are equal; the live view with its 8 px gap is not affected, `TileGridTest.liveView_withTheGap_isNotAffectedByTheTieRule`). Only the algorithm is shared, no BigBlueButton code is used.

At 1920 x 1080: 1 person 1x1, 2 people 2x1, 3-4 people 2x2, 5-6 people 3x2, 7-9 people 3x3, 10-12 people 4x3, 13-16 people 4x4.

`gridCellRects` places the cells (gap 0, the largest 16:9 cell that fits, even sizes for yuv420p, the block centred, an incomplete last row centred on its own); `assignSlots` keeps a picture in its slot while the shape stays the same
(a new picture takes the lowest free slot, a changed shape redistributes in first-seen order). With a screen share the share that started LAST (V1.9.115; before: the earliest one -- the rule of the live view) is shown large in the upper 72 % of the canvas and the other visible tracks in one row below it (`singleRowGrid`).

== Layouts: grid, speaker large, screen share (V1.9.115)

A moderator chooses in the "Moderation" disclosure of a running call how recordings (and the pre-selection of the stream dialog) show the room: *Raster* (`RASTER`, the grid above, the default) or *Sprecher groß* (`SPEAKER`).
The setting is stored on the room (`conference_room.broadcast_view`, `IConferenceModerationService.setRoomBroadcastView`, same authority and the same single `ForbiddenException` for every refusal as the audio policy, no LiveKit call, audit entry with metadata only) and applies from the NEXT recording. **When a recording starts the room's setting is frozen on the recording** (`conference_recording.broadcast_view`, written in the transaction that holds the room row lock): a later change of the room does not touch a running recording, a recompute uses the frozen view, and the notice banner names it ("... aufgezeichnet. Ansicht: Raster." / "Ansicht: Sprecher groß.").

*Speaker large* on the 1280 x 720 canvas: the speaker's picture 1024 x 576 on top (80 % of the height, centred), below it a strip of up to five thumbnails of 256 x 144 (`speakerLayoutRects`, all coordinates even for yuv420p, `lapis-shared`). The output resolution did not change (720p). The strip holds the most recent speakers whose picture is visible (newest first), then the others by first appearance; with more than six visible people the layout cannot show everybody.
Per segment (`RecordingEditDecisionList.build(..., layout, speakerSpans)`): a visible screen share always wins (the share that started last is large, the layout above); otherwise the speaker of the span that covers the middle of the segment is large if that person has a visible picture, else the grid is shown (before the first span, a speaker without a camera picture, fewer than two pictures). The boundaries of the speaker spans are cut points too, so the large tile changes on an exact frame. Audio is unaffected (a complete mix).

== Speaker timeline (V1.9.115)

*Where it comes from.* LiveKit reports speaker changes only to the browsers (there is no webhook and no server API for it), and a report from one person's browser could be forged. The server therefore derives the timeline when the recording is composed, from the *recorded microphone audio*: one `ffmpeg` run per audio file (`FfmpegSpeechActivityAnalyzer`: `aresample=16000`, `asetnsamples` windows of 100 ms, `astats` RMS, printed with `ametadata` to stdout; stdout is read with a line and byte cap and a hard timeout, nothing of it reaches a log or an exception). `SpeechActivity.detect` calls a window speech when its level is above `max(noise floor + 15 dB, -50 dBFS)` (noise floor = the 10th percentile of the file itself); the windows are placed on the wall clock with the *same* offset and `atempo` ratio as the composer uses for the sound (`AudioWallClock`, one function used by both -- pitfall: otherwise the large tile and the voice drift apart). `RecordingSpeakerTimeline.build` samples the people on a 100 ms grid (loudest first) and runs the *same* smoothing as the live view (`smoothSpeakerTimeline`: 800 ms claim, 2 s dwell, 1.5 s gap bridging, silence holds). The recording only has data for the time it was recorded, so there is nothing to ask for "during recording only".
In TRACK mode the audio inputs are the MICROPHONE tracks, in PARTICIPANT mode the audio stream of the person file; the sound of a screen share is not speech. Measured on this development machine (Apple silicon): 30 minutes of audio analysed in about 1.5 s per file (a synthetic tone; real speech decodes at the same speed). The analysis runs before the composition and is not part of its timeout.

*Persons are opaque.* A person is identified by the id of their first track row (the first CAMERA row, else the first MICROPHONE row), never by an identity or a name. The composer, the edit decision list and the stored rows only ever see that id.

*Stored once, reused.* The smoothed spans are stored in `conference_recording_speaker_span` (V94: recording, track row, `start_ms`, `end_ms`; `ON DELETE CASCADE` on both foreign keys), `conference_recording.speaker_timeline_computed` marks it. `RecordingSpeakerTimelineStore` is the only reader and writer (a tripwire pins that); a recompute reads the stored timeline and does not analyse again -- except for a recording whose person file needs the drift correction (V1.9.154, see <<participant-composition>>): then it is analysed again in corrected time and replaced, falling back to the stored one if the analysis is impossible.
*Failure is not failure.* If the analysis is not available or fails, that composition falls back to the plain grid and the recording still ends READY (warning with counts only).

=== Privacy: speaker timeline

* It is derived only from audio that was recorded, and it carries no name and no identity: only offsets and the id of a track row of this recording.
* It lives exactly as long as the raw files: `RecordingPoller` deletes it where it deletes the raw files after a successful composition (with `LAPIS_RECORDING_KEEP_RAW=false`), `ConferenceRecordingService.deleteRecording` deletes it with the recording, and the foreign keys cascade as a second line of defence. A FAILED recording keeps its raw files and so its timeline.
* It is exposed through no API: no DTO, no RPC, no route (`ConferenceRecordingDto` only carries the frozen `broadcastView`). A tripwire (`SpeakerTimelineAccessTripwireTest`) also fails the build if a shared DTO or RPC mentions it, if another class touches the table, or if a log line of the analysis, the timeline or the composer's speaker layout names an identity, a file name or a path.
* It is excluded from the organization backup (`OrganizationSchemaCatalog.EXCLUDED_TABLES`), because the backup exports every table otherwise.
* It is **not** part of the personal-data export of Art. 15 GDPR: it is short-lived, has no foreign key to a member and is deleted with the raw files. (Decision recorded here; to be confirmed with the data-protection owner.)

=== Limits of the speaker timeline

* *Loudness is not speech.* A cough, a bang, a loud neighbour or a person talking over a speaker without headphones counts as speech; a person whose microphone is very quiet (below -50 dBFS) never does.
* Browser noise suppression changes the levels; the floor is measured per file, so a consistently quiet room works, a room with a fluctuating floor may not.
* Several people speaking at once: the one holding the large tile keeps it while they speak; the loudest takes it only when nobody holds it.
* A speaker without a camera picture shows the grid for that stretch, not the person's initials.
* Over six visible people the strip cannot show everybody.

== Streams (RTMP) -- what is and is not different

Nothing changes on the server for streams: `startStream` stores the layout it is given, as before. The start dialog pre-selects `GRID` for *Raster* and `SPEAKER` for *Sprecher groß*; every layout can still be chosen. LiveKit's own template (`grid` / `speaker`) does the arrangement and the switching, **not** our 2 s smoothing; whether that template shows a shared screen large is not verified (there is no test against a real LiveKit here). There is no "pinned person with a strip" in a stream (only `SINGLE_PARTICIPANT`, one person without a strip). The setting applies from the next stream start; pausing and resuming keep the layout of the row.

=== X (V1.9.131)

`X` is a platform of the destination list like `YOUTUBE` or `GENERIC_RTMP`; on the server it is exactly `GENERIC_RTMP` with a different stored value. `createDestination` validates the URL the same way (`rtmp://` or `rtmps://`, loopback and link-local rejected), the key is stored encrypted and never returned, and `startStream` builds `<rtmpUrl>/<streamKey>` like for every platform. There is no server branch for X; the migration `V103` only widens the CHECK constraint on `conference_stream_destination.platform`.

* *Where to get the data.* Server URL and stream key come from X's Media Studio, under "Producer".
* *The key can change.* X may issue a new key for every broadcast. The edit dialog of an X destination says so; the key is entered again there (write-only, never shown).
* *No prefilled URL.* The ingest address of X is not reliably known, so the field stays empty (placeholder `rtmps://...`) and the create dialog only shows a hint. Switching the platform in the create dialog replaces or clears a *preset* address of another platform, but never a value somebody typed.
* *Tested with X on 2026-10-14 using the *Single person* layout only; other layouts, long-running streams and picture quality are untested.* The grid ("Galerie") and speaker ("Sprecher") layouts use the LiveKit web template and are not tested with X.

== Per-segment composition and A/V sync

`SegmentArgumentBuilder` (pure, `SegmentArgumentBuilderTest`) builds one `ffmpeg` run per segment and stream; `FfmpegSegmentedComposer` runs them one after the other (`FfmpegProcessRunner`: argument list only, no shell, stderr only in the log, timeout and
`destroyForcibly`). Each video and audio run has its own timeout and, since V1.9.155, up to three attempts (see <<Hanging ffmpeg runs (V1.9.155)>>); every run is additionally bounded by what is left of `LAPIS_RECORDING_COMPOSE_TIMEOUT_MINUTES` for the whole composition.

*Video.* A black `color` source of exactly the segment's frames, every visible track seeked (`-ss` before `-i`, on the remuxed file), `fps=...:start_time=0` (a picture that arrives a fraction of a frame late is not a black frame),
`scale` + `pad` into its cell, `overlay=eof_action=repeat`. Every segment is encoded with identical parameters (`libx264 -preset veryfast -crf 23 -profile:v high -g 60 -bf 0`): closed GOPs and *no B-frames* make the lossless join free of DTS overlaps
(the files are 5-10 % larger). The segments are MP4, not MPEG-TS: `ffprobe`, and with it the `concat` demuxer, cannot open a two- or three-frame MPEG-TS written by x264 (found by the sync test with a 2-frame first segment).

*Audio.* Each segment is rendered to PCM WAV, never to AAC: AAC per segment would add the encoder priming delay (about 21 ms) at every seam. The segment holds exactly `frames * 48000 / fps` samples (1600 per frame at 30 fps), counted with `atrim=end_sample` and
`apad=whole_len`, never in seconds, so rounding cannot accumulate. Every source contributes one input per data range that overlaps the segment (`-ss`, `-t`, `aformat` to 48 kHz stereo, `aresample=async=480:first_pts=0`, `adelay=<samples>S`);
without any input the segment is silence (`anullsrc`). The mix is `amix=normalize=0` followed by `alimiter=limit=0.891:attack=0.1:level=0`. The limiter's default 5 ms look-ahead would delay every segment by 240 samples against the video, so the attack is the minimum
(0.1 ms, measured: 3 samples). The audio is encoded to AAC *once*, in the final mux.

*Remux with `-copyts`.* LiveKit's WebM/OGG files have no cue points, so every `-ss` would scan from the file's start (quadratic I/O). Each raw file is therefore remuxed once with `-c copy` into Matroska. `-copyts` is essential:
OGG is a format with timestamp discontinuities, and without it `ffmpeg` closes every gap of more than 10 s in the file's own timeline (a muted microphone) by shifting all later packets, so the data ranges would no longer match the audio.
Ranges are relative to the first packet of the stream, which is what `ffmpeg`'s own `-ss` is relative to.

*`atempo`.* A microphone's media can be a little shorter than the wall-clock span it covers (sender clock drift). `AudioTempo.ratioFor(media, wall)` stretches it only when `0.95 < media / (wall - 0.4 s) < 0.997` *and* `wall - media > 1 s`: the reported wall duration contains
the egress's EOS flush tail of 0.1 to 0.4 s (see `RecordingTrackAlignment`), which must not be mistaken for drift. A corrected track is followed by `asetpts=N/SR/TB`.

*Bounded without `-shortest`* (V1.9.107, since `ffmpeg` 8 aborts with it when the audio runs far ahead of the video): every video segment has an exact frame count (`color=...:duration` and `-frames:v`), every audio segment an exact sample count, so the total is exactly `round(total * fps)` frames. An invalid spec (no video track, a duration that is not finite and positive) becomes a `RecordingComposeException`, so the poller's usual failure path applies and the raw files stay.

*Verification.* The finished file is probed (`RecordingMediaProber.probeOutput`): a video and an audio stream and a duration within one second of the expected length, else `RecordingComposeException("output verification failed")` and the usual failure path.
If `ffprobe` cannot be run the verification is skipped with a warning.

*What the sync test proves* (`RecordingSyncIntegrationTest`, real `ffmpeg`, LiveKit-like WebM/VP8 and OGG/Opus inputs with their own timelines): a beep in the microphone and a one-frame flash in a camera are the same wall-clock event every 10 s; in the composed
file both are within 150 ms of their nominal time and of each other (measured: within 1 ms for the beeps and exactly on the frame for the flashes), the frame count is exactly `round(total * 30)`, in four cases: base (cameras joining and leaving, forced cuts), a drifting microphone
(`atempo`), a camera that lost every 20th frame, and a 20 s hole in the microphone's timeline. Length: `LAPIS_RECORDING_SYNC_TEST_MINUTES` (default 6), directory `LAPIS_RECORDING_SYNC_TEST_DIR`.
The 70 minute proof was run by hand on 2026-10-11 (case base, 640 x 360, `LAPIS_RECORDING_SYNC_TEST_MINUTES=70`): passed, 4200.0 s, exact frame count, 121 MB, 3 min 7 s including the generation of the inputs.

=== Hanging ffmpeg runs (V1.9.155)

*Finding (2026-10-17).* In the six-camera segments of recording bacce4ae (171 segments) the video run of a segment sometimes did not end and was killed by its timeout. Observed outside the server on the production `ffmpeg` 8.0.1: one input alone runs in about 0.5 s; six inputs together hung in about half of the runs (10 of 20); threading options did not help; with every input bounded by `-t` about 1 of 20 hung. `compose_attempts` above 1 on bacce4ae (5), staging c13166f4 (2) and ELB cc27c031 (2) fits this. Upstream reports about `overlay` / `filter_complex` hanging when inputs differ in length (FFmpeg tickets 6292, 6458, 6854) point the same way (inputs without an end block the overlay queue); this is a theory, not a proof.

*Measures.*

* Every video input gets `-t <segment length - tpad lead + 0.5 s>` right after its `-ss` and before its `-i` (`VIDEO_INPUT_TAIL_SECONDS`). `tpad` supplies the first `lead` seconds itself, so the picture is unchanged; a source that ends early is still held by `eof_action=repeat`.
* A video or audio run that exceeds its limit (a `RecordingComposeTimeoutException`, thrown only by the timeout branch of `FfmpegProcessRunner`) is killed and started again, at most three attempts: attempts 1 and 2 get `max(30 s, 3 x segment length)` (a healthy run takes about 0.3 x), the last one the old `max(60 s, 4 x segment length)` so that a slow host is not mistaken for a hang. The half-written segment file is removed before a retry.
* *Only a timeout is retried.* A non-zero exit, a start failure and a cancellation are passed on at once. Remux and the final mux keep a single attempt (one input each, never seen hanging).
* The overall `LAPIS_RECORDING_COMPOSE_TIMEOUT_MINUTES` stays binding: when it is used up no further attempt starts.
* Log lines name only the step ("video segment 12/171") and the attempt, never a path or a name.

*Measuring tools.* `FfmpegSegmentStressTest` (off unless the test variable `LAPIS_RECORDING_STRESS_RUNS` is set; `LAPIS_RECORDING_STRESS_TIMEOUT_SECONDS` sets the per-run kill time; both are test variables, the server does not read them) runs the six-camera command in the variants old / production / canvas bounded by `-t` / `-thread_queue_size` / without `eof_action=repeat` / audio, and checks that the production command decodes to the same frames as the old one. `scripts/recording-segment-stress.sh` mirrors the old and the production command with `bash` and `ffmpeg` only, to measure inside the production image.

*Measured with synthetic inputs (2026-10-17), 20 runs per variant, six VP8 cameras, 184 frames:* no hang in any variant, neither with ffmpeg 9.0.2 (macOS, Homebrew; all variants) nor with ffmpeg 8.0.1-3ubuntu2 in the production base image (`eclipse-temurin:25-jre` plus the Ubuntu `ffmpeg` package, arm64; old and production command). The hang was therefore *not reproduced* here; the synthetic cameras lack the real LiveKit timestamps and gaps. The mean run time was 0.33 s (old) against 0.34 s (production).

== Participant egress mode (V1.9.110, default since V1.9.116)

=== Problem

Track Egress writes every published track into its own file, and nothing synchronises those files with each other: LiveKit's Track Egress has no RTCP sender-report (SR) synchronisation between audio and video.
Measured on the ELB recording `d08d4205` (2026-10-11): a hand clap is in the audio at 277.0 s and in the raw video at 282.3 s, an offset of 5.3 s that no later step can reconstruct.
Existing recordings made in this mode are therefore not repairable; a recompute re-uses the very same raw files.

In the default mode (`participant`) the server records every person with `StartParticipantEgress` and an `EncodedFileOutput` instead: LiveKit's SDK pipeline muxes the person's microphone and camera into ONE MP4 on one pipeline clock.

[kuml, conference-recording-participant-mode, svg]
----
activityDiagram(name = "Participant egress mode") {
    val start = initialNode()
    val list = action(name = "tick: ListParticipants of the room")
    edge(from = start, to = list)
    val gone = action(name = "person gone (SID no longer in the room): ONE StopEgress, refresh the row from ListEgress")
    edge(from = list, to = gone)
    val person = decision(name = "person")
    edge(from = gone, to = person)
    val startFile = action(name = "StartParticipantEgress, MP4 file p-<row uuid>.mp4; row egress_kind = PARTICIPANT, track_source = CAMERA, livekit_track_id = participant SID")
    edge(from = person, to = startFile, guard = "camera or microphone track, participant SID unknown")
    val share = decision(name = "share")
    edge(from = person, to = share, guard = "otherwise")
    edge(from = startFile, to = share)
    val trackEgress = action(name = "StartTrackEgress as before; row egress_kind = TRACK")
    edge(from = share, to = trackEgress, guard = "screen share track not yet recorded")
    edge(from = trackEgress, to = finalNode())
    edge(from = share, to = finalNode(), guard = "otherwise")
}
----

=== What is decided, and why

* *Default since V1.9.116, fixed per recording.* `LAPIS_RECORDING_EGRESS_MODE` is `participant` (default when blank) or `track` (trimmed, case-insensitive; anything else is the default `participant` plus one warning). Until V1.9.115 the default was `track`; the database column default `TRACK` of V90 is unchanged (the application always writes the mode explicitly). The mode is written to `conference_recording.egress_mode` (V90) when the recording starts. A server
  restart with another value never changes a running recording: a person would otherwise have a Participant Egress AND per-track egresses, i.e. doubled audio.
* *A separate column instead of a new `track_source`.* `conference_recording_track.egress_kind` (`TRACK`/`PARTICIPANT`, V90) marks a person file. The CHECK constraint on `track_source` is unnamed in V1; Postgres names it automatically, H2 generates its own name, so the usual
  `DROP CONSTRAINT IF EXISTS` pair cannot remove it on H2. For a person file `track_source` is `CAMERA` (the picture's main source), so `rawFilesAvailable`, the egress timeout and every "has video" check stay valid; `livekit_track_id` holds the participant SID (`PA_...`).
* *The path never contains the identity.* `RecordingEgressPaths.participantFile` builds `<container dir>/<recording uuid>/p-<row uuid>.mp4` from configuration and two server-generated UUIDs only; the row id is generated before the call. `HttpLiveKitEgressClient.startParticipantFileEgress` additionally
  refuses (before any network call) a path that is not an absolute `.mp4` path, or contains `..`, a backslash or a control character, and an identity that is empty or longer than 64 characters. The identity is only serialised into the JSON body. Track-Egress file names
  still contain the identity; both modes skip a participant whose identity is not `[A-Za-z0-9_.@:-]{1,64}` (warning once per participant).
* *Encoding.* 1280 x 720, 30 fps, H.264 main 2500 kbit/s, AAC 128 kbit/s, a keyframe every 2 s (`RECORDING_PARTICIPANT_ENCODING_OPTIONS`; only the `advanced` branch of the `preset`/`advanced` oneof exists on the request type, `screen_share` is written explicitly as `false`).
  The keyframe interval also bounds how exactly a switched-off camera is found (below). *CPU:* unlike Track Egress this RE-ENCODES, so every person is real encoder load; on a small host 960 x 540 is the lever to pull (edit the constant).
* *Screen shares stay on Track Egress* (`SCREEN_SHARE`, `SCREEN_SHARE_AUDIO`; the person egress is started with `screen_share: false`). A screen share can therefore be offset against the person's voice, as before. Acceptable for slides, not for lip-sync.
* *A person who leaves.* LiveKit hands out a new SID on every join. A person who comes back is a new row, a new file and a new picture in the layout. When a Participant-Egress row's SID is no longer in the room, the poller sends ONE `StopEgress` (remembered in memory until the
  recording leaves STOPPING; remembered only after a SUCCESSFUL call, so a failed one is tried again) and refreshes that row from `ListEgress`.
* *A refused start is not silently replaced.* If LiveKit refuses `StartParticipantEgress` (for instance because no egress CPU is left), the poller logs a warning (recording id, no identity) and tries again on the next tick. There is deliberately NO fallback to Track Egress: that would bring the
  offset back unnoticed. The consequence is that the person is missing from the recording until capacity is free.
* `maxTracks` counts every row, person files included.

=== Composition: per-stream offsets, conditional drift correction (V1.9.154)

`ParticipantFileInputs.build` turns one person file into one video input and one audio input that point at the same file. `FfmpegSegmentedComposer` remuxes `0:v:0` and `0:a:0` into separate files, so media time 0 of each stream is *its own first packet*.
In a real egress file the two streams do not start together: measured on a real `livekit/egress:v1.13.0` file (2026-10-11) video started 1.2 to 1.7 s after the audio. Giving both inputs the file's offset would therefore put the person 1.2 to 1.7 s out of sync inside the file.

* `fileZero = min(videoStart, audioStart)` (`ffprobe stream.start_time`, `RecordingMediaProber.probeStreamStartTimes`); `videoOffset = fileOffset + (videoStart - fileZero)`, `audioOffset = fileOffset + (audioStart - fileZero)`. Only the difference counts, so a common shift or the AAC priming
  (about -0.02 s) changes nothing. A stream whose start could not be measured is taken to start with the file (and a warning says so when neither could be measured).
* The audio input has no wall-clock duration, so the track-mode `atempo` rule never applies to it. The only stretching of a person file is the drift correction below.
* The file's `file_results[].started_at` (relative to the recording's earliest track) is the file offset; `t0` and the output length are computed as before, so recordings that mix person files and screen shares need no special case.
* *Who is in the picture.* The video ranges are the packet ranges of the video stream (gaps of at least 1 s) minus the black stretches (below). A file without a video stream contributes audio only; a picture that is black throughout contributes no video input at all
  (an empty range list would mean "not measured, visible throughout" to the composer). If nothing visible is left in the whole recording the composition ends with `COMPOSE_FAILED`, as in the track mode.
* *Recompute needs no special case.* `RecordingPoller.buildSpec` decides per ROW (`egress_kind`), not by the current configuration: a TRACK recording can be recomputed on an instance that now runs in participant mode and vice versa.

==== Drift correction (V1.9.154)

*Cause.* The LiveKit egress (v1.13.0) fills every Opus DTX gap of about 400 ms roughly 1.5 ms too long, so the audio of a person file is written about 0.34 % longer than the wall clock while the picture runs on the wall clock. Measured on 2026-10-17 in recording cc27c031 (ELB): audio 500.0 s in 21533 packets, picture 14950 frames = 498.33 s;
1057 silence pieces of 0.381 s at a spacing of 0.4215 s; the clap in the picture at 470.93 s, in the sound at 472.43 s (the model predicts 1.57 s); the egress synchronizer itself reports +-5 ms.

*Decision* (`ParticipantAudioDrift.tempoFor`, one pure function). The ratio comes from the END POINTS inside the container, not from `audioDur / videoDur`: `wallSpan = (videoStart + videoDur) - audioStart`, `ratio = audioDur / wallSpan`. The quotient of the durations would read the usual start offset
(video 1.2 to 1.7 s after the audio) as drift. Assumption: both streams end together when the egress stops (egress log: last PTS 8:18.27 against 8:18.32). Only measured packet durations count, never a reported duration.
Corrected only if all of this holds: audio, video and `wallSpan` are at least 30 s; `excess = audio - wallSpan` is at least `max(0.25 s, 0.05 % of wallSpan)` and at most 2 % of `wallSpan`. An audio that is SHORTER than the picture is never corrected (documented only).

*Application.* `ParticipantFileInputs` puts the ratio into `RecordingComposeAudioInput.driftTempo`; `RecordingComposeAudioInput.effectiveTempo()` is the one `atempo` decision (drift ratio first, else the track-mode `AudioTempo` rule) and is used by the composer AND the speaker timeline.
So the existing per-segment path does the work (`atempo` in the filter chain, `mediaStart = (from - offset) * ratio`); nothing is done at remux time, and the data ranges and the speech windows land on the wall clock with the same function. The output length stays `duration_ms`; at most about 1.7 s of still picture with silence can follow at the end.
If the egress is fixed one day, the audio is no longer longer than the picture and the correction switches itself off.

*Recompute and the stored speaker timeline.* The stored timeline of an existing recording was computed without the correction. If a person file needs the correction, "Neu berechnen" therefore analyses the microphones again and replaces the stored timeline (`RecordingSpeakerTimelineStore.replace`); if that analysis is impossible the stored timeline is used with a warning.

*Measuring by hand* (no script in the repo, it would be untested): picture event = luma jump around the clap (`ffmpeg -i f.mp4 -vf signalstats,metadata=print:key=lavfi.signalstats.YAVG:file=y.txt -an -f null -`); sound event = `astats` peak or `silencedetect`; silence statistics = `silencedetect=n=-85dB:d=0.04`. This allows re-measuring cc27c031 after "Neu berechnen" on ELB.
*Proof.* `RecordingParticipantDriftIntegrationTest` (real `ffmpeg`): a synthetic file with the audio 0.34 % too long, three events across the file, every beep/flash pair within 150 ms after the correction, and a counter-check that the last beep is more than `0.8 * T * 0.0034` late without it.

=== Detecting "camera off"

A person file is ONE continuous video stream, so a switched-off camera is not a gap in the packets any more. Two detections run, because the behaviour is expected but only partly confirmed:

. *Packet gaps* of at least 1 s (as before). Covers an egress that writes nothing for a muted camera.
. *Black pictures* (`FfmpegBlankVideoDetector`): `ffmpeg -copyts -skip_frame nokey -i <file> -map 0:v:0 -an -vf scale=160:-2,blackdetect=d=1.5:pic_th=0.98:pix_th=0.08 -f null -`. Only keyframes are decoded (one 720p picture every 2 s, a fraction of real time), so the accuracy is one keyframe interval.
  Argument list without a shell, a constant filter string (the path appears only as the `-i` argument), stderr read with a line and byte cap and a hard timeout, the raw output never leaves the class. The times are container timestamps minus the video stream's start time. A black stretch that
  ends within 2.5 s of the end of the picture runs to the end (the last keyframe closes it, so it would otherwise end up to one interval early).

*Confirmed on a real egress file (2026-10-11, local `livekit-server` 1.13.5 + `egress` 1.13.0, a `livekit-cli` demo publisher whose video track was muted by `MutePublishedTrack` ten seconds in):* the egress keeps writing CONTINUOUS BLACK pictures (30 fps, luma 16, no packet gap, no freeze) from the moment of the mute;
`blackdetect` on the keyframes reported the stretch within one keyframe interval. This is a synthetic Go publisher with a server-side mute, not a browser camera; the browser case is in the staging runbook.

*Limits, not hidden.* A very dark REAL picture can count as "off" (`pix_th=0.08`). A frozen last picture would not be recognised (a possible follow-up: `freezedetect`); the real egress did not freeze. A camera that flickers for less than 1.5 s is ignored.

== Worker and poller

Since V1.9.109 a composition no longer runs inside the poller's `tick()`. `tick()` collects the PROCESSING recordings and the READY recordings with a recompute marker and starts ONE worker coroutine for them, only when the single-slot semaphore is free
(`tryAcquire`); the worker walks them one after the other and re-reads each row before it starts. Before this, no `StartTrackEgress` was issued for any meeting that was recording at the same time while a composition ran, so somebody who joined then was never recorded.
Tests wait with `RecordingPoller.awaitCompositionIdleForTest()`. `stop()` cancels the worker (the child process is destroyed; a recompute marker is left in place and the next boot starts it again).

== Recompute

`IConferenceRecordingService.recomputeRecording(recordingId)` ("Neu berechnen"):

* *Callers.* As for the retry (moderator or BOARD/ADMIN, `mayAccess` for the recording's tier), and for a READY recording the archived document's own tier counts as well (a folder tightened afterwards).
* *READY.* Raw files must be present. The per-recording budget is the one of the retry (`manual_retry_*`, shared: 15 minutes spacing, 3 per 24 hours), 10 calls per minute per member. A conditional
  `UPDATE ... WHERE status = READY AND recompute_started_at IS NULL` sets `recompute_started_at` (V89; CHECK: only while READY). Zero rows is `RecordingRecomputeInProgressException`. Audit `UPDATE`, `status=READY` to `recompute requested`.
  The recording stays fully usable: document, media URL and playback are unchanged until the new version is committed.
* *FAILED + COMPOSE_FAILED.* Exactly the retry path (same flip, same counter), audit text `recompute requested (failed recording)`.
* *Disk.* `RecordingDiskBudget`: the work volume needs `max(1.5 x raw + 1 GiB, raw + pcm + 2 x file + 1 GiB)` (pcm = 192 000 bytes per second of recording), the document volume `file + 512 MiB`. Checked in the RPC (before the transaction, it reads the file system;
  `RecordingRecomputeInsufficientDiskException`) and again by the poller right before the work starts (the answer is minutes old).
* *The work.* The worker composes into `<raw dir>/recompute-<uuid>.mp4.part`, then `archiveNewVersionOfFile` copies it as a NEW `document_version` (`max + 1`) *outside* any transaction (streamed, SHA-256) and then, in ONE transaction, (1) runs the *fencing update*
  `UPDATE conference_recording SET file_size_bytes, duration_seconds, recomputed_at, recompute_started_at = NULL WHERE id = ? AND status = READY AND recompute_started_at = <the marker this worker was started with>` (it takes the recording's lock first, the order every other path uses),
  (2) locks the document row, inserts the version and switches `document.current_version_id`, (3) writes the audit entry (the last lock-taking operation). Zero rows in (1), or a deleted document, rolls everything back and removes the new blob:
  a deletion or a newer request in between can never leave an orphan version or overwrite a newer state. The same holds for the failure write (`last_recompute_failure_code = COMPOSE_FAILED`, marker cleared, audit `recompute failed (COMPOSE_FAILED)`).
* *The previous version stays* in the document history (blob and row): no data loss, the price is the doubled space. Raw files are never deleted by a recompute, whatever `LAPIS_RECORDING_KEEP_RAW` says.
* *Stale and restart.* A marker older than twice the composition timeout with no worker on it is declared failed; a marker found after a restart starts the recompute again.
* *Media URL.* `ConferenceRecordingDto.mediaUrl` carries the current document version (`/api/conference/recordings/<id>/media?v=<versionId>`; the route ignores `v`), so a browser cache or a resumed range request cannot mix old and new bytes after the switch.
* *Typed errors.* `RecordingRecomputeNotAllowedException`, `RecordingRecomputeInProgressException`, `RecordingRecomputeRateLimitedException`, `RecordingRecomputeInsufficientDiskException`, and `RecordingRawFilesMissingException`.

Who is told what: `canRecompute`, `recomputeInProgress`, `lastRecomputeFailed` and `rawFilesAvailable` (now also for READY) are only set for a caller who may recompute; `recomputedAt` is general information.

== Manual retry _(V1.9.107)_

`IConferenceRecordingService.retryRecordingComposition(recordingId)`:

* *Rights.* The room's moderator (`ConferenceModeratorAuthority`) or BOARD/ADMIN, and `ConferenceRecordingAccess.mayAccess` for the recording's own tier (no document exists for a failed row). This is stricter than deleting a failed row:
  a room creator without access to an `ADMIN_ONLY` recording can delete it but not restart it.
* *One transaction, one lock.* The row is locked `FOR UPDATE`; the state is checked; the raw files are checked (read-only, repeatable); the rate limits are checked; a conditional `UPDATE ... WHERE status = FAILED AND failure_code = COMPOSE_FAILED`
  flips it to `PROCESSING` with `compose_attempts = MAX_COMPOSE_ATTEMPTS - 1` and clears the failure fields. Zero updated rows means another caller won (`RecordingRetryNotAllowedException`).
  The audit entry (`CONFERENCE_RECORDING`, `UPDATE`, `status=FAILED` to `status=PROCESSING (manual composition retry #n)`, no path, no title) is the last lock-taking operation.
* *The poller's state machine is untouched.* It sees `PROCESSING` with four attempts, makes exactly one attempt (number five) and ends in `READY` or again `FAILED`/`COMPOSE_FAILED`; raw files are kept on failure. The service wakes it with `requestTick()`
  strictly after the commit. (V1.9.109: the attempt runs on the worker, see <<Worker and poller>>; the bookkeeping and the rights moved into helpers shared with the recompute.)
* *Raw-file check* (`RecordingRawFiles.rawFilesAvailable`): `raw_dir` parses as a UUID and its canonical directory lies below the canonical raw root; at least one COMPLETE video track; every COMPLETE track has a file name that
  `resolveWithin` accepts (no traversal, no symlink out) and the file is larger than zero bytes. Paths come from the database row, never from the client.
* *Typed errors.* `RecordingRetryNotAllowedException` (wrong status or code, lost race), `RecordingRawFilesMissingException`, `RecordingRetryRateLimitedException`. They are separate types because the message of a `ConflictException`
  does not reliably reach the client (see link:typed-conflict-errors.adoc[typed-conflict-errors.adoc]).

== Event rooms (V1.9.156)

Until V1.9.155 `EventConferenceGuard.requireNotEventRoom` refused `startRecording` and `startStream` for an event room, because a person without an account had
given no consent that could be proven. V1.9.156 replaces the refusal at **exactly these two places** by one decision function and builds the proof it relies on.
Operator view: link:../features/event-capture.adoc[Recording and live streaming in event rooms].

*The decision* (`EventConferenceGuard.requireEventCaptureAllowed(row)`, called under the room-row lock of the caller): an ordinary room is not touched; an event
room may be recorded or streamed iff the instance switch is on **with the current operator notice** (`EventCaptureSettings.startAllowed()`), the event is released
(`event.capture_allowed`) and it is a Lapis conference. Everything else stays `requireNotEventRoom` (`ConferenceService`, `MembershipGuards`); a tripwire
(`EventConferenceGuardTripwireTest`) counts the call sites of the new function (exactly `startRecordingInTransaction` and `startStream`) and the remaining ones.
`requireParticipantOrModerator` and `requireStillEntitled` are unchanged. A recording of an event room cannot be put at `PUBLIC_MEMBERS`.

*The proof the decision relies on.* Nobody gets a token for a released event room without having acknowledged the live `EVENT_REC` text (`EventOnlineJoin`, the only place
that mints a token for an event room besides `rejoinMainRoomToken`, which needs an open participation that only `EventOnlineJoin` creates). The proof is written in the
same transaction that records the participation (members) or before the token leaves the server (people without an account), under the row lock of the event.

*Why a lock and which order.* A release granted between a person's look at the event and their token would let somebody in who acknowledged nothing. The release is
therefore frozen (`EventCaptureLock.isActive`) from the opening of the online window, while the room lives, while a recording or stream is not over and while somebody
has an open participation. The entry path takes `lockEventForUpdate` first and the room row second; `setEventCaptureAllowed` takes the event lock first and reads the
room state without locking it; `updateEvent` locks the event. There is no path that locks the room and then the event, so the order cannot deadlock. The audit entry is the
last locking operation of the release transaction.

*The banner.* `EventCaptureLiveBroadcaster` sends `{"v":1,"r":0|1,"s":0|1}` on the topic `lapis-event-capture` (`sendDataPayloadLimit` knows it) after a recording started and
from a sweep every 5 seconds (a change at once, a heartbeat every 30 seconds while something runs). Only rooms of released events that are alive are looked at. A failed
send is not retried and not remembered. The clients drop every packet that carries a sending participant.

*Unchanged on purpose.* The poller (`RecordingPoller`) has no new runtime check: the identities `evg-<uuid>` and `evg-<32 hex>` satisfy `RecordingEgressPaths.isAcceptableIdentity`
(`RecordingPollerTest`, participant mode (i)); "Neu berechnen", the download and the speaker timeline process only tracks that already exist and obey the document rights.

== Known limitations

* *Participant egress mode (the default since V1.9.116) was measured with one real browser participant only* (see <<Staging results (2026-10-12)>>) and re-encodes (CPU), see <<Participant egress mode (V1.9.110, default since V1.9.116)>>: a late camera, the screen-share offset, several people and the CPU cost under load are open; there is no fallback to Track Egress when LiveKit refuses a start; recordings made in Track mode (all before V1.9.116 unless `track` was set) keep their audio/video offset and cannot be repaired.
* *Hanging `ffmpeg` runs (V1.9.155): cause not proven, hang not reproduced.* The cause is probably in the `ffmpeg` 8 command line (six unbounded inputs in one `overlay` chain), but that is a theory; the synthetic stress test found no hang, with `ffmpeg` 9.0.2 or with the 8.0.1 of the production image. The measures (`-t` per input, up to three attempts) reduce the effect, a residual risk remains (a segment that hangs three times fails the composition). Not verified on the real recording bacce4ae until "Neu berechnen" has run there. The diagnosis tools are `FfmpegSegmentStressTest` and `scripts/recording-segment-stress.sh`; the base image's `ffmpeg` is left untouched (the Dockerfile installs the unpinned Ubuntu package, 8.0.1-3ubuntu2 at the time of writing). `ffmpeg`'s own last output, which the runner logs on a timeout, can contain file paths (unchanged behaviour).
* *Raw files are usually gone.* `LAPIS_RECORDING_KEEP_RAW` defaults to `false`, and the poller deletes the raw tracks after a successful composition: for such recordings "Neu berechnen" is disabled (with that reason). Only instances that set `KEEP_RAW=true` can recompute.
  No retention period was added in this wave.
* *No name tag in the recording.* The composed video shows pictures only, no participant names.
* *Speaker view (V1.9.115):* see "Limits of the speaker timeline"; the ffmpeg chain was verified on synthetic inputs only (`RecordingSpeakerLayoutIntegrationTest`: tone-on-silence microphones, solid-colour cameras, the large tile switches within 150 ms of the second speaker's claim), not with a real meeting; the output stays 720p (the 1080p design measures are scaled).
* *No grace period.* A camera switched off and on again within a second changes the layout twice; only a data gap of at least the probe threshold (1.0 s video, 0.5 s audio) counts as "off".
* *Drift correction of person files is linear (V1.9.154).* The DTX gaps, and so the drift, arise only in silence. With evenly spread silence the remaining error is about 0.07 s (cc27c031: 1.50 s measured against 1.57 s modelled at 471 s); with unevenly spread speech it is at worst about half of the total drift
  (8 minutes, first half silent, second half speech: about 0.8 s in the middle). Not verified on a real recording until a recompute ran on ELB. It assumes the picture runs to the end of the egress. Switching DTX off in the browser is deliberately not built (it would cost bandwidth).
* *`atempo` in track mode only corrects small drift* (ratio between 0.95 and 0.997 and more than one second difference); everything else is left alone.
* *The sync proof is synthetic* (generated WebM/OGG inputs shaped like LiveKit's). The real ELB recordings were not listened to.
* *The budget is shared.* Retry and recompute draw on the same 3 per 24 hours of one recording.
* *The previous version stays* in the document store after a recompute (space).
* *`-bf 0`* makes the video 5-10 % larger.
* *Slower than before:* the composition is sequential (a remux of every file, then one `ffmpeg` run per segment and stream), one composition at a time system-wide.
* *Gradle tests that need the `ffmpeg` binary* (`FfmpegCompositionIntegrationTest`, `RecordingSyncIntegrationTest`; `RecordingParticipantSyncIntegrationTest` and `RecordingParticipantDriftIntegrationTest` need only `libx264` and `aac`) run only where `ffmpeg` with `libx264`, `aac`, `libvpx` and `libopus` is installed (the Docker image's Ubuntu `ffmpeg` 6.1 and the CI runner's `ffmpeg` have them).
* After a successful retry with `LAPIS_RECORDING_KEEP_RAW=true` the raw files stay on disk; cleaning them up is an operator decision.
* The backfill of V87 also classifies the cases "room gone while STOPPING" and "no resolvable video track" as `COMPOSE_FAILED` (same text); the raw-file check protects, but the classification is not exact.
* There is no real progress, only an estimate; the estimate ignores a queue.
