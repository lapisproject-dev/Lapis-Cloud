= DSGVO Framework — Subject Roots and Contributors
:description: How Lapis Cloud's Art. 15/17/20 DSGVO export/erasure framework is structured, and how it was widened in Welle V1.4.2 to cover non-member subjects.
:toc:
:toc-placement: preamble
:icons: font

== Context

Every table in this codebase that carries personal data about a `member` participates in Art.
15/17/20 DSGVO export and erasure through exactly one mechanism: a
`network.lapis.cloud.server.dsgvo.PersonalDataContributor` registered in
`network.lapis.cloud.server.dsgvo.PersonalDataRegistry`, enforced by
`PersonalDataCoverageTest`'s `information_schema` walk — a future table with a foreign key into a
DSGVO subject that is neither covered by a contributor nor explicitly allowlisted with a written
reason fails `./gradlew clean check`, not merely a code review.

Through V1.4.1, that walk covered exactly one table: `member`. Welle V1.4.2
("Interessenten-/Sympathisanten-CRM") introduced the first DSGVO subject that is **not** a member —
a `crm_contact` — and widened the framework accordingly rather than bolting on a second,
parallel mechanism. This document describes the resulting shape.

== Why one framework, not two

A second, CRM-specific export/erasure mechanism running alongside the existing one would have no
machine-checked completeness guarantee: `PersonalDataCoverageTest` is effective precisely because
it is a single `information_schema` walk over real foreign keys, not a hand-maintained list. A
second mechanism next to it is a second list that can silently drift from the schema — exactly the
failure mode the existing framework was built to prevent. Widening the one mechanism costs a
one-time refactor (see below); a parallel mechanism costs that same completeness guarantee forever.

== `DataSubject` and the subject-root walk

`network.lapis.cloud.server.dsgvo.DataSubject` is a sealed interface with two cases,
`DataSubject.Member` and `DataSubject.CrmContact`, each wrapping a `kotlin.uuid.Uuid`. It is
server-only — `lapis-shared` uses `kotlin.uuid.Uuid` nowhere, and the wire-visible discriminator is
the plain `@Serializable` enum `network.lapis.cloud.shared.domain.DsgvoSubjectKind` (`MEMBER`,
`CRM_CONTACT`), which travels on `DsgvoAuditLogEntryDto.subjectKind`.

`PersonalDataContributor.export`/`.erase` now take a `DataSubject`, not a bare member `Uuid`, and
every contributor declares `val handledSubjects: Set<DsgvoSubjectKind>`. A caller
(`DsgvoService`/`DsgvoRoutes` for members, `CrmService`/`CrmRoutes` for CRM contacts) filters
`PersonalDataRegistry.contributors` by `handledSubjects` before dispatch — a contributor that does
not handle the given subject kind is simply skipped, never called with a subject it cannot service.

`PersonalDataRegistry.subjectRootTables` now lists **two** tables (`member`, `crm_contact`), and
`PersonalDataCoverageTest`'s walk (`tablesReferencingSubjectRoots`) covers foreign keys into either
one. A table with a foreign key to `crm_contact` therefore goes red exactly the same way a table
with a foreign key to `member` always has, the moment it lacks a contributor or allowlist entry.

The two DSGVO subject roots and the audit log's discriminator column, in the same `[kuml]`-macro,
`ermMappingProfile` DSL this codebase's persistence model itself is authored in (see
`38-crm.kuml.kts`/`04-dsgvo.kuml.kts` for the full, real schema this is a deliberately narrowed
excerpt of):

[source,kuml,name="dsgvo-subject-roots"]
----
import dev.kuml.profile.erm.ermMappingProfile
import dev.kuml.uml.dsl.applyProfile
import dev.kuml.uml.dsl.stereotype

classDiagram(name = "DSGVO Subject Roots") {
    applyProfile(ermMappingProfile)

    val dsgvoSubjectKind = enumOf(name = "DsgvoSubjectKind") {
        literal(name = "MEMBER")
        literal(name = "CRM_CONTACT")
    }

    val member = classOf(name = "Member") {
        stereotype("Entity") { "tableName" to "member"; "kotlinObjectName" to "MemberTable" }
        attribute(name = "id", type = "UUID") { stereotype("Id"); stereotype("Column") { "columnName" to "id" } }
    }

    val crmContact = classOf(name = "CrmContact") {
        stereotype("Entity") { "tableName" to "crm_contact"; "kotlinObjectName" to "CrmContactTable" }
        attribute(name = "id", type = "UUID") { stereotype("Id"); stereotype("Column") { "columnName" to "id" } }
    }

    // subject_member_id is DELIBERATELY not modelled with a fkEntity override here -- since V1.4.2
    // it is a plain, polymorphic UUID column (see "dsgvo_audit_log.subject_kind" below), not a real
    // foreign key to either entity above.
    val dsgvoAuditLog = classOf(name = "DsgvoAuditLog") {
        stereotype("Entity") { "tableName" to "dsgvo_audit_log"; "kotlinObjectName" to "DsgvoAuditLogTable" }
        attribute(name = "id", type = "UUID") { stereotype("Id"); stereotype("Column") { "columnName" to "id" } }
        attribute(name = "subjectMemberId", type = "UUID") { stereotype("Column") { "columnName" to "subject_member_id" } }
        attribute(name = "subjectKind", type = dsgvoSubjectKind) {
            stereotype("Column") { "columnName" to "subject_kind"; "enumType" to "network.lapis.cloud.shared.domain.DsgvoSubjectKind" }
        }
    }
}
----

== `MemberPersonalDataContributor`: an adapter, not a rewrite

Widening the raw `PersonalDataContributor` interface to `DataSubject` would have forced every one
of the 29 pre-existing contributors into a `when (subject) { ... }` they have no use for — every one
of them, before this wave, only ever handled members. `MemberPersonalDataContributor` is a thin
adapter interface: it declares abstract `exportMember(memberId: Uuid)`/`eraseMember(memberId: Uuid,
mode: ErasureMode)` (the exact shape every existing contributor already had) and implements
`export`/`erase`/`handledSubjects` itself by unwrapping a `DataSubject.Member` (see
`DataSubject.asMember` for the one unsafe cast this whole framework contains, defensively checked
and reachable only through a caller bug, never a data condition).

Because `exportMember`/`eraseMember` are `abstract`, the compiler — not a person — forces every one
of the 29 contributors to be touched by this migration; nothing can be silently left behind. The
migration itself was mechanical: `: PersonalDataContributor` → `: MemberPersonalDataContributor`,
`override fun export(memberId: Uuid)` → `override fun exportMember(memberId: Uuid)`, `erase` →
`eraseMember` — no change to any contributor's actual query logic.

`CrmPersonalData` is the one contributor that implements the raw `PersonalDataContributor`
interface directly, because it genuinely handles both `MEMBER` and `CRM_CONTACT` subjects with
structurally different behaviour per kind — see its own KDoc for the full semantics (a real
`DELETE` for a `CRM_CONTACT` subject; retain-with-reason for rows a `MEMBER` subject only created or
recorded, not rows describing them).

== The `external_donor` gap: sichtbar, nicht geschlossen

`external_donor` (Welle V0.5.1, `10-accounting.kuml.kts`) carries PII of a non-member donor and has
no foreign key to `member` by design — it never entered the FK walk to begin with, and this wave
does not change that. What changes is how that gap is recorded: `PersonalDataRegistry
.knownUncoveredSubjectRoots` is a `Map<String, String>` (table name → written reason, naming the
wave expected to close it), checked by `PersonalDataCoverageTest` to be non-blank, to name a wave
number, and to be disjoint from `subjectRootTables`. `PersonalDataRegistry.nonMemberPiiTables` then
asserts every curated non-member-PII table is in exactly one of the two mechanisms — a future table
added to that set without a corresponding contributor or allowlist entry fails the build. The gap
was previously a KDoc comment nobody re-reads; it is now a row in a map a test reads on every build.

== `dsgvo_audit_log.subject_kind`

A `dsgvo_audit_log` row's `subject_member_id` column now polymorphically holds either a member id
or a `crm_contact` id — the sibling `subject_kind` column (`MEMBER`/`CRM_CONTACT`) says which. This
required dropping `fk_dsgvo_audit_log_subject_member_id` (`V17__crm_contacts.sql`): a single-target
foreign key can no longer be correct once the column's referent depends on a sibling column's
value. `erasure_request.subject_member_id` is unaffected and keeps its real FK to `member` — that
workflow (request → approve/reject → execute) stays a member self-service/ADMIN process; a CRM
contact has no login to request anything through, so `CrmService.eraseContact` executes directly
under ADMIN authority instead (see its own KDoc).

`subject_kind` carries no payload — same doctrine every other column on this table has always
followed (see `PersonalDataCoverageTest`'s "dsgvo_audit_log rows never carry payload" test, updated
in this wave to include the new column in its allowlist).

== Events (`event`/`event_registration`, Welle V1.4.3.1 + V1.4.3.2)

`EventPersonalData` is an ordinary `MemberPersonalDataContributor` covering `event`/
`event_registration` — the member-registration and event-creation paths only. Both tables are
**retained, not deleted, regardless of `ErasureMode`**: neither stores a member's name/email
directly, only the `member_id`/`created_by` FK (plus, since Welle V1.4.3.2, `checked_in_by`), and
that FK survives erasure as an ordinary anchor (the referenced `member` row itself is anonymized
elsewhere, same invariant every other retain-with-reason contributor in this codebase relies on).
Deleting the `member_id`/`created_by` FK instead would either orphan a `payment_transaction`/
`journal_entry`'s own accounting trail for a paid registration, or corrupt capacity/waitlist
accounting for a still-`PENDING_PAYMENT`/`WAITLISTED` row; deleting `checked_in_by` would erase who
let a person into an event they attended — organisatorische Nachvollziehbarkeit, not accounting.

A **guest** registration (`event_registration.guest_name`/`guest_email`, no `member_id`) is PII of a
person who is not a member and has no FK to `member` — invisible to the FK walk entirely.
`event_registration` therefore appears in BOTH `PersonalDataRegistry.nonMemberPiiTables` (as a
non-member-PII table) and `knownUncoveredSubjectRoots` (as the documented, wave-numbered gap for
that guest path) — not a contradiction: the XOR check
(`PersonalDataCoverageTest`, "every non-member PII table is either a subject root or a documented,
wave-numbered gap") is evaluated against `subjectRootTables`, while the table is separately, and
correctly, covered by `EventPersonalData` for its member-FK side (`coveredTableNames()`). A
self-service Auskunft/Löschung path for guests, plus an automatic retention limit for
`guest_name`/`guest_email` (Art. 5(1)(e) DSGVO), is deferred to a follow-up wave.

== Member honors (`member_honor`, Welle V1.4.4.3)

`MemberHonorPersonalData` is an ordinary `MemberPersonalDataContributor` covering `member_honor`
alone. The table carries a member in TWO roles — `member_id` (the honoree) and `recorded_by`
(whoever entered the row, always BOARD/ADMIN) — and the two roles are treated differently on
erasure, same "hybrid" posture `CommunicationPersonalData` already establishes for
`direct_message.body` (sender vs. recipient):

* The row itself (that an honor was awarded, when, of what category) is **retained regardless of
  `ErasureMode`** — an Art. 5(2) DSGVO accountability record, same posture
  `BoardMembershipPersonalData` already takes for board service history.
* `note` — a free-text Vorstandskommentar über die honorierte Person — is **unconditionally nulled**
  on the *honoree's* own erasure, unconditionally (not gated on `ErasureMode` the way
  `direct_message.body` is), because there is no third party's own interest in this particular free
  text the way a message recipient has an interest in their copy of a conversation.
* Erasing the *recorder* role does **not** touch `note` — for the person who merely entered the row,
  the note is fachlich fremd (it is not commentary about them); only the row's existence
  (`recorded_by = memberId`) is retained as an accountability record of who entered it.

`member_id` and `recorded_by` can coincide on the same row (a board member honoring themselves is
not excluded by any FK constraint) — `MemberHonorPersonalData.eraseMember` computes its row total
via a single `OR` condition rather than summing two separate `COUNT` queries, so an overlapping row
is never double-counted. See that class's own KDoc "Row-counting, not naive double-counting" for
the exact contract.

`deleteHonor` (`IMemberHonorService`, ADMIN-only) is a plain data-correction DELETE for a
mis-entered row and writes **no** `dsgvo_audit_log` entry — unlike `CrmService.eraseContact`, it is
not an Art. 17 erasure, and logging it as one would misrepresent what happened. The only DSGVO
erasure path for `member_honor` data is the ordinary member-wide Auskunft/Löschung workflow via
`MemberHonorPersonalData`, never this RPC method.

== Family memberships (`member_family`, `member_family_link`, Welle V1.4.4.4)

`MemberFamilyPersonalData` covers both `member_family` and `member_family_link`. Unlike
`member_honor`, this is a **hard DELETE, not a retain-and-null pattern**: a `member_family_link`
row is a statement about a relationship between TWO people (the household grouping), not an
organizational fact about the organization's own actions the way "the organization awarded member
X an honor" is. Retaining it would preserve exactly the relationship information of a THIRD PARTY
(the other family members) that nobody but the erased person's own data-subject request ever
consented to disclose. It also carries no accounting weight to retain FOR — no money flows through
this table, and (from this wave onward) any tier change it triggers is separately recorded in
`AuditEntityType.MEMBER`'s `MemberMembershipTierSnapshot`.

* `member_family_link.member_id = memberId` is hard-deleted (`rowsDeleted`).
* A family that loses its LAST link through this erasure is deleted too (a second
  `TableErasureOutcome` for `member_family`, `rowsDeleted`) — pure orphan data with no further
  purpose. A family that still has other members after this erasure is left standing, possibly now
  payerless — a visible, actionable state (see `IMemberFamilyService.removeFamilyMember` KDoc),
  never silently hidden data debris.
* `member_family.created_by` and `member_family_link.linked_by` are **retained**, same
  accountability posture every other `created_by`/`recorded_by` column in this codebase takes —
  only the membership-role facts about the erased person themselves are removed, not the record of
  who administered a family they did not belong to.
* `member_id`, `linked_by`, and `created_by` (on the owning family) can all name the SAME person on
  the same row/family — `export`/`erase` both filter with a single `OR` across all three roles, per
  table, never as a summed count, same "Row-counting, not naive double-counting" discipline
  `MemberHonorPersonalData` already establishes.

== Regional chapters (`regional_chapter_officer`, Welle V1.9.13/V1.9.14)

`RegionalChapterPersonalData` covers `regional_chapter_officer.member_id`/`granted_by_member_id` --
who was granted "Landesvorstand" (regional-chapter officer) access to which regional chapter, by
whom, and when. `regional_chapter` itself is NOT covered here: its `name` is an organizational
label, not personal data, but the table is deliberately not on the
`PersonalDataRegistry.noPersonalDataAllowlist` either -- it is not ownerless (`RegionalChapterService`
fully owns its lifecycle, and `member.regional_chapter_id` itself is covered by
`FoundationPersonalData`). See `docs/architecture/regional-chapters.adoc` for the full feature.

* Own grants (`member_id == subject`) are **hard-deleted** (`rowsDeleted`) -- unlike
  `CommunicationPersonalData`'s `direct_message`, there is no counterparty copy a grant needs to be
  preserved for.
* Grants the subject GRANTED to someone else (`granted_by_member_id == subject`) are **anonymized**
  (`granted_by_member_id = NULL`, `rowsAnonymized`) -- same accountability-preserving "WHO did this
  administrative act" treatment `AccountingPersonalData`/`accounting_export_run.started_by`
  already establishes: the fact that someone granted the access is retained, the identity of the
  now-erased grantor is not.
* `exportMember` emits two arrays: `officerGrants` (the subject's own grants) and
  `officerGrantsIssued` (grants the subject, as ADMIN, issued to OTHER members) --
  `officerGrantsIssued` deliberately carries no recipient identity (no `memberId`/`displayName`),
  only `chapterName`/`grantedAt`/`revokedAt`: the recipient is a different data subject whose own
  identity is not this export's business.

== Deceased-member exception: `member.date_of_death` (Welle V1.4.4.5)

`FoundationPersonalData` treats `member.date_of_death` (`V24__member_date_of_death.sql`)
differently from every other field it owns: `exportMember` includes it in the Art. 15 export
alongside `dateOfBirth`/`nationality`/the postal address, but `eraseMember` deliberately does
**not** null it on anonymization — ErwG 27 GDPR excludes the deceased from the Regulation's
protection, so there is neither an erasure nor an anonymization duty for this one field. It
documents the automatic end of membership under § 38 BGB and is retained as evidence of that.
This exception is intentional and must not be "cleaned up" by a later, well-meaning refactor that
notices it looks inconsistent with the rest of the class.

== Contribution relief (`contribution_relief_request`, Welle V1.4.10)

`ContributionReliefPersonalData` covers `contribution_relief_request`, which carries a member in
THREE roles — `subject_member_id` (whose contribution obligation is affected), `requested_by`
(whoever filed the request, self or a privileged actor on the subject's behalf), and `decided_by`
(the BOARD/ADMIN member who approved/rejected it). Same "row-counting via a single `OR`, never a
summed count" discipline `MemberHonorPersonalData`/`MemberFamilyPersonalData` already establish for
their own multi-role tables.

* The row itself — that a relief was requested, of what kind, and how the board decided — is
  **retained regardless of `ErasureMode` or role**, an Art. 5(2) DSGVO accountability record; §147
  AO additionally requires a board-authored waiver/reduction decision to stay reconstructable for a
  Kassenprüfung.
* `reason_text` is the one field erasure actually touches: a free-text antragsgrund that may carry
  Art. 9 special-category data (health), authored by the SUBJECT about themselves. It is
  **unconditionally nulled** on the subject's own erasure — regardless of `ErasureMode`, and
  regardless of the request's current status — same "no third party's own interest in this text"
  reasoning `MemberHonorPersonalData.note` already applies to its own honoree-role free text.
  `decision_note` (the board's own words) is never touched by this path.
* Erasing the `requested_by`- or `decided_by`-only role does **not** touch `reason_text` — that text
  is fachlich about the subject, not about the person who merely filed or decided the request; only
  the row's existence in that role is retained as an accountability record.
* `exportMember` mirrors that same asymmetry on the OTHER side of Art. 15: `reason_text` is included
  in the JSON export only for a row where the exporting member is the SUBJECT, even though the same
  row is also returned (without `reason_text`) when the exporting member matches only as
  `requested_by`/`decided_by`. Same role check `ContributionReliefService.toDto` applies over the RPC
  surface (`viewer.isPrivileged || viewer.memberId == subjectId`) — a self-service export must not
  become a side channel for a privileged actor to read a third party's Art. 9 disclosure after
  losing that privilege.
* `reason_redacted_at` is stamped by BOTH independent mechanisms that null `reason_text` — this
  Art. 17 erasure path AND `network.lapis.cloud.server.contribution.ContributionReliefRedaction`'s
  automatic 12-month sweep (see that class' own KDoc) — it is a factual "when was this text actually
  removed" timestamp, true regardless of which of the two triggered it.

== AI assistance (V1.6.1)

`AiAssistantPersonalData` (`sectionKey = "aiAssistant"`) owns the three AI tables that carry a
`member` FK:

* `ai_member_opt_in` -- **hard DELETE** on erasure; a consent record for a feature the person no
  longer uses has no retention interest of its own.
* `ai_call_audit` -- **retain-and-redact**: the row is a usage/traceability record holding only
  SHA-256 hashes and counters (never clear text), so erasure sets `member_id` to `NULL`, after which
  the row has no personal reference. The column is therefore nullable.
* `ai_knowledge_release` -- **retain-and-redact**: the release decision belongs to the knowledge base
  record; erasure nulls `released_by` (nullable for the same reason).

Export lists opt-in states, the member's calls (timestamp, agent type, outcome, token counts,
retrieved chunk count) and the titles of documents the member released. The hashes are never
exported -- like `code_hash` for `MemberCardPersonalData` they give the data subject no intelligible
information. `ai_knowledge_chunk`/`ai_knowledge_index_state` carry no member FK (derivatives of
document content, whose personal-data handling lives in `DocumentPersonalData`). Details and the
data flow to the provider: xref:ai-assistant.adoc[ai-assistant.adoc].

== MCP write-paths (V1.8.2 / V1.8.2b)

`McpPersonalData` covers `mcp_post_draft` -- an MCP agent's unpublished draft, see
xref:mcp-server.adoc[mcp-server.adoc] "The draft lifecycle". **Hard DELETE** on member erasure,
regardless of the draft's own status (`OPEN`/`DISCARDED`/`RELEASED`): a draft is disposable
agent-produced scratch content, not a record with its own retention interest independent of the
member.

Two ADDITIONAL, narrower data-minimization mechanisms exist alongside that member-level erasure
path, both introduced in V1.8.2b:

* **Content cleared at release, not after any delay** -- `PostDraftStore.markReleasedOwned` sets
  `content = ""` the MOMENT a draft is released, unconditionally. This closes a gap the ordinary
  post-scoped erasure path (`rpc.SocialContentTombstone`, a single `social_post.content_erased_at`
  tombstone) does not reach: erasing the PUBLISHED post a draft became would otherwise leave the
  ORIGINAL, unredacted text sitting in `mcp_post_draft` forever, entirely independent of that
  post's own erasure state.
* **Automatic retention poller** (`social.PostDraftRetentionPoller`, always active, independent of
  `LAPIS_MCP_*`) -- deletes a `DISCARDED` draft row after 7 days and a `RELEASED` one after 90 days
  (its `content` is already empty by then); an `OPEN` draft is never touched by this poller. Both
  windows are deliberately SHORTER than every other retention period in this document -- a draft is
  disposable scratch content, see that class' own KDoc.

== Board member map (aggregated postal codes) (V1.9.5, server + shared half only)

NOTE: This wave implements the RPC aggregate and the basemap HTTP route only -- `lapis-client` has
no member-map screen yet (see xref:member-map.adoc[member-map.adoc]'s status note). Everything
below already holds today because it is a property of the server-side query and response shape,
independent of whether a client screen exists.

The BOARD/ADMIN-only member map (xref:member-map.adoc[member-map.adoc]) is deliberately **not**
covered by `PersonalDataRegistry`/`PersonalDataContributor` at all -- it reads `member.postal_code`
and `member.country` for export/erasure purposes exactly as every other `member`-scoped column
already does through `MemberPersonalDataContributor`, and it never introduces a new table or a new
identifiable record. What makes this feature DSGVO-relevant is not a new storage location but a new
*view* over existing columns:

* **Purpose limitation**: the query is a board reporting aggregate (Art. 6(1)(f) legitimate
  interest -- understanding the organization's own geographic footprint), never a lookup of an
  individual member's address. The response shape enforces this structurally: no member id, name or
  precise address ever crosses the wire, only postal-code-bucketed counts -- see
  xref:member-map.adoc#privacy-boundary[member-map.adoc "Privacy boundary"].
* **Data minimization**: the underlying query selects only two columns
  (`postal_code`, `country`) for eligible members, nothing else -- there is no richer
  in-memory representation at any point for a later change to accidentally widen.
* **Access control**: `BOARD`/`ADMIN` only, enforced server-side today (`BoardMemberMapService`,
  `registerMemberMapRoutes`); a client-side route guard is planned as defense in depth once the
  client half of this wave lands, not yet implemented (see status note above). No self-service
  variant either way.
* **Erasure**: an anonymized member (`anonymized_at IS NOT NULL`) is excluded from every query this
  feature runs -- the existing `MemberPersonalDataContributor` erasure path (which clears
  `postal_code`/`country` along with the rest of a member's address) removes that member from the
  map's counts as an ordinary consequence, no separate erasure logic needed here.
* **Third-party data**: the postal-code centroid lookup (GeoNames, CC-BY-4.0) and the basemap
  vector tiles (OpenStreetMap, ODbL, via Protomaps) contain no personal data about this
  organization's members -- they are reference geodata, unrelated to any `DataSubject`.

== Self-service address and beneficial-owner data (V1.9.33)

`IMemberService.updateMemberAddress` (street, postal code, city, country) and `updateMemberBeneficialOwnerData` (date of birth,
nationality; the GwG data) have existed since the foundation waves. V1.9.33 hardens them and adds the first client UI for them
(card "Anschrift und Angaben nach Geldwäschegesetz" on "Meine Daten", own account only).

* **Who may**: the member themselves, or BOARD/ADMIN (`isPrivileged`). TREASURER may not. The authorization check comes before any
  validation of the input, so nobody can probe the rules without permission.
* **Validation** (`MemberAddressRules`, shared by server and client): values are trimmed, a blank value becomes `null` (clears the field);
  the lengths equal the columns (200/20/200/100/100, pinned by a test against `MemberTable`); control characters (`isISOControl`, which
  includes `\n`, `\r`, `\t`) are refused; the date of birth must not lie in the future, before 1900-01-01 or after a recorded date of
  death (the date of death is read `FOR UPDATE` in the same transaction). A refusal is a value-free `ConflictException` and writes nothing.
  Lengths are measured in UTF-16 code units, Postgres counts code points: the rule can only be stricter than the database for emoji.
  No format is checked for postal code or country (members live abroad).
* **Audit**: every call writes one `AuditLogEntry` (`MEMBER`, `UPDATE`) in the same transaction with the marker `ADDRESS_UPDATED` or
  `BENEFICIAL_OWNER_DATA_UPDATED` as `after_snapshot`. Never a before value, never a field value. It is also written when nothing changed.
* **No rate limit**: `MemberService` has no general limiter for writes and none was added.
* **Admin UI**: V1.9.35 adds it, see the next section.

== Privileged read of address and GwG data (V1.9.35)

`IMemberService.getMemberAddressForAdministration(memberId)` returns another member's address and GwG fields to BOARD/ADMIN so the board can
correct them without a blind form.

* **Who**: BOARD/ADMIN only (`isPrivileged`). The check is the first thing that happens: before the id is parsed, before any lookup, before the
  rate limit. A non-privileged caller (also for their own id: the self path is `getCurrentMember`) therefore learns nothing about which ids exist
  and uses up no budget.
* **Audit**: every successful call writes one `AuditLogEntry` (`MEMBER`, `UPDATE`, marker `ADDRESS_READ`, no before, no value) in the SAME
  transaction as the read. If the audit write fails the transaction rolls back and no data leaves. An unknown or anonymized member is a `NotFoundException`
  and writes nothing.
* **Rate limit**: 30 reads per 60 minutes per actor, one singleton `FederationInboxRateLimiter` created in `Application.kt` (`MemberService` is
  rebuilt per call, so a default parameter would limit nothing).
* **No value in logs**: no field value and no member id is logged or put in an exception.
* **UI** (`MemberAddressAdminDialog.kt`, roster action "Anschrift und GwG-Angaben bearbeiten", offered to BOARD/ADMIN only and not for an anonymized
  member): two steps. Step 1 only explains that the read is logged under the caller's name and makes NO server call, so a mis-click leaves no trace.
  "Angaben anzeigen" removes step 1 at once and starts exactly one audited read. Step 2 is the shared `MemberAddressCard` (variant ADMINISTRATION): every
  save asks first and is rebuilt from the DTO the server returned (no second read, no second audit entry); a refused write reloads once. Closing the
  dialog leaves no personal data in the DOM. Values never reach a toast, a log, browser storage or the URL (`ClientSelfServicePiiTripwireTest`).
* **Peer protection**: none. Like `updateMemberAddress` before, BOARD can read and write the data of ADMIN and other BOARD members.
* The protocol screen shows the read as "Eingesehen" and the three markers as sentences (`AuditMarkerLabels.kt`); the marker strings are pinned
  (`AuditMarkerStabilityTest`) because they live in the hash chain.

=== Event refunds (V1.9.35, migration V66)

`event_registration` gained `refund_marked_at` and `refund_marked_by` (FK to `member`). Auskunft exports `refundMarkedAt` of the member's own

== Gathering room / encounter space (V1.9.61, wave B1)

Taking part in a church service can reveal religious belief: a special category of personal data (Art. 9 GDPR). The *encounter space*
(`docs/architecture/encounter-space.adoc`) therefore keeps **no lasting record of who attended**, and the Art. 9(2)(a) consent of a non-member is
stored as an accountability proof that cannot be read as an attendance record. Legal bases are an *assumption* of this wave (explicit consent of
non-members; members: the performance of the organization's own purposes) and are to be confirmed by the controller.

[cols="2,3,3", options="header"]
|===
| Table | Content | Retention, export, erasure
| `conference_participation` (rows of an encounter session) | who is present *now* | deleted on leave, on close and by the poller; never `left_at`. Export: whatever exists at that moment (nothing after the session). Erasure: nothing to do.
| `encounter_space_role` | who holds the office PULPIT / STEWARD of a space | exported; **deleted** on erasure (pure office configuration).
| `encounter_space` | title, theme, entry policy, archive state | organization configuration; `created_by_member_id` is retained with the reason on erasure (the member row is anonymized, never deleted).
| `encounter_consent_acknowledgment` | (member, consent version, hash, **date**) -- no room, no space, no time | kept as accountability proof (Art. 5(2), 7(1)); exported; retained on erasure with the reason. The retention period is an open legal question.
| `audit_log_entry` (`ENCOUNTER_SPACE`) | configuration changes and open/close, actor = BOARD/ADMIN or the office holder, `null` for the poller | **never** entering, leaving, presence, removing or silencing -- the log is hash-chained and cannot be erased.
|===

The contributor is `network.lapis.cloud.server.dsgvo.EncounterSpacePersonalData`. Removed and silenced people of a running session exist only in
memory (`EncounterModerationState`) and vanish with the session or a restart.

*The client (V1.9.62, wave B2).* The page adds no lasting trace either: the only browser storage is the key `lapis.encounter.sceneOff` (a choice, no room, no
person, no time); the chat and the reactions live in memory for the visit and are never stored or sent anywhere but the LiveKit data channel; no time is shown
(the chat wire field is sent as `0`); nothing about a person is written to the console or to telemetry (`ClientEncounterPrivacyTripwireTest`). The listing of the people present
shows names to the people who are present themselves; `isGuest` is delivered to every present person by `listPresent` but the page shows the marker "Gast" only to people who moderate
(data minimisation on the server side would be a B1 change, see `encounter-space.adoc` "Known limitations of B2"). The entry notice names what others see (the name, not the camera),
what is transmitted if the pulpit is, that nothing is recorded, and the Art. 9 remark with "Dieser Hinweis ist keine Rechtsberatung."

*Room profile (V1.9.67).* An encounter room is either a church service or an *assembly* (a political or civic gathering). Attending an assembly can reveal a political opinion or a worldview, also a special
category (Art. 9). The second consent text (`EncounterAssemblyConsentDisclaimer`, version `2026-10-07.assembly.v1`, headline "Sie nehmen an einer Versammlung teil.") says the same about the system as the
church text (nothing about attendance is stored, nothing is recorded, only the podium is broadcast) and names the political opinion instead of a religious belief. A guest who consented for one text must
consent again for the other: the proof row is `(member, version)` and the purposes differ. *The assembly text is a DRAFT and must be reviewed by a lawyer before a real deployment.* The two new columns
(`profile`, `reaction_set`) describe the room only; reactions are never logged or stored, and the audit snapshots carry the room values only.

NOTE: *Known limitation.* The **ordinary conference** keeps what the encounter space deliberately does not: `conference_participation` is append-only
with `left_at`, `listParticipants` shows the history, and `conference_guest_consent_acknowledgment` is written per join. That is unchanged: a formal
meeting needs its attendance record. An encounter session is fenced off from all of it (`EncounterRoomGuard`).

== Card revocation without a new card (V1.9.33)

"Mitgliedsausweis" on "Meine Daten" lets a member block a lost card (`IMemberService.reissueMemberCard`, the existing RPC; no server code
changed). The server rotates the card code and the client reads only `previousCardRevoked`: neither the member number nor a code is shown.
The call shares the rate limit of the PDF download (`memberCardIssueRateLimiter`). A new card is obtained by the existing download on the
start page, which issues one. Kilua RPC transmits only the exception type, so a rate limit and a missing membership status are both
`ConflictException`: the client shows one general sentence for both.
