= Systemic consensus, web client (V1.9.28)
:toc:

== Purpose

`ISystemicConsensusService` (V0.2.5) has been able to run a systemic consensus for a long time: every participant rates *every* option
with a resistance from 0 ("I can live with it") to 10 ("not acceptable for me"), and the option with the lowest resistance wins. Until
V1.9.28 no screen could reach it. This wave adds the web client -- the "Konsensieren" screen in the sidebar group "Selbstverwaltung", an
entry in the resolution section of a scheduled motion, and the resistance booth -- plus four small server additions the client needed.
It deliberately does not change how a consensus is evaluated or recorded.

NOTE: This document's `[kuml]` blocks are rendered and validated by the `:docs-render:renderDocs` Gradle task.

== Lifecycle

A consensus is never created on the consensus screen. It is opened from a motion in the status `SCHEDULED`, like an election, and --
only when it is binding -- its result is written into the same resolution book.

[source,kuml,name="consensus-lifecycle"]
----
stateDiagram(name = "Consensus lifecycle") {
    val start = initialState()
    val collection = state(name = "COLLECTION")
    val rating = state(name = "RATING")
    val closed = state(name = "CLOSED")
    val evaluated = state(name = "EVALUATED")
    val aborted = state(name = "ABORTED")

    transition(source = start, target = collection) { trigger = "openSystemicConsensus" }
    transition(source = collection, target = rating) {
        trigger = "freezeOptions"
        guard = "[at least one option]"
    }
    transition(source = rating, target = closed) { trigger = "closeRating" }
    transition(source = closed, target = evaluated) { trigger = "evaluate" }
    transition(source = evaluated, target = rating) {
        trigger = "reopenRating (advisory only)"
        guard = "[round < maxRounds]"
    }
    transition(source = collection, target = aborted) { trigger = "abortSystemicConsensus" }
    transition(source = rating, target = aborted) { trigger = "abortSystemicConsensus" }
    transition(source = closed, target = aborted) { trigger = "abortSystemicConsensus" }
}
----

The server also allows `reopenRating` from `CLOSED` (a binding consensus has no resolution yet at that point). The screen never offers
it: after closing, the only main action is "Auswerten". A revote is offered only after an evaluation, only for an *advisory* consensus (a
binding one has written its resolution, and the server then refuses a reopen) and only while rounds are left.

== Roles and gates

The client mirrors the server's rules in `ConsensusAuthzUi.kt` (pure, unit-tested). Unlike the elections there is no role arithmetic in
the client: the server computes the flags in `SystemicConsensusParticipationDto` and the client combines them with the status.

[cols="2,3,3", options="header"]
|===
| Flag (server) | Meaning | Mirrors
| `canManage` | leadership of the *motion's own* committee, or BOARD/ADMIN | `canManageSystemicConsensus`: freeze, close, evaluate, revote, abort
| `canProposeOptions` | in `COLLECTION`: a privileged account or a live member of the committee's electorate | `addOption`
| `canRate` | `RATING`, in the frozen snapshot of the current round, not yet rated, active membership | `castResistanceBallot` (including `requireActiveMembership`)
|===

Every action is a pure function of the consensus, these flags and the result, returning hidden, enabled or disabled-with-reason (`Gate`);
the revote returns `Hidden`, `Primary` or `Secondary`. A disabled action shows its reason as visible text.

[cols="2,4,3", options="header"]
|===
| Status | Main action | Other
| `COLLECTION` | "Optionen einfrieren" (confirmation names the count, focus on "Abbrechen"); disabled without options | add / remove options, abort
| `RATING` | "Zur Bewertung" (members), "Bewertung schließen" (managers) | abort; counter "n von m haben bewertet"
| `CLOSED` | "Auswerten" (a binding consensus asks first and says it cannot be undone) | abort
| `EVALUATED` | revote, primary when the server reports `groupConflictWarning` for the winner or there is no winner (V1.9.42: decided by the server's own booleans, never by a figure) | "Quittung prüfen" (anonymous)
| `ABORTED` | none | none
|===

== Server additions (no migration)

All four read existing tables; `V1__baseline.sql` is unchanged and there is no new migration. (V1.9.39 adds `V68__systemic_consensus_option_rationale.sql`, see below.)

[cols="2,5", options="header"]
|===
| Addition | Guarantee
| `getSystemicConsensusResult(id)` | Only `EVALUATED` (otherwise a conflict). Computed by `computeSystemicConsensusOutcome`, the very function `evaluate` uses (extracted unchanged), so the display can never drift from what was recorded. Results of earlier rounds are not retrievable.
| `getSystemicConsensusParticipation(id)` | Only the caller's *own* flags plus public counters. Every lookup is filtered to the round of the row, so a rating from round 1 does not survive into round 2.
| `listSystemicConsensusParticipations(ids)` | The batch variant for the list: at most 100 distinct ids (otherwise a conflict), a constant number of queries, own flags only.
| `verifySystemicConsensusReceipt(id, code)` | Only for an anonymous consensus (otherwise a conflict). A code that cannot exist (not 27 Base64url characters) is `found = false` without a query. The receipt's resistances are returned only when the consensus is `EVALUATED` *and* the receipt belongs to the current round.
| length check in `addOption` | The text is trimmed and must be 1..200 characters (the column is `VARCHAR(200)`); otherwise a conflict instead of a database error.
|===

== The resistance booth

The booth is an irreversible single-shot action, so it is its own mode: it replaces the whole detail view (the URL does not change) and
has three steps.

[source,kuml,name="consensus-booth-flow"]
----
sequenceDiagram(name = "Resistance booth") {
    val member = lifeline(name = "Member")
    val booth = lifeline(name = "Booth (client)")
    val server = lifeline(name = "SystemicConsensusService")

    message(from = member, to = booth, label = "rate every option 0..10 (one radio group per option, nothing preselected)")
    message(from = member, to = booth, label = "check (enabled only when every option is rated)")
    message(from = booth, to = member, label = "review: option and rating as plain sentences, 'cannot be changed afterwards'")
    message(from = member, to = booth, label = "submit for good (once: the button locks)")
    message(from = booth, to = server, label = "castResistanceBallot(option id -> rating)")
    message(from = server, to = booth, label = "ok + receiptCode (anonymous) | ok | Conflict | Forbidden | network failure")
    message(from = booth, to = server, label = "on Conflict / failure: getSystemicConsensusParticipation + getSystemicConsensus (no toast, no message read)")
    message(from = server, to = booth, label = "hasRated? status still RATING?")
    message(from = booth, to = member, label = "receipt in groups of four | already rated | rating closed | please wait and retry")
}
----

The radio buttons of one option form a group named by a running group index; the buttons carry a running index as id. Neither an option id
nor the value a button stands for is ever written into an attribute, and there is no `data-*` attribute. The ratings live in one private
map of the booth (and the buttons' own checked state); the map is emptied when the request has been sent and the form DOM is thrown away.

The status quo option is stored with an English label by the server. The client recognises it by `isStatusQuoOption`, shows it last, translated
as "Alles bleibt wie bisher (Passivlösung)" everywhere (booth, review, result, receipt check), and never removes it.

[cols="2,5", options="header"]
|===
| Outcome | The booth says
| ok with a receipt code (anonymous) | the receipt, shown once; "Fertig" stays disabled until the member ticks "I have noted the receipt"
| ok without a code (open), or a code of the wrong shape | a thank-you; a wrong-shaped code is never drawn
| `Forbidden` | not eligible in this round
| `Conflict`, then `hasRated` | already rated
| `Conflict`, status no longer `RATING` | the rating is closed
| `Conflict`, status `RATING`, not rated | please wait and retry (typically: the conference stream is not paused yet, `SecretBallotStreamLock`); the ratings are kept and nothing is resent automatically
| network failure, then `hasRated` | counted, only the confirmation did not arrive
| network failure, unknown | the connection was interrupted; reload to find out
|===

=== Shared rating booth (V1.9.41)

The flow of the booth (rate every item, check, submit for good, explain failures by reading the state) now lives in `RatingBooth.kt`,
which knows no service and no DTO. `ConsensusBooth.kt` is a thin adapter (same signature, same texts, same receipt hand-over) and
`PollRatingBooth.kt` is the adapter of the consensus polls (see `polls.adoc`). Consequences:

* The conference room still uses `renderConsensusBooth` with `ConsensusBoothRoomHost`; the hook is mapped onto the shared booth's own
  room host, so the room files are unchanged.
* *One deliberate tightening:* coming back from the check step, the choice is restored as a DOM *property* (`checked = true`, after the
  first render), no longer as a `checked` attribute. The poll tripwire forbids the attribute for polls ("property only"), and the shared
  booth has to meet the stricter rule. What a member sees, the texts, the flow and every consensus test are unchanged; only the markup no
  longer carries a `checked` attribute after "Zurück".
* The calculation of one option (`computeSkOptionResult`, `SystemicConsensusTally.kt`) was extracted from the tally without any behavioural
  change; `SystemicConsensusTallyRegressionTest` compares the results to a frozen copy of the old code, double bits included.
* `renderOptionRationale` delegates to `renderUntrustedExplanation`; `renderResistanceDistribution` (the histogram) is shared with the poll
  result.

== Receipt handling

Same rules as the elections' receipt (`elections-ui.adoc`): 27 Base64url characters checked against their exact alphabet, drawn character by
character in groups of four, present only in the screen node, its hidden print twin and the closure of the "copy" button, never in storage,
URL, `AppState`, toast or console; a `beforeunload` guard and the hidden "back" button while it is shown; "Fertig" removes everything.

"Quittung prüfen" (anonymous consensus, from `RATING` on) reads the typed code once and clears the field. It says: not found; found but from
an earlier round and no longer counted; found and stored (values only after the evaluation); found with the values.

== Secrecy rules of the displays

* An anonymous consensus' single ratings are never requested: the result shows only the aggregates per option (mean, group conflict, the
  distribution) -- and below five ratings not even those (see "Minimum participation (V1.9.42)"). Only an *open* consensus lists who rated what, through `listResistanceBallots` (which returns nothing for an anonymous one anyway, V1.9.44), and only in `ConsensusResultView.kt`.
* `castAt` is never read by the consensus screens.
* Everything a member typed (titles, option texts, names) is sanitized before it becomes widget content.
* No exception message is read: conflicts get fixed texts and the screen reloads. `ConsensusSecrecyTripwireTest` pins all of this.

== Result display

Options are ranked by mean resistance, lowest first. Per option: the mean ("Ø 2,4 von 10"), the group conflict index in words
(below the viable threshold "Tragfähiger Konsens", up to the warning threshold "Mit Bedenken", above "Warnsignal") with the small number,
a hint when any single rating reached the strong-objection threshold of the scale (a mean can hide a strong objection; see V1.9.39 below), and a collapsed rating distribution with all eleven
columns (gaps filled with 0). A tie without a winner and a consensus without ratings say so in words. A binding result says that it was
recorded as a resolution and, when the status quo option won, that the motion counts as rejected.

== Minimum participation (V1.9.42)

*Rule.* An anonymous consensus (`secret = true`) whose *current round* holds fewer than `DisclosureRules.MIN_ANONYMOUS_RESPONSES` (5) ballots
discloses no figures. The constant is shared with the anonymous polls (`PollRules.MIN_RESPONSES_FOR_RESULT` is an alias of it), so the two features cannot
drift apart. An open (non-anonymous) consensus is unaffected: its ratings are public anyway.

*Where it is applied.* In exactly one place on the server: `SystemicConsensusOutcome.toResultDto` in `SystemicConsensusOutcome.kt`, the only way to a
`SystemicConsensusResultDto`. Both `evaluate` and `getSystemicConsensusResult` go through it, and the binding decision in `evaluate` is still made from the
full data -- only the *disclosure* is reduced. There is no role exception: managers and moderation receive the withheld form too.
`ServerConsensusDisclosureTripwireTest` pins that no other file builds the DTO or reads the ratings table.

[cols="2,5", options="header"]
|===
| Field of `SystemicConsensusResultDto` | Below the minimum
| `figuresWithheld` / `minimumResponses` | `true` / `5` (new, additive; default `false` / `5`)
| `optionResults` | **empty** -- no mean, maximum, deviation, index, distribution, and no ranking either (a ranking is itself a figure)
| `winnerOptionId`, `tie`, `tiebreakApplied`, `consensusViable`, `groupConflictWarning`, `noRatings` | unchanged, computed from the full data
|===

`listResistanceBallots` is stricter than the figures (V1.9.44): an anonymous consensus never delivers a single ballot -- in any status, at any participation,
to any role including BOARD/ADMIN -- it returns `[]` (before V1.9.44 it returned the complete single ballots of an evaluated anonymous consensus from five
ballots on, and in every status one row per ballot with id and cast time). An unknown id is still a NotFound, so the answer carries no existence oracle. The aggregates
(`getSystemicConsensusResult`) stay visible from five ballots on; only the single ballots are gone. The one decision point is
`disclosedSystemicConsensusBallots` / `systemicConsensusSingleBallotsDisclosable` in `SystemicConsensusOutcome.kt`; it decides before it reads the ballot or rating
table, and `ServerConsensusDisclosureTripwireTest` pins this order, the single DTO builder and the allowlist of ballot-table readers.

[cols="2,5", options="header"]
|===
| Read path (anonymous consensus) | Delivers
| `listResistanceBallots` | `[]` always, no role exception
| `getSystemicConsensusResult` / `evaluate` | aggregates per option from five ballots on, otherwise `figuresWithheld`
| `getSystemicConsensusParticipation` / `listSystemicConsensusParticipations` | the caller's own participation state and public counters
| `verifySystemicConsensusReceipt` | only the caller's own ratings, by receipt code
|===

Receipt verification returns only the
caller's own ratings and is unchanged; the room state (`RoomBallotDto`) never carried a figure and is pinned by an allowlist test.
The minimum is judged per round: a revote with fewer ballots withholds again, one with five or more discloses.

*Client.* Both result renderers (the detail page and the room operator step) branch on `figuresWithheld` only -- never on the emptiness of
`optionResults`. A withheld result shows the winner line, the sentence "Aus Datenschutzgründen werden Zahlen bei anonymem Konsensieren erst ab 5 Bewertungen
gezeigt.", the group-wide verdict in words (from `consensusViable` / `groupConflictWarning`), and the options in their list order (P, 1, 2, ...) with the
winner badge and the collapsed rationale -- no rank, mean, bar, group conflict number, highest-value count, strong-objection hint or distribution. With no
ratings at all there is no sentence and no verdict. The revote offer (`canReopen`) reads `groupConflictWarning`, not an index.

*Residual risk, stated plainly (accepted):*

* R1: with one participant the winner is the option with that person's lowest rating; a tie of the minima (visible as `tie` / `tiebreakApplied`, or REPEAT
  meaning "no winner") reveals that at least two options share it.
* R2: the group-wide verdict narrows the range of the winner's rating or sum (default thresholds, scale 10, n = 1: viable 0-1, with concerns 2-5, warning 6-10).
* R3: for a binding consensus the resolution status REJECTED reveals that the passive option had the minimum.
* R4: with two participants the same holds for sums; whoever knows their own rating can narrow the other.
* R5: the participation counter (`ballotCount` / `eligibleCount`) stays visible; `figuresWithheld` only says "fewer than 5", which the counter already shows.
* R6: also above the threshold: homogeneity or collusion of n - 1 participants reveals the last rating; whoever can read the database or its backups sees the
  ratings (a table separation, not cryptography).

An earlier leak through the ranking order of the result (the order of the rows exposed the order of the means) is closed by the empty `optionResults`.

== Exclusivity on the motion page

While a consensus is collecting or rating, or a binding one exists, it owns the motion: the resolution section shows "Zu diesem Antrag läuft
ein Konsensieren." and hides the quorum, vote, election and consensus forms (the server refuses them anyway; the screen offers less than the
server allows, never more). A finished advisory consensus is only a link to its result; the other ways stay. One non-aborted consensus per
motion is allowed. Pending amendments disable "Konsensieren eröffnen" with the other three ways. A `CLOSED` or `OPEN` meritocratic vote hides
the section's forms, like the server's `requireNoOpenVote`.

== Practice alignment, part 1 (V1.9.39)

Small points that bring the screens closer to how a Systemic Consensus is run in practice. One migration (`V68`), no new read call.

=== Order and numbers

* The status quo option ("Passivlösung", *P*) is listed *first* everywhere: options list, booth, named-ratings table. The server keeps it at
  position 0; the client orders through one helper (`consensusOrderedOptions`: P first, then the real options by `(position, id)`).
* Every option carries a plaque: *P* for the status quo option, *1..n* for the real options. The number is the *rank among the real options*
  in that order (gap-free), never `position` itself (a removal leaves gaps, equal positions are possible). Options cannot change after
  `freezeOptions` (add and remove need `COLLECTION`, `reopenRating` does not touch them), so the numbers are final from the freeze on -- also
  across revotes. In `COLLECTION` they can still move, and the list says so.
* Screen readers get "Option 3" as a visually hidden prefix; the plaque itself is `aria-hidden`. The option text is never concatenated with
  the number. The result shows the plaque instead of the rank digit (the rank stays readable as "Platz 1", visually hidden). The operator
  list in the room shows plaques as well; the receipt does not (known limitation).

=== Highest-value count and strong-objection threshold

* Each result row shows how often the top value of the scale was given ("Höchstwert 10 vergeben: 2-mal"), also when it is 0. The server
  already delivered the whole distribution to every signed-in member (also for an anonymous consensus) and has *no* minimum participation, so
  this number reveals nothing that the collapsed histogram did not: with one or two participants, mean and histogram expose single ratings,
  as before. This wave does not change that.
* The "strong objection" hint is no longer a fixed 9. It applies from the *upper tenth of the scale, rounded up*, computed in integers:
  `ceil(0.9 * scaleMax) = (9 * scaleMax + 9) / 10` (shared function `SystemicConsensusRules.strongObjectionThreshold`).
  Scale 5 -> 5, 7 -> 7, 10 -> 9, 11 -> 10, 20 -> 18. The booth legend is derived from the scale ("... · 7 = für mich nicht tragbar.").

=== Rationale of a proposal

* Optional free text per real option, at most 1000 characters (UTF-16 units *and* code points), at most 20 line breaks, normalised by the
  shared `PublicTextRules` (CRLF -> LF, tab -> space, trimmed, control/bidi characters rejected). Blank or `null` means none.
* Written with the proposal (`addOption`) or afterwards with `setOptionRationale(optionId, rationale)`: by the proposer or by the managers
  (same rule as removing), only in `COLLECTION`, never for the status quo option. The server locks the consensus row (`FOR UPDATE`) and
  re-checks the phase, so a rationale cannot be changed after a concurrent `freezeOptions` committed. A rejection is always the one fixed
  conflict text -- the input, ids and reasons are never echoed or logged.
* Shown in full in the options list, clamped to three lines (with a "Mehr anzeigen" switch for long text) in the booth on the page, behind a
  "Begründung" switch in the compact room booth, and behind "Begründung anzeigen" in the result. Never in the booth's review step, the receipt
  or the room's operator list. It is member input: shown only through the untrusted-text helpers, never in `title`, `aria-label` or a
  `data-*` attribute, never in a toast, a log or storage (`ConsensusSecrecyTripwireTest` pins this). The edit field is prefilled with the
  *sanitized* text.
* GDPR: the text of a proposal and its rationale are part of the decision record; they are exported to their author and retained on erasure
  (reason "Procedure record (text+rationale).").
* Anonymity: "Vorgeschlagen von" and the rationale concern *proposals*, not ratings. Both stay visible for an anonymous consensus; the
  anonymity of the ratings is unchanged.

== Known limitations

* A binding consensus has exactly one round (`evaluate` records the resolution at once; `reopenRating` then refuses). The form says so, the
  round label reads "Eine Runde (Beschluss)". For a discussion round, run the consensus as a poll first.
* The results of earlier rounds are not retrievable after a revote.
* V1.9.42: an anonymous consensus below five ratings in the current round discloses no figures (see "Minimum participation"); the residual risks R1 to R6
  of that section remain. `listResistanceBallots` has returned `[]` for every anonymous consensus since V1.9.44.
* The booth is embedded in the conference room since V1.9.32 (see the last section); the room has no results distribution.
* V1.9.39: the receipt carries no option numbers; the status quo option has no rationale; `addOption`/`removeOption` take no row lock against a
  concurrent `freezeOptions` (only `setOptionRationale` does); `scaleMax` has no server-side upper bound and the compact room grid has a fixed
  11 columns; rationales travel with `listSystemicConsensuses` (up to 25 x 1000 characters per consensus); there is still no minimum
  participation for anonymous results (closed by V1.9.42).
* The staging test is written, not executed: `consensus-staging-test.adoc`.

== In the conference room (V1.9.32)

The booth also runs inside the room panel (`ConferenceVotePanel.kt`), through a `ConsensusBoothRoomHost` (exit text, stream lock of an anonymous
consensus, busy signal, compact grid). Without a host the booth is unchanged. The room's card, the stream lock, the operator steps and
their limits are described in `conference-voting.adoc`, section "Systemic consensus in the room panel (V1.9.32)".
