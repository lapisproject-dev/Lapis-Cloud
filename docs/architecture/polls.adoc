= Opinion polls on an LTR basis, server and web UI (V1.9.30, V1.9.31)
:toc:

== Purpose

A poll is a *non-binding opinion poll* (Stimmungsbild) that a committee leader or the board puts to the active members. It is
deliberately separate from the elections (`ElectionService`) and the meritocratic votes (`GovernanceService`): a poll is never a
resolution (`PollDto.binding` is always `false`), is bound to no motion and no meeting, and moves *no LTR*. The responder's free LTR
balance is only read and stored as a weight snapshot, so the result can be shown twice: by head count and weighted by LTR.

V1.9.30 is the server (`IPollService`, `V65__polls.sql`, `PollService`); V1.9.31 adds the web UI (see "Web UI (V1.9.31)") and the one
read-only RPC `canCreatePolls()` it needs, without a migration.

NOTE: This document's `[kuml]` blocks are rendered and validated by the `:docs-render:renderDocs` Gradle task.

== Roles

[cols="2,4", options="header"]
|===
| Action | Who
| Create | ADMIN/BOARD, or a holder of a recording seat (`CHAIR`, `DEPUTY_CHAIR`, `GENERAL_SECRETARY`, `SECRETARY`, `MANAGING_DIRECTOR` -- the set of `COMMITTEE_RECORDING_ROLES`) in *any* active committee as of today, who is an ACTIVE member
| Close / abort | The creator while still creator-capable, or ADMIN/BOARD. The chair of another committee may not close somebody else's poll.
| Respond | ACTIVE members only. GUEST, FRIEND, federated guests, APPLICATION, WITHDRAWN and REJECTED are refused with `ForbiddenException` *before* the poll is looked up.
| Read | ACTIVE members, or creator-capable callers
| Ask "may I create?" | Every authenticated caller, through `canCreatePolls()` (V1.9.31): it returns `true`/`false` for the caller's own capability and never throws `ForbiddenException`, so it is no existence oracle. It is a UI hint only; `createPoll` checks again.
|===

Authorization is always checked before existence, so a refused caller cannot probe which poll ids exist. Error messages never contain
member ids.

== Lifecycle and lazy expiry

[source,kuml,name="polls-lifecycle"]
----
stateDiagram(name = "Poll, effective status") {
    val start = initialState()
    val open = state(name = "OPEN")
    val closed = state(name = "CLOSED")
    val aborted = state(name = "ABORTED")

    transition(source = start, target = open) {
        trigger = "createPoll"
        guard = "[creator-capable, fewer than 20 open polls]"
    }
    transition(source = open, target = closed) { trigger = "closePoll (manual)" }
    transition(source = open, target = closed) {
        trigger = "deadline passed (read-only, never written)"
        guard = "[closes_at <= now]"
    }
    transition(source = open, target = aborted) { trigger = "abortPoll" }
}
----

`poll.status` stores only the *manual* states. A poll whose deadline has passed keeps the stored status `OPEN` and is reported as
`CLOSED` to every reader (`PollLifecycle.effectiveStatus`). It is never written back: there is no background job, no "system actor" in the
audit log, and a read path never writes or takes the audit lock. The deadline is already in the audit entry written at creation, so the
expiry produces no entry of its own. Every status filter, the open-poll cap and `canRespond` therefore use the *effective* status
(`effectiveOpenPredicate` in SQL). An expired poll can neither be answered nor closed nor aborted (`ConflictException`).

The deadline must lie between 15 minutes and 365 days in the future; that catches a typo with an already-past deadline and "eternal" polls.

== Anonymity model

[source,kuml,name="polls-model"]
----
classDiagram(name = "Polls -- Data model") {

        attribute(name = "status", type = "PollStatus")
        attribute(name = "createdBy", type = "UUID")

        attribute(name = "closedAt", type = "LocalDateTime", isReadOnly = true)
    }
    val option = classOf(name = "PollOption") {
        attribute(name = "id", type = "UUID")
        attribute(name = "position", type = "Int")
        attribute(name = "text", type = "String")
    }
    val participation = classOf(name = "PollParticipation") {
        attribute(name = "id", type = "UUID")
        attribute(name = "memberId", type = "UUID")
    }
    val response = classOf(name = "PollResponse") {
        attribute(name = "id", type = "UUID")
        attribute(name = "weightLtr", type = "BigDecimal")
    }

    association(source = poll, target = option) {
        source { multiplicity(spec = "1") }
        target { multiplicity(spec = "2..10"); role = "options" }
    }
    association(source = poll, target = participation) {
        source { multiplicity(spec = "1") }
        target { multiplicity(spec = "0..*"); role = "participations" }
    }
    association(source = poll, target = response) {
        source { multiplicity(spec = "1") }
        target { multiplicity(spec = "0..*"); role = "responses" }
    }
    association(source = option, target = response) {
        source { multiplicity(spec = "1") }
        target { multiplicity(spec = "0..*"); role = "chosenBy" }
    }
    association(source = member, target = participation) {
        source { multiplicity(spec = "1") }
        target { multiplicity(spec = "0..*"); role = "participations" }
    }
}
----

NOTE: The diagram shows *no* connection between `PollParticipation` and `PollResponse`, and none between `Member` and `PollResponse`.
That is the design, not an omission.

* `poll_participation` says *who* answered, `poll_response` says *what* was answered. The two tables share no key.
* `poll_response` has no `member_id` and no time column; `poll_participation` has no time column. A constant time column (as the secret
  elections use since V1.9.23) would carry no information; an omitted one is stricter and spares the question of what to put into it.
* Both tables use random UUIDv4 ids, the application never orders responses by id, and the poll row lock (see below) means participation
  and response of one cast are written in the same step.
* `poll_response.weight_ltr` is the LTR balance of the responder as of the poll's creation instant (`LtrBalanceProvider.balanceAsOf(memberId, poll.created_at)`, the ledger sum with `created_at <= poll.created_at`, i.e. the balance
  the member sees as "my balance"; staked or bound LTR is already booked off and does not count), clamped to `>= 0`, scale 2.
* Single responses never leave the database layer. `getPollResult` reads `GROUP BY option_id` aggregates only, and the result computation
  (`PollTally`) is a pure function over those aggregates.
* Responses are *never* audited. The audit trail records `CREATE` / `UPDATE` (close) / `VOID` (abort) of the poll itself, with a snapshot
  of the question, the options, the status and the two instants. No counters, no weights, no respondents.
* The response count (`responseCount`) is `null` while a poll is open and for an aborted poll, so an observer who watches a counter cannot
  tie a click to a participation. An aborted poll keeps its responses but never discloses them.

=== Disclosure rules

LTR balances are practically public (movements are public; treasurer, board and admin can read any balance). A weighted share that rests
on one or two votes would therefore identify a person. The result is limited accordingly:

[cols="2,5", options="header"]
|===
| Result | Disclosed only if
| Head count | at least 5 responses (a unanimous result of 3 would reveal all three answers to anybody who knows the participants)
| Weighted result | at least 5 responses, a positive total weight, at least 5 responses with weight > 0, *and* every option with any weighted vote has at least 3 of them
|===

The weighted result consists of *whole-percent shares* only, never absolute LTR sums, computed by the largest-remainder method on exact
integer arithmetic (ties go to the lower option position), so the shares sum to exactly 100. If any rule fails, the weighted result is
withheld *entirely* with a reason (`TOO_FEW_RESPONSES`, `ZERO_TOTAL_WEIGHT`, `TOO_FEW_WEIGHTED_RESPONSES`, `SMALL_WEIGHTED_GROUP`),
never one suppressed share: a single missing share could be recomputed as "100 minus the rest". A weight of 0 counts fully in the head
count and not at all in the weighted result. The consequence is that small polls often show no weighted result.

== Locking and the open-poll cap

Every transaction takes its locks in one order, so no two of them can wait for each other in a cycle:

[cols="1,3,3", options="header"]
|===
| Step | Lock | Taken by
| 1 | `organization_settings` row, `FOR UPDATE` | `createPoll` only -- the global mutex for the cap of 20 effectively open polls
| 2 | `poll` row, `FOR UPDATE` | `castPollResponse`, `closePoll`, `abortPoll`
| 3 | audit log chain | `createPoll`, `closePoll`, `abortPoll`; always the last write (`AuditLogRecorder`)
|===

* `castPollResponse` and `closePoll`/`abortPoll` exclude each other through the poll row lock; "now" is read *after* the lock, so no
  response can land after the poll closed. Concurrent casts of one member serialise on the same lock, and the `UNIQUE (poll_id, member_id)`
  index is the backstop behind the application-level check; an `ExposedSQLException` is translated into a `ConflictException` inside the
  transaction.
* The cap is counted under the settings lock, because without it two concurrent creations both read "19 open" and both insert.
* Casting writes no ledger entry and takes no `lockForDebit`: the weight is a read-only snapshot.

== Data protection

`PollPersonalData` covers `poll` (`created_by`, `closed_by`) and `poll_participation` (`member_id`). The export lists the polls a member
created, closed or aborted and the ids of the polls he took part in -- never an answer, which cannot be attributed to him. Erasure
hard-deletes the member's participations (an erased member is not ACTIVE any more and can never answer again) and retains
`created_by` / `closed_by` as accountability for an organisation-wide question (precedent: `ElectionPersonalData`). `poll_option` and
`poll_response` carry no member reference and are in the `noPersonalDataAllowlist` with that reason.

== Web UI (V1.9.31)

Routes: `/polls` (list) and `/polls/:id` (detail), in the navigation group "Selbstverwaltung" directly after "Konsensieren"
(`NavVisibility.showsPolls`: ACTIVE members only, like the rest of the group). A GUEST or FRIEND who types the address gets the silent
redirect described below; the server refuses them anyway.

*List.* A status filter ("Offen", "Geschlossen", "Abgebrochen"; open by default, kept only in a local variable -- no storage, no URL), one row per
poll with the status, the deadline, the viewer's own state ("Offen für Sie" as a badge, "Beantwortet" as quiet text) and -- for closed polls
only -- the number of answers. "Mehr laden" asks for the next page of 50 (the screen requests 51 rows to know whether a next page exists and
cuts the extra one off; the offset is clamped to `PollRules.MAX_LIST_OFFSET`). The viewer's own states come in batches of
`PollRules.MAX_PARTICIPATION_BATCH`, never one call per row. "Umfrage erstellen" appears only if `canCreatePolls()` is `true`.

*Create form.* A `lapisForm`; the option fields are real form fields that are added (up to 10) and removed (from the third on) at run
time. The draft is validated with the constants of `PollRules` (question 500, description 2000, option 200 characters, 2..10 options,
duplicates by `PollRules.optionKey` of the normalised text, deadline between 15 minutes and 365 days); "Umfrage starten" stays disabled
while the draft is invalid and the first reason is shown under it. Deadline presets: 24 hours, 3, *7 (default)*, 14, 30 days, "Eigenes
Datum" or "Ohne Frist". The form says in a box that the poll is non-binding, the answers are anonymous and the result is visible only
after the end. A conflict from the server is shown as ONE fixed sentence that covers all three server limits (20 open polls, 5 per
creator, 10 per 24 hours) -- the server's own text is never shown.

*Detail.* Question, description (preformatted, sanitised), creator and date, deadline, and always the box "Unverbindlich -- ein Stimmungsbild,
kein Beschluss." While the poll is open and the server says the viewer may still answer, the answer booth is shown; after the poll was
closed the result; for an aborted poll the sentence that its answers are never evaluated. Whoever manages the poll sees "Umfrage
schließen" (a confirmation dialog) and "Umfrage abbrechen" (the viewer has to type the word "ABBRECHEN"; the dialog's close button is
labelled "Zurück" so that no second button says "Abbrechen" with the opposite meaning). Both actions are hidden while the check step of the
booth is open, and every successful write reloads the whole detail.

*Answer booth.* An answer is irreversible and anonymous, so the booth is its own mode with three steps and an end state that explains itself:

[source,kuml,name="polls-ui-flow"]
----
stateDiagram(name = "Answer booth") {
    val start = initialState()
    val select = state(name = "Choose")
    val review = state(name = "Check")
    val submitting = state(name = "Submitting")
    val saved = state(name = "Saved")
    val explained = state(name = "Explained by reading the state")

    transition(source = start, target = select) { trigger = "canRespond" }
    transition(source = select, target = review) { trigger = "Weiter" }
    transition(source = review, target = select) { trigger = "Zurueck" }
    transition(source = review, target = submitting) { trigger = "Endgueltig abgeben" }
    transition(source = submitting, target = saved) { trigger = "answer stored" }
    transition(source = submitting, target = explained) {
        trigger = "conflict, refusal or lost connection"
        guard = "[the participation and the poll are read again]"
    }
    transition(source = explained, target = review) {
        trigger = "still open and not answered"
        guard = "[choice kept, nothing is resent by itself]"
    }
}
----

The secrecy model of the client, enforced by `PollSecrecyTripwireTest` and the Karma tests `PollBoothDomTest`/`PollMaliciousTextDomTest`:

* The choice lives in exactly one place: the private `chosenIndex` of the booth (an index into the poll's options) and the radio buttons' own
  checked *state*. It is restored when the member steps back from the check step as a DOM *property* only (`checked = true`), never as an
  attribute, because attributes end up in `outerHTML`. (This is stricter than the consensus booth, which sets the attribute.)
* The radio buttons carry one constant group name and a running index as id; no `value`, no `data-*`, no option id in any attribute.
* `chosenIndex` is emptied in every end state; no toast, no console, no storage, no URL ever carries the answer, and the error texts are
  fixed sentences (Kilua RPC transmits only the exception type, and `e.message` is never read).
* The check step names the chosen option on screen on purpose -- only then does a member really check what is about to be sent. That
  single text node is discarded with the step.
* After a refusal or a lost connection the booth reads the participation and the poll again and says only what is known ("Ihre Antwort ist
  gespeichert.", "Die Umfrage ist beendet.", or -- when nothing could be read -- that the connection was interrupted and the page should
  be reloaded).
* Text a member typed (question, description, option, the creator's name) is sanitised before it is shown, including as placeholder
  arguments and as legend/label content.
* A refused read (`ForbiddenException`) is silent: no toast, no server text, the screen goes back to the dashboard.

*Result.* Two blocks side by side from 900 px on ("Nach Köpfen", "Nach LTR-Gewicht"), one column below. Each option appears once in the
order of the poll -- *never sorted by rank, no winner marker*: a poll is a mood picture, never a resolution. The head block shows whole
percents (largest-remainder method on the head counts, the same method the server uses for the weights) and the number of answers; the
weighted block shows whole percents only, always with the sentence that explains why it can differ from the head count. A block the
server withholds shows the reason in a sentence instead of partial numbers; a withheld head result shows the sentence in both blocks.

=== Known limitations of the UI

* The chosen option is in the DOM during the check step (on purpose, see above).
* The deadline is entered in the browser's local time while the server calculates in its own zone. A browser in another zone shifts the
  presets by the difference, and a custom deadline close to the 15-minute limit can be refused by the server (the form then asks to check
  the details, especially the deadline). The client uses the same 15-minute and 365-day limits as the server and adds no safety margin.
* "Abbrechen" asks for the keyword "ABBRECHEN" (translated per language) instead of the poll's title, because a question can be 500
  characters long.
* The staging test plan (`polls-staging-test.adoc`) was not executed in this wave: nothing was deployed.

== Known limitations

* The weight is bound to the cut-off `poll.created_at`, so LTR transferred or minted after the poll opened does not raise the recipient's
  weight and cannot be passed around to be counted several times. Remaining caveat: LTR held at the cut-off is not locked, so a member can
  still answer and then transfer the same LTR onward (only the answering member's weight counts; the recipient's cut-off balance does not
  grow). Ledger entries with a back-dated `created_at` would still count.
* Polls are limited per creator (5 open polls, 10 created per 24 hours, aborted ones count) in addition to the global cap of 20 open polls.
* Residual risk, stated plainly: whoever can read the database or its backups (an operator or administrator with access) sees option and
  weight per response and can try to match the weights against the public LTR ledger. The countermeasures (random ids, no time columns, no
  member column, no ordering by id) reduce this; they do not prevent it. There is no cryptography: the separation is a table separation,
  like the secret elections.
* The physical insertion order (Postgres heap, WAL) may still correlate a participation with its response; the poll row lock only makes
  the two inserts of one cast adjacent.
* There is no participation rate: eligibility is evaluated live when a member answers, no snapshot of the entitled members is taken.
* The concurrency tests run on H2 only; lock behaviour on Postgres is argued from the lock order, not measured.
* The web UI (V1.9.31) is described in the next section; its known limits are listed there.
