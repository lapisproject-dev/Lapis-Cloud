= Domain Model — V0.1.5 (Contributions, Documents, Communication)
:description: Data model for contribution management, document storage, and communication, including the Member/Account Foundation stub.
:toc:
:toc-placement: preamble

== Context

This document describes the data model introduced with V0.1.5: contribution management,
document storage, and communication (mailing lists + direct messages). `Member` and `Account` are
modelled here only as a **Foundation stub** — as granular as the three V0.1.5 areas need them as
foreign keys. The full member master-data model (application/withdrawal workflow, role and
permission concept, auth/session) follows in V0.1.2-V0.1.4 and replaces this stub without breaking
the foreign keys defined here.

Persistence generation: the `uml-to-erm`/`erm-to-exposed` MDA pipeline (ADR-0016, kUML modules
`kuml-transform-uml-to-erm` + `kuml-codegen-m2m-exposed`, Maven Central) has existed since V3.4.x —
the `dev.kuml` Gradle *plugin* itself, however, is unpublished. For **Foundation**
(`Member`/`Account`, this stub; `lapis-server/src/main/kuml/00-foundation.kuml.kts`),
**contribution management** (`MembershipTier`/`Contribution`;
`lapis-server/src/main/kuml/01-contribution.kuml.kts`), **document storage**
(`DocumentFolder`/`Document`/`DocumentVersion`;
`lapis-server/src/main/kuml/02-document.kuml.kts`), and **communication**
(`MailingList`/`MailingListSubscription`/`MailingMessage`/`MailingDeliveryLog`/`DirectMessage`;
`lapis-server/src/main/kuml/03-communication.kuml.kts`), these `.kuml.kts` files have, since the
MDA persistence retrofit wave, been the versioned source-of-truth model — verified per domain by a
dedicated `SchemaDriftTest`
(`lapis-server/src/test/kotlin/network/lapis/cloud/server/db/{SchemaDriftTest,
ContributionSchemaDriftTest, DocumentSchemaDriftTest, CommunicationSchemaDriftTest}.kt`) against
the real Flyway-migrated schema and the hand-written Exposed `Table` objects — no longer purely
documentary. The hand-written Exposed tables under
`lapis-server/src/main/kotlin/.../db/tables` remain, deliberately, the compiled/actually-imported
artifact (designModelStrategy option B: the enum-to-VARCHAR downgrade and the missing Kotlin
object-name override currently make a full generated-and-compiled swap lossy/disruptive for this
repository — see the header comments in the respective `.kuml.kts` files and CLAUDE.md's
kUML-Repo-Konventionen in the vault for the full rationale). The document-storage domain brought
one further modelling trade-off beyond Foundation/contribution management: `document.folder_id`,
`document.created_by`, and `document_version.uploaded_by` are modelled as plain `«Column»` UUID
attributes rather than UML associations, because `UmlToErmTransformer`'s association-to-FK
column-name derivation (`snake_case(singular(targetClass)) + "_id"`) doesn't match the real column
names and no DSL-side override exists (details in `02-document.kuml.kts`'s header comment). The
communication domain confirms the same naming-derivation trade-off (`mailing_list.created_by`,
`mailing_message.sent_by`) and additionally surfaces the case the retrofit plan flagged as a risk —
two associations from the same class to the same target: `direct_message.sender_id` and
`direct_message.recipient_id` both reference `member`, but `UmlToErmTransformer`'s role-name-based
collision resolution only ever yields `member_id`/`<role>_id` for a genuine association pair, never
both desired column names together — verified empirically during this wave. Both foreign keys are
therefore likewise modelled as plain `«Column»` attributes (details in `03-communication.kuml.kts`'s
header comment and `CommunicationSchemaDriftTest`). With this, all four V0.1.5 domains (Foundation,
contribution management, document storage, communication) are no longer purely documentary but each
verified by its own `SchemaDriftTest`.

== Accounting (SKR42 + double-entry, V0.3.1, chart swapped from SKR49 in V0.3.1.1)

`LedgerAccount`/`JournalEntry`/`Posting` (`lapis-server/src/main/kuml/10-accounting.kuml.kts`,
verified by `AccountingSchemaDriftTest`) implement double-entry bookkeeping on a representative
SKR42 chart of accounts (DATEV's current Kontenrahmen for Vereine, Stiftungen und gGmbHs, based on
SKR04; it replaced SKR49, which DATEV has maintained no further since 01.01.2025). `LedgerAccount`
is deliberately not named `Account` — that name is already taken by the Foundation domain's
user-login `Account`/`AccountRole`.

A SKR42 account number's leading digit (`LedgerAccount.accountClass`, 0-9) is the Kontenklasse.
Unlike the retired SKR49, SKR42 does *not* pre-partition the four Gemeinnützigkeit spheres into
account-number ranges, and the Kontenklassen do not separate income from expense the way a naive
reading might suggest: class 4 holds *all* Erträge/Umsatzerlöse across all four spheres (e.g. 4000
Mitgliedsbeiträge, 4045 Spenden, 4200/4201 Erlöse/Eintrittsgelder), class 5 is itself an *expense*
class (Wareneingang / Aufwendungen für Roh-, Hilfs- und Betriebsstoffe, e.g. 5000/5200
Wareneingang), class 6 covers the remaining operating expenses (e.g. 6000 Löhne und Gehälter, 6310
Miete), and class 7 is the Finanzergebnis (e.g. 7110 Zinserträge, 7300 Zinsaufwand) — covering both
income and expense sub-accounts. None of classes 4-7 are sphere-partitioned; the same account can
be booked to any of the four spheres. Sphere is assigned per booking via a cost center (DATEV
KOST1), not derived from the account. `accountClass` remains a reporting/grouping field only; the
real per-posting cost-center/sphere attribute is `Posting.sphere` -- see
<<four-sphere-separation,Four-sphere Gemeinnützigkeit separation (V0.3.3)>> below.

`JournalEntry.status` is `DRAFT` (incomplete/unbalanced postings allowed, freely editable) or
`POSTED` (immutable, validated balanced at the moment of transition). The balance invariant
(Σdebit = Σcredit per `JournalEntry`) is a cross-row aggregate that no CHECK constraint or index
can express — it is enforced exclusively at the service layer
(`network.lapis.cloud.server.rpc.AccountingService`, backed by the pure
`network.lapis.cloud.server.rpc.JournalEntryBalance` helper) inside the same transaction that
writes the entry and its postings, so an unbalanced attempt never leaves a partial write behind.
`network.lapis.cloud.server.rpc.GeneralLedgerCalculator` computes the Hauptbuch (general ledger)
running balance per `LedgerAccount`, signed by that account's `LedgerAccountType` normal-balance
side (`ASSET`/`EXPENSE` debit-normal, `LIABILITY`/`EQUITY`/`INCOME` credit-normal).

=== Financial statements (V0.3.2)

`network.lapis.cloud.server.rpc.FinancialStatementCalculator` derives three read-only reports
purely from the existing `POSTED` postings — no new persistence, no schema change, and therefore
no new `*SchemaDriftTest`. `IncomeStatementDto`/`BalanceSheetDto`/`AnnualFinancialStatementDto`/
`StatementLineDto` (`lapis-shared/.../domain/FinancialStatements.kt`) are non-persisted reporting
DTOs, exactly like the existing `GeneralLedgerDto`/`GeneralLedgerLineDto`. Three new read-only
`IAccountingService`/`AccountingService` methods expose them, gated by the same TREASURER/BOARD/
ADMIN roles as `getGeneralLedgerAccount`.

* **Gewinn- und Verlustrechnung (GuV / `getIncomeStatement`)** — the flow of `INCOME`/`EXPENSE`
  postings over `[from, to]` (`from == null` means "since inception"). `result` = `totalIncome` −
  `totalExpense`; negative is a Jahresfehlbetrag.
* **Bilanz (`getBalanceSheet`)** — the *cumulative* stock of postings since inception through a
  single `asOf` cutoff, deliberately **not** windowed to a fiscal year. This is the load-bearing
  design decision: `GeneralLedgerDto.openingBalance` is always `0` (no Saldenvortrag/carryforward
  support yet — see that DTO's KDoc), so there is nothing to seed a fiscal-year-windowed Bilanz
  with. Because `INCOME`/`EXPENSE` are never closed to `EQUITY` (no closing entries generated in
  this wave), the Bilanz only balances (Aktiva == Passiva) if the accumulated result
  (Σ`INCOME` − Σ`EXPENSE` through `asOf`) is shown as its own derived equity line
  (`BalanceSheetDto.accumulatedResult`) — this is guaranteed to reconcile by the
  server-enforced Σdebit = Σcredit invariant, and `balanced` is asserted `true` as a regression
  guard in `FinancialStatementCalculatorTest`/`AccountingServiceTest`.
* **Jahresabschluss (`getAnnualFinancialStatement`)** — assumes Geschäftsjahr = Kalenderjahr
  (calendar year) and bundles the GuV of `[Jan 1, Dec 31]` of the given year with the Bilanz as of
  that year's Dec 31. It reports two honest, distinct figures rather than conflating them:
  `periodResult` (that year's GuV flow) and `accumulatedResult` (the inception-cumulative Bilanz
  equity result) — these coincide in the very first fiscal year and legitimately diverge from the
  second year on, since nothing is closed/carried forward between years.

Line lists (`StatementLineDto`) omit accounts with a zero net balance in the requested scope — they
are a derived-from-journal view, not a complete chart-of-accounts listing. Still explicitly out of
scope (unchanged from V0.3.1's list above): fiscal-year close/Saldenvortrag, non-calendar fiscal
years. (Mittelverwendungsrechnung/Rücklagen, originally listed here as a later non-goal, shipped in
V0.3.4 -- see below. Kassenbuch, likewise originally listed here as a later non-goal, shipped in
V0.3.5 -- see further below. Kostenstellen, likewise originally listed here as a later non-goal,
shipped in V0.3.6 -- see further below.)

=== Four-sphere Gemeinnützigkeit separation (V0.3.3)

`Posting.sphere` (`network.lapis.cloud.shared.domain.GemeinnuetzigkeitSphere`) is a mandatory
(`NOT NULL`) per-posting enum column added to `lapis-server/src/main/kuml/10-accounting.kuml.kts`,
tagging every booking line with exactly one of the four legally-mandated Gemeinnützigkeit spheres
(§§ 51-68 AO): `IDEELLER_BEREICH`, `VERMOEGENSVERWALTUNG`, `ZWECKBETRIEB`,
`WIRTSCHAFTLICHER_GESCHAEFTSBETRIEB` (DATEV KOST1 codes 1-4). This is the highest-legal-risk wave
in the accounting backlog: losing the strict separation between these spheres risks the
organization's tax-exempt status, so the guarantee that every posting names exactly one sphere is
enforced structurally at three layers rather than by a single service-layer check —

* the Kotlin type: `PostingInput.sphere`/`PostingDto.sphere` are non-nullable with **no default
  value**, so every call site must supply one explicitly;
* the RPC wire format: `kotlinx.serialization` enum decoding rejects any payload that omits or
  mis-names the field;
* the database: the generated `sphere` column is `NOT NULL` with a `CHECK` constraint restricting
  it to the four real literals.

**Placement**: per-`Posting` (booking line), not `JournalEntry` and not `LedgerAccount`. As the
SKR42 discussion above establishes, sphere is *not* derivable from the account/Kontenklasse — it is
assigned per booking via DATEV KOST1, which is inherently a per-line cost center. A per-line
attribute is also the only placement that lets one balanced `JournalEntry` legitimately record an
inter-sphere transfer (Umbuchung): a debit line in one sphere, a credit line in another. This
deliberately also forces a sphere onto Bestandskonten lines (Kasse/Bank), which are conceptually
sphere-neutral — accepted tradeoff, since the four-sphere report below only aggregates
`INCOME`/`EXPENSE`-typed accounts, so a cash line's sphere is informational only.

**No Sammelposten/KOST9 escape bucket**: `GemeinnuetzigkeitSphere` has exactly the four real
spheres, on purpose — a fifth "unassigned"/collective literal would be a way to *not* assign a
sphere, which contradicts strict separation. A general-purpose, open-ended cost-center/
Kostenstellen allocation mechanism (DATEV KOST2, unrelated to this KOST1 sphere) shipped as its own
`CostCenter` entity in V0.3.6 -- see further below.

**A single `JournalEntry` may span multiple spheres**: no single-sphere-per-entry invariant is
enforced, because sphere is per-line — a cross-sphere Umbuchung is fully transparent since each
line names its own sphere. Inter-sphere transfers are representable this way but are not specially
validated, tracked, or reported this wave; a dedicated §58 AO Mittelweitergabe workflow is deferred
to V0.3.4 (Mittelverwendungsrechnung).

**Reporting payoff** — `getFourSphereIncomeStatement` (`FourSphereIncomeStatementDto`,
`SphereResultDto`, both in `lapis-shared/.../domain/FinancialStatements.kt`; derivation in
`FinancialStatementCalculator.fourSphereIncomeStatement`): the same `INCOME`/`EXPENSE` flow over
`[from, to]` as `getIncomeStatement`, re-aggregated per sphere instead of collapsed across all
four. `spheres` always contains exactly four entries in `GemeinnuetzigkeitSphere` enum order,
zero-filled if a sphere had no activity — so a UI can always render a fixed four-row layout. The
overall `result` equals both the sum of the four per-sphere results and the plain
`getIncomeStatement` result for the identical window: sphere is purely an orthogonal
re-aggregation of the same postings, not a different scope. Gated by the same
TREASURER/BOARD/ADMIN roles as the other statement methods.

Explicitly out of scope for V0.3.3: a four-sphere balance sheet, §64 Abs.3 AO
Freigrenze/taxability evaluation of the wirtschaftlicher Geschäftsbetrieb surplus, and any
dedicated inter-sphere-transfer tracking workflow — all deferred to later waves.

=== Mittelverwendungsrechnung + Rücklagen (V0.3.4)

**This is a treasurer's Nachweis (evidence) aid for §55 AO ("zeitnahe Mittelverwendung") and §62 AO
(Rücklagenbildung) -- it is NOT an automated Gemeinnützigkeit compliance verdict.** It is the
second-highest legal-risk wave in the accounting backlog after V0.3.3, and is scoped deliberately
conservatively: no percentage-cap enforcement, no automatic exemption application, no certification
of tax-exempt status one way or the other.

**Reserves are ordinary `EQUITY` ledger accounts, not a new persisted entity.** A treasurer moves
funds into a reserve via a normal balanced double-entry posting (e.g. debit a general equity
account, credit the reserve account) -- exactly the same mechanism as every other booking in this
codebase. The *only* schema addition this wave makes is one nullable enum column,
`LedgerAccount.reserveType`
(`network.lapis.cloud.shared.domain.ReserveType`: `PROJEKTRUECKLAGE`, `FREIE_RUECKLAGE`,
`WIEDERBESCHAFFUNGSRUECKLAGE`, `BETRIEBSMITTELRUECKLAGE`), which makes an `EQUITY` account
machine-classifiable by its §62 AO reserve category. A dedicated `Reserve`/`ReserveAllocation`
entity was deliberately rejected as over-scoped -- it would duplicate the ledger that already
tracks these balances via ordinary postings. `reserveType` may only be set on an `EQUITY` account
(`AccountingService.requireReserveTypeOnlyOnEquity`, a service-layer cross-column guard, same class
of constraint as the balance invariant -- not expressible as a single-row `CHECK`). §62 Abs.1 Nr.4
(Rücklage zum Erwerb von Gesellschaftsrechten) is not offered as a literal -- out of scope, rare for
a Verein/Partei. **The §62 Abs.1 Nr.3 freie-Rücklage percentage cap is deliberately NOT enforced in
code** -- it is a number a human must configure and verify against current law (see
`ReserveType.FREIE_RUECKLAGE` KDoc); this codebase does not hard-code an assumed percentage.

**`network.lapis.cloud.server.rpc.UseOfFundsCalculator`** (pure, unit-tested without a database,
same idiom as `FinancialStatementCalculator`/`GeneralLedgerCalculator`/`JournalEntryBalance`)
derives the read-only `UseOfFundsStatementDto` (`lapis-shared/.../domain/UseOfFunds.kt`) from the
existing `POSTED` postings plus each account's `reserveType`:

* **Mittelzufluss/Mittelverwendung** (`UseOfFundsYearDto.fundsReceived`/`fundsUsed`) -- the year's
  `INCOME`/`EXPENSE` flow, same derivation as the GuV.
* **Rücklagen-Zuführung** (`fundsAllocatedToReserves`, `reserveMovements`) -- the year's net
  Zuführung to `EQUITY` accounts carrying each `ReserveType`, broken down per type (always four
  entries, zero-filled), plus each type's cumulative closing balance.
* **Per-sphere disaggregation** (`receivedBySphere`/`usedBySphere`) -- purely informational; always
  four `GemeinnuetzigkeitSphere` entries, zero-filled.
* **Mittelvortrag / §55 AO timely-use clock** (`timelyUseObligationRemaining`, `overdueAmount`) -- a
  FIFO "vintage pot": each year's income enters the pot as a new vintage dated to that year; each
  year's expense and *net positive* reserve allocation consume the pot oldest-vintage-first (a
  reserve allocation legitimately removes funds from the §55 clock); a *net negative* allocation
  (dissolution) returns funds to the pot as a **new, current-year vintage** -- a deliberate,
  explicitly flagged simplification (the alternative -- re-deriving the dissolved funds' original
  vintage -- is genuinely ambiguous, and re-dating is the conservative choice, never less likely to
  flag work as time-barred). A vintage is overdue once strictly more than `timelyUseYears`
  (`UseOfFundsStatementDto.timelyUseYears`, currently `2` -- the historically-interpreted "by the
  end of the second fiscal year following receipt", surfaced as data rather than a silent constant
  because it should be verified against current AO guidance) fiscal years have elapsed since its
  vintage year. The pot is floored at `0`, never negative.

**The clock is anchored at inception and is org-wide, not per-sphere.** `statement` always rolls the
FIFO pot forward from the organization's *earliest* fiscal year with any activity through
`toFiscalYear` -- never merely from `fromFiscalYear` -- because windowing the roll-forward itself
would silently corrupt the reported Mittelvortrag/overdue figures whenever the requested window
starts after inception; `fromFiscalYear`/`toFiscalYear` only slice which years are *reported*.
The clock is deliberately aggregate (not split per `GemeinnuetzigkeitSphere`) because surpluses
legitimately move between spheres and a per-sphere clock would misstate the obligation --
per-sphere received/used is informational only, same "cash-line sphere is informational" tradeoff
V0.3.3 already accepted for Bestandskonten. `getUseOfFundsStatement` (role: TREASURER/BOARD/ADMIN,
same as every other statement method) validates `fromFiscalYear <= toFiscalYear` and both years in
range with `BadRequestException`, then loads one `UseOfFundsCalculator.YearFacts` per calendar year
with any `POSTED` activity (`AccountingService.loadYearFacts`) and delegates to the pure calculator.
Only `POSTED` postings contribute -- same "DRAFT is provisional" rule as every other statement.

**Reserve movements are keyed by the ledger account's `reserveType`, never by `posting.sphere`.**
A reserve-transfer posting's two lines are `EQUITY` and still each carry the mandatory (V0.3.3)
per-line sphere, which remains purely informational for these lines -- the reserve-movement loader
groups strictly by the target account's `reserveType`, so a transfer whose debit and credit lines
happen to name different spheres still books cleanly and is counted exactly once under its reserve
type.

Explicitly, deliberately out of scope for V0.3.4 (see `UseOfFundsCalculator`/`ReserveType` KDoc for
the full list, each flagged individually): the §62 Abs.1 Nr.3 freie-Rücklage percentage-cap
enforcement; automatic application of the §55 Abs.1 Nr.5 Satz 4 small-organization
(≤45.000 EUR) exemption; any automated "Gemeinnützigkeit lost/retained" verdict or certification;
§64 AO Freigrenze evaluation (later compliance-bundle territory); non-calendar fiscal years; and
any client/KVision UI (this is a backend-only wave). (Kassenbuch, listed here as a later non-goal,
shipped in V0.3.5 -- see below. General-purpose Kostenstellen, likewise listed here as a later
non-goal, shipped in V0.3.6 -- see further below.)

=== Kassenbuch (V0.3.5, GoBD-Vorstufe)

**This is the foundational piece a future V0.5 GoBD (Grundsätze zur ordnungsmäßigen Führung und
Aufbewahrung von Büchern) bundle needs to build on -- full GoBD tamper-evidence (cryptographic
hash-chaining, formal retention-period enforcement, audit-log infrastructure, TSE/
Kassensicherungsverordnung technical-security-equipment integration) is explicitly OUT of scope
this wave.** A Kassenbuch (cash book) is a chronological, gapless record of every cash-register
(Kasse) movement -- date, description, Beleg (voucher) reference, Einnahme/Ausgabe (amount in/out),
and running balance.

**`LedgerAccount.isCashRegister` is the only schema addition this wave makes** (NOT NULL boolean,
default `false`). `accountClass` alone cannot identify a physical cash register: SKR42 Kontenklasse
1 ("liquide Mittel") also holds `18000 Bank (Girokonto)` and
`12000 Forderungen aus Lieferungen und Leistungen`, both `ASSET` like `16000 Kasse` -- see
`DevSeedData.kt`. `isCashRegister` may only be `true` on an `ASSET` account
(`AccountingService.requireCashRegisterOnlyOnAsset`), the same class of service-layer cross-column
guard as `reserveType`'s only-on-`EQUITY` rule above -- not expressible as a single-row `CHECK`.
**The Kassenbuch itself is NOT a new persisted entity** -- `network.lapis.cloud.server.rpc
.KassenbuchCalculator` (pure, unit-tested without a database, same idiom as
`GeneralLedgerCalculator`/`JournalEntryBalance`/`UseOfFundsCalculator`) derives it purely from the
account's existing immutable `POSTED` postings, delegating the running-balance math to
`GeneralLedgerCalculator.runningBalances` with the `ASSET` (debit-normal) side and re-labelling each
line's single signed DEBIT/CREDIT amount into an Einnahme (`amountIn`)/Ausgabe (`amountOut`) pair --
a real Kassenbuch's columns, not Soll/Haben. `KassenbuchLineDto.kassenbuchNumber` is a 1-based,
gapless sequential line number derived purely from chronological ordering of the account's `POSTED`
postings -- no new persisted sequence, safe because a `POSTED` entry can never be reordered or
renumbered. This mirrors V0.3.4's "derive a report from the existing journal, add at most one
classificatory column" pattern.

Two GoBD-informed guards are enforced at the service layer (`AccountingService`), both **only at
the moment an entry becomes `POSTED`** (`postJournalEntry`, and the `postDraftEntry` DRAFT→POSTED
transition) -- `saveDraftEntry` stays free-form, matching the existing "draft is provisional"
philosophy:

* **"Kein Buchen ohne Beleg"** (`requireVoucherForCashPostings`) -- a posting set referencing any
  `isCashRegister` account is rejected (`ConflictException`) unless the entry's `voucherReference`
  is non-blank. Every other (non-cash) posting is unaffected -- `JournalEntry.voucherReference`
  stays nullable/optional, no schema change, no regression for existing non-cash bookings.
* **Never-negative cash balance** (`requireNonNegativeCashBalances`) -- for each `isCashRegister`
  account an entry's own postings touch, this entry's net signed delta for that account (aggregated
  across all of the entry's lines against it, not checked line-by-line -- a single entry may
  legitimately carry offsetting lines against the same cash account) is added to that account's
  pre-existing cumulative `POSTED` balance; a strictly negative projected result is rejected
  (`ConflictException`). Draining a cash account to exactly `0` is allowed -- only a strictly
  negative balance is not. Since `isCashRegister` implies `ASSET`, the normal-balance side is always
  `DEBIT` -- computed via `GeneralLedgerCalculator.normalBalanceSideOf(LedgerAccountType.ASSET)`
  rather than a second, hardcoded sign-convention constant.

**`getKassenbuch`** (role: TREASURER/BOARD/ADMIN, same as every other statement method) returns the
`KassenbuchDto` for one `LedgerAccount` over `[from, to]` (`from == null` means "since inception"),
only `POSTED` postings contributing -- same "DRAFT is provisional" rule as `getGeneralLedgerAccount`.
Rejects with `ConflictException` if the account exists but is not `isCashRegister` (wrong kind of
resource for this endpoint -- requires a DB lookup of persisted state to evaluate, same tier as the
other existing-entity-wrong-state checks), and `NotFoundException` if it does not exist at all -- mirrors
`getGeneralLedgerAccount`'s existing not-found behavior. `Posting.sphere` stays mandatory even on
cash-account lines (unchanged V0.3.3 rule, informational only there) and is deliberately NOT
surfaced in `KassenbuchLineDto` -- the Kassenbuch is a cash-audit view, not a Gemeinnützigkeit-sphere
report.

Explicitly, deliberately out of scope for V0.3.5 (deferred to V0.5's GoBD bundle unless noted
otherwise): cryptographic tamper-evidence/hash-chaining; formal retention-period enforcement; full
audit-log infrastructure; TSE (Kassensicherungsverordnung) integration; non-calendar fiscal years;
and any client/KVision UI (this is a backend-only wave, same as every prior accounting wave).
(General-purpose Kostenstellen, listed here as a later non-goal, shipped in V0.3.6 -- see below.)

=== Kostenstellen-/Projektbuchhaltung (V0.3.6)

**`CostCenter` is a new, independent, open-ended entity** (DATEV KOST2 sense) -- unlike the fixed
`GemeinnuetzigkeitSphere`/`ReserveType` enums above, a treasurer creates a new cost center per
project/campaign/event as needed (e.g. `SOMMERFEST-2027`, `WINTERHILFE-2027`), so it needs its own
id/lifecycle rather than a fixed literal set. `CostCenter` (`code`, `name`, `description`, `active`)
mirrors `LedgerAccount`'s own `accountNumber`+`name` split -- `code` is a free-text, UNIQUE, stable
business key (the future cross-referencing target for a V0.6 crowdfunding/auction campaign),
`name` the human-readable display label. Lifecycle is create/deactivate/list only, exactly
`LedgerAccount`'s own CRUD shape (`createCostCenter`/`deactivateCostCenter`/`listCostCenters`) --
deactivate, never delete, so historical postings that reference a cost center are never
invalidated. `createCostCenter` rejects a duplicate `code` (`ConflictException`, same pre-check +
`ExposedSQLException` backstop idiom as `createLedgerAccount`) and a blank `code`
(`BadRequestException` -- `code` is free-text user input from a UI form, unlike
`LedgerAccount.accountNumber`, which in practice is always populated from a fixed SKR42 reference
list).

**`Posting.costCenterId` is the only schema addition on the existing entities this wave makes** --
a nullable FK (`posting.cost_center_id`), deliberately the *opposite* default-value/nullability
policy from `Posting.sphere`: most day-to-day postings (membership dues, routine bills) have no
project/campaign association, so requiring every posting to carry one would misrepresent how
rarely a cost center actually applies -- there is no "no room to be unassigned" legal-risk
rationale here the way there is for sphere. `requireActiveCostCenters` (mirrors
`requireActiveLedgerAccounts`) validates every referenced `CostCenter` exists (`NotFoundException`)
and is `active` (`ConflictException`), but -- same "draft is provisional" rule as
`requireActiveLedgerAccounts` -- is only invoked at `postJournalEntry`/`postDraftEntry` time, never
`saveDraftEntry`: a treasurer must be able to save an in-progress draft that references a cost
center they have not finished setting up yet (or that has since been deactivated).

**`getCostCenterReport`** (role: TREASURER/BOARD/ADMIN, same as every other statement method)
derives a read-only `CostCenterReportDto` over `[from, to]` (`from == null` means "since
inception"), same `INCOME`/`EXPENSE` flow derivation as `getIncomeStatement`, re-aggregated by cost
center instead of collapsed across all accounts -- only `POSTED` postings contribute. Unlike
`FourSphereIncomeStatementDto.spheres` (always exactly four, zero-filled), `costCenters` is **NOT**
zero-filled for every existing `CostCenter` -- a cost center is open-ended/user-created and could
number in the dozens or hundreds over the years, so zero-filling all of them would be unbounded
noise; only cost centers with at least one in-scope posting appear, sorted by `code`. Every posting
whose `costCenterId` is `null` (the common case) is aggregated into a separate
`unassignedIncome`/`unassignedExpense`/`unassignedResult` bucket instead, so `totalIncome`/
`totalExpense`/`result` (the sum of every `costCenters` entry plus the unassigned bucket)
reconciles exactly with the plain, cost-center-agnostic `getIncomeStatement` result for the
identical `[from, to]` window over the same postings -- same reconciliation guarantee
`FourSphereIncomeStatementDto` documents for sphere, and verified as a regression test in
`AccountingServiceTest`.

Explicitly out of scope for V0.3.6 (see `02 Projekte/Lapis Cloud V0.3.md` for the full wave plan):
budgets, forecasts, variance/actual-vs-budget tracking; hierarchical/nested cost centers;
cross-cost-center allocation rules; and any crowdfunding/auction-specific fields or logic -- V0.6 is
a later, separate wave that will *consume* this classification mechanism (attach campaigns to a
`CostCenter`), not extend it now.

== Serienbrief-/PDF-Engine (V0.4.1)

Mail-merges three letter templates -- Beitragsrechnung (membership dues invoice), Spendenbescheinigung
(§ 50 EStDV / § 10b or § 34g EStG donation receipt), and Einladung (invitation letter) -- from the
existing `Member`/`Contribution`/`JournalEntry` domains plus one genuinely new domain introduced this
wave, `OrganizationSettings` (`lapis-server/src/main/kuml/11-organization-settings.kuml.kts`, verified
by its own `OrganizationSettingsSchemaDriftTest`). PDF generation itself
(`network.lapis.cloud.server.pdf.{LetterPdfBuilder,BeitragsrechnungPdfGenerator,
SpendenbescheinigungPdfGenerator,EinladungPdfGenerator,GermanAmountInWords}`) is built on **Apache
PDFBox** (Apache-2.0), chosen over openhtmltopdf specifically because this product (non-profit/
political-party) has a hard permissive-license-only constraint and openhtmltopdf's licensing is
dual/LGPL-flavoured per module -- see `LetterPdfBuilder` KDoc for the full trade-off (hand-rolled
word-wrap/page-break instead of HTML/CSS templating).

Two small, deliberately minimal schema additions on already-documented domains feed the templates:

* `Member.street`/`postalCode`/`city`/`country` (all nullable, see the Foundation diagram above) --
  the recipient postal address. The **only** production write path is
  `IMemberService.updateMemberAddress` (self-or-privileged, mirrors the `BOARD_ONLY` document-access
  privilege check), added specifically because the templates would otherwise be unreachable outside
  raw SQL.
* `JournalEntry.donorMemberId` (nullable, see the Accounting diagram above) -- the minimal bridge
  attributing a posted entry to a donating `Member`, distinct from `createdBy` (the booking
  treasurer). Deliberately not a full donation-management module (no campaigns/pledges/recurring
  donations).

parallel; if fewer than `minQuorum` responded, fall back to the cache. Otherwise compute a
provisional median, drop any price whose deviation exceeds `outlierThresholdBps`, and if the
survivors either drop below `minQuorum` or their own spread exceeds `maxSpreadBps`, ALSO fall back
to the cache. A cache hit within `cacheTtlSeconds` returns status `CACHED`; otherwise the call
**halts** -- `convertDonationToLtr` rejects the request outright rather than minting from a stale
or unreliable price (see `network.lapis.cloud.shared.rpc.IPriceOracleService` KDoc). Three real,
independent, no-API-key BTC sources are wired (Coinbase/Kraken/Bitstamp,
`network.lapis.cloud.server.economy.oracle.defaultBitcoinOracleSources`) behind a hardened,
allowlisted, timeout-bounded, response-size-capped HTTP client
(`network.lapis.cloud.server.economy.oracle.oracleHttpClient`).

Explicitly out of scope for V0.6.5: a persistent halt-queue with deferred/retroactive re-pricing
(the concept document's own design for this -- `PriceStatus.DEFERRED` is defined but reserved,
unused this wave); any anchor besides Bitcoin (`AnchorAsset.GOLD_XAU`/`FIAT` are unimplemented
literals -- no free, no-API-key, multi-source feed set exists for either); a payment-gateway/PSP
webhook intake (`convertDonationToLtr` is operator-triggered); and a shared/federated quote cache
(in-memory, per-server only -- a V0.7 federation concern).

== V1.4.4.1 — Member financial history (read view)

No new table, no migration. `IMemberFinancialHistoryService.getMemberFinancialHistory` is a pure
read across two already-existing table families — `contribution` (see the Contribution management
diagram above) and `journal_entry ⋈ posting ⋈ ledger_account` (see the Accounting diagram above) —
gated `MEMBER` (own id only) / `TREASURER`/`BOARD`/`ADMIN` (any member).

Four amounts are returned, deliberately never summed into a `total`: `contributionsPaid` (Σ
`contribution.paid_amount`, `PAID`), `contributionsWaived` (Σ `amount_due`, `WAIVED`),
`contributionsOutstanding` (Σ `amount_due` over `ContributionStatusSets.OUTSTANDING` —
`OPEN`/`OVERDUE`/`RETURNED`/`IN_DUNNING`), and `donationsTotal` (Σ the same
vorzeichenrichtige-Ertragsbetragsspalte the public donor ranking uses, now extracted into
`network.lapis.cloud.server.rpc.DonationIncomeAmount` so the two views can never derive the sign
rule differently). `DEBIT_SCHEDULED`/`DEBIT_SUBMITTED` (`ContributionStatusSets.DEBIT_IN_FLIGHT`)
appear in none of the four — neither paid, waived, nor (per that same status-set object) genuinely
outstanding yet — but (Review MEDIUM fix) they still surface as their own row kind,
`CONTRIBUTION_DEBIT_IN_FLIGHT`, dated by `due_date`, so a running SEPA collection is visible in the
history instead of vanishing between the collection run's creation and its reconciliation.

Each entry's place on the year-grouped timeline is chosen per kind, not by a single "the" date:
`PAID` → `paid_at` (falling back to `period_start` for a pre-V1.2.1-bridge legacy row with no
`paid_at`, logged once as a WARN — never a hard failure of the whole read), `WAIVED` →
`period_start`, an outstanding or debit-in-flight line → `due_date`, a donation →
`journal_entry.entry_date`.

One exclusion is structural, not a filter that could be loosened later without a schema change:
`EventFeePostingBridge` writes `journal_entry.donor_member_id = NULL` for every event-fee entry, so
an event fee can never carry a payer identity to attribute it to a member in the first place. The
`donor_member_id`/`external_donor_id` mutual exclusion is, by contrast, NOT a schema-level
guarantee — `journal_entry` carries no CHECK constraint for it at all (an earlier revision of this
paragraph wrongly cited `chk_payment_checkout_session_donor_identity`, which lived one hop upstream
on `payment_checkout_session` and was itself dropped in `V18__events.sql`). The exclusivity is
enforced purely application-side, by `AccountingService.requireDonorMutualExclusionAndCategory` and
`DonationPostingBridge`, on every path that writes a `journal_entry` row. As long as that rule
holds, `donor_member_id = :requestedMemberId` excludes every `external_donor`-attributed donation —
a donation an `ExternalDonor` (no `Member` relationship at all, see the Accounting/Donor-CRM
diagrams) made can never surface in a `Member`'s own financial history — but a future write path
that bypasses `AccountingService` could violate it silently.

A donation's row amount (and the two totals it feeds, `donationsTotal` and each
`FinancialHistoryYearDto.donationsTotal`) is netted per member across ALL of that member's posted,
donor-attributed `journal_entry` rows — not per individual entry. A Storno/correction booked as its
own `journal_entry` (this schema has no `REVERSED` status; a correction is always a second, separate
entry) nets against the original at the totals level exactly like
`AccountingService.priorPostedDonationTotalThisYear` and `PublicTransparencyReader.loadTopDonors`
already do for their own purposes — only entries whose OWN net is positive become a displayed row;
an entry that nets to zero or negative (e.g. a full-amount Storno) still counts correctly toward the
totals, it simply has no row of its own to show.

A calendar year surfaces in `MemberFinancialHistoryDto.years` at all only if it carries at least one
displayed row OR a non-zero netted `donationsTotal` for that year (`entries.isNotEmpty() ||
donationsTotal.signum() != 0`) — deliberately `!= 0`, not `> 0`: a year whose own donation net is
negative because a later year's Storno was booked against it stays visible, so its non-zero total is
never silently dropped, even though that year then has zero entries of its own (the client renders
the year heading with that negative amount but no table body for it). A year with no row at all AND
an exactly-zero netted total carries no information and produces no block — without this rule, a
`journal_entry` that is fully offset within itself (net exactly 0.00) would otherwise surface as an
empty year block.

A cross-member read (a TREASURER/BOARD/ADMIN viewing someone else's history) is recorded via
`kotlin-logging`, one INFO line naming actor/actorRole/subject — never a booking-relevant GoBD
audit-log entry (`AuditLogChainStateTable`'s hash chain exists for buchungsrelevante Veränderungen,
and a page view changes nothing), and never with an amount in the log line.

== V1.4.4.2 — Member anniversaries (read view)

No new table, no migration. `IMemberAnniversaryService.getUpcomingAnniversaries` is a pure,
BOARD/ADMIN-only read across `member` alone (`dateOfBirth`, `joinedAt`, `status`, `anonymizedAt`) --
no other table is touched.

**Eligibility, not membership**: the set of members this view considers at all is
`MemberStatusSets.ANNIVERSARY_ELIGIBLE` (`ACTIVE`, `DONOR`) -- deliberately WIDER than
`ORGANIZATION_MEMBER` (`ACTIVE` alone). A `DONOR` supports this organization without holding formal
membership, and the Design-Team review judged that a real reason to remind the board of a donor's
anniversary too. `FRIEND` is deliberately excluded -- an unverified self-registration
(see `LTR_ELIGIBLE` KDoc "Akzeptiertes Restrisiko") is not a relationship one congratulates.
`anonymizedAt IS NULL` is a SEPARATE, explicit exclusion, not something inferred from `status`:
`FoundationPersonalData.eraseMember` nulls `dateOfBirth` on erasure but leaves `joinedAt` and
`status` untouched, so an erased member with a still-`ACTIVE` status would otherwise keep generating
a membership anniversary row years after their DSGVO erasure -- an outcome the Design-Team review
named explicitly as unacceptable.

**One chronological list, not two**: birthdays and membership anniversaries share one
`occursOn`-sorted list (a client-side kind filter narrows it, never two separate loaded lists) --
the dominant ordering dimension is "when is this due", the kind is a secondary, form-only (never
color-only) marker on each row.

**Labelling follows status, not the field name**: a `MEMBERSHIP_ANNIVERSARY` row for a `DONOR`
renders "N Jahre Förderer", never "N Jahre Mitgliedschaft" -- a `DONOR` never held formal
membership, and a client rendering the field name unconditionally would let the board send a letter
asserting a legal status a person never had. `AnniversaryEntryDto.memberStatus` carries the status
into the DTO specifically so the label can be derived from it.

**No birthday year is ever returned or shown**: `AnniversaryEntryDto.years` is already the derived
number (age reached / years of affiliation); the exact date of birth stays in the member record
where it belongs. This is restraint, not anonymization -- the full `dateOfBirth` is unchanged and
fully visible on the member's own record; this aggregated view simply shows the minimum the task
needs.

**Coverage line is mandatory, not optional**: `dateOfBirth` is a nullable field, originally
introduced as a Transparenzregister beneficial-owner attribute (V0.5.2), not a universally-collected
membership attribute -- coverage is structurally incomplete. `membersWithoutDateOfBirth` (against
`eligibleMemberCount`) is returned specifically so the client can say "N of M have no date of birth
on file" rather than silently presenting an incomplete list as if it were complete.

**Calendar-wraparound and leap-day arithmetic run entirely in Kotlin, never in SQL**:
`AnniversaryCalendar.nextOccurrence` computes each member's next real calendar occurrence as an
actual date >= today, then filters on `<= today + windowDays` -- a naive "month/day between X and Y"
SQL predicate would silently return nothing across a year boundary (e.g. Dec 20 + 30 days). This
also sidesteps this schema's own H2-vs-PostgreSQL dialect-parity discipline (see `DbClock` KDoc) for
date arithmetic specifically, at member-table scale (~600 rows as of this wave; should this ever
need reconsidering at a much larger scale, that threshold is roughly 50,000 members). A Feb-29
anniversary in a non-leap year is shown on Feb 28 (`shiftedFromLeapDay = true`, `originalDate`
stays Feb 29) -- this is a reminder, not a legal deadline computation.

`windowDays` is validated server-side against `AnniversaryCalendar.MAX_WINDOW_DAYS` (90) --
`BadRequestException` outside `1..90` -- a server invariant, not merely a client dropdown
convenience; a caller bypassing the UI cannot silently widen the read.

**Deliberately NOT part of this wave** (Design-Team review, Jobs): no CSV/PDF export (a second
output path for personal data is its own future decision, not a button added incidentally here), no
mail/notification dispatch of any kind, no free-form date-range picker (no reusable date-input
component exists in this codebase yet, same limitation `CrmContactsScreen.kt`'s own KDoc documents;
window presets close this gap without inventing one), family memberships,
deceased-member workflow (each its own later sub-wave with its own scoping decision). Honors
management shipped as V1.4.4.3, see below.

== V1.4.4.3 — Member honors (honors management)

One new table, `member_honor` (`V21__member_honors.sql`, model in `41-member-honor.kuml.kts`) --
records that the organization awarded a member an honor (Ehrenmitgliedschaft,
Verdienst-/Treueauszeichnung, or a free-form "sonstige" category), on a given date, optionally
naming who/what body awarded it, with a free-text note a board member can attach. Backed directly
by `MemberHonorService` -- no separate Store/Policy pair, unlike `CrmContactStore`/
`CrmContactPolicy` (see that class's own KDoc "Architektur-Entscheidung" for why: a single simple
table with five validation rules and no concurrency problem does not warrant the extra
indirection, the same shape `BoardMembershipService` already established for itself).

**`category` (enum) and `title` (free text) both exist, deliberately**: `category` is the stable,
filterable/reportable axis (four fixed literals); `title` is the volatile, human-authored display
text a board minute actually used. Collapsing these into one field would either make
filtering/reporting by kind impossible, or force every award into one of four generic labels with
no room for the real wording. Same split `crm_contact.contact_type` (closed) vs.
`crm_interaction.summary` (free text) already establishes one hop over.

**No `revoked_at`/`revoked_reason` column**: aberkennung (revoking an honor) is a rare,
exceptional, governance-relevant PROCESS -- a Vorstandsbeschluss -- not a flag flip on this row.
Modelling it would additionally require deciding whether a revoked honor still counts in a public
member roster or a printed Urkunde, neither of which this wave answers. If aberkennung is ever
built, it is its own later wave's decision.

**All fields are editable on update, not just `note`** -- a deliberate departure from
`crm_interaction`'s append-only shape: an honor is a rare, deliberately-entered record a board
member reviews before saving, not a high-volume interaction log. A mis-entered date or a typo'd
title must be fully correctable, not only its free-text note.

**`awarded_by` is a plain free-text column, never a member FK** -- the body that awarded an honor
(the board, the Mitgliederversammlung, a named external party) very often cannot be represented as
a single `member` row. `recorded_by` IS a member FK -- the operator who entered the row (always
BOARD/ADMIN), tracked for the same accountability reason every other domain file's
`created_by`/`recorded_by` column exists.

**Hybrid DSGVO erasure, honoree role only** (`MemberHonorPersonalData`): the row itself
(that an honor was awarded, when, of what category) is an Art. 5(2) DSGVO accountability record
and is RETAINED regardless of erasure mode -- same posture `BoardMembershipPersonalData` already
takes for board service history. `note`, however, is unconditionally nulled on the *honoree's*
erasure (it is Vorstandskommentar über die Person). Erasing the *recorder* role does not touch
`note` -- it is fachlich fremd to that role. `member_id` and `recorded_by` can coincide on the
same row (a board member honoring themselves is not excluded by any FK constraint); the
contributor counts rows via a single `OR` condition rather than summing two separate counts, so an
overlapping row is never double-counted (see `MemberHonorPersonalData` KDoc "Row-counting").

**No `dsgvo_audit_log` entry on `deleteHonor`**: unlike `CrmService.eraseContact`, `deleteHonor` is
a plain data-correction DELETE for a mis-entered row (wrong member, duplicate entry) -- not an
Art. 17 erasure. A `dsgvo_audit_log` entry would misrepresent what happened. ADMIN-only, both
server-side (`current.requireRole(AccountRole.ADMIN)`) and client-side (the delete button is not
rendered at all for a BOARD caller, mirroring `CrmContactsScreen`'s own posture).

**No Selbstauskunft variant, same as V1.4.4.2**: `Routes.MEMBER_HONORS` is route-level
`requireRole(BOARD, ADMIN)`, not `requireAuth` -- there is no fachlicher Grund for a member to see
the organization's collected list of who was honored when.

**Deliberately NOT part of this wave**: CSV/PDF export, Serienbrief/Urkundengenerierung, a
link to the V1.4.4.2 anniversary automation (an honor is never auto-suggested from a milestone
anniversary), an "aberkannt" state, a Selbstauskunft path, bulk/CSV import of historical honors,
and any accounting-side booking. Each is its own later scoping decision.
