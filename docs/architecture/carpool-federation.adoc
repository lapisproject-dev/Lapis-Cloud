= Mitfahrzentrale exchange between partner servers (V1.9.311 and following waves)
:description: Design of the carpool exchange between partner servers: a short, consented hint per trip, how far it may travel, how it is withdrawn, and what wave 1 (switches only) already contains.
:toc:
:toc-placement: preamble
:icons: font

NOTE: **Implementation status.** **Waves 1 to 4 of 7 exist.** Wave 1 (V1.9.311, schema V159) is the foundation: switches and consent. Wave 2 (V1.9.312,
schema V160) is the **origin side of the teaser feed**. Wave 3 (V1.9.313, schema V161) is the **withdrawal on the origin side** (tombstones). Wave 4
(V1.9.314, schema V162) adds the **pull client**: this server fetches the feed of its approved direct partners, checks the signature of the origin of every
hint, stores the hints it accepts (pseudonymous, until the day of departure), hands them on within the reach, and passes withdrawals on. **Still nothing is
displayed to members** (wave 5): a member never sees a foreign hint. The sentence on the partner page says so to the administrator. Waves 5 to 7 below are the plan,
not the code. It was **never run against a real partner server** and has had no legal review.

== Goal

Members of one organisation often drive to a place where a *partner* organisation holds an event. A member who offers a ride can agree that a **short
hint** about the trip is shown to the members of partner servers. The hint tells a partner only *that* somebody drives from one region to another on a
day; to take part, a person still contacts the offering organisation. The feature is **off everywhere by default** and every step needs a separate,
revocable consent.

== The hint

[source,kuml,name="carpool-federation-model"]
----
classDiagram(name = "Carpool exchange -- hint and envelope") {
    val teaser = classOf(name = "CarpoolTeaser") {
        attribute(name = "teaserId", type = "String")
        attribute(name = "departureDate", type = "LocalDate")
        attribute(name = "fromPostcodeArea", type = "String")
        attribute(name = "toPostcodeArea", type = "String")
    }

    val envelope = classOf(name = "TeaserEnvelope") {
        attribute(name = "originHost", type = "String")
        attribute(name = "hops", type = "Int")
        attribute(name = "maxHops", type = "Int")
    }

    association(source = envelope, target = teaser) {
        source { multiplicity(spec = "1"); role = "envelope" }
        target { multiplicity(spec = "1"); role = "teaser" }
    }
}
----

The wire type `CarpoolTeaser` has exactly four fields (a tripwire test pins the set):

* `teaserId`, 16 to 64 characters `[A-Za-z0-9_-]`: a pseudonymous id. Since wave 2 it is the keyed, domain-separated HMAC-SHA256 of the trip id (64 hex
  characters, see "Key decisions" below), so nobody outside the origin server can compute it from the trip id and the id of a withdrawn trip cannot be
  linked to the trip.
* `departureDate`.
* `fromPostcodeArea` and `toPostcodeArea`, exactly two ASCII digits: the first two digits of the postcode of the start and of the destination.

Nothing else is in it: no place text, no time, no seats, no notes, no name, no internal id.

=== One projection

`projectCarpoolTeaser(fromPlace, toPlace, departureDate, teaserId)` in `lapis-shared` (`commonMain`, runs on the JVM and in Kotlin/JS) is the **only** place
that builds a hint. It takes exactly the three source fields, no row and no DTO, so it structurally cannot see anything else. The preview in the trip
form calls the same function, so the owner sees what a partner would receive. Since wave 2 the feed calls it too, from `CarpoolTeaserFeedBuilder` only.
A tripwire test pins that the client calls it only in `CarpoolFederationUi.kt` and the server only in `CarpoolService.kt` and `CarpoolTeaserFeedBuilder.kt`.

=== The postcode rule

`extractPostcodeArea(place)` returns the first two digits of the **first run of exactly five ASCII digits** `0-9` in the text. `D-` and `DE-` stand in
front of the digits and do not matter. The value must lie in 01001..99998. If the first such run is out of range the result is `null`: the next run is
**not** tried. A longer run (`381000`), a shorter one (four-digit postcodes of Austria and Switzerland) and Unicode digits (fullwidth, Arabic-Indic) give
`null`. There is no lookbehind and no `\d`, so the JVM and Kotlin/JS behave the same. A trip without a postcode on both places can never be shared.

=== Who may receive a hint

`isCarpoolTeaserEligible` is true only if **all** hold: the trip is an `OFFER`; the owner consented (`federation_opt_in`); the instance switch is on; the
partner is a *direct* partner with `carpool_sharing` on, active and not blocked; the author is still active; the day lies between today and today plus 90
days in the organisation's time zone; a seat is still free (`confirmed < seats`); the projection is not `null`. "The trip still exists" follows from the
fact that only existing rows are loaded. `carpool_posting` has no link to an event and no cancelled status, so nothing of that kind is checked.

The administrator calls (`IPartnerServerService`, `ADMIN` only, like every method of that service) are `getCarpoolFederationSettings`,
`setCarpoolFederationSettings` (a hop limit outside 1..3 is a bad request, never clamped silently) and `setPartnerCarpoolSharing`. The member calls
(`ICarpoolService`, `ACTIVE` only) are `getCarpoolFederationAvailability` and `setCarpoolPostingFederationOptIn`. A foreign trip gets the constant
not-found answer, also for an administrator. Giving consent needs the switch on, an `OFFER` and a postcode on both places; **withdrawing is always
allowed**. Changes are audited only when something really changed: `PARTNER_SERVER` entries for the administrator's choices, and the new entity type
`CARPOOL_FEDERATION_OPT_IN` (new state only, no place and no date) for the owner's consent, which doubles as the proof of consent (Art. 7 (1) GDPR).

== Reach: the hop limit

`partnerRecursionDepth` (wave P2) controls how far this server **reads** partner lists. The hop limit of this feature controls how far a hint is **passed
on**. They are independent. The effective reach of a hint is `min(maxHops of the origin, own hop limit)`: a server never passes a hint further than the
origin allowed and never further than its own limit.

== Wave 2: the teaser feed (origin side)

`GET /api/federation/carpool-feed/v1` (constant `CARPOOL_TEASER_FEED_PATH`). It is a **path of its own**, authenticated, server to server: it is never under
`/api/public` or `/api/embed`, never part of the public partner feed or of an embed feed, and no CORS header is sent. It is default off: it answers only if
the instance switch is on, the partner is a direct partner that is active, not blocked and has `carpool_sharing` on, **announced a signing key** that the
partner poll pinned, and the request is signed with that key. Everything else is one uniform answer.

=== Envelope

        source { multiplicity(spec = "1"); role = "feed" }
        target { multiplicity(spec = "0..1000"); role = "items" }

    association(source = item, target = teaser) {
        source { multiplicity(spec = "1"); role = "envelope" }
        target { multiplicity(spec = "1"); role = "teaser" }
    }

----

`kind` is `lapis-carpool-teaser-feed`, `schemaVersion` is 1. An item is `originHost` (this server), `hops` (0: this server owns the hint) and `maxHops` (this
server's own hop limit, 1 to 3) plus the four-field `CarpoolTeaser`. There is no `generatedAt`, no server id and no name, so the `ETag` (SHA-256 of the
body) changes only when the content changes. The list is sorted by `(departureDate, teaserId)` and is a **complete snapshot** of what is eligible for
**this partner** now.

**`complete`.** The snapshot is bounded: at most 1000 items, 5000 scanned trips and 256 KiB (1 MiB since wave 4: every item carries an origin signature, see below). When any bound cuts the list, `complete` is `false`. A
consumer (a later wave, the pull client) may treat a hint that is *missing* from the list as withdrawn **only when `complete` is `true`**.

[cols="1,3",options="header"]
|===
|Step |Rule

|Signature |draft-cavage `Signature` over `(request-target) host date digest`, RSA-SHA256; the `Digest` is the SHA-256 of the **empty** body
(`SHA-256=47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=`). `Date` within five minutes in both directions. A query string, a body or a transfer encoding is
refused. `HttpSignatures` itself is unchanged (it already handled a GET).
|Host and path |The signing string is checked against the **own host** (`LAPIS_PUBLIC_BASE_URL`, injected for tests) and the **constant path**, never against the
`Host` header or the path of the request. A signature a partner made for *another* server therefore cannot be replayed here (the replay guard is per JVM
and per server and would not stop that). A tripwire forbids reading the request's host or path in the feed files.
|Key |Only the **pinned** key (see below). No key is fetched while a request is answered; a tripwire forbids any HTTP client, key fetch or SSRF helper in the
feed package. A key id that is not pinned by exactly one row is verified against a throw-away dummy key (same RSA cost, no timing oracle).
|Replay |Its own `FederationReplayGuard` instance; only a **valid** signature is remembered. Per JVM (single-instance deployments), documented scope cut.
|Approval |Decided in the write transaction that also builds the snapshot: the row is read again, the pin must still equal the verified key, its host must equal
the row's host, the partner must be active, not blocked, with `carpool_sharing` on, and the instance switch must be on. A removal or a changed pin between
verification and approval is refused.
|Refusal |**One answer for every cause** (`404`, `{"error":"unavailable"}`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, no `ETag`, no
`Retry-After`), written only by `respondUnavailable`: a missing, malformed, stale, future or replayed signature, a wrong or unknown key, an unknown, inactive,
blocked or removed partner, sharing off, the instance switch off, a missing teaser key, a query string, an internal error. The administrator sees the
causes only as in-memory counters. **Wave 3 makes one deliberate exception to "one answer for every cause":** the trailing answer (see "Wave 3: withdrawal").
|Limits |Per IP (30 a minute, before the signature check), per partner (12 an hour) and global (600 an hour), the last two only **after** the approval, so a `429`
is visible to an approved partner only and says nothing about the consent of anybody else. All constants live in `CarpoolTeaserFeedLimits`.
|`ETag` |`"<sha256 of the body>"`, `If-None-Match` handled like the public partner feed (`*`, a list, `W/`). A `304` has no body and the same cache headers. There
is **no memo cache**: a withdrawal of consent shows on the very next fetch. The `304` path still costs one bounded database pass.
|Audit |One `CARPOOL_FEDERATION_FEED` entry per answered `200`, in the same transaction as the snapshot: `entityId` = the partner row, no actor, snapshot `{itemCount,
complete}` only. A refusal or a `304` writes none (no unauthenticated writes to the audit chain lock).
|Counters |Persistent on the partner row (`carpool_feed_served_at`, `carpool_feed_served_count`, `carpool_feed_last_items`, 200 and 304); in memory since the start:
refused (all causes together), rate limited. Shown to the administrator on the partner page through fields appended to the existing DTOs; no new RPC method.
|===

== Key decisions of wave 2

* **Where the origin gets the public key of a partner (K1).** `partner_server` had no key, and the keys of the ActivityPub relations belong to Follow
  relations that carpool partners usually do not have. The public partner feed (`PartnerFeedV1`) therefore got one additive top-level field `signingKey
  {keyId, publicKeyPem}`: this server's own federation key, the one `/federation/actor` already publishes. The poll that already fetches the partner feed
  over TLS with SSRF pinning validates it (`PartnerFeedParser.parseSigningKey`: https key id on exactly the partner's own host, a fragment, printable ASCII
  up to 512 characters; X.509 RSA 2048 to 4096 bits, PEM up to 4096 characters) and `PartnerServerStore` pins it (also on the first probe). An invalid key
  never invalidates the feed; it only means no pin. A feed **without** a valid key **clears** the pin: a partner that withdraws its key, or a partner
  downgraded to a build without the field, loses access on the next poll. Trust basis: the same TLS fetch to the partner host that already authenticates
  its events (trust on first use, refreshed on every poll). The partner must run V1.9.312 or later. The field does not contain the word "carpool", so the
  public feed still never mentions a carpool.
* **The HMAC key of the `teaserId`.** Derived from `LAPIS_SECRET_ENCRYPTION_KEY` with `SecretBox.hmacSha256Hex(purpose = "carpool-teaser-id/v1")`, the same
  idiom as the LupaBB erasure list (domain separation, never the AES key itself). No new environment variable. Without the key the feed refuses everybody
  and the administrator sees "Schlüssel für Kurzhinweis-IDs fehlt". **Rotating `LAPIS_SECRET_ENCRYPTION_KEY` changes every `teaserId`**; a partner sees
  this as "all withdrawn, all new".
* **`teaserId` is global**, not per partner: wave 4 needs one stable origin id for deduplication and tombstones across several paths. Two partners can see
  that they hold the same hint, which carries the same date and regions anyway.
* **V160 is a new migration** although V159 is unreleased: V159 is already on `origin/master` and a CI or local database may have run it.
* **Host binding.** The pin and the verification require that the host of the key id (the partner's `LAPIS_PUBLIC_BASE_URL`) equals `partner_server.host`,
  and that the partner signs exactly this server's own host. Different host names mean "not available". An operator who serves a server under another
  name than its public base URL has to align them.

== Wave 3: withdrawal (origin side, schema V161)

A hint that a partner may have cached has to be reported as taken back, or "switched off" would only be a promise. Wave 3 does exactly that on the **origin
side**: the snapshot gets a second list, `withdrawn`, with the hints that were withdrawn recently. There is **no pull client** in this wave: a partner with
its own client can read the list; a Lapis server does not yet.

[source,kuml,name="carpool-withdrawal-flow"]
----
sequenceDiagram(name = "Carpool withdrawal -- trigger to partner") {
    val trigger = lifeline(name = "Trigger (owner, admin, erasure, sweep)")
    val store = lifeline(name = "CarpoolFederationStore.withdraw")
    val table = lifeline(name = "carpool_teaser_tombstone")
    val builder = lifeline(name = "Snapshot builder")
    val partner = lifeline(name = "Direct partner")

    message(from = trigger, to = store, label = "targets (trip id + date the partner may hold), scope, clearOptIn")
    message(from = store, to = store, label = "lock order: trips first; consent filter; derive the hint id (HMAC)")
    message(from = store, to = table, label = "INSERT ... ON CONFLICT DO NOTHING (derived primary key)")
    message(from = partner, to = builder, label = "GET feed (signed)")
    message(from = builder, to = table, label = "live tombstones for this partner, after the items were read")
    message(from = builder, to = partner, label = "200 items + withdrawn (item wins; or the trailing answer)")
}
----

=== What a tombstone is

One row in `carpool_teaser_tombstone` says "the hint with this pseudonymous id was withdrawn": `teaser_id` (the HMAC id, 64 hex), `partner_id` (`NULL` = every
partner, otherwise exactly one), `created_at` and `expires_at`. **No member, no trip, no place, no text.** On the wire an entry is exactly `{teaserId,
withdrawnAt}` (the UTC day). The table is read and written **only** by `CarpoolFederationStore` (a tripwire pins it, and pins the field sets).

* **Life.** `expires_at = min(created_at + 14 days, departure + 2 days at 00:00 UTC)`. A partner never needs the tombstone for longer than it may hold the
  hint. The cap lives in the code (`CarpoolTeaserTombstonePolicy.TTL_DAYS`, not configurable). A tombstone whose life would already be over is not written.
  The poller deletes expired rows; the feed ignores them at read time anyway.
* **Idempotent without a lock on the settings.** The primary key is derived from `(teaserId, scope)` (SHA-256, version-4 shaped UUID), the insert is
  `ON CONFLICT DO NOTHING`. A second withdrawal changes nothing, in particular it does **not** extend the life. Two parallel withdrawals end in one row and no
  exception. Locking the `organization_settings` row (as first designed) would deadlock with the sweep, which locks the trip and then writes.
* **Lock order, one rule everywhere:** `carpool_posting` rows first (ascending id, `FOR UPDATE`), tombstone inserts after (also in ascending trip order).
  The admin triggers B4 and B5 lock no trip.

=== Triggers

[cols="1,3,3",options="header"]
|===
|# |Event |What is written

|B1 |The owner takes the consent back |Global tombstone; consent and its moment cleared. Giving the consent again deletes the *global* tombstone of that hint.
|B2 |The owner deletes a shared trip |Global tombstone, written **before** the row is deleted (the trip lock is held).
|B3 |The owner edits a shared trip |If it is no longer shareable (now a request, or no postcode): global tombstone **with the old date**, consent cleared. If it stays
shareable: nothing (the same hint id carries the new content in the next snapshot). If the date moves beyond the 90 day window: global tombstone, the consent stays.
|B4 |The administrator switches the exchange off |Global tombstones for every currently shareable trip; the consents stay (switching on again brings the items back, "item wins").
|B5 |The administrator switches one partner off |Tombstones scoped to that partner for every currently shareable trip. Switching it on again deletes them.
|B6 |GDPR erasure of the author |Global tombstones for his shared trips, written before the hard deletes in the same transaction. A tombstone holds no member reference, so nothing of it needs erasing.
|B7 |The author is no longer an active member (left, banned, anonymised) |Swept lazily (at most 50 per snapshot build) and by the daily poller: consent cleared, global tombstone, one audit entry
without an actor. The consent ends with the membership, also for a short ban.
|Removal |A partner is removed |Its scoped tombstones are deleted explicitly (not relying on the foreign key's `ON DELETE CASCADE`).
|===

**No tombstone** is written for: a trip whose departure grace period is over, a full trip that was never shareable, a trip never consented to, and when no
teaser key is configured (the consent is still cleared; the miss is counted in `CarpoolWithdrawalKey.skippedNoKey`).

**The consent filter.** B1, B2, B3, B6 and B7 write a tombstone only when some partner fetched the feed **after** the consent was given
(`carpool_posting.federation_opt_in_at`, set with the consent, backfilled with `created_at` for existing consents): nothing can have been handed out
before. Without it a single member could create, consent and delete trips in a loop and push real withdrawals out of the bounded list. The filter is sound
because the "served at" moment is taken **after** the snapshot is built. B4 and B5 have no filter.

=== The snapshot

`CarpoolTeaserFeedV1` gets a last field `withdrawn` (always present, empty by default; `schemaVersion` stays 1). The builder reads in a pinned order:
first the candidates and all items, then the lazy sweep, then the tombstones, then **removes every id that is in the complete item list ("item wins")**,
sorts by day descending and then id, and cuts at 1000. That order can at worst produce "item without a tombstone" under a concurrent withdrawal (the next
fetch shows the tombstone), never "neither". `complete` is `false` when either list was cut (by the item cap, the 1000 cap, the 5000 scan limit or the
byte cap, which halves the items first and then the withdrawals). The `ETag` is the hash of the body, so a new or an expired tombstone changes it and an old
`ETag` gets a `200`. The audit entry of a `200` gets one more number, `withdrawnCount`.

=== The trailing answer

Switching off must not leave cached hints standing. A partner that **was served before** and is still a trusted partner (same pin, key host = row host,
active, not blocked) gets, after the instance or its own switch went off, a `200` with `items = []` and the withdrawals that are still live for it, **only if
there are any**. Everything else (never served, nothing live to report, inactive, blocked, wrong pin) stays the one refusal, byte for byte. The same rate
limits and the same audit apply; it never carries an item.

=== Decisions

* **Same `teaserId` after a new consent.** The hint id stays the same for a trip; the new consent deletes the global tombstone. A new "epoch" in the id would
  not hide the link (date and regions are identical) and would break the deduplication wave 4 needs.
* **Reason and member are never reported**, only id and day.
* **Admin counters** are fields appended to the existing DTOs (`carpoolWithdrawalsActive`, `carpoolWithdrawalsScoped`); no new RPC method.
* **Backup.** The table is part of the backup (it holds nothing personal and belongs to the correctness of a withdrawal). A restore of an older backup brings
  back consents that were withdrawn after it (an existing property of a restore, not new).

Code: package `network.lapis.cloud.server.carpool.pull` is the **only** place with an outgoing connection for this feature (`CarpoolTeaserFeedClient`, same SSRF
chain as the partner feed: public addresses only, pinned address, no redirects, body and time bounded). `CarpoolTeaserFeedReader` is pure; `CarpoolReceivedStore`
is the only reader and writer of the two new tables; `CarpoolPullPoller` is started only in `Application.kt`.

=== Decisions

* **Wire, additive, `schemaVersion` stays 1.** Two fields at the end of an item: `via` (relay hosts from the origin, including the publishing server from
  `hops >= 1`, so `via.size == hops`) and `originSignature`. A wave 4 client **requires** the signature: items of a wave 2/3 origin are dropped and counted; its
  `withdrawn` list is still applied. A partner must run V1.9.314.
* **`hops`** on the wire = relays before this feed (0 = the feed server is the origin). Stored `hops = wire + 1`. Accepted when `wire + 1 <= min(maxHops, 3)`
  (the own limit does not limit what is *stored*); handed on to a partner when `stored + 1 <= min(maxHops, own limit, 3)`, never back to the source, the origin
  or a host on the path. Example `maxHops = 2`: O to A (A stores 1), A to B (B stores 2), B hands on nothing.
* **Origin signature.** Signed UTF-8 bytes, no trailing line feed: `lapis-carpool-teaser-origin/v1` LF `teaserId` LF `originHost` LF `departureDate` LF `fromArea` LF
  `toArea` LF `maxHops`. Every field is validated first (64 hex id, canonical host, two digits, 1 to 3), so no field can contain a line feed. RSA
  `SHA256withRSA` (PKCS#1 v1.5, deterministic, so the ETag stays stable), Base64. The purpose prefix separates it from HTTP signing strings, which start with
  `(request-target): `. Applies to every item, also hop 0.
* **Key of the origin without any new request:** the pinned key of a direct partner with that host, else the key pinned from the partner recursion (V162 columns
  `partner_discovered_server.signing_*`, filled from the TLS fetch the recursion makes anyway). **Hop 2 and further therefore need the partner recursion**
  to have reached the origin; otherwise the hint is dropped and counted (`unknownOriginKey`).
* **Dedup key is `(origin_host, teaser_id)`**, shortest path wins; a hostile origin that reuses a foreign pseudonym under its own host displaces nothing.
* **Withdrawals** only act on copies from that source or whose origin is that source. Effect: the copy goes, a local block (`carpool_received_tombstone`) is
  written, and when the copy could have travelled on and a partner fetched our feed since, a global tombstone is written (the existing W3 table) so the chain continues. A re-import over another path stays blocked
  until the block expires (at most 14 days); the reporting source or the origin itself (hop 0) may bring it back (renewed consent).
* **`complete = true`** deletes the copies of that source that are neither listed nor withdrawn, **without** a block (missing is not withdrawn).
* **Switching off:** instance off, sharing off for a partner, removing a partner, a block pattern, and a source that was not pulled successfully for 24 hours
  (`STALE_AFTER`) delete the copies, report the forwardable ones as withdrawn, and forget the ETags. A restore brings ETags back but not the copies (the tables
  are not backed up): a `304` with no copies although the last answer held some clears the ETag.
* **Limits:** 1000 copies per source, 5000 in total, a feed of at most 1000 items and 1 MiB (shared constant for builder and client), pull interval 30 minutes plus
  up to 10 minutes of jitter (the origin allows 12 per hour and partner), back-off 15 minutes doubling to 24 hours, a `429` waits at least an hour.
* **Locking:** the source row of `partner_server` first, then the received rows, then tombstone inserts; never `organization_settings`, never `carpool_posting`.
  The instance-wide switch-off takes all partner rows first. A rare deadlock between an apply and another switch-off is detected by the database and retried at the next tick.

=== What wave 4 deliberately does not do

* **No display and no member interface**: a foreign hint is never shown (wave 5). Only the administrator sees counters.
* `hops` and `via` are **not signed** (they change at every relay): a dishonest relay can shorten the path or the hop count. Content and `maxHops` are protected.
  A dishonest direct partner could spread a hint outside this protocol anyway.
* **No legal review** (Art. 26 GDPR open, see below); default off; never run against a real partner server.

== What wave 3 deliberately does not do

* **No pull client**, no display, no pass-on: a partner with its own client can read `withdrawn`, a Lapis server does not yet. The hop count is still 0.
* **No legal review** (still open, see below). A tombstone is a technical aid, not a statement of deletion by the partner: a partner that already cached a hint
  holds it until it reads the list or until the date. A blocked or removed partner keeps what it cached until the hint's date; this server cannot delete it.
* B4 and B5 report at most 5000 candidate trips per event (a longer tail is missed and counted in `CarpoolWithdrawalKey.scanCapped`); a trip that was
  handed out earlier and is meanwhile full is not reported when the partner is switched off.
* A global tombstone also goes to a partner whose own switch is already off, as long as it was served before: it learns the number and the days of withdrawals
  of the last 14 days (a small activity signal, accepted and documented).
* `deletePosting` has no rate limit of its own; the consent filter and the 1000 cap bound the effect of a flood.

== What wave 2 deliberately does not do

* **No pull client.** No Lapis server fetches the feed of a partner; the feed can only be fetched by a partner with its own client. No outgoing call is made
  for this feature, also not while a request is answered (the key comes only from the pin).
* No display, no tombstone, no pass-on (waves 3 to 5). The hop count in an item is always 0.
* The public partner feed and the embed feeds still never mention a carpool (a tripwire scans for it); the new `signingKey` field is a plain key.

== What wave 1 deliberately did not do

* No data left the server in wave 1. There is no HTTP client for this feature (a tripwire scans for it).
* The public partner feed and the embed feeds never mention a carpool (a tripwire scans for it).
* `organization_settings` wire types do not carry the switch, the hop limit or the consent; only `CarpoolFederationStore` reads and writes them.
* No legal review has taken place. In particular the question of **joint controllership between servers (Art. 26 GDPR)** is open, and there is no
  agreement template. The deletion pass-on to partners arrives with wave 4.

== Open questions

* Resolved in wave 2: the HMAC key of the `teaserId` is derived from `LAPIS_SECRET_ENCRYPTION_KEY` (no new secret).
* Joint controllership (Art. 26 GDPR) is still not reviewed, and with wave 2 a real transfer is technically possible (default off).
* Resolved in wave 4: the pull client, further hops and the pass-on of withdrawals are one wave. Open: a signature chain per hop (so that `hops` and `via` are protected) would be a wave of its own.
* Replay protection is per JVM; a multi-instance deployment would need a shared store.
* Whether the owner is told **which** organisations receive the hint (proposed for wave 5: list of the approved direct partners and the reach).
* Whether the board, not only the administrator, may switch the exchange (it would change the whole partner administration, a separate decision).
