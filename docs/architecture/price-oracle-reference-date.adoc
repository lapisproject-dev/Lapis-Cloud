= Price oracle: gold price at a reference date
:toc:

NOTE: Status: **implemented (V1.9.324, schema V171), off by default** (`price_oracle_config.conversion_rate_basis = CURRENT`). **Not reviewed by a tax adviser, not released.** Whether the "closing rate" defined here (see <<closing-rate>>) is acceptable as a booking basis is a question for the tax adviser.

== Goal

A donation that arrived on one day is booked as LTR some days later. In the default mode (`CURRENT`) the conversion uses the live quote of the moment of booking, exactly as before. In the mode `REFERENCE_DATE` the treasurer names the **reference date** (the day of the donation) and the conversion uses the closing rate of that day. The mode exists for the `GOLD_XAU` anchor only: the `FIAT` anchor has a quorum floor of one source (a single value, never acceptable as a stored basis), and Bitcoin has no trading calendar.

== One resolver

`PriceOracleReferenceRateResolver` is the only place that turns a reference date into a rate. It reads the database and never the network, and it runs inside an open transaction.

. *Validation*: the date is not before 2000-01-01 and strictly before today in the organisation zone (Europe/Berlin). Today is refused: the rate of a day only becomes final at midnight.
. *Trading day*: `LbmaGoldCalendar` moves a Saturday, a Sunday or a bank holiday of England and Wales back to the last London trading day. The reason (`WEEKEND`, `HOLIDAY`, or `NONE`) is stored with the conversion. The calendar contains a table of one-off changes (royal events: 2002, 2011, 2012, 2020, 2022, 2023) read from gov.uk/bank-holidays; nothing is fetched at run time. A future one-off closure needs a code update. Until then the calendar does not know it and the day resolves to `NO_DATA`/manual rate, never to a wrong automatic rate.
. *Manual rate wins*: a confirmed rate for the trading day is used. A snapshot of that day is only a yardstick.
. *Stored snapshot*: the latest snapshot of that Berlin calendar day that **qualifies**: status `LIVE`, `source_count` at least `max(minQuorum, quorum floor)`, and either (a) the raw values complete (the number of `included` rows in `price_oracle_snapshot_source` equals `source_count`) or (b) a *legacy snapshot* (see below). The Berlin day is converted to a UTC window with daylight-saving time (a day has 23, 24 or 25 hours). Of several qualifying snapshots the **latest** wins: a defective newer snapshot never hides an older qualifying one.
. *Otherwise* an outcome that says why: `NO_DATA`, `QUORUM_MISSING`, `STATUS_NOT_LIVE` (quorum met, but every snapshot of the day is DEGRADED), or `RAW_VALUES_MISSING` (a snapshot captured *after* the raw-values cutoff has no or incomplete raw values: a defect or a manipulation. Its median is shown as a hint only and is never used as the rate).

=== Legacy snapshots and the raw-values cutoff

A snapshot taken before V171 has no stored single values and never will. Refusing every such day would force a manual rate for the whole history, so a snapshot *without any* raw value row that was captured **before the cutoff** is accepted as the closing rate (b). The conversion and the preview then carry `rawValuesStored = false` and the screens say "single values not stored"; nothing else changes. The cutoff is `RawValuesCutoff` (read once at start-up, `FlywayRawValuesCutoff`): the minimum of

* `installed_on` of the Flyway entry for V171 (converted to UTC), and
* the earliest `captured_at` of any snapshot that *has* raw value rows.

The second term protects a restore: onto a fresh server `installed_on` is later than every snapshot, but a snapshot with raw values proves that V171 was active earlier; the minimum only ever makes the boundary stricter. A missing Flyway entry or a failed read gives "no legacy snapshot" (a warning in the log, never a crash). A `CACHED` replay written after V171 has no raw value rows either, but it is not `LIVE` and captured after the cutoff, so it never qualifies.

[[closing-rate]]
== What "closing rate" means

`price_timestamp` of a snapshot is the moment the oracle fetched the prices (the poller runs hourly), not the source's own observation time. The closing rate is therefore *the last qualifying hourly fetch of the calendar day*. It is **not** the LBMA PM fixing. The source's own timestamp is stored per raw value (`observed_at`).

== Data

* `price_oracle_config.conversion_rate_basis` -- the switch (`CURRENT`, `REFERENCE_DATE`). Only the administrator sets it; `PriceOracleConfigInput.conversionRateBasis = null` leaves it unchanged. The mode needs the gold anchor; leaving the gold anchor while the mode is on is refused.
* `price_oracle_snapshot_source` -- raw value per source of each snapshot taken from V171 on (`raw_price`, `observed_at`, `included`). Written only by `PriceOracleSnapshotStore`, in the same transaction as the snapshot (a unique-index collision rolls both back, no orphan rows). Sources outside the plausibility band or rejected as outliers are stored with `included = false`.
* `price_oracle_reference_rate` -- a manually confirmed rate, unique per (anchor, currency, effective date). Written only by `PriceOracleReferenceRateStore`, which has **no update and no delete** (`ReferenceDateTripwireTest`).
* `price_oracle_conversion` -- `rate_basis` (`CURRENT`, `SNAPSHOT`, `MANUAL`), `reference_date`, `effective_date`, `fallback_reason`, `snapshot_id` or `reference_rate_id`, `quorum_required`. A CHECK constraint ties the columns together per basis. A manual rate has no oracle status: the conversion stores `DEFERRED` as `price_status`, `source_count = 0`, `sources_used = 'manual'`, and the 00:00 UTC of the effective date as `price_timestamp`; `rate_basis` is what tells the cases apart.

== Manual confirmation

`confirmReferenceRate` (treasurer, board or administrator) records a rate with an evidence text of 20 to 2000 characters (trimmed). It is only possible where no automatic rate exists (a gap, never an override): a day that has a qualifying snapshot is refused, and so is a day that already has a manual rate. The server decides the effective date, the anchor and the currency; the client sends none of them. A price that deviates from the latest stored snapshot of that day by more than `maxSpreadBps` needs `acknowledgeDeviation`.

== Binding and self-confirmation

The conversion runs in one transaction without any network call. It carries the price and the snapshot or rate id the treasurer saw in the preview (`expectedPrice`, `expectedRateRefId`); a different rate (compared numerically, so `1.50` equals `1.5`) is refused and mints nothing. A member must not receive LTR converted at a rate he confirmed himself (`ForbiddenException`, also shown in the preview as `selfConfirmationBlocked`).

== Audit, data protection, restore

* Audit entries `PRICE_ORACLE_REFERENCE_RATE` (confirmation) and `PRICE_ORACLE_CONVERSION` (conversion in the reference-date mode only; the ordinary mode writes none, as before). Payloads hold dates, ids and the *length* of the evidence text, never a price, an amount or the text.
* `price_oracle_snapshot_source` has no personal data (allowlist in `PersonalDataRegistry`). `price_oracle_reference_rate.confirmed_by` is covered by `PriceOraclePersonalData` (export lists the member's confirmations; erasure retains them with a reason, GoBD).
* Backup and restore read the schema from `information_schema`; the new tables and the new columns need no code (`OrganizationBackupRoundTripTest` covers them). A backup taken after V171 cannot be restored onto a server that is still before V171.

== Reference date from the bank booking (V1.9.327, schema V173)

The conversion can be tied to the bank payment that is converted. In the form the treasurer picks the member, then the donation (`listDonationPaymentCandidates`); the amount and, where possible, the reference date follow from the payment.

[source,kuml,name="price-oracle-conversion-payment-link"]
----
classDiagram(name = "Price oracle conversion and bank payment (V173)") {

    val paymentTransaction = classOf(name = "PaymentTransaction") {
        attribute(name = "id", type = "UUID")
        attribute(name = "intent", type = "PaymentIntent")
        attribute(name = "status", type = "PaymentTransactionStatus")
        attribute(name = "amount", type = "BigDecimal")
    }

    val bankStatementLine = classOf(name = "BankStatementLine") {
        attribute(name = "bookingDate", type = "LocalDate")
        attribute(name = "status", type = "BankStatementLineStatus")
    }

    val priceOracleConversion = classOf(name = "PriceOracleConversion") {
        attribute(name = "paymentTransactionId", type = "UUID")
        attribute(name = "referenceDateSource", type = "ReferenceDateSource")
        attribute(name = "referenceDate", type = "LocalDate")
    }
}
----

* *Candidates*: captured donations (`intent = DONATION`, `status = CAPTURED`) of that member in the donation currency, backed by **exactly one** `bank_statement_line` in status `POSTED` (a payment with several is ambiguous and left out, as in V168), not converted yet; newest first, at most 50. Since V1.9.329 the candidates come from `donation` (see below) and include PayPal and Stripe donations without a booking day.
* *Booking day*: `bank_statement_line.booking_date`, the exact calendar day of the statement. It is **not** derived from `payment_transaction.received_at` (a start-of-day value in the organisation zone that may have been corrected afterwards).
* *Origin of the date*: `price_oracle_conversion.reference_date_source` (`BANK_BOOKING` when the reference date equals the booking day, otherwise `MANUAL`) is derived by the server alone. There is no input field for it. A booking of today is no reference date (the day is not over), so the form leaves the date empty and says why.
* *Checks* (all `ConflictException`, naming no foreign data): the payment exists and belongs to the member, is a captured donation in the donation currency, has exactly one posted bank line, and its amount equals `donationAmount` to the cent (`BigDecimal.compareTo`; the form makes the amount read-only). The payment row is locked (`FOR UPDATE`).
* *Once only*: `uq_poc_payment_transaction` (UNIQUE) plus the lock. Two simultaneous requests: one wins, the other gets a conflict and its whole transaction, including the `MINT`, is rolled back. `fk_poc_payment_transaction` is `ON DELETE RESTRICT`.
* *Mode CURRENT* is unchanged: a payment id there is refused (nothing is minted); the double-conversion guard exists only in the reference-date mode. It also only covers conversions linked to a payment: a donation converted earlier without a payment link (reference-date mode with `paymentTransactionId` empty, or in mode CURRENT) still appears as a candidate, and converting it via the payment mints a second time. The treasurer must check for an earlier unlinked conversion of the same donation first.
* *Audit and notes*: ids and flags only (`paymentTransactionId`, `referenceDateSource`, `rawValuesStored`); never an IBAN, a payer reference or an amount.

== Donation entity (V1.9.328, schema V174)

A reference-date conversion converts **one donation, once, in full**. The donation is an entity of its own (`donation`), no longer only a payment id on the conversion.

[source,kuml,name="price-oracle-donation-entity"]
----
classDiagram(name = "Donation entity (V174)") {

    val member = classOf(name = "Member") {
        attribute(name = "id", type = "UUID")
    }

    val paymentTransaction = classOf(name = "PaymentTransaction") {
        attribute(name = "id", type = "UUID")
    }

    val donation = classOf(name = "Donation") {
        attribute(name = "id", type = "UUID")
        attribute(name = "paymentTransactionId", type = "UUID")
        attribute(name = "memberId", type = "UUID")
        attribute(name = "amount", type = "BigDecimal")
        attribute(name = "currency", type = "String")
        attribute(name = "bookingDate", type = "LocalDate")
        attribute(name = "createdBy", type = "UUID")
    }

    val priceOracleConversion = classOf(name = "PriceOracleConversion") {
        attribute(name = "donationId", type = "UUID")
        attribute(name = "referenceDateSource", type = "ReferenceDateSource")
        attribute(name = "referenceDateOverrideReason", type = "String")
    }
}
----

* *Rows*: `donation` (id, `payment_transaction_id` UNIQUE, `member_id`, `amount` DECIMAL(18,2), `currency`, `booking_date`, `created_at`, `created_by`). A row is created by the V174 backfill (captured `DONATION` payments of a member with exactly one `POSTED` bank line; the id equals the payment id because a UUID function in SQL is not portable between H2 and PostgreSQL, and nobody may rely on that) or, in the same transaction as the first successful conversion, by `DonationStore`. `DonationStore` is the only writer and inserts only.
* *Lock order*: payment row first, donation row second, whichever id the caller sends (`donationId` or `paymentTransactionId`). Two requests for one donation queue on the payment row and cannot deadlock.
* *Once only, three times*: UNIQUE `donation.payment_transaction_id`, UNIQUE `price_oracle_conversion.donation_id`, UNIQUE `price_oracle_conversion.payment_transaction_id` (V173).
* *The conversion equals the donation*: the composite foreign key `(donation_id, payment_transaction_id, member_id, donation_amount, donation_currency)` -> `donation (id, payment_transaction_id, member_id, amount, currency)` (target: the UNIQUE constraint `uq_donation_link`; an index would not do for H2). A `MATCH SIMPLE` key is not checked while `donation_id` is NULL, so CURRENT conversions and pre-V174 rows without a donation stay valid.
* *CHECKs*: `chk_poc_donation_payment` (donation and payment are set together), `chk_poc_override_reason` (no donation: no reason; `BANK_BOOKING`: no reason; `MANUAL` with a donation: 10 to 500 characters), `chk_donation_amount` (> 0), `chk_donation_currency` (upper case).
* *Reference date*: the origin is still derived by the server (`BANK_BOOKING` when the date equals `donation.booking_date`). Any other date is `MANUAL` and needs a reason of 10 to 500 characters (trimmed; no real IBAN, checked by `IbanText` after the length bound). The reason is stored in `reference_date_override_reason` and shown to the treasury roles and the affected member's own data export. It never reaches the ledger note, a log line or the audit snapshot: the audit entry carries only its length and a SHA-256 digest. "Strictly before today" is still checked by the resolver alone.
* *Booking day frozen*: a stored donation keeps the booking day it was created with. If its bank line changed afterwards (cancelled, a second posted line) the donation is no longer convertible; there is no update path (open question F8).
* *Audit*: `AuditEntityType.DONATION` / `CREATE` (ids and booking day, no amount, no IBAN) when a donation is created by a conversion, then the conversion entry.
* *Data protection*: `PriceOraclePersonalData` exports a member's donations (and, by id only, those the member created as the actor) and retains the rows on erasure (GoBD).
* *Backup*: no restore hook. The restore order follows the foreign keys (`payment_transaction`, `member` -> `donation` -> `price_oracle_conversion`); the once-only locks work after a restore. **A backup taken after V174 cannot be restored onto a server that is still before V174.**
* *Migration aborts on purpose* for an inconsistent V173 row: `chk_poc_donation_payment` (the conversion's payment has no matching donation, e.g. its bank line is no longer the only posted one) or `fk_poc_donation_link` (amount, member or currency differ). The migration header carries the diagnosis query.
* *Behaviour change*: in mode REFERENCE_DATE a conversion needs a donation. Conversions "without a bank payment" (cash donations, donations without a bank booking) are no longer possible there (open question F1). Mode CURRENT is unchanged and refuses the new fields.
* *Not in the wave*: partial conversions and splits (F5).

== A donation for every payment (V1.9.329, schema V175)

* *Creation*: `DonationStore.ensureForPayment` is the only way a donation comes into being. It creates one row for every `CAPTURED` payment with intent `DONATION` and amount > 0 and returns nothing (writes nothing) for any other payment. It is called where such a payment is written: `BankStatementStore.assignLineToDonation` (after the bank line is `POSTED`, so the booking day is found), `PspWebhookIngestion` (right after the idempotent payment insert; the duplicate path returns earlier) and, as a fallback for older payments, the conversion itself. Order everywhere: payment, then donation, in one transaction. A lost race is answered by `uq_donation_payment_transaction` (only 23505 counts) with the existing row. `DonationStoreTripwireTest` fails when a new file inserts a `payment_transaction`.
* *Nullable columns*: `member_id` (anonymous donation) and `booking_date` (not backed by exactly one `POSTED` bank line). An anonymous donation can never be converted: `price_oracle_conversion.member_id` is NOT NULL and the composite foreign key checks it. The conversion RPC answers with the same neutral message as for a foreign or refunded donation.
* *Reference date without a booking day*: the origin is `MANUAL` and a reason is required. The origin is derived on the server (`donation.booking_date != null && referenceDate == booking_date` is `BANK_BOOKING`, everything else `MANUAL`); there is no field for it in the input.
* *Candidates*: `DonationStore.candidatesOf` reads open donations of the member in the donation currency (captured payment, no conversion by donation or payment), newest first by booking day or arrival day, at most 50. The DTO carries `bookingDate` (nullable), `channel` (`BANK`, `PAYPAL`, `STRIPE`, `OTHER`, information only) and `receivedDate` (in the organization's time zone).
* *Migration V175* (V174 is on `master` and is not edited): drops `fk_poc_donation_link` and `uq_donation_link`, makes both columns nullable, re-creates the unique constraint, backfills missing donations, links unambiguous legacy conversions through a helper table (the plan is computed from the state before any update, because H2 and PostgreSQL evaluate a self-referencing UPDATE differently) and re-creates the foreign key. No audit entry is written for the linking; the header carries diagnosis queries.

== Not in this wave

Bitcoin and fiat anchors; the LBMA PM fixing; a PDF receipt; voiding a manual rate; a four-eyes rule; rate limiting of the two new methods beyond the existing role check (no network call, one cheap indexed read each).

== Second user: refund of a travel expense report (V1.9.325)

`ReferenceRateConversion` is a thin facade in front of `PriceOracleReferenceRateResolver`: it resolves a reference date, does the LTR arithmetic (`amount / (peg * price)`, scale 2, half up), records a manual rate and maps a resolution to its DTO. It adds no rate logic and does not check the donation conversion mode (that check stays in the donation RPCs, in front of the call). `PriceOracleService` and `TravelExpenseLtrPayout` are its two callers; the allow list of `ReferenceDateTripwireTest` names the facade, the service and the resolver, and nothing else may name the resolver. The donation behaviour is unchanged.
