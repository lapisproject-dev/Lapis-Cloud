= UI/UX Guideline -- Foundation Building Blocks (W1)
:description: The shared table, state and token building blocks of the Lapis Cloud client UI/UX guideline, their rules and the tripwire that keeps migrated screens honest.
:toc:
:toc-placement: preamble
:icons: font

== Context

The client had grown one bespoke table per screen: different densities, no shared loading/error/empty
grammar, hard-coded hex colours in the conference code, no card layout on a phone and no way to sort. Wave V1.4.25
("W1 Foundation") introduces the shared building blocks and migrates three screens onto them
(`MemberAdministrationScreen`, `ContributionsScreen`, `OpenItemsScreen`). W2-W5 migrate the rest; until then a
tripwire test keeps the debt visible and stops it from growing.

It is a pure client wave: no RPC, DTO, table or migration.

== Principles

* One grammar per concept: one table density, one loading state, one error state, two empty texts.
* A state is not a toast. The toast that `guarded` shows is the notification; the state box stays and offers the way out.
* Colour is a token, never a literal. The one exception is a document colour on a canvas (whiteboard paper).
* Touch targets are at least 44 px under `pointer: coarse`; nothing relies on hover.
* Foreign data is text: cell content goes in as widget content, never as HTML.

== Decisions

[cols="1,3"]
|===
| Decision | Rule

| Table density
| `TableType.STRIPED`, `HOVER`, `SMALL` and `ResponsiveType.RESPONSIVE` together, always -- through `standardTable` or `dataTable`.

| Narrow viewports
| Below 768 px (`CARD_LIST_BREAKPOINT_PX`, media query `(max-width: 767.98px)`) a `dataTable` renders a card list. The only new breakpoint.

| Numbers
| Numeric columns are right-aligned with tabular figures and `white-space: nowrap` (`.lapis-num`) on `th` and `td`. A date that identifies a row (the primary column) stays left. Amounts are localized (grouping, decimal separator, currency position per UI language) and use the display minus U+2212 -- see wave W6a.

| Sorting
| A native `button` in the `th`, `aria-sort` on exactly one column, tooltip = next action, `aria-label` = current state once sorted. The idle icon is `fa-sort` in `--lapis-muted`, never a dimmed opacity (WCAG 1.4.11).

| Load states
| Loading, error, empty, no-match, content. The error sentence is fixed (no exception text, no identifier).

| Motion
| One `prefers-reduced-motion: reduce` block, last in `theme.css`, listing every selector that has a `transition`.
|===

== Building blocks

=== `DataTableState.kt` (pure)

* `SortDirection`, `SortState(key, direction)`, `nextSortState(current, clicked, firstDirection, allowUnsorted)`
* `ariaSortValue`, `sortIconClass`, `sortButtonTexts` -- ARIA value, icon class, tooltip and accessible name
* `DataColumn<R>(title, numeric, primary, sortKey, cell)` -- exactly five fields; `textColumn` is a factory for plain text
* `cardLayout(columnCount, primaryFlags)` -- primary column (default: column 0) and detail columns; a second primary is rejected
* `DataViewState` and `resolveDataViewState(loaded, isEmpty, filterTerm)`

=== `DataScreenLayout.kt`

* `dataScreenRoot(spacing = 16)`; screen widths `DATA_SCREEN_MAX_WIDTH_PX` (1440), `NARROW_FORM_MAX_WIDTH_PX` (480),
  `READING_MAX_WIDTH_PX` (720), `DASHBOARD_MAX_WIDTH_PX` (640) -- the last three are declared, not yet applied
* `standardTable(headers: List<TableHeader>)` and `Row.numCell(...)` for hand-built tables

=== `DataTable.kt`

`dataTable(columns, rows, sort, onSort, sortOptions, actions, focusSortKey)` is stateless: rows and the current
sort come from the caller, which reloads and calls it again on `onSort`. Pass `focusSortKey` so the keyboard focus
returns to the header button that was pressed. The mode (table or cards) is decided synchronously at construction
and re-decided on media-query changes, but re-rendered only when it really flips; the listener is released with the
widget. Cell lambdas run again on every re-render -- keep no state in them.

=== `DataSection.kt`

`dataSection(emptyText, filterTerm, noMatchText, isEmpty, onSettled, load, render)` owns a load and returns a
handle with `reload()` (call it once for the first load). The widget-free `DataLoadController` holds the lifecycle
and a generation counter that drops superseded results. The loading text lives in a `role="status"` live region that is
mounted once (`dataStatusRegion`, `DataSectionViews`) -- only its text changes, because a live region created together
with its text is not announced. `dataErrorState(onRetry)` is also usable on its own -- `OpenItemsScreen` has its own
cursor paging and client filter and only uses the error state.

== Row heights

[cols="1,1"]
|===
| Situation | Target

| `pointer: fine`
| `table-sm` rows

| `pointer: coarse`, row without a button
| at most 48 px

| `pointer: coarse`, row with an icon button
| at most 52 px (a 44 px button in a `table-sm` cell cannot be smaller; the cell padding drops to 2 px, about 49 px)

| Card
| 12 px padding, hairline border, no zebra, no shadow
|===

The 44 px target size is never undercut.

== Tripwire and debt ledger

`ClientUiGuidelineTripwireTest` (module `lapis-server`, it reads the client sources as text) enforces:

[cols="1,3"]
|===
| Rule | Check

| R2 | no `width = N.px` with N of 600 or more (use `maxWidth`)
| R9 | no colour literal in client Kotlin: `#hex`, `rgb()`, `rgba()`, `hsl()`, `hsla()`, `0xRRGGBB` (baseline: the whiteboard paper constant and three semi-transparent overlay chips in `ConferenceScreen`)
| R11 | every colour token of ANY light `:root` block (hex, `rgb()`/`rgba()`/`hsl()`/`color-mix()`, colour keywords, `var()` aliases of colour tokens) exists in both dark blocks, no colour token exists only in a dark block, and the two dark blocks agree; non-colour tokens (fonts, widths) are exempt
| R14 | every `table(...)` call carries `STRIPED`, `HOVER` and `SMALL` (also a call broken before the dot: `panel` newline `.table(`)
| R15 | every `table(...)` call carries `ResponsiveType.RESPONSIVE`
| R39 | an icon-only `button("", icon = ...)` (also `button(text = "", icon = ...)`) carries `title` and `aria-label` in the same block; the one factory line in `DataScreenLayout.kt` that labels its button in the next statement is exempted by name, not the file
| R24 | (W4a, extended W4b) no labelled `text(`/`password(`/`textArea(` call (a call that carries `label =`) in the 22 screens and dialogs migrated to the form grammar or in the 5 screens that have no labelled field to migrate, and (positive check) a `lapisForm(` in each migrated file, closed by `buttons(` or `finish(`; the search/filter fields of W4b are named exceptions (fingerprint, reason "a filter is not a form"). A downward ratchet (`R24_REMAINING_MAX`, 228 after W4b) covers the labelled fields outside the strict set; its floor (150) only guards against a vacuous scan
| R24B | (W4b) the same for labelled `select(`/`checkBox(` calls -- a SECOND counter, R24 is not redefined. The strict set holds them only as named exceptions (filter, area/action selector, immediate switch, selection list); a downward ratchet (`R24B_REMAINING_MAX`, 131 after W4b) covers the rest. The factories in `FormGrammar.kt` are exempt
| R55 | no `width = N.px` in client Kotlin (a fixed column width on a row or header cell is the mark of a pseudo-table; `maxWidth`/`minWidth` are not matched). Ledgered per file: after W3 `AuctionScreen`, `CrowdfundingScreen` and `PoliticianScreen` remain as hand-built pseudo-tables (a remainder wave, W5 in this document) and `SocialNetworkScreen` as one genuine form field (W4) -- they are not "form screens"
| C7c | no `reportTable(` call carries sort wiring (`onSort`, `sort =`, `sortOptions`, `sortKey`, `focusSortKey`); a text check of the call's own arguments, so a sort control added by a later statement is not seen -- the runtime side is `ReportTableDomTest`
| R54 | every selector with a `transition` is in the single `prefers-reduced-motion` block, nothing else is, and no transition is longer than 200 ms
|===

Rules R2, R9, R14, R15, R39 and R55 have a debt ledger with **one fingerprint per finding**: rule, file name, and the
trimmed source line of the offending spot (no line number; a line that starts with `.` is prefixed with the previous
code line). Compared as a multiset per file, so the test fails on a new finding, on a paid-off finding (delete its
ledger line) and -- unlike a plain count -- when one violation is fixed and another added in the same file. Editing a
ledgered line changes its fingerprint on purpose: re-list or pay the debt. Two findings with an identical line in one
file are indistinguishable (their number is still pinned). Files not in the ledger are held strictly -- that includes
the three migrated screens and the new building blocks. Every rule has a self-test with a bad and a good example.

`UiFoundationI18nCatalogTest` (W1), `HotTableI18nCatalogTest` (W2) and `PseudoTableI18nCatalogTest` (W3) guard the new strings: present in the template and all seven catalogs, translated,
with the `%N` placeholders intact. Each scans its own helper files completely and the migrated screens only through an
explicit list of the sentences that wave added -- the rest of those files is NOT covered (see Known gaps), because
they carry pre-existing debt that would fail the test for somebody else's reason.

Eleven files migrated: `LedgerScreen` (chart of accounts, journal, posting lines), `SepaBatchesScreen` (runs,
preview, items, returns), `SepaMandatesScreen`, `PaymentTransactionsScreen`, `DunningCasesScreen` (cases, notices),
`DonorsScreen`, `BankAccountsScreen`, `MemberFinancialHistoryScreen`, `MemberAnniversariesScreen`,

=== Decisions this wave had to make

[cols="1,3"]
|===
| Question | Decision

| Where do sort headers belong?
| Only on a list that is loaded COMPLETELY (chart of accounts, journal page). There the sort is a pure function
  (`sortLedgerAccounts`, `sortJournalEntries`) over the loaded rows. A cursor or offset list gets none: the server
  has no sort parameter, so re-ordering the loaded subset would contradict the order of the next page.

| Account numbers: number or text?
| Text. `0400` and `400` are two different accounts; a numeric comparison collapses them and fails outright on a
  non-numeric number. Secondary key is always the account number, so equal values keep a stable order.

| A search field over a partially loaded list?
| Yes, but never silently. `dataCountText(..., filtered = true, hasMore = true)` states that filters and search
  reach only the loaded rows, and `loadedSubsetNoMatchText` offers loading more as the way out. A bare "0 of 40"
  over a partial list is a false statement about the data.

| Which counter form?
| One function, three forms: filtered -> "shown of loaded"; unfiltered with a known total -> "loaded of total";
  unfiltered cursor list -> "N loaded" (+ "more on the server"). A cursor list never prints "12 of 12" -- it does
  not know a total.

| Does a phone get a card list inside a modal too?
| Yes. The member table of the family dialog used to run out of the dialog sideways; the breakpoint is a property
  of `dataTable`, not of the screen.

| The "default account" star glyph?
| Replaced by a `typeBadge` reading "Standard". A lone glyph is one channel, and a screen reader read nothing
  there. "Default" is a fixed category, not a lifecycle, so `typeBadge` is the right one of the three badges.

| Deleting a bank account had no confirmation.
| Added, as a direct consequence of this wave: an unlabelled bin icon between two other icons is far easier to hit
  by accident than a button reading "Löschen" (P6/R30).
|===

== Wave W3 "Pseudo tables" (V1.4.27)

Nine screens migrated for the first time and two revisited: `FinancialReportsScreen` (GuV, Bilanz,
Jahresabschluss), `NonprofitComplianceReportsScreen` (four spheres, use of funds, USt preview), `CostCentersScreen`
(overview AND report), `AuditLogScreen`, `LtrLedgerScreen`, `DocumentsScreen` (list and versions), the three approval
queues, plus the report parts of `LedgerScreen` (Hauptbuch, Kassenbuch, posting confirmation) and `DonorsScreen`
(the two section-25-PartG grids). The R55 ledger started with 185 fixed-width findings in 11 files.

=== Two table grammars, one criterion

[cols="1,3"]
|===
| Grammar | Use it when

| `dataTable` (list)
| A row stands on its own: a member, a cost centre, a document, an audit entry. Sortable when the list is loaded
  completely, card list below 768 px.

| `reportTable` (document)
| A row is only right in the context of its neighbours: a running balance, a number sequence, a total underneath.
  A real `<table>` in the responsive frame with a `<caption>`; section (a spanning `th`, no `scope`), sum and balance
  rows (their label is a `th scope="row"`); **no** sort buttons and **no** card list -- a card list renders only
  `rows`, so a sum row would silently vanish on a phone. Below 768 px it scrolls sideways.

| Both on one screen
| Allowed, and not a second grammar for one object: `CostCentersScreen` shows the cost centres as a LIST (`dataTable`,
  each row stands alone: edit, deactivate) and, below, a cost-centre REPORT (`reportTable`, rows only make sense with
  the total underneath). The criterion is per object and per purpose, not per screen. What is NOT allowed is the same
  object in both grammars -- the posting lines of a journal entry are a `reportTable` in the journal detail, in the
  posting confirmation and in the audit log's snapshot.

| Cards (`.lapis-card-list` / `.lapis-data-card`)
| A row needs a free-text field or carries a decision with a reason (the three approval queues). Never a second
  grammar for the same object (P3). Welle V1.8.2b's `AiDraftsScreen` is the same case, deliberate, not a missed
  migration to `dataTable`: at most `PostDraftStore.MAX_OPEN_DRAFTS_PER_MEMBER` (10) open drafts plus a handful of
  restorable discarded ones -- no sorting/filtering/pagination need -- and each card must visually anticipate the
  post it becomes (content, visibility, edit/release/discard actions inline), the same shape `SocialNetworkScreen`
  already uses for a real post.
|===

=== Decisions this wave had to make

[cols="1,3"]
|===
| Question | Decision

| Where do the figures come from?
| `ReportRows.kt`, once per report, pure and widget-free. The renderer only paints `ReportRow`s. `ReportGoldenTest`
  pins every cell string (blank cells and the row kind included); `ReportCellOracleDomTest` proves them against the
  DOM -- first the old `hPanel` renderers, then strictly the new tables. A golden value is never generated from the
  new code.

| Sum row versus Bootstrap's zebra
| The zebra is `--bs-table-bg-type` plus an inset shadow (5 % of the emphasis colour over the cell colour), and its
  selector has specificity (0,2,2). The report classes use `.table > tbody > tr.lapis-total-row > td` (0,2,3), set
  `--bs-table-bg-type` to the same opaque value as the background and win without `!important`. The surface is its
  own token, `--lapis-total-surface` (light #DBE0E8, dark #232933), NOT `--lapis-surface-sunken`: in the light theme
  the zebra is sunken plus 5 % black (#EBECEF), so a sum row in plain sunken (#F6F7F9) was LIGHTER than a zebra row.
  The top rule is `--lapis-muted` (at least 3:1 against both neighbours, WCAG 1.4.11), and warn-red amounts on
  these rows read `--lapis-total-danger-rgb` (at least 4.5:1). Report tables use `border-collapse: separate`: with
  collapsed borders the 1-px rule of a balance row loses against the 1-px bottom line of the row above and never
  shows. `ReportRowStyleDomTest` loads the real Bootstrap and `theme.css` into Karma and compares the VISIBLE
  background (colour plus shadow layer) of a sum row with a zebra row and a plain row, in both themes, and checks
  the contrast numbers.

| Where does the caption stand?
| Bootstrap's reboot sets `caption-side: bottom`; its own utility `caption-top` on the table fixes it without new CSS.

| Section headings and row headers
| A section heading is a spanning `th colspan` WITHOUT a `scope`: the report has ONE `<tbody>` (KVision's `Table` has
  no per-section body), and a `scope="rowgroup"` would let "Aktiva" claim the "Passiva" rows below it too. The label
  of a sum or balance row is a `th scope="row"` (the first text cell, also behind the blank cells of a ledger row);
  the column headers are `th scope="col"`.

| A caption that repeats the heading above
| The caption is the table's accessible name, so it stays; a caption that only repeats the heading or the account
  header right above the table is hidden visually (`reportTable(captionVisible = false)`, the `theme.css` rule
  `.lapis-report-caption-hidden` is Bootstrap's `visually-hidden` recipe). Inside a Jahresabschluss the embedded GuV
  and Bilanz keep their visible captions -- there they are the only heading.

| Do the toggle labels follow a language switch?
| No, by a known limit: the `aria-label` of every icon button (`expandToggleButton`, every `tableActionButton`) and the
  `title` of the expand toggle are resolved once, when the button is built (a `title` set from a `tr(...)` string does
  follow a switch). Attributes go around KVision's patch cycle, so a switch re-renders the
  `tr(...)` texts of an open report (captions, headers, row labels, sum labels) but not these two attributes; they
  catch up when the report is loaded again. The same is true for badge labels and the period lines ("Zeitraum: ...").

| How is a detail row collapsed?
| With `d-none`, not KVision's `hide()`: a hidden KVision widget leaves the DOM, and `aria-controls` must name an
  element that exists.

| Should the audit log sort?
| No. It is keyset-paginated (`beforeSequenceNumber`) and the server has no sort parameter -- re-ordering the loaded
  pages would contradict the next page. The list is a `dataTable` over all pages loaded so far, without `onSort`.

| The "Summe %1" label
| `trFormat(tr("Summe %1"), title)`: a composed `tr` string that keeps the marker prefix (the widget re-resolves it on
  every render) and whose title argument `I18nCatalogManager` resolves per language. It used to be
  `gettext("Summe %1", title)`, which resolved once and left the title's marker in the text ("Summe
  ###KvI18nS###Einnahmen") -- a defect of the old renderers that the first version of the wave preserved on purpose
  and the audit round fixed. `TrFormatTest` and `ReportLanguageSwitchDomTest` pin it.
|===

== Wave W4a "Form grammar, part 1" (V1.4.28)

The first half of the form roll-out: the building blocks (`FormGrammar.kt`, `FormRules.kt`) and the screens where a
form decides whether a person can get in or can safely change something -- login, the three registration and
password-reset screens, the admin password reset, the SEPA, dunning and receivable-dunning settings, the stream
destinations, the restore and the API-key issue form. A pure client wave: no RPC, DTO, table or migration was touched
and **every validation RULE is unchanged** (`Validation.PASSWORD_MIN_LENGTH`, 12..128, e-mail 320, the 1..30 prenotification
days, the dunning bounds, 3..1000 for a reason) -- **with two corrections made in review of this wave**: (1) the login
screen and its "request reset" form carry no e-mail format rule at all any more (only "not empty"), because accounts
whose identifier has no dot after the `@` (`admin@localhost`, `hans@intranet`) exist and must stay able to sign in; the
format rules stay on the screens that CREATE an identifier (registration, friend registration); (2) the dunning fee
field (`DunningSettingsScreen`) now uses the same amount parser as the receivable-dunning form: "12,999" and "1e1" are
rejected (before, "12,999" was silently rounded to 13,00), "2,50" is accepted, and "0" stays valid here -- what the field
approves is exactly what is saved. Do not revert (2) as a regression. Otherwise the rules only became visible earlier and
at the field. The server stays the authority. W4b (members, committees, meetings, motions, events, communication, CRM, DSGVO) and W4c (the
finance forms) reuse the same building blocks.

=== The grammar

[cols="1,3"]
|===
| Part | Rule

| Required fields
| Marked ONCE per form, in one of three ways (decided in `LapisForm.buttons`, where the field set is complete): (a) mixed
  (at least one required AND one optional field) -- a `*` on every required label plus the legend "* Pflichtfeld" above
  the first field; (b) three or more fields, all required -- no stars, the legend "Alle Felder sind Pflichtfelder.";
  (c) exactly two fields, both required -- neither stars nor a legend. **A single required field is NOT case (c)** (V1.4.29
  audit): it is marked like (a), a star plus the legend, because a lone required field without any marking is not
  recognisable as required. Several forms in ONE dialog (the member editor has six) share a `LegendGroup`: the same legend
  stands once, over the first form that needs it; the stars stay on every required label. `aria-required` is on the input in
  ALL three cases.
  The star is `aria-hidden` and NOT red: an empty required field in a fresh form is not an error.

| Errors
| At the field: an `invalid-feedback` slot that is mounted permanently and linked with `aria-describedby` (hint first,
  then the error). An error changes only the slot's `content` and a class -- never the structure. **That is about
  assistive technology (a live region announces a text CHANGE), not about layout:** a visible error is a
  `display: block` and DOES push everything below it down, including the submit button. The click is saved by the
  pointer gate instead (next row).

| The pointer gate (why the first click is not lost)
| `blur` fires on the mousedown of a button. If the error appeared then, the button would slide down between mousedown and
  mouseup, the mouseup would land on another element and the browser would fire no `click`. So while the mouse button is
  pressed on a button (`button`, `.btn`, `role=button`) the blur check is DEFERRED and made up after the mouseup (and its
  click). There is exactly ONE pair of `document` observers for the whole application (`PointerGate`), never one per form: a
  hidden KVision modal stays in the DOM, so per-form observers would never be released. Because that gate is global and never
  torn down it must not get stuck: a `mouseup` that never arrives (released outside the window, Alt-Tab, a context menu, a
  cancelled pointer gesture, a drag) would otherwise defer every later blur check of the application. The window `blur`,
  `pointercancel`, `contextmenu`, `dragend`, the pointer leaving the window and a 5 s time limit therefore release the gate
  and run the deferred checks. Chosen over a reserved error height because a message wraps differently per language and width -- a fixed height guarantees no
  stability and leaves a gap between every pair of fields. The keyboard (Tab) is not affected: there is no mouseup to miss.
  `FormGrammarAuditDomTest.theFirstClickOnAButton_afterLeavingAnInvalidField_isNotLost` asserts the button position and
  the element under the mousedown point at mouseup time (a synthetic `.click()` cannot show the defect).

| When is a field checked?
| On leaving it, but ONLY when it was touched (typed into) or the form was submitted once -- a field that was merely
  tabbed through stays silent. Typing clears an existing error and never creates a new one. No `keyup` validation, no
  debounce.

| Submit
| Validates everything. On errors: focus on the FIRST invalid field, scroll it into the middle (no animation), one
  collective message "Bitte korrigieren Sie diese Felder: ..." in a `role="alert"` region that is mounted (empty) when
  the form is built -- assistive technology announces a text CHANGE in an existing live region, not a region inserted
  with its text -- and NO server call. A form with exactly ONE field and no cross rule shows no collective sentence (it
  would repeat the field error). The collective sentence clears itself as soon as every field is valid again (a server
  text is not cleared by typing). Otherwise `runGuardedAction` with `aria-busy` on the button: no spinner, no text
  change. Server errors use the same region (`showFormError`; it fails loudly if called before `buttons()`/`finish()` has
  mounted the region). `LapisForm.validateAndReport()` is the checking half of `submit` for forms whose submit needs a
  confirmation first (the restore); `LapisForm.runBusy()` is the `aria-busy` half.

| Button order
| Cancel left, the confirming action right (guideline 2.5 / R27). The task text asked for "primary action left"; the
  guideline and every modal of this code base already do it the other way round, so the code follows the guideline.
  Exactly one `PRIMARY` per form (R28, by eye -- it cannot be checked textually per form). A destructive action stands
  in its own zone BELOW the button row, separated by a hairline (`lapis-form-danger-zone`) -- in a view with 14 px
  spacing a 16 px gap is no signal.

| Programmatic writes
| A value that code (not the person) puts into a field -- a preset from a dropdown, "Neu erzeugen", clearing and locking
  a field -- goes through `LapisField.setValue`, never through the raw control (`Input.value = ...`, `field.control as
  Text`): a control write raises no `input` event, so a field error that was already showing would stay. Directly after
  `setValue` call `validate(force = false)` (the new value may be valid or invalid; an untouched field stays silent) or,
  when the field is emptied and disabled in the same step, `clearError()`. Only where no error can be showing yet (the
  first load of saved settings) may the follow-up call be left out. Since W4b this also holds for a `Select` (`setValue` takes
  one; the options of a select that is filled after an RPC are set on the control first, then the value through the field) and
  for a reset of a `checkField`. This class of defect appeared three times in W4a
  (`MemberPasswordResetDialog` regenerate, `DunningSettingsScreen.updateFeeLock`,
  `ConferenceStreamDestinationsScreen.applyPlatformDefaults`); `ProgrammaticFieldWriteDomTest` and
  `SecretFieldDomTest` pin the three paths. There is no textual tripwire for it (a `.control as` cast is also a
  legitimate read), so W4b/W4c screens must follow this row by review. `setValue` on a control that is not a text
  control (a `select` registered with `register`) fails loudly instead of doing nothing; `reset()` also empties an
  upload.

| No "valid" state
| No `is-valid`, no green tick.
|===

=== Decisions this wave had to make

[cols="1,3"]
|===
| Question | Decision

| Where does the star go?
| `Tag.render()` renders the CHILDREN before the `content` text. A `span(" *")` next to the label content would stand
  BEFORE the label text ("* E-Mail"). So the label text itself becomes the first child and the star the second
  (`FormGrammarDomTest.mixedForm_putsTheStarAfterTheLabelText` pins `"E-Mail *"`).

| Which attributes, and how?
| Only through KVision's `Widget.setAttribute` (it lives in the attribute map and survives a re-render AND a language
  switch), never through a raw `getElement()?.setAttribute` (lost when a language switch rebuilds the root), and never
  through an insert hook (`ClientLateHookRatchetTest` counts them). `EmbedIntegrationScreen` had one raw call for
  `readonly`; it is the typed `readonly` property now.

| The login password
| Checked for "not empty" ONLY, never against the password policy: a password that was valid when it was set must never be
  declared wrong by the interface. The general rule behind it: **a check that could make a false statement about the
  state of the system does not happen.** The server text is shown word for word -- it is hardened against account
  enumeration, so the client adds no differentiation (no separate "unknown e-mail"). The same rule removed the e-mail
  format check from the login identifier and the "request reset" form (review correction): an identifier without a dot
  in the domain is a legal account name and the client must not lock it out.

| Password rules
| The length rule stands as a hint UNDER the field (visible before typing) and as the identical error text; it left the
  label ("Passwort (mind. 12 Zeichen)" became "Passwort" plus hint). Constants are `%1`/`%2` placeholders, never part of a
  msgid.

| Secrets that are not the editor's own
| The stream key and the temporary password generated for ANOTHER person: `autocomplete="off"` plus

=== Two more factories and one parameter

`selectField` and `checkField` are members of `LapisForm` (they need its private wiring) -- **and nothing else is added: no
date or time factory** (K1). `selectField` puts hint and error slot BESIDE the `<select>`, never inside it (`Select.add()`
delegates to the `<select>`). `checkField` treats "required" as "ticked": KVision's `CheckBox.getValueAsString()` is the
string `"false"`, never empty, so the empty-value path of `LapisField` would make `required` silently useless. Three
corrections to existing behaviour came with them, each pinned by a DOM test: `LapisField.setValue` takes a `Select` (the
options of most W4b selects arrive asynchronously, and a `checkField` resets to unchecked); the listener of a select or a
checkbox sits on `control.input` (a `blur` does not bubble to the wrapper, so blur validation of a choice field never ran);
and every field factory takes `host: Container = panel` for the eight fields that sit in a horizontal row (inline rename,
the door's code row, the attendance status beside the name) -- `host` must be a descendant of `form.panel`.

=== Dependable double-click protection (R29)

Before W4a/W4b only `ReceivableDunningSettingsScreen` of the 22 files used `runGuardedAction` (three call sites), none used
`InlineConfirmGate`; 18 of the other 21 guarded some of their writes by hand with `button.disabled = true`, and
`EventCheckInScreen`, `SocialModerationScreen` and `StatuteQaScreen` had no guard (the last has its own `loading` flag). A hand-set
flag that is not released in `finally` is not a guard. `form.submit(button) { ... }` runs the action through `runBusy`, which is
`runGuardedAction`, so the ten W4b screens that submit through a form have it. Three things the wave first claimed and the
audit corrected:

* **The dialogs.** `confirmWithReasonDialog` had no protection (its `onConfirm` is a plain callback, and the modal's button stays
  clickable during the hide animation). The three dialogs and the two postal dispatch dialogs are one-shot now (`ConfirmOnce`).
* **The guard itself is tested.** `runGuardedAction` returns while the button is disabled (the DOM attribute lags one render
  behind the widget, so two fast clicks got through). `FormAuditFixesDomTest.submit_aDoubleClick_*` clicks twice at once and once
  later against a slow request and counts one request; the dialog tests do the same for the three dialogs.
* **A ratchet (tripwire R29).** A plain `AppScope.launch { ... rpcService<S>().write(...) }` in a migrated file, outside a
  `runBusy`/`submit`/`runGuardedAction` block, is counted (39 today; only ever lowered). It is honest about its limits: writes are
  told from reads by the method NAME, a hand-written guard is not seen, idempotency is not judged -- the 39 are a baseline of
  unjudged sites, not justified exemptions.

=== The posting lines

A row of six controls (account, debit/credit, amount, sphere, cost centre, VAT if usable) is a table for the eyes and a form for
everything else. Each control sits in its own cell; the error slots of the selects sit in ONE full-width row beneath the cells
(`.invalid-feedback` has `width: 100%` and would squash six controls into one column). ONE visible column-header row
(`aria-hidden`, star on the required columns) stands above the block; the field name stays on every control ("Betrag · Zeile 2":
the line number is a `%2` placeholder, never a number in the msgid) and is visually clipped, never `display: none`, so a screen
reader keeps it. **The header row shows the titles on every line -- the first line's own labels are clipped too** (a first line
with visible labels next to a header row would print every title twice). Below 768 px the header row is hidden and each line
becomes a card with its labels visible. At a coarse pointer all controls and the remove button already reach 44 px through the
existing `.btn:not(.btn-link)` and `.lapis-form .form-control/.form-select` rules -- nothing was duplicated.

`LapisForm.unregister(field)` / `LapisField.detach()` (idempotent) is the one grammar addition. The remove button deregisters the
six fields FIRST and removes the widget afterwards; `resetForm()` and `prefill()` deregister the old lines before
`rowsPanel.removeAll()`. A small internal `LapisField.relabel` renames a numbered field without losing its star (`appendRequiredMark`
moved the label text into a `span` before the star; only that span is replaced) and keeps `resolvedLabel` in step. A line added
AFTER `buttons()` marks its required labels itself (the grammar decides the stars once, when the form is completed). CSS: one block
in `theme.css` (`.lapis-posting-row`, `--headed`, `-cell`, `-remove`, `.lapis-posting-header`, `.lapis-balance-strip`), tokens only,
no hex. Contrast of the strip (measured): 16.6:1 light, 11.7:1 dark. **No third addition**: no date/time factory, no upload factory.

== Rule precedence: attributes and `gettext`

The guideline (section 2.14) says `tr()` only as widget content and, for attributes (`title`, `aria-label`,
`placeholder`), string templates, concatenations and as an argument of `gettext()`, always `gettext()`; it also calls a
`gettext()` without an argument a convention break. Where the two collide -- an attribute that needs a plain word, e.g.
`title = gettext("Speichern")` -- **the attribute rule wins**: `gettext()` is correct there, `tr()` would leak
KVision's `###KvI18nS###` marker into the DOM. `ClientTrAttributeLeakTest` sees only the direct case; helpers that
receive a `tr()` string and set an attribute (`tableActionTooltip`, `segmentedControl`, `sortButtonTexts`) resolve it
through `resolvedAttributeText` (marker stripped AND translated).

== Wave W6a "Localized and exact amounts"

A client-only wave (no server production code, no `lapis-shared` change, no migration: `git diff master --stat -- lapis-server/src/main lapis-shared db/migration`
is empty). It pays the W4c debt "`formatMoney` and `sumPostingLines` add `Double` values" and revises decision D5.

=== D5 revised -- and why

D5 (Accounting UI wave) said: `Decimal.toString()`'s digits are never touched -- no thousands separator, no decimal comma, no padding -- so a
displayed figure can never diverge from what the server computed. That protected the digits and produced a display nobody can audit:
`1234.5 €` is not readable for a treasurer, and `1234.5600000000001` (double noise) is a loss of trust right before an irreversible booking.
D5 falls; the protection of the digits is kept differently:

* The transform is pure STRING arithmetic (`groupDecimalDigits`): the integer part is grouped from the right, the fraction is padded to two places
  when shorter and left completely untouched when longer. A genuine sub-cent value is never rounded (`12.345` shows as `12,345 €`). No `Double` is
  involved, so no magnitude loses a digit (`1e21` keeps all 22 digits).
* **No `Intl.NumberFormat`, `toLocaleString` or `toFixed`.** They round to two places by default (`12.345` would silently become `12,35` -- the very failure D5
  meant to prevent) and depend on the browser's ICU version, which would make the golden tests flaky. Tripwire M1 keeps them out.
* Sums are exact (`sumExact`, `scaledUnitsOf`, `centsToDecimal`): the cleaned digit strings are added as integers at a common scale (at most 9);
  the result is turned back into a `Decimal` only if `displayDigits` maps it to exactly the same string, otherwise the call fails loudly.
  The posting confirmation dialog can no longer show `1234.5600000000001`.

=== Locale table

The eight UI languages; the group separator is U+00A0 (never U+202F); an unknown language, or `de-DE`-style regional tag, falls back to the base tag or German.

[cols="1,2,1"]
|===
| Language | Example for 1234.5 | Euro sign

| `de`, `es`, `it` | `1.234,50 €` | after
| `en` | `€1,234.50` | before, no gap
| `nl` | `€ 1.234,50` | before
| `fr`, `pl`, `ru` | `1 234,50 €` (U+00A0 group separator) | after
|===

The minus is U+2212 and stands first, also in front of a prefix euro sign (`−€1,234.50`). Zero is `0,00 €`, never signed.
`LTR` (and a donation currency such as `USD`) is always a suffix after U+00A0 in every language: a prefixed "LTR" would be an invented convention,
the prefix is a euro-sign convention. LTR is localized too (`formatLtr`), so a screen never shows a localized LTR amount next to a raw one.

=== Display versus machine-readable

Everything above is DISPLAY. What prefills a field or is compared against an entered amount (`displayDigits`, `displayAmountValue`,
`exceedsDisplayedAmount`) stays ASCII, dot-decimal and ungrouped (audit fix M3) -- a formatted amount is never parsed back. Tripwire M2 keeps
U+2212 out of values. Callers fall in three classes: (A) widget content (`moneySpan`, `ltrSpan`, `ReportCell.Money`/`Ltr`) -- live; (B) `gettext`
arguments -- plain `formatMoney`, frozen at the language of the moment; (C) machine-readable -- unchanged.

=== Live language switch

`I18n.language`'s setter restarts the root, which re-renders the EXISTING widget tree; it does not re-run the screen build, so a plain string
keeps its text. Widget-content amounts are therefore a `moneyToken`/`ltrToken`: a `###KvI18nS###` marker string with a control-character sentinel
(U+0002), a kind letter and the cleaned digits, resolved by `I18nCatalogManager.gettext` on every render -- the mechanism `trFormat` already uses. Rules:

* Never concatenate a token into another string (marker leak, audit V1.4.30); pass it as a `trFormat` argument or as a widget's whole content (tripwire M3).
* The sentinel is not typeable, and the formatter fails closed: an unknown kind returns the raw digits, never an exception, never `eval`.
* `ltrSpan` keeps its `◆` glyph inside the token, so the token stays atomic.
* One formatter: a second `" €"` / `" LTR"` literal outside `Money.kt` is a defect (tripwire M4).

=== Untrusted widget text (security rounds 1-4)

KVision's `Widget` class resolves ANY content string that starts with `KV_I18N_MARKER` through `I18n.trans`/
`gettext` on render (`io.kvision.core.Widget`), independent of `trFormat`. A vote option label, motion title, donor
name, or any other server-/member-controlled field handed straight to `div(...)`/`span(...)`/`p(...)`/`h1(...)`..
`h6(...)` as plain widget content -- not just as a `trFormat` argument -- can therefore render as a fabricated,
freely chosen amount if it carries a forged `KV_I18N_MARKER` + `MONEY_SENTINEL` payload.

Rounds 1-3 built the sanitization boundary (`sanitizeUntrustedI18nText`, a fixed-point strip of the marker/
sentinel/`I18N_ARG_SEPARATOR` -- a single `replace` pass can splice a deleted marker's neighbours back into a new
one, so it iterates to a fixed point instead) and the type-based `trFormat` trust guard (`trusted()`/`TrArg`,
replacing string-prefix trust). By the end of round 3 the rule was enforced at 32 call sites (30 in screens, 2 in
`I18nCatalogManager.kt`) plus the sanitizer's own declaration.

Round 4 added a ledger test, `ClientUntrustedWidgetTextTripwireTest` (`lapis-server`, a source-regex heuristic in
the style of `ClientMoneyFormatTripwireTest`), and measured the remaining exposure at **58** raw, unsanitized
`receiver.div/span/p/h1..h6(dto.field)` sites -- 21 of them the identical `fw-bold flex-grow-1` card/list header
shape repeated verbatim across screens. Instead of wrapping each in `sanitizeUntrustedI18nText(...)` by hand a
58th time, round 4 built the missing central choke point: `network.lapis.cloud.client.UntrustedText` (`untrustedDiv`/
`untrustedSpan`/`untrustedP`/`untrustedHeading`/`untrustedCardTitle`, each sanitizing its `text` argument
unconditionally) and migrated all 58 findings onto it, bringing the ledger to **1**.

The one remaining entry is deliberate, not a miss: `ApiKeysScreen.kt`'s freshly issued `result.rawKey` is the
actual secret shown to the operator exactly once. Sanitizing it would risk silently stripping bytes from a real
key (even control-marker bytes a real key is vanishingly unlikely to contain) and the operator copying a
corrupted value -- documented with an inline comment at the call site and a matching ledger-test assertion, not
fixed by sanitizing.

**Known gap, not closed by round 4:** the detector is a source regex; it only catches a DIRECT
`receiver.call(dotted.field.access)` argument. A local `val` holding an untrusted DTO field before it reaches a
widget call (`val label = donor.displayName; row.div(label)`) is invisible to it. No such pattern is currently
known to exist in the client, but a future one would not be caught by this ledger test -- code review remains the
second line of defense for that shape. **Also not verified in round 4 (out of scope, server-side):** whether the
server accepts `KV_I18N_MARKER`/`MONEY_SENTINEL` in incoming field values at all. A server-side input validation
pass rejecting or stripping these control sequences on write would be a second line of defense independent of the
client sanitizer, but was deliberately not undertaken in this wave (it is server code, and this wave's scope is
the client).

**Standing rule going forward:** when a new forgery-vector class is found (a widget-content path, an attribute,
a title, a tooltip -- anything KVision or the DOM resolves untrusted text through), the response is: first
*measure* how many call sites exist and how many share a common shape a single helper could cover; then close the
shared shape *centrally* with a helper that sanitizes unconditionally; only what is left after that goes into a
ledger, one entry per remaining call site, each with an inline justification comment. Wrapping every call site
by hand, one `sanitizeUntrustedI18nText(...)` at a time, is the fallback for the sites a helper cannot cover --
not the default first move.

Round 5 ("money-forgery hardening" follow-up) closed a second shape the round-4 detector could not see: an
already-constructed widget's `content` overwritten by plain ASSIGNMENT, `widget.content = dtoField.field`
(e.g. a TAN dialog's prompt text refreshed from a suspend response) -- same render-time resolution path as the
construction-time shape, but no call-with-parens for the round-4 regex to anchor on. `untrustedContent(widget,
text)` is the assignment-shape counterpart to `untrustedDiv`/etc., and `RAW_DOTTED_WIDGET_TEXT_ASSIGNMENT` /
`KNOWN_UNSANITIZED_WIDGET_TEXT_ASSIGNMENTS` is a second, independent detector + ledger in
`ClientUntrustedWidgetTextTripwireTest` for exactly that shape (currently **1**, see the round-6 correction below).
Four call sites were migrated onto the helper in round 5 and stay there: `BankAccountsScreen.kt`
(`outcome.bankPrompt` -- the actual finding that started this round), `AccountingExportScreen.kt`
(`disclaimer.text`, `requestedProvider.displayName`), `ConferenceScreen.kt` (`d.text`).

Round 5 also migrated a fifth call site, `EventsScreen.kt` (`result.message`), onto the same helper -- round 6
review found this was a mistake and reverted it (major finding, ledger back up to 1). `result.message` is always
constructed via `tr(...)`/`gettext(...)` in `EventFormValidation.kt`, so it already carries the `KV_I18N_MARKER`
prefix `untrustedContent` (via `sanitizeUntrustedI18nText`) strips as part of neutralizing a *forged* marker --
routing genuinely trusted i18n output through the same sanitizer strips its legitimate marker too and silently
breaks translation resolution (the raw German msgid renders for every non-German locale instead of the
translated message). `EventsScreen.kt`'s call site now assigns `result.message` directly again, with an inline
comment explaining why, and is a documented exception in the ledger test -- analogous to `ApiKeysScreen.kt`'s
`result.rawKey` exception in the construction-time ledger above.

While auditing that shape, round 5 also found and fixed (by hand, `sanitizeUntrustedI18nText(...)` inline -- see
below for why not centrally) a closely related but syntactically distinct THIRD shape: a bare `content = ...`
property assignment inside a builder lambda's own receiver scope (no `widgetVar.` prefix at all, since the
receiver is implicit `this`), used for legal disclaimer/terms/agreement full-text bodies:
`AuctionScreen.kt`/`PaymentGatewaySettingsScreen.kt`/`SepaSettingsScreen.kt`/`DunningSettingsScreen.kt`/
`BankAccountsScreen.kt` (`disclaimer.text`), `FriendRegistrationScreen.kt` (`terms.text`), `RegistrationScreen.kt`
(`agreement.text`).

=== Table cells are an i18n sink too (V1.9.17)

KVision's `Cell`, `HeaderCell` and `Row` are `Tag`s; `Tag.render` hands every content string to `Widget.translate`
-> `I18n.trans`, which resolves a leading `###KvI18nS###` (gettext) and a `###KvI18nP###...` payload (ngettext) by
itself -- so a raw cell value is replaced by catalog text (text spoofing; HTML stays text). `TableCellI18nMarkerDomTest`
proves this against KVision in a real browser. **Rule: text goes into a table cell only through `textCell(...)`,
`numCell(...)` or (inside a `DataColumn` lambda or a card) `cellText(...)`** (`DataScreenLayout.kt`). They share
one trust rule with `textColumn`: a `String` is always sanitised, `trusted(tr(...))` is used as it is. Report rows
sanitise foreign values where the row is built (`untrustedText` in `ReportRows.kt`). Tripwires T-R1..T-R5 in
`ClientUntrustedWidgetTextTripwireTest` enforce it (raw `cell(<text>)`, `Cell(...)`, a `dropDown` label that is a bare
variable, any Tabulator import, unsafe `span/div/p/.content =` inside a `DataColumn` block); there is no ignore list.
Tabulator is not used anywhere; its cell formatters are a separate sink and need their own review before first use.

== Wave W7 "Zeitstempel-Formatierung app-weit" (Teilwelle A, feature/v1.4.32-timestamp-formatting)

The temporal sibling of W6a/W6b: one shared date/time display convention (`DateTime.kt`), replacing the hand-rolled
`.padStart`-based formatting that had grown independently across several screens. Same structure as `Money.kt`'s
convention throughout -- five `format*`/`*In` functions, five live-translatable widget-content tokens, three
temporal table-column factories, and a `machineDate`/`machineDateTime` pair for the prefill/sort-key form.

=== Locale table

Four date-component orderings across the eight UI languages (no month names, no AM/PM, no zone):

[cols="1,2"]
|===
| Languages | Date order

| `de`, `pl`, `ru` | `DD.MM.YYYY` (dot), day+month ends with a trailing dot
| `en` | `YYYY-MM-DD` (ISO)
| `fr`, `es`, `it` | `DD/MM/YYYY` (slash)
| `nl` | `DD-MM-YYYY` (dash)
|===

`HH:MM` (and `HH:MM:SS` for a timestamp) renders identically in all eight -- there is no per-language time variant, so
`formatTimeComponents` deliberately carries no locale parameter (Review-Befund 2026-09-24 removed an earlier, dead one).
A date+time joins with `,` + NBSP (never a plain space) -- `formatDateTimeIn`/`formatTimestampIn`.

=== Display versus machine-readable, and the live language switch

Exactly `Money.kt`'s split. DISPLAY goes through one of the five `format*` functions or, as widget content, a token
(`dateToken`/`dayMonthToken`/`dateTimeToken`/`timestampToken`/`timeToken` -- tripwire T2 forbids concatenating one into
another string, mirrors M3). What prefills a field or is a sort key stays `machineDate`/`machineDateTime`, the canonical
ISO form. A table cell whose value is a `LocalDate`/`LocalDateTime` goes through `dateColumn`/`dateTimeColumn`/
`timestampColumn`, never a bare `textColumn { formatDate(...) }` (the same sanitisation-loss trap `Money.kt`'s own
`textColumn` KDoc documents).

== Searchable person select and list filter (V1.9.16)

A native `<select>` with hundreds of members is unusable, so every PERSON picker is a `SearchableSelect`
(`SearchableSelect.kt`) and every fully loaded list of people has a name filter (`ListFilter.kt`). Matching is shared
(`SearchFilter.kt`): case- and diacritic-insensitive ("muller" and "mueller" both find "Müller"), every word of the query
must occur in any order, word-start matches rank first, the query is never compiled into a regular expression.

=== SearchableSelect

* It IS a `Text` control (an ARIA combobox), so it goes through the normal form grammar: `searchableSelectField(...)` next
  to `textField`/`selectField`, or `Container.searchableSelect(...)` outside a form. Hint, error slot, `aria-required`,
  `aria-invalid`, blur validation, `LapisField.setValue/reset/subscribe` work unchanged.
* `value` is always the `id` of an entry that was really offered, never free text. Typing only searches; leaving the field
  (blur, Tab without arrowing to an entry, Esc Esc) restores the previous selection. A choice from the list raises a real
  bubbling `change` event, because `LapisField` and `crossFieldRule(watch = ...)` listen for it.
* Options are `(id, label)` pairs like KVision's `Select`. A pair with id `""` is the pinned "none" entry (shown only for an
  empty query, label resolved through `resolvedAttributeText`). All other labels are untrusted and are run through
  `sanitizeUntrustedI18nText` by the widget itself (idempotent: the `untrustedOptions(...)` wrapper at the call sites stays,
  it keeps `ClientUntrustedWidgetTextTripwireTest` honest). They are rendered only as plain widget text.
* At most 50 entries are rendered; the dropdown says how many more match. `listNote` adds a standing remark, e.g. when a
  server cap means only part of the people were loaded (CRM contacts on the open-items form).
* Keyboard: focus selects the text and does not open the list; click, Arrow Down/Up, Alt+Arrow Down or typing open it; the
  first match is active; arrows do not wrap; Enter picks; Esc closes, a second Esc restores (a third reaches the surrounding
  modal); Tab picks only an entry the user moved to with the arrows. The dropdown never takes focus (`mousedown` on list and
  buttons is swallowed), so a click on an entry is not a blur and cannot trigger a premature validation.
* Layout is pure CSS (`.lapis-ssel*` in `theme.css`, tokens only): dropdown and the two icon buttons live in a zero-height
  layer directly below the `<input>` (flex `order`), z-index 1060 above Bootstrap modals, opens upwards when there is less
  than 200 px below. No global listeners and no insert/destroy hooks (`ClientLateHookRatchetTest` is unaffected).

=== ListFilter

`listFilterField()` builds a labelled filter with a clear button and a live "3 von 12" count; the screen renders through
`filter.apply(items, nameOf = ...)` and re-renders from `filter.subscribe { ... }`. The filter owns the text, so it survives a
reload of the list. The roster keeps the screen's own order. **Only for lists that are loaded completely**: a filter over
a page-wise loaded list would "not find" people on later pages -- those need a server-side search.

=== Enforcement and exceptions

`ClientPersonSelectTripwireTest` fails on a plain `select(`/`selectField(` built from person-name fields (heuristic, recall
limits stated in its KDoc). Its ledger lists the deliberate exceptions and may only shrink. `R24B_REMAINING_MAX` dropped from 77
to 69 because eight person selects left the scanner's view (`searchableSelect(` is not matched by R24B's `SELECT_CALL`;
that blind spot is stated, not hidden).

Person lists WITHOUT a new client filter, with the reason: `CrmContactsScreen` and `OpenItemsScreen` (page-wise loading),
`MemberAdministrationScreen` (server-side search exists), `MemberFamiliesScreen.memberPicker` (server search, limit 20 -- a plain
select on purpose; only its missing sanitising was fixed), `SepaMandatesScreen`, `MemberHonorsScreen`, `DonorsScreen`,
`MemberAnniversariesScreen`, `ChapterRosterScreen`, `EventCheckInScreen` (already have a search field).

=== W7 (V1.9.1): DocumentsScreen's folder list migrated from a button row to `dataTable`

The folder list (`DocumentsScreen.kt`) was a plain button row (`"${folder.name} (${folder.documentCount})"`),

every other reversible-setting-change dialog in this codebase. Both new `selectField` calls sit
inside that modal's `lapisForm`, so neither adds to R24B's "outside the strict set" count (the file
was already fully migrated); no ratchet number changed.

=== i18n-Restschuld (V1.9.3): plural-catalog support + `#:` reference regeneration

Closed the two follow-up gaps deliberately left open by commit d906e0b ("remove 28 orphaned msgids"),
both previously listed under "Known gaps" above, across two rounds on branch
`feature/i18n-restschuld-plural-refs`.

**Round 4 (correctness readiness):**

* `I18nCatalogManager.ngettext()` used to select singular/plural with a bare `value == 1` binary --
  wrong for Polish and Russian's one/few/many grammar. It now reads a real plural catalog array
  (`catalog[msgid] = [msgstr[0], msgstr[1], ...]`, the exact shape `gettext.js`'s own `po2json`
  wrapper produces for a `msgid`/`msgid_plural` `.po` entry) and indexes it with `pluralFormIndex()`
  (`PluralRules.kt`), a 1:1 transcription of the standard GNU gettext `Plural-Forms` expression for
  each of this app's eight UI languages. Falls back to the pre-existing binary whenever no plural
  array entry exists (untranslated key, plain-string entry, or German, which is never
  catalog-backed) -- never throws on a malformed catalog shape.
* A `Plural-Forms:` header was added to `messages.pot` and all seven `messages-<lang>.po` catalogs.
* `scripts/i18n/regenerate-source-refs.mjs` regenerated the `#:` source-reference comments of all
  eight catalogs from the current source tree -- about 400 stale W5-era references now point at
  real source locations. Verified empirically, not estimated: msgid/msgstr content is byte-for-byte
  identical before and after this script ran; only `#:` comments changed. Closes the "W5 audit
  round: `#:` source references ... point at wrong lines" gap above. Covered by
  `scripts/i18n/regenerate-source-refs.test.mjs` (12/12 green).
* This round intentionally added no application call site: this codebase's house style (audit fix
  M4) avoids grammatical plurals glued onto a template in favour of separate, fully translated
  sentences. `PluralRulesTest` + `I18nCatalogManagerPluralTest` covered all eight languages' category
  boundaries end-to-end, but with synthetic messages only -- no real call site exercised the new
  code path yet.

**Round 5 (first real adoption + review-fix):**

* The bug the whole effort exists for: `SepaBatchesScreen.kt` had three `gettext("%1 Positionen ...",
  count)` call sites that always used the German plural noun, even for `count == 1` -- "Lauf anlegen
  (1 Positionen, 10,00 €)", "1 Positionen konnten nicht gebucht werden.". All three are now
  `ngettext("%1 Position ...", "%1 Positionen ...", count, count, ...)`, and every one of the eight
  catalogs gained the matching `msgid`/`msgid_plural` block (a new German singular string, the
  existing plural string unchanged as `msgid_plural`, the existing translation reused as the
  highest-count form so only the new singular -- and, for pl/ru, an additional "few" form -- needed
  translating). A pre-existing DOM test (`FormSubmitBodyPart3FinanceDomTest`) had hard-coded the bug
  as its expectation (`startsWith("Lauf anlegen (1 Positionen")`) and was corrected in the same
  round -- the clearest evidence the bug was real and observable, not theoretical.
* **KVision publishes no top-level free function for the plural case** -- unlike `gettext()`
  (`io.kvision.i18n.gettext`, a real top-level function), there is no `io.kvision.i18n.ngettext` to
  import; only the `I18n` singleton's own `ngettext()` method exists, plus a `tr(...)`-style
  DEFERRED/marker-based `I18nManager.ntr(singularKey, pluralKey, value)` default method that takes
  NO substitution arguments at all (its `trans()` counterpart only ever reconstructs
  `ngettext(singular, plural, count, count)` from the marker) -- unusable here, since "Lauf anlegen
  (%1 Position, %2)" needs a second substituted value (the formatted amount) that a marker
  round-trip would silently drop. `I18nCatalogManager.kt` therefore gained its own small top-level
  `ngettext(singularKey, pluralKey, value, vararg args)`, an immediate-resolution wrapper around
  `I18n.ngettext(...)` mirroring KVision's own `gettext()` wrapper exactly -- this is what the three
  `SepaBatchesScreen.kt` call sites above actually call.
* New JVM-side safety net: `PluralMessagesCatalogTest` (`lapis-server`) + `parsePluralCatalog`
  (`CatalogSupport.kt`) -- `AllClientMessagesCatalogTest`'s existing scanner is blind to `ngettext(`
  call sites and to `msgid`/`msgid_plural` catalog blocks in both directions (see that test's own
  updated KDoc), so it gives these three entries no coverage at all. New Kotlin/JS tests in
  `I18nCatalogManagerPluralTest` exercise `I18nManager.ngettext()` with the three REAL
  msgid/msgid_plural pairs across all seven catalog languages (not just the synthetic pairs round 4
  added).
* `scripts/i18n/regenerate-source-refs.mjs`'s own comment claimed its matcher "would also pick up a
  literal first argument for `ntr(`/`ngettext(` too, if one ever appeared" -- empirically false (its
  negative lookbehind `(?<![A-Za-z0-9_])` blocks a match starting inside "n**tr(**"/"n**gettext(**",
  since the preceding "n" is a word character). The comment is corrected; the matcher itself is
  UNCHANGED this round (deliberately: extending it to cover two more call sites is a possible,
  separately scoped follow-up, not required for three sites) -- the three new `ngettext(...)` call
  sites in `SepaBatchesScreen.kt` therefore carry no `#:` reference, same as any other
  indirectly-reached msgid; no `#:` line is more honest than a wrong one.
* **Known, deliberate CLDR deviation kept as-is:** `PluralRules.kt`'s Polish/Russian handling uses
  the classic GNU gettext three-form (`one`/`few`/`many`) expression, not the newer CLDR category
  set -- this is the same expression already shipped in round 4 and reviewed then; round 5 did not
  revisit it, since the three new call sites are covered correctly by it (verified against the real
  `po2json` output for all eight catalogs, see the commit this section was added in).
* **Not done in this wave**: a grep for the same "naive plural, no `(en)` workaround" pattern found
  further candidates outside the required scope (`"%1 Einträge geladen"`, `"%1 Jahre Förderer"` /
  `"%1 Jahre Mitgliedschaft"`, `"%1 Stimmen abgegeben."`, `"%1 Antworten · %2 Boosts"`, `"%1 Tage ×
  %2"`) -- deliberately left for a future wave rather than expanding this one's scope past the three
  `SepaBatchesScreen.kt` sites the bug report named. Extending
  `scripts/i18n/regenerate-source-refs.mjs`'s matcher to also cover `ntr(`/`ngettext(` (closing the
  gap this round's comment fix only documents) remains a possible, separately scoped follow-up too.
