= UI/UX Guideline -- Foundation Building Blocks (W1)
:description: The shared table, state and token building blocks of the Lapis Cloud client UI/UX guideline, their rules and the tripwire that keeps migrated screens honest.
:toc:
:toc-placement: preamble
:icons: font

== Context

The client had grown one bespoke table per screen: different densities, no shared loading/error/empty
grammar, hard-coded hex colours in the conference code, no card layout on a phone and no way to sort. Wave V1.4.25
("W1 Foundation") introduces the shared building blocks and migrates three screens onto them
(`MemberAdministrationScreen`, `ContributionsScreen`, `OpenItemsScreen`). W2-W5 migrate the rest; until then a
tripwire test keeps the debt visible and stops it from growing.

It is a pure client wave: no RPC, DTO, table or migration.

== Principles

* One grammar per concept: one table density, one loading state, one error state, two empty texts.
* A state is not a toast. The toast that `guarded` shows is the notification; the state box stays and offers the way out.
* Colour is a token, never a literal. The one exception is a document colour on a canvas (whiteboard paper).
* Touch targets are at least 44 px under `pointer: coarse`; nothing relies on hover.
* Foreign data is text: cell content goes in as widget content, never as HTML.

== Decisions

[cols="1,3"]
|===
| Decision | Rule

| Table density
| `TableType.STRIPED`, `HOVER`, `SMALL` and `ResponsiveType.RESPONSIVE` together, always -- through `standardTable` or `dataTable`.

| Narrow viewports
| Below 768 px (`CARD_LIST_BREAKPOINT_PX`, media query `(max-width: 767.98px)`) a `dataTable` renders a card list. The only new breakpoint.

| Numbers
| Numeric columns are right-aligned with tabular figures (`.lapis-num`) on `th` and `td`. A date that identifies a row (the primary column) stays left.

| Sorting
| A native `button` in the `th`, `aria-sort` on exactly one column, tooltip = next action, `aria-label` = current state once sorted. The idle icon is `fa-sort` in `--lapis-muted`, never a dimmed opacity (WCAG 1.4.11).

| Load states
| Loading, error, empty, no-match, content. The error sentence is fixed (no exception text, no identifier).

| Motion
| One `prefers-reduced-motion: reduce` block, last in `theme.css`, listing every selector that has a `transition`.
|===

== Building blocks

=== `DataTableState.kt` (pure)

* `SortDirection`, `SortState(key, direction)`, `nextSortState(current, clicked, firstDirection, allowUnsorted)`
* `ariaSortValue`, `sortIconClass`, `sortButtonTexts` -- ARIA value, icon class, tooltip and accessible name
* `DataColumn<R>(title, numeric, primary, sortKey, cell)` -- exactly five fields; `textColumn` is a factory for plain text
* `cardLayout(columnCount, primaryFlags)` -- primary column (default: column 0) and detail columns; a second primary is rejected
* `DataViewState` and `resolveDataViewState(loaded, isEmpty, filterTerm)`

=== `DataScreenLayout.kt`

* `dataScreenRoot(spacing = 16)`; screen widths `DATA_SCREEN_MAX_WIDTH_PX` (1440), `NARROW_FORM_MAX_WIDTH_PX` (480),
  `READING_MAX_WIDTH_PX` (720), `DASHBOARD_MAX_WIDTH_PX` (640) -- the last three are declared, not yet applied
* `standardTable(headers: List<TableHeader>)` and `Row.numCell(...)` for hand-built tables

=== `DataTable.kt`

`dataTable(columns, rows, sort, onSort, sortOptions, actions, focusSortKey)` is stateless: rows and the current
sort come from the caller, which reloads and calls it again on `onSort`. Pass `focusSortKey` so the keyboard focus
returns to the header button that was pressed. The mode (table or cards) is decided synchronously at construction
and re-decided on media-query changes, but re-rendered only when it really flips; the listener is released with the
widget. Cell lambdas run again on every re-render -- keep no state in them.

=== `DataSection.kt`

`dataSection(emptyText, filterTerm, noMatchText, isEmpty, onSettled, load, render)` owns a load and returns a
handle with `reload()` (call it once for the first load). The widget-free `DataLoadController` holds the lifecycle
and a generation counter that drops superseded results. The loading text lives in a `role="status"` live region that is
mounted once (`dataStatusRegion`, `DataSectionViews`) -- only its text changes, because a live region created together
with its text is not announced. `dataErrorState(onRetry)` is also usable on its own -- `OpenItemsScreen` has its own
cursor paging and client filter and only uses the error state.

== Row heights

[cols="1,1"]
|===
| Situation | Target

| `pointer: fine`
| `table-sm` rows

| `pointer: coarse`, row without a button
| at most 48 px

| `pointer: coarse`, row with an icon button
| at most 52 px (a 44 px button in a `table-sm` cell cannot be smaller; the cell padding drops to 2 px, about 49 px)

| Card
| 12 px padding, hairline border, no zebra, no shadow
|===

The 44 px target size is never undercut.

== Tripwire and debt ledger

`ClientUiGuidelineTripwireTest` (module `lapis-server`, it reads the client sources as text) enforces:

[cols="1,3"]
|===
| Rule | Check

| R2 | no `width = N.px` with N of 600 or more (use `maxWidth`)
| R9 | no colour literal in client Kotlin: `#hex`, `rgb()`, `rgba()`, `hsl()`, `hsla()`, `0xRRGGBB` (baseline: the whiteboard paper constant and three semi-transparent overlay chips in `ConferenceScreen`)
| R11 | every colour token of ANY light `:root` block (hex, `rgb()`/`rgba()`/`hsl()`/`color-mix()`, colour keywords, `var()` aliases of colour tokens) exists in both dark blocks, no colour token exists only in a dark block, and the two dark blocks agree; non-colour tokens (fonts, widths) are exempt
| R14 | every `table(...)` call carries `STRIPED`, `HOVER` and `SMALL` (also a call broken before the dot: `panel` newline `.table(`)
| R15 | every `table(...)` call carries `ResponsiveType.RESPONSIVE`
| R39 | an icon-only `button("", icon = ...)` (also `button(text = "", icon = ...)`) carries `title` and `aria-label` in the same block; the one factory line in `DataScreenLayout.kt` that labels its button in the next statement is exempted by name, not the file
| R24 | (W4a, extended W4b) no labelled `text(`/`password(`/`textArea(` call (a call that carries `label =`) in the 22 screens and dialogs migrated to the form grammar or in the 5 screens that have no labelled field to migrate, and (positive check) a `lapisForm(` in each migrated file, closed by `buttons(` or `finish(`; the search/filter fields of W4b are named exceptions (fingerprint, reason "a filter is not a form"). A downward ratchet (`R24_REMAINING_MAX`, 228 after W4b) covers the labelled fields outside the strict set; its floor (150) only guards against a vacuous scan
| R24B | (W4b) the same for labelled `select(`/`checkBox(` calls -- a SECOND counter, R24 is not redefined. The strict set holds them only as named exceptions (filter, area/action selector, immediate switch, selection list); a downward ratchet (`R24B_REMAINING_MAX`, 131 after W4b) covers the rest. The factories in `FormGrammar.kt` are exempt
| R55 | no `width = N.px` in client Kotlin (a fixed column width on a row or header cell is the mark of a pseudo-table; `maxWidth`/`minWidth` are not matched). Ledgered per file: after W3 `AuctionScreen`, `CrowdfundingScreen` and `PoliticianScreen` remain as hand-built pseudo-tables (a remainder wave, W5 in this document) and `SocialNetworkScreen` as one genuine form field (W4) -- they are not "form screens"
| C7c | no `reportTable(` call carries sort wiring (`onSort`, `sort =`, `sortOptions`, `sortKey`, `focusSortKey`); a text check of the call's own arguments, so a sort control added by a later statement is not seen -- the runtime side is `ReportTableDomTest`
| R54 | every selector with a `transition` is in the single `prefers-reduced-motion` block, nothing else is, and no transition is longer than 200 ms
|===

Rules R2, R9, R14, R15, R39 and R55 have a debt ledger with **one fingerprint per finding**: rule, file name, and the
trimmed source line of the offending spot (no line number; a line that starts with `.` is prefixed with the previous
code line). Compared as a multiset per file, so the test fails on a new finding, on a paid-off finding (delete its
ledger line) and -- unlike a plain count -- when one violation is fixed and another added in the same file. Editing a
ledgered line changes its fingerprint on purpose: re-list or pay the debt. Two findings with an identical line in one
file are indistinguishable (their number is still pinned). Files not in the ledger are held strictly -- that includes
the three migrated screens and the new building blocks. Every rule has a self-test with a bad and a good example.

`UiFoundationI18nCatalogTest` (W1), `HotTableI18nCatalogTest` (W2) and `PseudoTableI18nCatalogTest` (W3) guard the new strings: present in the template and all seven catalogs, translated,
with the `%N` placeholders intact. Each scans its own helper files completely and the migrated screens only through an
explicit list of the sentences that wave added -- the rest of those files is NOT covered (see Known gaps), because
they carry pre-existing debt that would fail the test for somebody else's reason.

preview, items, returns), `SepaMandatesScreen`, `PaymentTransactionsScreen`, `DunningCasesScreen` (cases, notices),

=== Decisions this wave had to make

[cols="1,3"]
|===
| Question | Decision

| Where do sort headers belong?
| Only on a list that is loaded COMPLETELY (chart of accounts, journal page). There the sort is a pure function
  (`sortLedgerAccounts`, `sortJournalEntries`) over the loaded rows. A cursor or offset list gets none: the server
  has no sort parameter, so re-ordering the loaded subset would contradict the order of the next page.

| Account numbers: number or text?
| Text. `0400` and `400` are two different accounts; a numeric comparison collapses them and fails outright on a
  non-numeric number. Secondary key is always the account number, so equal values keep a stable order.

| A search field over a partially loaded list?
| Yes, but never silently. `dataCountText(..., filtered = true, hasMore = true)` states that filters and search
  reach only the loaded rows, and `loadedSubsetNoMatchText` offers loading more as the way out. A bare "0 of 40"
  over a partial list is a false statement about the data.

| Which counter form?
| One function, three forms: filtered -> "shown of loaded"; unfiltered with a known total -> "loaded of total";
  unfiltered cursor list -> "N loaded" (+ "more on the server"). A cursor list never prints "12 of 12" -- it does
  not know a total.

| Does a phone get a card list inside a modal too?
| Yes. The member table of the family dialog used to run out of the dialog sideways; the breakpoint is a property
  of `dataTable`, not of the screen.

| The "default account" star glyph?
| Replaced by a `typeBadge` reading "Standard". A lone glyph is one channel, and a screen reader read nothing
  there. "Default" is a fixed category, not a lifecycle, so `typeBadge` is the right one of the three badges.

| Deleting a bank account had no confirmation.
| Added, as a direct consequence of this wave: an unlabelled bin icon between two other icons is far easier to hit
  by accident than a button reading "Löschen" (P6/R30).
|===

== Wave W3 "Pseudo tables" (V1.4.27)

Nine screens migrated for the first time and two revisited: `FinancialReportsScreen` (GuV, Bilanz,
Jahresabschluss), `NonprofitComplianceReportsScreen` (four spheres, use of funds, USt preview), `CostCentersScreen`

=== Two table grammars, one criterion

[cols="1,3"]
|===
| Grammar | Use it when

| `dataTable` (list)
| A row stands on its own: a member, a cost centre, a document, an audit entry. Sortable when the list is loaded
  completely, card list below 768 px.

| `reportTable` (document)
| A row is only right in the context of its neighbours: a running balance, a number sequence, a total underneath.
  A real `<table>` in the responsive frame with a `<caption>`; section (a spanning `th`, no `scope`), sum and balance
  rows (their label is a `th scope="row"`); **no** sort buttons and **no** card list -- a card list renders only
  `rows`, so a sum row would silently vanish on a phone. Below 768 px it scrolls sideways.

| Both on one screen
| Allowed, and not a second grammar for one object: `CostCentersScreen` shows the cost centres as a LIST (`dataTable`,
  each row stands alone: edit, deactivate) and, below, a cost-centre REPORT (`reportTable`, rows only make sense with
  the total underneath). The criterion is per object and per purpose, not per screen. What is NOT allowed is the same
  object in both grammars -- the posting lines of a journal entry are a `reportTable` in the journal detail, in the
  posting confirmation and in the audit log's snapshot.

| Cards (`.lapis-card-list` / `.lapis-data-card`)
| A row needs a free-text field or carries a decision with a reason (the three approval queues). Never a second
  grammar for the same object (P3).
|===

=== Decisions this wave had to make

[cols="1,3"]
|===
| Question | Decision

| Where do the figures come from?
| `ReportRows.kt`, once per report, pure and widget-free. The renderer only paints `ReportRow`s. `ReportGoldenTest`
  pins every cell string (blank cells and the row kind included); `ReportCellOracleDomTest` proves them against the
  DOM -- first the old `hPanel` renderers, then strictly the new tables. A golden value is never generated from the
  new code.

| Sum row versus Bootstrap's zebra
| The zebra is `--bs-table-bg-type` plus an inset shadow (5 % of the emphasis colour over the cell colour), and its
  selector has specificity (0,2,2). The report classes use `.table > tbody > tr.lapis-total-row > td` (0,2,3), set
  `--bs-table-bg-type` to the same opaque value as the background and win without `!important`. The surface is its
  own token, `--lapis-total-surface` (light #DBE0E8, dark #232933), NOT `--lapis-surface-sunken`: in the light theme
  the zebra is sunken plus 5 % black (#EBECEF), so a sum row in plain sunken (#F6F7F9) was LIGHTER than a zebra row.
  The top rule is `--lapis-muted` (at least 3:1 against both neighbours, WCAG 1.4.11), and warn-red amounts on
  these rows read `--lapis-total-danger-rgb` (at least 4.5:1). Report tables use `border-collapse: separate`: with
  collapsed borders the 1-px rule of a balance row loses against the 1-px bottom line of the row above and never
  shows. `ReportRowStyleDomTest` loads the real Bootstrap and `theme.css` into Karma and compares the VISIBLE
  background (colour plus shadow layer) of a sum row with a zebra row and a plain row, in both themes, and checks
  the contrast numbers.

| Where does the caption stand?
| Bootstrap's reboot sets `caption-side: bottom`; its own utility `caption-top` on the table fixes it without new CSS.

| Section headings and row headers
| A section heading is a spanning `th colspan` WITHOUT a `scope`: the report has ONE `<tbody>` (KVision's `Table` has
  no per-section body), and a `scope="rowgroup"` would let "Aktiva" claim the "Passiva" rows below it too. The label
  of a sum or balance row is a `th scope="row"` (the first text cell, also behind the blank cells of a ledger row);
  the column headers are `th scope="col"`.

| A caption that repeats the heading above
| The caption is the table's accessible name, so it stays; a caption that only repeats the heading or the account
  header right above the table is hidden visually (`reportTable(captionVisible = false)`, the `theme.css` rule
  `.lapis-report-caption-hidden` is Bootstrap's `visually-hidden` recipe). Inside a Jahresabschluss the embedded GuV
  and Bilanz keep their visible captions -- there they are the only heading.

| Do the toggle labels follow a language switch?
| No, by a known limit: the `aria-label` of every icon button (`expandToggleButton`, every `tableActionButton`) and the
  `title` of the expand toggle are resolved once, when the button is built (a `title` set from a `tr(...)` string does
  follow a switch). Attributes go around KVision's patch cycle, so a switch re-renders the
  `tr(...)` texts of an open report (captions, headers, row labels, sum labels) but not these two attributes; they
  catch up when the report is loaded again. The same is true for badge labels and the period lines ("Zeitraum: ...").

| How is a detail row collapsed?
| With `d-none`, not KVision's `hide()`: a hidden KVision widget leaves the DOM, and `aria-controls` must name an
  element that exists.

| Should the audit log sort?
| No. It is keyset-paginated (`beforeSequenceNumber`) and the server has no sort parameter -- re-ordering the loaded
  pages would contradict the next page. The list is a `dataTable` over all pages loaded so far, without `onSort`.

| The "Summe %1" label
| `trFormat(tr("Summe %1"), title)`: a composed `tr` string that keeps the marker prefix (the widget re-resolves it on
  every render) and whose title argument `I18nCatalogManager` resolves per language. It used to be
  `gettext("Summe %1", title)`, which resolved once and left the title's marker in the text ("Summe
  ###KvI18nS###Einnahmen") -- a defect of the old renderers that the first version of the wave preserved on purpose
  and the audit round fixed. `TrFormatTest` and `ReportLanguageSwitchDomTest` pin it.
|===

== Wave W4a "Form grammar, part 1" (V1.4.28)

The first half of the form roll-out: the building blocks (`FormGrammar.kt`, `FormRules.kt`) and the screens where a
form decides whether a person can get in or can safely change something -- login, the three registration and
password-reset screens, the admin password reset, the SEPA, dunning and receivable-dunning settings, the stream
destinations, the restore and the API-key issue form. A pure client wave: no RPC, DTO, table or migration was touched
and **every validation RULE is unchanged** (`Validation.PASSWORD_MIN_LENGTH`, 12..128, e-mail 320, the 1..30 prenotification
days, the dunning bounds, 3..1000 for a reason) -- **with two corrections made in review of this wave**: (1) the login
screen and its "request reset" form carry no e-mail format rule at all any more (only "not empty"), because accounts
whose identifier has no dot after the `@` (`admin@localhost`, `hans@intranet`) exist and must stay able to sign in; the
format rules stay on the screens that CREATE an identifier (registration, friend registration); (2) the dunning fee
field (`DunningSettingsScreen`) now uses the same amount parser as the receivable-dunning form: "12,999" and "1e1" are
rejected (before, "12,999" was silently rounded to 13,00), "2,50" is accepted, and "0" stays valid here -- what the field
approves is exactly what is saved. Do not revert (2) as a regression. Otherwise the rules only became visible earlier and
at the field. The server stays the authority. W4b (members, committees, meetings, motions, events, communication, CRM, DSGVO) and W4c (the
finance forms) reuse the same building blocks.

=== The grammar

[cols="1,3"]
|===
| Part | Rule

| Required fields
| Marked ONCE per form, in one of three ways (decided in `LapisForm.buttons`, where the field set is complete): (a) mixed
  (at least one required AND one optional field) -- a `*` on every required label plus the legend "* Pflichtfeld" above
  the first field; (b) three or more fields, all required -- no stars, the legend "Alle Felder sind Pflichtfelder.";
  (c) exactly two fields, both required -- neither stars nor a legend. **A single required field is NOT case (c)** (V1.4.29
  audit): it is marked like (a), a star plus the legend, because a lone required field without any marking is not
  recognisable as required. Several forms in ONE dialog (the member editor has six) share a `LegendGroup`: the same legend
  stands once, over the first form that needs it; the stars stay on every required label. `aria-required` is on the input in
  ALL three cases.
  The star is `aria-hidden` and NOT red: an empty required field in a fresh form is not an error.

| Errors
| At the field: an `invalid-feedback` slot that is mounted permanently and linked with `aria-describedby` (hint first,
  then the error). An error changes only the slot's `content` and a class -- never the structure. **That is about
  assistive technology (a live region announces a text CHANGE), not about layout:** a visible error is a
  `display: block` and DOES push everything below it down, including the submit button. The click is saved by the
  pointer gate instead (next row).

| The pointer gate (why the first click is not lost)
| `blur` fires on the mousedown of a button. If the error appeared then, the button would slide down between mousedown and
  mouseup, the mouseup would land on another element and the browser would fire no `click`. So while the mouse button is
  pressed on a button (`button`, `.btn`, `role=button`) the blur check is DEFERRED and made up after the mouseup (and its
  click). There is exactly ONE pair of `document` observers for the whole application (`PointerGate`), never one per form: a
  hidden KVision modal stays in the DOM, so per-form observers would never be released. Because that gate is global and never
  torn down it must not get stuck: a `mouseup` that never arrives (released outside the window, Alt-Tab, a context menu, a
  cancelled pointer gesture, a drag) would otherwise defer every later blur check of the application. The window `blur`,
  `pointercancel`, `contextmenu`, `dragend`, the pointer leaving the window and a 5 s time limit therefore release the gate
  and run the deferred checks. Chosen over a reserved error height because a message wraps differently per language and width -- a fixed height guarantees no
  stability and leaves a gap between every pair of fields. The keyboard (Tab) is not affected: there is no mouseup to miss.
  `FormGrammarAuditDomTest.theFirstClickOnAButton_afterLeavingAnInvalidField_isNotLost` asserts the button position and
  the element under the mousedown point at mouseup time (a synthetic `.click()` cannot show the defect).

| When is a field checked?
| On leaving it, but ONLY when it was touched (typed into) or the form was submitted once -- a field that was merely
  tabbed through stays silent. Typing clears an existing error and never creates a new one. No `keyup` validation, no
  debounce.

| Submit
| Validates everything. On errors: focus on the FIRST invalid field, scroll it into the middle (no animation), one
  collective message "Bitte korrigieren Sie diese Felder: ..." in a `role="alert"` region that is mounted (empty) when
  the form is built -- assistive technology announces a text CHANGE in an existing live region, not a region inserted
  with its text -- and NO server call. A form with exactly ONE field and no cross rule shows no collective sentence (it
  would repeat the field error). The collective sentence clears itself as soon as every field is valid again (a server
  text is not cleared by typing). Otherwise `runGuardedAction` with `aria-busy` on the button: no spinner, no text
  change. Server errors use the same region (`showFormError`; it fails loudly if called before `buttons()`/`finish()` has
  mounted the region). `LapisForm.validateAndReport()` is the checking half of `submit` for forms whose submit needs a
  confirmation first (the restore); `LapisForm.runBusy()` is the `aria-busy` half.

| Button order
| Cancel left, the confirming action right (guideline 2.5 / R27). The task text asked for "primary action left"; the
  guideline and every modal of this code base already do it the other way round, so the code follows the guideline.
  Exactly one `PRIMARY` per form (R28, by eye -- it cannot be checked textually per form). A destructive action stands
  in its own zone BELOW the button row, separated by a hairline (`lapis-form-danger-zone`) -- in a view with 14 px
  spacing a 16 px gap is no signal.

| Programmatic writes
| A value that code (not the person) puts into a field -- a preset from a dropdown, "Neu erzeugen", clearing and locking
  a field -- goes through `LapisField.setValue`, never through the raw control (`Input.value = ...`, `field.control as
  Text`): a control write raises no `input` event, so a field error that was already showing would stay. Directly after
  `setValue` call `validate(force = false)` (the new value may be valid or invalid; an untouched field stays silent) or,
  when the field is emptied and disabled in the same step, `clearError()`. Only where no error can be showing yet (the
  first load of saved settings) may the follow-up call be left out. Since W4b this also holds for a `Select` (`setValue` takes
  one; the options of a select that is filled after an RPC are set on the control first, then the value through the field) and
  for a reset of a `checkField`. This class of defect appeared three times in W4a
  (`MemberPasswordResetDialog` regenerate, `DunningSettingsScreen.updateFeeLock`,
  `ConferenceStreamDestinationsScreen.applyPlatformDefaults`); `ProgrammaticFieldWriteDomTest` and
  `SecretFieldDomTest` pin the three paths. There is no textual tripwire for it (a `.control as` cast is also a
  legitimate read), so W4b/W4c screens must follow this row by review. `setValue` on a control that is not a text
  control (a `select` registered with `register`) fails loudly instead of doing nothing; `reset()` also empties an
  upload.

| No "valid" state
| No `is-valid`, no green tick.
|===

=== Decisions this wave had to make

[cols="1,3"]
|===
| Question | Decision

| Where does the star go?
| `Tag.render()` renders the CHILDREN before the `content` text. A `span(" *")` next to the label content would stand
  BEFORE the label text ("* E-Mail"). So the label text itself becomes the first child and the star the second
  (`FormGrammarDomTest.mixedForm_putsTheStarAfterTheLabelText` pins `"E-Mail *"`).

| Which attributes, and how?
| Only through KVision's `Widget.setAttribute` (it lives in the attribute map and survives a re-render AND a language
  switch), never through a raw `getElement()?.setAttribute` (lost when a language switch rebuilds the root), and never
  through an insert hook (`ClientLateHookRatchetTest` counts them). `EmbedIntegrationScreen` had one raw call for
  `readonly`; it is the typed `readonly` property now.

| The login password
| Checked for "not empty" ONLY, never against the password policy: a password that was valid when it was set must never be
  declared wrong by the interface. The general rule behind it: **a check that could make a false statement about the
  state of the system does not happen.** The server text is shown word for word -- it is hardened against account
  enumeration, so the client adds no differentiation (no separate "unknown e-mail"). The same rule removed the e-mail
  format check from the login identifier and the "request reset" form (review correction): an identifier without a dot
  in the domain is a legal account name and the client must not lock it out.

| Password rules
| The length rule stands as a hint UNDER the field (visible before typing) and as the identical error text; it left the
  label ("Passwort (mind. 12 Zeichen)" became "Passwort" plus hint). Constants are `%1`/`%2` placeholders, never part of a
  msgid.

| Secrets that are not the editor's own
| The stream key and the temporary password generated for ANOTHER person: `autocomplete="off"` plus
  `data-1p-ignore`, `data-lpignore`, `data-form-type="other"`, `spellcheck="false"`, `autocapitalize="off"`. Honest
  limit: browsers may ignore `autocomplete="off"` on password fields and the `data-*` attributes are a request to the
  password managers, not a guarantee. The temporary password has a reveal toggle (`aria-pressed`, `title` and
  `aria-label` in the same call, the name changes between "Passwort anzeigen" and "Passwort verbergen"); the value
  never appears in an attribute, a title or an error message (`SecretFieldDomTest`).

| Consent checkboxes

=== Two more factories and one parameter

`selectField` and `checkField` are members of `LapisForm` (they need its private wiring) -- **and nothing else is added: no
date or time factory** (K1). `selectField` puts hint and error slot BESIDE the `<select>`, never inside it (`Select.add()`
delegates to the `<select>`). `checkField` treats "required" as "ticked": KVision's `CheckBox.getValueAsString()` is the
string `"false"`, never empty, so the empty-value path of `LapisField` would make `required` silently useless. Three
corrections to existing behaviour came with them, each pinned by a DOM test: `LapisField.setValue` takes a `Select` (the
options of most W4b selects arrive asynchronously, and a `checkField` resets to unchecked); the listener of a select or a
checkbox sits on `control.input` (a `blur` does not bubble to the wrapper, so blur validation of a choice field never ran);
and every field factory takes `host: Container = panel` for the eight fields that sit in a horizontal row (inline rename,
the door's code row, the attendance status beside the name) -- `host` must be a descendant of `form.panel`.

=== Dependable double-click protection (R29)

Before W4a/W4b only `ReceivableDunningSettingsScreen` of the 22 files used `runGuardedAction` (three call sites), none used

audit corrected:

* **The dialogs.** `confirmWithReasonDialog` had no protection (its `onConfirm` is a plain callback, and the modal's button stays

* **The guard itself is tested.** `runGuardedAction` returns while the button is disabled (the DOM attribute lags one render
  behind the widget, so two fast clicks got through). `FormAuditFixesDomTest.submit_aDoubleClick_*` clicks twice at once and once

* **A ratchet (tripwire R29).** A plain `AppScope.launch { ... rpcService<S>().write(...) }` in a migrated file, outside a
  `runBusy`/`submit`/`runGuardedAction` block, is counted (39 today; only ever lowered). It is honest about its limits: writes are
  told from reads by the method NAME, a hand-written guard is not seen, idempotency is not judged -- the 39 are a baseline of

=== The posting lines

== Rule precedence: attributes and `gettext`

The guideline (section 2.14) says `tr()` only as widget content and, for attributes (`title`, `aria-label`,
`placeholder`), string templates, concatenations and as an argument of `gettext()`, always `gettext()`; it also calls a
`gettext()` without an argument a convention break. Where the two collide -- an attribute that needs a plain word, e.g.
`title = gettext("Speichern")` -- **the attribute rule wins**: `gettext()` is correct there, `tr()` would leak
KVision's `###KvI18nS###` marker into the DOM. `ClientTrAttributeLeakTest` sees only the direct case; helpers that
receive a `tr()` string and set an attribute (`tableActionTooltip`, `segmentedControl`, `sortButtonTexts`) resolve it
through `resolvedAttributeText` (marker stripped AND translated).
