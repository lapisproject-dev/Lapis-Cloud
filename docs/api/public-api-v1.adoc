== Overview

`/api/v1` is a read-only REST API for external, machine-to-machine consumption of a Lapis Cloud
organization's public governance data — independent of the Kilua-RPC layer `lapis-client` uses
internally. It is served by the same Ktor process as the rest of this application, registered
before the SPA's own static-file fallback (see `network.lapis.cloud.server.routes.PublicApiRoutes`).

Every endpoint is `GET`. There is no write endpoint on this surface — see <<scope>>.

== Authentication

Every request must carry:

----
Authorization: Bearer lapis_<key>
----

The key is issued by a BOARD or ADMIN member under *Verwaltung → API-Schlüssel* in the web UI (or
via the `IApiKeyService` RPC interface). It is a long-lived credential, structurally distinct from
this server's session cookies/tokens: both travel as `Authorization: Bearer <token>`, but a session
token and an API key are code-enforced to never resolve as each other, regardless of their content —
see `network.lapis.cloud.server.security.ApiKeyAuth`/`RequestContext.extractSessionToken`. A session
cookie alone, without this header, never authenticates this API.

The raw key is shown to the operator **exactly once**, at issuance/re-issuance time. It cannot be
retrieved again afterwards — only a SHA-256 hash of it is ever stored. If a key is lost, issue a new
one ("Neu ausstellen" in the UI, `reissueApiKey` over RPC) — this revokes the old key and mints a
replacement with the same label and expiry in one atomic step.

=== Error responses

Every error response (auth, rate limit, not found, bad request) is a flat JSON object:

[source,json]
----
{ "error": "<code>", "message": "<human-readable text>" }
----

[cols="1,1,3", options="header"]
|===
| HTTP status | `error` | Meaning

| 401
| `unauthorized`
| Missing/malformed `Authorization` header, wrong prefix, or an unknown key. `WWW-Authenticate` is
  always present on a 401.

| 401
| `key_revoked`
| The key's hash matched a row, and that row is revoked.

| 401
| `key_expired`
| The key's hash matched a row, and that row's expiry has passed.

| 429
| `rate_limited`
| Rate limit exceeded — see <<rate-limits>>. `Retry-After` names the actual remaining seconds in the
  current window, never a fixed placeholder value.

| 404
| `not_found`
| A well-formed path parameter (e.g. a meeting id) that does not resolve to an existing record.

| 400
| `bad_request`
| A malformed path parameter, or a `?status=` value outside the documented whitelist for that
  endpoint.
|===

`unauthorized` deliberately does not distinguish "no header at all" from "a syntactically valid but
completely unknown key" — both carry identical risk of enabling enumeration, so both collapse into
the same response. `key_revoked`/`key_expired` are only ever returned once a key's hash has actually
matched an existing row — the caller already possesses that key at that point, so naming the reason
does not itself leak anything a determined caller couldn't already infer.

Every response, success or error, carries `Cache-Control: no-store` and `Vary: Authorization`.

[[rate-limits]]
== Rate limits

Two independent limits apply, in this order:

1. **Pre-authentication, per IP address** — checked before the `Authorization` header is even
   parsed. Bounds anonymous request volume regardless of whether a caller has a key at all.
2. **Post-authentication, per API key** — checked after a key resolves successfully. Bounds a single
   integration's volume independently of every other caller's IP or key.

A `429` from either limit carries a `Retry-After` header with the actual remaining seconds in that
limiter's current window.

== Pagination

Every list endpoint accepts `?limit=` and `?offset=`. Neither is ever rejected — both are silently
clamped:

* `limit` — missing, non-numeric, or `<= 0` defaults to 25; anything above 100 is clamped down to
  100.
* `offset` — missing, non-numeric, or negative defaults to 0.

Every page response has the shape:

[source,json]
----
{ "items": [ ... ], "totalCount": <int>, "limit": <int>, "offset": <int> }
----

`totalCount` is the total number of matching records (before pagination), not the count of `items`
in this page.

== Endpoints

=== `GET /api/v1/members`

**Returns `id` and `displayName` only — permanently, by design, for DSGVO Datenminimierung.** No
e-mail address, postal address, membership status, role, or any other field is ever exposed here,
and this is not planned to change: an external caller has no legitimate need for a member's contact
or status data through this read-only surface, and the shape below is the API's documented contract,
not an incomplete first cut.

Only members whose status is `ACTIVE` are included.

[source,json]
----
{
  "items": [ { "id": "<uuid>", "displayName": "..." } ],
  "totalCount": 42, "limit": 25, "offset": 0
}
----

=== `GET /api/v1/members/{id}`

Returns a single member object (same two-field shape as one `items` entry above), or
`404 not_found` -- for BOTH an unknown id AND a well-formed id belonging to a member whose status is
NOT `ACTIVE`. These two cases are deliberately indistinguishable: a caller holding a member's UUID
must not be able to learn, by comparing a `404` against a `200`, whether that member is
`WITHDRAWN`/`APPLICATION`/`FRIEND`/`DECEASED` -- the SAME hard `ACTIVE`-only filter the list endpoint
above already applies, applied here too rather than relaxed "because it's just one record".

A syntactically malformed `{id}` (not a UUID) is `400 bad_request`, not `404` -- a parse failure is a
caller error, not an existence question.

=== `GET /api/v1/committees`

Query parameters: `?activeOnly=` (`true`/`false`, default `true`).

[source,json]
----
{
  "items": [
    {
      "id": "<uuid>", "name": "...", "type": "WORKING_GROUP", "description": "...",
      "active": true, "quorumPercent": 50
    }
  ],
  "totalCount": 1, "limit": 25, "offset": 0
}
----

`type` is one of `EXECUTIVE_BOARD`, `WORKING_GROUP`, `COMMISSION`, `OTHER`, `GENERAL_ASSEMBLY`.

=== `GET /api/v1/committees/{id}`

Returns a single committee object, or `404 not_found` (unknown or malformed-then-400, see
`/members/{id}` above for the general 400-vs-404 rule). Unlike `/members/{id}`, this endpoint applies
**no** status filter at all -- an inactive committee is already reachable through the list endpoint
above via `?activeOnly=false`, so a single-resource lookup applying no filter here is not a status
oracle the way it would be for `/members/{id}`/`/motions/{id}`.

=== `GET /api/v1/meetings`

Query parameters: `?committeeId=<uuid>`, `?status=` (one of `PLANNED`, `HELD`, `CANCELLED`).

[source,json]
----
{
  "items": [
    {
      "id": "<uuid>", "committeeId": "<uuid>", "committeeName": "...", "title": "...",
      "scheduledAt": "2026-03-01T18:00:00", "location": "Online", "format": "ONLINE",
      "status": "PLANNED"
    }
  ],
  "totalCount": 1, "limit": 25, "offset": 0
}
----

`format` is one of `IN_PERSON`, `ONLINE`, `HYBRID`.

=== `GET /api/v1/meetings/{id}`

Returns a single meeting object (same shape as one `items` entry above), or `404 not_found`.

=== `GET /api/v1/resolutions`

Query parameters: `?committeeId=<uuid>`, `?meetingId=<uuid>`.

[source,json]
----
{
  "items": [
    {
      "id": "<uuid>", "meetingId": "<uuid>", "number": "WORKING_GROUP-2026-01",
      "title": "...", "text": "...", "status": "ADOPTED", "resolutionMode": "COMMITTEE_QUORUM",
      "decidedAt": "2026-03-01T19:00:00",
      "votesYes": 5, "votesNo": 1, "votesAbstain": 0, "quorumMet": true
    }
  ],
  "totalCount": 1, "limit": 25, "offset": 0
}
----

`status` is one of `ADOPTED`, `REJECTED`, `POSTPONED`. `resolutionMode` is one of
`COMMITTEE_QUORUM`, `MERITOCRATIC`, `DEMOCRATIC`, `SYSTEMIC_CONSENSUS`.

=== `GET /api/v1/resolutions/{id}`

Returns a single resolution object, or `404 not_found` (unknown or malformed-then-400). No status
filter -- same as the list endpoint above, which shows every resolution unconditionally.

=== `GET /api/v1/motions`

Query parameters: `?targetCommitteeId=<uuid>`, `?status=` (see below).

**`status` is restricted to a fixed whitelist — `SCHEDULED`, `RESOLVED`, `REJECTED`, `POSTPONED`.**
These are the only statuses this endpoint will ever return, whether or not `?status=` is given: with
no filter, results are still limited to this set (internal workflow statuses like `SUBMITTED`,
`REVIEWED`, `REJECTED_PRELIMINARY`, `WITHDRAWN` never appear); passing a `?status=` value outside
this whitelist is `400 bad_request`, not a silently empty result.

[source,json]
----
{
  "items": [
    {
      "id": "<uuid>", "targetCommitteeId": "<uuid>", "targetCommitteeName": "...",
      "targetCommitteeType": "WORKING_GROUP", "title": "...", "text": "...",
      "status": "SCHEDULED", "submittedAt": "2026-01-01T00:00:00",
      "meetingId": "<uuid>", "resolutionId": null, "amendsMotionId": null
    }
  ],
  "totalCount": 1, "limit": 25, "offset": 0
}
----

=== `GET /api/v1/motions/{id}`

Returns a single motion object, or `404 not_found` -- for BOTH an unknown id AND a well-formed id
whose current status is outside the SAME fixed whitelist (`SCHEDULED`, `RESOLVED`, `REJECTED`,
`POSTPONED`) the list endpoint above enforces. Same reasoning as `/members/{id}`: an internal-only
status (`SUBMITTED`, `REVIEWED`, `REJECTED_PRELIMINARY`, `WITHDRAWN`) must stay structurally
unreachable through this endpoint too, not merely absent by default -- comparing a `404` against a
`200` must never let a caller learn which internal status a motion is actually in.

[[webhooks]]
== Webhooks (outbound) — V1.3.2

In addition to the pull-based `/api/v1` surface above, a Lapis Cloud organization can configure ONE
outbound webhook per API key: an HTTP `POST` this server sends automatically whenever one of a fixed
set of events happens, so an integration does not need to poll `/api/v1` on a schedule to notice new
governance/membership/payment activity.

Configured under **Verwaltung → API-Schlüssel** in the web UI, or via the `IWebhookService` RPC
interface (`setWebhookUrl`/`removeWebhookUrl`/`rotateWebhookSecret`/`reactivateWebhookEndpoint`/
`sendWebhookTestEvent`/`listWebhookDeliveries`) — there is no `/api/v1` REST surface for webhook
*configuration* itself, only for the events it announces.

=== Request shape

Every delivery is an HTTP `POST` with a JSON body and these headers:

[source]
----
Lapis-Signature:        t=<unix-seconds>,v1=<hex-hmac-sha256>
Lapis-Webhook-Id:       <uuid>              (stable across every retry attempt of the SAME delivery)
Lapis-Webhook-Event:    resolution.adopted
Lapis-Delivery-Attempt: 1
Content-Type:           application/json
User-Agent:             LapisCloud-Webhook/1
----

No other header is ever sent — in particular, no `Authorization` header and no cookie. **Redirects
are never followed** (`3xx` counts as a failed delivery attempt) — this is deliberately the single
most common integration mistake with any webhook consumer, so it is called out here explicitly:
point the configured URL directly at its final destination.

=== Verifying the signature

`Lapis-Signature`'s grammar is byte-for-byte the same as Stripe's own `Stripe-Signature` header:

[source]
----
t=<unix seconds>,v1=<lowercase hex HMAC-SHA256>
----

The signed material is `HMAC-SHA256(key = <your signing secret>, data = "<t>." + <raw request body
bytes>)`. Verify by recomputing that HMAC over the exact bytes you received (never a re-serialized
copy) and comparing it, in constant time, against the `v1` value. Reject the request if they don't
match, or if `t` is further in the past/future than your own freshness tolerance allows.

The signing secret (`whsec_lapis_…`) is shown to you **exactly once**, at configuration/rotation
time, the same "shown once, never retrievable again" discipline the API key itself already follows.
Rotating it (`rotateWebhookSecret`) invalidates the old secret immediately — there is no dual-secret
grace window.

=== Idempotency

`Lapis-Webhook-Id` is stable across every retry attempt of the SAME delivery (unlike the HTTP
request itself, which is a new connection each time) — use it as your idempotency key so a retried
delivery that you already processed once is safely ignored rather than double-applied.

=== Event catalogue

Every event's JSON body carries at least `id` (== `Lapis-Webhook-Id`), `eventType`, `entityId`, and
`occurredAt`:

[source,json]
----
{ "id": "<uuid>", "eventType": "resolution.adopted", "entityId": "<uuid>", "occurredAt": "2026-09-02T11:14:51.123456" }
----

For a **Thin** event (every event below except the two payment ones), that's the whole body — fetch
the current state of `entityId` from the corresponding `/api/v1` endpoint above if you need more than
the bare fact that something happened. For the two **Fat** (self-contained) payment events, the body
additionally carries `amount` (a decimal STRING, scale 2, e.g. `"42.00"` — never a JSON number),
`currency`, and `transactionId` — there is no `/api/v1/payments` endpoint to fetch further detail
from, so the payload is self-sufficient instead. Neither payment event ever carries `memberId`,
donor/payer identity, or any other personal data.

[cols="2,2,4", options="header"]
|===
| `eventType` | Fires from | Entity `/api/v1` endpoint

| `committee.created`
| A committee is created
| `GET /api/v1/committees/{id}`

| `committee.updated`
| A committee is edited
| `GET /api/v1/committees/{id}`

| `meeting.created`
| A meeting is scheduled
| `GET /api/v1/meetings/{id}`

| `meeting.held`
| A meeting's status transitions INTO `HELD` (never on a redundant re-confirmation)
| `GET /api/v1/meetings/{id}`

| `resolution.adopted`
| A resolution is recorded
| `GET /api/v1/resolutions/{id}`

| `motion.scheduled`
| A motion's status transitions to `SCHEDULED`
| `GET /api/v1/motions/{id}`

| `member.created`
| A member becomes `ACTIVE` (direct admin creation, or an approved application) — **never** for a
  self-registration landing in `APPLICATION`, which `/api/v1/members` never surfaces anyway
| `GET /api/v1/members/{id}`

| `contribution.paid`
| A contribution is marked paid (manual settlement, SEPA collection, or Stripe checkout) — **Fat**
  event, see above
| _(none — self-contained payload)_

| `donation.received`
| A donation is captured via Stripe checkout — **Fat** event, see above
| _(none — self-contained payload)_

| `webhook.test`
| `sendWebhookTestEvent` only — synchronous, one attempt, never queued/retried
| _(none — diagnostic only)_
|===

**Known limitation**: there is no "entity removed/left" event. A member leaving `ACTIVE` status (or
any other entity leaving the visible-through-`/api/v1` set) is not announced — a consumer that needs
to detect removals must periodically re-poll the corresponding `/api/v1` list endpoint and diff it
against its own local copy.

=== Retry policy

A failed attempt (any non-`2xx` response, a timeout, a connection/TLS/DNS failure, or a `3xx`
redirect) is retried up to 5 more times (6 attempts total), with this fixed backoff — no jitter:

[cols="1,2,2", options="header"]
|===
| Attempt | Wait before this attempt | Cumulative

| 1 | — (immediate)| 0:00
| 2 | 30 s | 0:00:30
| 3 | 2 min | 0:02:30
| 4 | 10 min | 0:12:30
| 5 | 45 min | 0:57:30
| 6 | 3 h | 3:57:30
|===

A `410 Gone` response is treated as permanent — no further attempts, and the endpoint is deactivated
immediately (see below). After all 6 attempts fail, the delivery is abandoned AND the whole webhook
endpoint is deactivated (`active: false`) — every BOARD/ADMIN member is notified by e-mail, and the
endpoint stays deactivated until an operator reviews and reactivates it in the UI.

=== URL requirements

The configured URL must be `https://` (no `http://` unless the OPERATOR of this server instance has
explicitly opted into an insecure development mode — never something a webhook consumer can control),
must resolve to a publicly routable address (no loopback/private/link-local/reserved range — the same
class of restriction any outbound-webhook feature needs to guard against SSRF), and must be at most
2048 characters. Rejected for any other reason returns one of four fixed, non-leaking messages — never
an IP address, resolved hostname, or DNS detail.

=== Retention

Delivery history (`listWebhookDeliveries`) is retained for 30 days after reaching a terminal state
(`DELIVERED`/`ABANDONED`), then deleted automatically. A delivery still `PENDING`/being retried is
never deleted regardless of age.

=== Operating assumption

Exactly one server instance is assumed to run the delivery poller. Delivery itself is safe under
multiple instances (each attempt is claimed atomically), but the deactivation-notification e-mail and
the retention sweep are not additionally guarded against running twice — see the poller's own KDoc if
this server is ever operated in a multi-instance configuration.

[[scope]]
== Out of scope (this wave)

Deliberately not implemented — see `CHANGELOG.md`: any write endpoint on the `/api/v1` REST surface
itself, OAuth2/OIDC/JWT/scopes, multi-tenancy, distributed (cross-instance) rate limiting,
OpenAPI/Swagger generation, ETag/conditional-request caching, CORS, field selection, sorting,
full-text search, cursor-based pagination, bulk endpoints, key-hash encryption at rest, automatic key
rotation/expiry reminder mail/cleanup, the RFC 9457 `application/problem+json` error format (this
API's flat `{"error","message"}` body is used instead throughout), a webhook "entity removed" event
(see the Webhooks section above), multi-instance-safe deactivation notification/retention, and a
dual-secret grace window during webhook signing-secret rotation.
