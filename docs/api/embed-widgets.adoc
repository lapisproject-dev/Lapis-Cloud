== No-JS fallback contract

Every widget host element carries a working, plain `<a>` link BEFORE the widget script ever runs.
If `lapis-widgets.js` never loads (JavaScript disabled, the script blocked, or this visitor's
origin not yet allowlisted), the operator's own fallback link stays exactly as they wrote it and
keeps working. The widget script only ever *replaces* that content on a successful hydration — it
never removes it as a first step and then fails to add anything back.

== Overview

Welle V1.4.1a lets a partner website (a party's or association's own site, hosted on a *different*
origin than this server) embed four small widgets:

* `data-lapis-widget="login"` — a button that opens a popup window for member login, using
  `postMessage` to report the outcome back to the embedding page without ever sharing a session
  cookie across the origin boundary.
* `data-lapis-widget="join"` — a plain link to this server's own `/app#/register` screen.
* `data-lapis-widget="donate"` — a one-field, anonymous donation form (Welle V1.4.1b, see
  <<anonymous-donation-widget>>).
* `data-lapis-widget="event"` — a name+email registration form for one specific, PUBLIC event
  (Welle V1.4.3.3, see <<event-registration-widget>>).

All four are opt-in, `LAPIS_EMBED_ENABLED=false` by default (see <<environment-variables>>).

== Embedding snippet

[source,html]
----
<script src="https://<lapis-host>/embed/v1/lapis-widgets.js" async></script>

<div data-lapis-widget="login">
  <a href="https://<lapis-host>/app#/login">Anmelden</a>
</div>

<div data-lapis-widget="join">
  <a href="https://<lapis-host>/app#/register">Mitglied werden</a>
</div>

<div data-lapis-widget="donate" data-lapis-fallback-url="">
  <a href="https://<lapis-host>/app#/donate">Spenden</a>
</div>

<div data-lapis-widget="event" data-lapis-event-slug="ihre-veranstaltung">
  <a href="https://<lapis-host>/veranstaltung/ihre-veranstaltung">Zur Anmeldung</a>
</div>
----

NOTE: Welle V1.4.6 "Öffentliche Startseite" moved the member SPA from `/` to `/app` — the fallback
links above changed accordingly. If you embedded this snippet before that release, re-copy it: the
old `/#/...` links now land on the new public landing page at `/` instead of the SPA, and lose their
hash fragment there.

`data-lapis-fallback-url` (optional, on the `donate` host only) is a link the widget offers as
"Andere Wege" when the checkout endpoint is rate-limited, over the amount ceiling, or unavailable —
see <<anonymous-donation-widget>>. `data-lapis-amounts` (optional, comma-separated) overrides the
four preset amounts (default `10,25,50,100`); an unparsable list falls back to the default
silently. Presets above the effective ceiling (the lower of `LAPIS_PSP_MAX_CHECKOUT_AMOUNT_EUR` and
this widget's own 500&#160;€ cap, see <<anonymous-donation-widget>>) are silently dropped -- if that
removes every preset (custom or default), the widget falls back to a single button at the
floor (5&#160;€ by default).

`data-lapis-event-slug` (required, on the `event` host only) is the *only* attribute the event
widget reads — it must be replaced with the target event's real slug. Leaving the placeholder
`"ihre-veranstaltung"` in place (or omitting the attribute) is not silently wrong: the widget logs
a `console.error` and never mounts, so the No-JS fallback link above stays visible instead of an
empty box. There is no `data-lapis-fallback-url` on this host — the widget derives its own
fallback link from `data-lapis-event-slug` itself, see <<event-registration-widget>>.

The exact snippet, pre-filled with this deployment's real `LAPIS_PUBLIC_BASE_URL`, is shown
read-only on the ADMIN-only *Website-Integration* screen
(`network.lapis.cloud.client.EmbedIntegrationScreen`), with a "Kopieren" button.

== Environment variables

[cols="1,3"]
|===
|Variable |Meaning

|`LAPIS_EMBED_ENABLED`
|`true` to serve the `/embed/v1/*` and `/api/embed/v1/*` routes at all. Default: disabled (every
route under those two prefixes then 404s, same as if this welle did not exist) -- with the single
exception of the ADMIN-gated `GET /api/embed/v1/admin/status`, which stays registered so the admin
screen can report an honest `enabled: false` instead of a 404 indistinguishable from a server error.

|`LAPIS_EMBED_ALLOWED_ORIGINS`
|Comma-separated list of exact `scheme://host[:port]` origins allowed to embed the widgets and
complete a popup login. Required, non-empty, and every entry must canonicalize successfully when
`LAPIS_EMBED_ENABLED=true` — an invalid or missing value fails the server start (see
`network.lapis.cloud.server.embed.EmbedConfig` KDoc). `www.` and the bare domain are *different*
origins — list both if both are used.

|`LAPIS_EMBED_ALLOW_INSECURE`
|Set to exactly `true` to also accept `http://` origins (local development only). Any other value,
including `false`, still logs a WARN if the variable is set at all — the safe default is to *omit*
it entirely, never to set it to `false` (see `WebhookConfig` KDoc "O4", the same doctrine this
variable follows).
|===

CAUTION: The origins in `LAPIS_EMBED_ALLOWED_ORIGINS` are **publicly visible** in the downloadable
`lapis-widgets.js` bundle — the client-side origin check the widget performs needs to see them to
decide whether to render at all. This is not a secret leak in the ordinary sense (the partner sites
are public by nature), but do not put an internal/staging origin in this list expecting it to stay
unlisted.

== CORS and CSP contract

`/api/embed/v1/session` (and its `OPTIONS` preflight) is the only endpoint that carries CORS
headers, and only for an `Origin` on the allowlist — `Access-Control-Allow-Origin` is always the
*canonical* allowlist entry, never the raw request value and never `*`, and
`Access-Control-Allow-Credentials` is never sent from anywhere in this welle's code. The popup
login page (`GET /embed/v1/login`) carries its own, separate Content-Security-Policy:

----
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self';
    connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
----

`script-src 'self'` is sufficient without a per-response nonce because `/embed/v1/login.js` is a
*constant* file — every value the page needs (the login `state`, the target origin, whether the
visitor is already signed in, their display name) travels through `data-*` attributes, never
interpolated into the script text itself.

== Popup login flow

[kuml, embed-login-flow, svg]
----
sequenceDiagram(name = "Embed-Widget Login-Flow (V1.4.1a)") {
    val partnerPage = participant(name = "Partner-Seite (fremde Origin)")
    val widget = participant(name = "lapis-widgets.js")
    val popup = participant(name = "Popup-Fenster (/embed/v1/login)")
    val server = participant(name = "Lapis Cloud Server")

    message(from = partnerPage, to = widget, text = "Klick auf \"Anmelden\"")
    message(from = widget, to = popup, text = "window.open(/embed/v1/login?state=<nonce>&origin=<HERE>)")
    message(from = popup, to = server, text = "GET /embed/v1/login?state&origin")
    message(from = server, to = popup, text = "200 Formular (Origin erlaubt) oder 403 (nicht erlaubt); signedIn immer false -- Cookie kommt bei dieser cross-site Top-Level-Navigation nie an")
    message(from = popup, to = server, text = "fetch /api/embed/v1/session (same-origin, credentials: same-origin)")
    message(from = server, to = popup, text = "200 {signedIn, displayName} -- ehrlich, weil dieser Aufruf same-site ist")
    message(from = popup, to = server, text = "[falls signedIn:false] POST /api/auth/login (same-origin, credentials: include)")
    message(from = server, to = popup, text = "200 + Set-Cookie: lapis_session (HttpOnly, Secure, SameSite=Strict)")
    message(from = popup, to = widget, text = "window.opener.postMessage({source:'lapis-embed', state, ok:true, displayName}, targetOrigin)")
    message(from = widget, to = partnerPage, text = "Zustand \"signed-in\" -- kein Cookie/Token verlässt die Lapis-Origin")
    message(from = popup, to = popup, text = "window.close() nach 800ms")
}
----

The session cookie never crosses the origin boundary — only the `postMessage` payload does, and
that payload carries no bearer credential at all (just `ok`/`displayName`). The partner page's own
origin never gains the ability to call any authenticated Lapis Cloud endpoint directly; every
subsequent authenticated action still happens on this server's own origin (e.g. via the
"Zum Mitgliederbereich →" link the widget shows after a successful login).

== Known, deliberate limitation

There is no "already signed in" indicator on the *partner page* on load without a click — the
widget (`lapis-widgets.js`) never calls `GET /api/embed/v1/session` itself. An automatic status
check on every page load, for every visitor, would be exactly the cross-site tracking channel this
welle is designed to avoid.

**Why the popup needs an extra round-trip instead of the server just rendering the right state
straight away:** `GET /embed/v1/login` is opened via `window.open()` *from the partner origin*,
which makes it a cross-site top-level navigation. The `lapis_session` cookie is `SameSite=Strict`
(see `AuthRoutes.kt` KDoc "Cookie transport" — this codebase's only CSRF control), and
`SameSite=Strict` cookies are — unlike `Lax` — never attached to a cross-site top-level navigation.
The server-rendered popup page therefore always starts out as `signedIn: false`, regardless of
whether the visitor actually has a session. `/embed/v1/login.js` (`EmbedAssets.loginPopupJs`)
compensates for this once the popup document has actually loaded on the Lapis origin: it keeps the
login form hidden, shows a "Anmeldung wird geprüft …" status text, and issues its own
`fetch("/api/embed/v1/session", {credentials: "same-origin"})` — a request from the Lapis origin
*to* the Lapis origin, which is same-site regardless of `SameSite=Strict` and therefore does carry
the cookie. If that probe reports `signedIn: true`, the popup skips the login form entirely and
closes itself the same way a fresh login would; otherwise the form is revealed and behaves exactly
as before. A three-second timeout (`SESSION_PROBE_TIMEOUT_MS`) guards against a hanging or very
slow probe: if no response has arrived by then, the status text clears and the login form is
revealed anyway, so the popup never sits blank with no form and no feedback. Should the probe
still resolve after that fallback already fired, its result is discarded — the form is already
shown at that point. This never widens the tracking-channel concern above: the probe only ever
fires after an explicit click already opened the popup on the Lapis origin, never from the partner
page itself.

On mobile browsers that open the popup as a new tab rather than a real popup window,
`window.opener` can be `null` — the popup then shows "Angemeldet. Sie können dieses Fenster
schließen." instead of auto-closing, since it has no opener to notify and no promise that the
originating tab is even still open.

Welle V1.4.3.3: after a successful Stripe payment for a paid event, the visitor is returned to
`\{lapis-host}/veranstaltung/{slug}/danke` — the Lapis host itself, *not* back to the partner page
that embedded the widget (see `StripeReturnUrls.eventRegistration`). Fixing this would require
threading the embedding page's own origin through the Stripe checkout session, touching
`EventRegistrationSubmission`/`StripeReturnUrls` — deliberately out of scope for this wave. Also
deliberately deferred: the snippet above carries a placeholder slug (`"ihre-veranstaltung"`) that
must be hand-edited per event; a one-click "copy snippet" button on the event's own admin record
(pre-filled with the real slug) is a documented follow-up wave, not built here.

[[anonymous-donation-widget]]
== Spenden-Widget (anonymous donation, Welle V1.4.1b)

`data-lapis-widget="donate"` renders a single-field form — an amount, nothing else. No category
choice, no purpose field, no email, no name. Clicking "Jetzt spenden" calls
`POST /api/embed/v1/donation/checkout` and, on success, does a full top-level redirect
(`window.location.assign`, never a popup — unlike the login widget, no credential crosses an
origin boundary here, and a popup does not survive Stripe's own redirects reliably on mobile
payment methods) to the Stripe-hosted checkout page.

=== Amount range

*5–500 EUR inclusive.* The ceiling is deliberately set to the SAME figure as
`network.lapis.cloud.server.rpc.PartyDonationComplianceCalculator.ANONYMOUS_FORWARDING_THRESHOLD_EUR`
(currently the current best understanding of the §25 PartG anonymous-donation-forwarding
threshold, itself an unverified starting point — see that class's own KDoc disclaimer) — a widget
donation is designed to never trigger the duty to forward an anonymous donation to the Bundestag
administration. This applies to every deployment, political party or not, for product simplicity.
The floor exists purely as an abuse-economics guard (card testing runs at cent/one-euro amounts),
not a legal requirement. A deployment's own `LAPIS_PSP_MAX_CHECKOUT_AMOUNT_EUR` can only LOWER the
effective ceiling, never raise it above 500 EUR.

=== `POST /api/embed/v1/donation/checkout`

CORS-gated exactly like the rest of this welle's endpoints, with ONE deliberate deviation: a
request with NO `Origin` header at all is *also* rejected (`403`), unlike
`/api/embed/v1/session` — this endpoint moves money and has no legitimate same-origin caller.

Request body (`application/json`, at most 2048 bytes):

[source,json]
----
{"amount": "25.00", "kommentar": ""}
----

`amount` travels as a *string*, never a JSON number (this codebase never represents money as a
floating-point type). `kommentar` is a honeypot — a hidden field a real donor never sees or fills;
a bot that fills every field in a scraped, RENDERED form does. A non-blank `kommentar` is treated
identically to a real cancellation (see below), never reported back as detected. Scope note: this
only catches a bot that renders and fills the widget's HTML — a bot calling this JSON endpoint
directly (the realistic case, since the endpoint and its shape are documented right here) never
sends `kommentar` at all and passes trivially. The actual defense against that case is the rate
limit below plus the CORS origin allowlist, not the honeypot.

Rate limit: *two separate budgets* (fix, review finding, so a client mistake or an abandoned
checkout can never lock a legitimate donor out of a real attempt). A generous admission limit (20
per hour per source IP) is checked first, before the body is even JSON-decoded, and rejects a flood
of malformed/garbage requests cheaply. The strict *3 requests per hour per source IP* budget — the
tightest limiter in this codebase, because this is the only unauthenticated endpoint anywhere in it
that triggers a real outbound Stripe API call and two database writes on a stranger's say-so — is
checked separately, immediately before the actual Stripe call: a honeypot hit, an unusable gateway,
an out-of-range amount, or a §25 PartG rejection never consumes it. A `CORS` preflight (`OPTIONS`)
is throttled separately again (60/minute) so a browser's own preflight request never eats into
either budget.

[cols="1,2"]
|===
|Response |Meaning

|`200 {"redirectUrl": "..."}`
|Success, or the honeypot was filled — both cases return this exact shape and redirect to a real
page (the honeypot case redirects to the *cancelled* page below), so the response itself is never
an oracle telling a bot it was detected.

|`400 {"error":"BAD_REQUEST"}`
|Malformed JSON body, or a non-numeric `amount`.

|`400 {"error":"AMOUNT_OUT_OF_RANGE","minAmount":"5.00","maxAmount":"..."}`
|More than 2 fractional digits, or outside the 5–500 EUR range (the effective ceiling, which may be
lower than 500, is echoed back so the widget can show the real number instead of an assumed one).

|`413`
|Body exceeds the 2048-byte cap (checked before the body is even read, or while streaming it in) —
no JSON body at all, just the status.

|`429 {"error":"RATE_LIMITED","retryAfterSeconds":N}`
|Either rate limit exceeded (see above); also carries a `Retry-After` header.

|`503 {"error":"UNAVAILABLE"}`
|The payment gateway is not usable (disabled, unconfigured, or the compliance disclaimer is stale)
— deliberately never says WHICH condition is missing.

|`409 {"error":"NOT_ACCEPTED"}`
|A §25 PartG verdict rejected the donation. The reason is logged server-side only, never returned.

|`502 {"error":"GATEWAY_ERROR"}`
|Stripe itself rejected or could not be reached. Stripe's own error text is logged server-side only.
|===

=== Return pages

`GET /embed/v1/spende/danke` and `GET /embed/v1/spende/abgebrochen` are the `success_url`/
`cancel_url` Stripe redirects the donor's browser to — two fixed, public paths, deliberately
carrying NO session identifier (no new token/polling surface). Both accept an optional
`?origin=` query parameter (the ORIGIN the widget was embedded on, so the page can offer a link
back); an unknown or missing value renders the page WITHOUT a return link, still at `HTTP 200` —
never an error status, because the visitor has just paid, or just cancelled, and that is the worst
possible moment for this product to fail loudly.

The thank-you page deliberately does not say "gebucht" — the webhook that actually posts the
donation to the ledger arrives asynchronously, after the redirect, so the server does not yet know
at that point whether it succeeded.

=== DSGVO / what is stored

An anonymous widget donation creates exactly one `external_donor` row (`display_name = "Online-
Spende ohne Namensangabe"`, `donor_category = ANONYMOUS`, every address field `NULL`) per donation
— there is no donor de-duplication or recognition across donations by design (DSGVO data
minimization). Neither the widget, the checkout endpoint, nor the return pages ever collect or
store a name or an email address; Stripe handles the payment method and any payment confirmation
email entirely on its own side.

[[event-registration-widget]]
== Anmeldungs-Widget (event registration, Welle V1.4.3.3)

`data-lapis-widget="event"` renders a two-field form — name and email — for exactly one, specific
`PUBLIC` event, identified by `data-lapis-event-slug`. It is the JSON/widget counterpart of the
server-rendered `<form method=post>` at `/veranstaltung/{slug}` — same fachlogik
(`EventRegistrationSubmission`), same honeypot, same abuse-protection layers, different transport.

=== `POST /api/embed/v1/event/{slug}/registration`

CORS-gated exactly like the rest of this welle's endpoints, with the SAME deliberate deviation the
donation checkout already establishes: a request with NO `Origin` header at all is *also* rejected
(`403`) — this endpoint has no legitimate same-origin caller either. `Content-Type: application/json`
is *required* (`415` otherwise) — unlike the donation checkout route, which has no such check (a
documented gap there, not a convention this route repeats). Requiring it here has a useful side
effect: a non-`GET`/non-simple `Content-Type` always triggers a browser CORS preflight first, so a
successful `POST` past this check is proof the Origin gate already ran.

Request body (`application/json`, at most 4096 bytes):

[source,json]
----
{"guestName": "Anna Beispiel", "guestEmail": "anna@example.org", "kommentar": ""}
----

`kommentar` is the SAME honeypot field the server-rendered form's `params["kommentar"]` already
uses — a hidden field a real registrant never sees or fills. A non-blank `kommentar` returns the
identical `200 {"outcome":"CONFIRMED"}` a genuine confirmed registration would, with no database
write and nothing logged, and is checked *before* the slug is even resolved: a bot gets the same
`200` regardless of which slug it guessed, while an honest caller with a genuinely unknown slug
gets `404`.

Rate limit: the SAME two budgets `/veranstaltung/{slug}/anmeldung` already uses — a generous
admission limit (30 per hour per source IP), checked before the JSON body is even decoded, and the
strict *5 registrations per hour per source IP* budget, checked immediately before the database/
Stripe work. Both are the SAME `FederationInboxRateLimiter` *instances* the form route uses (see
`Application.kt`), a deliberate shared budget — the widget cannot be used to grant a caller a
second, independent 5/60min allowance the form route doesn't already cap them to. The honeypot hit
consumes neither budget beyond the generous one. `OPTIONS` (the CORS preflight) runs against a
third, separate, soft 60/minute budget so a browser's own preflight before every real `POST` never
eats into either registration budget.

[cols="1,2"]
|===
|Response |Meaning

|`200 {"outcome":"CONFIRMED"}`
|A brand-new confirmed registration (free event, or a paid event's registration where — structurally
impossible today, but see the fachlogik — no payment step is needed), an ALREADY-registered guest
(same email, second attempt), or the honeypot was tripped.
+
**The byte-identical body only holds across all three cases for a fee-free event
(`feeAmount == 0`).** On a *paid* event, an ALREADY-registered guest still gets this exact
`{"outcome":"CONFIRMED"}` body, but a brand-new registration instead gets
`200 {"outcome":"PAYMENT_REQUIRED","redirectUrl":"..."}` (see below) — the two cases are
distinguishable on the wire. Deliberately still no *literal* "you are already registered" message
(no enumeration oracle in those exact words, and a detected bot never learns it was detected), but
an unauthenticated caller who already knows (or can send from) an allowlisted partner origin can
probe a specific, known e-mail address against a paid event and infer from `CONFIRMED` vs.
`PAYMENT_REQUIRED` whether that address is already registered — capped, but not prevented, by the
strict 5-attempts/60min `registrationRateLimiter` per source IP. The same distinguishability
already exists, unchanged, on the server-rendered `/veranstaltung/{slug}/anmeldung` form route (not
a regression of this widget) — closing it for both routes (e.g. by also returning a payment-resume
redirect for an ALREADY-registered guest on a paid event) is tracked as follow-up work, not yet
implemented.

|`200 {"outcome":"WAITLISTED"}`
|The event is full; the guest joined the waitlist. No waitlist position is ever returned.

|`200 {"outcome":"PAYMENT_REQUIRED","redirectUrl":"..."}`
|A paid event placed the guest in a `PENDING_PAYMENT` seat; `redirectUrl` is the Stripe-hosted
checkout page the widget redirects the browser to (`window.location.assign`, full top-level
navigation, same reasoning the donation widget's own redirect already documents).

|`400 {"outcome":"BAD_REQUEST"}`
|Malformed JSON, a blank/oversized `guestName` (over 300 characters), or a missing/oversized
`guestEmail` (over 320 characters). `EventPolicy.normalizeGuestEmail` trims and lowercases but does
not check the address for a valid email *shape* (no `@`/domain check) — same scope-cut
`CrmContactPolicy.normalizeEmail` already documents for CRM contacts. The widget's own client-side
check (`email.indexOf("@") <= 0`) and the `<input type="email">` field are the only format guard; a
direct API caller can submit an address with no `@` at all and receive `200 CONFIRMED`.

|`404 {"outcome":"NOT_AVAILABLE"}`
|The slug does not resolve to a `PUBLIC` event at all — covers an unknown slug, `DRAFT`,
`CANCELLED`, and `MEMBERS_ONLY` events uniformly. No existence oracle for an anonymous caller.

|`409 {"outcome":"WAITLIST_FULL"}`
|The event's waitlist is already at its cap (`EventPolicy.MAX_WAITLIST`, 500 entries).

|`413`
|Body exceeds the 4096-byte cap (checked before the body is even read, or while streaming it in) —
no JSON body at all, just the status.

|`415`
|`Content-Type` was not `application/json` — no JSON body, just the status.

|`429 {"outcome":"RATE_LIMITED","retryAfterSeconds":N}`
|Either rate limit exceeded (see above); also carries a `Retry-After` header.

|`503 {"outcome":"UNAVAILABLE"}`
|The event has a fee and the payment gateway is not usable (disabled, unconfigured, or the
compliance disclaimer is stale) — deliberately never says WHICH condition is missing. Also the
generic fallback for an unhandled server-side exception (`500` never leaves this endpoint's own
JSON envelope).

|`502 {"outcome":"GATEWAY_ERROR"}`
|Stripe itself rejected or could not be reached. Stripe's own error text is logged server-side only.
|===

Why `outcome` and not the donation checkout's `error` field: the donation contract is already
published and frozen, and retrofitting it would be a breaking change for any code already
integrating against it. A waitlisted registration is not an error either — a single discriminator
that is present in *every* response body, including `400`/`429`, reads more honestly than
overloading a field named `error` with a non-error value.

=== DSGVO / what is stored

Exactly what the server-rendered form already stores: the guest's name and email, nothing more.
The widget itself sets no cookie, uses no browser storage on the partner origin, and sends
`credentials: "omit"` on every request — no session/credential of any kind ever crosses the origin
boundary in either direction.

== Scope of this wave

Welle V1.4.1a shipped the login/join widgets and the read-only admin status screen. Welle V1.4.1b
added the anonymous donation widget, on the SAME `EmbedConfig`/`EmbedCors`/`EmbedAssets`
infrastructure — no new environment variable was needed (see <<environment-variables>>). Welle
V1.4.3.3 adds the event-registration widget above, on the SAME infrastructure again — still no new
